### What is the fundamental shift in Functional Design Patterns?
<details><summary>Show answer</summary>

Traditional OOP patterns were often structural workarounds. Because early Java couldn't pass behavior directly, you had
to wrap that behavior inside an object (using interfaces, abstract classes, and wrappers) just to move it around.

FP shifts the focus by treating functions as first-class citizens. When behavior can be passed directly, patterns built
on a one-method interface (Java's *functional interface*) change shape:

- Selection (Factory): Moves from control flow (`switch`) to Data (a `Map` of constructors).
- Swapping (Strategy): Moves from class hierarchies to Parameters (passing a lambda).
- Wrapping (Decorator): Moves from nested objects to Composition (`.andThen()`).

Only patterns that were a one-method interface change this way. Patterns with several methods or with state kept
across calls (Abstract Factory, Visitor, Builder) keep their classes.

The Takeaway: Functional programming doesn’t necessarily invent new design patterns; it removes the structural overhead
from the ones built on a one-method interface. You stop building object scaffolding and start passing behavior directly.

</details>

### Factory pattern — functional approach?
<details><summary>Show answer</summary>

In traditional OOP, a factory relies on structural workarounds—like a `switch` statement or creating dedicated factory
classes—to decide which object to instantiate.

Because FP treats functions as first-class citizens, you can pass constructors around just like data. The entire
pattern collapses into a simple `Map` linking a "type tag" to a functional interface (like a `Function` or `Supplier`).

OOP Way (The Switch):

```java
public Payment create(String type, int amount) {
    return switch (type) {
        case "CARD" -> new CardPayment(amount);
        case "CASH" -> new CashPayment(amount);
        default -> throw new IllegalArgumentException();
    };
}
```

FP Way (Map of Functions):

```java
// Map a type tag directly to a constructor reference
Map<String, Function<Integer, Payment>> FACTORY = Map.of(
    "CARD", CardPayment::new,
    "CASH", CashPayment::new
);

public Payment create(String type, int amount) {
    // Look up the function, then apply the constructor parameter
    return FACTORY.get(type).apply(amount); 
}
```

The Takeaway: No new pattern here. The factory's job stays the same; only the choice moved from code (a `switch`)
into data (a `Map` of constructor references).

</details>

### Decorator pattern — functional approach?
<details><summary>Show answer</summary>

In traditional OOP, decorating an object requires creating wrapper classes that implement the same interface and
delegate calls to the wrapped instance.

Because FP treats functions as first-class citizens, you don't need wrapper classes. The Decorator pattern is simply
function composition. You can chain behaviors directly using `.andThen()`.

OOP Way (Wrapper Classes):

```java
class MilkDecorator implements Coffee {
    private Coffee delegate;
    public MilkDecorator(Coffee delegate) { this.delegate = delegate; }
    
    public String getIngredients() { 
        return delegate.getIngredients() + ", Milk"; 
    }
}
// Usage: new MilkDecorator(new VanillaDecorator(new BlackCoffee()));
```

FP Way (Function Composition):

```java
Function<String, String> addMilk = coffee -> coffee + ", Milk";
Function<String, String> addVanilla = coffee -> coffee + ", Vanilla";

// Usage: Chain the behaviors directly
Function<String, String> customOrder = addVanilla.andThen(addMilk);
customOrder.apply("Black Coffee"); 
```

The Takeaway: The decorator is still there: same wrapping, same stacking. What changed: each decorator class is now a
function, and nesting constructors becomes a chain of `andThen`.

</details>





### Strategy pattern — functional approach?
<details><summary>Show answer</summary>

In traditional OOP, you define an interface and create a separate class for every algorithm you want to swap out.

Because FP treats functions as first-class citizens, an algorithm is just a behavior you can pass directly. The Strategy
pattern collapses from an entire class hierarchy into a single method parameter (like a `Function` or `UnaryOperator`).

OOP Way (Interfaces and Classes):

```java
interface Discount {
    double apply(double price);
}
class HalfPrice implements Discount {
    public double apply(double price) { return price * 0.5; }
}

// Usage: checkout(100.0, new HalfPrice());
```

FP Way (Passing a Function):

```java
public double checkout(double price, DoubleUnaryOperator discountStrategy) {
    return discountStrategy.applyAsDouble(price);
}

// Usage: Pass the algorithm directly as a lambda
checkout(100.0, price -> price * 0.5); 

// Or pass a method reference
checkout(100.0, Discounts::holidaySale);
```

The Takeaway: No interface hierarchy is needed. The strategy's job stays the same (swapping algorithms at runtime), 
but the mechanism changes from passing an object that contains a method to simply passing the method itself.

</details>

### How to combine OOP and FP at the architectural level?
<details><summary>Show answer</summary>

The functional core, imperative shell (FC/IS) approach — an architectural pattern that isolates side effects from
business logic to maximize testability.

* Functional Core: Contains all complex business logic. Written with pure functions (no side effects, no I/O,
  data-in/data-out). Highly testable without mocks.
* Imperative Shell: The outer layer that handles all side effects (DB, network, UI). It fetches data, passes it to
  the pure core, and writes the results back out. It contains minimal logic and focuses on orchestration.

The Takeaway: Push I/O to the edges (the shell) so your complex logic (the core) remains pure and trivially easy to
unit test.

</details>
