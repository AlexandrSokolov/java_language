### When is a language considered functional?
<details><summary>Show answer</summary>

When there's a way to express computations by creating and combining abstract functions.

</details>

### Programming style — OOP vs FP?
<details><summary>Show answer</summary>

**Imperative (typical OOP):** you write a series of [statements](#what-is-a-statement) 
telling the computer *what to do* — a step-by-step sequence to reach the result.


**Declarative (functional):** you describe *the outcome* — 
how your program should work with [expressions](#what-is-an-expression), 
not what it should do with [statements](#what-is-a-statement).

</details>

### What is an expression?
<details><summary>Show answer</summary>

A sequence of operators, operands, and method calls that defines a computation and evaluates to a single value.

```java
x * x
2 * Math.PI * radius
value == null ? true : false
```

The mark of an expression: it returns a value.

</details>

### What is a statement?
<details><summary>Show answer</summary>

An action your code takes to form a complete unit of execution — including method calls that return nothing.
You are using a statement any time you assign or change a variable, call a void method, or use control-flow like
if-else. They are usually mixed in with expressions.

```java
int totalTreasure = 0;
int newTreasuresFound = findTreasure(6);
totalTreasure = totalTreasure + newTreasuresFound;
if (totalTreasure > 10) {
  System.out.println("You have a lot of treasure!");
} else {
  System.out.println("You should look for more treasure!");
}
```

The mark of a statement: it returns no value.

</details>

### What makes a function pure?
<details><summary>Show answer</summary>

Two guarantees:

- The same input always creates the same output — the return value depends solely on its input arguments.
  Broken by a **side cause**.
- It is self-contained, without any side effect — it changes nothing outside itself.

</details>

### What does side effect mean?
<details><summary>Show answer</summary>

A pure function has two separate guarantees, and each is broken by a different thing:

- **Same input, same output** — the return value depends only on the arguments. Broken by a **side cause**.
- **No side effect** — it changes nothing outside itself. Broken by a **side effect**.

The two terms name opposite directions:

- **Side cause** — a hidden *input*. The function **reads** outside state it was not given: a DB row, the clock,
  config, a global. The outside world can change between calls, so the same argument can give two answers. This
  breaks the first guarantee, not the second.
- **Side effect** — a hidden *output*. The function **writes** outside state: saves to a DB, updates a global,
  prints. This changes the world. It breaks the second guarantee.

**Reading from an external system that changes the result on top of the input data is NOT a side effect — it is a
side cause.** A side effect is only a write.

Why the confusion exists: the two guarantees must cut on two different axes, or one would be redundant. If reading
counted as a side effect, "no side effect" would already cover "same input, same output," and the first guarantee
would mean nothing. It doesn't — so reads and writes are two different things.

The trap: purely functional languages (Haskell) send both reads and writes through the same `IO` machinery, so
they loosely call **all** outside interaction a "side effect." Some Java book authors copy that loose usage and get
it wrong. In a two-guarantee model, keep them apart: read = side cause, write = side effect.

</details>

### Give an example of an impure function.
<details><summary>Show answer</summary>

```java
public String buildGreeting(String name) {
  var now = LocalTime.now();
  if (now.getHour() < 12) {
    return "Good morning " + name;
  } else {
    return "Hello " + name;
  }
}
```

The same input creates different output: 
the return value depends on `LocalTime.now()`, not solely on its input argument.

</details>

### What is referential transparency?
<details><summary>Show answer</summary>

You can replace a call with its evaluated result, for any further invocations, 
without changing the behavior of your program.

```text
f x = x * x

result = f 5 + f 5
       = 25  + f 5
       = 25  + 25
```

All these variants are equal and won't change your program.

</details>

### What is immutability?
<details><summary>Show answer</summary>

Data structures can no longer change after their initialization.

</details>

### What are the benefits of using immutable classes (related to Java)?
<details><summary>Show answer</summary>

- **Simpler reasoning** — a single, fixed state established at construction; the object never changes under you.
- **Strong invariants** — once the constructor validates them, they hold forever.
- **Inherent thread safety** — no synchronization needed. The most practical payoff in real systems.
- **Safe sharing** — freely reused and shared without defensive copies.
- **Safe in collections** — stable `equals`/`hashCode`, so keys and set members never silently "move."

</details>

### What is recursion?
<details><summary>Show answer</summary>

A problem-solving technique that solves a problem by partially solving problems of the same form and combining
the partial results to solve the original problem.

In plain terms: a recursive function calls itself, with a slight change in its input arguments, 
until it reaches an end condition and returns an actual value.

</details>

### What to keep in mind with recursion?
<details><summary>Show answer</summary>

The repeated function calls can be inefficient and even dangerous — the stack can overflow.

That's why many functional languages to reduce the required stack frames use optimizations like:
- "unrolling" recursion into loops, or 
- tail-call optimization

Java doesn’t support any of these optimization techniques.

</details>

### What does "first-class citizen" mean for functions?
<details><summary>Show answer</summary>

The function observes all the properties inherent to other entities of the language: 
it can be assigned to variables, and used as arguments and return values in other functions and expressions.

</details>

### What is a higher-order function?
<details><summary>Show answer</summary>

A function that uses [first-class citizenship](#what-does-first-class-citizen-mean-for-functions) 
to accept functions as arguments, or return a function as its result, or both.

</details>

### What is a closure?
<details><summary>Show answer</summary>

A lambda that [captures a variable](#what-does-capturing-mean) from the surrounding scope and carries it along, 
so it can use that value later even after the outer method has returned.

</details>

### What does "capturing" mean?
<details><summary>Show answer</summary>

A local variable normally lives only until its block ends — that stretch of code is its **scope**. But a lambda
declared in that scope can mention the variable, and then keep using it *after* the block has returned. Holding
onto an outside variable like that is **capturing** it.

```java
Function<Integer, Integer> closure() {
  var count = new AtomicInteger(0);   // local — would normally die when closure() returns
  return i -> count.addAndGet(i);     // lambda captures count, keeps it alive across calls
}
```

The returned lambda still reads and updates `count` on every call, long after `closure()` finished.

</details>

### What is functional composition?
<details><summary>Show answer</summary>

Pure functions can be combined to create more complex expressions. 
In math terms, two functions `f` and `g` combine into:

```text
h(x) = g(f(x))
```

This way functions can stay as small and on point as possible, and therefore easier to reuse. To build a more
complex, complete task, such functions can be quickly composed as needed.

Composition builds a new function — it does not evaluate anything. `g` does not receive `f`'s result at compose time; 
`f` and `g` run only when the composed function is finally called with an input.

</details>

### What is currying?
<details><summary>Show answer</summary>

Converting a function that takes multiple arguments into a sequence of functions that each take only a single argument.

A function of three arguments can be curried like this:

```text
Initial function:
x = f(a, b, c)

Curried functions:
h = g(a)
i = h(b)
x = i(c)

Sequence of curried functions:
x = g(a)(b)(c)
```

Some functional languages reflect currying in their type definitions, like Haskell.

</details>

### No currying support — how to split arguments?
<details><summary>Show answer</summary>

[Partial function application](#what-is-partial-function-application) — supply a subset of the arguments now and
get back a function waiting for the rest.

It splits the argument-passing into stages, like currying does. 
The difference: a call to a partially applied function returns a **result**, not another function in a currying chain.

</details>

### What is partial function application?
<details><summary>Show answer</summary>

Creating a new function by providing only a subset of the required arguments to an existing one.

```text
add :: Integer -> Integer -> Integer
add x y = x + y

add3 = add 3
add3 5
```

- `add` accepts two arguments.
- Calling `add` with only the first argument `x` returns a partially applied function of type `Integer -> Integer`,
  bound to the name `add3`.
- `add3 5` is equivalent to `add 3 5`.

It lets you create less verbose functions on the fly, or specialized functions from a more generic pool, to match
your code's current context.

</details>

### Currying vs partial application?
<details><summary>Show answer</summary>

Both take a function of many arguments and let you supply arguments in stages.

The difference is what a call returns:

- [Currying](#what-is-currying) — each call takes one argument and returns the **next function** in the chain,
  until the last argument produces the result.
- [Partial application](#what-is-partial-function-application) — you supply a subset of the arguments and get back
  a **result** once enough are given, not another function in a chain.

</details>

### What is lazy evaluation?
<details><summary>Show answer</summary>

An evaluation strategy that delays evaluating an expression until its result is literally needed — separating how
you create an expression from whether or when you actually use it.

</details>

### What're lazy constructs in Java?
<details><summary>Show answer</summary>

```java
//logical short-circuit operators:
if (a || b) { }        // b is not evaluated if a is true
if (a && b) { }        // b is not evaluated if a is false

// control-flow statements such as if-else statements:
if (cond) { doX(); }   // the block runs only if cond holds
else { doY(); }

//or loops:
while (cond) { work(); }  // body runs only while cond holds
```

Short-circuit operators (`||`, `&&`) skip the right side when the left already decides the result. Control-flow
constructs (if-else, loops) run a block only when their condition calls for it.

</details>

### Advantages of functional programming?
<details><summary>Show answer</summary>

- **Simplicity** — no mutable state or side effects → small functions doing just what they should.
- **Safer concurrency** — no shared mutable state → safer parallel processing almost for free.
- **Modularity** — small independent functions → easy reuse; composition and partial application build big from small.
- **Testability** — purity, referential transparency, immutability, separation of concerns → easier to test.

</details>

### Disadvantages of functional programming?
<details><summary>Show answer</summary>

- **Learning curve** — new, unfamiliar terms and concepts, often with intimidating mathematical roots.
- **Higher level of abstraction** — data structures are elegant but often harder to recognize than OOP objects.
- **Dealing with state** — immutability removes bugs, but makes data harder to change when it genuinely must,
  especially if you're used to setters.
- **Performance** — not inherently faster, especially single-threaded; immutability and recursion add overhead
  (FP languages lean on optimizations to offset it).
- **Optimal problem context** — a poor fit for domains needing fine-grained control: 
  high-performance computing, I/O-heavy work, low-level or embedded systems.

</details>
