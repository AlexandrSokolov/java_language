### What limits Java as an FP language?
<details><summary>Show answer</summary>

**Can't enforce FP guarantees** — the compiler checks none of it:
- [purity](#why-cant-java-strictly-enforce-pure-functions) — no `pure` keyword, discipline only.
- [immutability](#what-limits-immutability-in-java) — `final` is shallow, reflection breaks it.
- [functional types](#how-does-javas-design-fragment-functional-types) — matched by name, not shape
  (`Callable` ≠ `Supplier`).

**Missing FP features** — either absent or faked awkwardly:
- [higher-order functions](#higher-order-functions--whats-awkward-in-java) — work, but syntactically noisy.
- [recursion](#why-is-recursion-inherently-risky-in-java-compared-to-other-fp-languages) — no tail-call
  optimization, so deep recursion overflows.
- [closures](#whats-the-limitation-of-java-closures) — capture a copy, so captured vars must be effectively final.
- [laziness](#whats-the-limitation-of-laziness-in-java) — none for ordinary values; only inside APIs like Streams.
- [currying](#whats-javas-limitation-with-currying) — no built-in support; type erasure blocks a clean fake.

**Type system & collections** — [structurally hostile to FP](#what-limits-functional-style-with-javas-type-system-and-collections):
no common root for primitives (autoboxing), `void` methods, mutable-by-default collections.

Trigger: Java can't *enforce* FP (purity, immutability, types), *lacks* FP *features* (TCO, laziness, currying,
real closures), and its *type system* fights it — all frozen by backward compatibility.

</details>

### Why can't Java strictly enforce pure functions?
<details><summary>Show answer</summary>

Java has no `pure` keyword and no compiler checks to prevent mutating outside state. To guarantee purity, 
you technically have to ensure the method generates no state-altering JVM bytecode (like `putfield` or `putstatic`).
Because the language provides no guardrails, enforcing pure functions relies entirely on strict developer discipline.

</details>

### How does Java's design fragment functional types?
<details><summary>Show answer</summary>

Java maps lambdas to specific named interfaces, not to universal function shapes. 
Because it matches types by *name*, not by shape, 
two interfaces with the exact same functional shape are still incompatible. 
For example, `Callable<T>` and `Supplier<T>` both take no arguments and return a value, 
but they are distinct named types — you cannot pass a `Callable` to a method expecting a `Supplier`. 
(They also carry different intent: `Callable` implies real work, `Supplier` maybe a cached value.)

</details>

### What limits immutability in Java?
<details><summary>Show answer</summary>

Java's data model is fundamentally mutable, and its protections are bypassed two ways:

- **Shallow `final`** — `final` freezes the reference, not the data. If a `final` field points to a mutable object
  (like a standard `List`), your state is still mutable. Deep immutability means manually checking every reference
  in the object graph.
- **Reflection backdoor** — subsystems like Reflection can override `final` fields at runtime 
  (e.g. via `setAccessible(true)`), breaking the guarantee entirely.

</details>

### Higher-order functions — what's awkward in Java?
<details><summary>Show answer</summary>

Not capability — Java does them fine — but **syntactic noise**. A function returning a function needs a nested
`Function<..., Function<...>>` type that's hard to read, and before lambdas (Java 8) the same thing meant nested
anonymous classes that buried the structure completely.

```java
// concise (Java 8+): reads as prefix -> (s -> ...)
Function<String, Function<String, String>> prefixer = prefix -> s -> prefix + ": " + s;

// pre-lambda: same logic, structure lost in boilerplate
new Function<String, Function<String, String>>() {
  public Function<String, String> apply(String prefix) {
    return new Function<String, String>() {
      public String apply(String s) { return prefix + ": " + s; }
    };
  }
};
```

Tell for a HOF type in Java: a `Function` that has `Function` as one of its type parameters.

</details>

### Why is recursion inherently risky in Java compared to other FP languages?
<details><summary>Show answer</summary>

Java lacks **Tail Call Optimization (TCO)**. In true functional languages, a tail-recursive method (where the
recursive call is the absolute last operation) is automatically optimized by the compiler into a safe, flat `goto` loop. 
`javac` doesn't do this — it translates every recursive call literally, 
adding a new stack frame each time until deep recursion triggers a `StackOverflowError`.

```java
long fact(long i, long acc) {
  if (i == 0) return acc;
  return fact(i - 1, i * acc);   // tail position — could be a loop, but javac keeps the call
}
```

This is a limit of the Java **compiler**, not the JVM: other JVM languages optimize tail calls — 
Kotlin (`tailrec`), Scala (`@tailrec`), Clojure (`recur`).

</details>

### What's the limitation of Java closures?
<details><summary>Show answer</summary>

Java captures a **copy of the value** (the bit pattern), not the variable itself — the compiler passes it into
the lambda as a hidden parameter. Consequences:

- **No shared environment** — Java is strictly pass-by-value, and the JVM has no symbol table to share a local
  variable across scopes; only values on the stack and objects on the heap.
- **Effectively final** — to stop the lambda's copy from drifting out of sync with the original, Java forces the
  captured variable to be read-only (*effectively final*), so it can't be reassigned after capture.
- **The workaround** — to mutate captured state, capture a `final` reference to a mutable heap object (like
  `AtomicInteger`) and change its contents, rather than the variable directly.

```java
int i = 42;
Function<String, String> f = s -> s + i;   // captures the value 42
// i = 37;                                  // won't compile — captured local can't be reassigned

var j = new AtomicInteger(42);
Function<String, String> g = s -> s + j.get();
j.set(37);                                  // works — same object, new contents
```

Because of this extra indirection, some theorists say Java doesn't have "true" closures.

</details>

### What's the limitation of laziness in Java?
<details><summary>Show answer</summary>

Java lacks first-class support for lazy evaluation for ordinary variables — no built-in way to declare a value
that's computed only when first used. Instead, laziness is opt-in and restricted to specific APIs like Streams.
You explicitly jump into a "lazy realm" (calling `.stream()`) to run lazy intermediate operations like `filter`
and `map`, then jump back out with an eager terminal operation (`.collect()`, `reduce`) to materialize the data.
A few JVM internals are lazy too (e.g. parts of class loading), but for ordinary values there's nothing.

</details>

### Why does Java need a holder class for a stateful generator?
<details><summary>Show answer</summary>

Because of Java's [closure limit](#whats-the-limitation-of-java-closures): captured variables must be effectively
final, and Java has no pass-by-reference. If you use `Stream.generate()` for a stateful sequence (tomorrow, then
the day after…), the lambda can't mutate a simple local to track where it is — so you're forced to build an
external class or mutable wrapper to hold and update the state.

```java
class DaySupplier implements Supplier<LocalDate> {
  private LocalDate current = LocalDate.now().plusDays(1);
  public LocalDate get() {
    var tmp = current;
    current = current.plusDays(1);   // mutate the field — a captured local couldn't be reassigned
    return tmp;
  }
}
Stream.generate(new DaySupplier()::get).limit(10).forEach(System.out::println);
```

In a pass-by-reference language `current` could be a plain local and the whole class would disappear.

</details>

### What's Java's limitation with currying?
<details><summary>Show answer</summary>

No language-level support for **currying** (turning a two-arg function into a chain of one-arg calls) or
**partial application** (fixing one argument now, getting a function that takes the rest). You *can* fake it with
default methods that capture an argument — they're just closures:

```java
default Function<U, R> curryLeft(T t)  { return u -> apply(t, u); }   // fix the first arg
default Function<T, R> curryRight(U u) { return t -> apply(t, u); }   // fix the second arg

Function<LocalDate, String> withCount = bif.curryLeft(42);
```

It's clunky, though. You can't overload a single `curry(T)` / `curry(U)` — **type erasure** would make their
signatures identical at runtime, so you're forced into explicitly named methods like `curryLeft` / `curryRight`.
The language designers deemed that too messy and of limited use, so it was never added to the standard library.

</details>

### What limits functional style with Java's type system and collections?
<details><summary>Show answer</summary>

Three separate problems:

- [**No common root for primitives and objects**](#how-does-javas-non-single-rooted-type-system-limit-collections)
  — you can't write `List<int>`, so everything gets autoboxed.
- [**`void`**](#why-does-the-void-keyword-conflict-with-functional-programming-principles) — a method that returns
  nothing can only act by side effect, the opposite of pure, and blocks "everything is an expression."
- [**Collections assume mutability**](#why-do-javas-collections-fight-functional-style) — `add`/`remove` mutate
  in place, not return new copies.

Trigger: the type system splits primitives from objects (autoboxing), allows nothing-returning methods (`void`),
and bakes mutation into the collection interfaces — none fixable, because backward compatibility freezes them.

</details>

### How does Java's non-single-rooted type system limit collections?
<details><summary>Show answer</summary>

Primitives and objects don't share a common supertype — there's no parent to both `int` and `Object`. So you
can't create true generic primitive collections like `List<int>`; you're forced into object wrappers like
`List<Integer>`, paying the overhead and complexity of autoboxing on every element. The book notes this hurts
collection-generics more than type erasure does — erasure gets the blame, but this split is the deeper cause.

</details>

### Why does the void keyword conflict with FP principles?
<details><summary>Show answer</summary>

A core FP principle is that "everything is an expression" that evaluates to a value. The `void` keyword defines a
method that returns nothing — and if a method returns nothing, the only way it can do useful work is by mutating
state or causing side effects, the exact opposite of a pure function. Its existence also means Java has both
statements and expressions, so "everything is an expression" is impossible.

</details>

### Why do Java's collections fight functional style?
<details><summary>Show answer</summary>

Mutability is baked into the method signatures. Interfaces like `List<E>` define methods like `boolean add(E e)`
that imply in-place mutation; the FP version would return a new copy (`List<E> add(E e)`). Because Java doesn't
separate mutable and immutable collections at the type level, making an immutable list forces ugly runtime hacks —
throwing `UnsupportedOperationException` when someone calls `.add()`. Rather than redesign the interfaces
(backward compatibility forbids it), Java made a clean break and added `Stream` as a new container without the
mutable baggage.

</details>
