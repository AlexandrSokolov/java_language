# Memory Areas

Where the JVM keeps data, and how big an object is.

### What memory areas exist in a Java application?
<details><summary>Show answer</summary>

The Java process takes all its memory from the machine's RAM. The JVM splits it into two kinds:

- **Heap** — objects and arrays; managed by the garbage collector; sized by `-Xmx`.
- **Native memory** — everything else the process takes from RAM; not managed by the GC and not limited by
  `-Xmx`. Two groups:
  - **JVM's own memory** — the JVM allocates it for itself:
    - **Thread stacks** — one per platform thread, each up to `-Xss` (1 MB by default on 64-bit Linux).
    - **Metaspace** — class metadata; cap it with `-XX:MaxMetaspaceSize`.
    - **JVM internals** — JIT code cache, GC tables and other bookkeeping; rarely tuned, but they count too.
  - **Off-heap memory** — the app or its libraries allocate it on purpose for their own data:
    - **Direct memory** — NIO buffers; cap it with `-XX:MaxDirectMemorySize`.
    - **FFM memory segments** (Java 22+) — `Arena` / `MemorySegment`; freed when the `Arena` is closed.

Example: a machine or container with 8 GB RAM running one Java service:

- **Heap** — 4 GB (`-Xmx4g`, half of RAM).
- **Metaspace** — 0.25 GB.
- **Direct memory** — 0.5 GB.
- **Thread stacks** — 0.25 GB (about 250 threads × 1 MB).
- **JVM internals** — 0.5 GB.

The Java process uses 5.5 GB; 2.5 GB stays for the OS, file cache and a safety margin. 
Rule of thumb: heap at 50–75% of RAM — closer to 50% if the app uses many threads or large direct buffers *(unverified)*.

Heap + native memory = the Java process; it must fit in RAM together with the OS.

</details>

### How to split RAM between the heap, native memory and the OS?
<details><summary>Show answer</summary>

For a machine or container that runs one Java service *(rules of thumb, unverified)*:

- **Heap — 50–75% of RAM.** Closer to 75% for a plain service (REST, business logic). Closer to 50% when
  native memory grows: hundreds of threads, heavy NIO, many loaded classes.
- **Native memory — 10–25% of RAM.** Grows with:
  - **Threads** — each platform thread adds a stack up to `-Xss`; hundreds of threads or a large `-Xss`
    add up fast.
  - **Direct memory** — network-heavy NIO libraries (Netty, Kafka clients, gRPC) and NIO file I/O keep large
    buffers off-heap.
  - **Metaspace** — many classes: big frameworks, proxy generation, app servers.
- **Free — 10–20% of RAM.** About 10% in a container (no OS of its own; the host kernel is shared). 15–20% on
  a VM or physical machine: the OS, monitoring and logging agents, file cache.

**The direct-memory trap:** if `-XX:MaxDirectMemorySize` is not set, its limit equals `-Xmx`. With the heap at
75%, direct buffers alone could reach as much again. Set it explicitly when the app uses NIO heavily.

These numbers are a starting point only; measure real native usage with `-XX:NativeMemoryTracking=summary` and
`jcmd <pid> VM.native_memory summary`.

The whole Java process stays at about 80–90% of RAM; the rest keeps the system alive.

</details>

### `-XX:MaxDirectMemorySize` — what to keep in mind?
<details><summary>Show answer</summary>

**The default equals the heap:** if the flag is not set, the direct memory limit equals `-Xmx`.

- **Heap above 50% of RAM** — heap plus default direct limit is already more than 100% of RAM. If the app
  really fills its direct buffers, the process can outgrow the machine or container and get killed by the OS.
- **Setting the heap** — every `-Xmx` change silently moves the direct limit with it.


Set `-XX:MaxDirectMemorySize` explicitly whenever the app uses NIO heavily (Netty, Kafka clients, gRPC), so the
JVM fails with a clear `OutOfMemoryError` before the OS kills the process.

</details>

### Can a Java process use more memory than `-Xmx`?
<details><summary>Show answer</summary>

Yes. `-Xmx` sizes the heap, not the process. The other
[memory areas](#what-memory-areas-exist-in-a-java-application) live in native memory, outside that limit.

</details>

### What if `-Xmx` equals the container limit?
<details><summary>Show answer</summary>

Example: container limit 512 MB, `-Xmx512m`.

- The heap can grow to 512 MB. Thread stacks, metaspace and the other
  [native areas](#what-memory-areas-exist-in-a-java-application) come on top of it.
- The kernel counts the whole process against the container limit, not just the heap.
- If the total passes 512 MB, the kernel kills the process: the container shows `OOMKilled`, exit code 137.
- No `OutOfMemoryError`, no stack trace: the heap was never full, so the JVM saw no problem.

The container limit must fit the whole process, not just the heap.

</details>

### Heap vs thread stack — what goes where?
<details><summary>Show answer</summary>

Objects go on the heap; local variables go on the stack.

- **Heap** — all objects and arrays, even those created inside a method. Shared by all threads.
- **Stack** — one per platform thread, in native memory; one frame per method call, holding its local variables:
  primitive values and references. Private to its thread; freed when the method returns.

`String s = new String("a")` — `s` (the reference) is on the stack, the `String` object is on the heap.

</details>

### What is class metadata and where is it stored?
<details><summary>Show answer</summary>

The JVM's internal record of each loaded class: class structure, method bytecode, constant pools.

- **Java 8+** — in **metaspace**, in native memory (outside the heap). Grows as needed by default; cap it with
  `-XX:MaxMetaspaceSize`.
- **Before Java 8** — in [PermGen](#permgen-vs-metaspace--why-was-permgen-replaced), capped with `-XX:MaxPermSize`.

</details>

### PermGen vs Metaspace — why was PermGen replaced?
<details><summary>Show answer</summary>

Before Java 8, class metadata sat in **PermGen**, a separate area with a fixed maximum size. Main reasons it
was replaced:

- **Fixed size failures** — apps that create many classes (app servers, proxy generation, hot redeploy) hit the
  limit and failed with `OutOfMemoryError: PermGen space`.
- **Hard to size** — the right `-XX:MaxPermSize` depended on the app and was hard to guess; teams kept raising
  it after each failure.

**Metaspace (Java 8+)** moved class metadata to native memory, where it grows as needed — no fixed size to
guess.

</details>

### Metaspace — what to keep in mind?
<details><summary>Show answer</summary>

- **No limit by default** — metaspace grows until native memory runs out. A class loader leak no longer fails
  early: the process grows until the OS or container kills it, with no Java error. Setting
  `-XX:MaxMetaspaceSize` brings back an early, visible `OutOfMemoryError: Metaspace`.
- **Freed only with the class loader** — classes are unloaded only when their whole class loader becomes
  unreachable. One leftover reference (a thread, a static field, a `ThreadLocal`) keeps all its classes in
  memory — the usual cause of leaks on hot redeploy.

Metaspace removed the guessing, not the leaks; cap it in production.

</details>

### Why put memory outside the heap (off-heap memory)?
<details><summary>Show answer</summary>

Off-heap memory is native memory an app (or its library) allocates on purpose for its own data — mostly direct
buffers. Two reasons to do it:

- **Faster I/O** — the GC may move heap objects at any time, so the OS cannot read or write heap data directly;
  I/O first copies it into a temporary native buffer. A direct buffer already lives in native memory, so the OS
  uses it as is — one copy less.
- **No GC cost** — the GC does not scan or move off-heap data, so a multi-gigabyte off-heap cache does not make
  GC pauses longer.

Typical users: Netty, Kafka clients, off-heap caches.

Off-heap = I/O without an extra copy + large data without GC work.

</details>

### How big is `new Object()`?
<details><summary>Show answer</summary>

16 bytes on a typical 64-bit JVM, though it holds no data.

- **Header (12 bytes)** — every object carries one: the JVM's own data about it (class, hash code, GC age,
  lock state).
- **Padding (4 bytes)** — objects are aligned to 8 bytes, so 12 rounds up to 16.

**Compact Object Headers** (Java 25, opt-in with `-XX:+UseCompactObjectHeaders`) shrink the header to 8 bytes,
so `new Object()` takes 8 bytes.

Even an empty object costs 16 bytes — 8 with compact headers.

</details>

### How big is an empty array?
<details><summary>Show answer</summary>

16 bytes on a typical 64-bit JVM — the same as `new Object()`, but with no padding:

- **Header (12 bytes)** — the same header every object has.
- **Length (4 bytes)** — an `int` that only arrays carry.

12 + 4 = 16 is already a multiple of 8, so every byte is used. In `new Object()` the same 4 bytes are padding;
in an array they hold the length.

An array is an object with one extra field — its length.

</details>

### How big is an empty `String`?
<details><summary>Show answer</summary>

About 40 bytes on a typical 64-bit JVM, though it holds no text:

- **`String` object — 24 bytes** — 12-byte header + array reference (4) + cached hash (4) + encoding flag (1) +
  "hash is zero" flag (1) = 22, padded to 24.
- **`byte[]` — 16 bytes** — the array header (12 + 4 for the length), with no data.

Every string pays these ~40 bytes before its first character.

</details>

### Max heap size — what critical size threshold must be considered and why?
<details><summary>Show answer</summary>

**Compressed Oops:** below ~32 GB, the JVM stores object references in 4 bytes instead of 8. Above it, every
reference grows to 8 bytes, so a 33 GB heap holds less data than a 31 GB one.

Keep the heap under ~31 GB, or go well above (40+ GB) so the extra space outweighs the bigger references.

</details>

### Creating a `String` — what are the ways and how do they differ?
<details><summary>Show answer</summary>

- **Literal** (`"abc"`) — taken from the string pool; every `"abc"` literal in the code is the same object.
- **Constructor** (`new String("abc")`) — always a new object on the heap, not in the pool.
- **Built at runtime** (concatenating variables, `StringBuilder`, reading a file or the network) — also a new
  object, not in the pool.
- **`intern()`** — returns the pool's copy of the same text; if there is none, adds this string to the pool and
  returns it.

```java
String a = "abc";
String b = new String("abc");
String c = b.intern();
a == b;   // false — different objects
a == c;   // true  — intern() returned the pooled "abc"
```

Literals come from the pool; everything built at runtime is a new object until `intern()` brings it in.

</details>

### String pool — where does it live and how is it cleaned?
<details><summary>Show answer</summary>

- **Strings** — the pooled `String` objects live on the regular heap (since Java 7).
- **Lookup table** — the hash table the JVM uses to find them lives in native memory, among the JVM's internal
  data.
- **Before Java 7** — the pool sat in [PermGen](#permgen-vs-metaspace--why-was-permgen-replaced), with its fixed
  size; heavy interning could end in `OutOfMemoryError: PermGen space`.

The pool does not keep strings alive: once nothing references a pooled string, the GC collects it like any
other object. Literals stay as long as the class that uses them is loaded.

The strings are on the heap and the GC cleans them; only the lookup table is native.

</details>

### `String.intern()` — when is it worth calling?
<details><summary>Show answer</summary>

Only when an app keeps millions of long-lived strings with few distinct values — for example, after parsing
large files or loading data with country codes, status labels or stock tickers. Interning keeps one `String`
per value; the duplicates become garbage.

Every string read from a file is a new object, even when the text is the same:

```java
// Without intern(): each Order keeps its own copy — 1 million orders, 1 million "DE" objects
for (String line : lines) {                    // "1001,DE", "1002,DE", ...
  String[] p = line.split(",");                // p[1] is a new "DE" object on every line
  orders.add(new Order(p[0], p[1]));           // the copy stays alive as long as the Order
}

// With intern(): every Order points to the one pooled "DE"
for (String line : lines) {
  String[] p = line.split(",");
  orders.add(new Order(p[0], p[1].intern()));  // the copy from split() becomes garbage at once
}
```

- **Typical code — not worth it** — each call is a lookup in the JVM's global table, and most strings live too
  briefly for sharing to save anything.
- **Not for comparison** — interning strings to compare them with `==` is a known misuse: one string that was
  not interned breaks the check. Use `equals()`.

`intern()` is a memory tool for many long-lived duplicates, nothing else.

</details>

### Many duplicate strings in an app — what are the options?
<details><summary>Show answer</summary>

- **[`intern()`](#stringintern--when-is-it-worth-calling)** — equal strings collapse into one shared object, so
  they become `==`. Saves the whole object. Needs a code change wherever strings are created; uses the JVM's
  global table.
- **GC String Deduplication** (`-XX:+UseStringDeduplication`) — the GC finds equal strings in the background
  and makes them share one internal byte array. The `String` objects stay separate (`==` is still `false`), so
  only the array is saved. No code changes; costs GC CPU, so it is
  [off by default](#why-is-gc-string-deduplication-disabled-by-default). G1 since Java 8u20; ZGC, Serial and
  Parallel since Java 18.
- **Own pool** — a `ConcurrentHashMap<String, String>`: `pool.computeIfAbsent(s, k -> k)`. Works like
  `intern()`, but you control its scope and can clear it when the data is gone.

`intern()` and an own pool share whole objects but need code changes; GC deduplication shares only the arrays,
with no code changes.

</details>

### Why is GC String Deduplication disabled by default?
<details><summary>Show answer</summary>

Because it trades CPU time for heap space, which only benefits workloads with many long-lived duplicate strings.

- **CPU overhead:** The GC must calculate hashes, compare character arrays byte-by-byte, and update references. This
  increases Garbage Collection pause times.
- **Memory overhead:** The JVM must maintain internal tracking tables to find duplicates, consuming native memory.
- **Workload dependency:** In typical web applications, most strings are short-lived and die before they are ever
  checked for duplicates. In these cases, the feature wastes CPU and slows down the GC while saving zero heap memory.

JVM defaults are tuned for general-purpose performance, leaving workload-specific optimizations as opt-in.

</details>

### How much memory does an 8-character `String` take?
<details><summary>Show answer</summary>

It depends on the characters. Every string pays a fixed ~40 bytes (24 for the `String` object, 16 for the array
header — typical 64-bit JVM), plus the text itself:

- **Latin-1** — every character fits in one byte (English text, digits, URLs, JSON keys): 1 byte per character.
  8 characters → 40 + 8 = 48 bytes.
- **UTF-16** — any one character does not fit (Cyrillic, Chinese, emoji): 2 bytes per character.
  8 characters → 40 + 16 = 56 bytes.

The fixed part hides the gap on short strings; the text part decides on long ones: 10,000 characters take
~10 KB in Latin-1 and ~20 KB in UTF-16.

**Compact Strings** (Java 9+) explain the difference: the text is stored in a `byte[]` with an encoding flag —
1 byte per character when the whole string fits Latin-1, 2 bytes when it does not.

**Before Java 9** — the text sat in a `char[]`, always 2 bytes per character, even for plain English.

Compact Strings halve the text for Latin-1; the fixed ~40 bytes stay the same.

</details>
