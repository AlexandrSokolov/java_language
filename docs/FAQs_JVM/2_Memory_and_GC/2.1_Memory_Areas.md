# Memory Areas

Where the JVM keeps data, and how big an object is.

### Why is the process bigger than `-Xmx`?
<details><summary>Show answer</summary>

`-Xmx` limits only the heap. The JVM keeps data in several **memory areas**, and the heap is just one of them. The
rest lives in native memory, outside the `-Xmx` limit:

- **Thread stacks** — one per platform thread, each up to `-Xss` (1 MB by default on 64-bit Linux).
- **Metaspace** — class metadata: class structure, method bytecode, constant pools.
- **Direct memory** — NIO buffers allocated outside the heap.
- **Code cache** — machine code produced by the JIT compiler.
- **GC data** — the collector's own tables for tracking objects and references.

So a container whose memory limit equals `-Xmx` gets killed by the OS, even though the heap never filled up.

`-Xmx` sizes the heap, not the process.

</details>

### Heap vs thread stack — what goes where?
<details><summary>Show answer</summary>

Objects go on the heap; method calls go on the stack.

The **heap** holds every object and array. All threads share it, and the GC frees it. A **thread stack** belongs to
one thread and holds one frame per running method call: parameters, local variables, partial results. For an object,
the stack holds only the reference — the object itself is on the heap. A frame is freed when its method returns, with
no GC involved. Recursion that goes too deep runs out of stack and throws `StackOverflowError`.

Two exceptions to "objects live on the heap":

- The JIT may skip heap allocation for an object that never leaves its method, and keep its fields in registers
  (escape analysis). This is an optimization you cannot rely on, not a rule.
- A virtual thread (Java 21) keeps its stack frames as objects on the heap while it is not mounted on a carrier thread.

Shared and freed by the GC: heap. Private to a thread and freed on return: stack.

</details>

### What replaced PermGen in Java 8?
<details><summary>Show answer</summary>

**Metaspace.** Class metadata — class structure, method bytecode, constant pools — moved from the heap into native
memory.

Before Java 8 this data lived in **PermGen**, a fixed-size part of the heap. Apps that loaded many classes — app
servers with repeated redeploys, libraries that generate proxy classes — hit `OutOfMemoryError: PermGen space`, and
the right `-XX:MaxPermSize` was hard to guess.

Metaspace grows as needed and has no upper limit by default, so a class leak no longer fails early on a small fixed
area — it keeps eating native memory. `-XX:MaxMetaspaceSize` sets a cap.

Class metadata left the heap: fixed PermGen became a growing, native Metaspace.

</details>

### Why put memory outside the heap?
<details><summary>Show answer</summary>

To do I/O without an extra copy, and to hold large data the GC does not have to scan or move. This is **direct
memory** (off-heap memory).

- **No extra copy for I/O.** The GC may move heap objects at any time, so the OS cannot read from or write into a
  heap array directly. For I/O on a heap `ByteBuffer`, the JDK first copies the data into a temporary native buffer.
  A direct buffer is already native, so the OS uses it as is. Netty and other network libraries rely on this.
- **No GC cost for big data.** The GC never scans or moves off-heap memory, so a multi-gigabyte cache kept off-heap
  adds nothing to GC pauses.

The classic way to get it is `ByteBuffer.allocateDirect(size)`, limited by `-XX:MaxDirectMemorySize`. Since Java 22
the Foreign Function & Memory API (`Arena`, `MemorySegment`) also gives off-heap memory, and frees it at a point you
choose instead of whenever the GC collects the buffer object.

Off-heap: the OS uses it as is, and the GC does not touch it.

</details>

### What is in an object header?
<details><summary>Show answer</summary>

Data the JVM keeps about the object for its own use: the object's class, hash code, GC age and lock state.

On a typical 64-bit JVM the header is 12 bytes:

- **Mark word** (8 bytes) — identity hash code, GC age (how many collections the object survived), lock state.
- **Class pointer** (4 bytes) — which class the object belongs to. It is 4 bytes because compressed class pointers
  are on by default; without them it is 8.
- Arrays add a 4-byte **length**.

Java 25 adds **compact object headers** (`-XX:+UseCompactObjectHeaders`, off by default): the class pointer is packed
into the mark word, and the header shrinks to 8 bytes. Apps with many small objects save heap this way.

Header = the JVM's notes on the object: which class, hash, age, lock.

**Verify (web search):** compact object headers — experimental in Java 24, product feature (still off by default) in
Java 25.

</details>

### How big is `new Object()`?
<details><summary>Show answer</summary>

16 bytes on a typical 64-bit JVM: a 12-byte header plus 4 bytes of padding.

The JVM places every object at an address that is a multiple of 8, so every object size is rounded up to 8. Fields
come after the header:

- one `int` field: 12 + 4 = 16 bytes, no padding needed;
- one `long` field: a `long` must start at a multiple of 8, so it goes at offset 16, and the object is 24 bytes.

This is why small objects are expensive. An `Integer` takes 16 bytes to hold 4 bytes of data, so a `List<Integer>`
costs about 20 bytes per item (a 4-byte reference plus the `Integer`), where an `int[]` costs 4.

With compact object headers (Java 25, opt-in) the header is 8 bytes, so `new Object()` is 8 bytes.

Object size = header + fields, rounded up to 8.

**Verify (web search):** the size of `new Object()` with compact object headers on.

</details>

### Why is a 33 GB heap a bad size?
<details><summary>Show answer</summary>

Because above about 32 GB the JVM turns off **compressed oops**, and every reference grows from 4 to 8 bytes. A 33 GB
heap can hold less data than a 31 GB one.

On a 64-bit JVM a reference ("oop", ordinary object pointer) would normally take 8 bytes. Every object starts at a
multiple of 8, so the last 3 bits of every address are always zero. The JVM therefore stores the address divided by 8
in 4 bytes, and multiplies it by 8 when it uses it. 4 bytes count up to about 4 billion; times 8, that reaches 32 GB.

Past that limit the JVM falls back to full 8-byte references. Objects are full of references, so the same data takes
noticeably more heap, and the extra gigabyte is eaten and more. In practice: keep the heap under about 31 GB, or go
well past 32 GB so the extra space pays for the bigger references.

Under ~32 GB references take 4 bytes; above it, 8.

</details>

### What does `String.intern()` do?
<details><summary>Show answer</summary>

It returns the one shared copy of that string from the JVM's **string pool**. If an equal string is already in the
pool, you get that one; if not, this string is added and returned.

String literals and compile-time constants go into the pool automatically, so `"abc" == "abc"` is `true`, while
`new String("abc") == "abc"` is `false` until you call `intern()` on the new one.

Since Java 7 the pool lives in the heap (before that it was in PermGen, which many interned strings could fill), and
pool entries no one uses any more are garbage-collected. Each call is a lookup in a fixed-size hash table, so it pays
off only when the same values repeat a lot — for example, millions of records with a handful of country codes.

`intern()`: one shared `String` object per distinct value.

</details>

### `intern()` vs GC string dedup — what differs?
<details><summary>Show answer</summary>

`intern()` makes equal strings the same `String` object. **String deduplication** makes equal strings share the same
internal array, while the `String` objects stay separate.

`intern()` is called by hand, at the places you choose. It saves both the object and its characters, and it changes
identity: two interned equal strings are `==`. The price is a pool lookup on every call and a code change.

String deduplication (`-XX:+UseStringDeduplication`, off by default) is done by the GC in the background. When it
finds equal strings among objects that survived a few collections, it points them at one shared array. There is no
code change and no identity change, but it saves only the array, it skips short-lived strings, and it costs some GC
CPU. It came with G1 in Java 8u20; since Java 18 the other collectors support it too.

`intern()` shares the whole object; dedup shares only the characters inside.

**Verify (web search):** string deduplication in Serial, Parallel, ZGC and Shenandoah since Java 18.

</details>

### How did Java 9 make strings smaller?
<details><summary>Show answer</summary>

With **compact strings**: a `String` now stores its text in a `byte[]` plus a one-byte encoding flag, instead of a
`char[]`.

If every character fits in Latin-1, each takes one byte; otherwise the string uses UTF-16, two bytes per character as
before. In a typical business app most strings are plain ASCII — ids, keys, JSON field names, codes — so the memory
they take roughly halves. It is on by default (`-XX:-CompactStrings` turns it off), and the `String` API did not
change, so no code had to change.

Latin-1 text: one byte per character.

</details>
