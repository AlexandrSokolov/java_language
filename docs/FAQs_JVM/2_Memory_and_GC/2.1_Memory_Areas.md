# Memory Areas

Where the JVM keeps data, and how big an object is.

### What memory areas exist in a Java application?
<details><summary>Show answer</summary>

- **Heap** — the main area for objects and arrays; shared by all threads.
- **Thread stacks** — one per platform thread, each up to `-Xss` (1 MB by default on 64-bit Linux).
- **Metaspace** — class metadata: class structure, method bytecode, constant pools.
- **Direct memory** — NIO buffers allocated outside the heap (off-heap).
- **Code cache** — machine code produced by the JIT compiler.
- **GC data** — the garbage collector's own tables for tracking objects and references.

</details>

### Can a Java process use more memory than `-Xmx`?
<details><summary>Show answer</summary>

Yes. `-Xmx` sizes the heap, not the process. The other
[memory areas](#what-memory-areas-exist-in-a-java-application) live in native memory, outside that limit.

</details>

### What if `-Xmx` equals the container limit?
<details><summary>Show answer</summary>

Example: container limit 512 MB, `-Xmx512m`.

- The heap can grow to 512 MB. Thread stacks, metaspace and the other
  [native areas](#what-memory-areas-exist-in-a-java-application) come on top of it.
- The kernel counts the whole process against the container limit, not just the heap.
- If the total passes 512 MB, the kernel kills the process: the container shows `OOMKilled`, exit code 137.
- No `OutOfMemoryError`, no stack trace: the heap was never full, so the JVM saw no problem.

The container limit must fit the whole process, not just the heap.

</details>

### Heap vs thread stack — what goes where?
<details><summary>Show answer</summary>

Objects go on the heap; method calls go on the stack.

- **Heap** — all objects and arrays. Shared by all threads. Freed by the garbage collector. Throws
  `OutOfMemoryError` when full.
- **Stack** — one per platform thread, holding one frame per method call: local variables (primitive values and
  references; the objects themselves stay on the heap). Private to its thread. Freed at once when the method
  returns, with no GC. Throws `StackOverflowError` when calls go too deep.

Exceptions to the rule:

- **Escape analysis** — the JIT checks whether an object ever leaves the method that created it. If not, it may
  skip the heap allocation and keep the fields in CPU registers or on the stack (**scalar replacement**: the
  object is split into its separate fields). Not guaranteed.
- **Virtual threads** (Java 21) — when a virtual thread is suspended (**unmounted**), its stack frames are copied
  to the heap as objects until it resumes.

</details>

### What is class metadata and where is it stored?
<details><summary>Show answer</summary>

The JVM's internal record of each loaded class: class structure, method bytecode, constant pools.

- **Java 8+** — in **metaspace**, in native memory (outside the heap). Grows as needed by default; cap it with
  `-XX:MaxMetaspaceSize`.
- **Before Java 8** — in [PermGen](#permgen-vs-metaspace--why-was-permgen-replaced), capped with `-XX:MaxPermSize`.

</details>

### PermGen vs Metaspace — why was PermGen replaced?
<details><summary>Show answer</summary>

**PermGen (before Java 8)** — class metadata sat in a separate area with a fixed maximum size. Apps that create
many classes (app servers, proxy generation, hot redeploy) kept failing with `OutOfMemoryError: PermGen space`,
and the right `-XX:MaxPermSize` was hard to guess.

**Metaspace (Java 8+)** — class metadata moved to native memory.

- **The fix** — it grows as needed, so there is no fixed size to guess.
- **The new risk** — a class loader leak no longer fails early with a clear error. Metaspace keeps growing until
  native memory runs out and the process gets killed. Setting `-XX:MaxMetaspaceSize` brings back an early,
  visible `OutOfMemoryError: Metaspace`.

</details>

### Why put memory outside the heap (off-heap memory)?
<details><summary>Show answer</summary>

- **One less copy in I/O** — the OS cannot read or write the Java heap directly, because the GC may move objects
  at any time. So standard I/O first copies heap data into a temporary native buffer. A direct buffer already
  lives in native memory, so the OS uses it as is.
- **No GC work** — the GC does not scan, track, or compact off-heap memory. A multi-gigabyte cache off-heap does
  not make GC pauses longer.

How to allocate:

- `ByteBuffer.allocateDirect()` — capped by `-XX:MaxDirectMemorySize`. The memory is freed only after the GC
  collects the buffer object on the heap.
- **FFM API** (Java 22+: `Arena`, `MemorySegment`) — the memory is freed when you close the `Arena`, at a point
  you choose, without waiting for the GC.

</details>

### What is in an object header?
<details><summary>Show answer</summary>

Metadata the JVM keeps about the object for its own use: its class, identity hash code, GC age, and lock state.

On a typical 64-bit JVM, the standard header is 12 bytes (16 bytes for arrays):
- **Mark word (8 bytes):** Holds the identity hash code, GC age (survived collections), and thread lock state.
- **Class pointer (4 bytes):** Points to the object's class (4 bytes instead of 8 due to Compressed Class Pointers).
- **Array length (4 bytes):** Added only for array objects.

**Compact Object Headers (Project Lilliput):**
Experimental in Java 24, a product feature in Java 25, and enabled by default in Java 27. The class pointer is
packed directly into the mark word, shrinking the standard header size to just 8 bytes. This significantly reduces heap
footprint for applications with many small objects.

</details>

### How big is `new Object()`?
<details><summary>Show answer</summary>

16 bytes on a typical 64-bit JVM (12-byte header + 4-byte alignment padding).

The JVM aligns objects to 8-byte boundaries. Fields are placed after the header:
- **One `int` field (4 bytes):** 12 (header) + 4 = 16 bytes (no padding).
- **One `long` field (8 bytes):** Placed at offset 16 (for 8-byte alignment), making the object 24 bytes.

**The small object penalty:**
A wrapper like `Integer` uses 16 bytes just to hold 4 bytes of data. A `List<Integer>` costs ~20 bytes per item
(4-byte reference + 16-byte object), whereas a primitive `int[]` costs just 4 bytes per item.

**Compact Object Headers (Project Lilliput):**
Introduced in Java 24/25 (opt-in), this shrinks the object header to exactly 8 bytes. Because 8 is already a multiple
of 8, no padding is needed, meaning a bare `new Object()` drops to exactly 8 bytes.

</details>

### Max heap size — what critical size threshold must be considered and why?
<details><summary>Show answer</summary>

You must carefully consider the **~32 GB** threshold. Crossing it disables **Compressed Oops** (Ordinary Object
Pointers), which means a 33 GB heap will actually hold *less* application data than a 31 GB heap.

**The mechanism:**
On a 64-bit JVM, object references are normally 8 bytes. Since objects are 8-byte aligned, the last 3 bits of their
address are always zero. The JVM optimizes this by storing the address divided by 8 into a 4-byte pointer.

**The limit:**
A 4-byte pointer can count up to ~4 billion. Multiplied by 8, this addresses a maximum of 32 GB. If the heap exceeds
this limit, the JVM falls back to full 8-byte references. Every reference in the app instantly doubles in size,
consuming the extra gigabytes and more.

**Best practice:**
Keep the heap under ~31 GB, or increase it significantly (e.g., 40+ GB) so the added capacity offsets the penalty of
larger references.

</details>

### What does `String.intern()` do?
<details><summary>Show answer</summary>

It returns a canonical (shared) instance of a string from the JVM's internal **string pool**.

**How it works:**
When you call `intern()`, the JVM checks its internal hash table to see if an exact match already exists.
- If a match is found, it discards the current object and returns the reference to the pooled string.
- If no match is found, it adds the current string to the pool and returns its reference.

**Key details:**
- String literals and compile-time constants are interned automatically. This is why `"abc" == "abc"` is `true`,
  but `new String("abc") == "abc"` is `false`.
- Since Java 7, the string pool resides on the regular heap (no longer in PermGen). This means unused interned
  strings will eventually be safely garbage-collected.

</details>

### When should `String.intern()` be used?
<details><summary>Show answer</summary>

In typical business logic, manually calling `intern()` is an **anti-pattern**. It adds execution
overhead due to native JNI calls and hash table lookups, and standard `.equals()` comparison is extremely fast.

**When it is actually reasonable:**
It is strictly a memory optimization tool for parsing massive datasets. If you load millions of objects into memory
that contain heavily duplicated string fields (e.g., country codes, status labels, or stock tickers), `intern()`
drastically reduces heap consumption by ensuring only one `String` object exists per unique value.

**Modern alternatives to avoid using it:**
- **GC String Deduplication:** By enabling `-XX:+UseStringDeduplication` (Java 8+), the Garbage Collector silently
  finds and merges identical strings in the background without any code changes.
- **Custom user-space pools:** Frameworks often prefer caching strings in a plain `ConcurrentHashMap<String, String>`
  rather than pushing them into the JVM's native string pool.

</details>

### `String.intern()` vs GC String Deduplication — what differs?
<details><summary>Show answer</summary>

- **`intern()` (Manual):** Returns a single, shared `String` object. If two strings are interned and equal, they have
  the exact same object identity (`==`). It saves memory for both the object shell and the character array, but costs
  a hash pool lookup on every call and requires explicit code changes.
- **GC String Deduplication (Automatic):** The Garbage Collector scans for duplicate strings in the background. When
  found, it updates the `String` objects to point to the exact same internal character array. The `String` objects
  themselves remain separate (so `==` is still `false`). It requires no code changes, but only saves the array memory
  and consumes background CPU cycles.

**Availability:** Enabled via `-XX:+UseStringDeduplication`. Initially introduced for G1 in Java 8u20, and extended to
support ZGC, Serial, and Parallel collectors in Java 18.

</details>

### Why is GC String Deduplication disabled by default?
<details><summary>Show answer</summary>

Because it trades CPU time for heap space, which only benefits workloads with many long-lived duplicate strings.

- **CPU overhead:** The GC must calculate hashes, compare character arrays byte-by-byte, and update references. This
  increases Garbage Collection pause times.
- **Memory overhead:** The JVM must maintain internal tracking tables to find duplicates, consuming native memory.
- **Workload dependency:** In typical web applications, most strings are short-lived and die before they are ever
  checked for duplicates. In these cases, the feature wastes CPU and slows down the GC while saving zero heap memory.

JVM defaults are tuned for general-purpose performance, leaving workload-specific optimizations as opt-in.

</details>

### How does the JVM optimize the memory footprint of Strings internally?
<details><summary>Show answer</summary>

Since Java 9, the JVM uses an internal optimization called **Compact Strings** to drastically reduce heap consumption.

- **Before Java 9:** Strings were backed by a `char[]`, meaning every character consumed 2 bytes (UTF-16), regardless
  of the actual text.
- **Java 9 and newer:** Strings are backed by a `byte[]` along with a 1-byte encoding flag.
  - **Latin-1:** If the string contains only Latin-1 characters (e.g., standard ASCII IDs, JSON fields, URLs), each
    character takes exactly 1 byte.
  - **UTF-16:** If it contains any non-Latin-1 characters, it falls back to using 2 bytes per character.

This optimization roughly halves the memory used by strings in typical business applications. It is enabled by default
and requires absolutely no API or code changes.

</details>
