# GC Basics

How the garbage collector decides what to free, and what it costs.

### How does the GC know an object is dead?
<details><summary>Show answer</summary>

An object is dead when no chain of references leads to it from a **GC root**. This rule is called **reachability**.

Java has no `free()` or `delete`. The **garbage collector** starts from the roots, follows every reference, and marks
each object it reaches. Whatever is not marked is garbage, and its memory is reused.

Two consequences:

- Cycles are not a problem. Two objects that point at each other, with no path from a root, are both collected.
- An object the program will never use again, but that is still reachable — say, kept in a static map — is never
  freed. That is how Java [leaks memory](2.4_OOM_and_Leaks.md#how-can-java-leak-memory-with-a-gc).

Alive means reachable from a root, not "still needed".

</details>

### Where does the GC start its search?
<details><summary>Show answer</summary>

From the **GC roots** — references the JVM knows are live without following anything else:

- local variables and parameters in every thread's stack frames;
- static fields of loaded classes;
- live threads;
- references held by native (JNI) code;
- objects locked by a running `synchronized` block.

Static fields matter most in practice: whatever a static field holds lives as long as its class, which usually means
as long as the app.

Roots: stacks, statics, threads, native references.

</details>

### Soft vs weak reference — when is each cleared?
<details><summary>Show answer</summary>

A **weak** reference is cleared at the next GC once nothing else holds its object strongly. A **soft** reference is
cleared only when the JVM is short of memory.

Both point to an object without keeping it alive the way a normal (strong) reference does:

- `WeakReference` — for data tied to an object you do not own: `WeakHashMap` keys, listener lists that must not keep
  listeners alive. The entry goes away when its key object does.
- `SoftReference` — the GC keeps the object while there is room, and clears all soft references before it would throw
  `OutOfMemoryError`. Meant for memory-sensitive caches.

Soft-reference caches work badly in practice: the GC, not you, decides what to drop and when, so the heap stays full
and GC work goes up. A size-limited cache such as Caffeine is the usual choice today.

Weak: gone at the next GC. Soft: gone when memory runs short.

</details>

### Why not rely on `finalize()`?
<details><summary>Show answer</summary>

Because nothing says when it runs, or whether it runs at all. The GC calls `finalize()` some time after the object
becomes unreachable — maybe much later, maybe never, if no GC happens before the JVM exits.

It also hurts the GC. An object with a finalizer needs at least two collections to be freed, and finalizers run on
one JVM thread; if that thread falls behind, unfreed objects pile up until `OutOfMemoryError`. A finalizer can also
store `this` somewhere and bring the object back to life, and exceptions thrown in it are silently ignored.

Deprecated in Java 9, deprecated for removal in Java 18; `--finalization=disabled` turns it off, to test that an app
does not depend on it. Release resources yourself with try-with-resources (`AutoCloseable`); if a safety net is truly
needed, use `java.lang.ref.Cleaner`.

The GC frees memory; it is not a cleanup scheduler.

</details>

### Why does the heap have a young and an old part?
<details><summary>Show answer</summary>

Because most objects die young. This observation is the **generational hypothesis**.

An iterator, a DTO built for one request, a string built for one log line — garbage within milliseconds. Only a few
objects live long: caches, singletons, connection pools. So the heap is split:

- New objects go to the **young generation**. It is collected often, and fast: the GC copies out only the few
  survivors, so the cost depends on how many objects are alive, not on how much garbage there is.
- Objects that survive several young collections move to the **old generation**, which is collected rarely.

Most collections then touch a small area with few live objects.

Collect young objects often and old objects rarely, because most die young.

</details>

### When does an object move to the old part?
<details><summary>Show answer</summary>

When it has survived enough young collections, or when the young generation has no room left for it.

The young generation is **Eden**, where new objects are created, plus two **survivor** spaces. At each young
collection, live objects from Eden and the current survivor space are copied into the other survivor space, and their
age (a counter in the object header) goes up by one. At the tenuring threshold — at most 15, because the age has 4
bits, and the JVM may lower it — the object is copied to the old generation. This move is called **promotion**.

An object can also be promoted early, when the survivor space is full. Very large objects may skip the young
generation altogether.

The costly case is **premature promotion**: objects that live a few seconds — per-session data, short-lived caches —
survive the young collections, reach the old generation, and die there. The old generation then fills with garbage
that only an expensive old or full collection can free.

Survive enough young collections and you move to old; garbage that dies just after the move costs the most.

</details>

### Why must the app stop during a GC?
<details><summary>Show answer</summary>

Because the app changes references while the GC reads them. If threads keep running, one could move a reference from
an object the GC has not scanned yet into one it already scanned — and the GC would free a live object. Or the GC
could move an object while a thread still uses its old address.

So the JVM brings every app thread to a **safepoint** — a point where the thread's stack and references are in a known
state — and holds them there. This is a **stop-the-world (STW) pause**: no app code runs, and requests just wait.

Concurrent collectors (G1's marking, ZGC, Shenandoah) do most of their work while the app runs. They make it safe
with **barriers**: small pieces of code the JIT adds to reference reads or writes, so the GC sees each change. They
still need short pauses, for example to scan thread stacks.

The GC cannot trace references while the app rewrites them: either stop the app, or watch every reference access.

</details>

### Short pauses vs throughput — what do you trade?
<details><summary>Show answer</summary>

Pause length against throughput — and memory is the third side.

**Throughput** is the share of CPU time the app gets, as opposed to the GC. **Pause time** is how long one stop lasts.
Short pauses mean doing GC work while the app runs, and that costs: barriers slow every reference access in app code,
GC threads compete with the app for CPU, and the heap needs spare room because the app keeps allocating during the
collection. A collector that stops the app and does everything at once works more efficiently, with no barriers — but
each pause is long.

More heap helps both, so in practice the trade is pause time, throughput, memory: pick two.
[Each collector](2.3_Collectors.md#how-do-you-pick-a-collector-for-an-app) is one such pick.

</details>
