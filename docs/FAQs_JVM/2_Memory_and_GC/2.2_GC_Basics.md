# GC Basics

How the garbage collector decides what to free, and what it costs.

### How does the GC know an object is dead?
<details><summary>Show answer</summary>

An object is dead when no chain of references leads to it from a **GC root**. This rule is called **reachability**.

Java has no `free()` or `delete`. The **garbage collector** starts from the roots, follows every reference, and marks
each object it reaches. Whatever is not marked is garbage, and its memory is reused.

Alive means reachable from a root, not "still needed".

</details>

### How does the garbage collector handle reference cycles?
<details><summary>Show answer</summary>

It frees them like any other garbage: if no path from a GC root reaches the cycle, none of its objects get marked.

The GC does not count references to an object; it only checks whether a root reaches it. Cycles are a problem only
for **reference counting** (Swift, for example), where objects in a cycle keep each other's count above zero forever.

Cycles do not matter; only reachability from a root does.

</details>

### How can you point to an object without keeping it alive?
<details><summary>Show answer</summary>

With a reference type from `java.lang.ref`. A normal reference, called **strong**, keeps its object alive; these three
do not:

- **Soft** (`SoftReference`) — the object stays while memory allows.
- **Weak** (`WeakReference`) — the object goes at the next GC once no strong reference is left.
- **Phantom** (`PhantomReference`) — never gives the object back; it only tells you the object has been collected.

Each one is a weaker level of reachability: an object is strongly, softly, weakly or phantom reachable, depending on
the strongest reference that still leads to it.

Strong keeps an object alive; soft, weak and phantom only watch it.

</details>

### Soft vs weak reference — what differs?
<details><summary>Show answer</summary>

When the GC clears them: 
- A **weak** reference is cleared at the next GC once no strong reference to its object is left. 
- A **soft** reference survives GCs while there is room; the GC clears all soft references before it would throw
  `OutOfMemoryError`.

So each answers a different question:

- **Weak:** is anyone else still using this object? Its life is tied to other code's strong references — for data
  attached to someone else's object, or one shared instance per value.
- **Soft:** can I afford to keep this object while nobody uses it? It is worth keeping on its own — a cache.

Mixed up, both break: a weak cache loses its entries at every GC, and soft lifetime tracking keeps dead entries
around until memory runs short.

Weak: as long as someone else uses it. Soft: as long as memory allows.

</details>

### What is a soft reference good for today?
<details><summary>Show answer</summary>

By design, for a cache: it keeps an object nobody uses while memory allows. Today caches are rarely built on it,
because a cache bounded by free memory leaves the GC to decide what to drop and when. Caches are bounded by limits
you choose instead:

- **size limit** — a maximum number of entries or total weight (Caffeine's `maximumSize` / `maximumWeight`);
- **time limit** — entries expire after a set time (`expireAfterWrite`, `expireAfterAccess`);
- **explicit invalidation** — entries are removed when the source data changes.

Soft is built for caching, but caches are bounded by size and time, not by free memory.

</details>

### A service under load caches database query results — which reference?
<details><summary>Show answer</summary>

**Neither — a cache with a size limit and expiry**, such as Caffeine. A soft-reference cache
[fits badly here](#what-is-a-soft-reference-good-for-today), for two reasons specific to this case:

- When memory runs short, the GC can clear many entries at once. Every cleared entry becomes a database query, so the
  database gets a burst of load exactly when the service is already under pressure.
- Soft references have no time limit. A result can stay in the cache long after the data in the database changed.

```java
Cache<String, List<Order>> orders = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build();
```

Query results need a size limit and an expiry, not a GC-dependent lifetime.

</details>

### Extra data for objects you do not own, gone when the object is gone — which reference?
<details><summary>Show answer</summary>

**Weak** — a `WeakHashMap` with the object as the key. When the key object is collected, its entry is removed.

```java
Map<Thread, Stats> stats = new WeakHashMap<>();
```

The trap: only keys are weak, values are held strongly. If a value refers to its own key, the key stays reachable
through the map, and the entry never goes away.

Data that lives as long as someone else's object: a weak key.

</details>

### One shared instance per value, dropped once nobody uses it — which reference?
<details><summary>Show answer</summary>

**Weak**, but on the values: a map from a value to a `WeakReference` to its shared instance, or Guava's
`Interners.newWeakInterner()`, which does the same.

A `WeakHashMap` alone does not work. Here the key and the value are the same instance, and the strongly held value
keeps its key alive, so nothing is ever removed.

Weak values, not weak keys, when the value is what must die.

</details>

### A cache of large objects you can rebuild, such as decoded images — which reference?
<details><summary>Show answer</summary>

**Neither — a size-limited cache.** Soft references are the textbook answer, since the GC drops them before
`OutOfMemoryError`, but [they work badly as a cache](#why-not-build-a-cache-on-soft-references).

Limit by memory, not by count, when entries differ in size:

```java
Cache<Path, BufferedImage> images = Caffeine.newBuilder()
    .maximumWeight(200_000_000)                                        // ~200 MB
    .weigher((Path path, BufferedImage img) -> img.getWidth() * img.getHeight() * 4)
    .build();
```

Rebuildable and large: bound the cache yourself.

</details>

### What does the GC free, and what does it not?
<details><summary>Show answer</summary>

It frees heap memory taken by unreachable objects, and nothing else. Files, sockets, database connections, threads
and native memory stay held, even when the object that owns them is collected.

The GC frees heap memory only.

</details>

### Relying on the GC to release things — considerations?
<details><summary>Show answer</summary>

You can't rely on it, because it has two limits:

- **Unpredictable timing** — nobody knows when it runs. The GC runs when the heap needs space, not when an object
  becomes unreachable. A dead object can wait for minutes, and if no GC happens before the JVM exits, it is never
  collected at all.
- **Heap memory only** — it [frees nothing else](#what-does-the-gc-free-and-what-does-it-not).

No promise when, and only for memory.

</details>

### How do you release a resource that is not memory?
<details><summary>Show answer</summary>

Close it yourself, at a known point — with try-with-resources. The tools, in the order they appeared:

- **`finalize()`** (Java 1.0) — the GC calls it some time before it collects the object. Unpredictable and
  [deprecated](#why-not-rely-on-finalize).
- **try-with-resources** (Java 7) — `close()` of an `AutoCloseable` runs when the block exits, also on an exception.
  The main solution.
- **`Cleaner`** (Java 9) — runs a cleanup action after the object is collected, built on
  [phantom references](#what-is-a-phantom-reference-for). It replaces `finalize()`, but is still timed by the GC, so it
  is only a safety net for a forgotten `close()`.

Close resources yourself; cleanup timed by the GC is only a safety net.

</details>

### Why not rely on `finalize()`?
<details><summary>Show answer</summary>

It has four problems:

- **Unpredictable** — it runs some time after the object becomes unreachable, or never, if no GC happens before the
  JVM exits.
- **Slow to free** — an object with a finalizer needs at least two collections. Finalizers run on one JVM thread, and
  if it falls behind, objects pile up until `OutOfMemoryError`.
- **Resurrection** — a finalizer can store `this` somewhere and bring the object back to life.
- **Lost exceptions** — an exception thrown in a finalizer is silently ignored.

Deprecated in Java 9, deprecated for removal in Java 18.

The GC frees memory; it is not a cleanup scheduler.

</details>

### What is a phantom reference for?
<details><summary>Show answer</summary>

To learn that an object has been collected, so you can release something it owned outside the heap: native memory, a
file handle.

You create it with a `ReferenceQueue`. After the GC collects the object, it puts the reference into the queue; your
code takes it from there and runs the cleanup. `get()` always returns `null`, so, unlike
[`finalize()`](#why-not-rely-on-finalize), the object cannot be brought back. The cleanup therefore must not need the
object itself: keep what it needs, such as a native address, in a separate object. There is still no promise when it
runs.

You rarely use it directly: `java.lang.ref.Cleaner` is built on phantom references and handles the queue for you.

Phantom: tells you the object is gone, never gives it back.

</details>

### Why does the heap have a young and an old part?
<details><summary>Show answer</summary>

Because most objects die young. This observation is the **generational hypothesis**.

An iterator, a DTO built for one request, a string built for one log line — garbage within milliseconds. Only a few
objects live long: caches, singletons, connection pools. So the heap is split:

- New objects go to the **young generation**. It is collected often, and fast: the GC copies out only the few
  survivors, so the cost depends on how many objects are alive, not on how much garbage there is.
- Objects that survive several young collections move to the **old generation**, which is collected rarely.

Most collections then touch a small area with few live objects.

Collect young objects often and old objects rarely, because most die young.

</details>

### When does an object move to the old part?
<details><summary>Show answer</summary>

When it has survived enough young collections, or when the young generation has no room left for it.

The young generation is **Eden**, where new objects are created, plus two **survivor** spaces. At each young
collection, live objects from Eden and the current survivor space are copied into the other survivor space, and their
age (a counter in the object header) goes up by one. At the tenuring threshold — at most 15, because the age has 4
bits, and the JVM may lower it — the object is copied to the old generation. This move is called **promotion**.

An object can also be promoted early, when the survivor space is full. Very large objects may skip the young
generation altogether.

The costly case is **premature promotion**: objects that live a few seconds — per-session data, short-lived caches —
survive the young collections, reach the old generation, and die there. The old generation then fills with garbage
that only an expensive old or full collection can free.

Survive enough young collections and you move to old; garbage that dies just after the move costs the most.

</details>

### Why must the app stop during a GC?
<details><summary>Show answer</summary>

Because the app changes references while the GC reads them. If threads keep running, one could move a reference from
an object the GC has not scanned yet into one it already scanned — and the GC would free a live object. Or the GC
could move an object while a thread still uses its old address.

So the JVM brings every app thread to a **safepoint** — a point where the thread's stack and references are in a known
state — and holds them there. This is a **stop-the-world (STW) pause**: no app code runs, and requests just wait.

Concurrent collectors (G1's marking, ZGC, Shenandoah) do most of their work while the app runs. They make it safe
with **barriers**: small pieces of code the JIT adds to reference reads or writes, so the GC sees each change. They
still need short pauses, for example to scan thread stacks.

The GC cannot trace references while the app rewrites them: either stop the app, or watch every reference access.

</details>

### Short pauses vs throughput — what do you trade?
<details><summary>Show answer</summary>

Pause length against throughput — and memory is the third side.

**Throughput** is the share of CPU time the app gets, as opposed to the GC. **Pause time** is how long one stop lasts.
Short pauses mean doing GC work while the app runs, and that costs: barriers slow every reference access in app code,
GC threads compete with the app for CPU, and the heap needs spare room because the app keeps allocating during the
collection. A collector that stops the app and does everything at once works more efficiently, with no barriers — but
each pause is long.

More heap helps both, so in practice the trade is pause time, throughput, memory: pick two.
[Each collector](2.3_Collectors.md#how-do-you-pick-a-collector-for-an-app) is one such pick.

</details>
