# Garbage Collectors

Which collectors the JVM has, how each keeps pauses short, and how to pick one.

### Serial vs Parallel — what differs?
<details><summary>Show answer</summary>

The number of GC threads: **Serial** collects with one thread, **Parallel** uses all cores.

HotSpot ships several **garbage collectors**, and these two are the oldest. Both stop the app for the whole
collection, young and old, and both compact the old generation.

- **Serial** (`-XX:+UseSerialGC`) — no coordination between GC threads and the smallest memory overhead. Fine for
  small heaps, one-CPU containers, command-line tools.
- **Parallel** (`-XX:+UseParallelGC`) — the same stop-the-world work, split across all cores, so it ends sooner. It
  gives the best total throughput, but pauses grow with heap size: a full collection of a large old generation can
  take seconds. It was the default up to Java 8.

Same stop-the-world model: one thread or all cores.

</details>

### What happened to CMS?
<details><summary>Show answer</summary>

**CMS** (Concurrent Mark Sweep) was deprecated in Java 9 and removed in Java 14. G1 replaced it.

CMS was HotSpot's first attempt to cut old-generation pauses: it marked live objects while the app ran, then freed the
dead ones in place. Its weak spot: it never compacted. The old generation broke into free gaps of mixed size. When a
new object fit nowhere — or when the app filled the old generation before CMS finished ("concurrent mode failure") —
the JVM fell back to a long stop-the-world full collection. It also needed many flags to tune and was costly to
maintain.

G1 kept the concurrent marking and added compaction in small steps.

Concurrent, but no compaction: the heap fragments, so G1 took over.

</details>

### How does G1 pick what to clean first?
<details><summary>Show answer</summary>

It collects the regions with the most garbage first — hence the name, **Garbage-First**.

G1 splits the heap into many equal **regions**. At any moment each region plays one role: Eden, survivor, old, or
"humongous" (one very large object). G1 marks live objects while the app runs, so it knows how much live data each
region holds.

In each pause it takes all young regions plus the old regions with the least live data — as many as it can process
within the pause goal (`-XX:MaxGCPauseMillis`, 200 ms by default). It copies their live objects into free regions and
frees the old ones whole. Copying is compaction, done a few regions at a time, so the heap does not fragment and full
collections are rare. The pause goal is a target, not a promise.

Small regions, most garbage first, as much as fits in the pause goal.

</details>

### How do ZGC and Shenandoah keep pauses short?
<details><summary>Show answer</summary>

They move objects while the app runs, so pause length does not grow with heap size — ZGC pauses are usually under a
millisecond, even on very large heaps.

Moving an object while the app runs breaks any reference that still points at the old address. ZGC solves this with
a **load barrier**: on every reference read from the heap, code the JIT added checks a few metadata bits stored in the
pointer itself (**colored pointers**). If the object has moved, the barrier finds the new address and fixes the
reference in place, so the next read goes straight through. Shenandoah reaches the same result with its own barriers.

The only pauses left are short ones, mainly to scan thread stacks. Both collectors have been production-ready since
Java 15.

Move objects while the app runs; barriers fix references on the fly.

</details>

### ZGC since Java 21 — what changed?
<details><summary>Show answer</summary>

It became **generational**. Java 21 added Generational ZGC (`-XX:+UseZGC -XX:+ZGenerational`), Java 23 made it the
default ZGC mode (`-XX:+UseZGC` alone), and Java 24 removed the old single-generation mode.

The original ZGC had one generation: every cycle marked the whole heap. With a high allocation rate it needed a lot of
spare heap and CPU to keep up, and when it fell behind, app threads had to wait for memory (**allocation stalls**).
Collecting young objects often and cheaply removes most of that load. Pauses stay under a millisecond, while CPU use
and the spare heap needed both go down.

ZGC took the generational idea; since Java 24 ZGC is always generational.

</details>

### Which collector does the JVM pick by default?
<details><summary>Show answer</summary>

G1, since Java 9 — but only on a machine the JVM treats as a server: at least 2 CPUs and about 2 GB of memory. Below
that it picks Serial. Before Java 9 the server default was Parallel.

The trap is containers. Since Java 10 the JVM reads the container's CPU and memory limits, not the host's. A pod with
a 1-CPU limit, or less than about 2 GB, gets Serial GC without any warning — and a service that expects G1 runs with
one GC thread and long pauses. `java -Xlog:gc -version` shows which collector was chosen.

G1 by default — unless the JVM sees a small machine; then Serial.

**Verify (web search):** the exact thresholds (2 CPUs, 1792 MB), and whether Java 26 made G1 the default everywhere.

</details>

### How do you pick a collector for an app?
<details><summary>Show answer</summary>

Keep the default (G1) unless GC logs (`-Xlog:gc*`) show that GC is the problem — most slow responses come from the
database, the network or locks, not the collector. If it is GC, pick by what hurts more, long pauses or lost
throughput, and by heap size:

- **G1** — most services. A balance of pause time and throughput, with a pause goal you can set.
- **Parallel** — batch jobs, ETL, offline processing: only total run time counts, and pauses do not matter.
- **ZGC** (or Shenandoah) — services with strict response-time limits (p99), or heaps of tens of gigabytes where G1
  pauses grow. You accept some throughput loss and more CPU and memory for the GC.
- **Serial** — tiny heaps, one-CPU containers, short-lived tools.

Default G1; Parallel for batch; ZGC for short pauses on big heaps; Serial for tiny ones.

</details>
