# OutOfMemoryError and Leaks

What runs out, and why memory leaks even with a garbage collector. How to find a leak in prod:
[4.2 Scenarios](../4_Diagnostics/4.2_Scenarios.md).

### `OutOfMemoryError` — which memory ran out?
<details><summary>Show answer</summary>

The text after the colon names it:

- `Java heap space` — the heap is full of live objects: a leak, or a heap too small for the real load.
- `Metaspace` — too many classes: a class loader leak after redeploys, or code that keeps generating classes.
- `Direct buffer memory` — direct `ByteBuffer`s reached `-XX:MaxDirectMemorySize`. They are freed only when their
  small heap objects are collected, so a heap with little GC activity can hold a lot of native memory.
- `unable to create native thread` — the OS refused a new thread: the process or container hit its thread limit, or
  there is no native memory left for another stack. Usually the code creates threads without a bound. A bigger heap
  makes this worse, not better — it leaves less native memory for stacks.

One more message, [`GC overhead limit exceeded`](#what-does-gc-overhead-limit-exceeded-mean), means the heap is not
full yet, but the GC can no longer keep up.

Read the text after the colon before you touch `-Xmx`.

</details>

### What does `GC overhead limit exceeded` mean?
<details><summary>Show answer</summary>

The app is still running but makes almost no progress: the GC takes nearly all the time and frees almost nothing. By
default the limit is hit when, over several collections in a row, more than 98% of the time goes to GC while less
than 2% of the heap is recovered.

Without this check the app would crawl for minutes or hours, doing one GC after another, before it finally failed. The
JVM throws early instead. The cause is the same as `Java heap space`: live data almost as big as the heap — a leak, or
a heap too small for the load. Turning the check off (`-XX:-UseGCOverheadLimit`) only changes which error you get, and
when.

The check is a Parallel GC feature; under G1 the same situation ends in `Java heap space`.

The heap is not full yet, but the GC is losing.

**Verify (web search):** whether G1 implements the GC overhead limit (it may have been added after Java 25).

</details>

### How can Java leak memory with a GC?
<details><summary>Show answer</summary>

By keeping references to objects the program will never use again. The GC frees only unreachable objects; it cannot
know that you are done with one that is still reachable.

So a Java leak is unused objects still reachable from a GC root, almost always through something that lives long and
only grows:

- a static collection or a cache with no size limit;
- a listener registered on a long-lived object and never removed;
- a `ThreadLocal` value left on a pool thread, which never dies;
- a class loader kept alive after a redeploy, holding every class of the old app version.

Reachable but unused — the GC cannot tell the difference.

</details>

### Describe a code snippet #01
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// A service in a long-running web app with millions of users.
public class ProfileService {
  private static final Map<String, Profile> CACHE = new ConcurrentHashMap<>();

  private final ProfileRepository repository;

  public ProfileService(ProfileRepository repository) {
    this.repository = repository;
  }

  public Profile find(String userId) {
    return CACHE.computeIfAbsent(userId, repository::load);
  }
}
```

</details>

<details><summary>Show answer</summary>

**Unbounded cache.** The map only grows: one entry per distinct user id, and nothing ever removes one. A static field
is a GC root, so every entry lives as long as the class — in practice, as long as the app. With many users and long
uptime the old generation fills up with profiles nobody will ask for again, and the app ends in
`OutOfMemoryError: Java heap space`. The size of the leak follows traffic, so it often shows up only in production.

Fix — a cache with a size limit and expiry, such as Caffeine:

```java
private static final Cache<String, Profile> CACHE =
    Caffeine.newBuilder()
            .maximumSize(10_000)
            .expireAfterWrite(Duration.ofMinutes(10))
            .build();

public Profile find(String userId) {
  return CACHE.get(userId, repository::load);
}
```

In Spring the same is `@Cacheable` backed by a Caffeine cache manager with the same limits.

`WeakHashMap` is not a fix here: its keys are the request's `String` ids, which nothing else holds, so entries
disappear at the next GC and the cache stops caching.

A cache without a size limit is a leak with a good name.

</details>

</details>

### Describe a code snippet #02
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public class PriceTicker {
  private final List<PriceListener> listeners = new CopyOnWriteArrayList<>();

  public void subscribe(PriceListener listener) {
    listeners.add(listener);
  }

  public void unsubscribe(PriceListener listener) {
    listeners.remove(listener);
  }

  void publish(BigDecimal price) {
    listeners.forEach(listener -> listener.onPrice(price));
  }
}

// One PriceTicker lives for the whole app. Users open and close price panels many times a day.
public class Dashboard {
  private final PriceTicker ticker;

  public Dashboard(PriceTicker ticker) {
    this.ticker = ticker;
  }

  public PricePanel openPanel() {
    PricePanel panel = new PricePanel();   // holds a chart buffer of a few MB
    ticker.subscribe(panel);
    panel.show();
    return panel;
  }

  public void closePanel(PricePanel panel) {
    panel.hide();
  }
}
```

</details>

<details><summary>Show answer</summary>

**Lapsed listener.** `closePanel` hides the panel but never unsubscribes it. The ticker lives for the whole app, and
its list holds a strong reference to every panel ever opened. Each closed panel stays reachable, with its chart
buffer, so the heap grows with every open and close until `OutOfMemoryError: Java heap space`. The ticker also keeps
calling `onPrice` on panels nobody sees, wasting CPU.

Minimal fix — unsubscribe on close:

```java
public void closePanel(PricePanel panel) {
  ticker.unsubscribe(panel);
  panel.hide();
}
```

This still depends on every caller remembering. A safer design makes `subscribe` return a handle the owner closes, so
the subscription cannot outlive its owner by accident — the same idea as `Flow.Subscription.cancel()`:

```java
public Subscription subscribe(PriceListener listener) {   // Subscription: AutoCloseable, close() throws nothing
  listeners.add(listener);
  return () -> listeners.remove(listener);
}
```

A weak-reference listener list also stops the leak, but it hides the lifetime: a listener nobody else holds — a
lambda, for example — is dropped at the next GC and silently stops getting prices.

A long-lived publisher keeps every listener alive until someone unsubscribes it.

</details>

</details>

### Describe a code snippet #03
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public final class RequestContext {
  private static final ThreadLocal<UserSession> SESSION = new ThreadLocal<>();

  public static void set(UserSession session) {
    SESSION.set(session);
  }

  public static UserSession current() {
    return SESSION.get();
  }
}

// Runs on a Tomcat worker thread (a fixed pool) for every request.
public void handle(Request request) {
  RequestContext.set(sessions.load(request));
  process(request);
}
```

</details>

<details><summary>Show answer</summary>

**ThreadLocal left on a pool thread.** Nothing ever calls `remove()`. Pool threads never end, so each worker keeps the
last request's session after the request is done. That causes three problems:

- **Memory held.** Each worker thread holds one stale session. With a fixed pool this is bounded — pool size ×
  session size — so it is a real leak only when sessions are large or the pool is big.
- **Data seen by the wrong user.** If the next request on that thread reads `current()` before `set()` — on an error
  path, or in code that runs earlier — it gets the previous user's session. That is a security bug, not only a memory
  one.
- **Class loader leak on redeploy.** The worker threads belong to the server, not the app. The stale value is an
  object of an app class, so it keeps the old app's class loader — and all its classes — alive after a redeploy,
  filling Metaspace.

Fix — clear it in `finally`:

```java
public void handle(Request request) {
  RequestContext.set(sessions.load(request));
  try {
    process(request);
  } finally {
    RequestContext.clear();   // calls SESSION.remove()
  }
}
```

Since Java 25 a `ScopedValue` does this by design: the value exists only while the bound code runs, so nothing can be
left behind.

```java
private static final ScopedValue<UserSession> SESSION = ScopedValue.newInstance();

ScopedValue.where(SESSION, sessions.load(request)).run(() -> process(request));
```

Pool threads never die: remove the `ThreadLocal` value in `finally`, or bind a scoped value instead.

</details>

</details>

### Describe a code snippet #04
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// Deployed as a .war to a shared Tomcat; the team redeploys it several times a day.
@WebListener
public class MetricsStartup implements ServletContextListener {

  @Override
  public void contextInitialized(ServletContextEvent event) {
    Thread reporter = new Thread(() -> {
      while (true) {
        Metrics.report();
        try {
          Thread.sleep(30_000);
        } catch (InterruptedException ignored) {
        }
      }
    });
    reporter.setDaemon(true);
    reporter.start();
  }
}
```

</details>

<details><summary>Show answer</summary>

**Class loader leak.** The app starts a thread and never stops it. On undeploy the server drops the app, but the
thread keeps running. A running thread is a GC root, its `Runnable` is an object of an app class, and that class holds
the app's class loader — so the old class loader stays alive with every class it loaded. Each redeploy adds one more
full copy of the app's classes, until `OutOfMemoryError: Metaspace`. Meanwhile the old version keeps running too and
reports metrics twice.

Two details make it worse. `setDaemon(true)` does not help: a daemon thread stops only when the whole JVM exits, and
the server JVM keeps running. And the loop swallows `InterruptedException`, so even interrupting the thread would not
stop it.

Fix — let an executor own the thread, and shut it down when the app stops:

```java
@WebListener
public class MetricsStartup implements ServletContextListener {
  private ScheduledExecutorService scheduler;

  @Override
  public void contextInitialized(ServletContextEvent event) {
    scheduler = Executors.newSingleThreadScheduledExecutor();
    scheduler.scheduleAtFixedRate(Metrics::report, 0, 30, TimeUnit.SECONDS);
  }

  @Override
  public void contextDestroyed(ServletContextEvent event) {
    scheduler.shutdownNow();
  }
}
```

In Spring, a `@Scheduled` method gives the same result: the framework owns the thread and stops it with the context.
The leak needs a redeploy into a running JVM, so it hits app servers with hot redeploy, not apps that run one per JVM
and restart on every release (a Spring Boot jar, one app per container).

Anything the app leaves running or registered after undeploy keeps its whole class loader alive.

</details>

</details>
