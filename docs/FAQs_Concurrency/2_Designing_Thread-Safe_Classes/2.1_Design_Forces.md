### What are the design forces in concurrent code?
<details><summary>Show answer</summary>

- [Safety](#what-is-a-concurrently-typesafe-system) — objects stay self-consistent under simultaneous access
- [Liveness](#what-is-liveness) — every activity eventually progresses or fails, never stuck in between
- [Performance](#what-is-performance-as-a-design-force) — how much work you get from given resources
- [Reusability](#what-is-reusability-as-a-design-force) — concurrent code designed to be reused

</details>

### What should never break on a method call?
<details><summary>Show answer</summary>

The object's state stays consistent.
Before and after any public method call, the object holds a valid combination of field values —
the rules that define a correct object (its invariants) are never violated.

</details>

### How do you keep an object's state valid?
<details><summary>Show answer</summary>

Encapsulation: keep all state private, expose only methods that move the object between valid states.
No caller can set a field directly to a bad value.


Under concurrent access the same goal holds, but encapsulation alone no longer delivers it — 
other threads touch the object at the same time on different cores. 
A system that stays valid under that is called a [concurrently typesafe system](#what-is-a-concurrently-typesafe-system).

Handle: encapsulation gives consistency in one thread; concurrency needs more.

</details>

### What is a concurrently typesafe system?
<details><summary>Show answer</summary>

A system of objects is **safe** — or **concurrently typesafe** — when every object stays self-consistent no matter
what other operations run at the same time. 
Its invariants hold even while other threads call methods on it on different cores.

</details>

### Strategy for achieving concurrent type safety?
<details><summary>Show answer</summary>

Two method-discipline rules plus one mechanism:

- [Never return from a non-private method while the object is inconsistent.](#how-can-returning-from-a-non-private-method-break-concurrent-type-safety)
- [Never call a non-private method](#how-can-calling-a-non-private-method-break-concurrent-type-safety) — 
  especially on another object — while inconsistent.
- Hold protection (a lock or critical section) over the window where the object is inconsistent.

The first two keep a half-done change from escaping through a method call;
the lock keeps another thread from seeing the object during that window.
Together they guarantee no thread ever observes a broken state.

Handle: stay consistent across every exit point, and lock the object shut while it isn't.

</details>

### How can returning from a non-private method break concurrent type safety?
<details><summary>Show answer</summary>

A method starts changing the object, then hits an early return on some branch and exits before the rest of 
the change runs — leaving the object half-updated and reachable to other threads.

```java
synchronized void applyDiscount(int percent) {
  price -= price * percent / 100;   // first field changed
  if (percent > 50) return;         // early exit — discountApplied never set
  discountApplied = true;           // skipped on the branch above
}
```

After the early return, `price` is reduced but `discountApplied` is still false — a state that should never exist.
Another thread reading the object sees the change half-done.

</details>

### How can calling a non-private method break concurrent type safety?
<details><summary>Show answer</summary>

- **Calling another object's method** — that object (or a chain from it) may call back into this one and read the
  broken state.
- **Calling a non-private method on this instance** — a non-private method may assume consistency, or re-enter
  under the same reentrant lock and act on half-done state.

A public method makes the first change, then calls a package-private method to finish the rest. 
The object is half-done at that handoff — that's normal, the callee is meant to complete it. 
But a subclass in the same package can override that method, and the override runs on the half-changed object. 
The lock is held, but it's the same thread and locks are reentrant, 
so nothing blocks the override from reading the broken state.

```java
class Account {
  private int balance;
  private boolean settled;

  synchronized void close() {
    balance = 0;        // first change
    finishClose();      // hand off to finish — an override runs here
  }

  void finishClose() {  // package-private: subclass in same package can override
    settled = true;
  }
}

// subclass:
void finishClose() {
  archive(balance, settled);   // reads balance cleared but settled still false — impossible state
  super.finishClose();
}
```

The method was non-private, so code you don't control ran on the object before it was whole.

Handle: finish all changes before calling any method that could be overridden — the lock won't stop your own
thread from re-entering.

</details>

### The complete form of the safety strategy?
<details><summary>Show answer</summary>

The **fully synchronized object (FSO)** — the named, complete form of the strategy,
built on the two inconsistent-state rules.
Its full [rule set](#the-rules-of-a-fully-synchronized-object) makes it both safe and live.

</details>

### The rules of a fully synchronized object?
<details><summary>Show answer</summary>

- All fields initialized to a consistent state in every constructor.
- No public fields.
- Every non-private method returns with the object consistent (given it was consistent on entry).
- Every method is `synchronized`.
- Every method finishes in bounded time.
- While inconsistent, no method calls another instance's methods.
- While inconsistent, no method calls any non-private method on this instance.

If all hold, the class is both safe and live.

Handle: fully synchronized = lock every method, expose nothing, always return consistent — safe and live by construction.

</details>

### A fully synchronized object — considerations?
<details><summary>Show answer</summary>

Safe and live, but two problems rule it out for real systems:

- **Slow.** Every access takes the lock — even reads. Nothing runs concurrently, so all access to the object is
  serialized. Safe and live does not mean fast.
- **Fragile at scale.** Correctness depends on *every* access sitting inside a synchronized method.
  In a tiny class you check that by eye; in a large codebase you cannot, and one unguarded access breaks it silently.

</details>

### What is liveness?
<details><summary>Show answer</summary>

A system is live when every attempted activity eventually either progresses or fails. 
The keyword is *eventually* — a live system always reaches one of those two ends.

What it rules out is a third end: neither. 
Sequential code finishes or errors — two outcomes, both give you an answer. 
Concurrency adds a way to reach neither: the system doesn't finish and doesn't crash, it just sits there.
Two threads each holding a lock the other needs — nothing throws, nothing returns, the process still "runs", forever.

Handle: live = always ends in progress or failure, never stuck in between.

</details>

### Why does a concept this obvious get a name?
<details><summary>Show answer</summary>

Because the failure it names is silent. 
- A crash announces itself; 
- a deadlocked system does not — the process is up, the CPU may even look busy, and nothing tells you anything is wrong. 
  It looks alive while being permanently dead.


You need a word for "the thing that should be true but silently isn't", or you can't point at its absence, 
reason about it, or test for it. That is what liveness gives you: a name for *ends in progress or failure*, 
so its violation — stuck and silent — becomes something you can talk about and check for.

Handle: the failure is invisible, so the property needs a name to make the absence visible.

</details>

### What does not-progressing mean for liveness?
<details><summary>Show answer</summary>

Not-progressing splits into two kinds, and only one breaks liveness:

- **Transient** — stalled now, but something will arrive to unblock it 
  (a lock frees, network input comes, a resource recovers, the thread gets CPU time). 
  Still live: *eventually* is satisfied, just not yet.
- **Permanent** — stalled, and nothing will ever unblock it. This is the liveness failure.


The split exists because *eventually* can't be read from a snapshot: 
a thread waiting 200ms on the network and a deadlocked thread look identical at any single instant. 
The line between them is whether anything will ever come to unblock it.

Handle: transient = something will unblock it (still live); permanent = nothing will (liveness failure).

</details>

### What causes a transient failure to progress?
<details><summary>Show answer</summary>

A stall that will clear on its own:

- waiting to acquire a lock
- waiting for input, such as network I/O
- a resource temporarily failing
- not enough CPU time to run the thread right now

All share one handle: something will arrive to unblock it, so the system is still live.

</details>

### What causes a permanent silent stall?
<details><summary>Show answer</summary>

A stall that never clears and never errors out — it just hangs, with no progress and no failure:

- deadlock — each thread waits on a lock another holds, forever
- a missed signal — the wakeup already fired with nobody listening, so it's never coming again

Both are silent: the process is up, nothing throws, nothing returns. 
That silence is the liveness failure — an error would have been a clean end.

Handle: never unblocks *and* never errors = hangs forever = liveness broken. 
An exception is a live outcome, not a liveness failure.

</details>

### What is performance as a design force?
<details><summary>Show answer</summary>

How much work a system does with a given amount of resources.

</details>

### What is reusability as a design force?
<details><summary>Show answer</summary>

Designing concurrent code so it can be reused.

</details>

### How do the design concepts relate?
<details><summary>Show answer</summary>

The four forces — safety, liveness, reusability, performance — pull against each other. You can't max all four;
push one and it taxes the other three. Each force has its own card of costs:

- [what safety costs](#what-does-safety-cost-the-other-forces) — locking serializes threads and can deadlock
- [what liveness costs](#what-does-liveness-cost-the-other-forces) — loosening locks lets stale/half state slip through
- [what performance costs](#what-does-performance-cost-the-other-forces) — stripping synchronization and specializing hard
- [what reusability costs](#what-does-reusability-cost-the-other-forces) — running foreign code and guarding for the unknown

Handle: every gain is bought from another force — the whole job is choosing which trade to make.

</details>

### What does safety cost the other forces?
<details><summary>Show answer</summary>

Safety needs synchronization, which costs the other three:

- **Performance.** A lock turns parallel work back into serial: one thread runs, the rest wait. Plus memory
  barriers that flush caches to make writes visible.
- **Liveness.** More locks → deadlock risk (threads grab them in different orders) and starvation (one long
  holder blocks quick readers).
- **Reusability.** A class safe on its own isn't safe when composed — a caller's `check-then-act` across two safe
  calls still races. Fixing it means either bloating the API with every compound method or exposing the internal
  lock, breaking encapsulation.

Handle: safety is bought with locking, and locking is what drags down speed, liveness, and reuse.

</details>

### What does liveness cost the other forces?
<details><summary>Show answer</summary>

Liveness means loosening locks to keep threads moving, which costs the other three:

- **Safety.** Shrinking a lock's scope opens a window where state changes between releasing one lock and taking the next. 
  Or you let threads read slightly stale data instead of waiting — moving, but not strictly consistent.
- **Performance.** Lock-free algorithms avoid sleeping by spinning (CAS loops), so under load threads burn CPU at
  100% doing no real work. Livelock fixes add random back-off delays — progress, but added latency.
- **Reusability.** Liveness is tuned to an environment: a `tryLock()` timeout that fits one setup fires constantly
  in a slower one, so the same component fails when reused elsewhere.

Handle: liveness is bought by loosening locks and spinning, which drags down consistency, CPU, and portability.

</details>

### What does performance cost the other forces?
<details><summary>Show answer</summary>

Performance means stripping away the "friction" of synchronization, which costs the other three:

- **Safety.** Dropping `volatile` lets threads cache variables locally — fast, but others read stale data. 
  Or you pick a non-thread-safe structure and accept a few lost or corrupted values because a lock would cost too much.
- **Liveness.** Splitting one big lock into many fine-grained ones lets threads run at once, but now a transaction
  takes several locks — deadlock odds rise sharply. And prioritizing fast tasks for throughput starves the slow ones.
- **Reusability.** Fast code is specialized: cache-line padding tied to one CPU, or `ConcurrentHashMap`-level CAS
  and fencing you can't subclass or extend without breaking it.

Handle: performance is bought by removing synchronization and specializing hard, which drags down safety, liveness,
and reuse.

</details>

### What does reusability cost the other forces?
<details><summary>Show answer</summary>

Reusability means building a black box for unknown callers, which costs the other three:

- **Safety.** Hiding internal locks makes a caller's `check-then-act` across two safe calls race — they can't lock
  the whole object. And a returned object the caller mutates unsynchronized corrupts state for everyone sharing it.
- **Liveness.** To be customizable, components run callbacks you don't control while holding a lock — an alien
  method that takes another lock can deadlock. And a component blind to its thread model (a blocking queue) can
  freeze a caller whose model it never anticipated.
- **Performance.** Blind to where it runs, it synchronizes every method — a caller in a single-threaded context
  pays for locks never contested. Interfaces, generics, and boxing add abstraction that wrecks cache locality.

Handle: reusability is bought by encapsulating and generalizing for the unknown, which drags down safety, liveness,
and speed.

</details>
