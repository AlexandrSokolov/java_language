### When to lazily initialize, and which idiom?
<details><summary>Show answer</summary>

Lazy initialization delays a field's setup until its value is first needed — 
if it's never needed, it's never built. Works for static and instance fields.

The trade-off is why it's not the default: it lowers the cost of creating the object or loading the class, 
but raises the cost of *every* access to the field (each read must check whether init has happened yet). 
Whether it pays depends on how many instances touch the field, how costly the init is, 
and how often the field is read after — so it can just as easily make things slower.

```java
private final FieldType field = computeFieldValue();   // normal — prefer this
```

Default to normal initialization. Go lazy only for a measured performance gain (or, rarely, a genuine
initialization cycle you couldn't design away). Once you must, pick by case:

- Instance field, for performance → [double-check idiom](#lazy-instance-field-for-performance)
- Static field, for performance → [holder class idiom](#lazy-static-field-for-performance)
- Instance field that tolerates repeated init → [single-check idiom](#lazy-field-that-tolerates-repeated-init)

Trigger: normal by default; lazy needs a measured reason; then instance vs static, and whether repeat init is
tolerable, picks the idiom.

</details>

### Lazy static field for performance?
<details><summary>Show answer</summary>

Use the holder class idiom — a nested class whose static field does the work:

```java
private static class FieldHolder {
  static final FieldType field = computeFieldValue();
}
private static FieldType getField() { return FieldHolder.field; }
```

The JVM doesn't initialize `FieldHolder` until it's first used, so `computeFieldValue` runs only on the first call
to `getField`. The accessor isn't synchronized and does nothing but read a field — so after the one-time class init,
access is as cheap as a normal field read. The VM handles the init-time synchronization once, then patches it away.

</details>

### Lazy instance field for performance?
<details><summary>Show answer</summary>

Use the double-check idiom — check without a lock, and only lock if the field looks uninitialized:

```java
private volatile FieldType field;
private FieldType getField() {
  FieldType result = field;          // read the volatile once
  if (result == null) {              // first check, no lock
    synchronized (this) {
      if (field == null)             // second check, under lock
        field = result = computeFieldValue();
    }
  }
  return result;
}
```

- `volatile` is mandatory: after init there's no lock on the read path, so without it another thread could see a
  stale or half-built value.
- The `result` local means the volatile field is read once on the common (already-initialized) path instead of
  twice — a small speed and clarity win.
- The second check inside the lock stops two threads that both passed the first check from initializing twice.

</details>

### Lazy field that tolerates repeated init?
<details><summary>Show answer</summary>

Use the single-check idiom — drop the second check, so init may run more than once:

```java
private volatile FieldType field;
private FieldType getField() {
  FieldType result = field;
  if (result == null)
    field = result = computeFieldValue();   // may run once per racing thread
}
```

Only valid when the field can be initialized repeatedly with no harm — each racing thread may compute its own value.
`volatile` stays so a computed value is visible to others.

Racy single-check variant: if you also don't care that each thread recomputes, and the field is a primitive other
than `long`/`double`, you may drop `volatile` too. Faster field access on some hardware, at the cost of up to one
extra init per thread. Exotic — not for everyday use.

</details>

### Lazy field that tolerates repeated init?
<details><summary>Show answer</summary>

Use the single-check idiom — drop the second check, so init may run more than once:

```java
private volatile FieldType field;
private FieldType getField() {
  FieldType result = field;
  if (result == null)
    field = result = computeFieldValue();   // may run once per racing thread
}
```

Only valid when the field can be initialized repeatedly with no harm — each racing thread may compute its own
value. `volatile` stays so a computed value is visible to others.

What it actually buys you is tiny: DCL already takes the lock only on the first init and runs every later read
lock-free, so single-check only saves the second null-check and the one-time init lock. What it costs is ongoing:
every future reader must stop and confirm "this isn't DCL — is repeated init really harmless here?" — and that
answer can quietly become wrong later if init gains a side effect. DCL removes that question (construction happens
exactly once, full stop); single-check adds it. So the trade is a negligible saving against a permanent reasoning
burden.

Where it fits: `String.hashCode()` — recompute is cheap, every thread computes the identical value, no side
effect. Where it's wrong: anything where init must happen once (a singleton, any side effect) — use DCL; and for a
static singleton, prefer the holder idiom anyway.

Racy single-check variant: if you also don't care that each thread recomputes, and the field is a primitive other
than `long`/`double`, you may drop `volatile` too. Exotic — not for everyday use.

Handle: single-check trades the once-guarantee for a micro-saving and a permanent "is repeat-init safe?" question —
almost never worth it; default to DCL, reach for single-check only when recompute is provably harmless like a hash
cache.

</details>

### Double-check vs holder class — which when?
<details><summary>Show answer</summary>

- Instance field → double-check idiom (per-instance, so a nested static holder can't help).
- Static field → holder class idiom (no `volatile`, no explicit checks — the classloader does the work).

You *can* write double-check for a static field, but there's never a reason to: the holder class is simpler and
just as fast. So double-check is the instance-field tool, holder class the static-field tool.

</details>

### Describe a code snippet
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
private FieldType field;
private synchronized FieldType getField() {
  if (field == null)
    field = computeFieldValue();
  return field;
}
```

</details>

<details><summary>Show answer</summary>

**Correct, but the wrong idiom.** This is thread-safe lazy init — the `synchronized` makes the check-and-set
atomic, so the field is built exactly once. Nothing here is a bug.


The cost is what's wrong: `synchronized` locks on **every** call to `getField()`, forever. Init happens once, but
the lock is paid on every read for the life of the object — even years after the field is set, every reader still
takes and releases the lock for nothing. Lazy init is supposed to be an optimization; this makes the common path
(reading an already-built field) permanently slower.


Both better idioms remove the after-init lock: for an instance field the 
[double-check idiom](#lazy-instance-field-for-performance) locks only during the first init and reads lock-free after; 
for a static field the [holder class idiom](#lazy-static-field-for-performance) 
lets the JVM do the one-time init with no `volatile` and no explicit lock.

</details>
