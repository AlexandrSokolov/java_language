### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// service.calculateCredit(id) returns CompletableFuture<Credit>, built on non-blocking drivers
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `join()` blocks the Tomcat thread until the whole chain finishes. The async service and the non-blocking
drivers buy nothing: each request still holds a platform thread for its full duration, and under load the pool empties
exactly as with plain blocking code, now with async code to maintain on top.

**Fix:** return the future and let Spring write the response.

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);  // thread goes back to the pool at once
}
```

**Where it matters:** only on platform threads. On virtual threads (`spring.threads.virtual.enabled=true`), `join()`
parks the virtual thread and frees its OS thread, but then the async chain is not needed at all.

An async chain frees threads only if nobody waits on it.

</details>

</details>


### Describe a code snippet #2
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Decision> decide(long id) {
  return webClient.get().uri("/customers/{id}/score", id)
      .retrieve().bodyToMono(Score.class).toFuture()
      .thenApply(score -> {
        Customer c = customerRepo.findById(id).orElseThrow();  // Spring Data JPA
        return rules.decide(c.getOrders(), score);             // orders: a lazy collection
      });
}
```

</details>

<details><summary>Show answer</summary>

**Defect 1 (JDBC on the event loop):** `thenApply` runs on the thread that completed the `WebClient` call, a Reactor
Netty event loop. `findById` blocks that thread on JDBC, and every connection the loop serves stalls meanwhile.

**Defect 2 (the lazy collection):** `findById` runs in its own short transaction, which ends when it returns. There is
no session left on this thread, so `c.getOrders()` throws `LazyInitializationException`. Had the session stayed open,
the lazy load would have blocked the event loop a second time.

**Fix:** give the JPA work its own pool, and one transactional method that loads everything it needs.

```java
return webClient.get().uri("/customers/{id}/score", id)
    .retrieve().bodyToMono(Score.class).toFuture()
    .thenApplyAsync(score -> decisions.decide(id, score), dbPool);  // @Transactional; fetch-joins the orders
```

For a fully non-blocking version, replace JPA with R2DBC or Hibernate Reactive, where related data is fetched
explicitly.

**Where it matters:** at low load the stall is invisible, and only lazy relations throw, so a test with eager fields
passes.

JPA in a non-blocking chain blocks the event loop, and its lazy getters fail or block again; give JPA its own pool and a
transaction that loads everything it needs.

</details>

</details>
