### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Credit> credit(Person p) {
  return getAssetsAsync(p)
      .thenCompose(assets -> getLiabilitiesAsync(p)
          .thenApply(liabilities -> calculate(assets, liabilities)));
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `getLiabilitiesAsync(p)` does not use `assets`, but it starts only after the assets reply arrives. The two
calls run one after another: 400 ms instead of 200 ms. No thread is wasted and the result is correct; the request is
just twice as slow as it needs to be.

**Fix:** start both calls at once and join the results.

```java
return getAssetsAsync(p)
    .thenCombine(getLiabilitiesAsync(p), this::calculate);  // both calls start now
```

**Where it matters:** only for calls that do not need each other's result. When the second call needs the first
result, `thenCompose` is the right tool. The full gain also assumes the downstream can take both calls at once (e.g., a
free DB connection for each).

Async is not concurrent: `thenCompose` waits for one result before it starts the next call.

</details>

### Describe a code snippet #2
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
private final ExecutorService dbPool = Executors.newCachedThreadPool();

@GetMapping("/person/{id}")
public CompletableFuture<Person> person(@PathVariable Long id) {
  return CompletableFuture.supplyAsync(() -> personDao.findById(id), dbPool);  // personDao uses plain JDBC
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** a cached thread pool has no upper limit on threads. Every task that finds no idle thread gets a new one.
When the DB slows down, calls take longer, idle threads run out, and each new request creates another platform thread
blocked on JDBC. Most of them only wait for one of the few JDBC connections. Thousands of threads pile up, until the OS
refuses more and the JVM fails with an `OutOfMemoryError`. The slowdown is not kept inside the pool; it spreads to the
whole JVM.

**Fix:** a fixed pool sized to the connection pool, with a bounded queue.

```java
private final ExecutorService dbPool = new ThreadPoolExecutor(10, 10, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100));  // 10 threads for 10 connections; extra requests are rejected fast
```

**Where it matters:** at normal load it looks fine, because threads are reused and few new ones are created. It breaks
only when the DB slows down, which is exactly when the isolation is needed.

A pool with no limit isolates nothing: a slow DB turns into unlimited threads.

</details>

### Describe a code snippet #3
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@GetMapping("/offer/{id}")
public Mono<Offer> offer(@PathVariable long id) {    // WebFlux handler: runs on an event loop
  Customer c = customerClient.find(id).block();      // wait for the customer first
  return pricingClient.price(c).map(Offer::new);
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `.block()` waits on an event-loop thread. Reactor refuses this and throws `IllegalStateException`
("block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-…"). The guard
exists for two reasons. Blocking the loop would stall every connection it serves. And the reply being waited for may be
handled by that same loop, which can then wait for itself forever.

**Fix:** chain the second call instead of waiting for the first.

```java
return customerClient.find(id)
    .flatMap(c -> pricingClient.price(c))  // runs when the customer arrives; no thread waits
    .map(Offer::new);
```

**Where it matters:**
- **On a Tomcat thread (Spring MVC):** the same `.block()` is allowed. There it only holds the request thread, as in
  [snippet #1](#describe-a-code-snippet-1).
- **`CompletableFuture.join()` on an event loop:** it has no such guard. It blocks the loop silently, with the same
  stall and the same risk of waiting forever.

Never wait on an event loop: chain the next step, and let the reply start it.

</details>

</details>
