# Capacity — Pool Sizing

How big a pool must be, and why it fails. Applies to any pool: threads, DB connections, HTTP connections, queue slots.
- what fills up first, and what goes wrong when it does
- how many requests are inside at once (Little's law)
- why a pool needs idle time to keep waits short
- how to pick the size: from the load, from the CPU cores, and from what runs behind the pool

## Why capacity breaks (the basics)

### What runs out before the CPU does?
<details><summary>Show answer</summary>

Under load, a service usually stops on a fixed-size resource while the CPU still has room:

- server threads that take requests — Tomcat: 200 by default
- database connections — HikariCP: 10 by default
- HTTP connections to other services — Apache HttpClient 5: 5 per target host, 25 in total by default
- the waiting queues in front of each of these

A request that waits on a slow database or remote service still holds its thread and its connection while it waits.
So the pools fill up with waiting work, and new requests queue or fail, while the CPU stays mostly idle.

A service runs out of places to wait long before it runs out of CPU.

</details>

### What goes wrong when pools fill up and how to fix it?
<details><summary>Show answer</summary>

Under load, the [fixed-size pools fill up](#what-runs-out-before-the-cpu-does) long before the CPU does. 
Two different things go wrong, each with its own fix:

- **The pools are too small for the load** (**pool exhaustion**): every dependency runs at normal speed, but at peak
  traffic more calls are in flight than the pools have slots. Fast, healthy requests queue or are rejected.
  - **Fix — capacity:**
    - find [how full the pools get](#how-many-requests-are-in-flight-at-once) at peak load
    - size each pool from that
- **One slow dependency takes every slot** (**cascading failure**, where one failing part brings down the others): its
  calls hold their slots longer and
  [fill the pools](7.04_Capacity_Slow_&_Overloaded_Dependencies.md#how-does-one-slow-dependency-stop-a-whole-service)
  the rest of the service shares. Calls to healthy dependencies find no free slot, and unrelated features stop working.
  - **Fix — isolation:**
    [give each dependency its own limit](7.04_Capacity_Slow_&_Overloaded_Dependencies.md#how-do-you-keep-one-slow-dependency-from-taking-every-thread),
    so a slow one fills only its own slots.

Exhaustion: 
- normal traffic outgrows the pools, so fix it with size. 
- Cascading failure: one slow dependency takes the room from everything else, so fix it with isolation.

</details>

## How full a pool gets (Little's law)

### How many requests are in flight at once?
<details><summary>Show answer</summary>

**Little's Law:** requests in flight = arrival rate × time each request is held.

```text
200 requests/s × 0.05 s = 10 in flight
200 requests/s × 2 s    = 400 in flight
```

Pool size follows rate × hold time; when latency grows, the same traffic needs a bigger pool.

</details>

### 200 requests per second — what pool size?
<details><summary>Show answer</summary>

Traffic is not enough to size a pool. 
A pool holds the requests in progress at the same moment, not the ones that arrive per second. 
The same 200 requests/s need [10 slots or 400](#how-many-requests-are-in-flight-at-once), 
depending on whether each request holds its slot for 0.05 s or 2 s. Traffic alone is missing the hold time.

The number in progress is not something you configure: it is the result of rate × hold time. 
What you configure is the pool size, the limit that result must fit into.

Traffic alone says nothing about pool size; traffic × hold time does.

</details>

### One request, several pools — which time?
<details><summary>Show answer</summary>

The time that pool's resource is held, not the whole request time. 
One request uses several pools, each for a different part of its life:

```text
request, 200 ms:  |-- 50 ms logic --|-- 5 ms query --|-------- 145 ms build response --------|
Tomcat thread:    held the whole 200 ms
DB connection:    taken for the query only, 5 ms, then returned to HikariCP
```

At 400 requests/s:

```text
Tomcat threads:  400 × 0.2   = 80 in use
DB connections:  400 × 0.005 = 2 in use
```

The same rule works for any pool: threads, DB connections, HTTP connections, queue slots. It is why a small DB pool
can serve [far more threads than it has connections](7.02_Capacity_Threads_and_Requests.md#should-server-threads-outnumber-db-connections): 10 connections
held 5 ms each serve about 2,000 requests/s.

The trap is code that keeps the connection for the whole request, for example a transaction left open across a
remote call or while building the response. The hold time becomes 200 ms, so 400 × 0.2 = 80 connections are needed,
and a pool of 10 overflows. That is why
[nothing slow may happen while a connection is held](7.03_Capacity_Dependencies.md#what-should-not-happen-while-a-connection-is-held).

Each pool fills by its own hold time; one long hold on the wrong resource breaks a pool sized for a short one.

</details>

### Why does a well-sized pool suddenly overflow?
<details><summary>Show answer</summary>

In the formula, traffic and time count the same: in flight = rate × hold time. 
Double either one and the pool needs twice the slots. What differs is which one jumps in practice:

- **Traffic** changes slowly and mostly predictably: daily curves, a sale you know about. A 2× surge is a big one;
  a 40× jump within seconds is rare.
- **Hold time** can jump 20× to 100× within seconds, with no warning: a locked row, a slow third-party API, a
  dependency that stops answering.

The same numbers as [in flight](#how-many-requests-are-in-flight-at-once), Tomcat with 200 threads:

```text
normal:    200 requests/s × 0.05 s = 10 threads   → pool 95% idle
slowdown:  200 requests/s × 2 s    = 400 threads  → pool of 200 full in about 1 s
```

Traffic did not grow by a single request. 
Once the pool is full, new requests wait in Tomcat's accept queue, 
then are refused or time out, even though the request rate never changed.

A pool sized for normal speed fails on time, not on traffic. Time is not the bigger factor; it is the one that jumps,
which is why it has to be [capped](#what-caps-a-pools-worst-case).

</details>

### What caps a pool's worst case?
<details><summary>Show answer</summary>

A timeout. It puts a ceiling on the hold time, so it puts a ceiling on how full the pool gets: rate × timeout.

```text
dependency hangs, 200 requests/s:
no timeout:     hold time grows without end → the pool stays full
0.5 s timeout:  200 × 0.5 = about 100 in flight → Tomcat's 200 threads hold
```

The 100 is an average, so leave room for bursts ([keep the pool below full load](#why-keep-a-pool-below-full-load)).

The cap holds only if:

- the timeout covers [every wait the call makes](7.05_Time_Timeouts_and_Retries.md#which-waits-must-an-outgoing-call-limit).
  Waits in a row add up: three calls with 0.5 s each can hold the thread for 1.5 s.
- the timeout frees the waiting thread. A timeout that only stops the caller from waiting, while the call keeps
  running on another thread, leaves
  [that thread held](7.05_Time_Timeouts_and_Retries.md#what-does-a-completablefuture-timeout-actually-stop).

You can't stop a dependency from slowing down; a timeout decides how long that slowness can hold your pool.

</details>

### How do you think about pool size?
<details><summary>Show answer</summary>

You don't size a pool from [requests per second](#200-requests-per-second--what-pool-size). You size it from
[how many requests are inside at the same moment](#how-many-requests-are-in-flight-at-once), and that number depends
on [how long each one holds the pool](#one-request-several-pools--which-time).

The time part is [what changes in production](#why-does-a-well-sized-pool-suddenly-overflow): a dependency slows down
and every request stays longer. So a pool sized for normal speed overflows when a dependency gets slow, even with no
extra traffic.

Two fixes follow:

- [a timeout](#what-caps-a-pools-worst-case) caps the time
- [isolation](7.04_Capacity_Slow_&_Overloaded_Dependencies.md#how-do-you-keep-one-slow-dependency-from-taking-every-thread)
  keeps one slow dependency's time from filling everyone's pool

Rate × hold time fills the pool; hold time is what jumps; cap it, and keep each dependency's time in its own pool.

</details>

## Why a pool needs idle time (queues)

### 1 s per request, 1 request per second: any queue?
<details><summary>Show answer</summary>

The worker is busy 100% of the time on average. Whether anyone waits depends on how even things are:

- **Perfectly even:** one request arrives every second, and each takes exactly 1 s. Each arrives just as the previous
  one finishes. Nobody ever waits.
- **Uneven, the normal case:** requests come in **bursts** (several close together, then none for a while), and some
  take longer than others. In a burst of 3, the worker takes the first and the other 2 wait. A request that takes
  3 s makes the next ones wait. With no idle time, the queue [never empties](#what-empties-the-queue) and keeps
  growing.

Load alone does not make a queue; unevenness does: bursts of arrivals or slow requests.

</details>

### What empties the queue?
<details><summary>Show answer</summary>

One worker, 1 s per request. **Busy** (utilization) is the share of time the worker is working; for a pool, the
average number of slots in use divided by the pool size. **Idle share** = 1 − busy.

A queue grows while requests arrive faster than the worker finishes them, during a burst. It shrinks only when the
worker finishes them faster than new ones arrive. While there is a queue, the worker never stops and finishes
1 request per second. New ones keep arriving at the average rate, which for 1 s requests equals the busy share. The
difference is how fast the queue shrinks, and it is exactly the idle share:

```text
busy   finished − arriving per second   queue of 5 is empty after
50%    1 − 0.5  = 0.5                     10 s
90%    1 − 0.9  = 0.1                     50 s
95%    1 − 0.95 = 0.05                   100 s
100%   1 − 1    = 0                        never
```

While the queue empties slowly, new bursts arrive and add more, so near full load a new request almost always finds
a queue.

For one worker with random arrivals and random request times, the average queue wait is busy / idle × service time.
Next to it, a pool of 200 workers at the same share busy (queue formula for many workers, Erlang C; approximate):

```text
       average queue wait (× service time)
busy   1 worker   200 workers
50%    1          ≈ 0
80%    4          ≈ 0.0001
90%    9          ≈ 0.005
95%    19         ≈ 0.04
99%    99         ≈ 0.5
```

Only idle time empties the queue, and near full load there is almost none left.

</details>

### How does pool size change the queue wait?
<details><summary>Show answer</summary>

At the same share busy, a big pool waits far less. At 90% busy, one worker waits about 9 service times, while 200
workers wait about 0.005 ([numbers](#what-empties-the-queue)). There are two reasons:

- **A burst finds idle workers.** 200 threads at 90% busy have about 20 idle on average, so a burst of 5 is taken at
  once and nobody waits. One worker at 90% is idle only 10% of the time, so a burst almost always queues.
- **A queue empties faster.** When a queue does form, all workers empty it. With 1 s requests at 90% busy, 200
  workers finish 200 per second while 180 arrive, so the queue shrinks by 20 per second. With one worker it shrinks
  by 0.1.

Near 100%, the idle workers run out. At 99% busy, 200 threads have about 2 idle, so in a burst of 5, 3 wait. Between
90% and 99%, the 200-worker wait grows about 100×. A big pool does not remove the sharp growth; it moves it closer to
100% and makes it more sudden.

Pool size decides how close to full a pool can run; no size lets it run at full.

</details>

### Why keep a pool below full load?
<details><summary>Show answer</summary>

Requests wait in a queue only because things are uneven:
[bursts of arrivals or slow requests](#1-s-per-request-1-request-per-second-any-queue). Only idle time
[empties the queue](#what-empties-the-queue), and near full load there is almost none left, so the wait grows very
fast: one worker waits 9 service times at 90% busy and 19 at 95%. A
[bigger pool](#how-does-pool-size-change-the-queue-wait) handles bursts much better at the same load, but hits the
same wall near 100%. So [size the pool](#160-requests-in-flight-at-peak-what-pool-size) to leave idle time at peak
load.

Unevenness fills the queue, idle time empties it; a full pool has no idle time left.

</details>

## Picking the size

### 160 requests in flight at peak: what pool size?
<details><summary>Show answer</summary>

Not 160. A pool of 160 for 160 in flight is 100% busy. It has no idle time, so the queue
[never empties](#what-empties-the-queue). Size the pool so that the peak load leaves idle time:

```text
pool size = in flight at peak / target busy share
160 / 0.8 = 200
160 / 0.7 ≈ 230
```

- **In flight at peak:** peak traffic × [the time this pool is held](#one-request-several-pools--which-time).
- **Target busy share:** 70–80% at peak is a common starting point. Big pools can run busier, and small pools need
  more idle share ([pool size changes the wait](#how-does-pool-size-change-the-queue-wait)).
- **Then measure:** load-test at peak, check the latency, and adjust the size from that.
- **DB pools:** the extra connections must still fit what the database can run at once, because
  [a bigger pool can be slower](7.03_Capacity_Dependencies.md#why-can-a-bigger-connection-pool-be-slower).

The in-flight count is the load; the pool size is that load plus the idle time it needs to stay fast.

</details>

### How big should a thread pool be?
<details><summary>Show answer</summary>

It depends on how much of each task's time the thread waits instead of using the CPU.

- **CPU-only work** — about one thread per core (cores + 1 covers a short stall). More threads only add switching.
- **Work that waits** (DB, HTTP, files) — more threads than cores, because a waiting thread uses no CPU. The formula
  from *Java Concurrency in Practice*:

```text
threads = cores × target CPU use × (1 + wait time / compute time)
8 cores × 100% × (1 + 90 ms / 10 ms) = 80 threads
```

- The formula only answers "how many threads keep the CPU busy". It knows nothing about what the threads wait on: 80
  threads that all need one of 10 DB connections means 70 of them wait on the connection pool. The scarcest resource
  behind the pool caps its useful size.
- Wait and compute times come from measurements, not guesses — and they change when a dependency slows down.

Count cores for CPU work, add threads for waiting, then cap by the scarcest thing the threads wait on.

</details>

### What limits how big a pool can be?
<details><summary>Show answer</summary>

The load sets the smallest size: enough slots to
[leave idle time at peak](#160-requests-in-flight-at-peak-what-pool-size). Two things set the largest:

- **What each slot costs.** A platform thread needs its own stack memory and an OS thread, and thousands of busy ones
  spend CPU switching between each other. A DB connection is a session the database must keep, often with its own
  process or thread. [Virtual threads](7.02_Capacity_Threads_and_Requests.md#do-virtual-threads-remove-the-need-for-limits) remove this cost for threads,
  not for connections.
- **What runs behind the pool.** The pool size is how much work you send at once to the database, the remote service
  or the CPU. Past what that resource can run at once, the calls only slow each other down. The hold time grows, and
  by [Little's law](#how-many-requests-are-in-flight-at-once) more requests end up in flight, not fewer. Give a
  database 1,000 queries at once and each one gets slower while the total done per second does not grow. The waiting
  just moves from your pool, where it is cheap, into the database, where it slows everyone down
  ([a bigger pool can be slower](7.03_Capacity_Dependencies.md#why-can-a-bigger-connection-pool-be-slower)).

So a pool is also a limit. Size it from the load, but never above what is behind it. If the load needs more than
that, a bigger pool cannot help. Shorten the hold time, add capacity behind the pool, or
[refuse the extra work](7.02_Capacity_Threads_and_Requests.md#what-should-a-full-pool-do-with-new-work).

The load sets how small a pool may be; what is behind it sets how big.

</details>
