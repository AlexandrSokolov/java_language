# 7.02 Capacity — Dependencies

How much your database and the services you call can take: 
- connection pools, 
- limits on outgoing calls, and 
- how queues and caching shield them from spikes.

## Database connections

### Why can a bigger connection pool be slower?
<details><summary>Show answer</summary>

The database does the work, not the pool, and it has a fixed number of cores and disks. A DB with 8 cores runs about 8
queries at the same moment; the rest wait inside the DB anyway.

- With 200 connections, 200 queries compete inside the DB: it switches between them, they wait on each other's locks,
  and each connection costs DB memory (in PostgreSQL, a separate process). Each query gets slower, and total
  throughput can drop.
- With a small pool, the extra requests wait in the app, in the pool's queue, where waiting costs almost nothing. The
  DB runs a few queries at a time, at full speed.
- HikariCP's starting point for the pool size, counted on the DB server (Hikari calls the disk count "effective
  spindle count"):

```text
connections = (DB cores × 2) + effective disk count     (disk count ≈ 0 when the data fits in memory)
```

- For an 8-core DB that gives about 16 connections, not 200. Then test under load.

The DB, not the pool, sets how much work runs at once; extra connections move the queue into the DB, where waiting is
most expensive.

</details>

### How many threads for a DB call pool?
<details><summary>Show answer</summary>

About as many as the JDBC pool has connections. Each blocking call holds a thread and a connection for its whole
duration, so the smaller of the two sets the limit:

- **More threads than connections:** e.g. 200 threads, 10 connections (HikariCP's default). 190 threads wait inside
  `getConnection()`, up to 30 s by default, and then the call fails. The extra threads add nothing: the DB still runs
  10 queries at a time.
- **Fewer threads than connections:** connections sit idle, and the DB could take more work than you send it.

The connection pool itself is sized to what the DB can handle, not to your traffic, and the thread pool follows it.

Size the thread pool to the connection pool; size the connection pool to the database.

</details>

### How many connections reach the database?
<details><summary>Show answer</summary>

Every app instance has its own pool, so the DB sees all of them at once:

```text
total = instances × pool size  (+ other apps, batch jobs, admin tools)
10 instances × 20 = 200 connections
```

- HikariCP keeps a fixed-size pool by default (`minimumIdle` = `maximumPoolSize`), so each instance opens all its
  connections at startup, not on demand.
- PostgreSQL's default `max_connections` is 100. With a pool of 20, five instances fill it; the sixth fails to get
  connections.
- Autoscaling makes it worse. Under load, Kubernetes adds instances, each brings a full pool, and the DB — the thing
  already under load — gets more connections exactly when it can least take them.
- A rolling deploy runs old and new instances side by side for a while: count both.
- So pool size is set from the DB down, not from one app up: pool per instance = DB connection budget / max instances.
  When that number gets too small, a connection proxy (PgBouncer, RDS Proxy) lets many app connections share a few DB
  connections.

Connections multiply by the number of instances; size each pool from the database's limit down.

</details>

### What should not happen while a connection is held?
<details><summary>Show answer</summary>

A connection counts as busy for as long as the code holds it, even when no query runs — and
[hold time](#how-many-requests-are-in-flight-at-once) is what fills the pool.

- **A remote call inside a transaction** — a `@Transactional` method that calls an HTTP service holds the connection
  for the whole call. The service slows to 2 s, each connection is held 2 s, and a pool of 10 serves 5 requests per
  second. The DB is idle; the pool is empty.
- **Slow work between queries in one transaction** — file parsing, heavy computation, sending emails.
- **Open Session in View** — `spring.jpa.open-in-view` is on by default in Spring Boot. The session stays open for the
  whole web request, and with Spring's default setting the connection it took stays with it until the response is
  written — JSON serialization and lazy loading in the view included.

The pattern: read what you need, release the connection, do the slow work, then write the result in a second short
transaction.

Pool capacity is spent by hold time, not by query time — hold the connection only for the queries.

</details>

### How does one query per row affect the pool?
<details><summary>Show answer</summary>

**N+1 queries:** a list of 100 orders, each with a lazy `customer`, runs 1 query for the list plus 100 for the
customers.

- Inside one transaction or an open session, all 101 queries run on the same connection — the pool is not asked 101
  times. The cost is hold time: 101 round trips instead of 1 or 2. At about 1 ms each, the connection is held ~100 ms
  instead of ~2 ms, and by [Little's Law](7.01_Capacity_and_Isolation.md#how-many-requests-are-in-flight-at-once) the
  same traffic needs ~50× the connections.
- The DB runs 101 statements instead of one, so its CPU goes to overhead and every other query slows too.
- The pool really is asked 101 times only with `hibernate.enable_lazy_load_no_trans=true`, which opens a new session —
  and takes a new connection — for each lazy load.

N+1 costs the pool through hold time, not through extra checkouts.

</details>

## Outgoing HTTP calls

### What limits concurrent calls to one service?
<details><summary>Show answer</summary>

Apache HttpClient keeps a pool of connections per route — one route is one target host and port. It has two limits:

- `maxTotal` — all connections in the pool. Default 25 in HttpClient 5 (20 in 4.x).
- `defaultMaxPerRoute` — connections to one host. Default 5 in HttpClient 5 (2 in 4.x).

What follows:

- 50 server threads calling one service share 5 connections. 45 threads wait for the pool, and it looks as if the
  remote service were slow.
- Behind a load balancer or API gateway, every call goes to one host name, so one route. The per-route limit caps
  everything, however many instances run behind the balancer.
- The per-route limit is also isolation: one slow host can take at most its own route's connections, not the whole
  pool.
- The JDK `HttpClient` has no pool size to set: over HTTP/1.1 it opens a new connection whenever none is free. The
  only limit is how many threads call it — with virtual threads, none — so the code must set one.

The per-host limit, not the total, is what one service gets — and a load balancer turns many backends into one host.

</details>

### What does HTTP/2 change for connection limits?
<details><summary>Show answer</summary>

- **HTTP/1.1** — one request at a time per connection (pipelining exists but is practically unused). Parallel calls to
  one host = connections open to it, and a slow response blocks its connection: **head-of-line blocking**.
- **HTTP/2** — many requests (streams) run at once over one connection. The limit becomes streams per connection, set
  by the server (`SETTINGS_MAX_CONCURRENT_STREAMS`; the spec recommends at least 100). One connection can do the work
  of a whole pool.
- Still one TCP connection underneath: a lost packet stalls every stream on it until it is resent. HTTP/3 runs over
  QUIC (UDP) to remove this.
- Isolation trap: behind a load balancer that balances connections (layer 4), one long-lived HTTP/2 connection lands
  on one backend, so all calls from that client hit one instance — a known gRPC problem. Balance per request (layer 7,
  or on the client side), or open several connections.

HTTP/2 moves the limit from connections to streams per connection — and one connection can pin all traffic to one
backend.

</details>

## Absorbing load with queues

### How do you take write spikes the database cannot keep up with?
<details><summary>Show answer</summary>

**Queue-based load leveling:** put a message queue between the API and the DB.

- The API checks the request, writes it to the queue (Kafka, RabbitMQ), and returns `202 Accepted`, often with a
  status URL. The request thread is free in milliseconds.
- Workers read from the queue at a fixed concurrency the DB can handle. A spike becomes a backlog in the broker, not a
  pile of waiting threads and connections.

What it costs:

- The caller gets no result in the response, only a promise; it must poll or get a callback.
- Delivery is at least once: consumers see duplicates and must be idempotent (safe to run twice).
- A queue absorbs spikes, not lasting overload. If input stays above what the workers handle, the backlog grows
  without end — watch queue depth and message age, and decide what happens to messages that get too old.
- The broker is now on the write path: if it is down, the API cannot accept writes.

A queue turns a write spike into a backlog the DB drains at its own pace, paid for with a delayed, at-least-once
result.

</details>

### How many consumer threads should write to the DB?
<details><summary>Show answer</summary>

- No more than the connections they can get. 50 consumer threads and a pool of 20: 30 threads wait on the pool and add
  nothing.
- If consumers share the pool with REST requests, a backlog makes consumers hold every connection, and REST requests
  wait behind them. Keep consumer concurrency below the pool size, or give consumers their own pool (a separate
  `DataSource`).
- Kafka caps it too: in one consumer group, each partition goes to at most one consumer, so consumers beyond the
  partition count sit idle. 12 partitions → at most 12 busy consumers, whatever `concurrency` is set to.
- Unlike a REST request, a message can wait safely in the broker. Fewer consumers means a longer backlog, not errors —
  so consumers are the right place to slow down.

Size consumers by the scarcest of: DB connections left for them, partitions, and what the DB can take; the broker holds
the rest.

</details>


### How should a service send webhooks to customers?
<details><summary>Show answer</summary>

Not from the request thread. The receivers are outside your control: one customer's slow server holds your threads for
its full timeout, and
[enough of those stop your service](7.01_Capacity_and_Isolation.md#how-does-one-slow-dependency-stop-a-whole-service).

- Write the event to a queue, or to an outbox table in the same transaction as the business change, and return.
- Workers deliver with short connect and read timeouts.
- Limit concurrent deliveries per receiver (or use a queue per receiver), so one slow or dead receiver does not delay
  everyone else's events.
- Retry with growing delays over hours, then move the event to a dead-letter store after N attempts.
- Send an event ID with each delivery, so receivers can drop duplicates — retries mean duplicates.
- Pause delivery to a receiver that keeps failing, instead of spending workers on it.

Webhooks go out from a queue with a limit per receiver, so a customer's slow server stays the customer's problem.

</details>

## Caching under load

### What happens when a hot cache entry expires?
<details><summary>Show answer</summary>

**Cache stampede (thundering herd):**

- A popular entry — say, read 500 times a second — expires.
- Every request that arrives before the new value is stored sees a miss. If the DB query takes 200 ms, about 100
  requests run the same query at once.
- They all take DB connections and DB CPU for identical work. The query slows down because of the crowd, so the window
  grows and even more requests miss.
- Entries loaded together at startup expire together, so it can hit many keys at the same moment.

A cache keeps load off the DB only while it holds the value; the moment it doesn't, all of that load arrives at once.

</details>

### How do you stop many requests rebuilding one cache entry?
<details><summary>Show answer</summary>

- **Load once per key** — the first request loads, the others wait for its result. Caffeine
  `cache.get(key, k -> load(k))` runs the loader at most once per key; Spring `@Cacheable(sync = true)` does the same.
  This works per JVM: 10 instances means at most 10 loads, which is usually fine.
- **Refresh before expiry** — Caffeine `refreshAfterWrite`: after the refresh time, the next read starts one
  background reload and keeps getting the old value meanwhile. Nobody waits, nobody misses.
- **Spread the expiry** — add a random part to each TTL, so entries loaded together do not expire together.
- **Lock across instances** — a distributed lock (e.g. in Redis) when even one load per instance is too much. Costs a
  network round trip and handling of a lock whose holder died.

One loader per key, a refresh before expiry, and random TTLs keep the crowd from reaching the DB at once.

</details>
