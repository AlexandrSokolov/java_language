### What is lost when work moves to another thread?
<details><summary>Show answer</summary>

Anything tied to the request thread through `ThreadLocal`. Thread-bound context stays on its thread; it does not
follow the task to the pool:

```java
@Transactional
public CompletableFuture<Void> placeOrder(Order o) {
  orderRepo.save(o);                                                      // request thread: in the transaction
  return CompletableFuture.runAsync(() -> stockRepo.reserve(o), dbPool);  // pool thread: no transaction, no user,
}                                                                         // no request ID in the logs
```

- **Transaction (`@Transactional`):** the connection and transaction state are bound to the request thread, and the
  transaction [can't follow the task](#can-a-transaction-follow-work-to-another-thread). The task runs with its own
  connection and commit, so a failure can leave half the work committed. Here the transaction even commits when the
  method returns, before `reserve` runs.
- **Security context:** the authenticated user is stored on the thread. The pool thread runs
  [with no user](#how-does-the-user-reach-a-pool-task), so permission checks fail with unexpected `401` or `403`
  errors.
- **Logging context (MDC):** request IDs and trace IDs [disappear](#how-do-log-ids-reach-a-pool-task) from the task's
  log lines, so its logs can't be tied back to the request.
- **Request-scoped data:** request-scoped beans and the current-request holder
  [are not available](#how-does-request-data-reach-a-pool-task).

Anything stored per thread stays behind; pass it on, or rebuild it in the task.

</details>

### Can a transaction follow work to another thread?
<details><summary>Show answer</summary>

No. A transaction is bound to the thread and connection that started it. Keep every step of one transaction on one
thread:

- **Move the whole unit into the task:** the task calls one `@Transactional` method, on another bean so the proxy
  applies, and that method does all the writes.
- **Or keep the writes on the request thread,** and move only side effects outside the DB (email, events) to another
  thread, after the commit.

If the steps must run on different threads, they are separate transactions; undoing one after the other fails is up to
you.

One transaction, one thread: a thread hop always starts a new one.

</details>

### How does the user reach a pool task?
<details><summary>Show answer</summary>

Copy the security context into each task, and clear it when the task ends:

- **Spring:** wrap the pool in `DelegatingSecurityContextExecutorService`; it does both for every task.
- **Jakarta EE:** use a `ManagedExecutorService`; it carries the security context by default.
- **Or pass the user explicitly** as a plain value.

Never switch to an inheritable `ThreadLocal`: pool threads are created once and reused, so each keeps the user of
whichever request created it, and later tasks run as that user.

Copy the user per task, not per thread.

</details>

### How do log IDs reach a pool task?
<details><summary>Show answer</summary>

Copy the MDC into each task, and clear it when the task ends:

```java
executor.setTaskDecorator(task -> {                    // Spring's ThreadPoolTaskExecutor
  Map<String, String> mdc = MDC.getCopyOfContextMap();  // captured on the submitting thread
  return () -> {
    if (mdc != null) {
      MDC.setContextMap(mdc);
    }
    try {
      task.run();
    } finally {
      MDC.clear();                                      // the pool thread leaves clean
    }
  };
});
```

Tracing libraries (Micrometer Tracing, OpenTelemetry) can do the same for trace IDs.

Copy the MDC in, clear it out, once per task.

</details>

### How does request data reach a pool task?
<details><summary>Show answer</summary>

Read it on the request thread, and pass plain values into the task (user ID, locale, a header value). Don't touch
request-scoped beans or the current-request holder inside the task:

- The task may run after the request has finished, when those objects are gone.
- The container may reuse the request object for another request, so a late read can return someone else's data.

Take what the task needs from the request up front; the task gets values, not the request.

</details>

### How do transactions work in a non-blocking stack?
<details><summary>Show answer</summary>

In blocking code, the transaction sits on the request thread. In a non-blocking chain the steps run on different
threads, so the transaction must travel with the chain instead. The data library hands you a session, you run the steps
on it, and it commits when the chain completes:

```java
public CompletionStage<Void> transfer(long fromId, long toId, BigDecimal amount) {
  return sessionFactory.withTransaction((session, tx) ->
      session.find(Account.class, fromId)
          .thenCompose(from -> session.find(Account.class, toId)
              .thenAccept(to -> {
                from.debit(amount);
                to.credit(amount);
              })));  // committed when this stage completes; rolled back if it fails
}
```

- **Plain Java has no transactions of its own:** `CompletableFuture` knows nothing about connections, so the
  transaction must come from the data library. Above, it's Hibernate Reactive's Stage API, which uses only JDK types.
- **Spring:** its reactive transactions work only on methods that return Reactor types (`Mono` / `Flux`). For
  `CompletableFuture` chains it has none: `@Transactional` commits when the method returns, before the async steps run
  ([snippet #13](#describe-a-code-snippet-13)).

Two rules carry over from blocking code:
- The commit happens when the whole chain completes, not when the method returns.
- The connection is held for the whole chain, so remote calls still don't belong inside it
  ([snippet #18](#describe-a-code-snippet-18)).

Without a thread per request, the transaction travels with the chain; a plain future carries none.

</details>

### Why is thread context harder in a non-blocking chain?
<details><summary>Show answer</summary>

Behind a pool, the hop is one place you control: you submit to your executor, so you wrap it once and every task gets
the context. In a non-blocking chain, the thread changes at every reply, to threads you don't own (the client's event
loops), and there is no executor to wrap:

```java
MDC.put("requestId", requestId);
return client.fetchAsync(p)                          // the reply arrives on the client's event loop
    .thenApply(reply -> {
      log.info("reply received");                    // runs on that event loop: no requestId in this line
      return toScore(reply);
    });
```

Three ways to carry it:

- **Pass values explicitly:** carry what later steps need (user, tenant, request ID) as parameters or in a small
  context object. Plain Java, always works; the cost is that every step's signature carries it.
- **Restore it around each step:** capture the context once, and set and clear it inside every step.
```java
  static <T, R> Function<T, R> withMdc(Map<String, String> mdc, Function<T, R> step) {
    return t -> {
      MDC.setContextMap(mdc);
      try {
        return step.apply(t);
      } finally {
        MDC.clear();                                 // the event loop leaves clean
      }
    };
  }
  // .thenApply(withMdc(mdc, reply -> toScore(reply)))
```
It works, but every step must remember it.
- **A context-propagation library:** Micrometer Context Propagation captures the registered `ThreadLocal`s (MDC,
  security, tracing) and restores them around each step. Reactor does this automatically once
  `Hooks.enableAutomaticContextPropagation()` is on.

Spring's own non-blocking replacements (such as `ReactiveSecurityContextHolder`) keep the value in the chain instead of
on the thread, but they work only with Reactor types.

Behind a pool, wrap the executor once; in a non-blocking chain the thread changes at every reply, so the context must
travel with the chain itself.

</details>
