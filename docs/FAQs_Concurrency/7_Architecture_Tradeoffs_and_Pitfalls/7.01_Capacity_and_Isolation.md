### How many threads for a DB call pool?
<details><summary>Show answer</summary>

About as many as the JDBC pool has connections. Each blocking call holds a thread and a connection for its whole
duration, so the smaller of the two sets the limit:

- **More threads than connections:** e.g. 200 threads, 10 connections (HikariCP's default). 190 threads wait inside
  `getConnection()`, up to 30 s by default, and then the call fails. The extra threads add nothing: the DB still runs
  10 queries at a time.
- **Fewer threads than connections:** connections sit idle, and the DB could take more work than you send it.

The connection pool itself is sized to what the DB can handle, not to your traffic, and the thread pool follows it.

Size the thread pool to the connection pool; size the connection pool to the database.

</details>


### How do you cap a dependency without a thread pool?
<details><summary>Show answer</summary>

With a limit on calls in flight instead of threads. Two places to put it:

**1. The client's connection pool.** Its size caps the calls at once, and a bounded wait queue with a timeout makes
the overflow fail fast:

```java
ConnectionProvider provider = ConnectionProvider.builder("bureau")
    .maxConnections(100)                           // the partner allows 100 calls at once
    .pendingAcquireMaxCount(200)                   // at most 200 calls waiting for a connection
    .pendingAcquireTimeout(Duration.ofSeconds(1))  // then fail fast
    .build();
WebClient bureau = WebClient.builder()
    .clientConnector(new ReactorClientHttpConnector(HttpClient.create(provider)))
    .build();
```

For the DB, the R2DBC pool's maximum size plays the same role.

**2. A permit counter per dependency.** A `Semaphore`, or a library bulkhead such as Resilience4j's. It must never
block, so use `tryAcquire`, not `acquire`:

```java
private final Semaphore bureauPermits = new Semaphore(100);

CompletableFuture<Score> score(Person p) {
  if (!bureauPermits.tryAcquire()) {
    return CompletableFuture.failedFuture(new BureauBusyException());  // reject at once; never wait for a permit
  }
  return bureau.fetchScoreAsync(p)
      .whenComplete((score, ex) -> bureauPermits.release());
}
```

On an event loop, a blocking `acquire()` would stall every connection that loop serves.

Without thread pools, the limit is a count of calls in flight: cap it, bound the wait, and never block to take a
permit.

</details>

### Connection pool vs semaphore?
<details><summary>Show answer</summary>

Both make extra threads wait. They differ in what they count:

- **Connection pool:** counts real connections to one database. The cap comes built in: `getConnection()` waits when
  all connections are borrowed, and throws after a timeout (HikariCP: 30 s by default). It limits only the calls that
  go through that pool.
- **`Semaphore`:** counts permits, a plain number you pick. You write the limit yourself (`acquire()`, then
  `release()` in `finally`), so it fits any call: an external API, a file store, or a subset of database calls.
  `acquire()` waits with no time limit; `tryAcquire(timeout)` gives up.

For the database, the pool already caps calls. Add a `Semaphore` for a resource with no pool, or for a tighter cap on
some calls (at most 5 heavy report queries out of 20 connections).

A pool limits the resource it owns; a semaphore limits any code you wrap.

</details>
