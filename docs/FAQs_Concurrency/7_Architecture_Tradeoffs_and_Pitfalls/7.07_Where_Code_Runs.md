# 7.06 Where Code Runs

Which thread, pool, process or machine actually runs a piece of code, and what follows from that. Covers which thread
runs a CompletableFuture stage or a client callback, event-loop threads where one blocking call stalls everything,
virtual threads and the platform threads under them, what the JVM sees inside a container (CPU count, memory), and
code that runs on many instances at once: a scheduled job that fires on every node, a lock or cache that covers only
one JVM.

Layers: Java code, frameworks and HTTP clients, the JVM, containers, the set of running instances.
Not here: how big a pool should be (7.01); what context travels with the work (7.05).

## Which thread runs the work

### Where should blocking async work run?
<details><summary>Show answer</summary>

Not in `ForkJoinPool.commonPool()` — but that is where it goes by default:

- `CompletableFuture.supplyAsync(...)`, `runAsync(...)` and every `...Async` stage without an executor argument
- `parallelStream()`
- library code that does the same

The common pool is one pool for the whole JVM, sized for CPU work: cores − 1 threads (7 on 8 cores). A blocking call in
it (JDBC, HTTP, `Thread.sleep`) takes one of those few threads for the whole wait. Seven slow remote calls at once, and
every async stage and parallel stream in the JVM stops — including code that never touches that remote service.

Pass an executor sized for waiting:

```java
CompletableFuture<Price> price =
    CompletableFuture.supplyAsync(() -> client.fetchPrice(id), ioExecutor);  // not the common pool
```

`ioExecutor` can be a bounded `ThreadPoolExecutor` or, on Java 21+, `Executors.newVirtualThreadPerTaskExecutor()`
with the limit placed on the [scarce resource](#do-virtual-threads-remove-the-need-for-limits) instead.

The common pool is shared by everything and sized for CPU; blocking work needs its own executor.

</details>

### One blocking call inside a non-blocking chain — effect?
<details><summary>Show answer</summary>

It usually runs on an event loop, and then it stalls far more than one request:

```java
return bureau.fetchScoreAsync(p)                     // completes on the client's event loop
    .thenApply(score -> auditJdbc.save(p, score));   // JDBC call on that event loop
```

A plain `thenApply` runs on the thread that completed the previous step, here the client's event loop. That thread
serves many connections. Say 8 event loops each serve about 1,000 connections: one 50 ms JDBC call freezes 1,000
connections for 50 ms, and 8 such calls at once freeze the whole server. There is no error, only latency spikes in
unrelated requests. It is worse than blocking a pool thread, which holds up only its own request.

**Fix:** make the call non-blocking. If that's not possible, move it off the loop on purpose, to a bounded pool:

```java
return bureau.fetchScoreAsync(p)
    .thenApplyAsync(score -> auditJdbc.save(p, score), dbPool);  // the blocking call gets its own bounded pool
```

A blocking call on an [event loop](6.4_How_the_OS_Waits_on_IO.md#why-keep-slow-work-off-the-event-loop) stalls every
connection that loop serves: make it non-blocking, or move it to a bounded pool on purpose.

</details>

### Which thread runs the next stage?
<details><summary>Show answer</summary>

It depends on the method, and for a plain stage, on timing:

```java
CompletableFuture<Data> f = CompletableFuture.supplyAsync(() -> load(), ioPool);

f.thenApply(d -> parse(d));               // f still pending: runs on the thread that completes f (an ioPool thread)
                                          // f already complete: runs right here, on the calling thread
f.thenApplyAsync(d -> parse(d));          // the default executor: ForkJoinPool.commonPool()
f.thenApplyAsync(d -> parse(d), cpuPool); // cpuPool, always
```

- **Plain stage** (`thenApply`, `thenCompose`, `thenAccept`, `whenComplete`…): runs on the thread that completes the
  previous stage, or on the calling thread if that stage is already complete. When the two happen at the same moment,
  either thread may run it, so you can't rely on which.
- **`*Async` without an executor:** the common pool (or a new thread per task, if the common pool has fewer than 2
  threads).
- **`*Async` with an executor:** that executor.

It matters whenever the stage does real work. The completing thread may be a pool sized for something else, or an
[event loop](6.4_How_the_OS_Waits_on_IO.md#why-keep-slow-work-off-the-event-loop), and thread-bound context depends on
the thread too.

A plain stage runs on whichever thread completes the previous one, or on the caller if it is already done; only an
`*Async` stage with an executor names its thread.

</details>
