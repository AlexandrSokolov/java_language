# Capacity — Threads and Requests

How your own service runs its threads:
- how incoming requests use server threads
- how thread pools behave under load
- what still needs a limit when calls stop holding a thread

## Incoming requests (server side)

### What happens when all server threads are busy?
<details><summary>Show answer</summary>

Tomcat (the Spring Boot default server) takes requests in stages, with these defaults:

- `maxThreads` = 200 — requests that run at once, one thread each (`server.tomcat.threads.max`).
- `maxConnections` = 8192 — connections Tomcat accepts; above 200, their requests wait for a free thread
  (`server.tomcat.max-connections`).
- `acceptCount` = 100 — connections the OS holds in its accept queue once Tomcat stops accepting
  (`server.tomcat.accept-count`).
- Beyond that, new connections are refused or hang until the client's connect timeout.

What this means under load:

- The server does not say "busy" early. Thousands of requests can wait while 200 run, so callers see slow responses,
  not errors.
- Callers time out and retry while the server still works on the old request — the same work twice.
- Every waiting request counts as [in flight](7.01_Capacity_Pool_Sizing.md#how-many-requests-are-in-flight-at-once): its wait is added to its response time.

A full server queues quietly for a long time before it refuses anything.

</details>

### Should server threads outnumber DB connections?
<details><summary>Show answer</summary>

Usually yes — a waiting thread is cheap, and a [small DB pool is faster](7.03_Capacity_Dependencies.md#why-can-a-bigger-connection-pool-be-slower).
Take Tomcat with 200 threads and HikariCP with 20 connections:

- While the pool keeps up, the extra threads wait a few milliseconds for a connection and move on. Nothing is wrong.
- The pool keeps up while rate × connection hold time stays under 20. Past that, the pool's queue grows, and each
  waiting thread waits up to `connectionTimeout` (30 s by default).
- Soon all 200 threads wait on the pool. Endpoints that never touch the DB — health checks, cached data — get no
  thread either, so the instance looks dead.
- Kubernetes can then fail the liveness check and restart the pod. The other pods get its traffic and fall over the
  same way.

What keeps the mismatch safe:

- A short pool wait (well under the caller's timeout), so requests fail fast with 503 instead of holding a thread for
  30 s.
- A [bulkhead](7.04_Capacity_Slow_&_Overloaded_Dependencies.md#how-do-you-keep-one-slow-dependency-from-taking-every-thread) on
  DB-heavy endpoints, so they cannot take all 200 threads.
- Health and actuator endpoints on a separate port (`management.server.port`): Spring Boot then serves them from a
  separate server with its own threads.

More threads than connections is fine; it breaks only when the pool falls behind, so cap how long and how many threads
may wait.

</details>

### How do long-open connections change server capacity?
<details><summary>Show answer</summary>

Server-Sent Events and long polling keep a request open for minutes, waiting for something to send.

- With thread-per-request, each open stream holds a Tomcat thread the whole time. 200 open streams, and no thread is
  left for normal requests.
- Servlet async gives the thread back while the request waits: Spring MVC `SseEmitter`, `DeferredResult`, or a
  returned `CompletableFuture`. A thread is used only when there is something to write.
- The connection is still held: each open stream counts against Tomcat's `maxConnections` (8192) and uses an OS file
  descriptor. With async, connections, not threads, become the ceiling.
- Other ways out: virtual threads (Spring Boot 3.2+: `spring.threads.virtual.enabled=true`), where a blocked thread is
  cheap, or a non-blocking server (WebFlux).

Long-open requests must not hold a thread each; once they don't, the connection limit is the ceiling.

</details>

### Which limits stop one request from filling the heap?
<details><summary>Show answer</summary>

Thread and pool limits cap how many requests run, not how big one request is.

- **Output: rows with no limit** — "return all active users" works with 1,000 rows and throws `OutOfMemoryError` at
  5 million. Enforce a maximum page size on the server; stream large exports instead of loading them.
- **The driver may load everything anyway** — the PostgreSQL JDBC driver reads the whole result into memory by
  default. It streams only with a fetch size set and autocommit off (inside a transaction). MySQL's driver also reads
  everything by default.
- **Input: body with no limit** — Spring Boot's 2 MB limit (`server.tomcat.max-http-form-post-size`) applies to form
  posts only. A JSON body has no size limit by default: a huge body is read and parsed into objects. Set a limit at the
  proxy or gateway (nginx `client_max_body_size`, default 1 MB) or in a filter.

Every request needs a size limit in both directions, because one oversized request is enough to kill the instance.

</details>

## Thread pools under load

### When does a ThreadPoolExecutor add threads above core size?
<details><summary>Show answer</summary>

For each new task, `execute` checks in this order:

- Fewer than `corePoolSize` threads → start a new thread, even if other threads are idle.
- Otherwise → put the task in the queue.
- Queue full → start a new thread, up to `maximumPoolSize`.
- Pool at max and queue full → reject.

So threads above core start only when the queue is full.

- **Trap:** with an unbounded queue, the queue is never full. `maximumPoolSize` is ignored, the pool stays at core
  size under any load, and the [backlog grows in memory](#what-happens-when-an-executors-pool-falls-behind).

```java
new ThreadPoolExecutor(10, 100, 60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>());   // unbounded: never more than 10 threads, the 100 never happens
```

- A bounded queue makes max reachable, but only after the queue fills: with a queue of 1,000, a task waits behind
  1,000 others before the first extra thread starts.

Core first, queue second, extra threads last — and with an unbounded queue, "last" never comes.

</details>

### What happens when an Executors pool falls behind?
<details><summary>Show answer</summary>

The `Executors` factory methods each leave one thing without a limit:

- `newFixedThreadPool(n)` and `newSingleThreadExecutor()` — threads are fixed, but the queue is an unbounded
  `LinkedBlockingQueue`.
- `newCachedThreadPool()` — no queue, and threads are unbounded (`maximumPoolSize = Integer.MAX_VALUE`).

When tasks arrive faster than they finish:

- **Fixed pool, growing queue** — each task waits for every task ahead of it, so latency climbs with queue length.
  `submit` never fails, so nothing tells the producer to slow down. Tasks hold request data, so the heap fills, and the
  end is `OutOfMemoryError` — long after the real problem started.
- **Fixed pool, stale work** — tasks that waited long enough belong to callers who already timed out. The pool still
  runs them and spends its threads on answers nobody reads.
- **Cached pool** — a burst creates one thread per waiting task: thousands of threads, each with its own stack memory,
  until the JVM fails with `OutOfMemoryError` (unable to create native thread).

Each factory pool leaves one thing without a limit, and overload grows exactly there.

</details>

### What should a full pool do with new work?
<details><summary>Show answer</summary>

A bounded `ThreadPoolExecutor` reaches a point where every thread is busy and the queue is full. Its
`RejectedExecutionHandler` then decides what happens to the next task:

```java
ExecutorService pool = new ThreadPoolExecutor(
    16, 16, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),               // bounded: overload becomes visible
    new ThreadPoolExecutor.CallerRunsPolicy());  // what to do when full
```

- `AbortPolicy` (the default) — throws `RejectedExecutionException`. The caller knows at once and can answer 503 or
  try later. The safe default for request work.
- `CallerRunsPolicy` — the submitting thread runs the task itself, so the producer slows to the pool's speed:
  backpressure for free. Cost: the caller's thread is tied up. If it is a request thread, that request gets slower; if
  it is a single thread that pulls messages, it stops pulling — which is the point.
- `DiscardPolicy` — drops the new task silently. Only for work that may be lost (sampled metrics), and only with a
  counter, since nothing reports the loss.
- `DiscardOldestPolicy` — drops the oldest queued task and queues the new one. Fits work where only the latest value
  matters (status updates).

A bounded pool forces a choice: fail now, slow the producer, or drop — never wait without limit.

</details>

## When calls stop blocking a thread (async, virtual threads)

### Do virtual threads remove the need for limits?
<details><summary>Show answer</summary>

No. They remove the cost of threads, not the limits of what the threads wait on.

- A blocked virtual thread (unless pinned) frees its carrier thread, so 10,000 waiting requests no longer need 10,000
  platform threads. The thread count stops being the limit.
- The limit moves to what the threads wait on. 10,000 virtual threads still share 10 DB connections: 9,990 of them
  wait in the pool's queue, up to its timeout. A remote service with no limit in front of it gets all 10,000 calls at
  once.
- Do not pool virtual threads: they are cheap to create, and a pool of them only hides the real limit. Put the limit
  on the scarce resource itself:

```java
Semaphore permits = new Semaphore(50);                     // at most 50 calls in flight

Response call(Request r) throws InterruptedException {
  if (!permits.tryAcquire(200, TimeUnit.MILLISECONDS)) {   // limit the wait too
    throw new RejectedExecutionException("service busy");
  }
  try {
    return client.send(r);
  } finally {
    permits.release();
  }
}
```

- This shows what a platform thread pool did all along: besides saving thread creation, it limited concurrency. With
  virtual threads the two jobs separate — creation is free, so the limit must be written down on its own.

Virtual threads make waiting cheap, not the thing being waited on; the limit moves from the thread pool to an explicit
semaphore.

</details>

### When does an async HTTP client free the request thread?
<details><summary>Show answer</summary>

Only when the whole request path is async. A controller that calls an async client and then calls `join()` still holds
the Tomcat thread for the full wait — no better than a blocking client.

Spring MVC gives the thread back when the controller returns the future (Servlet async):

```java
@GetMapping("/prices/{id}")
CompletableFuture<Price> price(@PathVariable String id) {
  return client.fetchPriceAsync(id);   // Tomcat thread goes back to the pool here
}
```

- The response is written later, from the thread that completes the future.
- Costs: callbacks run on whatever thread completes the call — often the client's own small set of threads — so
  blocking work inside them can stall other calls; `ThreadLocal` context (transaction, security, log MDC) does not
  follow the callback; stack traces get harder to read.
- On Java 21+, virtual threads give the same thread saving with plain blocking code
  (`spring.threads.virtual.enabled=true`).
- The limits do not disappear; [they move](#what-limits-work-when-calls-no-longer-block-a-thread).

An async client saves a thread only if nothing on the path waits for it.

</details>

### What limits work when calls no longer block a thread?
<details><summary>Show answer</summary>

With a blocking client, the thread pool is the limit: 200 threads, at most 200 calls in progress. A non-blocking client
(or virtual threads) removes that limit — the code that starts calls never waits, so it can start them faster than they
finish.

- **Connections** — a client without a pool cap opens a connection per pending call: thousands of TCP connections, OS
  file-descriptor limits, and a downstream that gets everything at once.
- **Memory** — calls the client cannot send yet wait in its internal queue. The producer keeps adding, the heap fills,
  `OutOfMemoryError`. This is missing **backpressure**: nothing makes the producer slow down.

So the limit must be set on purpose: a cap on connections in the client pool, a cap on in-flight calls in front of it
(a [`Semaphore`](#do-virtual-threads-remove-the-need-for-limits), a bulkhead), and a
limit on how long a call may wait for a slot.

Taking the thread out of the wait takes away the limit the thread used to give; it has to be added back explicitly.

</details>

### How do you cap a dependency without a thread pool?
<details><summary>Show answer</summary>

With a limit on calls in flight instead of threads. Two places to put it:

**1. The client's connection pool.** Its size caps the calls at once, and a bounded wait queue with a timeout makes
the overflow fail fast:

```java
ConnectionProvider provider = ConnectionProvider.builder("bureau")
    .maxConnections(100)                           // the partner allows 100 calls at once
    .pendingAcquireMaxCount(200)                   // at most 200 calls waiting for a connection
    .pendingAcquireTimeout(Duration.ofSeconds(1))  // then fail fast
    .build();
WebClient bureau = WebClient.builder()
    .clientConnector(new ReactorClientHttpConnector(HttpClient.create(provider)))
    .build();
```

For the DB, the R2DBC pool's maximum size plays the same role.

**2. A permit counter per dependency.** A `Semaphore`, or a library bulkhead such as Resilience4j's. It must never
block, so use `tryAcquire`, not `acquire`:

```java
private final Semaphore bureauPermits = new Semaphore(100);

CompletableFuture<Score> score(Person p) {
  if (!bureauPermits.tryAcquire()) {
    return CompletableFuture.failedFuture(new BureauBusyException());  // reject at once; never wait for a permit
  }
  return bureau.fetchScoreAsync(p)
      .whenComplete((score, ex) -> bureauPermits.release());
}
```

On an event loop, a blocking `acquire()` would stall every connection that loop serves.

Without thread pools, the limit is a count of calls in flight: cap it, bound the wait, and never block to take a
permit.

</details>
