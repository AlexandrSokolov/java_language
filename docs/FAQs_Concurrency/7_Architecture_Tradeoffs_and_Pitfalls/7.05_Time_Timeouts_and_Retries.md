# Time — Timeouts and Retries

How long a call may wait, and what happens after it gives up. Covers the waits at each layer (connect, read, waiting
for a pooled connection, row locks, the whole request), passing one time budget down a chain of calls, what a timeout
really stops and what keeps running, the unknown result after a timeout (did the write happen?), and how to retry
safely: which failures to retry, backoff, retry limits, and making a repeated call safe (idempotency).

Layers: Java code, HTTP and DB clients, the database, load balancers and gateways, message brokers.
Not here: how many calls run at once (7.01–7.03); circuit breakers, rate limits and load shedding (7.03).

## Timeouts

### Which waits must an outgoing call limit?
<details><summary>Show answer</summary>

A call to a DB or another service can wait in three places. Each needs its own limit:

- **Pool wait** — for a free connection from the pool. HikariCP `connectionTimeout` (default 30 s); Apache HttpClient
  `connectionRequestTimeout`.
- **Connect** — to open the TCP (and TLS) connection. A healthy server answers in milliseconds, so keep it short.
- **Read** — for the response. Set it from the service's normal slow case (p99) plus margin.

Traps:

- No limit is a common default. `HttpURLConnection` (behind the classic `RestTemplate` default) has connect and read
  timeouts of 0 = wait forever; a JDK `HttpRequest` without `.timeout(...)` also waits forever. A call with no limit
  holds its thread for good, so [one hung dependency fills any pool](#how-many-requests-are-in-flight-at-once).
- A socket read timeout limits the gap between two reads, not the whole response. A server that sends one byte every
  few seconds never trips it. For a limit on the whole call, add a deadline around it, e.g. `orTimeout` on a
  `CompletableFuture` — it frees the caller; the call itself runs on until its own timeouts fire.
- The waits must fit inside what the caller will wait. A 30 s pool wait inside a request whose caller gives up after
  5 s spends 25 s on an answer nobody reads.

Every wait gets its own limit, and together they must fit inside the caller's deadline.

</details>

### How long can a query wait for a locked row?
<details><summary>Show answer</summary>

- PostgreSQL: forever by default — `lock_timeout` and `statement_timeout` are both 0 (off).
- MySQL InnoDB: 50 s (`innodb_lock_wait_timeout`).

While the query waits, its thread and its pool connection wait too. One slow transaction that holds a busy row (a
counter, an account balance, a status row) makes every request that needs that row queue behind it, and the pool fills.

- Deadlocks end on their own: PostgreSQL and InnoDB detect them and abort one transaction, usually within about a
  second. A plain wait behind a slow transaction has no such end.
- Set a limit: `lock_timeout` / `statement_timeout` for the DB user or per transaction (`SET LOCAL`), or a query
  timeout from Java (`Statement.setQueryTimeout`, `@Transactional(timeout = ...)`).
- Keep transactions that lock busy rows short — the lock is held until commit.

A lock wait holds a pool connection for as long as the lock holder runs; deadlocks get cut, plain waits need a timeout.

</details>

### What does a CompletableFuture timeout actually stop?
<details><summary>Show answer</summary>

```java
CompletableFuture
    .supplyAsync(() -> client.fetchPrice(id), ioExecutor)
    .completeOnTimeout(Price.UNKNOWN, 2, TimeUnit.SECONDS);  // or orTimeout(2, SECONDS) -> TimeoutException
```

- It stops the waiting: after 2 s the future completes — with the fallback (`completeOnTimeout`) or with a
  `TimeoutException` (`orTimeout`; both Java 9+). The caller and the later stages move on.
- It does not stop the work: `CompletableFuture` never interrupts the thread running the task (`cancel(true)` does not
  interrupt either). The `ioExecutor` thread stays busy until the HTTP call ends or its own socket timeout fires.
- So in a thread-pool bulkhead, abandoned calls still hold their slots. Without socket timeouts, a hung service fills
  the pool even though every caller already gave up.
- It is not a circuit breaker: every new call still starts and waits the full 2 s; nothing is remembered between calls.

A future timeout frees the caller, not the thread; only the call's own timeouts free the thread.

</details>


## Retries

### How do retries change the load?
<details><summary>Show answer</summary>

**Retry storm:**

- Each retry is a new request. Three attempts per call means up to 3× the load on the dependency — exactly when it is
  already slow or failing.
- Layers multiply. A → B → C, and both A and B try 3 times: C can get 3 × 3 = 9 calls for one user action. One more
  layer, 27.
- The first attempt is often still running. The caller timed out, but the server keeps working on it, and now it works
  on the retry too.
- Retries without delay come in waves: clients that failed at the same moment retry at the same moment.

A retry is extra load, sent to the part of the system that has the least room for it.

</details>

### How do you retry without adding to overload?
<details><summary>Show answer</summary>

- **One layer retries** — usually the one closest to the user, or the one that owns the operation; the layers below
  fail fast. This stops the [multiplication across layers](#how-do-retries-change-the-load).
- **Wait longer each time, with randomness** — about 100 ms, 200 ms, 400 ms, each randomized (backoff with jitter), so
  clients that failed together do not retry together.
- **Cap retries with a budget** — e.g. retries may add at most 10% to normal traffic; once that is spent, fail
  instead. A fixed "3 attempts" triples the load in an outage; a budget does not.
- **Retry only what is safe and may pass** — idempotent operations (safe to run twice), or ones with an idempotency
  key; and only for errors that can go away: timeouts, 503, connection reset. Never for 400 or a validation error.
- **Don't retry into an open [circuit breaker](#bulkhead-vs-rate-limiter-vs-circuit-breaker)**, and respect
  `Retry-After` when the server sends it.
- **Fit inside the caller's deadline** — a retry that finishes after the caller gave up is pure extra load.

Spend retries on one layer, spread them out in time, and keep them within a budget.

</details>
