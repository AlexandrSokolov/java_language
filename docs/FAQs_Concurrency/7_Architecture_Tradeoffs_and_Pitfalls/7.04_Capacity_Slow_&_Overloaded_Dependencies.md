# 7.03 Capacity — Slow and Overloaded Dependencies

What to do when a dependency is slow or overloaded even with the limits from 
[7.02](7.02_Capacity_Dependencies.md) in place: 
- keeping it from taking every thread, 
- cutting load with circuit breakers, 
- rate limits and load shedding.

## Isolation (one slow dependency)

### How does one slow dependency stop a whole service?
<details><summary>Show answer</summary>

**Cascading failure**, step by step:

- All endpoints share one pool of server threads (Tomcat: 200). `/checkout` calls a payment service; `/catalog` does
  not.
- Payment slows from 100 ms to 10 s. At 20 checkout requests per second,
  [that is 200 requests in flight](#how-many-requests-are-in-flight-at-once) — all 200 threads now wait on payment.
- `/catalog` has nothing to do with payment, but it needs a thread too. It queues behind, then times out. The whole
  service looks down.
- The services that call this one now wait on it, so their threads fill the same way. The slowdown climbs the call
  chain one service at a time.
- Every layer that [retries](#how-do-retries-change-the-load) adds more calls to the service that is already slow.

A shared pool lets the slowest dependency set the capacity of every endpoint.

</details>

### How do you keep one slow dependency from taking every thread?
<details><summary>Show answer</summary>

**Bulkhead** — named after the walls inside a ship's hull, so one leak floods one section, not the whole ship:

- Give each dependency its own limit on calls in flight: payment ≤ 30, email ≤ 10, and so on.
- Payment slows down: its 30 slots fill, and call 31 is rejected at once instead of taking a server thread. The other
  170 threads keep serving everything else.
- The rejected call fails fast: the caller gets an error or a fallback in milliseconds, not after a 10 s wait.
- Size each limit per dependency by [Little's Law](#how-many-requests-are-in-flight-at-once): peak rate × normal
  latency, plus margin. The call's timeout sets the worst case.
- Tools: a [`Semaphore` per dependency](#do-virtual-threads-remove-the-need-for-limits), Resilience4j `Bulkhead` /
  `ThreadPoolBulkhead`, or the [per-host limit](#what-limits-concurrent-calls-to-one-service) of an HTTP client pool
  for connections. Hystrix made the pattern known; it has been in maintenance mode since 2018.

Split shared capacity per dependency, so a slow one fills its own share and stops there.

</details>

### Thread-pool or semaphore bulkhead?
<details><summary>Show answer</summary>

Both cap the calls in flight to one dependency. They differ in which thread makes the call.

**Semaphore** — the caller's own thread makes the call after taking a permit.

- Buys: no hand-off between threads; [context](7.3_Context_and_Transaction_Boundaries.md) held in `ThreadLocal`
  (transaction, security, log MDC) just works; almost no cost.
- Costs: the caller cannot walk away from a stuck call. Its thread stays blocked until the call's own timeout fires,
  so the bulkhead is only as good as that timeout.

**Thread pool** — the call runs on a separate pool for that dependency; the caller waits on a `Future`.

- Buys: the caller can stop at its own deadline (`future.get(timeout)`) even if the call never returns; the pool's
  queue absorbs short bursts.
- Costs: a hand-off per call; `ThreadLocal` context does not follow the call and must be copied over; an abandoned call
  still holds a pool thread until it ends; one more pool to size and watch.

Which one: a client with timeouts you trust, or virtual threads → semaphore. A client you cannot trust to time out, or
a caller that needs a hard deadline → thread pool.

Semaphore: cheap and same-thread, but trusts the call's timeout. Thread pool: a hard deadline for the caller, paid for
with a hand-off and context copying.

</details>

### Connection pool vs semaphore?
<details><summary>Show answer</summary>

Both make extra threads wait. They differ in what they count:

- **Connection pool:** counts real connections to one database. The cap comes built in: `getConnection()` waits when
  all connections are borrowed, and throws after a timeout (HikariCP: 30 s by default). It limits only the calls that
  go through that pool.
- **`Semaphore`:** counts permits, a plain number you pick. You write the limit yourself (`acquire()`, then
  `release()` in `finally`), so it fits any call: an external API, a file store, or a subset of database calls.
  `acquire()` waits with no time limit; `tryAcquire(timeout)` gives up.

For the database, the pool already caps calls. Add a `Semaphore` for a resource with no pool, or for a tighter cap on
some calls (at most 5 heavy report queries out of 20 connections).

A pool limits the resource it owns; a semaphore limits any code you wrap.

</details>

### Which rejection policy breaks a bulkhead?
<details><summary>Show answer</summary>

`CallerRunsPolicy`.

- A [bulkhead](7.01_Capacity_and_Isolation.md#how-do-you-keep-one-slow-dependency-from-taking-every-thread) pool for
  the payment service: 20 threads, a queue of 50. Payment slows down; threads and queue fill.
- With `CallerRunsPolicy`, task 71 runs on the thread that submitted it — a Tomcat request thread. The slow payment
  call now runs outside the bulkhead, on the shared request threads.
- Every further call does the same, so the slow dependency takes Tomcat threads one by one — exactly what the bulkhead
  was there to stop.
- On a bulkhead pool, reject instead (`AbortPolicy`) and answer with a fallback or 503. `CallerRunsPolicy` fits where
  slowing the producer is the goal (a single thread that pulls messages), not where the producer is a shared request
  thread.

`CallerRunsPolicy` moves overflow onto the caller's thread, so on a bulkhead it moves the slow call back into the shared
pool.

</details>

### What should a request do when an optional dependency fails?
<details><summary>Show answer</summary>

**Graceful degradation:** answer without the part that failed, instead of failing the whole request.

- Split dependencies first. Core (payment, order write): failure means an error. Optional (recommendations, reviews,
  personalization): failure means a smaller answer.
- Fallbacks: the last good value from a cache, a static default (global top sellers), or an empty section.
- Keep the fallback cheap and local. A fallback that calls another remote service can fail the same way and adds load
  where there is no room.
- Get to the fallback fast: an open circuit breaker or a full bulkhead returns it in milliseconds, not after the
  timeout.
- Count every fallback in metrics. A silent fallback can hide an outage for days.

An optional dependency gets a cheap fallback, so its failure shrinks the answer instead of breaking it.

</details>


## Overload protection

### Why add a circuit breaker when every call has a timeout?
<details><summary>Show answer</summary>

- A timeout ends one call, and the next call waits the full timeout again. During an outage at 20 calls/s with a 5 s
  timeout, 20 × 5 = 100 threads are always busy learning the same thing.
- A circuit breaker remembers: once the failure or slow-call rate passes its threshold, it fails calls at once, and
  those 100 threads drop to almost none.
- It also stops sending load to a service that is trying to recover, and lets a few test calls through to see when it
  is back.
- Async calls or virtual threads do not remove the problem: doomed calls then hold memory and connections instead of
  threads.
- The timeout is still needed: it turns a hang into a failure the breaker can count, and it bounds the calls made while
  the breaker is closed.

A timeout limits each call; a circuit breaker limits how many calls go into a known failure.

</details>

### Bulkhead vs rate limiter vs circuit breaker?
<details><summary>Show answer</summary>

They count different things, so each one is blind to what the others catch:

| | Limits | Protects against | Blind to |
|---|---|---|---|
| Bulkhead | calls in flight at once | slow calls piling up | call rate, errors |
| Rate limiter | calls started per second | too many calls (quota, fragile service) | how long calls take |
| Circuit breaker | whether to call at all | calls that will almost surely fail | load, while it lets calls through |

- A rate limiter alone does not stop slowness: 100 calls/s at 10 s each is 1,000 calls in flight.
- A bulkhead alone keeps sending calls to a failing service as long as it has free slots.
- A circuit breaker opens when the error rate or slow-call rate passes a threshold, fails every call at once for a
  while, then lets a few test calls through to see if the service is back.
- They stack: rate limiter for the agreed rate, bulkhead for slowness, circuit breaker for failure, timeouts under all
  three.

Bulkhead counts calls in flight, rate limiter counts calls per second, circuit breaker counts failures.

</details>


### Rate limiting vs load shedding?
<details><summary>Show answer</summary>

- **Rate limiting** — per client: "this client sent more than its share". Applies even when the server is idle.
  Answer `429 Too Many Requests` with `Retry-After`.
- **Load shedding** — per server: "I am too busy, no matter who asks". Applies only under overload. Answer
  `503 Service Unavailable` with `Retry-After`.
  - It triggers on signals that track waiting — requests in flight, time spent in the queue, latency — not on CPU. A
    service that waits on a DB or remote calls fills up
    [while the CPU is idle](7.01_Capacity_and_Isolation.md#what-runs-out-before-the-cpu-does).
  - It drops the least important work first: keep checkout, drop recommendations, keep health checks answering.

Rate limiting keeps clients fair to each other; load shedding protects the server from everyone at once.

</details>

### How do rate limiters treat a burst?
<details><summary>Show answer</summary>

- **Token bucket** — tokens refill at a steady rate up to a maximum; each request takes one. A burst passes at once
  while tokens last, then requests are held to the refill rate. Two settings: rate and burst size. AWS API Gateway
  throttling works this way.
- **Leaky bucket** — requests enter a bounded queue that drains at a fixed rate; when the queue is full, the rest are
  dropped. Output is perfectly even; a burst is delayed, never passed at once. Fits a fragile downstream that cannot
  take bursts. nginx `limit_req` (without `nodelay`) works this way.
- **Fixed window** — count requests per window (per second, per minute) and reset at the edge. Simple, but up to 2×
  the limit gets through around the edge: the end of one window plus the start of the next. Resilience4j `RateLimiter`
  hands out permits per fixed period.
- **Sliding window** — counts over the last N seconds at any moment, which removes the edge burst at the cost of more
  memory or computation.

Token bucket lets bursts through up to a size, leaky bucket smooths them into a queue, fixed window lets a double burst
slip through at the edge.

</details>

### Where should rate limits run?
<details><summary>Show answer</summary>

- **At the edge (gateway, WAF, proxy)** — limits by IP or API key before the request reaches Java. A rejected request
  costs no TLS work in the app, no Tomcat thread, no heap. The right place for volume and abuse limits.
- **In the app** — limits that need data only the app has: per customer plan, per tenant, per expensive operation.
- **Next to an outgoing call** — limits that protect someone else (a partner API with a quota) belong where the call is
  made, not at the edge.

Trap: an in-memory limiter (Resilience4j, Bucket4j without a shared store) counts on one instance only. A limit of
100/s on 10 instances lets 1,000/s through, and the total changes whenever autoscaling adds an instance. A global limit
needs a shared counter (Redis, Bucket4j with a distributed backend) or the edge.

Each limit runs where its data is and before the resources it protects; in-memory limits are per instance.

</details>
