### Why not write your own work queue or use threads directly?
<details><summary>Show answer</summary>

Both are obsolete and failure-prone. A hand-rolled work queue is subtle, delicate code — easy to get wrong in ways
that cause safety and liveness failures. Working directly with `Thread` has the same problem at a lower level.

The executor framework replaces all of it. A better work queue than a page of hand-written code is one line:

```java
ExecutorService exec = Executors.newSingleThreadExecutor();
exec.execute(runnable);
```

So don't manage threads and queues by hand — describe the work and let an executor run it.

</details>

### What did the executor framework separate?
<details><summary>Show answer</summary>

It split the **work** from the **thing that runs it** — two things a raw `Thread` fuses into one.

- With a raw `Thread`, the thread *is* both the unit of work and the mechanism that executes it. You can't change
  how work runs without rewriting the work.
- With the executor framework, the **task** is the unit of work, and the **executor service** is the mechanism that
  runs it. They're separate.

Because they're separate, you pick how work runs — one thread, a fixed pool, scheduled — and change that choice
later without touching the tasks. Same move the Collections Framework made for grouping data: name the abstraction,
swap the implementation freely.

</details>

### Runnable vs Callable?
<details><summary>Show answer</summary>

Both are tasks — a unit of work handed to an executor. The difference is what they give back:

- **`Runnable`** — runs, returns nothing, can't throw checked exceptions.
- **`Callable`** — runs, **returns a value**, and **can throw checked exceptions**.

Reach for `Callable` when the work produces a result or may fail in a way the caller must see; `Runnable` when it's
fire-and-forget.

</details>

### What can an executor service do? (reference)
<details><summary>Show answer</summary>

A lookup card — the range of things an `ExecutorService` offers, grouped by what you're doing:

- **Submit work** — `execute` (fire-and-forget), `submit` (returns a `Future`).
- **Wait for results** — `get` on a `Future` (one task), `invokeAny` (any one of many), `invokeAll` (all of many).
- **Take results as they finish** — `ExecutorCompletionService`, which hands them back in completion order.
- **Schedule** — `ScheduledThreadPoolExecutor` for tasks that run later or repeat.
- **Wind down** — `awaitTermination` to wait for the service to finish.

Treat this as a menu to recognize, not a list to recite — you look up the exact method when you need it.

</details>

### What are fork-join pools and parallel streams?
<details><summary>Show answer</summary>

A way to run one big job as many small ones — named here, detail left for later.

A **fork-join task** splits itself into smaller subtasks. The threads in a **fork-join pool** run those subtasks and
also **steal** work from each other, so no thread sits idle while another has a backlog — higher CPU use, more
throughput, lower latency.

**Parallel streams** are built on fork-join pools, so they give you this benefit with almost no effort — when the
work actually suits parallelism. Writing and tuning fork-join tasks by hand is tricky; parallel streams are the easy
door to the same engine.

</details>
