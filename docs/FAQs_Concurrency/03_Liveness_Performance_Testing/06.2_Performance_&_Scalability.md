### What does synchronization cost in performance?
<details><summary>Show answer</summary>

Not what most people guess. The cost is **not** the CPU time spent acquiring the lock — that part is cheap on
modern JVMs. The real cost of holding locks more than you need — **oversynchronization** — is:

- **Lost parallelism.** While one thread holds the lock, every other thread that wants it sits idle. On a
  multicore machine that's cores doing nothing — the whole point of multiple cores lost.
- **Memory-consistency delays.** A lock forces every core to agree on one view of memory, which takes real time
  and coordination across cores.
- **The VM can't optimize.** Synchronized code limits the reorderings and optimizations the JVM would otherwise
  apply, so the code itself runs slower.

So the price isn't getting the lock — it's **contention**: threads competing for it, and the coordination the lock
forces underneath.

</details>

### How does a lock slow threads down?
<details><summary>Show answer</summary>

Four threads each need to update the same shared counter, guarded by one lock. Each update takes 10ms.

- Thread A takes the lock, works 10ms, releases. B, C, D wait.
- Thread B takes it, works 10ms, releases. C, D still waiting.
- Then C. Then D.

Total: **40ms**, run one after another — even though four cores were free the whole time. The lock forced the work
to be serial: only one thread inside at a time, so three cores sat idle waiting their turn.

Without the shared lock, the four could run at once and finish in **10ms**. The 30ms difference is the cost — not
CPU spent on the lock itself, but parallelism thrown away because threads had to line up for it.

</details>

### Reducing synchronization's performance cost?
<details><summary>Show answer</summary>

Do as little as possible while holding the lock: take it, touch the shared state, release it. Move anything
slow — I/O, a long computation — outside the block.

While you hold the lock, every other thread that wants it waits. The less you do inside, the shorter that wait,
and the more threads get through.

</details>

### Should a mutable class synchronize itself?
<details><summary>Show answer</summary>

Two choices when you write a mutable class:

- **No internal synchronization** — leave it to the client to lock from outside if it needs concurrent use.
- **Internal synchronization** — the class locks itself and is thread-safe.

Pick internal only if it buys **significantly more concurrency** than the client locking the whole object would.
If internal sync gives no real gain over a client-side lock, don't build it in — it just adds cost every caller
pays, even single-threaded ones.

</details>

### Internal vs no internal synchronization — JDK examples?
<details><summary>Show answer</summary>

- **No internal synchronization** — `java.util` collections (`ArrayList`, `HashMap`); the client locks if needed.
- **Internal synchronization** — `java.util.concurrent` (`ConcurrentHashMap`, `CopyOnWriteArrayList`); thread-safe,
  built for real concurrency gain.

</details>

### When must a class synchronize a static field itself?
<details><summary>Show answer</summary>

Whenever a method modifies a static field and could be called from more than one thread — 
the class **must** lock it internally. The client can't do it from outside.

Why the client can't: external locking works only when all callers share one lock on one object. But unrelated
callers, in unrelated code, invoke the method without any shared lock between them. A static field is reachable by
all of them, so it behaves like a global variable — even if it's `private`. No client-side lock can cover callers
that don't know about each other.

So the usual "let the client lock" option isn't available here — internal synchronization is the only way.

</details>

### Should you synchronize a class when unsure?
<details><summary>Show answer</summary>

No. When in doubt, don't synchronize — but **document that the class isn't thread-safe**, so callers know they own
that job. The default is no synchronization: it's cost every caller pays, including the single-threaded common case.

History backs this — [classes that oversynchronized got replaced](#which-classes-were-replaced-for-oversynchronizing).

</details>

### Which classes were replaced for oversynchronizing?
<details><summary>Show answer</summary>

Classes that synchronized when they didn't need to got supplanted by unsynchronized versions:

- **`StringBuffer` → `StringBuilder`.** `StringBuffer` locks internally, but it's almost always used by a single
  thread — so the locking was pure cost. `StringBuilder` is the same class without it.
- **`java.util.Random` → `ThreadLocalRandom`.** Same story: the thread-safe version paid for synchronization most
  callers never needed.

The lesson: needless synchronization is cost every caller pays, single-threaded ones included — so the default is
no synchronization.

</details>

### What techniques give higher concurrency under a lock?
<details><summary>Show answer</summary>

When a class synchronizes internally and you need more concurrency than one lock allows, three techniques go
further — named here, detail left for later:

- **Lock splitting** — one lock guarding unrelated state becomes two locks, so operations on different state don't
  block each other.
- **Lock striping** — split into many locks by key (e.g. per bucket), so threads touching different keys run at once.
- **Nonblocking concurrency** — no lock at all; use atomic operations that retry instead of waiting.

The shared idea: replace one coarse lock with finer-grained control, so fewer threads wait on each other.

</details>

### Why not depend on the thread scheduler?
<details><summary>Show answer</summary>

The scheduler decides which runnable threads run and for how long, and that policy varies across operating systems
and JVMs. A program that relies on it for correctness or performance behaves differently from one machine to the
next — it isn't portable. Write programs whose correctness doesn't depend on scheduling decisions at all.

</details>

### Keeping a concurrent program portable across machines?
<details><summary>Show answer</summary>

Keep the average number of *runnable* threads close to the number of processors. Then the scheduler has almost no
choice — it just runs each runnable thread until it blocks — so the program behaves the same under very different
scheduling policies.

Runnable is not the same as total. A program can have many threads while few are runnable; threads that are
waiting don't count. It's the runnable ones competing for CPU that scheduling decisions affect.

</details>

### Keeping the number of runnable threads low?
<details><summary>Show answer</summary>

Each thread should do some useful work, then wait for more — a thread that isn't doing useful work shouldn't be
runnable at all.

With the Executor Framework this means sizing the thread pool to the work, and keeping tasks short — but not so
short that dispatch overhead outweighs the work. The aim is threads that run when there's something to do and wait
otherwise, so the runnable count stays near the processor count.

</details>

### Why not busy-wait?
<details><summary>Show answer</summary>

Busy-waiting is looping to recheck a shared value until it changes, instead of waiting to be woken. It keeps the
thread runnable the whole time, so it burns a processor doing nothing useful and steals CPU from threads that have
real work. It also makes the program's behavior hostage to the scheduler. Wait to be signalled instead — a
synchronizer, `wait`/`notify`, a blocking queue.

</details>

### Fixing threads that don't get enough CPU?
<details><summary>Show answer</summary>

Restructure to reduce the number of concurrently runnable threads — don't patch it with `Thread.yield` or thread
priorities.

- `Thread.yield` has no testable semantics: the same calls can help on one JVM, hurt on another, do nothing on a
  third. Any fix it gives is unportable.
- Thread priorities are among Java's least portable features. Fine to tune the responsiveness of an already-working
  program sparingly; never use them to rescue one that barely works — the underlying problem returns until you fix
  its cause.

</details>
