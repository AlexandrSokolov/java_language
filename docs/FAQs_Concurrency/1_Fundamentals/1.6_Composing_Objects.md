### Locking safely — what are the considerations?
<details><summary>Show answer</summary>

- **A dedicated lock, not `this`.** Locking on `this` 
  [exposes your lock to the outside](#stopping-clients-and-subclasses-from-touching-your-lock) — 
  a client can hold it, and a subclass can lock it for its own reasons and collide with you. 
  Prefer a separate lock object you own.
- **Final — always.** A reassignable lock means 
  [two threads can lock different objects and get no mutual exclusion](#why-must-a-lock-field-be-final) at all.
- **Private — by default, not by law.** Hiding the lock is the usual choice, but not absolute: sometimes you
  deliberately expose a lock for callers to hold across compound operations (the pattern behind the
  `Collections.synchronized…` wrappers, whose iteration the client locks). 
  Private unless you have a reason to publish it.

</details>

### Stopping clients and subclasses from touching your lock?
<details><summary>Show answer</summary>

Lock on a private object the outside world can't reach, instead of on `this`:

```java
private final Object lock = new Object();
public void foo() {
  synchronized (lock) {
    // ...
  }
}
```

A `synchronized` method locks `this`, which is public. That lets a client hold your lock forever — a denial-of-
service, accidental or deliberate — and lets a subclass lock `this` for its own reasons and collide with the base
class on the same lock. A private lock is invisible outside the class, so neither can interfere. It's encapsulating
the lock inside the object it guards.

</details>

### Why must a lock field be final?
<details><summary>Show answer</summary>

So the lock can't be reassigned. If the field could change, two threads might synchronize on different objects —
one on the old lock, one on the new — and get no mutual exclusion at all, so they run the guarded code at the same
time with no error. `final` pins every thread to the same lock. Lock fields should always be `final`, whether it's
a plain monitor object or a `java.util.concurrent.locks` lock.

</details>

### When can't you hide the lock from clients?
<details><summary>Show answer</summary>

Only unconditionally thread-safe classes can use a private lock. 


A conditionally thread-safe class must tell clients which lock to acquire 
for the sequences that need external synchronization — so that lock has to be publicly reachable, not hidden. 
You can't document "lock on X" and make X private at the same time.

</details>

### Does the synchronized modifier document thread safety?
<details><summary>Show answer</summary>

No. `synchronized` on a method is an implementation detail, not part of the API — Javadoc doesn't even emit it,
and its presence doesn't reliably mean the method is safe to call concurrently.

The deeper mistake is treating thread safety as all-or-nothing. It has levels, and a class must state in prose (or
a thread-safety annotation) which level it offers. See
[the levels of thread safety](#what-are-the-levels-of-thread-safety). The `synchronized` keyword plays no part in that documentation.

</details>

### What are the levels of thread safety?
<details><summary>Show answer</summary>

A spectrum, from "never needs synchronization" to "can't be made safe at all":

- Immutable — instances never change, so no synchronization is ever needed. `String`, `Long`, `BigInteger`.
- Unconditionally thread-safe — mutable, but enough internal synchronization that callers need none.
  `AtomicLong`, `ConcurrentHashMap`.
- Conditionally thread-safe — safe, except some sequences need external locking by the caller. The
  `Collections.synchronized…` wrappers, whose iterators must be locked by the client.
- Not thread-safe — the caller must wrap every call (or call sequence) in its own synchronization. `ArrayList`,
  `HashMap`.
- Thread-hostile — unsafe even if the caller synchronizes every call. Usually from unsynchronized mutation of
  static state; such classes get fixed or deprecated, never written on purpose.

Trigger: no sync needed → caller syncs some sequences → caller syncs everything → sync can't save it.

</details>

### What makes a class thread-hostile?
<details><summary>Show answer</summary>

It stays unsafe for concurrent use *even when the caller synchronizes every single call* — the strongest form of
thread-unsafe. Normal not-thread-safe classes are rescued by the caller wrapping each call in a lock;
thread-hostile ones can't be rescued that way.


The marker: the broken state is **static/global and mutated without synchronization**, not per-instance. 
A caller can only lock what it can reach — its own shared reference. 
It cannot lock a hidden static field it doesn't even know exists, so no amount of external locking covers the race. 
Nobody writes these on purpose; they come from ignoring concurrency, and they get fixed or deprecated rather than kept.


Handle: if locking every call still can't make it safe, the unsafe state is global, 
not per-instance — that's thread-hostile.

</details>

### Is SimpleDateFormat thread-hostile?
<details><summary>Show answer</summary>

No — it's **not-thread-safe**, not thread-hostile. The difference matters: its broken state is per-instance, not
global, so external locking *can* rescue it. A thread-hostile class couldn't be saved that way.

It mutates an internal `Calendar` field during `format` / `parse`. So a shared instance corrupts under concurrent
use — wrong dates, exceptions, garbage, with no error at the point of sharing.

The trap: declaring it `static final` does **not** make it safe. `final` freezes the reference, not the object's
internal state — the shallow-immutability trap. A shared `static final SimpleDateFormat` is exactly the setup that
corrupts.

```java
// BROKEN — shared instance, no synchronization
static final SimpleDateFormat FMT = new SimpleDateFormat("yyyy-MM-dd");
String s = FMT.format(date);   // internal Calendar stomped by concurrent calls

// WORKS — lock every access to the shared instance
synchronized (FMT) { return FMT.format(date); }

// BETTER — immutable and thread-safe, no locking needed
static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");
String s = FMT.format(localDate);
```

Handle: not thread-hostile — external locking fixes it — but `static final` alone doesn't; 
lock every call, or use the immutable `DateTimeFormatter` instead.

</details>

### What must a class document about thread safety?
<details><summary>Show answer</summary>

State the class's thread-safety level in its doc comment — in prose or as a thread-safety annotation.

- A conditionally thread-safe class must also say *which* call sequences need external locking and *which lock* the
  client acquires for them (usually the instance, sometimes another object).
- A method with its own special thread-safety behavior documents it on the method, not only on the class.
- A static factory must document the returned object's thread safety unless the return type makes it obvious — as
  `Collections.synchronizedMap` does.
- Enum immutability needs no mention; it's a given.

</details>
