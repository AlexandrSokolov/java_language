### The state model of a Java thread?
<details><summary>Show answer</summary>

Six states in `Thread.State`, a layer over the OS view:

- **NEW** — object created, no OS thread yet. `start()` signals the OS to make one.
- **RUNNABLE** — the whole scheduling cycle: waiting in the run queue, running on a core, placed back. 
  Not the same as "running right now."
- **WAITING** — stepped off the core voluntarily via `wait()`, indefinitely, until `notify()`.
- **TIMED_WAITING** — stepped off voluntarily via `sleep()`, until a timer expires.
- **BLOCKED** — forced off: waiting for a lock another thread holds, or on I/O.
- **TERMINATED** — the OS thread has ceased.

![The state model of a Java thread](../../images/Thread_State_Model.png)

Spine: 
- NEW (no OS thread) → 
- RUNNABLE (in the queue or on a core) → 
- leave the core three ways — 
  - two voluntary (`wait()`, `sleep()`), 
  - one forced (`BLOCKED` on a lock or I/O) → 
- TERMINATED.

</details>

### The NEW thread state?
<details><summary>Show answer</summary>

A `Thread` object exists, but no OS thread yet — it hasn't begun and may never. 
It waits here until `start()`, which ends NEW and moves it to RUNNABLE. NEW is exited once and never re-entered.

</details>

### The RUNNABLE thread state?
<details><summary>Show answer</summary>

Entered from NEW by `start()`, which creates the OS thread and moves the state NEW → RUNNABLE.

Not "running on a core." 
It covers the whole scheduling cycle: 
- waiting in the run queue, 
- running, and 
- being placed back to await the next time slice. 


A RUNNABLE thread may not be executing right now.

</details>

### WAITING vs TIMED_WAITING?
<details><summary>Show answer</summary>

Both step off the core voluntarily; they differ in what wakes them.

- **WAITING** — `Object.wait()`, waits indefinitely, wakes only on `notify()` from another thread.
- **TIMED_WAITING** — `Thread.sleep()`, the OS sets a timer, wakes on its own when the timer expires.

Handle: WAITING needs another thread to wake it; TIMED_WAITING wakes itself on a clock.

</details>

### The BLOCKED thread state?
<details><summary>Show answer</summary>

Forced off the core, not voluntary: the thread wants a lock another thread holds, or is waiting on I/O. 
It did not choose to step off — it is stuck on something external.

</details>

### The TERMINATED thread state?
<details><summary>Show answer</summary>

The OS thread behind the Java `Thread` object has ceased execution. The object is done; it cannot run again.

</details>

### What are the ways for a thread off the core?
<details><summary>Show answer</summary>

Two voluntary, one forced.

- **Voluntary** — the thread chooses to step off: `wait()` → WAITING, `sleep()` → TIMED_WAITING.
- **Forced** — the thread is stuck on something external: waiting for a lock or on I/O → BLOCKED.

Handle: WAITING and TIMED_WAITING are the thread choosing to leave; BLOCKED is the thread forced to wait.

</details>

### How to safely force-stop a thread?
<details><summary>Show answer</summary>

You can't — there is no safe force-stop in Java. From outside you cannot know where the thread is in its code: 
it may be mid-update, holding a lock, inside a `finally` that must finish. 
Killing it there leaves objects half-changed and locks released over broken state.

The only safe model is **cooperative**: you *ask* the thread to stop by 
[setting its interrupt flag](#what-does-interrupt-do-to-a-thread), 
and the thread checks for that request at points where it knows stopping is safe and winds down itself.

Spine: outside code can't know a thread's safe stopping points, so stopping is a request the thread honors, not a
command — the interrupt flag, its traps, and the deprecated `stop`/`suspend` all follow from that.

</details>

### What does interrupt() do to a thread?
<details><summary>Show answer</summary>

It only sets a flag on the thread. It does not stop it, pause it, or throw anything on its own — the thread keeps
running unless its own code checks the flag and acts.

```java
var t = new Thread(() -> { while (true); });  // never checks the flag
t.start();
t.interrupt();   // sets the flag — ignored, loop runs on
```

The thread has to look for the request. Two ways it notices:

```java
// 1. check the flag yourself and act on it
var t = new Thread(() -> {
  while (!Thread.currentThread().isInterrupted()) {
    doWork();
  }
  // flag seen → fall out of the loop and wind down
});

// 2. call a blocking method (sleep/wait/join/blocking I/O) — it checks the flag and throws
var t = new Thread(() -> {
  try {
    while (true) {
      doWork();
      Thread.sleep(100);   // throws InterruptedException when the flag is set
    }
  } catch (InterruptedException e) {
    // interrupted while blocked → wind down
  }
});
```

The two readers differ in whether they clear the flag — 
[`interrupted()` clears it, `isInterrupted()` doesn't](#interrupted-vs-isinterrupted).

Handle: `interrupt()` is a request, not a kill — it sets a flag that only the thread's own checks (or a blocking
method's throw) can act on.

</details>

### interrupted() vs isInterrupted()?
<details><summary>Show answer</summary>

Both read the interrupt flag; they differ in whether they clear it.

- **`Thread.interrupted()`** — static, checks the *current* thread, and **clears** the flag as it reads it.
- **`isInterrupted()`** — instance method on a thread, checks it and **leaves it set**.

The trap: throwing `InterruptedException` also clears the flag — it's considered handled once thrown. So after
catching it, the flag is already gone:

```java
try {
  Thread.sleep(1000);
} catch (InterruptedException e) {
  // interrupt flag is now FALSE here — cleared by the throw
}
if (Thread.currentThread().isInterrupted()) { ... }   // won't fire — flag was cleared
```

Handle: `interrupted()` clears, `isInterrupted()` doesn't, and catching `InterruptedException` clears too — so
after the catch the thread no longer looks interrupted.

</details>

### What to do in an InterruptedException catch?
<details><summary>Show answer</summary>

Never swallow it. Catching `InterruptedException` clears the interrupt flag, so an empty catch — or one that only
logs — eats the stop request, and the thread runs on as if never asked to stop.

Two correct responses:
- **Let it propagate** — declare `throws InterruptedException`, let the caller handle it. The textbook first
  choice. (A convention that bans checked exceptions in signatures skips this and always takes the next option.)
- **Restore the flag** — if you catch here, re-set it so the owner still sees the request:

```java
try {
  Thread.sleep(1000);
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();   // restore the flag the catch just cleared
  // then wind down your own work
}
```

Whether the restore is required or can be skipped depends on 
[who owns the thread](#restoring-the-interrupt-flag-strategies).

Handle: catching clears the flag — propagate it or restore it, never swallow it.

</details>

### Restoring the interrupt flag, strategies?
<details><summary>Show answer</summary>

Whether you must restore the flag after catching `InterruptedException` depends on **who owns the thread** — and
owning the *code* in `run()` is not the same as owning the *thread*.

- **You own the thread — restore can be skipped.** You created a raw `Thread`, its `run()` is the whole story, and
  catching the exception means you're ending it right here. Nothing runs above you, so there's no one to notify —
  catch, wind down, let `run()` return. Restoring a flag nothing will read is pointless.

- **A pool owns the thread — restore is required.** Your task runs inside an executor, `@Async`, a container. 
  The worker thread is *borrowed*: the pool made it and reuses it. When the pool calls `shutdownNow()` or
  `future.cancel(true)`, it interrupts that worker to stop your task. If you catch and don't restore, the worker
  returns to the pool with the flag cleared, and the pool can't tell the task honored the stop — cancellation and
  shutdown silently fail. Here "who to notify" is the pool, not your own code.

The trap in the reasoning: "I wrote the run code, so I'm the owner." 
In a pool you own the *code*, not the *thread* — so you must restore even though the logic is yours.

Handle: own the thread and you're terminating → skip; borrowed from a pool → restore, 
because the pool reads the flag to confirm the stop.

</details>

### Describe a code snippet
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
Future<?> f = executor.submit(() -> {
  try {
    while (true) {
      doWork();
      Thread.sleep(100);
    }
  } catch (InterruptedException e) {
    throw new IllegalStateException("worker interrupted", e);
  }
});
```

</details>

<details><summary>Show answer</summary>

**The defect is the missing flag restore, not the wrapping.** Catching `InterruptedException` cleared the interrupt
flag. The code then throws a wrapped exception — so it *looks* responsible, it didn't swallow silently — but the
flag is now false and the interrupt is lost.

This task runs on a pool worker (`executor.submit`). The worker is borrowed: when the pool calls `shutdownNow()`
or `f.cancel(true)`, it interrupts the worker to stop this task. With the flag cleared and not restored, the pool
can't tell the task was interrupted — the stop request is gone. Wrapping and throwing does not carry it; only the
flag does.

Fix — restore the flag before throwing:

```java
} catch (InterruptedException e) {
  Thread.currentThread().interrupt();               // restore — the pool still sees the stop
  throw new IllegalStateException("worker interrupted", e);
}
```

Note the exception *type* is not the defect here — wrapping in one unchecked type is a valid convention. The bug
is purely the forgotten restore: the one line that keeps cancellation and shutdown working.

Handle: wrapping an interrupt without restoring the flag looks safe but eats the stop — restore first, then wrap.

</details>

### How to safely use stop() and suspend()?
<details><summary>Show answer</summary>

You can't — both are deprecated because there is no safe way to use them. They break other threads' safety, not
just their own.

- **`stop()`** — kills the thread by throwing `ThreadDeath` at whatever point it happens to be: mid-update, or
  inside a `finally` the developer assumed would finish. The stack unwinds and **all its locks release**, exposing
  half-changed objects to every other thread. You cannot guard against it — the object is left corrupt.
- **`suspend()`** — freezes the thread **while it still holds its locks**. Any other thread needing one of those
  locks blocks until the suspended thread resumes — a liveness hazard, and an easy deadlock.

The safe model is cooperative interruption: ask the thread to stop and let it wind down at a point it knows is
safe.

Handle: there is no safe use — `stop()` unlocks over broken state, `suspend()` freezes holding locks; both hand
other threads a damaged or blocked world. Use interruption instead.

</details>

### What happens to an exception in a thread?
<details><summary>Show answer</summary>

In a raw `Thread` you created, it dies with the thread, silently. An exception thrown from the `Runnable` ends
that thread, but no other thread is told — the program runs on unaware the worker crashed. There's no caller to
catch it: the thread was launched with `start()` and runs on its own, so the exception has nowhere to propagate.

The only hook to observe it is an uncaught-exception handler, set **before** starting the thread:

```java
var t = new Thread(() -> { throw new UnsupportedOperationException(); });
t.setUncaughtExceptionHandler((thread, e) ->
  System.err.println(thread.getName() + " died: " + e));
t.start();
```

The handler is a callback the JVM invokes as the thread dies from an uncaught exception. Set thread properties —
name, daemon status, this handler — before `start()`, not after; some throw once the thread is running. (An
exception thrown inside the handler itself is ignored.)

This is the raw-thread case. In practice you rarely write this, because 
[the layers that lend you a thread catch the exception for you](#who-catches-a-threads-exception-for-you).

Handle: in a raw thread an uncaught exception kills it silently — the uncaught-exception handler, 
set before `start()`, is the only way to see it.

</details>

### Who catches a thread's exception for you?
<details><summary>Show answer</summary>

The layer that lends you the thread wraps your code, so the exception rarely reaches the silent-death boundary.

- **Pool task via `submit()`** — the exception is captured in the `Future` and surfaces when you call
  `future.get()`, as an `ExecutionException`. Not lost — stored. The trap: if you never call `get()`, it sits
  there unseen.
- **Pool task via `execute()`** — the worker's wrapper catches it; the worker survives and takes the next task.
  A plain `ThreadPoolExecutor` prints it to `System.err` and replaces a dead worker, so the pool doesn't drain.
- **REST / container request** — the container runs your handler inside a try/catch, turns the escaped exception
  into a response (a 500, or whatever an exception mapper says), and returns the request thread to the pool clean.
  One failed request, not a dead server.

The through-line: reusable-thread infrastructure never lets your exception kill the borrowed thread — it wraps,
catches, and reports. That backstop is why letting an exception propagate out of your code is safe in a web app,
and why you don't set an uncaught-exception handler yourself.

Handle: pools and containers wrap your code and catch what escapes — the raw uncaught-exception handler is only
for threads you built yourself.

</details>
