### What order do threads see by default?
<details><summary>Show answer</summary>

None. No guaranteed order, no guaranteed visibility. A write from one thread may reach another out of order, or never. 
You have to establish order yourself, at specific points.

</details>

### How do you get guaranteed ordering across threads?
<details><summary>Show answer</summary>

You create a **happens-before** link: where it connects a write in A to a read in B, B sees that write, in order.
You get it by using a construct that carries it — 
same lock release/acquire, same `volatile` write/read, thread start, thread join.

</details>

### What is happens-before?
<details><summary>Show answer</summary>

A guarantee between two actions: if A happens-before B, then A is finished first **and** every write A made is
visible to B. It is about order and visibility, not clock time.

It is a *partial* order — only pairs with a happens-before link are ordered. Two actions with no link are
unordered: the JVM may run them either way, and B may see none of A's writes.

</details>

### What are the tools for a happens-before edge?
<details><summary>Show answer</summary>

Specific actions *create* an edge — you don't request one, you perform an action that carries it.
The JMM calls these pairings **synchronizes-with**:

- **volatile** — a write to a volatile field happens-before a later read of the *same* field by another thread.
- **lock** — releasing a lock happens-before the next acquire of the *same* lock.
- **thread start** — `thread.start()` happens-before everything the started thread does.
- **thread join** — everything a thread does happens-before another thread's `thread.join()` returning.

Each connects *two* points across threads; that edge is the only thing that makes the writer's changes visible and
ordered to the reader.

Handle: edges are created, not requested — volatile (same field), lock (same lock), thread start, thread join.

</details>

### What does program order guarantee?
<details><summary>Show answer</summary>

Only ordering *within a single thread* — and even that is loose: the CPU may reorder underneath as long as that
one thread's own result is unchanged. It gives **no** cross-thread guarantee at all.

```java
// Thread A
a = 1;          // program order: a before ready, within thread A
ready = true;

// Thread B — plain fields, no edge
if (ready) {    // may see ready == true
  use(a);       // yet still see a == 0 — program order in A promises B nothing
}
```

Writing `a` before `ready` in the code does not mean thread B sees them in that order. Program order orders A's
statements *for A*; B sees nothing guaranteed until a real edge (volatile, lock, start/join) connects them.

Handle: program order is within-thread only — "I wrote A before B" tells another thread nothing without an edge.

</details>

### Synchronizes-with vs happens-before?
<details><summary>Show answer</summary>

- **Synchronizes-with** — *how* a cross-thread edge forms: the specific pairings 
  (unlock/lock of the same monitor, volatile write/read of the same field).
- **Happens-before** — *what* that edge promises: A is done and visible to B.

Rule: if A synchronizes-with B, then A happens-before B. 
(Within one thread you get happens-before from program order, no pairing needed.)

</details>

### How do happens-before edges chain?
<details><summary>Show answer</summary>

Two sources of edges combine by transitivity to reach across threads.

- **Program order** — within one thread, if A is written before B, then A happens-before B.
- **Synchronizes-with** — a pairing (unlock→lock, volatile write→read) gives a happens-before edge between
  threads.
- **Transitivity** — if X happens-before Y and Y happens-before Z, then X happens-before Z.

Chaining them is what lets a write reach a thread it never directly synchronized with:

```java
// Thread A: x = 1;  then  flagA (volatile) = true;      // program order: x hb flagA-write
// Thread B: reads flagA;  then  flagB (volatile) = true; // flagA-write hb flagA-read (pairing); read hb flagB-write
// Thread C: reads flagB;  then  reads x;                 // flagB-write hb flagB-read; read hb read-x
// transitivity: A's x = 1  happens-before  C's read of x  ->  C sees 1
```

This is the formal reason one volatile flag publishes every plain write before it: program order links the plain
write to the volatile write, the pairing carries it across, transitivity stretches it to the far reader.

</details>

### Which edges do start() and join() give?
<details><summary>Show answer</summary>

Two cross-thread edges people forget exist — they publish state without any explicit lock or volatile.

- **`start()`** — everything the starting thread did *before* calling `t.start()` happens-before the new thread's
  first action. So the new thread sees all the setup that preceded its start.
- **`join()`** — every action of a thread happens-before `t.join()` returns in the joining thread. So after
  `join()`, the joiner sees everything the finished thread did.

```java
config = load();        // main thread
t.start();              // new thread sees config, fully built
// ...
t.join();               // main thread now sees everything t wrote
result = t.output;      // safe — published by the join edge
```

Handle: `start()` publishes the starter's prior writes to the new thread; `join()` publishes the finished
thread's writes back to the joiner — both are happens-before edges, no lock needed.

</details>

### Does working code mean no memory bug?
<details><summary>Show answer</summary>

No. The JMM rules are the **minimum** — a real JVM often does better than required, publishing writes you never
synchronized, on your machine, today. So code with a missing happens-before edge can pass for years, then read
stale on another JVM, CPU, or under heavier load.

Correctness is judged against the rules, not observed behavior: 
no happens-before edge for a write means the code is broken even if it currently works.

</details>
