### Java threading — fundamental concepts?
<details><summary>Show answer</summary>

- Shared, visible-by-default mutable state
- Preemptive thread scheduling by the operating system

</details>

### What breaks when threads share an object?
<details><summary>Show answer</summary>

- An object can be shared between all threads in a process.
- Any thread holding a reference can change it.
- The OS can swap threads on and off cores at any time.
- So a swap can leave a method half-done and the object in a broken state.
- Objects can be locked to protect the vulnerable data.
- Without locking, changes made in one thread may not be seen correctly in others.

Lock it: in Java the tool is `synchronized`.

</details>

### What requirement do threaded methods carry?
<details><summary>Show answer</summary>

A running method must be interruptible — the OS has to be able to swap it off the core at any point. Otherwise a
method with an infinite loop would hold the CPU forever and starve every other thread.

The cost of that requirement: a swap can land in the middle of a method, leaving the object it was updating
half-finished — which is exactly why shared objects then need locking.

</details>

### What are the design forces in concurrent code?
<details><summary>Show answer</summary>

Four concerns that pull on any concurrent design, often conflicting — each forces a decision:

- [Safety](#what-does-concurrently-typesafe-mean) — objects stay self-consistent under simultaneous access
- [Liveness](#what-is-liveness) — every activity eventually progresses or fails, never stuck in between
- [Performance](#what-is-performance-as-a-design-force) — how much work you get from given resources
- [Reusability](#what-is-reusability-as-a-design-force) — concurrent code designed to be reused

</details>

### What should never break on a method call?
<details><summary>Show answer</summary>

The object's state stays consistent.
Before and after any public method call, the object holds a valid combination of field values —
the rules that define a correct object (its invariants) are never violated.

</details>

### How do you keep an object's state valid?
<details><summary>Show answer</summary>

Encapsulation: keep all state private, expose only methods that move the object between valid states.
No caller can set a field directly to a bad value.


Under concurrent access the same goal holds, but encapsulation alone no longer delivers it —
other threads touch the object at once on different cores.
That harder version has a name: [concurrently typesafe](#what-does-concurrently-typesafe-mean).

Handle: encapsulation gives consistency in one thread; concurrency needs more.

</details>

### What does concurrently typesafe mean?
<details><summary>Show answer</summary>

An object is safe — or concurrently typesafe —
when it stays self-consistent no matter what other operations run on it at the same time.
Its invariants hold even while other threads call methods on the same object on different CPU cores.

</details>

### Strategy for achieving concurrent type safety?
<details><summary>Show answer</summary>

Two method-discipline rules plus one mechanism:

- Never return from a non-private method while the object is inconsistent.
- Never call a non-private method — especially on another object — while inconsistent.
- Hold protection (a lock or critical section) over the window where the object is inconsistent.

The first two keep a half-done change from escaping through a method call;
the lock keeps another thread from seeing the object during that window.
Together they guarantee no thread ever observes a broken state.

Handle: stay consistent across every exit point, and lock the object shut while it isn't.

</details>

### The complete form of the safety strategy?
<details><summary>Show answer</summary>

The **fully synchronized object** — the named, complete version of the strategy.
On top of the two inconsistent-state rules, a class qualifies when:

- every constructor leaves all fields consistent;
- no public fields;
- every non-private method returns with the object consistent (given it was consistent on entry);
- every method is `synchronized`;
- every method finishes in bounded time (liveness — nothing blocks forever).

If all hold, the class is both safe and live.

Handle: fully synchronized = lock every method, expose nothing, always return consistent — safe and live by construction.

</details>

### The rules of a fully synchronized object?
<details><summary>Show answer</summary>

- All fields initialized to a consistent state in every constructor.
- No public fields.
- Every non-private method returns with the object consistent (given it was consistent on entry).
- Every method is `synchronized`.
- Every method finishes in bounded time.
- While inconsistent, no method calls another instance's methods.
- While inconsistent, no method calls any non-private method on this instance.

Handle: lock every method, hide every field, never let a half-done object escape or be re-entered —
then it is safe and live.

</details>

### Why forbid method calls while inconsistent?
<details><summary>Show answer</summary>

A half-updated object must never be observed. Two ways it leaks while inconsistent:

- **Calling another object's method** — that object (or a chain from it) may call back into this one and read the
  broken state.
- **Calling a non-private method on this instance** — a non-private method may assume consistency, or re-enter
  under the same reentrant lock and act on half-done state.

The lock does not save you here: it is reentrant, so the same thread walks straight back in.
The guard is discipline — finish the change before making any such call.

Handle: the lock stops other threads, not yourself — never call out or re-enter while the object is half-done.

</details>

### A fully synchronized object — considerations?
<details><summary>Show answer</summary>

Safe and live, but two problems rule it out for real systems:

- **Slow.** Every access takes the lock — even reads. Nothing runs concurrently, so all access to the object is
  serialized. Safe and live does not mean fast.
- **Fragile at scale.** Correctness depends on *every* access sitting inside a synchronized method. In a tiny
  class you check that by eye; in a large codebase you cannot, and one unguarded access breaks it silently.

Handle:
safe and live but serial and unverifiable — fine to understand, not to reach for;
use higher-level concurrency tools instead.

</details>
