What I did: ran `images.parallelStream().map(uploader::send).toList()` inside `pool.submit(...).get()` on a custom
`ForkJoinPool(20)` to upload images (5–20 s each). It worked for several reasons. The pool was isolated, so the common
pool was not starved. The source was a list, so it split to about one image per task and the pool size was the real
limit (Java 10+; on Java 8 the chunk count follows the common pool). Upload time dwarfed splitting cost, failures came
back as `Result` values, and client timeouts meant no call could hang the stream. It is still called the wrong tool
because Fork/Join is built for short CPU work. It cannot see a thread blocked on a socket, and stealing moves whole
chunks, not single slow calls. The source split decides concurrency, not me. A hung call holds the whole terminal
operation, and cancelling does not stop running subtasks. Running a parallel stream in a custom pool is JDK behavior,
not a spec guarantee.

How it should be done: use a tool built for "run N blocking calls, wait for all, get results in order". Java 19+:
`ExecutorService.invokeAll(tasks)` in try-with-resources, then `Future::resultNow`. That gives one task per element,
pool size as the concurrency limit, and a documented API. Java 24+:
`stream.gather(Gatherers.mapConcurrent(20, uploader::send)).toList()`. It runs on virtual threads, at most 20 at once,
keeps order, and is shorter than the parallel-stream version. Skip `CompletableFuture.allOf` here: it returns `Void`,
so results need a second pass. Verify before carding: Java 10 split fix (JDK-8190974), `close()`/`resultNow()` in
Java 19, `mapConcurrent` final in Java 24.

The Problem (The Wrong Approach)
Using Java's parallelStream() (which relies on ForkJoinPool) for blocking I/O like network calls is an architectural anti-pattern. 
A ForkJoinPool is optimized for CPU-bound, divide-and-conquer tasks and maintains a strict limit on active threads. 
When you execute blocking I/O inside it, the operating system puts those limited threads to sleep while waiting for network responses, 
and the pool does not automatically spawn replacements. 
In a high-throughput environment, this rapidly leads to thread starvation—stalling your application entirely 
as the pool runs out of threads to process the remaining queue.

The Solution (How it Should Be Done)
Concurrent I/O requires mechanisms explicitly designed for blocking operations. 
Historically, the correct approach was using CompletableFuture backed by a standard ThreadPoolExecutor 
(which dynamically scales threads as others block) or reactive, non-blocking frameworks. 
Today, the modern standard is to use Java 21+ Virtual Threads. Virtual threads allow you to write simple, sequential, 
blocking code while the JVM seamlessly handles millions of concurrent I/O waits in the background, 
giving you the clean syntax you want without the risk of OS thread exhaustion.

**Cases you're missing**

You have two so far: all must succeed (fail fast), and first success wins. The others:

1. **Wait for all, keep every outcome.** No task cancels another, and you get back both successes and failures. Example: upload 100 images, then report which ones failed. Tools: `invokeAll` and then check each `Future`, `allOf` with `handle` on each future, or `StructuredTaskScope` `awaitAll()`.
2. **N of M must succeed (quorum).** Stop once N tasks have succeeded and cancel the rest. Fail as soon as so many have failed that N is no longer possible. Example: 2 of 3 replicas must confirm a write. There's no ready method; you build it with an `ExecutorCompletionService` loop that counts successes and failures.
3. **Required and optional calls mixed.** A failed required call fails the group; a failed optional call is replaced by a default. Example: the page needs the product, while reviews are nice to have. Tools: `exceptionally(e -> default)` on the optional futures, and fail-fast on the required ones.
4. **Hedged request.** First success wins, but the backup call starts only if the first call is slow. Example: call replica B only if A hasn't answered within 50 ms. Tools: `ExecutorCompletionService.poll(timeout)`, then submit the backup.
5. **Handle each result as it finishes.** This isn't a stop rule. You act on each result in finish order instead of waiting for the whole group. Example: show search results as they arrive. Tools: a `take()` loop, or `thenAccept` on each future.

A deadline isn't a separate case. It sits on top of any case above: stop at time X, then either fail or return what has finished. Tools: the timeout versions of `invokeAll` / `invokeAny`, `orTimeout`, `completeOnTimeout`, and `poll(timeout)`.

Handle: every case answers two questions. What must come back: all, one, N, or whatever is ready? And what does a failure do: stop the group, get ignored, or get recorded?

**Tools you're missing**

- `ExecutorService`: the timeout versions of `invokeAll` / `invokeAny`. Also `close()` (JDK 19+), which waits for all submitted tasks, so try-with-resources gives you a simple "wait for all."
- `CompletableFuture`:
    - `thenCombine` merges two results into one.
    - `applyToEither` / `acceptEither` take the first of two to finish; a failure can win, as with `anyOf`.
    - `orTimeout` / `completeOnTimeout` add a deadline.
    - `exceptionally` / `handle` turn a failure into a value.
- `ExecutorCompletionService`: `poll()` and `poll(timeout)`, besides `take()`.
- `StructuredTaskScope` (preview): its `Joiner` methods are close to a ready-made catalog of these cases. `allSuccessfulOrThrow` and `anySuccessfulResultOrThrow` are your two cases, `awaitAll` is case 1, and `allUntil(predicate)` handles custom rules such as quorum.     - `CountDownLatch` is the low-level "wait for N tasks."

## Gemini

**Wait for All, Tolerate Failures (Best-Effort Scatter-Gather)**
You want every task to finish. If one fails, you log the error, return a default value, or omit that piece of data, but you **do not** cancel the other running tasks. This is standard for aggregating data for UI dashboards. If the "Recommendations" service fails, you still want to show the user their "Profile" and "Order History" rather than failing the entire page load.

* **Tooling:** `CompletableFuture.allOf(...)`, where each individual future handles its own errors using `.exceptionally()`. Alternatively, `ExecutorService.invokeAll(...)` where the inner `Callable` has a try-catch block that swallows the exception and returns an empty/default object.

**Quorum / Threshold (First *N* Successes Win)**
You spawn 5 parallel tasks, but you only need 3 successful responses to proceed. Once the first 3 succeed, you immediately cancel the remaining 2. This is common in distributed systems (e.g., needing agreement from a quorum of database replicas) or when querying multiple flight-pricing APIs and showing the user the first 5 results that load.

* **Tooling:** `ExecutorCompletionService`. You loop `take()` until you accumulate *N* successful results, then iterate through the remaining futures and call `cancel(true)`. In Java 25+, this is handled by writing a custom `StructuredTaskScope.Joiner`.

**Deadline-Bound Execution (Gather what you can in *X* time)**
You have a strict SLA (e.g., 500ms). You fire off tasks, wait exactly 500ms, take whatever finished successfully in that window, and aggressively cancel anything still running.

* **Tooling:** `ExecutorService.invokeAll(tasks, time, unit)`. This specific overload automatically cancels any tasks that have not completed when the timeout expires. In Java 21+, `StructuredTaskScope.join()` handles this via a deadline configuration.

**Pipeline / Dependency Graph (Task Chaining)**
Tasks are not just a flat list run in parallel; they depend on each other. Task C requires the results of Task A and Task B, but A and B can run in parallel.

* **Tooling:** This is the primary domain of `CompletableFuture`. You use `.thenCombine()` to merge two parallel tasks when they both finish, or `.thenCompose()` to start a new task using the result of a previous one.

### Additional Native Java Tools

You have the core task-execution APIs covered for I/O and general concurrency, but here are the other native tools that fit different niches:

* **Parallel Streams (`Collection.parallelStream()`):** Designed for homogeneous, CPU-bound data processing (e.g., applying a mathematical filter to a list of 10,000 integers). They are generally a poor choice for heterogeneous, I/O-bound tasks (like making HTTP calls) because they use the shared common `ForkJoinPool`, and a slow network call will starve the pool.
* **ForkJoinPool:** The engine behind parallel streams and `CompletableFuture`. When used directly, it is meant for recursive, divide-and-conquer algorithms (like parallel merge sort) where tasks spawn sub-tasks. It uses a "work-stealing" algorithm to keep threads busy.
* **Synchronization Aids (`CountDownLatch`, `Phaser`, `CyclicBarrier`):** These do not execute tasks or return results. They are signaling tools used when you manage threads manually and need them to wait for each other at specific checkpoints in your code.
