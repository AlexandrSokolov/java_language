### What represents an async task result?
<details><summary>Show answer</summary>

[`Future`](#what-does-future-give-you) — a handle to a result that may not exist yet but will arrive later. 
The task runs elsewhere; the `Future` is your claim ticket for its outcome.

</details>

### What does Future give you?
<details><summary>Show answer</summary>

A `Future<T>` holds the result of a task that may still be running, so you can hand off work and pick up the
outcome later. Three primary methods:

- `get()` — returns the result; **blocks** if it is not ready yet.
- `isDone()` — asks whether the task has finished; non-blocking, returns right away.
- `cancel()` — tries to stop the task before it finishes.

Handle: the task runs somewhere else, the `Future` is how you check on it and collect the result.

</details>

### How do you use a Future safely?
<details><summary>Show answer</summary>

You get a `Future` when you submit a task to an `ExecutorService`; it is your only handle to a task now running
on a pool thread.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<String> f = pool.submit(() -> loadData());

try {
  String result = f.get(5, TimeUnit.SECONDS);   // wait with a limit, never forever
} catch (TimeoutException e) {
  f.cancel(true);                     // didn't finish in time — ask it to stop
} catch (ExecutionException e) {
  Throwable cause = e.getCause();     // the task threw — real error is wrapped inside
} catch (InterruptedException e) {
  Thread.currentThread().interrupt(); // restore the flag before leaving
  f.cancel(true);
}
```

The three checked exceptions mean three different things:

- `TimeoutException` — your wait ran out; the task is **still running**, nothing failed.
- `ExecutionException` — the **task itself threw**; the real exception is inside, dug out with `getCause()`.
- `InterruptedException` — **your** waiting thread was interrupted; restore the flag and stop.

Two traps this guards against: plain `get()` [blocks forever](4.3_Cancellation_&_Shutdown.md#how-does-futurecancel-work) 
if the task hangs — always use the timeout overload; 
and a task exception stays invisible until you call `get`, so a `submit` you never read silently swallows the failure.

Handle: the `Future` is a claim ticket — wait with a limit, and know whether it failed, timed out, 
or you were interrupted.

</details>

### CompletableFuture — known by another name?
<details><summary>Show answer</summary>

It is Java's version of a **promise** — the general name in other languages (JavaScript, Scala) for an object
that stands for a value that will be supplied later. Same idea: an empty slot now, filled once by whoever holds
it.

</details>

### How does CompletableFuture differ from Future?
<details><summary>Show answer</summary>

`CompletableFuture<T>` is a concrete class that implements the [`Future`](#what-does-future-give-you) interface
and adds more on top. The key new idea: you create it in an **uncompleted** ("unfulfilled") state — it holds no
value yet — and it is generic in the type of value it will eventually hold.

Where a plain `Future` gets its value from the task the pool runs for you, a `CompletableFuture` is an empty box
you hand around, to be filled in later by whoever holds a reference.

Handle: `CompletableFuture` = a `Future` you create empty and fill in yourself.

</details>

### How does a CompletableFuture get its value?
<details><summary>Show answer</summary>

Any thread that has a reference to it calls [`complete(value)`](#how-does-completablefuture-differ-from-future).
That fills ("fulfills") the future. The value becomes **immediately visible** to every thread blocked on a `get()` call.

The first `complete()` wins: after the future is completed, any further `complete()` calls are simply ignored.

```java
CompletableFuture<String> cf = new CompletableFuture<>();
// thread A, waiting:
String v = cf.get();              // blocks until someone completes it
// thread B, later:
cf.complete("done");              // fills it — thread A's get() now returns "done"
cf.complete("other");            // ignored, already completed
```

Handle: whoever holds the reference calls `complete()`; the first call sets the value for everyone, the rest are ignored.

</details>

### Is a CompletableFuture immutable and thread-safe?
<details><summary>Show answer</summary>

It is **not immutable** — its state does change over time. But it is still safe, because it changes only **once**:
from uncompleted to completed, and never again. There is no way for different threads to see different values.

Two facts make this hold:

- The value is whatever the **first** thread to call `complete()` provided — fixed from then on.
- Every thread sees that same one value; there is no window where an inconsistent or half-changed state is
  visible.

So it sidesteps the usual problem of shared mutable state: mutation is real but happens exactly once and is
atomic to observers.

Handle: not immutable, but safe — one-way change, once only, same value seen by all.

</details>

### How do you create a CompletableFuture?
<details><summary>Show answer</summary>

Two ways:

- **Empty box you fill yourself** — `new CompletableFuture<>()`, then some thread calls `complete(value)` later.
- **Run a task that fills itself** — the common one in practice:

```java
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> loadData());  // returns a value
CompletableFuture<Void>   r  = CompletableFuture.runAsync(() -> doWork());        // no result
```

`supplyAsync` runs a task that produces a value; `runAsync` runs a `Runnable` with nothing to return. Both hand
back a future that completes on its own when the task finishes.

Handle: create it empty and `complete()` it by hand, or let `supplyAsync`/`runAsync` run a task and fill it.

</details>

### thenApply vs thenCompose?
<details><summary>Show answer</summary>

Both chain a next step onto the result. The difference is what your function returns:

- `thenApply` — a **plain** function, `T -> U`. Use when the next step is ordinary work.
- `thenCompose` — a function that returns **another future**, `T -> CompletableFuture<U>`. Use when the next step
  is itself async. This is `flatMap`.

```java
cf.thenApply(user -> user.email());          // T -> U
cf.thenCompose(email -> lookupAsync(email)); // T -> CompletableFuture<U>
```

The trap: use `thenApply` when the function returns a future and you get a nested `CompletableFuture<CompletableFuture<U>>`
that nobody unwraps. Async-returning step → `thenCompose`.

Handle: next step returns a value → `thenApply`; next step returns a future → `thenCompose` (it flattens).

</details>

### Does thenApply modify the original CompletableFuture?
<details><summary>Show answer</summary>

No. Every `then...` method returns a new `CompletableFuture` (a new stage in the pipeline). The original future
remains unchanged.

The trap is the "lost chain". If you write:

```java
cf.thenApply(user -> user.toUpperCase());
return cf; // BUG: returning the original, unmodified future!
```

The caller gets the original `cf`. The uppercase transformation happens, but its result is abandoned in a new,
unreferenced future. You must assign or return the result of the chain.

Handle: pipeline methods create new futures; if you don't assign the result of `thenApply`, you lose the
transformation.

</details>

### What does the Async suffix change?
<details><summary>Show answer</summary>

Which thread runs your callback.

- `thenApply(fn)` — `fn` may run on the thread that **completed** the future, sometimes even the caller's thread,
  inline.
- `thenApplyAsync(fn)` — `fn` runs on a pool: the [common pool](#why-pass-your-own-executor) by default, or one
  you pass as a second argument.

Why it matters: if the callback is slow or blocking and it runs inline on the completing thread, it can stall
whatever that thread was meant to do next.

Rule of thumb: use the `Async` variant when the callback does real work, and pass your own executor to it.

Handle: no suffix → may run inline on the completing thread; `Async` → runs on a pool.

</details>

### Why pass your own executor?
<details><summary>Show answer</summary>

Because `supplyAsync(fn)` and the `*Async` methods, called with no executor, use `ForkJoinPool.commonPool()` — a
single pool sized to your CPU count and **shared across the whole JVM**.

The trap: run blocking I/O on it and you tie up its few threads, starving every other user of the common pool in
the process — including parts of the JDK that lean on it.

```java
CompletableFuture.supplyAsync(() -> blockingIoCall(), myPool);  // your pool, not the shared one
```

For CPU-bound work the common pool is fine. For anything that blocks, pass your own executor.

Handle: the default pool is small and shared JVM-wide — give blocking work its own executor so it can't starve
everything else.

</details>

### How do you handle a failed CompletableFuture?
<details><summary>Show answer</summary>

A failure inside the task does not blow up — it sits in the future silently. If you never attach a handler and
never call `get`, the error is **lost**. So you attach one of three:

- `exceptionally(fn)` — runs **only** on the failure path; supplies a fallback value.
- `handle((value, ex) -> ...)` — runs on **both** success and failure; `ex` is null on success. Use when you need
  to inspect either outcome and transform the result.
- `whenComplete((value, ex) -> ...)` — sees both outcomes but only **observes**; it does not change the result.

```java
cf.thenApply(...)
  .exceptionally(ex -> { log(ex); return fallback; });
```

Handle: failure is silent until handled — `exceptionally` for the error path, `handle` to transform either
outcome, `whenComplete` to just watch.

</details>

### The exception wrapping trap in handle/exceptionally?
<details><summary>Show answer</summary>

When a pipeline fails, the original exception is often wrapped inside a `CompletionException`.

If your async task throws an `IllegalArgumentException`, the `ex` parameter in your `exceptionally(ex -> ...)`
block might be a `CompletionException`. If you simply check `if (ex instanceof IllegalArgumentException)`, it will
return `false` and bypass your error logic.

Always dig out the root cause before checking the exception type:

```java
cf.exceptionally(ex -> {
  Throwable cause = ex.getCause() != null ? ex.getCause() : ex;
  if (cause instanceof IllegalArgumentException) { ... }
});
```

Handle: always check `ex.getCause()` inside callbacks, because the framework wraps runtime exceptions in a
`CompletionException`.

</details>

### get() vs join()?
<details><summary>Show answer</summary>

Both block and return the completed value. The difference is the exception they throw on failure:

- `get()` — throws **checked** `ExecutionException` and `InterruptedException`, so you must catch or declare them.
- `join()` — throws **unchecked** `CompletionException`, nothing to declare.

That is why `join()` fits inside lambdas and streams, where checked exceptions don't compile:

```java
list.stream().map(cf -> cf.join()).collect(toList());  // get() would not compile here
```

Both block, so both are the thing composition is meant to avoid — reach for them only at the edge, when you truly
need the value in hand.

Handle: same blocking wait — `get()` throws checked, `join()` throws unchecked (fits in lambdas).

</details>

### Does CompletableFuture.cancel interrupt the task?
<details><summary>Show answer</summary>

No. `cancel()` completes the future exceptionally with a `CancellationException`, so anything waiting downstream
stops seeing a value — but the running task is **not** interrupted. The `mayInterruptIfRunning` flag is ignored.

This is the sharp contrast with [`Future.cancel`](#how-does-futurecancel-work), where `cancel(true)` does send an
interrupt. On a `CompletableFuture` the work already running keeps going to the end regardless.

Handle: `cancel` breaks the chain, not the work — it fails the future but lets the running task finish.

</details>

### How do you wait for multiple CompletableFutures?
<details><summary>Show answer</summary>

You use static factory methods to combine them without blocking:

- `CompletableFuture.allOf(cf1, cf2, ...)` — completes when all of them finish. Returns `CompletableFuture<Void>`.
- `CompletableFuture.anyOf(cf1, cf2, ...)` — completes when the first one finishes. Returns `CompletableFuture<Object>`.

The trap with `allOf`: it returns `Void`, meaning it doesn't automatically collect the results into a list. You
use it just to know they are done, and then you must map over the original futures and call `join()` on each to
actually extract the values (which is safe and non-blocking now, because `allOf` guarantees they are ready).

Handle: `allOf` to wait for everything (then extract manually), `anyOf` for the first one to cross the finish line.

</details>

### How do you timeout a CompletableFuture without blocking?
<details><summary>Show answer</summary>

While a plain [`Future`](#how-do-you-use-a-future-safely) requires you to use the blocking `get(timeout)`,
`CompletableFuture` (since Java 9) lets you handle timeouts asynchronously as part of the pipeline:

- `orTimeout(time, unit)` — completes exceptionally with a `TimeoutException` if not done in time.
- `completeOnTimeout(fallbackValue, time, unit)` — supplies a default value instead of failing.

```java
cf.orTimeout(5, TimeUnit.SECONDS)
  .exceptionally(ex -> fallback); // catches the timeout seamlessly
```

Handle: use `orTimeout()` or `completeOnTimeout()` to enforce limits asynchronously, keeping the pipeline
non-blocking.

</details>
