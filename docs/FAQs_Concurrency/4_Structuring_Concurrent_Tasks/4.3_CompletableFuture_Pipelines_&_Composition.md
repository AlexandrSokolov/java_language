### What sequential composition options does `CompletableFuture` provide?
<details><summary>Show answer</summary>

Pick by what your next step takes and returns:

- `thenApply(Function)` — takes the result, transforms it, returns a new value (`T -> U`). This is `map`.
- `thenAccept(Consumer)` — takes the result, consumes it, returns nothing; yields `CompletableFuture<Void>`
  (`T -> void`).
- `thenRun(Runnable)` — takes no input, returns nothing; fires a side effect when the previous stage finishes
  (`() -> void`).
- `thenCompose(Function)` — the next step itself returns a `CompletableFuture` (`T -> CompletableFuture<U>`); it
  flattens the result instead of nesting it. This is `flatMap`.

Handle: transform → `thenApply`; use the value → `thenAccept`; ignore the value → `thenRun`; next step returns a
future → `thenCompose`.

</details>

### CompletableFuture.thenApply vs CompletableFuture.thenCompose?
<details><summary>Show answer</summary>

Both chain a next step onto the result. The difference is what your function returns:

- `thenApply` — a **plain** function, `T -> U`. Use when the next step is ordinary work.
- `thenCompose` — a function that returns **another future**, `T -> CompletableFuture<U>`. Use when the next step
  is itself async. This is `flatMap`.

```java
cf.thenApply(user -> user.email());          // T -> U
cf.thenCompose(email -> lookupAsync(email)); // T -> CompletableFuture<U>
```

The trap: use `thenApply` when the function returns a future and you get a nested `CompletableFuture<CompletableFuture<U>>`
that nobody unwraps. Async-returning step → `thenCompose`.

Handle: next step returns a value → `thenApply`; next step returns a future → `thenCompose` (it flattens).

</details>

### Does thenApply modify the original CompletableFuture?
<details><summary>Show answer</summary>

No. Every `then...` method returns a new `CompletableFuture` (a new stage in the pipeline). The original future
remains unchanged.

The trap is the "lost chain". If you write:

```java
cf.thenApply(user -> user.toUpperCase());
return cf; // BUG: returning the original, unmodified future!
```

The caller gets the original `cf`. The uppercase transformation happens, but its result is abandoned in a new,
unreferenced future. You must assign or return the result of the chain.

Handle: pipeline methods create new futures; if you don't assign the result of `thenApply`, you lose the
transformation.

</details>

### CompletableFuture.thenApply vs CompletableFuture.thenApplyAsync?
<details><summary>Show answer</summary>

Which thread runs your callback.

- `thenApply(fn)` — `fn` may run on the thread that **completed** the future, sometimes even the caller's thread,
  inline.
- `thenApplyAsync(fn)` — `fn` runs on a pool: 
  the [common pool](4.2_Task_Result.md#what-dictates-the-execution-pool-for-a-completablefuture-and-what-limitations-must-be-considered) 
  by default, or one you pass as a second argument.

Why it matters: if the callback is slow or blocking and it runs inline on the completing thread, it can stall
whatever that thread was meant to do next.

Rule of thumb: use the `Async` variant when the callback does real work, and pass your own executor to it.

Handle: no suffix → may run inline on the completing thread; `Async` → runs on a pool.

</details>

### How do you wait for multiple CompletableFutures?
<details><summary>Show answer</summary>

You use static factory methods to combine them without blocking:

- `CompletableFuture.allOf(cf1, cf2, ...)` — completes when all of them finish. Returns `CompletableFuture<Void>`.
- `CompletableFuture.anyOf(cf1, cf2, ...)` — completes when the first one finishes. Returns `CompletableFuture<Object>`.

The trap with `allOf`: it returns `Void`, meaning it doesn't automatically collect the results into a list.
You use it just to know they are done, and then you must map over the original futures and call `join()` on each to
actually extract the values (which is safe and non-blocking now, because `allOf` guarantees they are ready).

Handle: `allOf` to wait for everything (then extract manually), `anyOf` for the first one to cross the finish line.

</details>

### Exception-handling considerations when using `CompletableFuture.allOf()`?
<details><summary>Show answer</summary>

The trap is assuming it is always safe to loop through the futures and call `join()` after `allOf` finishes.

If **any** input future fails:
1. The `allOf()` future itself completes exceptionally — calling `join()` on it throws.
2. The failed input still holds its exception — blindly calling `join()` on it during extraction throws.

**The fix:** guard or handle errors *before* extracting. The most robust way is to attach `.exceptionally()` to each
individual future *before* passing them to `allOf`, so they always resolve to a safe state:

```java
// 1. heal individual futures first
CompletableFuture<String> safe1 = f1.exceptionally(ex -> "fallback 1");
CompletableFuture<String> safe2 = f2.exceptionally(ex -> "fallback 2");

// 2. inputs can't fail now, so allOf can't fail either
CompletableFuture.allOf(safe1, safe2).join();

// 3. safe: safe1 was healed, so join() can't throw
String result1 = safe1.join();
```

Handle: `allOf` waits for all, but if any failed, joining throws; guard or handle before extracting.

</details>

### Exception-handling considerations when using `CompletableFuture.anyOf()`?
<details><summary>Show answer</summary>

The trap is assuming it waits for the first *successful* result.

`anyOf()` completes with the very first future to cross the finish line, regardless of outcome. If the fastest
future completes exceptionally, the whole `anyOf` immediately completes exceptionally with that error. A fast
failure beats a slow success.

```java
CompletableFuture<String> slowSuccess = CompletableFuture.supplyAsync(() -> {
  sleep(1000);          // takes 1 second
  return "Data";
});
CompletableFuture<String> fastFailure =
  CompletableFuture.failedFuture(new RuntimeException("Boom")); // instant

// completes exceptionally with "Boom" — the upcoming success is ignored
CompletableFuture.anyOf(slowSuccess, fastFailure).join();
```

Handle: `anyOf` is "first to finish", not "first to succeed" — a fast failure beats a slow success and instantly
propagates the error.

</details>

### Combine two independent CompletableFutures?
<details><summary>Show answer</summary>

Use `thenCombine()`. Two independent futures run in parallel; it waits for both, then passes both results to a
`BiFunction` to merge them.

```java
CompletableFuture<User> userCf = fetchUserAsync();
CompletableFuture<Cart> cartCf = fetchCartAsync();

// runs when BOTH are done, combining the results
CompletableFuture<HtmlPage> pageCf = userCf.thenCombine(cartCf, (user, cart) -> renderPage(user, cart));
```

Unlike `allOf()` (returns `Void`), `thenCombine()` returns a new future holding the merged result.

Handle: `thenCombine` — two futures in parallel, merge both results; `thenCompose` — sequential, one feeds the next.

</details>

### What happens to downstream stages if a `CompletableFuture` fails?
<details><summary>Show answer</summary>

A failure **short-circuits** the normal pipeline.

All subsequent success-path stages (`thenApply`, `thenAccept`, `thenCompose`) are completely skipped.
Their lambdas never execute.
Instead, the exception falls straight down the chain until it hits an error handler (`exceptionally` or `handle`).

```java
fetchUserAsync()                     // fails: server returns 404 -> future completes with an exception
  .thenApply(User::getName)          // SKIPPED — the future holds an exception, not a User
  .thenApply(String::toUpperCase)    // SKIPPED
  .thenAccept(System.out::println)   // SKIPPED
  .exceptionally(ex -> {             // ex is the 404 error (e.g. RestClientException)
    log(ex);
    return "FALLBACK_NAME";
  })
  .thenAccept(System.out::println);  // EXECUTES normally with "FALLBACK_NAME"
```

</details>


### How do you handle a failed CompletableFuture?
<details><summary>Show answer</summary>

A failure inside the task does not blow up — it sits in the future silently. If you never attach a handler and
never call `get`, the error is **lost**. So you attach one of three:

- `exceptionally(fn)` — runs **only** on the failure path; supplies a fallback value.
- `handle((value, ex) -> ...)` — runs on **both** success and failure; `ex` is null on success. Use when you need
  to inspect either outcome and transform the result.
- `whenComplete((value, ex) -> ...)` — sees both outcomes but only **observes**; it does not change the result.

```java
cf.thenApply(...)
  .exceptionally(ex -> { log(ex); return fallback; });
```

Handle: failure is silent until handled — `exceptionally` for the error path, `handle` to transform either
outcome, `whenComplete` to just watch.

</details>

### What must you consider when placing `exceptionally` or `handle` in a pipeline?
<details><summary>Show answer</summary>

That returning a fallback value **heals** the pipeline.

When these handlers catch an error and return a default value, the future becomes **successful again**. 
The pipeline merges back onto the success track, and any stage chained *after* the handler runs normally.

```java
fetchUser()
  .thenApply(user -> user.email())
  .exceptionally(ex -> "default@email.com") // HEALS the pipeline if fetchUser or email() fails
  .thenAccept(email -> sendWelcome(email)); // EXECUTES on the success path with the fallback
```

Because of this healing, placement defines the control flow:

- **Local handler (in the middle):** catches a failure early, heals the chain, and lets downstream stages keep
  doing useful work with the fallback data.
- **Global handler (at the very end):** a universal catch-all, but a single failure means every intermediate stage
  was skipped — you save the pipeline, not the work.

Handle: handlers heal the chain — returning a fallback puts it back on the success path, so *where* you place it
decides what gets skipped and what gets saved.

</details>


### How do you timeout a CompletableFuture without blocking?
<details><summary>Show answer</summary>

While a plain [`Future`](4.2_Task_Result.md#how-do-you-use-a-future-safely) requires you to use the blocking `get(timeout)`,
`CompletableFuture` (since Java 9) lets you handle timeouts asynchronously as part of the pipeline:

- `orTimeout(time, unit)` — completes exceptionally with a `TimeoutException` if not done in time.
- `completeOnTimeout(fallbackValue, time, unit)` — supplies a default value instead of failing.

```java
cf.orTimeout(5, TimeUnit.SECONDS)
  .exceptionally(ex -> fallback); // catches the timeout seamlessly
```

Handle: use `orTimeout()` or `completeOnTimeout()` to enforce limits asynchronously, keeping the pipeline
non-blocking.

</details>

### What is the hidden resource trap with `orTimeout()` and `completeOnTimeout()`?
<details><summary>Show answer</summary>

They do **not** stop the underlying task.

When the timeout triggers, the `CompletableFuture` itself completes (exceptionally or with a fallback value) and your
downstream pipeline immediately moves on. But the task running inside `supplyAsync()` is completely unaware of the
timeout. It keeps running on the pool thread — making network calls or database queries, burning CPU — until it
naturally finishes, and then its result is simply discarded.

```java
CompletableFuture<String> cf = CompletableFuture
  .supplyAsync(() -> loadData(), pool)   // keeps running even after the timeout fires
  .orTimeout(5, TimeUnit.SECONDS);       // future fails at 5s; loadData() does NOT stop

cf.exceptionally(ex -> "fallback");      // caller moves on — the pool thread is still busy
```

**Why?** A `CompletableFuture` timeout only resolves the state of the *future* (the claim ticket). It does not send a
thread interrupt to the background worker, and the future has no handle on the task to stop it.

Handle: timeouts bound the wait, not the work — the future completes but the underlying task blindly keeps running
and wasting pool resources.

</details>


### If `CompletableFuture` is non-blocking, when and how do you actually extract the final value?
<details><summary>Show answer</summary>

**The problem: bridging async to sync.** Your async pipeline computes data in the background, but eventually a
synchronous caller (a standard REST controller, a legacy method, or a `main` method) needs the actual data to
proceed, respond, or exit.

**The solution: "escaping the async world."** You intentionally block the current thread to wait for the pipeline to
finish and extract the inner value. You do this using either:

- `join()` — throws unchecked exceptions (cleaner, used 90% of the time).
- `get()` — throws checked exceptions (useful if you want strict compiler checks).

**The golden rule:** only call these methods at the absolute "edge" of your architecture (right before returning an
HTTP response or exiting `main`). Never call them inside the pipeline.

```java
// 1. The async pipeline (non-blocking)
CompletableFuture<String> pipeline = CompletableFuture.supplyAsync(() -> fetchDb())
                                                      .thenApply(String::toUpperCase);

// 2. The sync edge (blocking)
// The main thread stops here until the pipeline finishes
String finalData = pipeline.join(); // or pipeline.get()

System.out.println("Done: " + finalData);
```

</details>

### CompletableFuture.get() vs CompletableFuture.join()?
<details><summary>Show answer</summary>

Both block and return the completed value. The difference is the exception they throw on failure:

- `get()` — throws **checked** `ExecutionException` and `InterruptedException`, so you must catch or declare them.
- `join()` — throws **unchecked** `CompletionException`, nothing to declare.

That is why `join()` fits inside lambdas and streams, where checked exceptions don't compile:

```java
list.stream().map(cf -> cf.join()).collect(toList());  // get() would not compile here
```

Both block, so both are the thing composition is meant to avoid — reach for them only at the edge, when you truly
need the value in hand.

Handle: same blocking wait — `get()` throws checked, `join()` throws unchecked (fits in lambdas).

</details>

### Describe a code snippet #1?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
CompletableFuture<Order> getOrderAsync(String userId) {
  return CompletableFuture.supplyAsync(() -> {
    User user = fetchUserAsync(userId).join();
    return fetchOrder(user);
  }, myPool);
}
```

</details>

<details><summary>Show answer</summary>

The stage blocks a pool thread. `join()` (same for `get()`) sits inside the `supplyAsync` body, so the worker
running that stage stops and does nothing while it waits for the inner future — a thread held hostage doing no work.

Concrete failure: `myPool` has 4 threads; 4 concurrent `getOrderAsync` calls each block on `join()`, and the pool is
exhausted. If the inner futures (`fetchUserAsync`) run on that **same** pool, they are stuck in the queue with no
thread free to run them — so they never complete, so the blocked stages never wake. Permanent deadlock, not just
slowdown.

Fix: never block inside a stage. Depend on another async task with `thenCompose` (flatMap) — the worker returns to
the pool immediately, and a thread picks up the next step when the inner future is ready:

```java
CompletableFuture<Order> getOrderAsync(String userId) {
  return fetchUserAsync(userId)
    .thenCompose(user -> fetchOrderAsync(user));
}
```

Handle: blocking inside a stage holds the worker hostage and can deadlock the pool; chain async dependencies with
`thenCompose` instead of `join`/`get`.

</details>

</details>

### Describe a code snippet #2?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
CompletableFuture<Integer> pipeline =
  CompletableFuture.supplyAsync(() -> {
    throw new IllegalArgumentException("bad id");
  });

try {
  Integer result = pipeline.join();
} catch (IllegalArgumentException e) {
  // handle the bad-argument case
} catch (CompletionException e) {
  Throwable realCause = e.getCause();
}
```

</details>

<details><summary>Show answer</summary>

The `IllegalArgumentException` catch never runs. The task threw `IllegalArgumentException`, but `join()` does not
re-throw it directly — it wraps it in a `CompletionException` and throws that. `join()` throws an **unchecked**
exception, so nothing forces you to catch it, but the type you get is the wrapper, not your original. So
`catch (IllegalArgumentException)` matches nothing; control falls to the `CompletionException` block, where you dig
the real error out with `getCause()`.

Fix: catch `CompletionException` and switch on the cause:

```java
try {
  Integer result = pipeline.join();
} catch (CompletionException e) {
  Throwable cause = e.getCause();
  if (cause instanceof IllegalArgumentException) {
    // handle the bad-argument case
  }
}
```

One exception to the wrapping: `join()` throws `CancellationException` directly, unwrapped — so that one you *can*
catch by its own type.

Handle: `join()` wraps the task's exception in a `CompletionException`; a `catch` for the specific type misses it —
catch `CompletionException` and read `getCause()`.

</details>
