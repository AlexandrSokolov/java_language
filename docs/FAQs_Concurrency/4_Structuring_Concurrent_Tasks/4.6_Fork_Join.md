### How do you coordinate thread execution in the following scenario #1?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show question</summary>

You are writing a parallel sorting engine to process a massive array. To maximize speed, the initial task splits the
array in half, submits two new subtasks to sort each half, and waits for them to return so it can merge the results.
Each subtask repeats this splitting and waiting process recursively until the array chunks are small enough to sort
directly. You submit the initial task to a standard `FixedThreadPool` with 8 threads.

</details>

<details><summary>Show answer</summary>

This scenario describes a recursive, divide-and-conquer algorithm with inter-dependent tasks.

Using a standard `ExecutorService` (like a fixed or cached thread pool) and standard `Future` objects for this pattern
will almost certainly freeze your application.

**The Fatal Flaw: Thread Starvation Deadlock**
Traditional thread pools are designed for independent tasks. When a parent task splits its work and calls `future.get()`
to wait for its subtasks, the underlying OS thread blocks entirely. In the scenario above, once 8 parent tasks are
actively blocked waiting for their subtasks to finish, all 8 threads in the pool are consumed. There are zero threads
left to actually execute the pending subtasks in the queue. The system freezes permanently—a state explicitly known as
Thread Starvation Deadlock.

**Secondary Flaw: Lock Contention**
Even if you bypassed the deadlock with an unbounded thread pool, standard executors place all tasks into a single,
global shared queue. Generating millions of tiny recursive subtasks that constantly compete for locks on a single queue
will destroy performance due to massive synchronization overhead.

**The Solution**
This fundamental inability to handle inter-dependent, recursive tasks efficiently requires a completely different
architectural approach. You must use [the Fork/Join Framework](#how-is-thread-starvation-deadlock-solved), 
which redefines how threads wait and utilizes work-stealing to prevent deadlock.

</details>

</details>

### How is thread starvation deadlock solved?
<details><summary>Show answer</summary>

To solve the starvation problem, Java 7 introduced the Fork/Join Framework.

**Definition:** The Fork/Join framework is a highly specialized implementation of `ExecutorService` (specifically, the
`ForkJoinPool`) designed exclusively for divide-and-conquer workloads. It allows a massive task to be recursively broken
down (forked) into smaller subtasks, and then combined (joined) without deadlocking the underlying threads.

**The Magic of Work-Stealing:**
The genius of Fork/Join is how it redefines the act of waiting. When a Fork/Join task calls `join()` to wait for a
subtask to complete, the underlying OS thread does not block or go to sleep. Instead, the framework suspends the current
parent task, and the thread actively looks for other pending subtasks to execute in the meantime. Each worker owns its
own task queue (a deque); an idle worker **steals** tasks from the far end of another worker's deque, so threads stay
busy without fighting over one shared queue. Because threads never idly block waiting for subtasks, a pool of just 4
physical threads can seamlessly execute a tree of 4,000,000 inter-dependent subtasks without ever deadlocking.

</details>

### ExecutorService vs ForkJoinPool - Task Submission
<details><summary>Show answer</summary>

How you submit tasks — and how the pool stores them — is the core mechanical difference between a standard
`ExecutorService` and a `ForkJoinPool`.

**Standard `ExecutorService`:**
- **Code:** you call `pool.submit(task)`.
- **Architecture:** all tasks go into a single, global queue.
- **Result:** every thread competes for locks on that one queue to fetch its next task. Fine for 100 heavy web requests; 
  disastrous for 10 million microsecond-long calculations, where the queue-contention overhead takes longer 
  than the math itself.

**Fork/Join:**
- **Entry point:** you still submit the *root* task from outside the pool once — an ordinary thread calls
  `pool.invoke(task)` (or `submit`). Only inside a running task does the mechanism below take over.
- **Code:** inside a task, it splits by forking its own subtasks — `subtask.fork()` — not by submitting to the pool.
- **Architecture:** no single central queue for the recursion. Every worker thread has its own double-ended queue
  (**deque**).
- **Result:** forking pushes a subtask onto one end of the worker's own deque; the worker pops its next work from that
  same end. Its own end, its own thread — almost no synchronization, no locks.
- **The steal:** a worker that runs out of local work becomes a thief — it takes a task from the *far* end of another
  worker's deque. Stealing from the opposite end keeps it out of the owner's way, so contention stays low and the CPUs
  stay busy.

Handle: one shared queue every thread locks, vs. a private deque per worker with stealing from the far end.

</details>

### What represents a unit of work in a ForkJoinPool?
<details><summary>Show answer</summary>

A `ForkJoinTask` represents a unit of work. It is a plain, lightweight object — not a thread — and it implements 
`Future`, so the task is its own result handle. Unlike a standard task, a passive object you hand to a pool, 
it coordinates its own lifecycle: `fork()` pushes it onto the executing worker's local deque, 
`join()` waits for its result. You put the work in `compute()`;
`RecursiveTask<V>` returns a value, `RecursiveAction` returns none. Tasks are cheap, so you can make millions of them.

**Cooperative waiting:** `join()` does not park or block the OS thread. The runtime suspends the calling task and
repurposes that worker to execute or steal other pending tasks until the awaited one finishes. This is what lets a few
threads drive a deep recursion without deadlocking.

By design a task does **computation only** — no blocking, no I/O, no locks, except joining its own subtasks. A worker
that blocks on anything else stalls the pool, the very thing Fork/Join exists to avoid. (If you must block, a
`ManagedBlocker` tells the pool to add a fill-in thread.)


</details>

## How does a ForkJoinTask compare with other task types?
<details><summary>Show answer</summary>

- **`ExecutorService` — `Callable`/`Runnable`:** a passive unit of work; the pool runs it and hands back a *separate*
  `Future`. No recursion.
- **`CompletableFuture`:** a handle to an async result you chain — `thenApply`, `thenCompose` — for a pipeline of
  dependent steps, often I/O-bound. Not for recursive splitting.
- **`ForkJoinTask`:** the task *is* the `Future` and schedules itself, splitting and waiting recursively. For CPU-bound
  divide-and-conquer.

Handle: `Callable` = work you hand off; `CompletableFuture` = steps you chain; `ForkJoinTask` = a task that splits and
joins itself.

</details>

### What two kinds of task does Fork/Join use?
<details><summary>Show answer</summary>

Both are instances of `ForkJoinTask`:

- **"Small" tasks** — can be performed straightaway, without consuming too much processor time.
- **"Large" tasks** — need to be split up (possibly more than once) before they can be directly performed.

Handle: small = do it now; large = split first, then do the pieces.

</details>

### What are the ForkJoinTask subclasses?
<details><summary>Show answer</summary>

You don't subclass `ForkJoinTask` directly — you extend one of its abstract subclasses, each for a style of work.
The logic goes in `compute()`.

- **`RecursiveAction`** — a task that returns no result. For work done for its effect (fill an array, sort in place).
- **`RecursiveTask<V>`** — a task that returns a value of type `V`. For work whose subtask results are combined
  (sum, search).
- **`CountedCompleter<V>`** — a task where completing one action triggers a follow-on action, instead of a parent
  blocking on `join`. For event-style fan-out where tasks are never joined.

Handle: no result → `RecursiveAction`; returns a value → `RecursiveTask`; completion triggers more work → `CountedCompleter`.

</details>

### What problems suit Fork/Join?
<details><summary>Show answer</summary>

While pure math and sorting algorithms are the textbook cases, Fork/Join is highly effective for practical, CPU-bound
workloads where data can be cleanly partitioned and processed without blocking for I/O.

Practical Examples:

- **Physics Simulations:** Simulating the motion, gravity, and collisions of large numbers of simple objects (e.g.,
  rendering particle effects in a game engine).
- **Log File Analysis:** Parsing massive log files by splitting the file into chunks, scanning for specific patterns or
  errors in parallel, and merging the extracted metrics.
- **Map-Reduce Data Aggregation:** Operations where a final business quantity is calculated from aggregated inputs
  across a massive, in-memory dataset (e.g., mapping user records to sales totals, then reducing them to a global sum).
- **Batch Image/Video Processing:** Applying visual filters or transformations by recursively dividing an image or
  frame into smaller quadrants down to individual pixel blocks.

Checklist — a problem likely reduces well if the answers are "Yes" or "Mostly, with edge cases":

- Can the subtasks work without explicit cooperation or synchronization between them?
- Do the subtasks calculate a value from their data without altering it (i.e., are they pure functions)?
- Is divide and conquer natural for the subtasks?

</details>

### When is Fork/Join the wrong tool?
<details><summary>Show answer</summary>

Fork/Join is for **CPU-bound divide-and-conquer** — work that only ever waits on its own subtasks. 
It's wrong when the work **blocks on anything else**: I/O, sleeping, locks, an external event. 
With about one worker per core, a few blocked workers freeze the pool — the exact stall it exists to avoid.

Use instead:
- **Blocking I/O, independent jobs:** a normal `ExecutorService`, sized for waiting.
- **Chained async steps:** `CompletableFuture`.

Escape hatch: if you must block inside a task, wrap the wait in a `ManagedBlocker` so the pool adds a fill-in thread.

Handle: F/J splits CPU work; anything that blocks belongs on a normal pool or a `CompletableFuture`.

</details>

### Where does the JDK use Fork/Join for you?
<details><summary>Show answer</summary>

**Parallel streams** are built on fork-join pools, so they give you this benefit with almost no effort — when the
work actually suits parallelism. Writing and tuning fork-join tasks by hand is tricky; parallel streams are the easy
door to the same engine.

Handle: `parallelStream()` is Fork/Join without the hand-written tasks.

</details>

### How is recursive splitting implemented in Fork/Join?
<details><summary>Show answer</summary>

Extend a `ForkJoinTask` subclass (here `RecursiveAction`, no return value) and put the whole split-or-solve decision in
one `compute()` method. Each task holds the slice it owns — the array plus a `start`/`end` range.

`compute()` has exactly two branches:

```java
protected void compute() {
  if (size() < THRESHOLD) {
    // small enough: solve directly (here, sort this slice serially)
  } else {
    int mid = size() / 2;                       // split the range
    var left  = new TransactionSorter(txns, start, start + mid);
    var right = new TransactionSorter(txns, start + mid, end);
    invokeAll(left, right);                      // fork both, wait for both
    merge(left, right);                          // combine the two results
  }
}
```

The steps of the scheme:
1. **Base case** — below a threshold (e.g. 32 elements), do the work directly. Below this, splitting costs more than it
   saves.
2. **Split** — make child tasks over the two halves of your range.
3. **Fork + join** — `invokeAll(left, right)` submits both children and waits for both. It's the batch form of
   `left.fork(); right.fork(); left.join(); right.join()` — and while waiting, the worker runs other pending tasks
   instead of blocking.
4. **Combine** — merge the children's results into this task's result.

**Submitting it** — from outside the pool, once:

```java
var pool = new ForkJoinPool(4);   // or ForkJoinPool.commonPool()
pool.invoke(new TransactionSorter(transactions));   // blocks the caller until done
```

Handle: `compute()` = if small solve, else split → `invokeAll` → merge; drive the root from outside with `pool.invoke`.

</details>

### What problem does work-stealing solve?
<details><summary>Show answer</summary>

**Task imbalance.** Subtasks in a divide-and-conquer job take different amounts of time. Without work-stealing, a thread
that happens to get a queue of "fast" tasks finishes early and sits idle, while another thread is bogged down with
"slow" ones — if the small tasks run ~5× faster, that thread is done long before the large-task thread. Work-stealing
fixes it: the idle thread steals pending tasks from the overloaded one, so every CPU core stays busy for the whole job.

Handle: uneven task sizes leave threads idle; stealing keeps all cores working to the end.

</details>

### How does the pool rebalance work?
<details><summary>Show answer</summary>

The pool keeps a separate list of tasks for each thread. When one thread finishes its own work, the service reassigns a
task from a still-busy thread to the idle one. It's completely automatic — you write nothing to get it; the runtime does
this balancing for you. (The same mechanism seen at the data-structure level: each worker owns a deque, and an idle
worker takes work from the far end of another's.)

Handle: finished thread gets a task handed over from a busy one — automatic, no code required.

</details>

### What does work-stealing assume about tasks?
<details><summary>Show answer</summary>

**That tasks are independent of each other.** Work-stealing runs tasks in an unpredictable order across different
threads, so any shared mutable state or inter-task dependency turns into race conditions and results that differ from
run to run. If the independence assumption doesn't hold, the computation is no longer correct.

Handle: stealing reorders tasks freely — depend on order or shared state and results go non-deterministic.

</details>

### What methods interact with a ForkJoinPool?
<details><summary>Show answer</summary>

Three ways to start a task from outside the pool:

- **`invoke(task)`** — synchronous: starts the task and blocks the caller until the result comes back.
- **`execute(task)`** — asynchronous, fire-and-forget: starts the task, returns nothing.
- **`submit(task)`** — asynchronous: starts the task and immediately returns a `Future` to fetch the result later.

Handle: `invoke` = run and wait; `execute` = fire and forget; `submit` = get a `Future` back.

</details>

### What is the common pool?
<details><summary>Show answer</summary>

`ForkJoinPool.commonPool()` — a single, globally shared `ForkJoinPool` for the whole JVM, added in Java 8. It can run
recursive tasks, but it exists mainly so standard features (like parallel streams) get work-stealing without every
developer creating and managing their own pool. Its properties — parallelism level (how many threads) and the thread
factory — are configurable.

Handle: one JVM-wide pool so built-in features get work-stealing for free; you rarely make your own.

</details>
