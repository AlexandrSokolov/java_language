### How do you create an ExecutorService?
<details><summary>Show answer</summary>

Factory methods on `Executors`. First three pick a **pool size**; the last is a different axis — **timing**.

- [`newSingleThreadExecutor()`](#what-is-newsinglethreadexecutor) — one thread, a queue; tasks run one at a time.
- [`newFixedThreadPool(n)`](#what-is-newfixedthreadpool) — a fixed count of threads you set.
- [`newCachedThreadPool()`](#what-is-newcachedthreadpool) — unbounded; reuses idle threads, makes new ones as needed.
- [`newScheduledThreadPool(n)`](#what-is-newscheduledthreadpool) — adds delayed and repeating tasks.

Trigger: one → fixed N → unbounded (the size spectrum), then scheduled (the timing one).

</details>

### What is newSingleThreadExecutor()?
<details><summary>Show answer</summary>

One thread plus a task queue. The single thread takes tasks one at a time and runs each to completion before taking
the next. Tasks never overlap — serial execution with a backlog.

</details>

### What must you handle when using a single-thread executor?
<details><summary>Show answer</summary>

Its lifecycle end — the pool runs tasks on a background thread, so ending the program correctly is on you.

**Exit-before-run.** `submit(task)` only queues the task; the worker picks it up asynchronously. 
If `main` exits right after submitting, the JVM can terminate before the task ever runs.

**Orderly shutdown.** `shutdown()` stops accepting new tasks and finishes what's queued — but it does **not** block.
Call it, and `main` still races ahead. To actually wait, follow it with `awaitTermination(timeout)`, which blocks
`main` (keeping the JVM alive) until the queue drains or the timeout hits.

**The infinite-loop trap.** `shutdown()` waits for queued tasks to finish. 
A task with `while(true)` never finishes, so the worker is stuck in it and the pool never terminates — the process hangs. 
`shutdown()` won't interrupt it; `shutdownNow()` (or the `awaitTermination` timeout → `shutdownNow`) is the escape.

```java
executor.submit(() -> System.out.println("running"));
executor.shutdown();                                  // no new tasks; does NOT block
if (!executor.awaitTermination(5, TimeUnit.SECONDS))  // blocks main until drained or timeout
  executor.shutdownNow();                             // force-stop stragglers (interrupts workers)
```

Handle: `shutdown()` signals, `awaitTermination()` waits, `shutdownNow()` forces — and a non-interruptible infinite
task defeats the first two.

</details>

### What is newFixedThreadPool()?
<details><summary>Show answer</summary>

The multi-thread generalization of [`newSingleThreadExecutor()`](#what-is-newsinglethreadexecutor). You give a thread
count at creation; the pool holds exactly that many threads and runs up to that many tasks at once.

</details>

### What must you consider when using a fixed thread pool?
<details><summary>Show answer</summary>

**Exceptions go quiet, not the pool.** A common myth is that a worker killed by a runtime exception isn't replaced and
the pool starves. Not so — `ThreadPoolExecutor` replaces a dead worker and restores the thread count. 
The real problem is that the *failure* can vanish:

- `execute(task)` — an uncaught exception propagates: the worker dies (and is replaced), and the exception reaches the
  thread's `UncaughtExceptionHandler` or prints a stack trace. Visible.
- `submit(task)` — the exception is captured in the returned [`Future`](#) as the task's outcome and **swallowed**. You
  see nothing unless you call `get()`.

So with `submit()`, failing tasks disappear silently while the pool keeps running as if nothing happened.

Handle: a fixed pool survives task failures — but `submit()` hides them in the `Future`; call `get()`, or hook
`afterExecute`, to not lose them.

</details>

### What is newCachedThreadPool()?
<details><summary>Show answer</summary>

An unbounded pool. It reuses an idle thread if one is free, otherwise creates a new one for each incoming task. Idle
threads are eventually reaped. Good for many short tasks; risky under heavy load — no cap on thread count.

</details>

### What is newScheduledThreadPool()?
<details><summary>Show answer</summary>

Extends the usual executor service with **timing**:

- `schedule()` — run a one-off task after a delay.
- `scheduleAtFixedRate()` — repeat at a fixed period.
- `scheduleWithFixedDelay()` — repeat with a fixed gap between the end of one run and the start of the next.

</details>

### Cached vs fixed thread pool — which to use?
<details><summary>Show answer</summary>

The trade-off is largely about reusing threads vs creating and destroying threads to achieve different effects.

Depends on load:

- **`newCachedThreadPool`** — no configuration, does the right thing for a small program or a lightly loaded server.
  But it doesn't queue tasks: if no thread is free, it makes a new one. On a heavily loaded server that's dangerous —
  more tasks arriving on a maxed-out machine spawn more threads, making things worse.
- **`newFixedThreadPool`** — a fixed number of threads, so load can't spawn unbounded threads. The right default for
  a heavily loaded production server. For full control, use `ThreadPoolExecutor` directly.

Rule of thumb: cached for small or lightly loaded, fixed (or `ThreadPoolExecutor`) for production under real load.

</details>

### What happens when a slow call's pool queue fills?
<details><summary>Show answer</summary>

It depends on the queue:

- **Unbounded (the default for `Executors.newFixedThreadPool`):** it never fills. When the DB slows down, tasks pile up
  in memory. Each one is a client still waiting, until the [async timeout](#what-if-a-future-never-completes) ends the
  request. The task may still run later, for a client who is already gone.
- **Bounded:** when it is full, the executor's rejection policy decides:
  - **Abort (the default):** `supplyAsync` throws `RejectedExecutionException` at once, in the request thread. Map it
    to a fast `503`. This is what you want.
  - **Caller runs:** the task runs on the calling thread, which is the Tomcat request thread, and that thread now
    waits on JDBC. The isolation is gone exactly when you need it.
  - **Discard:** the task is dropped silently, the future never completes, and the client waits until the timeout.

```java
var dbPool = new ThreadPoolExecutor(10, 10, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100));  // at most 100 waiting; the default policy rejects the rest
```

Bound the queue and reject fast: during a slowdown, a quick `503` beats a pile of requests that time out anyway.

</details>
