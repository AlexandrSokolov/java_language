### Task dependencies across threads — challenges?
<details><summary>Show answer</summary>

When tasks are distributed across multiple threads without coordination, several issues occur:

- **Orphaned Threads:** If a parent task fails or terminates unexpectedly, its subtasks continue running. Their
  results are no longer needed, yet they keep consuming memory and CPU time.
- **Lack of Cancellation Propagation:** If a parent requires all subtasks to complete successfully, the failure of
  one subtask should ideally cancel the others. Unstructured concurrency fails to do this automatically.

[**Structured concurrency**](#structured-concurrency--core-principle) solves this by establishing 
strict **task hierarchies**, treating groups of related tasks as a single unit of work. 
This ensures that the lifetime of child tasks is strictly bound to their parent, 
enabling automatic cancellation and resource cleanup.

</details>

### All results vs fastest one — how?
<details><summary>Show answer</summary>

- **All must succeed** — fan-out to several services, the answer needs every part (product + reviews + price).
  `invokeAll(tasks)` or `CompletableFuture.allOf(...)` collect every result, but wait for all tasks even after one
  failed. To stop early, submit to an `ExecutorCompletionService`, take results as they finish, and on the first
  failure `cancel(true)` the other `Future`s.
- **First success wins** — the same request to several replicas, take the fastest. `ExecutorService.invokeAny(tasks)`
  returns the first successful result, cancels the rest with an interrupt, and throws only if every task fails.
  Not `CompletableFuture.anyOf(...)`: it returns whichever finishes first, even a failure, and cancels nothing.

The modern alternative is `StructuredTaskScope`, where both policies are built in. It is not final yet (a preview
feature in JDK 25).

Same job, different stop rule: cancel the rest on the first failure, or on the first success.

</details>

### Parallel calls, one fails — stop the rest?
<details><summary>Show answer</summary>

`CompletableFuture.allOf(a, b)` does not stop early: it completes only after every future completes, even when one
failed at once. To fail fast, you cancel the others yourself:

```java
var product = CompletableFuture.supplyAsync(() -> fetchProduct(id));
var reviews = CompletableFuture.supplyAsync(() -> fetchReviews(id));
product.whenComplete((p, e) -> { if (e != null) reviews.cancel(true); });  // fetchReviews() keeps running
```

- **`cancel(true)` does not interrupt:** on a `CompletableFuture` the flag is ignored. The future completes with
  `CancellationException`, so the caller moves on, but the task keeps running on its thread until it finishes.
- **Fix today:** run the tasks through an `ExecutorService` and, on the first failure, cancel the other `Future`s
  with `cancel(true)`. That interrupts the worker thread; the task still has to react to the interrupt.

`StructuredTaskScope` is built for this: the first failure cancels the sibling subtasks by interrupting their threads.
As of JDK 25 it is still a preview feature, so production code today uses the `Future` approach.

Cancelling a `CompletableFuture` changes its result, not the work behind it.

</details>

### StructuredTaskScope in production — ready?
<details><summary>Show answer</summary>

Not as of JDK 25. It is a **preview feature**: fully built, but not final, and allowed to change or be removed.

- **Needs a flag:** code compiles and runs only with `--enable-preview` (javac also needs `--release 25`).
- **Tied to one JDK:** class files that use a preview feature run only on the exact JDK they were compiled for.
  Every JDK upgrade means a recompile.
- **API still moving:** JDK 21–24 chose the policy by subclass (`ShutdownOnFailure`, `ShutdownOnSuccess`); JDK 25
  replaced that with `open()` and `Joiner`. Code written against one preview breaks on the next.

The senior answer: know the problem it solves and its shape, ship production code on `CompletableFuture` or
`ExecutorService`, and adopt it once it is final.

</details>

### Structured concurrency — core principle?
<details><summary>Show answer</summary>

A parent task splits its work into concurrent subtasks. The rule:

- All subtasks return to the same point in the parent's code.
- Every subtask reports back, success or failure, before the parent can finish.
- The parent supervises: it waits for the subtasks and steps in when one fails.

Concurrent tasks mirror the program's structure, like a manager whose team all reports back before the project is
done.

</details>

### StructuredTaskScope — core API?
<details><summary>Show answer</summary>

`StructuredTaskScope<T, R>` is a sealed interface that ties a group of subtasks to one lifetime. 
`T` is the subtask result type, `R` is what `join()` returns. 
It is `AutoCloseable`, so it lives in a try-with-resources block.

- `open()` — static factory that creates the scope. 
  Default policy: `join()` waits until all subtasks succeed or one fails.
- `fork(...)` — starts a subtask (`Callable` or `Runnable`) in its own thread, virtual by default; returns a `Subtask`.
- `join()` — owner thread only, once. Blocks until subtasks finish or the scope is cancelled, then returns the result
  or throws `FailedException` (cause = the failure); `TimeoutException` if a configured timeout expires.
- `close()` — makes sure every subtask is finished or cancelled; called by try-with-resources, never by hand.

</details>
