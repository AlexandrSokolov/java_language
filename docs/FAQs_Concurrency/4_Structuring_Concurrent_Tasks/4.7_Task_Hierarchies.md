### Task dependencies across threads — challenges?
<details><summary>Show answer</summary>

When tasks are distributed across multiple threads without coordination, several issues occur:

- **Orphaned Threads:** If a parent task fails or terminates unexpectedly, its subtasks continue running. Their
  results are no longer needed, yet they keep consuming memory and CPU time.
- **Lack of Cancellation Propagation:** If a parent requires all subtasks to complete successfully, the failure of
  one subtask should ideally cancel the others. Unstructured concurrency fails to do this automatically.

[**Structured concurrency**](#structured-concurrency--core-principle) solves this by establishing 
strict **task hierarchies**, treating groups of related tasks as a single unit of work. 
This ensures that the lifetime of child tasks is strictly bound to their parent, 
enabling automatic cancellation and resource cleanup.

</details>

### Fail-fast wait for all tasks — how?
<details><summary>Show answer</summary>

When gathering data from multiple services (like product, reviews, and price), the entire operation fails if one
fails. You want to stop the remaining tasks immediately to save resources.

**The Wrong Try:**
Using `ExecutorService.invokeAll()` or `CompletableFuture.allOf()` - has the same problem: 
it completes only when every task is done. If task A fails in 100ms, but task B takes 5 seconds, 
these methods still wait the full 5 seconds before reporting the failure.
```java
List<Future<Part>> futures = executor.invokeAll(tasks);  // blocks until ALL tasks are done
for (Future<Part> f : futures) {
  parts.add(f.get());                                    // the failure shows up only here, too late
}
```

**The Right Approach:**
Use an `ExecutorCompletionService`. Submit all tasks, loop through `done.take()`, and if one throws an exception, 
iterate through the remaining Futures and call `cancel(true)`.
```java
ExecutorCompletionService<Part> done = new ExecutorCompletionService<>(executor);
List<Future<Part>> futures = new ArrayList<>();
for (Callable<Part> task : tasks) {
  futures.add(done.submit(task));
}
List<Part> parts = new ArrayList<>();
try {
  for (int i = 0; i < tasks.size(); i++) {
    parts.add(done.take().get());        // next task to finish; a failure throws here right away
  }
  return parts;                          // finish order, not task order
} catch (Exception e) {
  futures.forEach(f -> f.cancel(true));  // stops the rest after a failure; no effect on finished tasks
  throw e;
}
```
`cancel(true)` only interrupts the thread. A task that ignores interrupts keeps running.

The modern alternative is `StructuredTaskScope`, where "cancel the rest on the first failure" is built in. 
It is not final yet (still a preview feature).

Handle: need any one result → first success wins, a failure never wins, the rest are cancelled.

</details>

### First success wins — how?
<details><summary>Show answer</summary>

The same request goes to several replicas, and the first good answer is enough. A failure must not win, and the slower
calls should be cancelled to free up resources.

Wrong try:

```java
Object first = CompletableFuture.anyOf(
    CompletableFuture.supplyAsync(replicaA::fetch),
    CompletableFuture.supplyAsync(replicaB::fetch)).join();  // first to FINISH, even if it failed
```

- A fast failure wins over a slower success.
- Nothing is cancelled: the other calls keep running. Even calling `cancel(true)` on a `CompletableFuture` does not
  interrupt the running task.
- The result is `Object`, so a cast is needed.

Right:

```java
try (ExecutorService executor = Executors.newFixedThreadPool(3)) {
  List<Callable<Price>> replicas = List.of(replicaA::fetch, replicaB::fetch);
  Price price = executor.invokeAny(replicas);  // first SUCCESS; the rest are cancelled with an interrupt
} catch (ExecutionException e) {
  // Handled only if ALL replica tasks failed
}
```

The modern alternative is `StructuredTaskScope`, where "first success wins, cancel the rest" is built in. 
It is not final yet (still a preview feature).

Handle: need any one result → first success wins, a failure never wins, the rest are cancelled.

</details>

### Parallel calls, one fails — stop the rest?
<details><summary>Show answer</summary>

`CompletableFuture.allOf(...)` does not stop early: it completes only after every future completes, even when one
fails at once. Cancelling the others yourself does not help either:

```java
var product = CompletableFuture.supplyAsync(() -> fetchProduct(id));
var reviews = CompletableFuture.supplyAsync(() -> fetchReviews(id));
product.whenComplete((p, e) -> { if (e != null) reviews.cancel(true); });  // fetchReviews() keeps running
```

`cancel(true)` on a `CompletableFuture` does not interrupt: the flag is ignored. The future completes with
`CancellationException`, so the caller moves on, but `fetchReviews()` keeps running on its thread.

**Solutions:**
- A plain `Future` from an [`ExecutorService`](#fail-fast-with-executorservice--how) can stop the work: 
  its `cancel(true)` interrupts the thread. 
- An [`ExecutorCompletionService`](#fail-fast-with-executorcompletionservice--how) adds the other half: 
  it shows the first failure as soon as it happens.

`StructuredTaskScope` is built for this: the first failure cancels the sibling subtasks by interrupting their threads.
As of JDK 25 it is still a preview feature, so production code today uses the executor approach.

Cancelling a `CompletableFuture` changes its result, not the work behind it.

</details>

### Fail fast with ExecutorService — how?
<details><summary>Show answer</summary>

`submit` returns a plain `Future`. Unlike `CompletableFuture`, its `cancel(true)` interrupts the thread running the
task.

```java
Future<Product> product = pool.submit(() -> fetchProduct(id));
Future<Reviews> reviews = pool.submit(() -> fetchReviews(id));
try {
  return new Page(product.get(), reviews.get());
} catch (Exception e) {
  product.cancel(true);  // interrupts the thread if still running; no effect if done
  reviews.cancel(true);
  throw e;
}
```

The task still has to react to the interrupt; one that ignores it keeps running.

Limit: `get()` waits in the order you call it. If `fetchReviews()` fails at 100 ms and `fetchProduct()` takes 5 s,
`product.get()` holds you for the full 5 s before the failure shows up. To react to whichever task fails first, use
[`ExecutorCompletionService`](#fail-fast-with-executorcompletionservice--how).

`Future.cancel(true)` stops the work; the order of `get()` calls decides how early you see the failure.

</details>

### Fail fast with ExecutorCompletionService — how?
<details><summary>Show answer</summary>

It wraps an executor and hands back each `Future` when its task finishes: `take()` returns the next finished one. 
So the first failure shows up as soon as it happens, whichever task it is.

```java
var done = new ExecutorCompletionService<Object>(pool);  // one result type, so mixed results are Object
Future<Object> product = done.submit(() -> fetchProduct(id));
Future<Object> reviews = done.submit(() -> fetchReviews(id));
try {
  done.take().get();     // first task to finish; a failure throws here at once
  done.take().get();     // second task to finish
} catch (Exception e) {
  product.cancel(true);  // interrupts the one still running
  reviews.cancel(true);
  throw e;
}
return new Page((Product) product.get(), (Reviews) reviews.get());  // both done: get() returns at once
```

Results come in finish order, not call order, so the first failure is the first thing you see.

</details>

### StructuredTaskScope in production — ready?
<details><summary>Show answer</summary>

Not as of JDK 25. It is a **preview feature**: fully built, but not final, and allowed to change or be removed.

- **Needs a flag:** code compiles and runs only with `--enable-preview` (javac also needs `--release 25`).
- **Tied to one JDK:** class files that use a preview feature run only on the exact JDK they were compiled for.
  Every JDK upgrade means a recompile.
- **API still moving:** JDK 21–24 chose the policy by subclass (`ShutdownOnFailure`, `ShutdownOnSuccess`); JDK 25
  replaced that with `open()` and `Joiner`. Code written against one preview breaks on the next.

The senior answer: know the problem it solves and its shape, ship production code on `CompletableFuture` or
`ExecutorService`, and adopt it once it is final.

</details>

### Structured concurrency — core principle?
<details><summary>Show answer</summary>

A parent task splits its work into concurrent subtasks. The rule:

- All subtasks return to the same point in the parent's code.
- Every subtask reports back, success or failure, before the parent can finish.
- The parent supervises: it waits for the subtasks and steps in when one fails.

Concurrent tasks mirror the program's structure, like a manager whose team all reports back before the project is
done.

</details>

### StructuredTaskScope — core API?
<details><summary>Show answer</summary>

`StructuredTaskScope<T, R>` is a sealed interface that ties a group of subtasks to one lifetime. 
`T` is the subtask result type, `R` is what `join()` returns. 
It is `AutoCloseable`, so it lives in a try-with-resources block.

- `open()` — static factory that creates the scope. 
  Default policy: `join()` waits until all subtasks succeed or one fails.
- `fork(...)` — starts a subtask (`Callable` or `Runnable`) in its own thread, virtual by default; returns a `Subtask`.
- `join()` — owner thread only, once. Blocks until subtasks finish or the scope is cancelled, then returns the result
  or throws `FailedException` (cause = the failure); `TimeoutException` if a configured timeout expires.
- `close()` — makes sure every subtask is finished or cancelled; called by try-with-resources, never by hand.

</details>
