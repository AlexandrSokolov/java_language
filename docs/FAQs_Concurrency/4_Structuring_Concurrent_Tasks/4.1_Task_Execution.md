### Why not write your own work/thread queue or use `java.lang.Thread` directly?
<details><summary>Show answer</summary>

Both are obsolete and failure-prone. A hand-rolled work queue is subtle, delicate code — easy to get wrong in ways
that cause safety and liveness failures.

`Thread` is the low-level primitive; the modern move is tasks-as-code run on a thread pool, not one thread per job.

The executor framework replaces all of it. A better work queue than a page of hand-written code is one line:

```java
ExecutorService exec = Executors.newSingleThreadExecutor();
exec.execute(runnable);
```

So don't manage threads and queues by hand — describe the work and let an executor run it.

</details>

### What did the executor framework separate?
<details><summary>Show answer</summary>

It split the **work** from the **thing that runs it** — two things a raw `Thread` fuses into one.

- With a raw `Thread`, the thread *is* both the unit of work and the mechanism that executes it. 
  You can't change how work runs without rewriting the work.
- With the executor framework, the **task** is the unit of work, 
  and the **executor service** is the mechanism that runs it. They're separate.

Because they're separate, you pick how work runs — one thread, a fixed pool, scheduled — 
and change that choice later without touching the tasks. 

</details>

### What can represent a task in the executor framework?
<details><summary>Show answer</summary>

Three shapes, from simplest to most capable:

- [`Runnable`](#what-is-a-runnable) — runs, returns nothing.
- [`Callable`](#what-is-a-callable) — runs and returns a result (and may throw checked exceptions).
- [`FutureTask`](#what-is-a-futuretask) — a task that is *also* its own result handle.

Trigger: no result → result → result-that-is-its-own-handle.

</details>

### What is a Runnable?
<details><summary>Show answer</summary>

A task with no result. Its `run()` method takes nothing, returns `void`, and cannot throw a checked exception. The
original task type since Java 1.0 — you hand it to a thread or an executor to run.

Use it when the work has a side effect but nothing to return.

</details>

### What is a Callable?
<details><summary>Show answer</summary>

A task that **returns a result**. Its `call()` method returns a value and may throw a checked exception — the two
things [`Runnable`](#what-is-a-runnable) can't do. Introduced with `java.util.concurrent`.

Submit it to an executor and you get a [`Future`](#) back to collect the result.

</details>

### What is a FutureTask?
<details><summary>Show answer</summary>

A task that is **also its own result handle**. It implements both `Runnable` (so an executor or thread can run it) and
[`Future`](4.2_Futures_&_CompletableFuture.md#what-does-future-give-you) 
(so you can call `get()` on the same object to collect the result or cancel it).

It has two constructors: one takes a [`Callable`](#what-is-a-callable), the other a [`Runnable`](#what-is-a-runnable)
(converted internally via `Executors.callable()`). So you write the job as a `Callable`, wrap it in a `FutureTask`,
and — because a `FutureTask` *is* a `Runnable` — schedule it on an executor, then cancel or collect from that same
object. No separate `Future` handed back.

</details>

### Runnable vs Callable?
<details><summary>Show answer</summary>

Both are tasks — a unit of work handed to an executor. The difference is what they give back:

- **`Runnable`** — runs, returns nothing, can't throw checked exceptions.
- **`Callable`** — runs, **returns a value**, and **can throw checked exceptions**.

Reach for `Callable` when the work produces a result or may fail in a way the caller must see; `Runnable` when it's
fire-and-forget.

</details>

### What is the state model of a FutureTask?
<details><summary>Show answer</summary>

Seven internal states, four one-way paths from `NEW`. Once past `NEW` the task is settling or settled — no going back.

- **NEW** — created, not yet finished (may be running or not started).
- **COMPLETING** — transient: result is being set, not yet visible.
- **NORMAL** — finished with a result. *(terminal)*
- **EXCEPTIONAL** — finished by throwing. *(terminal)*
- **CANCELLED** — cancelled before running, no interrupt. *(terminal)*
- **INTERRUPTING** — transient: cancel-with-interrupt in progress.
- **INTERRUPTED** — cancelled and the running thread was interrupted. *(terminal)*

Paths: 
- `NEW → COMPLETING → NORMAL`; 
- `NEW → COMPLETING → EXCEPTIONAL`; 
- `NEW → CANCELLED`; 
- `NEW → INTERRUPTING → INTERRUPTED`.

**Observable via the `Future` API** (the internal states aren't exposed directly):

- `isDone()` — `true` in every terminal state (NORMAL, EXCEPTIONAL, CANCELLED, INTERRUPTED).
- `isCancelled()` — `true` for CANCELLED and INTERRUPTED only.

So the API collapses seven states into two questions: is it finished, and was it cancelled. 
`NORMAL` vs `EXCEPTIONAL` you learn only by calling `get()` — result returns, or the exception is rethrown.

</details>

### Who decides when and where a task runs?
<details><summary>Show answer</summary>

Not the caller — an [`Executor`](#what-is-an-executor). It splits *submitting* a task from *running* it.

You call `execute(task)` and return at once; the `Executor` picks the thread and the timing (pooled thread, new
thread, or inline). You own the *what*; it owns the *where and when*.

</details>

### What is an Executor?
<details><summary>Show answer</summary>

The base interface for running tasks. One method: `execute(Runnable)` — "run this, on some thread, not mine."

Its purpose: **decouple submitting a task from running it**. 
The caller stops managing threads; the `Executor` decides how the work runs (pooled thread, fresh thread, or inline). 
Change the execution policy without touching the submitting code.

</details>

### Is Executor a functional interface?
<details><summary>Show answer</summary>

Single abstract method, so a **SAM type** — but **not** tagged `@FunctionalInterface`. A lambda still compiles
(`Executor e = r -> r.run();`); the missing annotation is deliberate — it models a component with a job, not a
function to pass around.

</details>

### What are the limits of Executor?
<details><summary>Show answer</summary>

`Executor` only fires off a task — `execute(Runnable)` returns nothing and offers no way to get a result, wait for
completion, or stop the pool. No result, no lifecycle.

Those gaps are filled by [`ExecutorService`](#what-is-an-executorservice), which extends `Executor`.

</details>

### What is an ExecutorService?
<details><summary>Show answer</summary>

The interface that extends [`Executor`](#what-is-an-executor) and makes it usable. It adds:

- `submit()` — run a task and get a [`Future`](#) back to collect the result or cancel it.
- lifecycle methods — `shutdown()` and friends to stop the pool cleanly.

So `Executor` runs tasks; `ExecutorService` runs them, hands back results, and manages the pool's life.

</details>

### What can an executor service do? (reference)
<details><summary>Show answer</summary>

A lookup card — the range of things an `ExecutorService` offers, grouped by what you're doing:

- **Submit work** — `execute` (fire-and-forget), `submit` (returns a `Future`).
- **Wait for results** — `get` on a `Future` (one task), `invokeAny` (any one of many), `invokeAll` (all of many).
- **Take results as they finish** — `ExecutorCompletionService`, which hands them back in completion order.
- **Schedule** — `ScheduledThreadPoolExecutor` for tasks that run later or repeat.
- **Wind down** — `awaitTermination` to wait for the service to finish.

Treat this as a menu to recognize, not a list to recite — you look up the exact method when you need it.

</details>

### execute() vs submit() — how are task exceptions handled?
<details><summary>Show answer</summary>

A dead worker is always replaced — the pool restores its thread count either way. The difference is what happens to
the *exception*, and it splits by which method you used.

**`execute(Runnable)` — visible, worker dies.** An uncaught exception propagates out of the task. The worker thread
dies and is replaced, and the exception reaches the thread's `UncaughtExceptionHandler` (or prints a stack trace).
Rapid repeated failures mean constant thread destroy-and-recreate — *thread churn*.

**`submit(...)` — silent, worker survives.** The task is wrapped in a [`FutureTask`](#what-is-a-futuretask), whose
`run()` catches the throwable and stores it via `setException`. The worker does **not** die — no churn — but the
exception is swallowed: the `UncaughtExceptionHandler` is never called. It surfaces only when you call
[`Future`](#)`.get()`, rethrown wrapped in an `ExecutionException`.

So the risk inverts: `execute()` is loud and costly (churn); `submit()` is quiet and lossy (hidden failures).

Handle: `execute()` → exception escapes, worker dies + replaced, handler sees it; `submit()` → exception trapped in the
`Future`, worker lives, seen only via `get()`. Wrap the task body in try-catch, or call `get()` — don't trust the
default.

</details>
