### What represents an async task result?
<details><summary>Show answer</summary>

[`Future`](#what-does-future-give-you) — a handle to a result that may not exist yet but will arrive later. 
The task runs elsewhere; the `Future` is your claim ticket for its outcome.

</details>

### What does Future give you?
<details><summary>Show answer</summary>

A `Future<T>` holds the result of a task that may still be running, so you can hand off work and pick up the
outcome later. Three primary methods:

- `get()` — returns the result; **blocks** if it is not ready yet.
- `isDone()` — asks whether the task has finished; non-blocking, returns right away.
- `cancel()` — tries to stop the task before it finishes.

Handle: the task runs somewhere else, the `Future` is how you check on it and collect the result.

</details>

### How do you use a Future safely?
<details><summary>Show answer</summary>

You get a `Future` when you submit a task to an `ExecutorService`; it is your only handle to a task now running
on a pool thread.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<String> f = pool.submit(() -> loadData());

try {
  String result = f.get(5, TimeUnit.SECONDS);   // wait with a limit, never forever
} catch (TimeoutException e) {
  f.cancel(true);                     // didn't finish in time — ask it to stop
} catch (ExecutionException e) {
  Throwable cause = e.getCause();     // the task threw — real error is wrapped inside
} catch (InterruptedException e) {
  Thread.currentThread().interrupt(); // restore the flag before leaving
  f.cancel(true);
}
```

The three checked exceptions mean three different things:

- `TimeoutException` — your wait ran out; the task is **still running**, nothing failed.
- `ExecutionException` — the **task itself threw**; the real exception is inside, dug out with `getCause()`.
- `InterruptedException` — **your** waiting thread was interrupted; restore the flag and stop.

Two traps this guards against: plain `get()` [blocks forever](4.4_Cancellation_&_Shutdown.md#how-does-futurecancel-work) 
if the task hangs — always use the timeout overload; 
and a task exception stays invisible until you call `get`, so a `submit` you never read silently swallows the failure.

Handle: the `Future` is a claim ticket — wait with a limit, and know whether it failed, timed out, 
or you were interrupted.

</details>

### What is the major limitation of a plain `Future`, and what is the alternative?
<details><summary>Show answer</summary>

The fatal flaw of a legacy `Future` is that it **cannot be chained or composed**. There is no built-in way to tell a
`Future`: *"when you finish, pass your result to this next function."* To read the value or handle an error you must
eventually call `.get()`, which **blocks** the calling thread until the result is ready.

**The alternative:** [`CompletableFuture`](#completablefuture--known-by-another-name) (Java 8+). It adds the missing
half — a non-blocking API where you attach callbacks that fire automatically when the task finishes, and can chain,
combine, and handle errors inside the pipeline instead of blocking to pull the value out.

Handle: `Future` can't be chained and forces you to block on `get()`; `CompletableFuture` is the modern alternative
that allows non-blocking pipelines.

</details>

### What are the core architectural differences between `CompletableFuture` and `Future`?
<details><summary>Show answer</summary>

`CompletableFuture` shifts Java concurrency from blocking/imperative to non-blocking/declarative.

**1. Callbacks vs. blocking (`get`).** Legacy `Future` forces you to call `.get()` to retrieve the result, which
blocks the calling thread. `CompletableFuture` allows attaching non-blocking callbacks (`thenApply`, `thenAccept`)
that trigger automatically when the data is ready.

**2. Chaining and composition.** You cannot easily combine legacy futures. `CompletableFuture` lets you chain
dependent tasks (`thenCompose`), combine independent parallel tasks (`thenCombine`), or wait for an entire batch to
finish (`allOf`).

**3. Functional error handling.** Legacy futures force you to wrap `.get()` in an ugly `try-catch` to handle
`ExecutionException`. `CompletableFuture` handles errors directly inside the pipeline using `.exceptionally()` or
`.handle()`.

**4. Manual completion (event-driven).** Legacy futures are strictly tied to an `ExecutorService` finishing a task.
`CompletableFuture` can be manually fulfilled from anywhere by any thread using `.complete()`.

**5. The cancellation gotcha.**
- Legacy: `Future.cancel(true)` interrupts the underlying worker thread.
- Modern: `CompletableFuture.cancel(true)` does **not** interrupt the thread. It only marks the future's state as
  cancelled, so the background thread blindly keeps running and wastes CPU cycles.

</details>

### CompletableFuture — known by another name?
<details><summary>Show answer</summary>

It is Java's version of a **promise** — the general name in other languages (JavaScript, Scala) for an object
that stands for a value that will be supplied later. Same idea: an empty slot now, filled once by whoever holds
it.

</details>

### CompletableFuture vs Future — submit?
<details><summary>Show answer</summary>

Instead of passing the task into the executor, you pass the task to the `CompletableFuture` static factory:

- Legacy: `pool.submit(Callable)`
- Modern: `CompletableFuture.supplyAsync(Supplier)` (use `runAsync(Runnable)` if there is no return value).

**Why the design flip?**

In the legacy model, the `ExecutorService` creates, owns, and tightly couples the execution to the `Future`.
`CompletableFuture` flips this to decouple the asynchronous pipeline from the execution mechanism. 
By acting as an independent state machine, `CompletableFuture` allows you to chain dozens of callbacks 
(`thenApply`, `thenAccept`) seamlessly, dynamically shifting execution across different threads or pools 
without forcing a single executor to manage the entire workflow.

</details>

### What dictates the execution pool for a `CompletableFuture`, and what limitations must be considered?
<details><summary>Show answer</summary>

If you call `supplyAsync(Supplier)` without specifying a thread pool, the task runs on the JVM-wide
`ForkJoinPool.commonPool()`.

**The limit:** the common pool size is strictly tied to your CPU core count (`availableProcessors() - 1`).

**The danger:** because it is shared globally across the JVM, running blocking I/O tasks (database queries, network
calls) on the common pool will instantly exhaust its threads. This starves and freezes all other
`CompletableFuture` tasks and parallel streams in your application.

**The solution:** for anything other than pure CPU-bound computation, always isolate your workloads. Use the
overloaded method to pass a dedicated pool: `CompletableFuture.supplyAsync(Supplier, customPool)`.

</details>

### Run CompletableFuture on your own pool?
<details><summary>Show answer</summary>

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

// 1. Pass the executor as the second argument
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> loadData(), pool);

// 2. Chain operations (Java 9+ for timeout features)
cf.orTimeout(5, TimeUnit.SECONDS)
  .exceptionally(ex -> {
      // orTimeout completes with a RAW TimeoutException -> ex is it, ex.getCause() is null.
      // If loadData() throws, ex is a CompletionException wrapping the real cause.
      // exceptionally does NOT unwrap, so normalize both shapes yourself:
      Throwable rootCause = ex.getCause() != null ? ex.getCause() : ex;

      if (rootCause instanceof TimeoutException) {
          System.out.println("Task timed out!");
      } else {
          System.out.println("Task failed with: " + rootCause.getMessage());
      }
      return "Fallback Data"; // Provide a default value to recover
  })
  .thenAccept(result -> {
      // This only runs if we succeeded (or recovered in exceptionally)
      System.out.println("Result: " + result);
  });
```

How the concepts map over:

- **Submitting the task:** `pool.submit(Callable)` becomes `CompletableFuture.supplyAsync(Supplier, ExecutorService)`.
  (Use `runAsync(Runnable, ExecutorService)` if it doesn't return a value.)
- **Timeouts:** instead of blocking the main thread with `f.get(5, SECONDS)`, you attach
  `.orTimeout(5, TimeUnit.SECONDS)` to the pipeline. If the time expires, the future automatically completes
  exceptionally with a `TimeoutException`.
- **Execution exceptions:** instead of catching `ExecutionException`, you append `.exceptionally(ex -> ...)` or
  `.handle((result, ex) -> ...)`. The error travels down the pipeline to the first handler — but the throwable it
  arrives as is not normalized: a raw `TimeoutException` from `orTimeout`, or a `CompletionException` wrapping what
  `loadData()` threw. The `getCause()` line above is what reconciles the two.

</details>

### Two design styles a `CompletableFuture` supports?
<details><summary>Show answer</summary>

Manually calling `complete()` represents a shift from **task-driven** to **event-driven** concurrency.

**Task-driven — `supplyAsync()`.** You tie the future to a specific execution: "here is a block of code, run it on a
thread pool, and the future is the result of that code."

**Event-driven — `new CompletableFuture<>()` + `complete()`.** You decouple the future from any specific task or
thread pool. You create an empty "dropbox" (a promise). You don't care how the work is done, which pool does it, or
when it happens. You hand out the dropbox and say: "whenever the data arrives, whoever has it, drop it in here."

Mental model:
- Use `supplyAsync()` when you have a job to give to a thread.
- Use `new CompletableFuture<>()` + `.complete()` when you are waiting on an event (a callback, a network message, a
  human) and just need a way to signal the rest of your program that the event has occurred.

</details>

### Turn a callback API into a Future?
<details><summary>Show answer</summary>

Many older libraries (older HTTP clients, GUI frameworks, Android APIs) use asynchronous callbacks instead of
returning futures. Manually completing a `CompletableFuture` lets you wrap a messy, nested callback API into a
modern, chainable future.

```java
public CompletableFuture<String> fetchUserAsync(String userId) {
    // 1. Create the empty "dropbox"
    CompletableFuture<String> future = new CompletableFuture<>();

    // 2. Call the legacy API that takes a callback listener
    legacyHttpClient.get("/users/" + userId, new AsyncCallback() {
        @Override
        public void onSuccess(String response) {
            future.complete(response); // Fill the dropbox from the network thread
        }

        @Override
        public void onFailure(Exception e) {
            future.completeExceptionally(e); // Propagate the error
        }
    });

    // 3. Return the future immediately to the caller
    return future;
}
```

Now the caller can use `.thenApply()`, `.orTimeout()`, and other modern features, completely unaware that the
underlying library uses old-school callbacks.

</details>

### What is the thread-hijacking trap when using manual `complete()` (e.g., bridging a callback)?
<details><summary>Show answer</summary>

The thread that calls `.complete()` is forced to execute all downstream **synchronous** stages.

If you call `future.complete(response)` from inside a legacy network listener or a UI event thread, that thread
instantly starts executing the rest of the pipeline. If the pipeline holds heavy CPU work or blocking calls, you
have just frozen the network or UI thread.

```java
// 1. network thread receives data and completes the future
legacyHttpClient.get("/users", new AsyncCallback() {
  public void onSuccess(String response) {
    future.complete(response); // the network thread runs this
  }
});

// 2. SOMEWHERE ELSE, where the chain is defined:
// runs INLINE on the network thread the moment complete() is called
future.thenApply(this::heavyCpuProcessing);
```

**The fix:** chain heavy work with `thenApplyAsync()` / `thenAcceptAsync()` so it runs off the completing thread,
releasing the I/O or UI thread immediately. Pass **your own** pool for blocking or heavy work — a bare `...Async`
goes to the common pool, which is only safe for short CPU work:

```java
future.thenApplyAsync(this::heavyCpuProcessing, myPool);
```

Handle: manual `complete()` runs plain stages inline on the completing thread; use `...Async` with your own pool so
you don't hijack an I/O or UI thread.

</details>

### Describe a solution for the following scenario #1?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A lookup method must return a `CompletableFuture<User>`, because callers chain onto it. But on a cache hit you
already have the value in hand — there is no async work left to do. How do you satisfy the `CompletableFuture`
return type without spawning a task or tying up a pool thread just to carry a value you already have?

</details>

<details><summary>Show solution</summary>

Use `CompletableFuture.completedFuture(value)`. It creates a future that is already resolved — nothing runs on a
pool, nobody waits. Highly useful in caching, where you only pay the async penalty when the data is actually
missing.

```java
public CompletableFuture<User> getUser(String id) {
  User cached = cache.get(id);
  if (cached != null) {
    // Instant return, no threads used, no waiting
    return CompletableFuture.completedFuture(cached);
  }
  // Only pay the cost of spawning a task if there is a cache miss
  return CompletableFuture.supplyAsync(() -> db.fetch(id));
}
```

Any callback (`thenApply`, etc.) attached to a `completedFuture` executes immediately on the caller's thread,
because the future is already done.

Handle: `CompletableFuture.completedFuture(val)` bypasses thread pools to return a pre-resolved promise.

</details>

</details>

### Is a CompletableFuture immutable and thread-safe?
<details><summary>Show answer</summary>

It is **not immutable** — its state does change over time. But it is still safe, because it changes only **once**:
from uncompleted to completed, and never again. There is no way for different threads to see different values.

Two facts make this hold:

- The value is whatever the **first** thread to call `complete()` provided — fixed from then on.
- Every thread sees that same one value; there is no window where an inconsistent or half-changed state is
  visible.

So it sidesteps the usual problem of shared mutable state: mutation is real but happens exactly once and is
atomic to observers.

Handle: not immutable, but safe — one-way change, once only, same value seen by all.

</details>
