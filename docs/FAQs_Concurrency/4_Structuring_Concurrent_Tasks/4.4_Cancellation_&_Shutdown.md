### How do you stop one thread from another?
<details><summary>Show answer</summary>

Have the thread poll a `boolean` flag: it starts `false`, and another thread sets it `true` 
[to ask the running thread to stop itself.](../1_Fundamentals/1.5_Thread_Lifecycle_&_Control.md#what-is-a-safe-way-to-stop-a-running-thread) 
The running thread checks the flag between iterations and returns when it sees `true`.

This is for a thread doing a long, heavy job — one that runs its own loop long enough to need checking a
flag partway through. Never use `Thread.stop`: it was deprecated long ago because it can leave data
half-written and corrupted.

For work that splits into small, short tasks, there is an alternative design where no thread needs
stopping at all — you stop handing out new work and let the running pieces finish. Covered separately.

</details>

### What are the main challenges of managing an ExecutorService lifecycle?
<details><summary>Show answer</summary>

Managing thread pools requires handling several critical lifecycle issues to prevent hangs and resource leaks:

- **[The JVM Hang (Resource Leak):](#never-stopping-an-executor--what-happens)** 
  Worker threads are non-daemon by default. If you do not shut down the executor,
  these idle threads will keep the JVM alive indefinitely after the main program finishes.
- **The Shutdown Race:** Calling `shutdown()` initiates a graceful stop but does **not** block the main thread. If
  `main` exits immediately, the JVM might terminate before queued tasks run.
- **[The Infinite Task Trap:](#why-can-an-executorservice-hang-even-if-you-call-shutdown-and-shutdownnow)** 
  `shutdownNow()` attempts to force-stop tasks by sending an interrupt. If a task ignores
  interrupts (e.g., a tight `while(true)` loop), the pool can never terminate.
- [Both `shutdown()` and `shutdownNow()` return at once](#waiting-for-an-executor-to-stop): 
  tasks may still be running.
- [`close()` waits, but with no time limit](#executor-in-try-with-resources--what-happens)

</details>

### Never stopping an executor — what happens?
<details><summary>Show answer</summary>

It depends on whether the pool's threads are **daemon threads** — background threads the JVM does not wait for at exit.

- **JVM hang (normal threads):** `Executors` pools (`newFixedThreadPool`, `newSingleThreadExecutor`) create
  non-daemon threads by default. Their idle workers keep the JVM alive after `main` ends, so the program never exits.
  In a long-running app, every forgotten pool also keeps its threads forever, which is a resource leak.
- **Lost work (daemon threads):** `ForkJoinPool`, including the common pool, and virtual threads. When `main` ends,
  the JVM exits and unfinished tasks are lost, even ones that never started.

Handle: normal threads → the JVM hangs; daemon threads → work is lost.

</details>

### Ways to stop an executor?
<details><summary>Show answer</summary>

Two ways. Both reject new tasks (`submit` throws `RejectedExecutionException`), and both return at once without waiting.

- `shutdown()`: queued tasks still run, running tasks finish. Nothing is interrupted.
- `shutdownNow()`: queued tasks are removed and returned as `List<Runnable>`, so they never run. Running tasks are
  interrupted; a task that ignores the interrupt keeps running.

**Special cases:**
- On `ForkJoinPool.commonPool()` both do nothing, because the whole JVM shares it.
- On a virtual thread executor (`newVirtualThreadPerTaskExecutor`), there is no queue. `shutdownNow()` interrupts
  running tasks but always returns an empty list.


Handle: `shutdown()` lets the work finish; `shutdownNow()` drops the queue and asks running tasks to stop.

</details>

### Waiting for an executor to stop?
<details><summary>Show answer</summary>

`shutdown()` only starts the stop and returns at once. Code after it runs while tasks are still running, and with
daemon threads `main` can end and lose them. `awaitTermination(timeout)` blocks until all tasks are done, or returns
`false` when the time runs out.

```java
pool.shutdown();
try {
  if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                                // time is up: drop the queue, interrupt running tasks
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
      log.error("pool did not stop");                  // a task ignores the interrupt
    }
  }
} catch (InterruptedException e) {
  pool.shutdownNow();
  Thread.currentThread().interrupt();                  // keep the interrupt for the caller
}
```

Handle: `shutdown()` starts the stop, `awaitTermination()` waits for it, `shutdownNow()` is plan B when time runs out.

</details>

### Executor in try-with-resources — what happens?
<details><summary>Show answer</summary>

Since JDK 19, `ExecutorService` is `AutoCloseable`. At the end of the block, `close()`:

1. calls `shutdown()`: no new tasks are accepted; queued and running tasks still finish;
2. waits until every task is done, **with no time limit**;
3. if the thread waiting in `close()` is interrupted, calls `shutdownNow()` and keeps waiting.

```java
try (var pool = Executors.newFixedThreadPool(4)) {
  pool.submit(() -> doWork());
}  // close(): shutdown() + wait until all tasks are done
```

- A task that never ends → `close()` never returns.
- The same holds for every executor, including `newVirtualThreadPerTaskExecutor()`. Nothing is queued there, so
  `close()` just waits for every task's thread.
- On `ForkJoinPool.commonPool()`, `close()` does nothing. The whole JVM shares that pool, so closing it would break
  parallel streams and `CompletableFuture` async calls.

Handle: 
- `close()` waits forever and only forces `shutdownNow()` if the parent thread is interrupted; 
- when you need a time limit, use `shutdown()` + `awaitTermination()`.

</details>

### Why can an ExecutorService hang even if you call shutdown() and shutdownNow()?
<details><summary>Show answer</summary>

`shutdown()` waits for all running tasks to finish. If a task contains an infinite loop (like `while(true)`) or
blocks indefinitely on an unresponsive network call, it will never finish naturally.

When you escalate to `shutdownNow()` (or when the Java 19+ `close()` fallback triggers), the executor attempts to
stop the task by interrupting the worker thread.

However, `shutdownNow()` only sets the thread's interrupt flag. If your task code swallows `InterruptedException`
or fails to periodically check `Thread.currentThread().isInterrupted()`, the task will completely ignore the
cancellation attempt. The thread remains stuck, the pool fails to terminate, and your application hangs.

</details>

### How does Future.cancel work?
<details><summary>Show answer</summary>

`cancel(boolean mayInterruptIfRunning)` does **not** guarantee the task stops. What it does depends on the task's
state:

- **Not started yet** → removed from the queue, never runs. Clean cancel.
- **Already running** → the boolean decides: `cancel(true)` interrupts the running thread; `cancel(false)` leaves
  it running and only marks the `Future` cancelled.
- **Already finished** → does nothing, returns `false`.

The trap: `cancel(true)` only **interrupts** — a request, not a kill. It stops the task only if the task
**cooperates**: it calls a blocking method that responds to interrupt (`sleep`, `wait`, interruptible I/O), or it
checks the flag itself in its loop. A tight CPU loop that never checks runs to the end and ignores the cancel.
Java has no force-kill for a thread by design.

```java
Future<?> f = pool.submit(() -> {
  while (!Thread.currentThread().isInterrupted()) {   // checks → can be cancelled
    doChunk();
  }
});
```

Handle: cancellation is cooperative — `cancel(true)` asks the task to stop, and only a task written to notice the
interrupt actually will.

</details>

### Cancelled vs interrupted — when to trigger which?
<details><summary>Show answer</summary>

Both come from one call: `cancel(boolean mayInterruptIfRunning)`. The boolean decides one thing — *do I also poke the
running thread?* Two separate things move: the task's own `state` field, and the running thread's interrupt flag.

- `cancel(false)` → sets state **CANCELLED**. Touches no thread. It does not call `interrupt()` and does not clear any
  flag — it only marks the task so it never runs (if not started) or is recorded as cancelled.
- `cancel(true)` → sets **INTERRUPTING**, calls `runner.interrupt()` on the executing thread (which *sets* that
  thread's interrupt flag), then sets **INTERRUPTED**.

Neither call ever *clears* the interrupt flag. The flag is a side effect of `cancel(true)` only — the code calls
`interrupt()` unconditionally on the runner if one exists (a no-op if already set); nothing reads or resets it.

**Why the split — interrupt only does something if the task checks it.** Setting the flag has no effect unless the
task hits a blocking call (`sleep`, I/O, queue `take`) that throws `InterruptedException`, or polls the flag itself. A
tight CPU loop that never checks runs to the end regardless. And a task that hasn't started has no thread to interrupt.

**So the choice:**

- Not started yet, or running but fine to finish / won't respond to interrupt → `cancel(false)`.
- Running and blocked in a wait you need it to break out of *now* → `cancel(true)`.

Handle: `state` field and thread interrupt flag are two different things — `cancel(false)` writes only the state;
`cancel(true)` writes the state *and* calls `interrupt()` on the runner; neither clears the flag.

</details>

### Does CompletableFuture.cancel interrupt the task?
<details><summary>Show answer</summary>

No. `cancel()` completes the future exceptionally with a `CancellationException`, so anything waiting downstream
stops seeing a value — but the running task is **not** interrupted. The `mayInterruptIfRunning` flag is ignored.

This is the sharp contrast with [`Future.cancel`](#how-does-futurecancel-work), where `cancel(true)` does send an
interrupt. On a `CompletableFuture` the work already running keeps going to the end regardless.

Handle: `cancel` breaks the chain, not the work — it fails the future but lets the running task finish.

</details>

### CompletableFuture vs Future — cancel?
<details><summary>Show answer</summary>

**`Future.cancel(true)`** interrupts the worker thread running the task — calls `Thread.interrupt()` on it.

**`CompletableFuture.cancel(true)`** does not — `mayInterruptIfRunning` is ignored. It only marks the future cancelled;
the background thread keeps running and burns CPU. A `CompletableFuture` holds no reference to the worker, so it has
nothing to interrupt.

Handle: cancelling a `CompletableFuture` cancels the *future*, not the *work*.

</details>
