### Why is concurrent code hard to test?
<details><summary>Show answer</summary>

Bugs depend on the exact timing and interleaving the scheduler happens to pick, which changes run to run. A race
can pass 10,000 times, then fail once. Failures rarely reproduce on demand — and a passing test only proves *this*
run's interleaving was fine, not that the code is thread-safe.

</details>

### Why does a bug vanish when you add logging?
<details><summary>Show answer</summary>

Logging (or a debugger, or a print) changes timing — it slows a thread just enough that the racing interleaving no
longer lines up. The bug is still there; you've only hidden the window where it happens. (Field name: "heisenbug".)

</details>

### Making a race more likely to surface?
<details><summary>Show answer</summary>

Push the code toward the bad interleaving: many threads, many iterations, run on real multicore hardware, and start
all threads at the same instant so they actually collide. Stress/soak runs beat a single pass.

</details>

### Starting many threads at the same instant?
<details><summary>Show answer</summary>

Gate them so none runs until all are ready — otherwise early threads finish before later ones start and never
contend. Use `CountDownLatch` (one-shot gate) or `CyclicBarrier` (reusable).

```java
CountDownLatch start = new CountDownLatch(1);
// each worker: start.await(); doWork();
start.countDown();  // releases all workers at once
```

</details>

### Why avoid Thread.sleep in concurrency tests?
<details><summary>Show answer</summary>

It guesses at timing: too short and the test is flaky, too long and the suite crawls — and it ties the test to the
scheduler. Wait on a real signal instead — a latch, a barrier, or `Future.get()` — not a sleep-and-hope.

</details>

### Finding a deadlock at runtime?
<details><summary>Show answer</summary>

Take a thread dump (`jstack <pid>`, or Ctrl-Break in the console) and look for threads BLOCKED on locks each other
holds. Programmatically: `ThreadMXBean.findDeadlockedThreads()`. jconsole / VisualVM show it in a GUI.

</details>

### Tool for stress-testing concurrency?
<details><summary>Show answer</summary>

jcstress (Java Concurrency Stress — an OpenJDK harness) hammers tiny code snippets across huge numbers of
interleavings to expose races and memory-ordering bugs. Static analysis (SpotBugs) catches some issues without
running. Enough to name in an interview.

</details>

### Measuring how fast a small piece of code runs?
<details><summary>Show answer</summary>

Don't hand-roll it — use a benchmarking harness such as JMH.

A simple `nanoTime` before/after gives misleading numbers on small code because the JVM reshapes it as it runs:
the JIT hasn't warmed up on the first runs so early timings are slow, dead-code elimination can delete work whose
result you never use, and GC or inlining can land inside your measured window. The result looks precise but isn't
real.

A harness handles this for you — warmup runs, many iterations, and consuming results so the JIT can't optimize
the work away. Reach for one whenever the thing you're timing is short.

</details>

### Measuring how long something took?
<details><summary>Show answer</summary>

Use `System.nanoTime`, not `System.currentTimeMillis`.

`currentTimeMillis` is wall-clock time and can jump mid-measurement — an NTP correction, a manual clock change,
daylight-saving — even backwards, so subtracting two readings can give a wrong or negative duration.

`nanoTime` is a steady counter with no calendar meaning: its absolute value is useless, but the difference between
two readings is a true elapsed time, unaffected by any clock adjustment. It's also finer-grained. Use it for every
interval measurement (wall-clock vs steady counter).

</details>

### Why is testing concurrent code inherently difficult?
<details><summary>Show answer</summary>

Concurrent code is non-deterministic.

Bugs like race conditions, visibility issues, or deadlocks depend heavily on exact thread scheduling and
hardware-level timing. A test might pass 9,999 times and fail once (a "Heisenbug"), making it extremely difficult
to reliably reproduce failures or prove correctness.

</details>

### How do you force threads to execute simultaneously in a unit test?
<details><summary>Show answer</summary>

Use a `CountDownLatch` to create a "starting gun" and a "finish line".

1. **The Starting Gun:** Create a latch initialized to `1`. Have all worker threads call `await()` on it. The main
   thread calls `countDown()` to release them all at the exact same time.
2. **The Finish Line:** Create a second latch initialized to the number of worker threads. Each worker calls
   `countDown()` when done. The main thread calls `await()` on this latch before running any JUnit assertions.

</details>

### Difference between safety testing and liveness testing?
<details><summary>Show answer</summary>

- **Safety testing (Correctness):** Verifies that "nothing bad happens" (e.g., no lost updates, no corrupted
  state). You test this by running high-concurrency workloads and asserting the final data matches the expected
  mathematical result.
- **Liveness testing (Progress):** Verifies that "something good eventually happens" (e.g., no deadlocks or
  infinite loops). You test this by enforcing strict timeouts on your test execution. If the test hangs and times
  out, liveness is broken.

</details>

### What tools are used for testing Java concurrency?
<details><summary>Show answer</summary>

- **Standard API:** `ExecutorService` to blast the system with threads, paired with `CountDownLatch` or
  `CyclicBarrier` for coordination.
- **Awaitility:** A popular library for testing asynchronous code, allowing you to express expectations like "wait
  at most 5 seconds until this condition becomes true."
- **jcstress (Java Concurrency Stress):** A specialized tool created by OpenJDK engineers to test JVM-level
  concurrency and memory-model edge cases. (Usually reserved for writing core library infrastructure, not standard
  business logic).

</details>

### Why shouldn't you rely heavily on unit tests to catch concurrency bugs?
<details><summary>Show answer</summary>

Unit tests run in controlled, isolated, and often low-load environments. Many concurrency bugs only manifest under
heavy, sustained production loads where the OS thread scheduler is under pressure.

Concurrency correctness must be guaranteed by design (e.g., using immutable objects, proper lock ordering, or
`java.util.concurrent` utilities) and verified via stress/load testing, rather than relying on standard unit tests.

</details>
