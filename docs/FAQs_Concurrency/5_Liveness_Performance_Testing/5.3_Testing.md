### Why is concurrent code hard to test?
<details><summary>Show answer</summary>

Bugs depend on the exact timing and interleaving the scheduler happens to pick, which changes run to run. 
A race can pass 10,000 times, then fail once. 
Failures rarely reproduce on demand — and a passing test only proves *this* run's interleaving was fine, 
not that the code is thread-safe.

</details>

### Logging to find a concurrency bug?
<details><summary>Show answer</summary>

Logging (or a debugger, or a print) changes timing — it slows a thread just enough that the racing interleaving no
longer lines up. The bug is still there; you've only hidden the window where it happens. (Field name: "heisenbug".)

</details>

### Making a race more likely to surface?
<details><summary>Show answer</summary>

Push the code toward the bad interleaving: many threads, many iterations, run on real multicore hardware, and start
all threads at the same instant so they actually collide. Stress/soak runs beat a single pass.

</details>

### Starting many threads at the same instant?
<details><summary>Show answer</summary>

Gate them so none runs until all are ready — otherwise early threads finish before later ones start and never contend. 
Use `CountDownLatch` (one-shot gate) or `CyclicBarrier` (reusable).

```java
CountDownLatch start = new CountDownLatch(1);
// each worker: start.await(); doWork();
start.countDown();  // releases all workers at once
```

</details>

### Thread.sleep in concurrency tests?
<details><summary>Show answer</summary>

A sleep guesses how long the other thread needs. 
- Too short: the thread is not done yet, so the test sometimes fails for no real reason (field term: **flaky test**). 
- Too long: every run waits the full time, so the test suite gets slow. 
- The right length also depends on the machine and its load, so a sleep that passes on your laptop can fail on a busy
  build server. 


Wait for a real signal instead — a latch, a barrier, or `Future.get()` — so the test goes on the moment the work is done.


</details>

### Finding a deadlock at runtime?
<details><summary>Show answer</summary>

Take a thread dump (`jstack <pid>`, or Ctrl-Break in the console) and look for threads BLOCKED on locks each other holds. 
Programmatically: `ThreadMXBean.findDeadlockedThreads()`. jconsole / VisualVM show it in a GUI.

</details>

### Tool for stress-testing concurrency?
<details><summary>Show answer</summary>

`jcstress` (Java Concurrency Stress — an OpenJDK harness) hammers tiny code snippets across huge numbers of 
interleavings to expose races and memory-ordering bugs. Static analysis (SpotBugs) catches some issues without running. 

</details>

### Measuring how fast a small piece of code runs?
<details><summary>Show answer</summary>

Use JMH (Java Microbenchmark Harness), not `nanoTime` before and after. 
The JVM changes small code while it runs, so a hand-written timer gives wrong numbers:

- **No warmup** — the first runs happen before the JIT compiles the code, so they are slow.
- **Dead-code elimination** — if the result is never used, the JIT may delete the work, so you time nothing.
- **Noise** — a GC pause or JIT compilation can happen inside the timed window.

JMH runs warmup rounds, repeats the code many times, and passes results to a `Blackhole` so the JIT can't delete the work.

</details>

### Measuring how long something took?
<details><summary>Show answer</summary>

Use `System.nanoTime`, not `System.currentTimeMillis`.

`currentTimeMillis` reads the system clock, and the system clock can jump during a measurement, even backwards (NTP 
sync, someone changing the clock by hand). The difference between two readings can then be wrong or negative.

`nanoTime` is a counter that only moves forward. Its value alone means nothing, but the difference between two
readings is the real elapsed time.

</details>

### Difference between safety testing and liveness testing?
<details><summary>Show answer</summary>

- **Safety — nothing bad happens** (no lost updates, no corrupted state). Run many threads on the shared data, then
  check the result against the value you can compute: e.g. 4 threads × 1000 increments must give 4000.
- **Liveness — something good eventually happens** (no deadlock, livelock, or starvation). Run the test under a
  timeout; if it hangs, liveness is broken. A timeout turns "eventually" into "within N seconds" — no test can check
  "eventually" itself.

</details>

### What tools are used for testing Java concurrency?
<details><summary>Show answer</summary>

- **Standard API:** `ExecutorService` to blast the system with threads, paired with `CountDownLatch` or
  `CyclicBarrier` for coordination.
- **Awaitility:** A popular library for testing asynchronous code, allowing you to express expectations like "wait
  at most 5 seconds until this condition becomes true."
- **jcstress (Java Concurrency Stress):** A specialized tool created by OpenJDK engineers to test JVM-level
  concurrency and memory-model edge cases. (Usually reserved for writing core library infrastructure, not standard
  business logic).

</details>
