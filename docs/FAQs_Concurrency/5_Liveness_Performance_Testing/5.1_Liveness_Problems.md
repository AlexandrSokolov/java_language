### Synchronized block — how to avoid liveness and correctness problems?
<details><summary>Show answer</summary>

Never call code you don't control from inside the block — only code you control. A method you hand off to is
[**alien**](#which-methods-count-as-alien): you don't know what it does while you hold the lock, so
[things can go wrong](#what-can-go-wrong-calling-an-alien-method-from-a-synchronized-block).

</details>

### Which methods count as alien?
<details><summary>Show answer</summary>

Any method you don't control — you can't see what it does while you hold the lock:

- an overridable method (a subclass decides the body),
- a listener or callback you were handed,
- a function passed in as an argument.

The common thread: the code was supplied from outside, so its behavior isn't yours to know.

</details>

### What can go wrong calling an alien method from a synchronized block?
<details><summary>Show answer</summary>

Three ways, all bad:

- **Deadlock (Liveness is broken).** The alien method tries to take a lock you already hold, or takes a second lock in the opposite
  order another thread uses — both sides wait forever.
- **Reentered state (Safety - is broken).** The alien method calls back into your object and sees it mid-update — a half-changed state
  you assumed no one could observe while locked.

</details>

### Alien-method bugs — how to test for them?
<details><summary>Show answer</summary>

You mostly can't — the failure is **nondeterministic**: whether it breaks depends on what the caller's code
happens to do, so it passes in tests and fails in production. There's no test that reliably triggers it — the
guarantee comes from
[not calling alien code inside the lock](#synchronized-block--how-to-avoid-liveness-and-correctness-problems) in
the first place, not from testing it out.

</details>

### How do you call an alien method safely when a lock is needed?
<details><summary>Show answer</summary>

Call it outside the lock. Do the locked work, release the lock, then make the call — an alien call made with no
lock held is an **open call**.

When the alien method needs data the locked part produced (a list to iterate), copy that data under the lock — a
**snapshot** — release the lock, then call the method using the copy. The lock protects the read; the copy lets
the call run free, and the alien method can't corrupt it mid-iterate.

</details>

### What does an open call give you?
<details><summary>Show answer</summary>

- **Liveness** — no deadlocks. The alien method runs without your lock, so it can't clash with other locks being
  acquired elsewhere.
- **Safety** — no reentrancy into a broken state. You finish your updates and restore invariants before
  releasing the lock and making the call.
- **Performance** — no needless waiting. An alien method can take an arbitrarily long time. Calling it outside
  the lock drastically shortens lock hold time, freeing other threads to proceed.

</details>

### When does a reentrant lock fail to protect state?
<details><summary>Show answer</summary>

When you call an [alien method](#which-methods-count-as-alien) from inside the lock *while your state is half-updated*, 
and that method calls back into your object.

Normally the lock keeps others out while you break and restore an invariant. 
But a [reentrant lock](../1_Fundamentals/1.2_Synchronization_Deep_Dive.md#what-happens-when-a-thread-re-takes-its-own-lock)
doesn't stop the *same* thread from re-entering — so the alien callback walks straight back in and sees the
half-updated state the lock was supposed to hide.

```java
synchronized void add(E e) {
  data.add(e);              // invariant temporarily broken here
  notify(e);                // alien call, still under the lock
  rebuild();                // would restore the invariant — too late
}
```

If `notify`'s callback re-enters and reads `data`, it sees the broken middle. Without reentrancy that re-entry
would deadlock — a liveness failure, loud and safe. Reentrancy lets it through instead, so you get corrupted
state — a **safety failure**, silent and worse. The same feature that stops self-deadlock removes the wall that
would have caught this.

</details>

### Liveness failure vs safety failure?
<details><summary>Show answer</summary>

Two different kinds of concurrency failure:

- **Liveness failure** — the program stops making progress. Nothing wrong happens; nothing happens at all.
  Deadlock is the classic case — threads wait on each other forever.
- **Safety failure** — the program makes progress, but does the wrong thing. State gets corrupted; a reader
  sees data it should never have seen.

The trade you never want: 
- a liveness failure is loud and safe — it hangs, you notice, the bad state never escapes. 
- A safety failure is silent and worse — it keeps running on corrupted data. 
  [A reentrant lock can turn the first into the second](#when-does-a-reentrant-lock-fail-to-protect-state).

</details>

### Why can a thread pool hang with work left to do?
<details><summary>Show answer</summary>

Thread starvation deadlock: every thread in a bounded pool is blocked waiting on a task that's still in the queue,
with no free thread to run it — so nothing finishes and nothing starts.

Example: a pool of 3 threads, 3 tasks each blocking until a 4th completes. All 3 threads park waiting; the 4th
never gets a thread; the pool hangs forever.

Nothing throws — the pool just stops making progress: a liveness failure, not an error.

</details>

### How do you avoid thread starvation deadlock?
<details><summary>Show answer</summary>

- Don't have pool tasks block waiting on other tasks submitted to the same pool.
- Size the pool for the peak number of tasks that can be blocked at the same time.
- Or use a pool that can grow threads on demand rather than a fixed one.

</details>

### What is a deadlock?
<details><summary>Show answer</summary>

Two or more threads each holding a lock the other needs, each waiting for the other to release — 
so none of them ever moves again. The program does not crash; the threads just stop, permanently.

The core is a cycle:
- Thread A holds lock X, waiting for Y.
- Thread B holds lock Y, waiting for X.

All [deadlock theory](#what-conditions-are-required-for-a-deadlock) and all fixes simply come down to forming or breaking this cycle.

</details>

### Deadlocked vs blocked thread?
<details><summary>Show answer</summary>

Both sit still, waiting on something. The difference is whether the wait can ever end.

- **Blocked** — waiting for something that *will* arrive: a lock another thread holds and will release, I/O that
  will complete. Progress resumes on its own.
- **Deadlocked** — waiting for something that never can, because the thread that would release it is itself
  waiting on you. No outside event ends it.

Handle: a blocked thread is stuck for now; a deadlocked thread is stuck forever — the cycle means nothing will
ever free it.

</details>

### Give an example of a deadlock?
<details><summary>Show answer</summary>

Two threads transferring between the same two accounts in opposite directions:

```java
public synchronized void transfer(Account target, int amount) {
  this.balance -= amount;    // holds THIS account's lock (method is synchronized)
  target.deposit(amount);    // deposit is synchronized too — needs TARGET's lock, while holding THIS
}
```

- Thread 1: `a.transfer(b)` → holds a, wants b.
- Thread 2: `b.transfer(a)` → holds b, wants a.

Each waits on the lock the other holds; neither releases — both stop forever.

The trigger: taking a second lock while holding the first, in opposite order across threads.

</details>

### What conditions are required for a deadlock?
<details><summary>Show answer</summary>

There are four conditions, and they must all be true at the same time. 

- **Mutual exclusion** — one thread holds a lock at a time; others wait.
- **Hold and wait** — a thread holds one lock while asking for another.
- **No preemption** — a lock can't be taken away; only its holder releases it.
- **Circular wait** — a cycle of threads, each waiting for the lock the next holds.

</details>

### How to prevent a deadlock?
<details><summary>Show answer</summary>

A deadlock needs all four conditions at once, so each fix kills one:

- **Order the locks** — always acquire multiple locks in the same global order across all threads.
  Breaks *circular wait*: [lock ordering](#fix-lock-ordering).
- **Use timeouts (`tryLock`)** — if a thread can't get the second lock, it releases the first and retries instead
  of blocking forever. Breaks *hold-and-wait / no preemption*: [tryLock with timeout](#fix-trylock-with-timeout).
- **Never hold two locks at once** — Breaks *hold-and-wait*. Remove the nested locks entirely, via:
  - [open calls](#fix-open-calls), 
  - [one coarse lock](#fix-one-coarse-lock), or
  - [lock-free atomics](#fix-lock-free-with-atomics). 

Trigger: break the cycle one of three ways — order the locks (kills circular wait), time out the wait (kills
hold-and-wait), or never hold two at once (kills hold-and-wait).

</details>

### Fix: lock ordering?
<details><summary>Show answer</summary>

Every thread acquires locks in the same global order. If both threads always take a's lock before b's, the cycle
cannot form — the second thread is simply blocked at the *first* lock until the first thread finishes.

```java
// pick a fixed order by some stable key (e.g. account id)
FSOAccount first  = a.id() < b.id() ? a : b;
FSOAccount second = a.id() < b.id() ? b : a;
synchronized (first) {
  synchronized (second) {
    // transfer
  }
}
```

Breaks **circular wait**: with one global order there is no A-holds-a-wants-b vs B-holds-b-wants-a — both want a first.

Handle: same lock order everywhere = no cycle. The primary, most-asked fix.

</details>

### Fix: tryLock with timeout?
<details><summary>Show answer</summary>

Use `ReentrantLock.tryLock` instead of blocking forever. If the second lock doesn't come in time, release the
first and retry — so no thread sits holding one lock waiting endlessly for another.

```java
while (true) {
  if (fromLock.tryLock(1, SECONDS)) {
    try {
      if (toLock.tryLock(1, SECONDS)) {
        try { /* transfer */ break; }
        finally { toLock.unlock(); }
      }
      // got from, not to → fall through, release from, loop
    } finally { fromLock.unlock(); }
  }
  // couldn't get both this round → back off and retry
}
```

Breaks **hold-and-wait / no preemption**: the waiting thread gives up and releases what it holds instead of 
waiting forever, so the cycle dissolves.

Handle: can't get the second lock in time → let go of the first and retry. Use when a global lock order isn't practical.

</details>

### When does tryLock still fail to progress?
<details><summary>Show answer</summary>

**Livelock** — a liveness failure where threads are actively running but make no progress, because they keep
changing state in response to each other. Analogy: two polite people in a hallway stepping side to side to let
each other pass, perfectly in sync, forever.

Classic cause: the [tryLock-and-retry fix](#fix-trylock-with-timeout) with no back-off — both threads grab the
first lock, both fail the second, both release and retry in lockstep, forever.

```java
while (!getBothLocks()) {
  releaseAny();     // be polite, let the other go first
  // no delay → both retry together → same collision next round
}
```

Vs. deadlock: deadlocked threads are blocked (frozen); livelocked threads run flat out (burning CPU) but caught
in an endless retry loop. Fix: add randomness (jitter) to the retry timing so they break their sync.

</details>

### Fix: open calls?
<details><summary>Show answer</summary>

Don't call another object's method while holding your lock. Do the locked work, release, *then* make the outward call. 
With no lock held during the call, no second lock is ever requested while holding the first.

```java
public boolean transferTo(FSOAccount other, int amount) {
  synchronized (this) {
    if (balance < amount) return false;
    balance -= amount;
  }                         // lock released here
  other.deposit(amount);    // open call: no lock held while calling out
  return true;
}
```

Breaks **hold-and-wait**: `other`'s lock is taken only after `this` is released, so two locks are never held at once. 
(Note: the money briefly leaves one account before landing — fine here, 
but the window must be acceptable for your invariant.)

Handle: never call out while holding a lock — release first, then call.

</details>

### Fix: one coarse lock?
<details><summary>Show answer</summary>

Guard both accounts (or the whole subsystem) with a single shared lock. With only one lock, a thread can never
hold one while waiting for another — there is no second lock to wait for.

```java
private static final Object BANK = new Object();
public boolean transferTo(FSOAccount other, int amount) {
  synchronized (BANK) {      // one lock for all transfers
    // transfer
  }
}
```

Breaks **hold-and-wait**: only one lock exists, so hold-and-wait is impossible.

Handle: one lock = no deadlock, but everything serializes through it. Simplest fix, real concurrency cost.

</details>

### Fix: lock-free with atomics?
<details><summary>Show answer</summary>

Drop locks entirely for the shared field. An atomic type updates in one hardware step with `compareAndSet`, 
so no lock is held across anything and there is nothing to deadlock on.

```java
private final AtomicLong balance;   // minor units, not double
// withdraw: loop compareAndSet(old, old - amount) until it succeeds or funds run out
```

Breaks **mutual exclusion**: the update needs no held lock at all, so none of the deadlock conditions can arise.

Handle: no lock held → no deadlock possible. Works for single-field updates; a two-account transfer needs more
(a lock-free transfer is hard — this is the limit of the technique).

</details>

### How does a deadlock break the fully synchronized object rules?
<details><summary>Show answer</summary>

It violates the **bounded-time** rule: every method must finish in bounded time. A synchronized method that
calls out while holding its lock can block forever waiting on a lock another thread holds. Once a method can
block with no bound, it has no bounded running time — and the object's "safe and live" guarantee is gone.

Handle: a deadlock breaks the bounded-time rule — a method holds a lock and makes a call that may never return.

</details>
