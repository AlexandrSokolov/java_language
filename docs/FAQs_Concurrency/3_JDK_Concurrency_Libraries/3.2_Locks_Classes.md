### How do you choose a thread waiting mechanism based on intent?
<details><summary>Show answer</summary>

Threads wait for different reasons. Choose the tool based on the intent of the wait:

- **[Data Protection (Locks)](#what-is-the-primary-purpose-of-a-lock):** "Get out of my way."**
  The wait is a forced side-effect of mutual exclusion. 
  The thread just wants to safely read/write data, but the door is currently locked.
- **[Data Handoff (Blocking Queues)](#...):** "Here is the work / I need work."**
  The wait happens because a producer is safely passing data to a consumer. A thread waits either because the queue
  is full (nowhere to put data) or empty (nothing to take) (e.g., `ArrayBlockingQueue`).
- **[Workflow Coordination (Synchronizers)](3.3_Synchronizers.md#what-is-a-synchronizer):** "Let's move together."**
  The wait is the architectural goal. 
  The workflow specifically requires threads to meet at a checkpoint, wait for a count, or limit concurrency.
- **[Custom Signaling (Wait/Notify & Conditions)](#how-to-wait-without-spinning):** "Wake me when X is true."**
  The low-level fallback. Used only when pre-built synchronizers don't fit. 
  You must manually write the wait loops and signal management yourself.

</details>

### What is the primary purpose of a lock?
<details><summary>Show answer</summary>

The primary purpose is **Mutual Exclusion** — forcing threads to take turns.

When multiple threads access shared, mutable state, a lock provides three guarantees:

- **Mutual Exclusion (The How):** Only one thread can enter the critical section at a time. 
  This prevents race conditions and corrupted data.
- **Atomicity:** It turns multiple operations into a single, indivisible step.
- **Visibility:** It acts as a memory barrier. Releasing a lock flushes all changes to main memory,
  ensuring the next thread sees the freshest data, not a stale CPU cache.

</details>

### What are the limits of `synchronized`?
<details><summary>Show answer</summary>

- **One lock type only.** Can't split readers from writers, so many threads that only read still block each other
  even though nothing they do conflicts. A reader/writer lock would let them run together.
- It applies equally to **all synchronized operations** on the locked object.
- **The lock is welded to the block.** Acquire and release must sit in the same method; you can't take the lock in
  one method and drop it in another.
- **Get the lock or block forever.** No way to say "try, and if it's taken, do something else instead" — that's
  `tryLock()`.
- **The wait has no time limit.** Can't say "wait for the lock, but give up after N seconds."

</details>

### What replaces `synchronized` for more control?
<details><summary>Show answer</summary>

The `Lock` interface in `java.util.concurrent.locks`. It ships with two implementations:

- [`ReentrantLock`](#what-is-reentrantlock) — the same lock you get from a `synchronized` block, 
  but more flexible (unbind from the block, `tryLock()`, timed wait).
- [`ReentrantReadWriteLock`](#what-is-reentrantreadwritelock) — better performance when there are many readers but
  few writers, since readers no longer block each other.

</details>

### What is `ReentrantLock`?
<details><summary>Show answer</summary>

The plain explicit lock — the same behavior as a `synchronized` block, but as an object you control. 
"Reentrant" means a thread that already holds the lock can take it again without blocking itself 
(same as `synchronized`).

Why it exists — lifts the limits of `synchronized`:
- unbind acquire from release across methods
- try for the lock without blocking (`tryLock()`)
- wait for the lock with a timeout

</details>

### What is `ReentrantReadWriteLock`?
<details><summary>Show answer</summary>

A lock split into two: 
a read lock many threads can hold at once, and a write lock only one thread holds and which excludes all readers.

Why it exists:
- when reads greatly outnumber writes, plain locking makes readers block each other for no reason
- readers run together, so they no longer block each other
- writers still get exclusive access

</details>

### What can go wrong with `ReentrantReadWriteLock`?
<details><summary>Show answer</summary>

Two traps, split by who pays:

- **Writers pay: [writer starvation](#reentrantreadwritelock-under-constant-reads--trap).** The write lock needs the
  read count at zero. With overlapping reads the count never gets there, so a writer can wait a very long time, even
  forever.
- **Readers pay: [fighting over the lock counter](#why-dont-reads-scale-on-reentrantreadwritelock).** Every read lock
  and unlock writes the same shared count. Even with no writer at all, short reads on many cores don't scale.

Both come from one shared read count: writers need it at zero, and every reader writes to it.

</details>

### `ReentrantReadWriteLock` under constant reads — trap?
<details><summary>Show answer</summary>

**Writer starvation**: a writer waits a very long time, possibly forever, while readers keep the lock busy.

How: the write lock needs the read count at zero. With overlapping reads, a new reader gets in before the last one
leaves, so the count never hits zero and the writer never gets its turn.

In the default (non-fair) mode the spec allows this. The JDK lowers the risk because a new reader waits if a writer
is first in the queue. That is a best-effort check, not a guarantee.

Fix: fair mode.

```java
ReadWriteLock lock = new ReentrantReadWriteLock(true); // fair
```

Threads get the lock in roughly arrival order. Once a writer is waiting, new readers queue behind it. Cost: lower
throughput than the default.

A lock that lets many in at once must, at some point, stop letting new ones in. Otherwise the one who needs it alone
never gets a turn.

</details>

### Why don't reads scale on `ReentrantReadWriteLock`?
<details><summary>Show answer</summary>

**Readers fight over the lock's own counter.** Every read lock and unlock does a compare-and-set on the same shared
lock state. Readers never block each other, but on many cores that one memory spot keeps moving between CPU caches.
With short reads, the lock can cost more than the read itself, so adding readers adds little speed.

Fix: `StampedLock` (Java 8) with an optimistic read. Take a stamp (a `long` version number), read without locking,
then check that no write happened in between.

```java
long stamp = lock.tryOptimisticRead();  // no lock taken, nothing written
double x = this.x, y = this.y;          // copy into locals
if (!lock.validate(stamp)) {            // did a write get in?
  stamp = lock.readLock();              // fall back to a real read lock
  try {
    x = this.x;
    y = this.y;
  } finally {
    lock.unlockRead(stamp);
  }
}
return Math.hypot(x, y);                // use values only after validate
```

Values read before `validate` can be half-updated, so don't act on them until the check passes. This only pays off
when writes are rare. If the check keeps failing, every read ends up taking the lock anyway.

A read lock still writes, to the lock itself. The fix is to read without touching the lock, then check that nothing
changed.

</details>

### Same thread locks twice: `StampedLock` vs `ReentrantLock`?
<details><summary>Show answer</summary>

`ReentrantLock` remembers which thread holds it and counts the holds. When the same thread locks again, it gets in at
once and the count goes up by one. It must unlock once per lock.

`StampedLock` remembers no owner. When the thread that holds the write lock asks for it again, the lock sees just
another thread and makes it wait for the holder, which is itself. It blocks forever.

Read locks aren't safe either. A second read lock from the same thread usually gets in. But if a writer is already
waiting, the second read queues behind that writer, and the writer waits for the first read. That deadlock shows up
only under load.

In practice, keep `StampedLock` sections short and don't call methods that might lock again. Pass them the stamp
instead.

Locking again only works if the lock records who holds it. `StampedLock` records no one, so the same thread asking
again is just one more thread waiting.

</details>

### `ReentrantReadWriteLock`: switching read and write — trap?
<details><summary>Show answer</summary>

question from Gemini:
In ReentrantReadWriteLock, can you upgrade a Read Lock to a Write Lock, or downgrade a Write Lock to a Read Lock?
You cannot upgrade a Read Lock to a Write Lock. If a thread holding a Read Lock attempts to acquire a Write
Lock, it will deadlock. However, you can downgrade a Write Lock to a Read Lock. You do this by acquiring the
Write Lock, modifying data, acquiring the Read Lock, and then releasing the Write Lock. This keeps the data locked
for reading while safely giving up exclusive write access.

**Upgrade deadlock.** A thread that holds the read lock asks for the write lock. The write lock waits for the read
count to reach zero, but the thread's own read hold is part of that count. So the thread waits for itself, forever.

Fix: release the read lock first, then take the write lock, then check the state again. Another thread may have
written in the gap.

The other direction is safe. To **downgrade**, take the read lock while you still hold the write lock, then release
the write lock. You keep reading the data you just wrote, other readers can join, and no writer gets in between.

```java
lock.readLock().lock();
if (!valid) {
  lock.readLock().unlock();     // release first: no upgrade
  lock.writeLock().lock();
  try {
    if (!valid) {               // check again: someone may have written in the gap
      data = load();
      valid = true;
    }
    lock.readLock().lock();     // downgrade: take read before releasing write
  } finally {
    lock.writeLock().unlock();
  }
}
try {
  use(data);
} finally {
  lock.readLock().unlock();
}
```

A thread can step down from writer to reader, but never up. Stepping up means waiting for all readers to leave, and
the thread is one of them.

</details>

### How does `ReentrantLock` support fairness?
<details><summary>Show answer</summary>

`new ReentrantLock(true)` gives a fair lock. The default `new ReentrantLock()` is unfair.

A fair lock checks the wait queue before taking the lock. If any thread is already waiting, a newcomer joins the end
of the queue, even when the lock is free right now. An unfair lock lets the newcomer grab a free lock at once and jump
the queue. That queue-jumping is called **barging**.

What fair mode buys: no thread waits forever, and wait times are more even.

What it costs: when many threads compete, it is often much slower. When the holder releases, the next queued thread
is asleep and must be woken up, which takes time. An unfair lock lets a thread that is already running take the lock
in that gap and get work done. A fair lock makes the running thread queue and sleep too, and the lock sits idle until
the sleeping thread wakes up. You get more context switches and less work done.

Fair means "the longest waiter goes first", not strict FIFO for every call. The untimed `tryLock()` ignores fairness
and takes a free lock even when other threads are waiting.

Fairness costs speed because it won't give a free lock to a thread that is already running. It waits for a sleeping
thread to wake up instead.

</details>

### Multiple locks — the safe pattern?
<details><summary>Show answer</summary>

Danger: two threads each hold one lock and wait for the other → deadlock. 
Happens when threads take the locks in different orders.

Rule: every thread acquires the locks in the **same global order**, so the wait cycle can't form.

You get that order by **sorting the locks by a fixed key before touching either**, 
so every thread picks the same first lock regardless of which lock it started from.

```java
void lockBoth(Resource a, Resource b) {
  Lock first  = a.id < b.id ? a.lock : b.lock;   // sort by a fixed key
  Lock second = a.id < b.id ? b.lock : a.lock;

  first.lock();
  try {
    second.lock();
    try {
      // ... work needing both ...
    } finally {
      second.unlock();
    }
  } finally {
    first.unlock();
  }
}
```

Why `a.id < b.id`: it decides first/second from a fact about the resources, not from argument order. 
One thread may call `lockBoth(x, y)` while another calls `lockBoth(y, x)` — same pair, opposite argument order. 
If each locked in argument order, one would take `x` then `y` and the other `y` then `x` — the deadlock. 
Comparing ids drops "which was passed first" and uses a shared rule instead: 
the lower id is always locked first, so both calls agree no matter how the arguments came in. 
Any total order works — only that it's computed from the resources.

</details>
