### What is an atomic class?
<details><summary>Show answer</summary>

A class that gives thread-safe mutable access to a single variable — many threads can read and update it safely
with no lock of your own. 


Four types, one per variable kind: 
- `AtomicBoolean`, 
- `AtomicInteger`, 
- `AtomicLong`, and
- `AtomicReference`

</details>

### Atomic classes vs volatile?
<details><summary>Show answer</summary>

`volatile`'s main job is **visibility** — a write is published to other threads, a read gets the latest value.
It also gives **single-access atomicity** for `long`/`double`: because of their 64-bit size a plain write can tear
into two halves, and `volatile` makes the single read or write whole.

What it cannot do is make a **read-modify-write** atomic: `volatile int i; i++;` is still broken, because `i++` is
three steps — read `i`, add 1, write it back — and two threads can both read the same value before either writes,
so one update is lost. `volatile` publishes each step; it doesn't make the three indivisible.

Atomic classes extend atomicity to exactly that — a general read-modify-write done as one atomic step, no lock:

```java
private static final AtomicInteger nextId = new AtomicInteger(1);
int id = nextId.getAndIncrement();   // read, +1, write — atomic; two threads never get the same id
```

With a plain `volatile int` and `nextId++`, two threads could read the same number and collide.

Handle: `volatile` gives visibility (plus whole `long`/`double` access); an atomic class extends atomicity to
compound read-modify-write — reach for it when the new value depends on the old.

</details>

### What lock do atomic classes use?
<details><summary>Show answer</summary>

None — they take no lock at all. That's the point: atomic classes are **lock-free** (nonblocking). 
No thread ever waits its turn, because there's no lock to wait for.

Instead of locking, they lean on a hardware instruction — 
[compare-and-swap(CAS)](#what-is-compare-and-swap-cas) — that performs the read-modify-write atomically at the CPU level. 
The worst that happens under contention is a thread retries, never blocks.

Memory behavior is the same as `volatile` (writes published, reads fresh), with the atomic operations added on top. 
So you get visibility *and* atomic compound updates, without a thread ever being parked.

Handle: no lock — atomic classes are lock-free, backed by a CPU-level compare-and-swap; 
contention costs a retry, not a wait.

</details>

### What is compare-and-swap (CAS)?
<details><summary>Show answer</summary>

An operation that updates a value only if no one else changed it first. Three steps:

1. Read the current value (call it the *expected* value).
2. Compute the new value from it.
3. Atomically: write the new value **only if** the location still holds the expected value. If it still matches,
   the write happens and CAS succeeds. If someone changed it in between, the write is skipped and CAS fails.

On failure you re-read the now-current value and try again — the **retry loop**. That loop is how a lock-free
update makes progress without ever blocking: keep trying until your CAS lands.

```java
// how incrementAndGet works underneath
int prev, next;
do {
  prev = value.get();        // read expected
  next = prev + 1;           // compute new
} while (!value.compareAndSet(prev, next));  // swap only if unchanged; retry if not
```

If another thread increments between the read and the swap, `compareAndSet` fails, the loop re-reads the new
value, and tries again — so no update is ever lost.

The atomicity of that compare-and-write step comes from the hardware, not a lock — 
[how CAS is atomic at the CPU level](#how-is-cas-atomic-without-a-lock).

Handle: CAS = write only if the value is still what I read, else retry — the lock-free building block under every
atomic class.

</details>

### How is CAS atomic without a lock?
<details><summary>Show answer</summary>

The compare-and-write is a single CPU instruction — `CMPXCHG` on x86/x64 (with a `LOCK` prefix). 
The whole compare-then-write happens as one uninterruptible machine operation, 
not several steps the JVM stitches together.
So there's no window between "check the value" and "write it" for another thread to slip into — 
the hardware never splits the two.


To stop another core changing the value during that instant, the CPU takes exclusive hold of the **cache line**
(the small block of memory a core caches at once) that holds the value. Older CPUs locked the whole memory bus;
modern ones lock just the one cache line, using the cores' cache-coherence protocol 
(**MESI** — the scheme that keeps each core's cached copy in sync). Other cores must drop and reload that line.


None of this touches the operating system — no kernel call, no mutex, no thread parked. That's the exact sense in
which CAS is "lock-free": there's no *OS/software* lock, even though the hardware briefly locks a cache line to do
the swap.

Handle: CAS is one CPU instruction that locks the cache line, not the OS — "lock-free" means no software lock, not
no locking at all.

</details>

### When does CAS perform badly?
<details><summary>Show answer</summary>

Under high write **contention** — many threads updating the *same* variable at once 
(contention = threads fighting over one memory location). 
CAS is cheap when writes are rare or spread out: a losing CAS is uncommon, so retries are few. 
Pile many threads onto one variable and it collapses:

- one thread wins each CAS, every other thread's CAS fails,
- the losers immediately re-read and retry — **spinning** (looping and retrying with no useful work done),
- so most threads burn CPU on empty attempts while almost nothing gets counted. CPU near 100%, throughput near zero.

This is worse than a lock under the same load. A lock's losers **park** — they stop using CPU while they wait.
CAS's losers stay hot, spinning. So under heavy contention a plain `synchronized` can actually beat an atomic.

The fix for a hot counter is `LongAdder` (Java 8+). Instead of one variable everyone fights over, it holds an 
internal array of cells; different threads update different cells, so they rarely collide on a CAS. 
`sum()` adds the cells when you need the total.

```java
LongAdder hits = new LongAdder();
hits.increment();   // threads spread across cells — little contention
long total = hits.sum();
```

Trade-off: much faster writes under contention, but `sum()` is a bit more work and only approximate if reads race
with writes — fine for counters and metrics, not for a value you read-and-decide-on each time.

Handle: CAS is great under low contention and spins the CPU under high write contention — for a hot counter use
`LongAdder`, which shards the count across cells so threads stop fighting over one variable.

</details>

### How can CAS miss a change?
<details><summary>Show answer</summary>

CAS checks the *value*, not whether it changed and changed back. If a location holds A and another thread does
A → B → A, your CAS sees "still A" and succeeds — blind to the intermediate B. This blind spot is the **ABA
problem**.

For a plain counter it's harmless: an `int` back at 5 *is* 5, nothing was lost. It bites for **references**, where
the same pointer doesn't mean the same state. The classic case is a lock-free stack:

- you read `top` → node A, and plan to pop it by CAS-ing `top` from A to A.next;
- meanwhile another thread pops A, pops more, then pushes A back on top — `top` is A again, but the stack beneath
  it is different;
- your CAS on `top == A` succeeds, and you corrupt the structure — you set `top` to a stale `A.next` that no
  longer belongs there.

So the value matched, but the world moved. That's why ABA is a reference problem in lock-free structures, not an
`AtomicInteger` one — [fixing it means versioning the reference](#how-do-you-fix-the-aba-problem).

Handle: CAS compares the value, not its history — A → B → A looks unchanged, harmless for a counter, corrupting for
a reference in a lock-free structure.

</details>

### How do you fix the ABA problem?
<details><summary>Show answer</summary>

Attach a version to the reference so A-then-A no longer looks the same. CAS then matches *both* the reference and
the version, so an A that was changed and restored fails the check. Two JDK classes do this:

- **`AtomicStampedReference`** — pairs the reference with an integer **stamp**. You bump the stamp on every change,
  so A-with-stamp-1 and A-with-stamp-3 are different to CAS even though the reference is the same. Use it when you
  need to know a change happened (a version count).
- **`AtomicMarkableReference`** — pairs the reference with a boolean **mark**. Use it when you only need "was this
  changed at all?" rather than how many times — e.g. marking a node logically deleted in a lock-free structure.

```java
AtomicStampedReference<Node> top = new AtomicStampedReference<>(a, 0);
int[] stampHolder = new int[1];
Node cur = top.get(stampHolder);            // read reference AND stamp
int stamp = stampHolder[0];
// ... compute newTop ...
top.compareAndSet(cur, newTop, stamp, stamp + 1);  // succeeds only if BOTH still match
```

The idea in one line: CAS the (reference, version) pair, not the bare reference — an A → B → A cycle changes the
version, so the stale CAS fails instead of silently succeeding.

Handle: version the reference — `AtomicStampedReference` (int stamp) or `AtomicMarkableReference` (boolean mark) —
so CAS matches reference *and* version, and A → B → A no longer looks unchanged.

</details>

### Is an AtomicInteger an Integer?
<details><summary>Show answer</summary>

No. The atomic classes don't inherit from the boxed types — `AtomicInteger` is not an `Integer`, `AtomicBoolean`
is not a `Boolean`, so you can't pass one where the boxed type is expected. `AtomicInteger` *does* extend `Number`
(so `intValue()`, `longValue()`, etc. work), but it's not interchangeable with `Integer`.

Handle: an atomic class wraps a value, it doesn't subclass the boxed type — `AtomicInteger` extends `Number`, but
it is not an `Integer`.

</details>

### What is AtomicReference for?
<details><summary>Show answer</summary>

It's `AtomicInteger` for objects: atomic compound updates on a *reference*, lock-free. The same read-modify-write
family, but the value is a whole object —

- `compareAndSet(expected, new)` — swap to `new` only if the reference still points at `expected`,
- `getAndSet(new)` — replace and return the old,
- `updateAndGet(fn)` / `getAndUpdate(fn)` — apply `fn` to the current object and swap in the result, retrying on
  contention (the CAS loop, done for you).

The motivating use is swapping an **immutable object as one unit**. Several fields that must change together and
stay consistent get bundled into one immutable object held behind the reference. To "change" state, build a new
object from the current one and swap it in; if another thread raced you, the CAS fails and you retry with their
version. No lock, and no thread ever sees a half-updated multi-field state — the whole-object swap is atomic.

```java
record State(int x, int y) {}                          // fields that must stay consistent
AtomicReference<State> ref = new AtomicReference<>(new State(0, 0));
ref.updateAndGet(s -> new State(s.x() + 1, s.y() - 1)); // atomic, lock-free, both fields together
```

That's what `volatile` and `AtomicInteger` can't give: a lock-free atomic update across several fields, by making
them one immutable object and swapping the reference. If the value can cycle back to an earlier reference and that
matters, [CAS can miss it](#how-can-cas-miss-a-change).

Handle: `AtomicReference` = atomic lock-free swap of an object reference — bundle multi-field state into one
immutable object and CAS the whole thing in.

</details>
