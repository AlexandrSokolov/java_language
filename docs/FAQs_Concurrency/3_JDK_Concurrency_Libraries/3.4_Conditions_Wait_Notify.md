### How to wait without spinning?
<details><summary>Show answer</summary>

When a thread must wait for a specific state change (e.g. `!ready`), the naive approach is a busy loop:

```java
while (!ready) { }   // burns a whole CPU doing nothing
doWork();
```

The solution is "sleep until signaled." The thread safely parks itself at no CPU cost, and another thread wakes
it up when the condition flips.

The tools (lowest level):

- [`Condition`](#what-is-a-condition) (modern): used with an explicit `ReentrantLock`.
  Gives fine-grained control (multiple conditions per lock, timed waits). Always the preferred choice for custom logic.
- [`wait`/`notify`](#waitnotify--the-legacy-idiom) (legacy):
  used with intrinsic `synchronized` blocks. Prone to missed signals and deadlocks.
  Learn it to read old code, but avoid it in new code.

**The golden rule:** only build custom sleep/signal loops if a higher-level tool cannot do the job.
- first check whether a [synchronizer](3.3_Synchronizers.md#which-synchronizers-exist) (like `CountDownLatch`) or
- a blocking collection (like `BlockingQueue`) can handle the waiting for you.

</details>


### What is a `Condition`?
<details><summary>Show answer</summary>

The `Lock`-API replacement for `wait()`/`notify()`: a thread waits for some condition to become true and is woken
when another thread signals it. Created by calling `newCondition()` on a `Lock`.

Unlike the intrinsic version — where each object has a single built-in wait-set — a `Lock` can create as many
`Condition` objects as you want, so threads can wait on different conditions separately.

</details>

### `Condition` vs `wait()`/`notify()` — the gain?
<details><summary>Show answer</summary>

Intrinsic locking gives each object **one** wait-set — all waiting threads share it, so a signal may wake threads
waiting on a different condition, and they must recheck and sleep again.

A `Lock` can create **many** `Condition` objects, so threads waiting on different conditions wait separately and a
signal wakes only the right group.

</details>

### wait/notify — the legacy idiom?
<details><summary>Show answer</summary>

Two sides, both under a `synchronized` block on the same object:

**Waiter** — loop on the condition, `wait` inside the loop:

```java
synchronized (obj) {
  while (conditionDoesNotHold())
    obj.wait();          // releases the lock, reacquires it on wakeup
  // condition holds — do the work
}
```

**Notifier** — change the state, then signal, still holding the lock:

```java
synchronized (obj) {
  changeStateSoConditionHolds();
  obj.notifyAll();       // wake waiters so they recheck
}
```

`wait` must hold the object's lock (it releases it while waiting, retakes it on wakeup). Never call it outside a
loop — a woken thread must recheck the condition before proceeding. The notifier must change the state *before*
notifying, or a woken waiter rechecks, still finds it false, and waits again.

</details>

### Why call wait in a loop, not an if?
<details><summary>Show answer</summary>

The loop rechecks the condition before and after waiting; one axis, two failures it prevents:

- Test *before* waiting: if the condition already holds and the `notify` already fired, skipping the wait avoids
  waiting for a signal that will never come again — the thread would hang forever (liveness).
- Test *after* waking: a thread can wake with the condition still false; looping back to wait again stops it from
  acting on a state that doesn't hold and wrecking the invariant the lock guards (safety).
- Prevents [spurious wakeup](#spurious-wakeup)

An `if` does neither recheck, so it fails both ways.

</details>

### Why isn't wait/notify idiom a deadlock?
<details><summary>Show answer</summary>

The **wait/notify idiom** is the standard pairing: waiters loop-and-`wait` inside `synchronized`, the notifier
changes state and `notifyAll`s inside `synchronized` on the same lock. It looks like a deadlock — the waiter holds
the lock, and the notifier needs that same lock to change the state and signal. If a sleeping waiter kept the lock,
the notifier could never get in, and the waiter would sleep forever waiting for a signal that can't fire.

`wait()` breaks the trap: it **drops the lock** as it puts the thread to sleep, and **retakes it on wakeup**. 
The sequence, with waiters A and B and notifier C:

1. A takes the lock, checks the condition — false, calls `wait()`, drops the lock, sleeps.
2. B takes the now-free lock, condition false, `wait()`, drops the lock, sleeps.
3. C takes the free lock, changes the state so the condition holds, calls `notifyAll()`.
4. `notifyAll()` wakes A and B — but neither can return from `wait()` yet, because returning needs the lock, and C
   still holds it.
5. C exits its block, drops the lock.
6. A and B compete for it. A wins, returns from `wait()` (it now holds the lock), rechecks the condition — true —
   does the work, exits, drops the lock.
7. B gets the lock, returns from `wait()`, rechecks, does the work.

Handle: a sleeping waiter holds nothing — `wait()` gives up the lock on the way to sleep, so wait/notify is a
hand-off, not a hold.

</details>

### Why might a thread wake when its condition is false?
<details><summary>Show answer</summary>

A wakeup does not promise the condition holds. Four reasons it may not:

- Another thread grabbed the lock and changed the guarded state between the `notify` and this thread waking.
- Another thread called `notify` when the condition didn't hold — by accident or malice. Waiting on a publicly
  reachable object exposes you to this: any code can notify it.
- The notifier was over-generous — called `notifyAll` when only some waiters actually had their condition met.
- [A spurious wakeup](#spurious-wakeup): the thread woke with no `notify` at all (rare, but real at the OS level).

This is exactly why `wait` lives in a `while` loop — the recheck absorbs every one of these.

</details>

### notify vs notifyAll?
<details><summary>Show answer</summary>

- `notifyAll` wakes every waiting thread; `notify` wakes one.
- Default to `notifyAll` — it's safe.
  Extra threads wake, recheck their condition, find it false, and go back to waiting, so correctness holds.
- `notify` looks like a free optimization when every waiter is on the same object waiting for the same state —
  wake one, it proceeds, why wake all?
  But that reasoning is a trap, because a single `notify` can be delivered to the wrong waiter and lost:
    - One object often carries more than one condition. A bounded buffer has producers waiting for "not full" and
      consumers waiting for "not empty" on the same object. After a `take`, a single `notify` meant for a producer
      can wake another consumer instead — it rechecks "not empty", finds it false, sleeps again, and the producer
      that should have woken never does. The signal is consumed, not passed on, so the right thread hangs forever.
    - Even with one condition, if a single state change lets several waiters proceed, `notify` wakes one and leaves
      the rest asleep though they could run.
- So `notify` is valid only when *both* hold: every waiter waits on the same condition, **and** one signal lets
  exactly one thread proceed. Prove both before using it — and even then `notifyAll` is often kept for safety,
  since a later change (a second condition added to the same lock) silently breaks `notify` with no error, just a
  stall under load.

</details>

### Spurious wakeup?
<details><summary>Show answer</summary>

A waiting thread waking without any `notify`/`notifyAll` call. Rare, but permitted by the platform (an OS-level
reality). It's one of the reasons `wait` must always run in a `while` loop that rechecks the condition — the code
must never assume a wakeup means the condition is now true.

</details>
