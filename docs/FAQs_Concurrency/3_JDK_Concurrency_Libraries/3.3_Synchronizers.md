### What is a synchronizer?
<details><summary>Show answer</summary>

An object that makes threads **wait for one another** so they can coordinate their work. Unlike a lock, where the
wait is a forced side effect, here the wait is the whole point.

Threads arrive and ask to proceed, and the synchronizer's internal state — a count, available permits, a meeting
point — dictates whether the thread is released or forced to wait. Threads are released by the state, not by who
arrived first.

</details>

### Which synchronizers exist?
<details><summary>Show answer</summary>

- **Wait for a count to hit zero — one-shot gate** — [CountDownLatch](#countdownlatch--purpose): 
  wait until N events finish. Never resets.
- **Wait for a free permit — resource limiter** — [Semaphore](#semaphore--purpose): 
  cap how many threads run a section at once.
- **Wait for everyone to arrive — reusable meeting point** — [CyclicBarrier](#cyclicbarrier--purpose): 
  fixed parties meet each round, reusable.
- **Wait for one partner, then swap — two-party swap** — [Exchanger](#exchanger--purpose): 
  a strict meeting point for exactly two threads to hand data back and forth.
- **Dynamic multi-phase — the flexible one** — [Phaser](#phaser--purpose): a reusable barrier where the party
  count can change at runtime across numbered phases.

Trigger: count-to-zero, free permit, everyone-arrives, swap-with-one, flexible-barrier (phaser).

</details>

### CountDownLatch — purpose?
<details><summary>Show answer</summary>

A one-shot gate. Built with a count N; threads call `await` and block until the count reaches zero. Other threads
call `countDown` to decrement it. Once it hits zero it stays open — it never resets.

Use: let one or more threads wait until N events have finished, once. "Don't start until all N workers are ready."

</details>

### Semaphore — purpose?
<details><summary>Show answer</summary>

Hands out a fixed number of permits. A thread calls `acquire` to take one (waiting if none are free) and `release`
to give it back. Caps how many threads run a section at once.

Use: limit concurrent access to a resource pool — e.g. at most 10 threads hitting a service at a time.

</details>

### CyclicBarrier — purpose?
<details><summary>Show answer</summary>

A reusable meeting point for a fixed number of threads.

How it works:

- **The wait:** a thread does its chunk of the work, and when it finishes it calls `await()` and blocks at the
  barrier — "I am done with my part, I'll wait here until the rest of you finish yours."
- **The release:** when the last thread arrives, all waiting threads are released together.
- **The cycle:** it immediately resets and can be used again for the next round — which is why it is "cyclic".
- **The bonus (barrier action):** you can configure it to execute a specific task (a `Runnable`) exactly once
  when the last thread arrives, before waking the others up — perfect for merging intermediate results.

Use case: repeated phases where all threads must completely finish one step before any thread starts the next.

</details>

### CyclicBarrier — a real-world example?
<details><summary>Show answer</summary>

Calculate total sales across 4 regions in parallel, then combine.

- Spawn 4 threads, one per region. Each computes its region's subtotal in parallel.
- As each finishes, it calls `await()` — "my part is done, I'll wait for the rest."
- When the 4th arrives, the barrier action runs once: it sums the 4 subtotals into the global total,
  *before* releasing anyone.
- All 4 threads are then released together to start the next phase of the pipeline.

This is the classic map-reduce / parallel-calculation shape: parallel work, a sync point where results merge,
then the next phase — see [CyclicBarrier — purpose?](#cyclicbarrier--purpose).

</details>

### Exchanger — purpose?
<details><summary>Show answer</summary>

A meeting point for exactly two threads that also swaps data. 
Each calls `exchange(x)`, blocks for the other, then both return holding the other's object.

Use: hand data back and forth between two threads — e.g. a filling buffer swapped for an empty one.

</details>

### Exchanger vs SynchronousQueue?
<details><summary>Show answer</summary>

Both force two threads to meet and block until the handoff is complete. They differ in direction:

- **`SynchronousQueue` — one-way handoff.** A producer gives an item to a consumer. Thread A brings an item and
  calls `put()`; Thread B arrives empty-handed and calls `take()`. A leaves empty-handed, B leaves with the item.
  Data flows in one direction.
- **`Exchanger` — two-way swap.** Both threads arrive carrying an object and both call `exchange(x)`. They trade,
  and each leaves holding what the other brought. Data flows both ways.

Handle: same meet-and-block, opposite direction — SynchronousQueue hands off, Exchanger swaps.

</details>

### Phaser — purpose?
<details><summary>Show answer</summary>

The most flexible synchronizer. Like a reusable barrier, but the number of participating threads can change at
runtime — threads `register` and `deregister` — and it advances through numbered phases.

Use: multi-phase work where how many threads take part varies from phase to phase.

</details>

### CountDownLatch vs CyclicBarrier?
<details><summary>Show answer</summary>

- CountDownLatch: one-shot, never resets. Waiters block on a count driven by *other* threads' `countDown` calls —
  they wait for an event to happen, not for each other.
- CyclicBarrier: reusable, resets each round. The threads that wait *are* the ones being counted — they wait for
  each other to all arrive, then proceed together.

Handle: latch = wait for N things to happen (once); barrier = N threads wait for each other (repeatedly).

</details>
