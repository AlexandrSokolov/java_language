### What is a synchronizer?
<details><summary>Show answer</summary>

An object that makes threads **wait for one another** so they can coordinate their work. Unlike a lock, where the
wait is a forced side effect, here the wait is the whole point.

Threads arrive and ask to proceed, and the synchronizer's internal state — a count, available permits, a meeting
point — dictates whether the thread is released or forced to wait. Threads are released by the state, not by who
arrived first.

</details>

### Which synchronizers exist?
<details><summary>Show answer</summary>

- **Wait for a count to hit zero — one-shot gate** — [CountDownLatch](#countdownlatch--purpose): 
  wait until N events finish. Never resets.
- **Wait for a free permit — resource limiter** — [Semaphore](#semaphore--purpose): 
  cap how many threads run a section at once.
- **Wait for everyone to arrive — reusable meeting point** — [CyclicBarrier](#cyclicbarrier--purpose): 
  fixed parties meet each round, reusable.
- **Wait for one partner, then swap — two-party swap** — [Exchanger](#exchanger--purpose): 
  a strict meeting point for exactly two threads to hand data back and forth.
- **Dynamic multi-phase — the flexible one** — [Phaser](#phaser--purpose): a reusable barrier where the party
  count can change at runtime across numbered phases.

Trigger: count-to-zero, free permit, everyone-arrives, swap-with-one, flexible-barrier (phaser).

</details>

### CountDownLatch — purpose?
<details><summary>Show answer</summary>

A one-shot gate. Built with a count N; threads call `await` and block until the count reaches zero. Other threads
call `countDown` to decrement it. Once it hits zero it stays open — it never resets.

Use: let one or more threads wait until N events have finished, once. "Don't start until all N workers are ready."

</details>

### Semaphore — purpose?
<details><summary>Show answer</summary>

Hands out a fixed number of permits. A thread calls `acquire` to take one (waiting if none are free) and `release`
to give it back. Caps how many threads run a section at once.

Use: limit concurrent access to a resource pool — e.g. at most 10 threads hitting a service at a time.

</details>

### CyclicBarrier — purpose?
<details><summary>Show answer</summary>

A reusable meeting point for a fixed number of threads.

How it works:

- **The wait:** a thread does its chunk of the work, and when it finishes it calls `await()` and blocks at the
  barrier — "I am done with my part, I'll wait here until the rest of you finish yours."
- **The release:** when the last thread arrives, all waiting threads are released together.
- **The cycle:** it immediately resets and can be used again for the next round — which is why it is "cyclic".
- **The bonus (barrier action):** you can configure it to execute a specific task (a `Runnable`) exactly once
  when the last thread arrives, before waking the others up — perfect for merging intermediate results.

Use case: repeated phases where all threads must completely finish one step before any thread starts the next.

</details>

### CyclicBarrier — a real-world example?
<details><summary>Show answer</summary>

Calculate total sales across 4 regions in parallel, then combine.

- Spawn 4 threads, one per region. Each computes its region's subtotal in parallel.
- As each finishes, it calls `await()` — "my part is done, I'll wait for the rest."
- When the 4th arrives, the barrier action runs once: it sums the 4 subtotals into the global total,
  *before* releasing anyone.
- All 4 threads are then released together to start the next phase of the pipeline.

This is the classic map-reduce / parallel-calculation shape: parallel work, a sync point where results merge,
then the next phase — see [CyclicBarrier — purpose?](#cyclicbarrier--purpose).

</details>

### Exchanger — purpose?
<details><summary>Show answer</summary>

A meeting point for exactly two threads that also swaps data. 
Each calls `exchange(x)`, blocks for the other, then both return holding the other's object.

Use: hand data back and forth between two threads — e.g. a filling buffer swapped for an empty one.

</details>

### Exchanger vs SynchronousQueue?
<details><summary>Show answer</summary>

Both force two threads to meet and block until the handoff is complete. They differ in direction:

- **`SynchronousQueue` — one-way handoff.** A producer gives an item to a consumer. Thread A brings an item and
  calls `put()`; Thread B arrives empty-handed and calls `take()`. A leaves empty-handed, B leaves with the item.
  Data flows in one direction.
- **`Exchanger` — two-way swap.** Both threads arrive carrying an object and both call `exchange(x)`. They trade,
  and each leaves holding what the other brought. Data flows both ways.

Handle: same meet-and-block, opposite direction — SynchronousQueue hands off, Exchanger swaps.

</details>

### Phaser — purpose?
<details><summary>Show answer</summary>

The most flexible synchronizer. Like a reusable barrier, but the number of participating threads can change at
runtime — threads `register` and `deregister` — and it advances through numbered phases.

Use: multi-phase work where how many threads take part varies from phase to phase.

</details>

### CountDownLatch vs CyclicBarrier?
<details><summary>Show answer</summary>

- CountDownLatch: one-shot, never resets. **Event-driven**. Waiters don't have to be the ones counting down. 
  They block on a count driven by *other* threads' `countDown` calls — 
  they wait for an event to happen, not for each other.
- CyclicBarrier: reusable, resets each round. **Thread-driven**. 
  The threads that wait *are* the ones being counted — they wait for each other to all arrive, then proceed together.

Handle: latch = wait for N things to happen (once); barrier = N threads wait for each other (repeatedly).

</details>

### How do you coordinate thread execution in the following scenario #1?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A main thread must wait for 4 background workers to finish loading configuration files before starting the server.

</details>

<details><summary>Show answer</summary>

Solvable with a [`CountDownLatch`](#countdownlatch--purpose) or a [`CyclicBarrier`](#cyclicbarrier--purpose) (or even
a [`Phaser`](#phaser--purpose)), depending on the lifecycle you need.

**`CountDownLatch` — the natural fit (one-shot gate).** Build it with count 4. The main thread calls `await()` and
blocks. Each worker calls `countDown()` as it finishes; when the count hits zero the main thread is released. The
latch never resets — which is fine, startup happens once.

**`CyclicBarrier` — fits if the work is phased/reusable.** A reusable meeting point. If the workers and main thread
move through repeated rounds, they all `await()` on each other. Or use a **barrier action**: the 4 workers `await()`,
and when the last arrives the barrier runs the server-startup task exactly once before releasing them for the next
round.

**Why both work — the discriminator.** A latch is driven by *events*: the waiter blocks while other threads count
down toward it. A barrier is driven by the *threads themselves* waiting for each other to arrive. This scenario is a
pure one-shot event wait, so the latch is the cleaner match; the barrier only earns its place if there are repeated
phases or a merge step to run at the meeting point.

</details>

</details>

### How do you coordinate thread execution in the following scenario #2?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A producer thread fills a buffer with log events and needs to hand it off directly to a consumer thread to be written
to disk. The producer must wait for the consumer to take it.

</details>

<details><summary>Show answer</summary>

Both `SynchronousQueue` and [`Exchanger`](#exchanger--purpose) force two threads to meet and block until the handoff
completes. The choice is the *direction* of data flow.

**`SynchronousQueue` — one-way handoff.** Use it if the producer just gives the buffer away. Producer arrives with the
buffer and calls `put()`; consumer arrives empty-handed and calls `take()`. Producer leaves empty, consumer leaves
with the data. Zero capacity — there is no slot to store into, so the two must meet.

**`Exchanger` — two-way swap.** Use it if the producer wants an empty buffer back to keep filling. Producer arrives
with the full buffer, consumer arrives with an empty one; both call `exchange()`. They trade — consumer gets the data
to write, producer immediately gets an empty buffer to reuse. This is the classic double-buffering shape.

**The discriminator.** Same meet-and-block rendezvous; the question is whether anything comes back. Nothing back →
`SynchronousQueue`. An empty buffer back to recycle → `Exchanger`. For a plain "hand it off and forget it," the
`SynchronousQueue` is the simpler fit; the `Exchanger` earns its place only when reusing the buffer matters.

</details>

</details>

### How do you coordinate thread execution in the following scenario #3?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A background cleanup thread must pause and wait until `activeUserCount == 0` **and** `systemMode == MAINTENANCE`.

</details>

<details><summary>Show answer</summary>

**No synchronizer fits — use a `ReentrantLock` with a `Condition`.**

**Why synchronizers fail here.** A synchronizer releases threads on its *own* internal state — a count reaching zero,
a free permit, a meeting point. It cannot evaluate arbitrary business logic over external variables. The release
condition here is a two-variable predicate (`activeUserCount == 0 && systemMode == MAINTENANCE`) that no latch,
barrier, semaphore, or phaser can express.

**The solution.** The cleanup thread holds the lock and loops on the predicate, calling `await()` while it is false.
Any thread that changes those variables takes the same lock and calls `signalAll()`, waking the cleanup thread to
re-check.

```java
private final ReentrantLock lock = new ReentrantLock();
private final Condition ready = lock.newCondition();

void awaitMaintenanceWindow() throws InterruptedException {
  lock.lock();
  try {
    while (!(activeUserCount == 0 && systemMode == MAINTENANCE))  // re-check on every wake
      ready.await();
    // predicate holds — safe to run cleanup
  } finally { lock.unlock(); }
}

// any writer of those variables, holding the same lock:
void onStateChange() {
  lock.lock();
  try {
    // ...mutate activeUserCount / systemMode...
    ready.signalAll();   // wake waiters to re-evaluate
  } finally { lock.unlock(); }
}
```

`while`, not `if`: a wake means "re-check," not "the predicate is now true" — it guards spurious wakeups and the case
where another thread invalidated the predicate before this one ran. `signalAll`, not `signal`: the predicate is
multi-variable, so a single change may not satisfy the waiter — wake all and let each re-test.

Handle: waiting on a predicate over your own shared state → `Lock` + `Condition`, never a synchronizer.

</details>

</details>

### How do you coordinate thread execution in the following scenario #4?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A multi-stage batch job processes data in parallel across sequential tiers. The thread pool autoscales dynamically
between stages based on system load, and worker threads can crash or drop out on failure. All currently active workers
must completely finish their current tier before any worker begins the next tier.

</details>

<details><summary>Show answer</summary>

**[`Phaser`](#phaser--purpose).** It is a reusable barrier whose party count can change at runtime — the exact
combination this scenario needs: meet-and-release per tier, plus a membership that grows and shrinks.

**Why `Phaser` fits.** Workers `register()` when the pool scales up and `arriveAndDeregister()` when they leave or
crash, so the phaser's target count tracks the live crowd. It advances through numbered phases, so each tier is a
phase: every active worker arrives, the phase advances, all proceed to the next tier together.

**Why the others fail.**

- [`CyclicBarrier`](#cyclicbarrier--purpose): party count is fixed at construction. A crash or a scale event means the
  barrier never reaches its target (deadlock) or a broken party trips `BrokenBarrierException`. It cannot model a
  changing crowd.
- [`CountDownLatch`](#countdownlatch--purpose): one-shot, never resets — can't serve repeated tiers.

Handle: reusable meet-and-release **plus** membership that changes at runtime → phaser; that pairing is the phaser's
signature and nothing else in the chapter covers it.

</details>

</details>

### How do you coordinate thread execution in the following scenario #5?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

An ultra-low-latency telemetry writer: Thread A writes metrics to buffer 1 while Thread B flushes buffer 2 to disk.
Once A fills its buffer and B finishes its write, they must instantly trade buffers — no new allocation, no shared
queue.

</details>

<details><summary>Show answer</summary>

**[`Exchanger<ByteBuffer>`](#exchanger--purpose).** A two-way rendezvous: A calls `exchange(fullBuffer)`, B calls
`exchange(emptyBuffer)`, and both return holding the other's buffer. They swap references in one atomic step — no GC
allocation, no queue in between. This is textbook zero-allocation double-buffering.

**Why not `SynchronousQueue`?** It is a one-way handoff. A could `put()` the full buffer and B could `take()` it, but
B has no way to return the empty buffer *in the same step* — A leaves empty-handed and must get a buffer from
somewhere else, which defeats the recycle-without-allocating requirement. Two `SynchronousQueue`s in opposite
directions could fake it, but that is two rendezvous where the exchanger does one.

**Why nothing else fits.** Latch/barrier/phaser meet threads but carry no data; a semaphore counts slots. Only the
exchanger both synchronizes two threads *and* moves an object each way.

Handle: two threads must each leave holding what the other brought → exchanger; the two-way swap in a single step is
its signature.

</details>

</details>

### How do you coordinate thread execution in the following scenario #6?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

An outbound HTTP client must strictly cap active outbound requests to an external API at 50 concurrent calls. Extra
threads must block until an active request completes and frees up capacity.

</details>

<details><summary>Show answer</summary>

**[`Semaphore`](#semaphore--purpose) with 50 permits.** Each thread calls `acquire()` before the call and `release()`
in a `finally`. At most 50 hold a permit at once; the 51st blocks until one is returned. Permits are a reusable pool
of slots — exactly a concurrency cap.

```java
private final Semaphore permits = new Semaphore(50);

void call() throws InterruptedException {
  permits.acquire();
  try {
    api.send();        // at most 50 threads reach here at once
  } finally {
    permits.release(); // release even if send() throws — or the cap leaks a slot
  }
}
```

**Why nothing else fits.** Latch/barrier/phaser wait for threads or events to line up; none counts *available
capacity*. Only the semaphore models "hold a slot while working, give it back when done."

**Senior nuance — concurrency limit ≠ rate limit.** A semaphore caps how many run *at once* (50 in flight); it does
not track time. A cap of "50 requests per second" is a different tool — a token bucket / Guava `RateLimiter`. Don't
reach for a semaphore when the requirement is per-second throughput.

Handle: limiting how many run concurrently → permits; limiting how many per unit time → rate limiter.

</details>

</details>

### Fixed thread pool vs Semaphore to cap concurrent calls?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show answer</summary>

Sizing a fixed thread pool to 50 *technically* caps concurrent outbound requests, but it is the wrong tool — 
it controls execution when the requirement is access control. 
Why the pool falls short of a [`Semaphore`](#semaphore--purpose):

**1. Unnecessary thread handoff and overhead.** If your app already has threads handling incoming requests (e.g.
Tomcat web threads), forcing them to submit HTTP tasks to a separate 50-thread pool means:

- The caller must create a task object (`Runnable`/`Callable`), submit it to a queue, and either block on a `Future`
  or hand off execution.
- This adds thread context switching, CPU overhead, and latency.
- With a `Semaphore`, the calling thread simply acquires a permit, makes the outbound call directly on its own thread,
  and releases the permit when done. No extra pool required.

**2. Queue management and memory pressure.** A fixed pool relies on an internal work queue to hold requests when all
50 slots are busy:

- Unbounded queues grow indefinitely under heavy load, eventually causing `OutOfMemoryError`.
- Bounded queues throw `RejectedExecutionException` when full, forcing you to handle rejections explicitly.
- A `Semaphore` doesn't queue tasks; it blocks the calling thread at the `acquire()` line until a permit frees up —
  memory stays predictable and flow control is natural.

**3. Thread pools manage execution; semaphores manage permission.**

- A thread pool limits concurrent execution *capacity* by reusing a pool of workers.
- A semaphore does *access control* to a shared resource (an external API cap, a DB connection pool).

Rule of thumb: control **who executes** the work → thread pool. Control **how many threads may touch a resource at
once** → `Semaphore`.

</details>

</details>

### How do you coordinate thread execution in the following scenario #7?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A worker thread must pause until three independent system properties all hold: `networkConnected == true`,
`batchQueue.size() >= 100`, and `maintenanceMode == false`.

</details>

<details><summary>Show answer</summary>

**No synchronizer fits — use a `ReentrantLock` with a `Condition`.**

**Why synchronizers fail.** A synchronizer releases on state *internal to itself* — permits, a counter, barrier
arrivals. It cannot evaluate a boolean expression over external variables, and here the release gate is three
independent ones combined: `networkConnected && batchQueue.size() >= 100 && !maintenanceMode`. No latch, semaphore,
barrier, or phaser can express that.

**Solution.** The worker holds the lock and loops on the compound predicate, `await()`-ing while it is false. Every
thread that changes any of the three variables takes the same lock and `signalAll()`s so the worker re-checks.

```java
lock.lock();
try {
  while (!(networkConnected && batchQueue.size() >= 100 && !maintenanceMode))  // re-test every wake
    condition.await();
  // predicate holds — execute work
} finally {
  lock.unlock();
}
```

`while`, not `if`: a wake means "re-check," not "the gate is open" — a different thread may have flipped one variable
back before this one runs, and it guards spurious wakeups. `signalAll`, not `signal`: with three contributing
variables a single change may satisfy one waiter but not this one — wake all, let each re-test its own predicate.

**Senior escalation.** For a hot path where this gating dominates, a custom `AbstractQueuedSynchronizer` (AQS) can
encode the wait/release logic directly and avoid the lock's overhead — but it is far harder to get right, so reach for
it only when `Lock` + `Condition` is measurably the bottleneck.

Handle: waiting on a compound predicate over your own shared state → `Lock` + `Condition`; AQS only when it's the
proven hot spot.

</details>

</details>

### How do you coordinate thread execution in the following scenario #8?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

N worker threads must block until an external coordinator finishes its setup, then all be released at once.

</details>

<details><summary>Show answer</summary>

**[`CountDownLatch`](#countdownlatch--purpose) as a start gate.** Build it with count 1. Every worker calls `await()`
and blocks. The coordinator does its setup, then calls `countDown()` once — the count hits zero and all workers are
released together.

**Why not [`CyclicBarrier`](#cyclicbarrier--purpose)?** A barrier makes the *waiting threads* count each other. Here
the workers don't wait for each other — they wait for one external "go" from the coordinator. That is an event another
thread causes, which is the latch's shape, not the barrier's. (Barrier fits the opposite case: the workers themselves
are the parties, and the last to arrive releases the rest.)

Handle: wait for an event someone else causes → latch; wait for each other → barrier.

</details>

</details>

### When do both a latch and a barrier work, and when only one?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show answer</summary>

The whole difference reduces to one mechanical rule: **who has to block?**

- **[`CountDownLatch`](#countdownlatch--purpose) — the trigger does not block.** A thread calls `countDown()` to
  signal an event and keeps moving. Fired like a switch, from outside.
- **[`CyclicBarrier`](#cyclicbarrier--purpose) — every participant blocks.** To release the barrier a thread must call
  `await()` and freeze until everyone arrives. You can't trip it without joining the huddle yourself.

**Where BOTH work — [main thread waits for 4 workers](#how-do-you-coordinate-thread-execution-in-the-following-scenario-1).**

- `CountDownLatch(4)`: each worker finishes, calls `countDown()`, and exits or carries on. Main `await()`s and wakes
  when the count hits zero.
- `CyclicBarrier(4)` + barrier action: the 4 workers finish and `await()` — **they are the ones waiting**, on each
  other. The last to arrive trips the barrier, the action runs the server startup once, then all 4 release.

Both fit because the workers themselves participate in the wait at the end of their task. Either mechanism has a
blocker that belongs in the huddle.

**Where ONLY the latch works — [N workers wait for one coordinator's "go"](#how-do-you-coordinate-thread-execution-in-the-following-scenario-8).**

- `CountDownLatch(1)`: the N workers `await()`. The coordinator does its setup, calls `countDown()` once, and **does
  not block** — fires the gun and keeps moving while all N wake at once.
- `CyclicBarrier` cannot fire a gun without trapping the firer:
  - `CyclicBarrier(N)` — the N workers `await()`, the N-th trips it automatically, and they release themselves
    *without ever waiting for the coordinator*. The coordinator never gets to gate them.
  - `CyclicBarrier(N+1)` (to include the coordinator) — now the coordinator must `await()` to signal "go," but
    `await()` **blocks it**. It's stuck in its own barrier instead of continuing.

**The golden rule.**

| Mechanism        | Trigger call  | Does the triggering thread block?            |
|------------------|---------------|----------------------------------------------|
| `CountDownLatch` | `countDown()` | No — fired from outside like a switch.       |
| `CyclicBarrier`  | `await()`     | Yes — you must join the group to release it. |

If the trigger source must **not** block (a coordinator firing a start gun, a worker reporting "done") → latch. If all
participants **must** wait for each other before any proceed → barrier.

</details>

### Two threads trade a full buffer for an empty one?
<details><summary>Show answer</summary>

**[`Exchanger`](#exchanger--purpose).** Each thread calls `exchange(x)`, blocks for the other, and both return
holding what the other brought. The producer arrives with a filled buffer, the consumer with an empty one; they swap
in a single meeting point.

This is a two-party, two-way trade — the exchanger's exact shape. A barrier meets N threads but carries no data; a
latch and semaphore don't pair threads at all. If the handoff were one-way — a producer handing an item to a consumer
who arrives empty — that would be [`SynchronousQueue`](#exchanger-vs-synchronousqueue) instead.

Handle: exactly two threads, both bring something, both leave with the other's → exchanger.

</details>

### Producer hands one item to a waiting consumer, no buffer?
<details><summary>Show answer</summary>

Two threads meet and block until the handoff completes — this looks like an [`Exchanger`](#exchanger--purpose), 
but it is one-directional, so the fit is **`SynchronousQueue`**.

- **`SynchronousQueue` — one-way.** Producer calls `put(item)` and blocks; consumer calls `take()` and blocks; they
  rendezvous, the item moves producer→consumer, producer leaves empty-handed. Zero capacity — no slot to store into,
  the two must meet.
- **`Exchanger` — two-way.** Both arrive carrying an object and both call `exchange(x)`; each leaves with what the
  other brought.

Naming both as candidates is right — they share the meet-and-block rendezvous. The discriminator is direction: one
item moving one way → `SynchronousQueue`; two objects trading → `Exchanger`.

Handle: same rendezvous, opposite direction — hand off one way vs swap both ways.

</details>

</details>

### How do you coordinate thread execution in the following scenario #9?
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A bounded buffer between producers and consumers: producers must block while it is full, consumers must block while it
is empty.

</details>

<details><summary>Show answer</summary>

**Best fit: a bounded [`BlockingQueue`](#) — e.g. `new ArrayBlockingQueue<>(100)`.** `put()` blocks while the queue is
full; `take()` blocks while it is empty. That is exactly this problem, already packaged — no code to write.

**No synchronizer fits.** A latch/barrier/phaser waits for threads or events; a semaphore counts free slots. 
None can express "block while *this* buffer is full, block while it is empty, and let each side wake the other." 
Both waits are predicates over shared mutable state — outside every synchronizer's model.

**The low-level tool underneath.** If you needed to build it by hand, it's a `ReentrantLock` with two `Condition`s
(`notFull`, `notEmpty`): producers `await()` on `notFull` and `signal()` `notEmpty`; consumers do the mirror. That is
precisely what `ArrayBlockingQueue` is made of — so use the queue, and reach for the raw `Lock` + `Condition` only when
you need behaviour the queue doesn't give you.

Handle: block-while-full / block-while-empty → bounded `BlockingQueue`; the hand-rolled `Lock` + two `Condition`s is
what's inside it.

</details>

</details>
