### How do workers see data they weren't passed?
<details><summary>Show answer</summary>

When work crosses an async boundary — handed off to a thread pool, queue, or callback — the data travels beside the
call, not in it.

A web filter knows the request ID, but the logger deep in the repository needs it. A parameter cannot be passed because:

- **Some signatures can't change.** `Runnable.run()`, a framework callback, an interface from a library — the method
  is fixed, there is no slot for one more argument.
- **Most layers never read it.** Every method in between takes the value only to hand it on. Add one more field
  (tenant, locale, trace ID) and every signature changes again.

So the data is kept next to the running work, where downstream workers can read it without having it passed in. That
is **context propagation** — carrying request-level data across boundaries without making it a parameter.

</details>

### What JDK tools carry request context?
<details><summary>Show answer</summary>

- [`ThreadLocal`](#what-is-a-threadlocal) — the value is tied to the thread. Any code running on that thread reads it.
- [`InheritableThreadLocal`](#what-is-an-inheritablethreadlocal) — tied to the thread, and copied into a new thread
  when that thread is created.
- [`ScopedValue`](#what-is-a-scopedvalue) — tied to one call. Everything that call reaches reads it; it ends when the
  call returns.

What changes from one to the next is what the value is tied to: a thread, a thread plus its new children, one call.

</details>

### What is a ThreadLocal?
<details><summary>Show answer</summary>

A variable where each thread sees its own value. The value lives in a map inside the `Thread` object, with the
`ThreadLocal` as the key; `get()` and `set()` always work on the current thread's value.

Two jobs:

- **[Context propagation.](#how-do-workers-see-data-they-werent-passed)** 
  A filter calls `USER.set(user)`; code deep in the same thread calls `USER.get()`.
- **[A per-thread copy of an object that isn't thread-safe.](#how-do-you-achieve-safe-sharing-for-a-non-thread-safe-class)**
  Each thread gets its own instance instead of sharing one, so no locking is needed.

</details>

### Where does ThreadLocal keep its value?
<details><summary>Show answer</summary>

Not in the `ThreadLocal`. Each `Thread` has its own map (field `threadLocals`, type `ThreadLocal.ThreadLocalMap`), and
the `ThreadLocal` instance is the key:

```java
USER.get();  // roughly: Thread.currentThread().threadLocals.get(USER)
```

Only the owning thread touches its map, so there is no locking. 
The value lives as long as the thread: until `remove()` is called or the thread dies.

</details>

### How does ThreadLocalMap handle collisions?
<details><summary>Show answer</summary>

Not with chains like `HashMap`. It is one flat array, and on a collision it steps to the next slot until it finds a free
one. This is **linear probing**, a form of open addressing.

It works because the map stays small and sparse:
- Each new `ThreadLocal` gets the previous hash plus a fixed number (`0x61c88647`), which spreads keys evenly, so
  collisions are rare.
- The array doubles once it is about two-thirds full, so the steps to a free slot stay short.

While stepping through slots, it also clears entries whose `ThreadLocal` was
[garbage collected](#how-can-threadlocal-leak-memory).

</details>

### How do you achieve safe sharing for a non-thread-safe class?
<details><summary>Show answer</summary>

By definition, a non-thread-safe class mutates internal state during its operations. To achieve safe sharing across
multiple threads, you must prevent concurrent access. There are two main approaches:

**1. Synchronization (shared lock)**
Share a single instance, but force threads to wait their turn to use it.

- **Pro:** Minimal memory footprint (only one instance exists).
- **Con:** Creates a performance bottleneck under high concurrency due to thread blocking.

**2. ThreadLocal (per-thread copy)**
Give each thread its own isolated instance so nothing is actually shared.

- **Pro:** Maximum performance (zero locking or waiting).
- **Con:** Memory overhead. In thread pools, instances live forever and risk memory/classloader leaks if not cleared.
- **Con:** Useless with virtual threads: one thread per task, so every task builds its own copy.

**Example:** `SimpleDateFormat` mutates an internal `Calendar` field during formatting.

```java
// Option 1: Lock the shared instance
static final SimpleDateFormat SHARED_FORMAT = new SimpleDateFormat("yyyy-MM-dd");

String formatLocked(Date date) {
  synchronized (SHARED_FORMAT) { return SHARED_FORMAT.format(date); }
}

// Option 2: Use a per-thread instance
static final ThreadLocal<SimpleDateFormat> THREAD_LOCAL_FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String formatPerThread(Date date) {
  return THREAD_LOCAL_FORMAT.get().format(date);
}
```

</details>

### SimpleDateFormat per thread — still needed?
<details><summary>Show answer</summary>

No, not in new code. A per-thread copy is a workaround for a class that isn't thread-safe. When an immutable
replacement exists, one shared instance is enough: no lock, no copy.

For dates that replacement is `DateTimeFormatter` (Java 8, `java.time`). It is immutable and thread-safe, and it formats
`java.time` types (`LocalDate`, `Instant`, …), not `java.util.Date`.

```java
static final DateTimeFormatter FORMAT = DateTimeFormatter.ofPattern("yyyy-MM-dd");

String format(LocalDate date) {
  return FORMAT.format(date);  // one shared instance, safe from any thread
}
```

</details>

### What problems does ThreadLocal have?
<details><summary>Show answer</summary>

Each problem comes from how the value is stored:

- **No owner.** Any code on the thread can call `set()`, 
  so [a deep call can overwrite the value](#who-can-overwrite-a-threadlocal-value).
- **Lives as long as the thread, not the task.**
    - [The next task on a pooled thread sees old data](#why-does-a-pooled-thread-see-old-data).
    - [The value is never freed](#how-can-threadlocal-leak-memory).

</details>

### Who can overwrite a ThreadLocal value?
<details><summary>Show answer</summary>

Any code on the same thread that can reach the `ThreadLocal`. `set()` is public and the value has no owner, so a method
deep in the call can replace it, and every caller above sees the new value after the call returns.

```java
USER.set(alice);     // filter
service.handle();    // somewhere inside: USER.set(admin)
audit(USER.get());   // admin, not alice
```

Keep the `ThreadLocal` private and expose only a getter to limit who can write. 
[`ScopedValue`](#what-is-a-scopedvalue) removes the problem: it has no `set()`.

</details>

### Why does a pooled thread see old data?
<details><summary>Show answer</summary>

A pool reuses threads, and the value lives in the thread, not in the task. If task A sets it and never removes it,
task B on the same thread reads A's value. Task B then runs as A's user.

```java
ExecutorService pool = Executors.newSingleThreadExecutor();
pool.submit(() -> { USER.set(alice); handle(); });   // task A: never removes
pool.submit(() -> audit(USER.get()));                // task B: sets nothing, reads alice
```

Fix: remove the value in `finally`, so the thread goes back to the pool clean.

```java
USER.set(user);
try {
  handle();
} finally {
  USER.remove();
}
```

</details>

### How can ThreadLocal leak memory?
<details><summary>Show answer</summary>

The thread's map holds the value strongly. Pool threads never die, so a value that is never removed is never freed. 
The key is held weakly, but that does not help: even after the `ThreadLocal` itself is gone, the value stays until later
map operations happen to clean it up.

In an app server it gets worse. The value's class belongs to the web app, so a container thread still holding the value
keeps the whole app's class loader alive after a redeploy, along with every class of the old version.

Fix: the same [`remove()` in `finally`](#why-does-a-pooled-thread-see-old-data).

</details>

### ThreadLocal is gone — when is its value freed?
<details><summary>Show answer</summary>

Not by the garbage collector. The GC clears only the weak key; the entry and its value stay in the thread's map. The map
frees them itself, and only during its own operations on the same thread:

- `get()`, when it misses its first slot and steps over a cleared key;
- `set()`, which scans a few slots after inserting, and sweeps the whole array before growing it;
- `remove()`.

Each cleanup (`expungeStaleEntry`) clears the stale slot and the run of slots after it.

If the thread never touches another `ThreadLocal` again, as with an idle pooled thread, the value is never freed. Only
`remove()` or the thread's death frees it for sure.

</details>

### ThreadLocal on virtual threads — what changes?
<details><summary>Show answer</summary>

Millions of virtual threads run on a few platform threads (carriers), but each virtual thread still has its own
`ThreadLocal` map. Inside it, `Thread.currentThread()` returns the virtual thread, so the carrier's values stay
invisible. A virtual thread runs one task and ends; it is never pooled.

- **Context propagation:** fine. The value is set and read within the same task, as before.
- **[Per-thread copy](#how-do-you-achieve-safe-sharing-for-a-non-thread-safe-class):** useless. Each task builds its
  own copy and throws it away, so nothing is reused, and a million threads means a million copies.

</details>

### How can a child thread see its parent's ThreadLocal?
<details><summary>Show answer</summary>

Not with a plain `ThreadLocal`. The value lives in the map of the thread that set it, and a new thread starts with an
empty map:

```java
static final ThreadLocal<String> USER = new ThreadLocal<>();

USER.set("alice");
new Thread(() -> System.out.println(USER.get())).start();  // null
```

The JDK way is [`InheritableThreadLocal`](#what-is-an-inheritablethreadlocal).

</details>

### What is an InheritableThreadLocal?
<details><summary>Show answer</summary>

A `ThreadLocal` that a new thread takes from its parent: when a thread is created, it gets the parent's values.

```java
static final InheritableThreadLocal<String> USER = new InheritableThreadLocal<>();

USER.set("alice");
new Thread(() -> System.out.println(USER.get())).start();  // alice, taken at creation
```

It happens once, at creation. A later `set()` in either thread is not seen by the other.

</details>

### InheritableThreadLocal in a pool — what happens?
<details><summary>Show answer</summary>

The copy happens when a thread is created, not when a task is submitted. A pool creates its threads once and reuses
them, so a task sees the values of whichever thread created the worker, not of the thread that submitted the task.

```java
ExecutorService pool = Executors.newSingleThreadExecutor();

USER.set("alice");
pool.submit(() -> System.out.println(USER.get()));  // alice: the worker is created now, from this thread

USER.set("bob");
pool.submit(() -> System.out.println(USER.get()));  // alice again: same worker, no new copy
```

In a pool, the value must be taken at submit time and set inside the task.

</details>

### Can a child change the parent's inherited value?
<details><summary>Show answer</summary>

Two cases:

- **`set()` in the child:** no. The child has its own entry, so the parent keeps its value.
- **Changing the object itself:** yes. The child gets the same reference, not a copy of the object. A mutable object is
  now shared by two threads with no lock, which is a data race.

```java
ROLES.set(new ArrayList<>(List.of("user")));

new Thread(() -> ROLES.set(List.of("admin"))).start();  // own entry: parent still has [user]
new Thread(() -> ROLES.get().add("admin")).start();     // same list: parent's list changes too
```

Fix: store immutable values, or override `childValue()` so the child gets its own copy.

</details>

### What problems does InheritableThreadLocal have?
<details><summary>Show answer</summary>

It is a `ThreadLocal`, so it has [all of ThreadLocal's problems](#what-problems-does-threadlocal-have). On top of those,
each problem comes from how the value is copied:

- **Copied at thread creation, not at submit.** [In a pool, a task sees the values of whoever created the
  worker](#inheritablethreadlocal-in-a-pool--what-happens).
- **Copies the reference, not the object.** [A child can change the parent's
  object](#can-a-child-change-the-parents-inherited-value).
- **Copies on every thread creation.** [Many threads mean many
  copies](#what-does-inheriting-cost-with-many-threads).

</details>

### What does inheriting cost with many threads?
<details><summary>Show answer</summary>

Every new thread copies all of its parent's inheritable entries into its own map when it is created. With a few
long-lived threads that costs nothing worth noticing. With one thread per task, as with virtual threads, it is one copy
per task: millions of tasks mean millions of copies, each paid before the task starts.

</details>

### InheritableThreadLocal on virtual threads — what changes?
<details><summary>Show answer</summary>

Virtual threads inherit by default, and one is created per task, from the thread that submits it.

- **[The pool problem](#inheritablethreadlocal-in-a-pool--what-happens) goes away.** Each task gets a new thread,
  created at submit time, so it sees the submitter's current values.
- **The copy cost grows.** Every thread creation copies the parent's map. One thread per task means one copy per task,
  so millions of tasks mean millions of copies.

</details>

### What JDK alternative fixes ThreadLocal for context?
<details><summary>Show answer</summary>

The [ThreadLocal](#what-problems-does-threadlocal-have) and
[InheritableThreadLocal](#what-problems-does-inheritablethreadlocal-have) problems come from three things.
[`ScopedValue`](#what-is-a-scopedvalue) removes each one:

- **Anyone can overwrite the value** → no `set()`: the value is bound once and read-only.
- **The value lives as long as the thread** → it ends when the call returns, so there is nothing to remove.
- **Every new thread copies it** → forked child threads share it without copying.

</details>

### What is a ScopedValue?
<details><summary>Show answer</summary>

A value bound for the length of one call. Everything that call reaches can read it; when the call returns, the binding
is gone.

```java
static final ScopedValue<String> USER = ScopedValue.newInstance();

void onRequest() {
  ScopedValue.where(USER, "alice").run(this::handle);  // bound only while handle() runs
}

void handle() {
  log(USER.get());  // alice, read anywhere below without a parameter
}
```

</details>

### Which ThreadLocal job does ScopedValue replace?
<details><summary>Show answer</summary>

Only context propagation. It can't do the per-thread copy:

- **The binding ends when the call returns,** so there is no copy kept for the thread to reuse.
- **Forked child threads share the same object,** so a non-thread-safe object is shared again.

For a non-thread-safe object, the choice stays
[a lock or a per-thread copy](#how-do-you-achieve-safe-sharing-for-a-non-thread-safe-class).

</details>

### ScopedValue — how does a sub-call get another value?
<details><summary>Show answer</summary>

Bind it again inside, with a nested `where(...).run(...)`. The inner call sees the new value, and when it returns the
outer value is back. Nothing is overwritten: unlike [ThreadLocal's `set()`](#who-can-overwrite-a-threadlocal-value),
callers above never see the change.

```java
ScopedValue.where(USER, "alice").run(() -> {
  log(USER.get());                                         // alice
  ScopedValue.where(USER, "system").run(() -> audit());    // audit() reads system
  log(USER.get());                                         // alice again
});
```

</details>

### ScopedValue — what exactly stays fixed?
<details><summary>Show answer</summary>

The binding, not the object. There is no `set()`, but a mutable object stays mutable: any code that reads it can change
it, and forked child threads share it with no lock. That is the same trap as
[InheritableThreadLocal's shared object](#can-a-child-change-the-parents-inherited-value).

```java
ScopedValue.where(ROLES, new ArrayList<>(List.of("user"))).run(() -> {
  ROLES.get().add("admin");  // allowed: only the binding is fixed, the list is not
});
```

Fix: bind immutable values (`List.of(...)`, records).

</details>

### What happens reading an unbound ScopedValue?
<details><summary>Show answer</summary>

`get()` throws `NoSuchElementException`. A `ThreadLocal` would return `null` instead. Check first, or give a default:

```java
USER.get();                // outside any binding: NoSuchElementException
USER.isBound();            // false
USER.orElse("anonymous");  // default when unbound
```

</details>

### What code shape does ScopedValue need?
<details><summary>Show answer</summary>

One call that wraps all the work. The value is bound when `run()` starts and gone when it returns, so you can't bind in
one method and unbind in another. APIs with separate begin and end hooks can't host a binding. That is why frameworks
built on such hooks keep using `ThreadLocal`.

```java
// fits: one method wraps the whole work
void handle(Request r) {
  ScopedValue.where(USER, r.user()).run(() -> process(r));
}

// doesn't fit: begin and end are separate calls
void preHandle(Request r)       { /* bind here? */ }
void afterCompletion(Request r) { /* unbind here? */ }
```

</details>

### How does a ScopedValue reach other threads?
<details><summary>Show answer</summary>

Only through child threads forked in a `StructuredTaskScope`. They see the parent's bindings, shared rather than copied.
This is safe because the scope does not close until every fork has finished, so no fork outlives the binding.

Any other thread sees nothing. A task sent to an `ExecutorService`, or a plain `new Thread`, has no binding:

```java
ScopedValue.where(USER, "alice").run(() -> {
  executor.submit(() -> USER.get());  // fails inside the task: NoSuchElementException
});
```

</details>

### JDK Context Tools — when to use which?
<details><summary>Show answer</summary>

- **`ScopedValue`** — the default for context propagation in new code, when one call wraps all the work. 
  It also reaches [forked child threads](#how-does-a-scopedvalue-reach-other-threads).
- **`ThreadLocal`** — 
  - when [begin and end are separate hooks](#what-code-shape-does-scopedvalue-need), 
  - when a deep call must change what callers above see, or 
  - for a [per-thread copy](#how-do-you-achieve-safe-sharing-for-a-non-thread-safe-class) 
    on a fixed pool of platform threads.
  Always `remove()` in `finally`.
- **`InheritableThreadLocal`** — rarely: only for threads you create yourself that need the parent's values. 
  Never with a [pool](#inheritablethreadlocal-in-a-pool--what-happens).

</details>

### Will `ScopedValue` work if I use `CompletableFuture.supplyAsync()`?
<details><summary>Show answer</summary>

No. `supplyAsync()` runs the task on the common `ForkJoinPool`, and that pool thread has no binding. `get()` inside the
task throws `NoSuchElementException`, and `join()` rethrows it wrapped in a `CompletionException`.

```java
ScopedValue.where(USER, "alice").run(() -> {
  CompletableFuture.supplyAsync(() -> USER.get())
      .join();  // CompletionException caused by NoSuchElementException
});
```

A non-async stage like `thenApply()` sees the binding only when it happens to run on the calling thread: by accident,
not by design. Only [forks of a `StructuredTaskScope`](#how-does-a-scopedvalue-reach-other-threads) get the binding.

</details>
