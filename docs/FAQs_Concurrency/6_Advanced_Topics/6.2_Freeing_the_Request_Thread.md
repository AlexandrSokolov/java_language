## Freeing the request thread

### Must a synchronous REST call hold a thread?
<details><summary>Show answer</summary>

No. "Synchronous" describes the client: it sends a request and waits on the same connection for the answer.
The server does not need an OS thread to wait with it:

- **Client side:** the client waits on an open connection. The OS holds that connection, and keeping it open costs
  almost nothing.
- **Server side:** the thread fires its I/O calls and goes back to the pool. When the result is ready, a thread writes
  the response to the still-open connection.

The client cannot tell the difference: same call, same response, same wait.

Whether an OS thread is held:

- **Held:** platform thread, handler returns the plain result (`Credit`). The thread must wait to get it.
- **Not held:** platform thread, handler returns `CompletableFuture<Credit>`. The thread goes back to the pool at once,
  and the [framework – Spring MVC or the JAX-RS runtime – ](todo) writes the response when the future completes.
- **Not held:** virtual thread, handler returns plain `Credit`.
  The [virtual thread](6.3_Virtual_Threads.md) waits, but not on an OS thread.

The client waits; an OS thread does not have to.

</details>

### How does a REST method free its thread?
<details><summary>Show answer</summary>

By returning control to the framework before the I/O is finished: the method returns a future
(`CompletableFuture<Credit>`) instead of the plain `Credit`.

1. **Return immediately:** the worker thread hands the future to the framework and goes straight back to the pool.
2. **Suspend the request:** the framework keeps the client's connection open, but no thread is tied to it (on a
   servlet container: `request.startAsync()`).
3. **Resume and write:** when the future completes, the framework's callback fires, and an available thread, possibly
   a different one, writes the response.

```java
@GET @Path("/credit/{id}")
public CompletionStage<Credit> credit(@PathParam("id") Long id) {
  return service.calculateCredit(id);  // thread returns at once; the runtime writes the response later
}
```

`CompletableFuture<T>` works in all the major frameworks, since each accepts a `CompletionStage<T>`:

- **Spring MVC** and **Spring WebFlux:** return `CompletableFuture<T>`.
- **Jakarta REST (2.1+):** declare `CompletionStage<T>` as the return type and return a `CompletableFuture` from it.

Each also has a native type: `DeferredResult<T>` (Spring MVC), `Mono<T>` (WebFlux), `@Suspended AsyncResponse`
(Jakarta REST).

With [virtual threads](6.3_Virtual_Threads.md), none of this is needed: the JVM unmounts the virtual thread at the I/O
call, so the method can return a plain `Credit` without holding an OS thread.

</details>

### Where must an async chain end?
<details><summary>Show answer</summary>

At the web framework (Spring MVC, Spring WebFlux, or the JAX-RS runtime). The handler returns the future itself,
untouched. The framework frees the thread and registers its own callback to write the response when the future
completes.

```java
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();  // thread waits here: the non-blocking gain is lost
}

@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);         // thread returns at once; Spring writes the response later
}
```

A `join()` or `get()` anywhere on the way (in a service, a helper, or the controller) makes a platform thread wait
right there, and the non-blocking pipeline turns back into a blocking one. On virtual threads, `join()` does not hold
an OS thread, but then the async chain is not needed at all.

Never unwrap the future yourself. Every layer passes it up to the framework.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// service.calculateCredit(id) returns CompletableFuture<Credit>, built on non-blocking drivers
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `join()` blocks the Tomcat thread until the whole chain finishes. The async service and the non-blocking
drivers buy nothing: each request still holds a platform thread for its full duration, and under load the pool empties
exactly as with plain blocking code, now with async code to maintain on top.

**Fix:** return the future and let Spring write the response.

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);  // thread goes back to the pool at once
}
```

**Where it matters:** only on platform threads. On virtual threads (`spring.threads.virtual.enabled=true`), `join()`
parks the virtual thread and frees its OS thread, but then the async chain is not needed at all.

An async chain frees threads only if nobody waits on it.

</details>

### Returning a future — what does it free?
<details><summary>Show answer</summary>

Only the request thread.

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return CompletableFuture.supplyAsync(() -> jdbcRepo.findCredit(id), dbPool);  // request thread free; a dbPool
}                                                                               // thread waits for JDBC instead
```

- **The gain:** Tomcat's 200 request threads no longer sit on DB waits. They return to the pool at once and keep
  serving requests that don't need the DB (fast CPU work, cache hits), so the server stays responsive. How much
  [throughput](6.1_Blocking_vs_Non-Blocking_IO.md#does-non-blocking-make-a-request-faster) that adds overall depends on
  what fills the future.
- **What fills the future:**
    - a blocking client (JDBC, `RestTemplate`): a thread in another pool waits instead. The wait
      [moved](#blocking-call-in-supplyasync--any-gain); it did not go away.
    - a [non-blocking client](todo): no thread waits.

A future frees the thread that returns it, not the thread that fills it.

</details>

### Blocking call in `supplyAsync` — any gain?
<details><summary>Show answer</summary>

Some, but no thread is saved. The wait moves from Tomcat's pool to yours.

```java
public CompletableFuture<Person> findPersonAsync(Long id) {
  return CompletableFuture.supplyAsync(() -> jdbcRepo.findPerson(id), dbPool);  // a dbPool thread waits here
}
```

- **Gain (isolation):** the request thread is freed, as long as the future
  [reaches the framework](#where-must-an-async-chain-end). If the DB slows down, only `dbPool` threads get stuck;
  Tomcat's threads keep serving requests that don't need the DB.
- **Gain (time):** two independent blocking calls on two pool threads
  [run at the same time](6.1_Blocking_vs_Non-Blocking_IO.md#when-does-async-reduce-service-time).
- **No gain (waiting threads):** 200 waiting requests still hold 200 threads, now in `dbPool`. Requests that need the
  DB are capped by `dbPool`'s size instead of Tomcat's.

Leave out the executor, and the wait lands in the [common pool](#describe-a-code-snippet-2), which is worse.

Moving a wait isolates it; only a [non-blocking client](todo) removes it.

</details>

### How many threads for a DB call pool?
<details><summary>Show answer</summary>

About as many as the JDBC pool has connections. Each blocking call holds a thread and a connection for its whole
duration, so the smaller of the two sets the limit:

- **More threads than connections:** e.g. 200 threads, 10 connections (HikariCP's default). 190 threads wait inside
  `getConnection()`, up to 30 s by default, and then the call fails. The extra threads add nothing: the DB still runs
  10 queries at a time.
- **Fewer threads than connections:** connections sit idle, and the DB could take more work than you send it.

The connection pool itself is sized to what the DB can handle, not to your traffic, and the thread pool follows it.

Size the thread pool to the connection pool; size the connection pool to the database.

</details>

### What is lost when work moves to another thread?
<details><summary>Show answer</summary>

Anything tied to the request thread through `ThreadLocal`. Thread-bound context stays on its thread; it does not
follow the task to the pool:

```java
@Transactional
public CompletableFuture<Void> placeOrder(Order o) {
  orderRepo.save(o);                                                      // request thread: in the transaction
  return CompletableFuture.runAsync(() -> stockRepo.reserve(o), dbPool);  // pool thread: no transaction, no user,
}                                                                         // no request ID in the logs
```

- **Transaction (`@Transactional`):** the connection and transaction state are bound to the request thread. The task
  runs outside the transaction, with its own connection and commit, so a failure can leave half the work committed.
  Here the transaction even commits when the method returns, before `reserve` runs.
- **Security context:** the authenticated user is stored on the thread. The pool thread runs with no user, so
  permission checks fail with unexpected `401` or `403` errors.
- **Logging context (MDC):** request IDs and trace IDs disappear from the task's log lines, so its logs can't be tied
  back to the request.
- **Request-scoped data:** request-scoped beans and the current-request holder are not available.

**Fix:** copy the context across the hop. Pass what the task needs as plain values, or wrap the pool so it copies the
context (Spring: `TaskDecorator`, `DelegatingSecurityContextExecutor`; Jakarta EE: `ManagedExecutorService`, which
carries security but not the transaction). A transaction is the exception: it cannot move to another thread, so start
a new one inside the task.

Anything stored per thread stays behind; pass it on, or rebuild it in the task.

</details>

### What if a future never completes?
<details><summary>Show answer</summary>

Take a task that hangs forever, e.g. an HTTP call with no read timeout:

1. **The client gets an error:** the framework's async timeout ends the request. Spring MVC answers `503` after the
   container's limit (Tomcat: 30 s), unless `spring.mvc.async.request-timeout` is set.
2. **The pool loses a thread:** that timeout does not stop the task. Its pool thread stays blocked, and a few hung
   calls drain the whole pool.

`orTimeout` on the future lets you answer first, but it does not free the thread either:

```java
return CompletableFuture.supplyAsync(() -> slowApi.fetch(), pool)
    .orTimeout(5, TimeUnit.SECONDS)    // fails the future after 5 s; slowApi.fetch() keeps running
    .exceptionally(ex -> fallback());  // answer the client before the framework's timeout
```

Only a timeout on the client itself (an HTTP read timeout, a JDBC query timeout) stops the call and frees the thread.

Time out the future to answer the client; time out the client to free the thread.

</details>

### Describe a code snippet #5
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
private final ExecutorService dbPool = Executors.newCachedThreadPool();

@GetMapping("/person/{id}")
public CompletableFuture<Person> person(@PathVariable Long id) {
  return CompletableFuture.supplyAsync(() -> personDao.findById(id), dbPool);  // personDao uses plain JDBC
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** a cached thread pool has no upper limit on threads. Every task that finds no idle thread gets a new one.
When the DB slows down, calls take longer, idle threads run out, and each new request creates another platform thread
blocked on JDBC. Most of them only wait for one of the few JDBC connections. Thousands of threads pile up, until the OS
refuses more and the JVM fails with an `OutOfMemoryError`. The slowdown is not kept inside the pool; it spreads to the
whole JVM.

**Fix:** a fixed pool sized to the connection pool, with a bounded queue.

```java
private final ExecutorService dbPool = new ThreadPoolExecutor(10, 10, 0, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100));  // 10 threads for 10 connections; extra requests are rejected fast
```

**Where it matters:** at normal load it looks fine, because threads are reused and few new ones are created. It breaks
only when the DB slows down, which is exactly when the isolation is needed.

A pool with no limit isolates nothing: a slow DB turns into unlimited threads.

</details>
