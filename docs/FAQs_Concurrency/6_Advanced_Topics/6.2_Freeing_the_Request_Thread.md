## Freeing the request thread

### Must a synchronous REST call hold a thread?
<details><summary>Show answer</summary>

No. "Synchronous" describes the client: it sends a request and waits on the same connection for the answer. 
The server does not need an OS thread to wait with it:

- **Client side:** the client waits on an open connection. The OS holds that connection, and keeping it open costs
  almost nothing.
- **Server side:** the thread fires its I/O calls and goes back to the pool. When the result is ready, a thread writes
  the response to the still-open connection.

The client cannot tell the difference: same call, same response, same wait.

The client waits; an OS thread does not have to.

</details>

### When does a REST handler hold an OS thread?
<details><summary>Show answer</summary>

It depends on what the handler returns, and on the kind of thread running it:

- **Held:** platform thread, plain result (`Credit`). The thread must wait to get it.
- **Not held:** platform thread, `CompletableFuture<Credit>`. The thread goes back to the pool at once, and the
  framework [writes the response later](#how-does-a-rest-method-free-its-thread).
- **Not held:** virtual thread, plain `Credit`. The [virtual thread](6.x_Virtual_Threads.md) waits, but not on an OS
  thread.

A plain result holds a platform thread; a future or a virtual thread does not.

</details>

### How does a REST method free its thread?
<details><summary>Show answer</summary>

By returning a [future](#which-future-types-do-rest-frameworks-accept) (`CompletableFuture<Credit>`) instead of the
plain `Credit`, so control goes back to the framework before the I/O is finished:

1. **Return immediately:** the worker thread hands the future to the framework and goes straight back to the pool.
2. **Suspend the request:** the framework keeps the client's connection open, but no thread is tied to it (on a
   servlet container: `request.startAsync()`).
3. **Resume and write:** when the future completes, the framework's callback fires, and an available thread, possibly
   a different one, writes the response.

```java
@GET @Path("/credit/{id}")
public CompletionStage<Credit> credit(@PathParam("id") Long id) {
  return service.calculateCredit(id);  // thread returns at once; the runtime writes the response later
}
```

</details>

### Which future types do REST frameworks accept?
<details><summary>Show answer</summary>

All of them accept `CompletionStage<T>`, so a `CompletableFuture<T>` works everywhere:

- **Spring MVC** and **Spring WebFlux:** return `CompletableFuture<T>`.
- **Jakarta REST (2.1+):** declare `CompletionStage<T>` as the return type, and return a `CompletableFuture` from it.


Each also has a native type: 
- `DeferredResult<T>` (Spring MVC), 
- `Mono<T>` (WebFlux), 
- `@Suspended AsyncResponse` (Jakarta REST).


`CompletionStage` is the common ground: declare it, and the same handler works in every framework.


With [virtual threads](6.3_Virtual_Threads.md), none of this is needed: the JVM unmounts the virtual thread at the I/O call, 
so the method can return a plain `Credit` without holding an OS thread.

</details>

### Who should take the result out of a future?
<details><summary>Show answer</summary>

The web framework (Spring MVC, Spring WebFlux, or the Jakarta REST runtime), never your code. 
Every layer passes the future up, and the controller returns it untouched:

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);  // GOOD: the thread returns at once
}
```

The framework then frees the worker thread and registers its own callback, which writes the HTTP response when the
future completes. Outside a framework (a `main`, a batch job, a test), your code is the end of the chain, and waiting
there is fine.

In a REST API the framework unwraps the future; every layer of your code only passes it up.

</details>

### What does waiting on a future cost?
<details><summary>Show answer</summary>

`join()` and `get()` block the calling thread until the future completes. 
Anywhere on a request's path (repository, service, controller), that turns the pipeline back into a blocking one:

```java
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();  // BAD: the request thread waits here; the non-blocking gain is lost
}
```

The cost depends on which thread waits:

- **Platform request thread:** held for the whole wait, so the throughput gain is lost.
- **Event loop:** every connection on the loop stalls, and it can wait forever if the reply needs that same loop.
- **Virtual thread:** cheap, since it parks without holding an OS thread, but then the async chain buys nothing; 
  plain blocking code would do.
- **Main thread, batch job, test:** fine. This is where a chain may end.

Waiting on a future blocks the thread that waits; that's acceptable only where blocking is cheap or expected.

</details>

### Returning a future — what does it free?
<details><summary>Show answer</summary>

Only the request thread.

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return CompletableFuture.supplyAsync(() -> jdbcRepo.findCredit(id), dbPool);  // request thread free; a dbPool
}                                                                               // thread waits for JDBC instead
```

- **The gain:** Tomcat's 200 request threads no longer sit on DB waits. They return to the pool at once and keep
  serving requests that don't need the DB (fast CPU work, cache hits), so the server stays responsive. How much
  [throughput](6.1_Blocking_vs_Non-Blocking_IO.md#does-non-blocking-make-a-request-faster) that adds overall depends on
  what fills the future.
- **No gain (waiting threads):** with a blocking client (JDBC, `RestTemplate`), a `dbPool` thread waits instead. 
  200 waiting requests still hold 200 threads, now in `dbPool`, and requests that need the DB are capped by its size. 
  The wait moved; it did not go away.
- **Only a [non-blocking client](6.3_Non-Blocking_Clients.md#when-does-no-thread-wait-at-all)** removes the wait, 
  so that no thread waits.

A future frees the thread that returns it, not the thread that fills it.

</details>

### What if a future never completes?
<details><summary>Show answer</summary>

Take a task that hangs forever, e.g. an HTTP call with no read timeout:

1. **The client gets an error:** the framework's async timeout ends the request. Spring MVC answers `503` after the
   container's limit (Tomcat: 30 s), unless `spring.mvc.async.request-timeout` is set.
2. **The pool loses a thread:** that timeout does not stop the task. Its pool thread stays blocked, and a few hung
   calls drain the whole pool.

`orTimeout` on the future lets you answer first, but it does not free the thread either:

```java
return CompletableFuture.supplyAsync(() -> slowApi.fetch(), pool)
    .orTimeout(5, TimeUnit.SECONDS)    // fails the future after 5 s; slowApi.fetch() keeps running
    .exceptionally(ex -> fallback());  // answer the client before the framework's timeout
```

Only a timeout on the client itself (an HTTP read timeout, a JDBC query timeout) stops the call and frees the thread.

Time out the future to answer the client; time out the client to free the thread.

</details>
