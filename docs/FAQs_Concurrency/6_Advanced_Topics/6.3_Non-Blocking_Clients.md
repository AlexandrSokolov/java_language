## Non-blocking clients

### When does no thread wait at all?
<details><summary>Show answer</summary>

When nothing in the request's path blocks:

1. **Every DB call uses a non-blocking driver** (e.g. R2DBC, not JDBC).
2. **Every HTTP call uses a non-blocking client** (e.g. `WebClient`, `HttpClient.sendAsync`, not `RestTemplate`).
3. **Nobody blocks on the result:** the chain [reaches the framework](6.2_Freeing_the_Request_Thread.md#where-must-an-async-chain-end).

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable long id) {
  return personRepo.findById(id).toFuture()                      // R2DBC: returns at once
      .thenCompose(p -> bureau.get().uri("/score/{id}", p.id())  // WebClient: returns at once
          .retrieve().bodyToMono(Score.class).toFuture()         // WebClient: convert to Future
          .thenApply(score -> calculate(p, score)));
}
```

While a call is in flight, the kernel holds the socket, and the client's [event loop](todo) waits for all its sockets
at once. So no thread waits for any single call, and threads run only the short steps between replies. One blocking
call anywhere in the path puts a waiting thread back.

No thread waits only when every client in the path is non-blocking and the future goes to the framework.

</details>



### Which libraries mean a thread still waits?
<details><summary>Show answer</summary>

Any I/O call that returns the data itself. If `orderRepo.findAll()` hands back a `List<Order>`, the calling thread sat
there until the rows arrived.

- **Database:** JDBC and everything built on it: `JdbcTemplate`, JPA / Hibernate ORM, Spring Data JPA repositories,
  MyBatis.
- **HTTP:** `RestTemplate`, `RestClient`, OpenFeign (by default), the JDK `HttpClient.send` (not `sendAsync`),
  `HttpURLConnection`, the Jakarta REST client's plain `get()`, and RESTEasy / MicroProfile Rest Client proxy methods
  that return `T`. Proxy methods that return `CompletionStage<T>` still wait on a pool thread unless the engine
  underneath is non-blocking.
- **Other I/O:** file APIs (`Files`, `FileInputStream`), socket streams, Jedis for Redis.

Wrapping any of these in a future does not change it: the wait only
[moves to a pool thread](6.2_Freeing_the_Request_Thread.md#blocking-call-in-supplyasync--any-gain).

A call that returns the data has waited for it; a non-blocking call returns a future or a publisher, or takes a
callback.

</details>

### Why can't JDBC be non-blocking?
<details><summary>Show answer</summary>

Because every JDBC call that talks to the DB returns its result directly:

```java
ResultSet rs = statement.executeQuery(sql);  // returns the rows: the thread waited for the DB
while (rs.next()) {                          // may fetch the next batch over the network: waits again
  ...
}
connection.commit();                         // waits for the DB to confirm
```

The API has no future and no callback anywhere, from `getConnection()` to `commit()`. So the calling thread must wait
inside the call, however the driver talks to the network underneath.

That leaves two ways out:

- **A different API:** [R2DBC](todo) returns publishers instead of results, so no thread waits.
- **Keep JDBC and make the wait cheap:** [virtual threads](todo). The thread still waits, but it no longer holds an OS
  thread.

JDBC's API hands back the data, so some thread must wait for it; no driver can change the shape of the API.

</details>

### Non-blocking DB access — what are the options?
<details><summary>Show answer</summary>

Two driver families, each with an ORM-free and an ORM-style way to use it:

- **R2DBC** (the Spring side): drivers for PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, and more.
    - Spring Data R2DBC: repositories that return `Mono` / `Flux`.
    - `DatabaseClient`: plain SQL.
- **Vert.x reactive SQL clients** (the Quarkus / Vert.x side): PostgreSQL, MySQL, DB2, SQL Server, Oracle.
    - Hibernate Reactive: a JPA-style ORM built on these clients.

```java
interface PersonRepository extends ReactiveCrudRepository<Person, Long> {}

Mono<Person> person = personRepo.findById(id);  // returns at once; the row arrives later
```

For NoSQL, most mainstream clients already have a non-blocking API: the MongoDB Reactive Streams driver, Lettuce for
Redis, the Cassandra driver's async API.

Every option replaces JDBC; none of them sits on top of it.

</details>

### What happens to JPA in a non-blocking stack?
<details><summary>Show answer</summary>

Classic JPA (Hibernate ORM) cannot stay on the request path. It is built on JDBC, and lazy loading hides DB calls
inside getters:

```java
Order order = orderRepo.findById(id).orElseThrow();  // JDBC query: the thread waits
int count = order.getItems().size();                 // lazy loading: a hidden query, another wait
```

The choices:

- **Hibernate Reactive:** keeps entities and mappings, on non-blocking drivers. Lazy loading is no longer hidden:
  related data is fetched explicitly, e.g. `Mutiny.fetch(order.getItems())`, which returns the result later.
- **Spring Data R2DBC:** not an ORM. No relationships, no lazy loading, no cascades, no automatic change tracking;
  related data is loaded with explicit queries.
- **Keep JPA behind its own pool:** it keeps working, but that part of the service stays blocking. The waits only
  [move to a pool thread](6.2_Freeing_the_Request_Thread.md#blocking-call-in-supplyasync--any-gain).

A getter that may query the DB cannot live in a non-blocking stack: every DB call must be visible and return its result
later.

</details>

### Which HTTP clients return without waiting?
<details><summary>Show answer</summary>

Those that return a future or a publisher, and do their I/O on non-blocking sockets:

- **JDK `HttpClient.sendAsync`:** plain Java, returns a `CompletableFuture`.
- **Spring `WebClient`:** returns `Mono` / `Flux`, runs on Reactor Netty by default, and works inside Spring MVC too.
- **Vert.x `WebClient`, and Quarkus's REST Client** (built on Vert.x): return `Future`, `Uni`, or `CompletionStage`.
- **Apache HttpClient 5's async API** (`CloseableHttpAsyncClient`): takes a callback.
- **The Jakarta REST client's `rx()`, and RESTEasy / MicroProfile proxies returning `CompletionStage`:** only if the
  engine underneath is non-blocking. With a blocking engine, a pool thread does the waiting.

```java
HttpClient client = HttpClient.newHttpClient();
CompletableFuture<String> body = client
    .sendAsync(HttpRequest.newBuilder(uri).build(), HttpResponse.BodyHandlers.ofString())
    .thenApply(HttpResponse::body);  // returns at once; the reply arrives later
```

A future in the signature is not proof: check that the I/O underneath is non-blocking, or a pool thread does the
waiting for you.

</details>

### How do you cap a dependency without a thread pool?
<details><summary>Show answer</summary>

With a limit on calls in flight instead of threads. Two places to put it:

**1. The client's connection pool.** Its size caps the calls at once, and a bounded wait queue with a timeout makes
the overflow fail fast:

```java
ConnectionProvider provider = ConnectionProvider.builder("bureau")
    .maxConnections(100)                           // the partner allows 100 calls at once
    .pendingAcquireMaxCount(200)                   // at most 200 calls waiting for a connection
    .pendingAcquireTimeout(Duration.ofSeconds(1))  // then fail fast
    .build();
WebClient bureau = WebClient.builder()
    .clientConnector(new ReactorClientHttpConnector(HttpClient.create(provider)))
    .build();
```

For the DB, the R2DBC pool's maximum size plays the same role.

**2. A permit counter per dependency.** A `Semaphore`, or a library bulkhead such as Resilience4j's. It must never
block, so use `tryAcquire`, not `acquire`:

```java
private final Semaphore bureauPermits = new Semaphore(100);

CompletableFuture<Score> score(Person p) {
  if (!bureauPermits.tryAcquire()) {
    return CompletableFuture.failedFuture(new BureauBusyException());  // reject at once; never wait for a permit
  }
  return bureau.fetchScoreAsync(p)
      .whenComplete((score, ex) -> bureauPermits.release());
}
```

On an event loop, a blocking `acquire()` would stall every connection that loop serves.

Without thread pools, the limit is a count of calls in flight: cap it, bound the wait, and never block to take a
permit.

</details>

### One blocking call inside a non-blocking chain — effect?
<details><summary>Show answer</summary>

It usually runs on an event loop, and then it stalls far more than one request:

```java
return bureau.fetchScoreAsync(p)                     // completes on the client's event loop
    .thenApply(score -> auditJdbc.save(p, score));   // JDBC call on that event loop
```

A plain `thenApply` runs on the thread that completed the previous step, here the client's event loop. That thread
serves many connections. Say 8 event loops each serve about 1,000 connections: one 50 ms JDBC call freezes 1,000
connections for 50 ms, and 8 such calls at once freeze the whole server. There is no error, only latency spikes in
unrelated requests. It is worse than blocking a pool thread, which holds up only its own request.

**Fix:** make the call non-blocking. If that's not possible, move it off the loop on purpose, to a bounded pool:

```java
return bureau.fetchScoreAsync(p)
    .thenApplyAsync(score -> auditJdbc.save(p, score), dbPool);  // the blocking call gets its own bounded pool
```

In Reactor code, the same move is `publishOn(Schedulers.boundedElastic())`.

A blocking call on an [event loop](todo) stalls every connection that loop serves: make it non-blocking, or move it to
a bounded pool on purpose.

</details>

### How do you find hidden blocking calls?
<details><summary>Show answer</summary>

Make them visible, because a blocking call on an event loop raises no error by itself:

- **In tests: BlockHound** (from the Reactor project). It is a Java agent that throws when a thread marked non-blocking
  calls a blocking JDK method: socket reads, file I/O, `Thread.sleep`.
```java
  BlockHound.install();  // in test setup: a blocking call on an event loop now throws BlockingOperationError
```
- **At runtime, from the framework:**
  - Vert.x logs a warning with a stack trace when an event loop is blocked longer than a limit (2 s by default).
  - Quarkus throws when a blocking API such as Hibernate ORM is called on an I/O thread.
  - Reactor throws when `block()` is called on one of its non-blocking threads.
- **In production: thread dumps and JFR.** Look for event-loop threads (`reactor-http-nio-*`,
  `vert.x-eventloop-thread-*`) stuck in socket reads or JDBC frames.

Hidden blocking calls don't fail; they slow everyone down. Turn them into errors in tests, and check event-loop stacks
in production.

</details>

### Describe a code snippet #23
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Decision> decide(long id) {
  return webClient.get().uri("/customers/{id}/score", id)
      .retrieve().bodyToMono(Score.class).toFuture()
      .thenApply(score -> {
        Customer c = customerRepo.findById(id).orElseThrow();  // Spring Data JPA
        return rules.decide(c.getOrders(), score);             // orders: a lazy collection
      });
}
```

</details>

<details><summary>Show answer</summary>

**Defect 1 (JDBC on the event loop):** `thenApply` runs on the thread that completed the `WebClient` call, a Reactor
Netty event loop. `findById` blocks that thread on JDBC, and every connection the loop serves stalls meanwhile.

**Defect 2 (the lazy collection):** `findById` runs in its own short transaction, which ends when it returns. There is
no session left on this thread, so `c.getOrders()` throws `LazyInitializationException`. Had the session stayed open,
the lazy load would have blocked the event loop a second time.

**Fix:** give the JPA work its own pool, and one transactional method that loads everything it needs.

```java
return webClient.get().uri("/customers/{id}/score", id)
    .retrieve().bodyToMono(Score.class).toFuture()
    .thenApplyAsync(score -> decisions.decide(id, score), dbPool);  // @Transactional; fetch-joins the orders
```

For a fully non-blocking version, replace JPA with R2DBC or Hibernate Reactive, where related data is fetched
explicitly.

**Where it matters:** at low load the stall is invisible, and only lazy relations throw, so a test with eager fields
passes.

JPA in a non-blocking chain blocks the event loop, and its lazy getters fail or block again; give JPA its own pool and a
transaction that loads everything it needs.

</details>

</details>

### Describe a code snippet #24
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@GetMapping("/offer/{id}")
public Mono<Offer> offer(@PathVariable long id) {    // WebFlux handler: runs on an event loop
  Customer c = customerClient.find(id).block();      // wait for the customer first
  return pricingClient.price(c).map(Offer::new);
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `.block()` waits on an event-loop thread. Reactor refuses this and throws `IllegalStateException`
("block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-…"). The guard
exists for two reasons. Blocking the loop would stall every connection it serves. And the reply being waited for may be
handled by that same loop, which can then wait for itself forever.

**Fix:** chain the second call instead of waiting for the first.

```java
return customerClient.find(id)
    .flatMap(c -> pricingClient.price(c))  // runs when the customer arrives; no thread waits
    .map(Offer::new);
```

**Where it matters:**
- **On a Tomcat thread (Spring MVC):** the same `.block()` is allowed. There it only holds the request thread, as in
  [snippet #1](#describe-a-code-snippet-1).
- **`CompletableFuture.join()` on an event loop:** it has no such guard. It blocks the loop silently, with the same
  stall and the same risk of waiting forever.

Never wait on an event loop: chain the next step, and let the reply start it.

</details>

</details>

### What does a full non-blocking switch cost?
<details><summary>Show answer</summary>

Two things you could rely on before are gone: calls may no longer wait, and a request no longer lives on one thread.
Each cost follows from one of them.

**No call may wait:**
- **The data layer:** JDBC and classic JPA leave the request path.
  [R2DBC or Hibernate Reactive](#non-blocking-db-access--what-are-the-options) replace them, and lazy loading
  [is no longer hidden](#what-happens-to-jpa-in-a-non-blocking-stack).
- **Every other blocking library** on the path must be replaced or moved to a bounded pool
  ([which ones](#which-libraries-mean-a-thread-still-waits)).

**A request no longer lives on one thread:**
- **Transactions** can't be bound to a thread ([how they work instead](#how-do-transactions-work-in-a-non-blocking-stack)).
- **`ThreadLocal` context** (security, MDC, tenant) doesn't follow the request
  ([what happens to it](#what-happens-to-threadlocal-data-across-async-hops)).
- **Stack traces** no longer show who called whom ([why](#why-are-async-stack-traces-hard-to-follow)).

**And the team:** a different coding style, error handling inside chains, new testing tools, and a learning curve for
everyone who touches the code.

Whether to pay all of it: [is a partial switch worth it?](#is-a-partial-switch-worth-it) Most of it can also be
avoided with [virtual threads](todo).

Trigger: *no call may wait → replace the data layer and blocking libraries; no thread per request → transactions,
context, and stack traces change.*

</details>

### How do transactions work in a non-blocking stack?
<details><summary>Show answer</summary>

In blocking code, the transaction sits on the request thread. In a non-blocking chain the steps run on different
threads, so the transaction must travel with the chain instead. The data library hands you a session, you run the steps
on it, and it commits when the chain completes:

```java
public CompletionStage<Void> transfer(long fromId, long toId, BigDecimal amount) {
  return sessionFactory.withTransaction((session, tx) ->
      session.find(Account.class, fromId)
          .thenCompose(from -> session.find(Account.class, toId)
              .thenAccept(to -> {
                from.debit(amount);
                to.credit(amount);
              })));  // committed when this stage completes; rolled back if it fails
}
```

- **Plain Java has no transactions of its own:** `CompletableFuture` knows nothing about connections, so the
  transaction must come from the data library. Above, it's Hibernate Reactive's Stage API, which uses only JDK types.
- **Spring:** its reactive transactions work only on methods that return Reactor types (`Mono` / `Flux`). For
  `CompletableFuture` chains it has none: `@Transactional` commits when the method returns, before the async steps run
  ([snippet #13](#describe-a-code-snippet-13)).

Two rules carry over from blocking code:
- The commit happens when the whole chain completes, not when the method returns.
- The connection is held for the whole chain, so remote calls still don't belong inside it
  ([snippet #18](#describe-a-code-snippet-18)).

Without a thread per request, the transaction travels with the chain; a plain future carries none.

</details>

### Why is thread context harder in a non-blocking chain?
<details><summary>Show answer</summary>

Behind a pool, the hop is one place you control: you submit to your executor, so you wrap it once and every task gets
the context. In a non-blocking chain, the thread changes at every reply, to threads you don't own (the client's event
loops), and there is no executor to wrap:

```java
MDC.put("requestId", requestId);
return client.fetchAsync(p)                          // the reply arrives on the client's event loop
    .thenApply(reply -> {
      log.info("reply received");                    // runs on that event loop: no requestId in this line
      return toScore(reply);
    });
```

Three ways to carry it:

- **Pass values explicitly:** carry what later steps need (user, tenant, request ID) as parameters or in a small
  context object. Plain Java, always works; the cost is that every step's signature carries it.
- **Restore it around each step:** capture the context once, and set and clear it inside every step.
```java
  static <T, R> Function<T, R> withMdc(Map<String, String> mdc, Function<T, R> step) {
    return t -> {
      MDC.setContextMap(mdc);
      try {
        return step.apply(t);
      } finally {
        MDC.clear();                                 // the event loop leaves clean
      }
    };
  }
  // .thenApply(withMdc(mdc, reply -> toScore(reply)))
```
It works, but every step must remember it.
- **A context-propagation library:** Micrometer Context Propagation captures the registered `ThreadLocal`s (MDC,
  security, tracing) and restores them around each step. Reactor does this automatically once
  `Hooks.enableAutomaticContextPropagation()` is on.

Spring's own non-blocking replacements (such as `ReactiveSecurityContextHolder`) keep the value in the chain instead of
on the thread, but they work only with Reactor types.

Behind a pool, wrap the executor once; in a non-blocking chain the thread changes at every reply, so the context must
travel with the chain itself.

</details>

### Why are async stack traces hard to follow?
<details><summary>Show answer</summary>

Because a stage runs as a callback, on whichever thread delivered the previous result. When it throws, the stack shows
that thread's work, not the path that built the chain:

```
java.util.concurrent.CompletionException: java.lang.NullPointerException
Caused by: java.lang.NullPointerException
    at com.acme.ScoreMapper.toScore(ScoreMapper.java:17)
    at java.base/java.util.concurrent.CompletableFuture$UniApply.tryFire(...)
    at java.base/java.util.concurrent.CompletableFuture.postComplete(...)
    ... (HTTP client and event-loop frames)
    at java.base/java.lang.Thread.run(...)
```

- **No caller:** no frame from the controller or the service that started the chain. You can't see which request, or
  which call site, led here.
- **Wrapped:** the real error sits inside a
  [`CompletionException`](#describe-a-code-snippet-15).
- **Blocking code shows it all:** controller → service → repository → socket read, in one stack.

What puts the missing context back:

- **Messages:** add it to exceptions at each step (e.g. "fetching score for customer 42").
- **Logs:** carry the request ID into every step's log lines
  ([context across hops](#why-is-thread-context-harder-in-a-non-blocking-chain)).
- **Tracing** (OpenTelemetry, Micrometer Tracing): it links the steps of one request across threads and services.
- **Tools:** IDE debuggers can stitch async stacks together, and Reactor has its own aids (`checkpoint`, a debug agent).

Virtual threads avoid the problem: the code stays blocking, so the stack shows the full path again.

An async stack shows who ran the callback, not who asked for it; add the missing context yourself, in messages, logs,
and traces.

</details>

### Is a partial switch worth it?
<details><summary>Show answer</summary>

Often, when one dependency causes most of the waiting.

Example: a request waits ~1 s on the partner API and ~10 ms on the DB. Switching only the partner call to a
non-blocking client removes about 99% of the thread-waiting. The DB stays on JDBC and JPA, behind a small bounded pool:

```java
public CompletableFuture<Credit> credit(long id) {
  return CompletableFuture.supplyAsync(() -> personDao.find(id), dbPool)  // JDBC on a bounded pool, ~5 ms
      .thenCompose(p -> bureau.fetchScoreAsync(p)                         // non-blocking client, ~1 s, no thread waits
          .thenApplyAsync(score -> creditDao.save(p, score), dbPool));    // back to the pool for JDBC
}
```

**Worth it when:**
- one or two dependencies cause most of the waiting;
- the rest of the stack (JPA, transactions, libraries) would cost too much to replace.

**Not worth it when:**
- the waiting is spread over many blocking dependencies: you pay the cost of two models everywhere for little gain;
- the CPU is the limit;
- Java 21+ is available: [virtual threads](todo) make every blocking call cheap at once, with one model.

**The cost of mixing:** two models in one codebase, and every boundary between them is a place for the known traps: a
blocking call on an event loop ([snippet #23](#describe-a-code-snippet-23)), a wait on an event loop
([snippet #24](#describe-a-code-snippet-24)), context lost at a hop. The rule that keeps it safe: blocking code runs
only on its own bounded pools, never on an event loop.

Switch the dependency that causes most of the waiting; keep the rest blocking behind bounded pools, and guard the
boundaries.

</details>

### Which thread runs the next stage?
<details><summary>Show answer</summary>

It depends on the method, and for a plain stage, on timing:

```java
CompletableFuture<Data> f = CompletableFuture.supplyAsync(() -> load(), ioPool);

f.thenApply(d -> parse(d));               // f still pending: runs on the thread that completes f (an ioPool thread)
                                          // f already complete: runs right here, on the calling thread
f.thenApplyAsync(d -> parse(d));          // the default executor: ForkJoinPool.commonPool()
f.thenApplyAsync(d -> parse(d), cpuPool); // cpuPool, always
```

- **Plain stage** (`thenApply`, `thenCompose`, `thenAccept`, `whenComplete`…): runs on the thread that completes the
  previous stage, or on the calling thread if that stage is already complete. When the two happen at the same moment,
  either thread may run it, so you can't rely on which.
- **`*Async` without an executor:** the common pool (or a new thread per task, if the common pool has fewer than 2
  threads).
- **`*Async` with an executor:** that executor.

It matters whenever the stage does real work. The completing thread may be a pool sized for something else, or an
[event loop](6.4_How_the_OS_Waits_on_IO.md#why-keep-slow-work-off-the-event-loop), and thread-bound context depends on
the thread too.

A plain stage runs on whichever thread completes the previous one, or on the caller if it is already done; only an
`*Async` stage with an executor names its thread.

</details>
