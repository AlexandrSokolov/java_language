## Non-blocking clients

### When does no thread wait at all?
<details><summary>Show answer</summary>

When nothing in the request's path [blocks](#where-can-a-request-still-block).

While a call is in flight, the kernel holds the socket, and the client's event loop waits for all its sockets at once.
So no thread waits for any single call, and threads run only the short steps between replies.

No thread waits only when every call in the path is non-blocking and the future goes to the framework.

</details>

### Where can a request still block?
<details><summary>Show answer</summary>

1. **A [DB call](#how-does-a-db-call-stop-blocking)** through JDBC, or anything built on it (JPA, Spring Data JPA):
  ```java
     Person p = jdbcTemplate.queryForObject(sql, mapper, id);  // waits for the DB
  ```

2. **An [HTTP call](#how-does-an-http-call-stop-blocking)** through a blocking client (`RestTemplate`, `RestClient`,
   `HttpClient.send`):
  ```java
     Score s = restTemplate.getForObject(url, Score.class);    // waits for the reply
  ```

3. **A [wait on a future](#how-to-use-a-future-without-blocking):** `join()` or `get()` anywhere on the way:
  ```java
     Credit c = service.calculateCredit(id).join();            // waits for the result
  ```

4. **A [message send](#how-does-a-message-send-stop-blocking)** that waits for the broker (JMS `send()`, Kafka
   `send().get()`, RabbitMQ `waitForConfirms()`):
  ```java
     producer.send(record).get();                              // waits for the broker
  ```

One blocking call anywhere in the path puts a waiting thread back.

</details>

### Why can't JDBC be non-blocking?
<details><summary>Show answer</summary>

Because every JDBC call that talks to the DB returns its result directly:

```java
ResultSet rs = statement.executeQuery(sql);  // returns the rows: the thread waited for the DB
while (rs.next()) {                          // may fetch the next batch over the network: waits again
  ...
}
connection.commit();                         // waits for the DB to confirm
```

The API has no future and no callback anywhere, from `getConnection()` to `commit()`. 
So the calling thread must wait inside the call, however the driver talks to the network underneath.

JDBC's API hands back the data, so some thread must wait for it; no driver can change the shape of the API.

</details>

### How does a DB call stop blocking?
<details><summary>Show answer</summary>

Only by replacing JDBC, whose API [returns the data itself](#why-cant-jdbc-be-non-blocking). A non-blocking driver
returns a future instead:

```java
CompletionStage<Person> p = session.find(Person.class, id);  // Hibernate Reactive: returns at once
```

Two driver families, each usable with plain SQL or with an ORM:

- **R2DBC** (the Spring side): PostgreSQL, MySQL, MariaDB, SQL Server, Oracle. 
  Plain SQL with `DatabaseClient`, or repositories with Spring Data R2DBC.
- **Vert.x reactive SQL clients** (the Quarkus / Vert.x side): PostgreSQL, MySQL, DB2, SQL Server, Oracle. 
  Plain SQL directly, or Hibernate Reactive, a JPA-style ORM on top.

For NoSQL, most mainstream clients already have a non-blocking API: 
the MongoDB Reactive Streams driver, Lettuce for Redis, the Cassandra driver.

A DB call stops blocking only with a driver that replaces JDBC; none of them sits on top of it.

</details>

### What happens to JPA in a non-blocking stack?
<details><summary>Show answer</summary>

Classic JPA (Hibernate ORM) cannot stay on the request path. 
It is built on JDBC, and lazy loading hides DB calls inside getters:

```java
Order order = orderRepo.findById(id).orElseThrow();  // JDBC query: the thread waits
int count = order.getItems().size();                 // lazy loading: a hidden query, another wait
```

The choices:

- **Hibernate Reactive:** keeps entities and mappings, on non-blocking drivers. Lazy loading is no longer hidden:
  related data is fetched explicitly, e.g. `Mutiny.fetch(order.getItems())`, which returns the result later.
- **Spring Data R2DBC:** not an ORM. No relationships, no lazy loading, no cascades, no automatic change tracking;
  related data is loaded with explicit queries.
- **Keep JPA behind its own pool:** it keeps working, but that part of the service stays blocking. The waits only
  [move to a pool thread](6.2_Freeing_the_Request_Thread.md#blocking-call-in-supplyasync--any-gain).

A getter that may query the DB cannot live in a non-blocking stack: 
every DB call must be visible and return its result later.

</details>

### How does an HTTP call stop blocking?
<details><summary>Show answer</summary>

Use a client that returns a future (or a publisher) and does its I/O on non-blocking sockets:

```java
CompletableFuture<HttpResponse<String>> r = httpClient.sendAsync(request, BodyHandlers.ofString());  // returns at once
```

- **JDK `HttpClient.sendAsync`:** plain Java, returns a `CompletableFuture`.
- **Spring `WebClient`:** runs on Reactor Netty, and works inside Spring MVC too.
- **Vert.x `WebClient`, and Quarkus's REST Client** (built on Vert.x).
- **Apache HttpClient 5's async API:** takes a callback.
- **The Jakarta REST client's `rx()`, and RESTEasy / MicroProfile proxies returning `CompletionStage`:** only if the
  engine underneath is non-blocking. With a blocking engine, a pool thread does the waiting.

An HTTP call stops blocking only when the client's I/O is non-blocking, not just its return type.

</details>

### Non-blocking vs reactive client — same thing?
<details><summary>Show answer</summary>

No:

- **Non-blocking** is about the I/O: no thread waits for the reply.
- **Reactive** is a programming model: results arrive as streams of events (`Mono` / `Flux`, `Uni` / `Multi`), 
  combined with operators, with back-pressure (the consumer sets the pace).

Reactive clients are built on non-blocking I/O, but neither implies the other:

- **Non-blocking, not reactive:** the JDK `HttpClient.sendAsync` returns a plain `CompletableFuture`.
- **Called reactive, blocking inside:** the Jakarta REST "reactive client API" (`rx()`) on RESTEasy's default engine,
  where a pool thread still waits. The same goes for `Mono.fromCallable(() -> blockingCall())`.

Docs often say "reactive" loosely, meaning async; check the I/O underneath, not the name.

</details>

### How to use a future without blocking?
<details><summary>Show answer</summary>

Attach the next step to the future instead of waiting for it, and hand the final future to the framework:

```java
return service.calculateCredit(id).thenApply(CreditDto::of);  // runs when the result arrives; no thread waits
```

Use `thenApply` for a plain next step, and `thenCompose` when the next step is itself async. At the end,
[the framework unwraps it](6.2_Freeing_the_Request_Thread.md#who-unwraps-a-future-in-a-rest-api).

Don't wait for a result; attach the next step to it.

</details>

### How does a message send stop blocking?
<details><summary>Show answer</summary>

Take the broker's answer as a callback instead of waiting for it:

```java
producer.send(record, (meta, ex) -> {  // Kafka: returns at once; the callback runs later
  if (ex != null) {
    log.warn("send failed", ex);
  }
});
```

- **Kafka:** `send()` still blocks when its buffer is full or topic metadata is missing (up to `max.block.ms`). Size
  the buffer, and never call `.get()` on the result.
- **JMS 2.0:** an async send with a `CompletionListener`.
- **RabbitMQ:** listen for publisher confirms (`ConfirmListener`) instead of calling `waitForConfirms()`.

A send stops blocking when the broker's answer comes back as a callback, not as a wait.

</details>

### How do you find hidden blocking calls?
<details><summary>Show answer</summary>

Make them visible, because a blocking call on an event loop raises no error by itself:

- **In tests: BlockHound** (from the Reactor project). It is a Java agent that throws when a thread marked non-blocking
  calls a blocking JDK method: socket reads, file I/O, `Thread.sleep`.
```java
  BlockHound.install();  // in test setup: a blocking call on an event loop now throws BlockingOperationError
```
- **At runtime, from the framework:**
  - Vert.x logs a warning with a stack trace when an event loop is blocked longer than a limit (2 s by default).
  - Quarkus throws when a blocking API such as Hibernate ORM is called on an I/O thread.
  - Reactor throws when `block()` is called on one of its non-blocking threads.
- **In production: thread dumps and JFR.** Look for event-loop threads (`reactor-http-nio-*`,
  `vert.x-eventloop-thread-*`) stuck in socket reads or JDBC frames.

Hidden blocking calls don't fail; they slow everyone down. 
Turn them into errors in tests, and check event-loop stacks in production.

</details>

### Why are async stack traces hard to follow?
<details><summary>Show answer</summary>

Because a stage runs as a callback, on whichever thread delivered the previous result. When it throws, the stack shows
that thread's work, not the path that built the chain:

```
java.util.concurrent.CompletionException: java.lang.NullPointerException
Caused by: java.lang.NullPointerException
    at com.acme.ScoreMapper.toScore(ScoreMapper.java:17)
    at java.base/java.util.concurrent.CompletableFuture$UniApply.tryFire(...)
    at java.base/java.util.concurrent.CompletableFuture.postComplete(...)
    ... (HTTP client and event-loop frames)
    at java.base/java.lang.Thread.run(...)
```

- **No caller:** no frame from the controller or the service that started the chain. You can't see which request, or
  which call site, led here.
- **Wrapped:** the real error sits inside a `CompletionException`.
- **Blocking code shows it all:** controller → service → repository → socket read, in one stack.

An async stack shows who ran the callback, not who asked for it.

</details>

### How do you trace an error through an async chain?
<details><summary>Show answer</summary>

Put back the context the stack no longer shows:

- **Messages:** add it to exceptions at each step (e.g. "fetching score for customer 42").
- **Logs:** carry the request ID into every step's log lines
  ([context across hops](7.3_Context_and_Transaction_Boundaries.md#why-is-thread-context-harder-in-a-non-blocking-chain)).
- **Tracing** (OpenTelemetry, Micrometer Tracing): it links the steps of one request across threads and services.
- **Debuggers:** IDEs can stitch async stacks together.

Or avoid the problem: on [virtual threads](6.x_Virtual_Threads.md) the code stays blocking, and the stack shows the
full path again.

Add the missing context yourself, in messages, logs, and traces.

</details>

### Mixing blocking and non-blocking clients — worth it?
<details><summary>Show answer</summary>

Often, when one dependency causes most of the waiting.

Example: a request waits ~1 s on the partner API and ~10 ms on the DB. Switching only the partner call to a
non-blocking client removes about 99% of the thread-waiting. The DB stays on JDBC and JPA, behind a small bounded pool:

```java
public CompletableFuture<Credit> credit(long id) {
  return CompletableFuture.supplyAsync(() -> personDao.find(id), dbPool)  // JDBC on a bounded pool, ~5 ms
      .thenCompose(p -> bureau.fetchScoreAsync(p)                         // non-blocking client, ~1 s, no thread waits
          .thenApplyAsync(score -> creditDao.save(p, score), dbPool));    // back to the pool for JDBC
}
```

**Worth it when:**
- one or two dependencies cause most of the waiting;
- the rest of the stack (JPA, transactions, libraries) would cost too much to replace.

**Not worth it when:**
- the waiting is spread over many blocking dependencies: you pay the cost of two models everywhere for little gain;
- the CPU is the limit;
- Java 21+ is available: [virtual threads](todo) make every blocking call cheap at once, with one model.

**The cost of mixing:** two models in one codebase, and every boundary between them is a place for the known traps: a
blocking call on an event loop ([snippet #23](#describe-a-code-snippet-23)), a wait on an event loop
([snippet #24](#describe-a-code-snippet-24)), context lost at a hop. The rule that keeps it safe: blocking code runs
only on its own bounded pools, never on an event loop.

Switch the dependency that causes most of the waiting; keep the rest blocking behind bounded pools, and guard the
boundaries.

</details>
