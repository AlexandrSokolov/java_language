## Virtual Threads — limits and hazards

### Virtual threads — what are the limits?
<details><summary>Show answer</summary>

Virtual threads make one thing cheap: a thread waiting on network IO. Each limit sits in one of three places.

**1. Task Suitability (No magic speedup).**
- Network IO waits off the carrier, so it [gains a lot](#which-tasks-benefit-most-from-virtual-threads).
- CPU work and file IO [gain little](#where-do-virtual-threads-give-little): CPU work doesn't wait, and
- [file IO waits while holding the carrier](#blocking-io-on-virtual-threads). And
- [one task never gets faster](#how-do-virtual-threads-speed-up-tasks); only more tasks run at once.

**2. Unlimited Concurrency Hazards.** Virtual threads are one per task with no cap, so a downstream service gets
[the whole load](#virtual-threads-without-a-limit--what-breaks).

**3. Carrier Pinning.** Sometimes a virtual thread [can't leave its carrier](#what-keeps-a-virtual-thread-on-its-carrier),
even on network IO, and waits holding an OS thread.

Cheap waiting helps only work that waits, only as far as the rest of the system can keep up, and only while the
thread can leave its carrier.

</details>

### Virtual threads without a limit — what breaks?
<details><summary>Show answer</summary>

**Before:** a pool of 200 platform threads. Every request runs on one of them, so at most 200 calls reach a downstream
resource at once. Nobody wrote that limit on purpose, but it protected everything behind the app.

**With virtual threads:** the executor has no cap. A million requests become a million virtual threads, and if they
all call the same limited resource (an external API, a database), it gets them all at once. Sized for 200, it slows
down, times out, rejects calls or crashes. The failure shows up downstream, not in your app.

The pool limited downstream load for free. Without it, you have to add **rate limiting** yourself: a cap on how many
calls run at once, in front of each limited resource.

</details>

### Rate limiting — what are the tools?
<details><summary>Show answer</summary>

**Cap on calls at once:**
- **`Semaphore`** (JDK): `acquire()` before the call, `release()` in `finally`. Waiting in `acquire()` is cheap on a
  virtual thread.
- **Connection pool** (for a database): its size is the cap, and extra threads wait for a free connection.
- **Resilience4j `Bulkhead`:** the same cap as a library, plus timeouts and metrics.

**Cap on calls per second:** a rate limiter, such as Resilience4j `RateLimiter` or Guava `RateLimiter`.

Not a pool of virtual threads: they are cheap and meant to be one per task. Limit the resource, not the threads.

</details>

### Semaphore wait — platform vs virtual thread?
<details><summary>Show answer</summary>

```java
Semaphore permits = new Semaphore(50);

// run by each of 10,000 threads
permits.acquire();   // 50 go through, 9,950 wait here
try {
  return api.call(req);
} finally {
  permits.release();
}
```

- **Platform threads:** 9,950 OS threads sit idle in `acquire()`. Too costly, so the old way was a pool of 50 threads
  and a queue of waiting tasks.
- **Virtual threads:** each waiting thread leaves its carrier and stays on the heap as a small object. 10,000 waiting
  threads cost about as much as 10,000 queued tasks, so one thread per task plus a semaphore replaces pool plus queue.

With virtual threads, the waiting threads are the queue.

</details>

### Database stalls, requests keep coming — what happens?
<details><summary>Show answer</summary>

**Heap exhaustion:** waiting virtual threads pile up on the heap until it runs out.

```java
Semaphore permits = new Semaphore(50);

// a new virtual thread per request; the database has stalled
permits.acquire();   // every new request waits here, holding its request data
```

- A waiting virtual thread is small but not free: its stack and its request data stay on the heap.
- The semaphore protects the database, but nothing protects your app. Requests keep arriving, and
  [the waiting threads are the queue](#semaphore-wait--platform-vs-virtual-thread), a queue with no bound. No thread
  limit is ever hit; the heap fills up and you get `OutOfMemoryError`.

Fix: bound the wait and reject the rest (**load shedding**). In the app, `tryAcquire(200, MILLISECONDS)` gives up and
returns an error (503) instead of waiting forever. At the edge, the gateway or load balancer caps incoming requests.

Rate limiting protects the downstream; only a bound on waiting protects your own heap.

</details>

### ThreadLocal with virtual threads?
<details><summary>Show answer</summary>

**Purpose of `ThreadLocal`:** to store and manage data that is accessible only by a specific, individual thread.

**The hazards with virtual threads:**

- **Memory bloat:** `ThreadLocal` assumes a small number of long-lived threads (like a platform pool). With millions
  of short-lived virtual threads, it creates millions of object copies, causing severe memory exhaustion and GC strain.
- **Inheritance bugs:** virtual threads inherit `InheritableThreadLocal` values from their parent thread. In massive
  concurrency, this unintended inheritance can easily leak sensitive context (like user sessions or security tokens)
  across thousands of tasks, causing subtle and hard-to-trace bugs.

**Alternative:** `ScopedValue`, a read-only value bound for one call. Child tasks see it without a copy, and it's
gone when the call ends.

</details>

### What keeps a virtual thread on its carrier?
<details><summary>Show answer</summary>

**Carrier pinning:** a virtual thread can't leave its carrier while it waits.

```java
synchronized (cache) {
  cache.put(key, client.fetch(key));  // network wait inside synchronized: on JDK 21–23 the carrier is held
}
```

To leave its carrier, a virtual thread's stack is copied to the heap, and it may resume on another carrier.
Anything that ties the stack to this one carrier keeps it there (**pinning**):

- **`synchronized` (JDK 21–23):** the monitor records the carrier as its owner, so the thread can't move while it
  holds the monitor. Blocking inside it (IO, `sleep`, `wait()`) [holds the carrier](#pinned-by-synchronized--whats-the-fix).
- **Native code (all versions):** a native method or foreign function on the stack. The JVM can't copy native frames,
  so the thread stays on its carrier until the call returns.

A pinned thread waits like a platform thread and holds an OS thread.
Carriers are few (one per core), so with 8 carriers, 8 pinned waits stop every other virtual thread.

A virtual thread leaves its carrier only if its whole stack can move;
a native frame, or a held monitor before JDK 24, ties it down.

</details>

### Pinned by synchronized — what's the fix?
<details><summary>Show answer</summary>

**JDK 24 and later:** nothing to do. The monitor now records the virtual thread as its owner, not the carrier, so a
thread blocking inside `synchronized` leaves its carrier.

**JDK 21–23:** replace `synchronized` around blocking code with `ReentrantLock`. Its owner is the virtual thread, so
waiting inside the lock, or waiting to get it, frees the carrier:

```java
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
  cache.put(key, client.fetch(key));  // network wait: the thread leaves its carrier
} finally {
  lock.unlock();                      // always release, like a semaphore permit
}
```

- Synchronized blocks use object monitors that until JDK 24 require pinning.
- `ReentrantLock` uses park/unpark mechanisms that are virtual-thread-aware.

</details>

### Legacy blocking library with virtual threads?
<details><summary>Show answer</summary>

Run its calls on a separate pool of platform threads:

```java
ExecutorService legacy = Executors.newFixedThreadPool(20);  // platform threads for the old library

// on a virtual thread:
Result r = legacy.submit(() -> oldClient.call(req)).get();  // a pool thread blocks; this thread leaves its carrier
```

The old code blocks platform threads set aside for it, and the carriers stay free.

</details>

### Legacy blocking library on a virtual-thread pool?
<details><summary>Show answer</summary>

```java
// a pool of 20 virtual threads for the old library
ExecutorService legacy = Executors.newFixedThreadPool(20, Thread.ofVirtual().factory());
```

It doesn't help. The 20 virtual threads still run on the shared carriers, about one per core, and you can't give some
virtual threads carriers of their own. Each pinned call holds a carrier while it blocks, so with 8 carriers, 8 pinned
calls stall every virtual thread in the app. [A platform pool](#legacy-blocking-library-with-virtual-threads) gives
the calls their own OS threads instead.

A pool smaller than the carrier count only limits the damage: the carriers it pins are still lost to everyone else.

Pooling virtual threads changes how many exist, not where they run.

</details>

### Monitoring virtual threads — which tools?
<details><summary>Show answer</summary>

- **Java Flight Recorder - JFR (main tool):** has virtual-thread events, most importantly `jdk.VirtualThreadPinned`,
  which shows when and where a thread couldn't leave its carrier.
- **New thread dump:** `jcmd <pid> Thread.dump_to_file -format=json <file>` includes virtual threads, grouped by the
  executor that owns them.
- **Pinning trace:** `-Djdk.tracePinnedThreads=full` prints a stack trace when a pinned thread blocks.
  The flag exists only on JDK 21–23; on 24+, use the JFR event above.
- **Thread-locals:** `-Djdk.traceVirtualThreadLocals` prints a stack trace each time a virtual thread sets a
  thread-local value, including the ones inside libraries.
- **Carrier health:** CPU use, busy carriers and queued virtual threads (JMX `VirtualThreadSchedulerMXBean`, JDK 24+).
  All carriers busy with a growing queue means starvation.
- **Downstream pressure:** waits at the limit (pool connection, semaphore permit), plus downstream latency and errors.

**Traps:**
- Old tools skip virtual threads: `jstack`, `Thread.getAllStackTraces()` and `ThreadMXBean` show only platform threads.
- Thread count is no longer a load signal. Don't track millions of threads; watch the carriers, pinning events and
  waits at the limits.

</details>
