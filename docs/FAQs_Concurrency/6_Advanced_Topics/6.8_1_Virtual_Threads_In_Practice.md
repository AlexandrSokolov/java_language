## Virtual Threads — The Gain and How to Code With It

### What is Little's law?
<details><summary>Show answer</summary>

In a stable system, on average:

**throughput = concurrency / response time** (λ = N / d)

- **Throughput (λ):** tasks finished per unit of time.
- **Concurrency (N):** tasks in progress at the same moment.
- **Response time (d):** time for one task, from start to finish.

Example: 200 threads and 1 s per task give 200 tasks per second.

The law doesn't care whether the time is spent working or waiting, or what does the work: a thread, a CPU core or a
bank teller. So when response time is fixed, the only way to raise throughput is to
[raise concurrency](#how-do-virtual-threads-scale).

</details>

### How does Little's law explain virtual threads?
<details><summary>Show answer</summary>

[Little's law](#what-is-littles-law) (throughput = N / d) gives two ways to raise throughput: raise N (tasks in
progress) or cut d (time per task).

**Traditional threads hit a wall.** N stops at the OS thread limit, a few thousand. The only lever left is d, and for IO
tasks d is mostly the database's or the remote service's time, so it's out of your hands. Throughput is stuck.
With platform threads, throughput can improve with larger thread pools, but there’s a limit.
Eventually, OS resources will be constrained, and thread management overhead becomes the bottleneck

**Virtual threads remove the wall.** N can grow to millions with the same blocking code, so throughput grows with it
while d stays the same.

</details>

### How do virtual threads scale?
<details><summary>Show answer</summary>

A blocked virtual thread leaves its carrier and waits as a small object on the heap. Waiting costs no OS thread, so
the number of tasks in progress is no longer capped at the few thousand OS threads a machine can hold.

Little's law ties this to throughput: throughput = tasks in progress / time per task. For tasks that each sleep 1 s
(the ideal case):

- 10,000 virtual threads → about 10,000 tasks per second.
- 1,000,000 virtual threads → about 1,000,000 tasks per second.

Platform threads stop growing at the OS thread limit. Virtual threads keep growing with the number of tasks.

</details>

### How do virtual threads speed up tasks?
<details><summary>Show answer</summary>

They don't. A task takes as long on a virtual thread as on a platform thread. What goes up is
[throughput](#how-do-virtual-threads-scale): more tasks are in progress at once, so more of them finish per second.

</details>

### 10,000 blocking tasks — executor results?
<details><summary>Show answer</summary>

Each task sleeps for 1 second.

- **`newVirtualThreadPerTaskExecutor()`:** all 10,000 start right away, each on its own virtual thread.
  While blocked, they wait off the carriers, so a few OS threads carry them all. Done in about 1 s.
- **`newCachedThreadPool()`:** all 10,000 start right away, each on its own OS thread. If the OS allows 10,000
  threads, it also finishes in about 1 s. If not, it fails with `OutOfMemoryError`.
- **`newFixedThreadPool(200)`:** limits concurrency to 200 active tasks at a time, forcing the rest into a queue and
  causing severe processing delays: 10,000 / 200 = 50 rounds, about 50 s.

</details>

### Which tasks benefit most from virtual threads?
<details><summary>Show answer</summary>

Tasks that mostly wait on IO, when there are thousands or more of them at once:

- a server handling many requests at the same time, each on its own thread;
- code making many calls in parallel to databases, other services or message brokers.

CPU-bound tasks gain nothing, because only as many run at once as there are carriers.

</details>

### Migrating to virtual threads — what code changes?
<details><summary>Show answer</summary>

Only how threads are created. The code that runs on them stays the same:

```java
ExecutorService ex = Executors.newFixedThreadPool(200);           // before
ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor();  // after
```

**Trap:** the fixed pool also capped how many tasks ran at once, for example 200 database calls.
The virtual executor has no cap, so 10,000 tasks hit the database together.
Keep the cap with a `Semaphore`, not by pooling virtual threads.

</details>

### ThreadLocal with virtual threads?
<details><summary>Show answer</summary>

**Purpose of `ThreadLocal`:** to store and manage data that is accessible only by a specific, individual thread.

**The hazards with virtual threads:**

- **Memory bloat:** `ThreadLocal` assumes a small number of long-lived threads (like a platform pool). With millions
  of short-lived virtual threads, it creates millions of object copies, causing severe memory exhaustion and GC strain.
- **Inheritance bugs:** virtual threads inherit `InheritableThreadLocal` values from their parent thread. In massive
  concurrency, this unintended inheritance can easily leak sensitive context (like user sessions or security tokens)
  across thousands of tasks, causing subtle and hard-to-trace bugs.

**Alternative:** `ScopedValue`, a read-only value bound for one call. Child tasks see it without a copy, and it's
gone when the call ends.

</details>

### What decides the cost of get() on a virtual-thread task?
<details><summary>Show answer</summary>

**Before:** `future.get()` on a platform thread held its OS thread idle until the result was ready.
OS threads are few, so code avoided waiting and chained callbacks instead (`thenCombine`, `allOf`).
That scales, but the logic is split across callbacks and is hard to read and debug.

**Now:** start the tasks on virtual threads and wait for each result in plain order:

```java
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  Future<User> user = ex.submit(() -> users.find(id));
  Future<Order> order = ex.submit(() -> orders.last(id)); // both calls run at once
  return new Page(user.get(), order.get()); // cheap wait only if this code runs on a virtual thread
}
```

What the wait costs depends on the thread running this code, the same rule as for
[`join()`](6.7_Virtual_Threads.md#joining-a-virtual-thread):
- **Virtual thread** (e.g. the server runs each request on its own virtual thread): each `get()` takes it off its
  carrier while it waits. Waiting is cheap.
- **Platform thread** (`main`, a classic request pool): the two tasks still run at once, but each `get()` keeps the
  caller's OS thread idle, as before. Threads are saved for the tasks, not for the caller: the request pool is still
  the cap.

Inside each task, what the call itself costs depends on
[how the client waits for the reply](#virtual-threads-calling-a-networkdb-client).

When this code runs on a virtual thread, waiting is cheap, so you wait for results instead of chaining callbacks.

</details>

### Several parallel calls, one fails — what happens?
<details><summary>Show answer</summary>

The caller waits for the slowest task, even if the fastest one fails immediately.

```java
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  Future<User> user = ex.submit(() -> users.find(id));     // fails after 10 ms
  Future<Order> order = ex.submit(() -> orders.last(id));  // takes 5 s
  return new Page(user.get(), order.get());                // user.get() throws at 10 ms
}                                                          // close() waits 5 s for order
```

**The Trap:** `user.get()` throws at 10 ms and aborts the `try` block. But the implicit `close()` on the executor
blocks until every submitted task finishes. Nobody cancels `order`, so the parent thread freezes for the full 5 seconds
just to propagate an error that happened instantly. You lose both response time and the resources wasted on the
orphaned task.

**The Fix:** tie the tasks' lifetimes together so one failure cancels the rest.
- **By hand:** use
  [`ExecutorCompletionService` plus `cancel(true)`](../4_Structuring_Concurrent_Tasks/4.7_Task_Hierarchies.md#fail-fast-wait-for-all-tasks--how).
- **Modern Java (preview):** `StructuredTaskScope` (structured concurrency) handles this natively, automatically
  canceling sibling tasks on the first failure.

An executor starts tasks but doesn't manage their relationships. One failing doesn't stop the others.

</details>

### Do virtual threads replace reactive code?
<details><summary>Show answer</summary>

```java
// reactive: returns at once, the next step is a callback
CompletableFuture<Page> page = users.findAsync(id).thenCombine(orders.lastAsync(id), Page::new);

// virtual thread: plain blocking code
Future<User> user = ex.submit(() -> users.find(id));
Future<Order> order = ex.submit(() -> orders.last(id));
Page page = new Page(user.get(), order.get());  // run by a virtual thread: waits off the carrier
```

Neither holds an OS thread while waiting. They differ in who keeps track of where you were:
- **Virtual threads, the JVM:** the stack waits on the heap. Loops, `try`/`catch`, stack traces and blocking libraries
  (JDBC) work as usual.
- **Reactive, your code:** the next step is a callback. Logic is split across lambdas, errors go through operators,
  stack traces show pool threads, and every call in the chain must be non-blocking.

Where reactive still wins:
- **Streams with backpressure:** the consumer slows the producer down.
- **An existing event-loop stack** (WebFlux, Netty): nothing may block there.
- **Huge numbers of idle connections** (WebSockets): callbacks can use less memory than parked stacks. Measure first.

For plain request/response, virtual threads give reactive's scaling with blocking code; reactive stays for streams.

</details>

### Monitoring virtual threads — which tools?
<details><summary>Show answer</summary>

- **Java Flight Recorder - JFR (main tool):** has virtual-thread events, most importantly `jdk.VirtualThreadPinned`,
  which shows when and where a thread couldn't leave its carrier.
- **New thread dump:** `jcmd <pid> Thread.dump_to_file -format=json <file>` includes virtual threads, grouped by the
  executor that owns them.
- **Pinning trace:** `-Djdk.tracePinnedThreads=full` prints a stack trace when a pinned thread blocks.
  The flag exists only on JDK 21–23; on 24+, use the JFR event above.
- **Thread-locals:** `-Djdk.traceVirtualThreadLocals` prints a stack trace each time a virtual thread sets a
  thread-local value, including the ones inside libraries.
- **Carrier health:** CPU use, busy carriers and queued virtual threads (JMX `VirtualThreadSchedulerMXBean`, JDK 24+).
  All carriers busy with a growing queue means starvation.
- **Downstream pressure:** waits at the limit (pool connection, semaphore permit), plus downstream latency and errors.

**Traps:**
- Old tools skip virtual threads: `jstack`, `Thread.getAllStackTraces()` and `ThreadMXBean` show only platform threads.
- Thread count is no longer a load signal. Don't track millions of threads; watch the carriers, pinning events and
  waits at the limits.

</details>
