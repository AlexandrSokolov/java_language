### What do virtual threads change for JDBC and JPA?
<details><summary>Show answer</summary>

The code stays blocking; the waiting becomes cheap.

```java
@Transactional
public OrderDto order(long id) {                       // runs on the request's virtual thread
  Order order = orderRepo.findById(id).orElseThrow();  // blocks: the virtual thread leaves its OS thread
  return OrderDto.of(order, order.getItems());         // lazy loading blocks again, just as cheaply
}
```

**What changes:** when a virtual thread blocks on socket I/O, the JDK takes it off its OS thread (the carrier), and the
carrier runs other virtual threads meanwhile. Underneath, the JDK uses the same machinery as non-blocking servers
([non-blocking sockets and a poller](todo)), hidden from your code.

**What you keep:**
- **JDBC, JPA, Hibernate, and lazy loading, unchanged.** No non-blocking drivers, no new data layer.
- **Thread-bound context.** Each request runs on one virtual thread from start to end, with no hop to another pool, so
  `@Transactional`, the security context, and the MDC work as before. With futures they
  [get lost at the hop](6.2_Freeing_the_Request_Thread.md#what-is-lost-when-work-moves-to-another-thread).

**What stays the same:**
- **Downstream limits.** 5,000 virtual threads still share, say, 20 JDBC connections, so most of them wait for a
  connection. Waiting is cheap, but the DB is still the cap. Limit each dependency with its connection pool or a
  `Semaphore`.

**What can hold the OS thread after all (pinning):**
- Blocking inside a `synchronized` block, up to JDK 23. Older JDBC drivers and libraries use `synchronized` a lot. Fixed
  in JDK 24.
- Native code (JNI), such as a driver with a native part.

**What costs more:**
- **`ThreadLocal` caches.** Code that caches expensive objects per thread now creates one per virtual thread, which can
  mean millions of them.
- **Drivers that bypass JDK sockets.** Most pure-Java drivers do their I/O through JDK sockets and are fine; a driver
  that doesn't keeps its OS thread while it waits.

Virtual threads keep the code blocking and make the wait cheap; the downstream limits and the pinning cases remain.
