### Why were virtual threads created?
<details><summary>Show answer</summary>

With platform threads, every **blocking IO call** (to a database or another service) holds an OS thread that does
nothing while it waits. Only a few thousand OS threads fit, so the app runs out of threads while the CPU sits idle.
Async code avoids this, but it's hard to write and debug.

A virtual thread frees its carrier when it [blocks](#blocking-call--platform-vs-virtual-thread), so simple blocking
code scales to millions of IO calls at once.

</details>

### What is a virtual thread?
<details><summary>Show answer</summary>

A lightweight thread managed by the JVM, not by the OS.

- **Platform thread:** a thin wrapper around one OS thread (1:1). The OS creates it and schedules it.
- **Virtual thread:** a plain Java object on the heap. The JVM schedules it on a few **carrier threads**, which are
  platform threads from a dedicated `ForkJoinPool` (not the common pool). The OS sees only the carriers.

</details>

### Common pool vs virtual thread scheduler?
<details><summary>Show answer</summary>

Both are work-stealing `ForkJoinPool`s. They differ in the order a worker takes tasks from its own queue.

- **Common pool.** Runs parallel streams. A worker takes its own tasks newest first (LIFO). A task splits into pieces
  and waits for them, so the worker handles the newest, smallest piece first.
- **Virtual thread scheduler.** Runs virtual threads on carriers. A worker takes its own tasks oldest first (FIFO).
  Each virtual thread is a separate job, so oldest first stops a flood of new threads from pushing an old one back
  forever.

In both pools, a worker that steals from another worker takes the oldest task.

</details>

### How is scheduler parallelism set?
<details><summary>Show answer</summary>

**Scheduler parallelism** is the number of carrier threads, 
so it's the most virtual threads that can run at the same moment, not how many can exist.

**Default:** one carrier thread per available processor, meaning `Runtime.getRuntime().availableProcessors()`. That
counts the logical CPUs the JVM may use, not physical chips. With hyper-threading, 8 cores count as 16.

**In a managed runtime:** an app server or a container platform owns the JVM startup and the CPU limits, so it decides
this value. Check its documentation first.

**Last resort, setting it yourself:** use the system property `jdk.virtualThreadScheduler.parallelism`. The scheduler
reads it once, when it starts, so it must be set before the first virtual thread is created:

</details>

### Blocking call — platform vs virtual thread?
<details><summary>Show answer</summary>

On a blocking call, such as a network read or `sleep`:

- **Platform thread:** its OS thread sits idle until the call returns.
- **Virtual thread:** the JVM takes it off its [carrier](#what-is-a-virtual-thread), and the carrier runs another
  virtual thread. When the call returns, the virtual thread continues on any free carrier.

</details>

### Switching to virtual threads — what changes?
<details><summary>Show answer</summary>

Only how threads are created. The code that runs on them stays the same:

```java
ExecutorService ex = Executors.newFixedThreadPool(200);           // before
ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor();  // after
```

**Trap:** the fixed pool also capped how many tasks ran at once, for example 200 database calls. 
The virtual executor has no cap, so 10,000 tasks hit the database together. 
Keep the cap with a `Semaphore`, not by pooling virtual threads.

</details>

### How do you create a virtual thread?
<details><summary>Show answer</summary>

Every way returns a plain `Thread` with the same API as before (`join()`, `interrupt()`):

```java
Thread.ofPlatform().start(task);     // platform thread
Thread.ofVirtual().start(task);      // virtual: same builder, same Thread type

Thread.startVirtualThread(task);     // shortcut
Thread.ofVirtual().unstarted(task);  // create now, start() later

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
  ex.submit(task);                   // one new virtual thread per task
}                                    // close() waits for all tasks
```

</details>

### How do you stop a virtual thread?
<details><summary>Show answer</summary>

**Trap:** the JVM schedules virtual threads, but it doesn't stop them for you. It works the same as with platform threads.
You call `interrupt()`, which only sets a flag, and the thread's own code must react to it:

```java
Thread t = Thread.ofVirtual().start(() -> {
  while (!Thread.currentThread().isInterrupted()) {
    // work
  }
});
t.interrupt();  // sets the flag; the loop above decides to exit
```

If the thread is blocked in `sleep()`, `join()` or `wait()`, that call throws `InterruptedException` instead.

</details>

### How do you manage thread groups for virtual threads?
<details><summary>Show answer</summary>

You can't. Every virtual thread returns the same placeholder group, `"VirtualThreads"`, from
`getThreadGroup()`, and `Thread.ofVirtual()` has no method to set a different one. The group doesn't track its threads
either, so `activeCount()` and `enumerate()` won't list virtual threads.

</details>

### How do you make a virtual thread a daemon thread?
<details><summary>Show answer</summary>

There's nothing to do. Every virtual thread is always a daemon. 
- `setDaemon(true)` changes nothing, and
- `setDaemon(false)` throws `IllegalArgumentException`.

</details>

### How do you check if a thread is virtual?
<details><summary>Show answer</summary>

Call `isVirtual()` on the `Thread`, for example `Thread.currentThread().isVirtual()`.

</details>

### What are the Duration-based thread methods?
<details><summary>Show answer</summary>

Overloads that take a `Duration` instead of milliseconds. They work on any thread, not only virtual threads:

```java
Thread.sleep(Duration.ofSeconds(2));           // static, like sleep(long)
boolean done = t.join(Duration.ofSeconds(5));  // true if t finished in time
```

</details>

### How do you get a thread's ID?
<details><summary>Show answer</summary>

Use `threadId()`, not `getId()`, which has been deprecated since Java 19. 
`getId()` isn't final, so a subclass can override it and return any number. 
`threadId()` is final, so it always returns the real ID.

</details>

### What happens to the deprecated Thread methods?
<details><summary>Show answer</summary>

`stop()`, `suspend()`, `resume()` and `countStackFrames()` throw `UnsupportedOperationException` since Java 20, for
platform and virtual threads alike. They were unsafe, have been deprecated since Java 1.2, and are scheduled for
removal.

</details>

### How do you get virtual thread stack traces?
<details><summary>Show answer</summary>

Not with `Thread.getAllStackTraces()`, which returns platform threads only and skips virtual ones. 
For one virtual thread, call `getStackTrace()` on its `Thread` object.

</details>

### 10,000 blocking tasks — executor results?
<details><summary>Show answer</summary>

Each task sleeps for 1 second.

- **`newVirtualThreadPerTaskExecutor()`:** all 10,000 start right away, each on its own virtual thread. 
  While blocked, they wait off the carriers, so a few OS threads carry them all. Done in about 1 s.
- **`newCachedThreadPool()`:** all 10,000 start right away, each on its own OS thread. If the OS allows 10,000
  threads, it also finishes in about 1 s. If not, it fails with `OutOfMemoryError`.
- **`newFixedThreadPool(200)`:** limits concurrency to 200 active tasks at a time, forcing the rest into a queue and
  causing severe processing delays: 10,000 / 200 = 50 rounds, about 50 s.

</details>

### How do virtual threads scale?
<details><summary>Show answer</summary>

A blocked virtual thread leaves its carrier and waits as a small object on the heap. Waiting costs no OS thread, so
the number of tasks in progress is no longer capped at the few thousand OS threads a machine can hold.

Little's law ties this to throughput: throughput = tasks in progress / time per task. For tasks that each sleep 1 s
(the ideal case):

- 10,000 virtual threads → about 10,000 tasks per second.
- 1,000,000 virtual threads → about 1,000,000 tasks per second.

Platform threads stop growing at the OS thread limit. Virtual threads keep growing with the number of tasks.

</details>

### How do virtual threads speed up tasks?
<details><summary>Show answer</summary>

They don't. A task takes as long on a virtual thread as on a platform thread. What goes up is
[throughput](#how-do-virtual-threads-scale): more tasks are in progress at once, so more of them finish per second.

</details>

### Which tasks benefit most from virtual threads?
<details><summary>Show answer</summary>

Tasks that mostly wait on IO, when there are thousands or more of them at once:

- a server handling many requests at the same time, each on its own thread;
- code making many calls in parallel to databases, other services or message brokers.

CPU-bound tasks gain nothing, because only as many run at once as there are carriers.

</details>

### Where do virtual threads give little?
<details><summary>Show answer</summary>

- **CPU-bound work** (heavy computing, image processing): only as many run at once as there are carriers, the same
  as a platform pool sized to the CPUs.
- **A few hundred tasks at once:** a platform pool already fits them.
- **A downstream limit:** with 50 database connections, only 50 queries run at once, no matter how many threads wait.
- **Calls that hold the carrier while blocked:** native calls, and file IO on most systems.

</details>

### What is Little's law?
<details><summary>Show answer</summary>

In a stable system, on average:

**throughput = concurrency / response time** (λ = N / d)

- **Throughput (λ):** tasks finished per unit of time.
- **Concurrency (N):** tasks in progress at the same moment.
- **Response time (d):** time for one task, from start to finish.

Example: 200 threads and 1 s per task give 200 tasks per second.

The law doesn't care whether the time is spent working or waiting, or what does the work: a thread, a CPU core or a
bank teller. So when response time is fixed, the only way to raise throughput is to
[raise concurrency](#how-do-virtual-threads-scale).

</details>

### How does Little's law explain virtual threads?
<details><summary>Show answer</summary>

[Little's law](#what-is-littles-law) (throughput = N / d) gives two ways to raise throughput: raise N (tasks in
progress) or cut d (time per task).

**Traditional threads hit a wall.** N stops at the OS thread limit, a few thousand. The only lever left is d, and for IO
tasks d is mostly the database's or the remote service's time, so it's out of your hands. Throughput is stuck.
With platform threads, throughput can improve with larger thread pools, but there’s a limit. 
Eventually, OS resources will be constrained, and thread management overhead becomes the bottleneck

**Virtual threads remove the wall.** N can grow to millions with the same blocking code, so throughput grows with it
while d stays the same.

</details>
