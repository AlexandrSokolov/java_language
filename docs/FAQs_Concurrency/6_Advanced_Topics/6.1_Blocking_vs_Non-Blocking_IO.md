### How is a blocking request handled?
<details><summary>Show answer</summary>

It uses a thread-per-request model. The server keeps a pool of threads (Tomcat: 200 by default). For each request:

1. A free pool thread takes the request and runs your handler.
2. At each database or API call, the thread waits until the reply comes back. It does nothing, but no other request
   can use it.
3. When the handler returns, the thread writes the response and goes back to the pool.

```java
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {  // runs on one pool thread
  var person = repo.findPerson(id);            // thread waits for the DB
  var assets = assetsApi.fetch(person);        // thread waits for the API
  return calculate(person, assets);            // thread does CPU work
}                                              // response sent, thread back to the pool
```

One request holds one thread from start to finish, waits included.

</details>

### What does a waiting request thread cost?
<details><summary>Show answer</summary>

A waiting thread costs no CPU. It costs:
- **Memory:** each thread reserves about 1 MB for its stack. That is reserved address space; real RAM is used only
  as the stack grows.
- **Concurrency capacity:** while the thread waits on I/O (a DB query, an API call), it stays taken and cannot serve
  other users.

The limit: if 200 users send a slow request at once, all 200 threads are waiting and the pool is empty. Request 201
waits in a queue, even though the CPU is almost idle.

</details>

### All pool threads busy — what happens?
<details><summary>Show answer</summary>

The request is not rejected. It waits, and the waiting happens in three layers (Tomcat defaults):

1. **Worker queue (in the JVM):** Tomcat has accepted the connection, and the request waits in the thread pool's task
   queue until a thread is free. This queue has no size limit of its own.
2. **Connection limit (`maxConnections`, 8,192):** this is what caps the queue. At 8,192 open connections Tomcat stops
   accepting new ones.
3. **OS accept queue (`acceptCount`, 100):** new connections then wait in the kernel. The TCP handshake is done, but
   Tomcat has not picked them up yet. When these 100 places fill, the OS refuses or drops new connections.

So under load a request first gets slower. It fails only at layer 3, or earlier if it waits longer than the client's
timeout.

</details>

### Blocked request threads — what are the fixes?
<details><summary>Show answer</summary>

There are three main approaches to stop wasting OS threads on long waits:

- **Non-blocking I/O (event loops):** the OS thread detaches from the socket during I/O and returns to the pool. The
  OS holds the connection, and an event loop resumes the work when data arrives (e.g., Netty, WebFlux).
- **[Virtual threads](6.3_Virtual_Threads.md) (Java 21+):** you write standard blocking code, but the JVM
  automatically unmounts the lightweight virtual thread from the heavy OS thread during I/O.
- **Asynchronous API (background processing):** change the client contract to decouple the producer from the
  consumer.
    - The server accepts the request, drops the task into a queue/broker, and immediately returns `HTTP 202 Accepted`.
    - The result is delivered later via pull (the client polls a status endpoint), push (webhooks/WebSockets), or not at
      all (fire-and-forget).

</details>

### How is a non-blocking request handled?
<details><summary>Show answer</summary>

It uses an asynchronous pipeline. Threads are decoupled from connections and never wait for I/O.

1. A worker thread accepts the request and runs your handler.
2. At each database or API call, the thread fires the network request, registers a callback, and immediately returns
   to the pool to serve other users.
3. When the network reply arrives, the thread that receives it runs the next step. At the end, the framework writes
   the HTTP response.

    ```java
    @GetMapping("/credit/{id}")
    public CompletableFuture<Credit> credit(@PathVariable Long id) { // Thread A starts
      return repo.findPersonAsync(id)                                // Thread A fires DB call & leaves
          .thenCompose(p -> assetsApi.fetchAsync(p)                  // Thread B gets DB reply, fires API call & leaves
          .thenApply(assets -> calculate(p, assets)));               // Thread C gets API reply, computes
    }                                                                // (The OS keeps the socket open the whole time)
    ```

One request is processed as a sequence of events, handled by potentially multiple different threads, with zero idle
waiting.

</details>

### Does non-blocking make a request faster?
<details><summary>Show answer</summary>

Response time = network + queueing delay (waiting for a thread) + service time (the work, including DB and API waits).

- **Network and service time:** no change. The DB still takes 200 ms and the API another 200 ms. When each call needs
  the previous result, they add up as before.
- **Queueing delay:** shrinks under load. A blocking server with all 200 threads taken makes request 201 wait for a
  free thread; a non-blocking server starts it at once, until the [next limit](todo) (CPU, DB pool) is hit.

So at low load one request is no faster. 
The main gain is **throughput**: the same threads serve many more requests at once. 

</details>

### When does non-blocking pay off?
<details><summary>Show answer</summary>

It pays off when the application is both highly concurrent and I/O-bound:

- **High concurrency:** heavy traffic, or many connections held open for a long time (long polling, slow clients),
  enough to use up a 200-thread pool.
- **I/O-bound:** the request spends most of its time waiting on databases or other services, not using the CPU.

Example: 600 ms waiting, 5 ms CPU. With 200 blocking threads, each request holds a thread for about 605 ms, so the
server tops out near 330 requests/s while the CPU is mostly idle. Non-blocking holds a thread only for the 5 ms, so
8 cores can go up to about 1,600 requests/s.

It does not pay off:

- **CPU-bound work** (image processing, heavy cryptography): a thread busy computing cannot go back to the pool anyway.
  Example: 200 ms of CPU per request, so 8 cores top out at 40 requests/s, long before 200 threads run out. Same if a
  [downstream limit](todo) (e.g. 10 DB connections) is hit first.
- **Low-traffic apps** that never come near the thread limit: async code is harder to write and debug, for no gain.

</details>

### What caps a non-blocking server's load?
<details><summary>Show answer</summary>

When non-blocking I/O stops the server from running out of threads, the limit moves to physical or downstream
resources:

- **Downstream connection pools:** a DB pool with 10 connections still runs only 10 queries at a time. The waiting
  moves from blocked OS threads to an in-memory queue of futures.
- **Downstream services:** the DB or API can handle only so much. More load makes them slower, not faster.
- **CPU:** no longer capped by threads, the server can accept enough requests to push the CPU to 100% just parsing
  HTTP, running callbacks, and executing business logic.
- **Memory and GC:** thousands of waiting requests, with their object graphs and `CompletableFuture` chains, stay alive
  in the heap at once and put heavy pressure on the garbage collector.
- **OS / network limits:** the OS cap on open [file descriptors](todo) (`ulimit`), port exhaustion (no free local ports
  for outgoing connections), or raw network bandwidth.

Non-blocking does not remove the queue. It moves it to the next limit.

</details>

### When does async reduce service time?
<details><summary>Show answer</summary>

Only when independent I/O calls run at the same time.

If a DB query and an API call take 200 ms each and neither needs the other's result:

- **Sequential (blocking or async):** the DB call finishes (200 ms), then the API call starts (200 ms). Service time
  = 400 ms.
- **Concurrent:** both calls start at once, their waits overlap, and service time drops to the slowest call: ~200 ms.

```java
CompletableFuture<Credit> credit(Person p) {
  return getAssetsAsync(p)                                    // call 1 starts
      .thenCombine(getLiabilitiesAsync(p), this::calculate); // call 2 starts too; both run at once
}
```

The tools: `CompletableFuture.thenCombine()` for async code, or `StructuredTaskScope` on virtual threads for blocking
code. Calls that depend on each other still add up.

</details>

### Async vs concurrent — same thing?
<details><summary>Show answer</summary>

No. They answer different questions:

- **Async:** does the thread wait for the call? No. It moves on, and a callback runs when the reply arrives.
- **Concurrent:** do the calls overlap in time? Yes, when both are started before waiting on either.

Each can exist without the other:

|              | Sequential                                 | Concurrent                                            |
|--------------|--------------------------------------------|-------------------------------------------------------|
| **Blocking** | call, wait, call, wait                     | 2 threads (`ExecutorService` / `StructuredTaskScope`) |
| **Async**    | `thenCompose`: calls run one after another | `thenCombine` / `allOf`: calls in flight at once      |

```java
getPersonAsync(id).thenCompose(p -> getAssetsAsync(p));                  // async, sequential
getAssetsAsync(p).thenCombine(getLiabilitiesAsync(p), this::calculate);  // async, concurrent
```

**Async saves threads. Concurrency saves time.**

</details>

### Must a synchronous REST call hold a thread?
<details><summary>Show answer</summary>

No. "Synchronous" describes the client: it sends a request and waits on the same connection for the answer. 
The server does not need an OS thread to wait with it:

- **Client side:** the client waits on an open connection. The OS holds that connection, and keeping it open costs
  almost nothing.
- **Server side:** the thread fires its I/O calls and goes back to the pool. When the result is ready, a thread writes
  the response to the still-open connection.

The client cannot tell the difference: same call, same response, same wait.

Whether an OS thread is held:

- **Held:** platform thread, handler returns the plain result (`Credit`). The thread must wait to get it.
- **Not held:** platform thread, handler returns `CompletableFuture<Credit>`. The thread goes back to the pool at once,
  and the [framework – Spring MVC or the JAX-RS runtime – ](todo) writes the response when the future completes.
- **Not held:** virtual thread, handler returns plain `Credit`. 
  The [virtual thread](6.3_Virtual_Threads.md) waits, but not on an OS thread.

The client waits; an OS thread does not have to.

</details>

### Where must an async chain end?
<details><summary>Show answer</summary>

At the web framework (Spring MVC, Spring WebFlux, or the JAX-RS runtime). The handler returns the future itself,
untouched. The framework frees the thread and registers its own callback to write the response when the future
completes.

```java
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();  // thread waits here: the non-blocking gain is lost
}

@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);         // thread returns at once; Spring writes the response later
}
```

A `join()` or `get()` anywhere on the way (in a service, a helper, or the controller) makes a platform thread wait
right there, and the non-blocking pipeline turns back into a blocking one. On virtual threads, `join()` does not hold
an OS thread, but then the async chain is not needed at all.

Never unwrap the future yourself. Every layer passes it up to the framework.

</details>

### How does a REST method free its thread?
<details><summary>Show answer</summary>

By returning control to the framework before the I/O is finished: the method returns a future
(`CompletableFuture<Credit>`) instead of the plain `Credit`.

1. **Return immediately:** the worker thread hands the future to the framework and goes straight back to the pool.
2. **Suspend the request:** the framework keeps the client's connection open, but no thread is tied to it (on a
   servlet container: `request.startAsync()`).
3. **Resume and write:** when the future completes, the framework's callback fires, and an available thread, possibly
   a different one, writes the response.

```java
@GET @Path("/credit/{id}")
public CompletionStage<Credit> credit(@PathParam("id") Long id) {
  return service.calculateCredit(id);  // thread returns at once; the runtime writes the response later
}
```

`CompletableFuture<T>` works in all the major frameworks, since each accepts a `CompletionStage<T>`:

- **Spring MVC** and **Spring WebFlux:** return `CompletableFuture<T>`.
- **Jakarta REST (2.1+):** declare `CompletionStage<T>` as the return type and return a `CompletableFuture` from it.

Each also has a native type: `DeferredResult<T>` (Spring MVC), `Mono<T>` (WebFlux), `@Suspended AsyncResponse`
(Jakarta REST).

With [virtual threads](6.3_Virtual_Threads.md), none of this is needed: the JVM unmounts the virtual thread at the I/O
call, so the method can return a plain `Credit` without holding an OS thread.

</details>



### Async API vs non-blocking server?
<details><summary>Show answer</summary>

They solve different problems: one changes the HTTP contract, the other changes the server's thread model.

- **Async API (the HTTP contract):** the client sends a request and does not wait for the result. The server
  immediately returns `HTTP 202 Accepted` with a job ID, and the call is over. The client polls later or receives a
  webhook.
  Use case: long-running business tasks (e.g., generating a PDF report, processing video).
- **Non-blocking server (the internal architecture):** the client does wait on an open HTTP connection for the final
  `HTTP 200 OK`. Under the hood, the server frees its OS thread to the pool while waiting for the DB or downstream
  services.
  Use case: highly concurrent, standard CRUD or microservice calls.

An async API breaks the HTTP wait. A non-blocking server breaks the thread wait.

</details>

### Blocking call in `supplyAsync` — any gain?
<details><summary>Show answer</summary>

No thread is saved. You just **move the block** from one thread pool to another.

```java
public CompletableFuture<Person> findPersonAsync(Long id) {
  return CompletableFuture.supplyAsync(() -> jdbcRepo.findPerson(id), dbPool);  // a dbPool thread waits here
}
```

- **The web thread is freed:** it returns at once and can take new requests, as long as the future
  [reaches the framework](todo).
- **A background thread is blocked:** a `dbPool` thread sits idle for the full DB wait. 200 waiting requests still hold
  200 threads, now in `dbPool`.

**The danger:** without the second argument, the task runs on `ForkJoinPool.commonPool()`, which is sized for CPU work
(cores − 1). A few slow queries take all of it, and every other `supplyAsync` and parallel stream in the JVM freezes
too.

**Valid uses:**
- **Bulkhead (keep a failure inside one pool):** a dedicated pool for a legacy blocking API, e.g. 50 threads just for
  the DB. If the DB slows down, only those 50 threads get stuck; the web threads stay alive.
- **Concurrency:** running two independent blocking calls at the same time.

To actually save threads, you need a non-blocking driver (R2DBC, an async HTTP client) built on non-blocking sockets,
so no thread waits.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// service.calculateCredit(id) returns CompletableFuture<Credit>, built on non-blocking drivers
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {
  return service.calculateCredit(id).join();
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `join()` blocks the Tomcat thread until the whole chain finishes. The async service and the non-blocking
drivers buy nothing: each request still holds a platform thread for its full duration, and under load the pool empties
exactly as with plain blocking code, now with async code to maintain on top.

**Fix:** return the future and let Spring write the response.

```java
@GetMapping("/credit/{id}")
public CompletableFuture<Credit> credit(@PathVariable Long id) {
  return service.calculateCredit(id);  // thread goes back to the pool at once
}
```

**Where it matters:** only on platform threads. On virtual threads (`spring.threads.virtual.enabled=true`), `join()`
parks the virtual thread and frees its OS thread, but then the async chain is not needed at all.

An async chain frees threads only if nobody waits on it.

</details>

</details>

### Describe a code snippet #2
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Person> findPersonAsync(Long id) {
  return CompletableFuture.supplyAsync(() -> personDao.findById(id));  // personDao uses plain JDBC
}
```

</details>

<details><summary>Show answer</summary>

**Defect 1 (nothing becomes non-blocking):** `findById` still blocks on JDBC. A thread still waits for the full DB
call; it is just a common-pool thread instead of the request thread.

**Defect 2 (the wait lands in the common pool):** with no executor argument, `supplyAsync` uses
`ForkJoinPool.commonPool()`, which is sized for CPU work (cores − 1). A handful of slow queries fill it, and every other
`supplyAsync` and parallel stream in the JVM stalls behind them.

**Minimal fix (a dedicated pool):** keeps the damage inside one pool (bulkhead). Still blocking: one thread per
waiting query.

```java
return CompletableFuture.supplyAsync(() -> personDao.findById(id), dbPool);
```

**Rewrite (a non-blocking driver such as R2DBC):** no thread waits. Only this one actually saves threads.

**Where it matters:** if the common pool's parallelism is below 2 (a 1–2 core machine), `CompletableFuture` starts a
new thread per task instead. Then nothing freezes, but there is no limit on threads either.

Wrapping a blocking call moves the wait to another thread; it does not remove it.

</details>

### Describe a code snippet #3
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
// asyncClient: Netty-based HTTP client
@GetMapping("/report/{id}")
public CompletableFuture<Report> report(@PathVariable Long id) {
  return asyncClient.fetchAsync(id)
      .thenApply(data -> renderPdf(data));  // ~300 ms of CPU
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** a plain `thenApply` runs on the thread that completed the future: here, a Netty event-loop thread. That
thread serves many connections. For the 300 ms of `renderPdf`, every connection on that loop stalls: other requests'
replies, reads, and writes all wait. There is no error and no warning; unrelated requests just get slow, and some time
out.

**Fix:** move the CPU work to a CPU pool.

```java
return asyncClient.fetchAsync(id)
    .thenApplyAsync(data -> renderPdf(data), cpuPool);  // CPU work leaves the event loop
```

**Where it matters:** the stage runs on the event loop only if the future is still pending when `thenApply` is
attached. That is the usual case, since the reply comes later. If the future is already complete, the calling thread
runs the stage instead.

An event-loop thread serves many connections; anything slow on it stalls all of them.

</details>

### Describe a code snippet #4
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Credit> credit(Person p) {
  return getAssetsAsync(p)
      .thenCompose(assets -> getLiabilitiesAsync(p)
          .thenApply(liabilities -> calculate(assets, liabilities)));
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `getLiabilitiesAsync(p)` does not use `assets`, but it starts only after the assets reply arrives. The two
calls run one after another: 400 ms instead of 200 ms. No thread is wasted and the result is correct; the request is
just twice as slow as it needs to be.

**Fix:** start both calls at once and join the results.

```java
return getAssetsAsync(p)
    .thenCombine(getLiabilitiesAsync(p), this::calculate);  // both calls start now
```

**Where it matters:** only for calls that do not need each other's result. When the second call needs the first
result, `thenCompose` is the right tool. The full gain also assumes the downstream can take both calls at once (e.g., a
free DB connection for each).

Async is not concurrent: `thenCompose` waits for one result before it starts the next call.

</details>

### Credit endpoint — 5,000 requests at once
<details><summary><strong>Show details</strong></summary>

<details><summary>Show scenario</summary>

A Spring Boot credit service (MVC on Tomcat) runs on Java 21 with 8 cores. Each request:

1. loads the person from the DB (~5 ms),
2. calls a partner credit-bureau API with the person (~1 s),
3. loads the person's liabilities from the DB (~5 ms),
4. computes the credit (~1 ms of CPU).

Today: plain blocking code, 200 Tomcat threads, a JDBC pool of 100. A campaign is coming: up to 5,000 requests in
flight at once, each answered in under 2 s. A load test at 1,000 in flight already shows ~5 s response times, while the
CPU stays under 5%.

What do you change, and why?

</details>

<details><summary>Show answer</summary>

**Clarifying questions (the numbers answer most of them):**
- **Where does the time go?** About 1 s waiting and 1 ms of CPU. The CPU is idle, so threads run out, not CPU. 200
  threads × ~1 s each ≈ 200 requests/s; the other 800 wait in the queue for ~4 s.
- **Can the downstream take 5,000 in flight?** That is ~4,950 requests/s. DB: 2 queries × 5 ms ≈ 50 busy
  connections, so the pool of 100 fits. CPU: ~5 of 8 cores, which fits. Partner API: it must accept ~5,000 calls at
  once, and so must your local HTTP client's connection pool. If that pool is capped at 100 connections, 4,900
  requests just wait for a free connection, and the 2 s target is lost. Confirm this first, or nothing below helps.
- **Must the client get the credit in the same call?** Yes, in under 2 s, so keep the synchronous contract.

**Options:**
1. **Bad: raise `maxThreads` to 5,000.** 5,000 OS threads means ~5 GB of reserved stack and heavy OS scheduling. It
   pays for the waiting instead of removing it, and the next growth needs even more threads.
2. **Bad: wrap the calls in `supplyAsync`.** The wait only moves to another pool. You still have ~5,000 blocked threads,
   or a frozen common pool.
3. **Bad here: async API (`202` + polling).** It changes the contract for every client, and it is not needed when the
   answer fits in 2 s.
4. **Works, but costly: non-blocking rewrite** (`CompletableFuture` or WebFlux, R2DBC, a non-blocking HTTP client).
    - **Buys:** a few threads carry 5,000 waits; works on any Java version; supports back-pressure and streaming.
    - **Costs:** every layer is rewritten (drivers, transactions, error handling), stack traces become harder to read,
      and the team must learn the style.
5. **Right: virtual threads.** Set `spring.threads.virtual.enabled=true` (Spring Boot 3.2+) and keep the code as is.
   Each waiting request costs a small heap object instead of an OS thread. Tomcat's default `maxConnections` (8,192)
   already covers 5,000 open connections; virtual threads remove the need for 5,000 matching OS threads. One check on
   Java 21: `synchronized` around blocking I/O pins the OS thread (fixed in JDK 24).

**The test that decides:** find what runs out first. Here it is threads (waits dominate, CPU idle), and the code is
blocking on Java 21, so virtual threads free the threads without a rewrite. On older Java, or when you need streaming
and back-pressure, use the non-blocking rewrite. If the partner or the DB runs out first, fix that instead (limits,
caching, or an async API); no thread model helps there.

</details>

</details>
