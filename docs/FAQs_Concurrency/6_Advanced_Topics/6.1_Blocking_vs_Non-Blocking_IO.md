## The model: what a waiting thread costs and what non-blocking buys

### What governs blocking vs non-blocking I/O?
<details><summary>Show answer</summary>

A request thread that calls a DB or an API waits, doing nothing, until the reply comes back. 
Everything here follows from that wait.

In this file:
- **The cost:** a [waiting thread](#what-does-a-waiting-request-thread-cost) is one of a small pool, so the pool size
  caps how many requests can wait at once.
- **The ways out:** [three fixes](#blocked-request-threads--what-are-the-fixes): non-blocking I/O, virtual threads,
  or an async API.
- **What non-blocking buys:** [throughput, not speed](#does-non-blocking-make-a-request-faster). One request gets
  faster only when independent calls [overlap](#async-vs-concurrent--same-thing).

The next files, each one step further:
- **Free the request thread** ([6.2](6.2_Freeing_the_Request_Thread.md#must-a-synchronous-rest-call-hold-a-thread)):
  return a future to the framework. The waits behind it move to your own pools, isolated but still there.
- **Free every thread** ([6.3](todo)): non-blocking DB and HTTP clients, so no thread waits anywhere, at the price of
  replacing JDBC, JPA, and thread-bound context.
- **Who waits instead** ([6.4](todo)): the kernel holds the sockets, and an event loop wakes when data arrives.

The other way out: [virtual threads](todo) keep the blocking code and make the wait cheap.

Trigger: *a waiting thread is the cost → return a future to free the request thread → the waits move to your pools →
non-blocking clients free every thread → the kernel does the waiting.*

</details>

### How is a blocking request handled?
<details><summary>Show answer</summary>

It uses a thread-per-request model. The server keeps a pool of threads (Tomcat: 200 by default). For each request:

1. A free pool thread takes the request and runs your handler.
2. At each database or API call, the thread waits until the reply comes back. It does nothing, but no other request
   can use it.
3. When the handler returns, the thread writes the response and goes back to the pool.

```java
@GetMapping("/credit/{id}")
public Credit credit(@PathVariable Long id) {  // runs on one pool thread
  var person = repo.findPerson(id);            // thread waits for the DB
  var assets = assetsApi.fetch(person);        // thread waits for the API
  return calculate(person, assets);            // thread does CPU work
}                                              // response sent, thread back to the pool
```

One request holds one thread from start to finish, waits included.

</details>

### What does a waiting request thread cost?
<details><summary>Show answer</summary>

A waiting thread costs no CPU. It costs:
- **Memory:** each thread reserves about 1 MB for its stack. That is reserved address space; real RAM is used only
  as the stack grows.
- **Concurrency capacity:** while the thread waits on I/O (a DB query, an API call), it stays taken and cannot serve
  other users.

The limit: if 200 users send a slow request at once, all 200 threads are waiting and the pool is empty. Request 201
waits in a queue, even though the CPU is almost idle.

</details>

### All pool threads busy — what happens?
<details><summary>Show answer</summary>

The request is not rejected. It waits, and the waiting happens in three layers (Tomcat defaults):

1. **Worker queue (in the JVM):** Tomcat has accepted the connection, and the request waits in the thread pool's task
   queue until a thread is free. This queue has no size limit of its own.
2. **Connection limit (`maxConnections`, 8,192):** this is what caps the queue. At 8,192 open connections Tomcat stops
   accepting new ones.
3. **OS accept queue (`acceptCount`, 100):** new connections then wait in the kernel. The TCP handshake is done, but
   Tomcat has not picked them up yet. When these 100 places fill, the OS refuses or drops new connections.

So under load a request first gets slower. It fails only at layer 3, or earlier if it waits longer than the client's
timeout.

</details>

### Blocked request threads — what are the fixes?
<details><summary>Show answer</summary>

There are three main approaches to stop wasting OS threads on long waits:

- **Non-blocking I/O (event loops):** the OS thread detaches from the socket during I/O and returns to the pool. The
  OS holds the connection, and an event loop resumes the work when data arrives (e.g., Netty, WebFlux).
- **[Virtual threads](6.3_Virtual_Threads.md) (Java 21+):** you write standard blocking code, but the JVM
  automatically unmounts the lightweight virtual thread from the heavy OS thread during I/O.
- **Asynchronous API (background processing):** change the client contract to decouple the producer from the
  consumer.
    - The server accepts the request, drops the task into a queue/broker, and immediately returns `HTTP 202 Accepted`.
    - The result is delivered later via pull (the client polls a status endpoint), push (webhooks/WebSockets), or not at
      all (fire-and-forget).

</details>

### Async API vs non-blocking server?
<details><summary>Show answer</summary>

They solve different problems: one changes the HTTP contract, the other changes the server's thread model.

- **Async API (the HTTP contract):** the client sends a request and does not wait for the result. The server
  immediately returns `HTTP 202 Accepted` with a job ID, and the call is over. The client polls later or receives a
  webhook.
  Use case: long-running business tasks (e.g., generating a PDF report, processing video).
- **Non-blocking server (the internal architecture):** the client does wait on an open HTTP connection for the final
  `HTTP 200 OK`. Under the hood, the server frees its OS thread to the pool while waiting for the DB or downstream
  services.
  Use case: highly concurrent, standard CRUD or microservice calls.

An async API breaks the HTTP wait. A non-blocking server breaks the thread wait.

</details>

### How is a non-blocking request handled?
<details><summary>Show answer</summary>

It uses an asynchronous pipeline. Threads are decoupled from connections and never wait for I/O.

1. A worker thread accepts the request and runs your handler.
2. At each database or API call, the thread fires the network request, registers a callback, and immediately returns
   to the pool to serve other users.
3. When the network reply arrives, the thread that receives it runs the next step. At the end, the framework writes
   the HTTP response.

    ```java
    @GetMapping("/credit/{id}")
    public CompletableFuture<Credit> credit(@PathVariable Long id) { // Thread A starts
      return repo.findPersonAsync(id)                                // Thread A fires DB call & leaves
          .thenCompose(p -> assetsApi.fetchAsync(p)                  // Thread B gets DB reply, fires API call & leaves
          .thenApply(assets -> calculate(p, assets)));               // Thread C gets API reply, computes
    }                                                                // (The OS keeps the socket open the whole time)
    ```

One request is processed as a sequence of events, handled by potentially multiple different threads, with zero idle
waiting.

</details>

### Does non-blocking make a request faster?
<details><summary>Show answer</summary>

Response time = network + queueing delay (waiting for a thread) + service time (the work, including DB and API waits).

- **Network and service time:** no change. The DB still takes 200 ms and the API another 200 ms. When each call needs
  the previous result, they add up as before.
- **Queueing delay:** shrinks under load. A blocking server with all 200 threads taken makes request 201 wait for a
  free thread; a non-blocking server starts it at once, until the [next limit](todo) (CPU, DB pool) is hit.

So at low load one request is no faster. 
The main gain is **throughput**: the same threads serve many more requests at once. 

</details>

### When does non-blocking pay off?
<details><summary>Show answer</summary>

It pays off when the application is both highly concurrent and I/O-bound:

- **High concurrency:** heavy traffic, or many connections held open for a long time (long polling, slow clients),
  enough to use up a 200-thread pool.
- **I/O-bound:** the request spends most of its time waiting on databases or other services, not using the CPU.

Example: 600 ms waiting, 5 ms CPU. With 200 blocking threads, each request holds a thread for about 605 ms, so the
server tops out near 330 requests/s while the CPU is mostly idle. Non-blocking holds a thread only for the 5 ms, so
8 cores can go up to about 1,600 requests/s.

It does not pay off:

- **CPU-bound work** (image processing, heavy cryptography): a thread busy computing cannot go back to the pool anyway.
  Example: 200 ms of CPU per request, so 8 cores top out at 40 requests/s, long before 200 threads run out. Same if a
  [downstream limit](todo) (e.g. 10 DB connections) is hit first.
- **Low-traffic apps** that never come near the thread limit: async code is harder to write and debug, for no gain.

</details>

### What caps a non-blocking server's load?
<details><summary>Show answer</summary>

When non-blocking I/O stops the server from running out of threads, the limit moves to physical or downstream
resources:

- **Downstream connection pools:** a DB pool with 10 connections still runs only 10 queries at a time. The waiting
  moves from blocked OS threads to an in-memory queue of futures.
- **Downstream services:** the DB or API can handle only so much. More load makes them slower, not faster.
- **CPU:** no longer capped by threads, the server can accept enough requests to push the CPU to 100% just parsing
  HTTP, running callbacks, and executing business logic.
- **Memory and GC:** thousands of waiting requests, with their object graphs and `CompletableFuture` chains, stay alive
  in the heap at once and put heavy pressure on the garbage collector.
- **OS / network limits:** the OS cap on open [file descriptors](todo) (`ulimit`), port exhaustion (no free local ports
  for outgoing connections), or raw network bandwidth.

Non-blocking does not remove the queue. It moves it to the next limit.

</details>

### Async vs concurrent — same thing?
<details><summary>Show answer</summary>

No. They answer different questions:

- **Async:** does the thread wait for the call? No. It moves on, and a callback runs when the reply arrives.
- **Concurrent:** do the calls overlap in time? Yes, when both are started before waiting on either.

Each can exist without the other:

|              | Sequential                                 | Concurrent                                            |
|--------------|--------------------------------------------|-------------------------------------------------------|
| **Blocking** | call, wait, call, wait                     | 2 threads (`ExecutorService` / `StructuredTaskScope`) |
| **Async**    | `thenCompose`: calls run one after another | `thenCombine` / `allOf`: calls in flight at once      |

```java
getPersonAsync(id).thenCompose(p -> getAssetsAsync(p));                  // async, sequential
getAssetsAsync(p).thenCombine(getLiabilitiesAsync(p), this::calculate);  // async, concurrent
```

**Async saves threads. Concurrency saves time.**

</details>

### When does async reduce service time?
<details><summary>Show answer</summary>

Only when independent I/O calls run at the same time.

If a DB query and an API call take 200 ms each and neither needs the other's result:

- **Sequential (blocking or async):** the DB call finishes (200 ms), then the API call starts (200 ms). Service time
  = 400 ms.
- **Concurrent:** both calls start at once, their waits overlap, and service time drops to the slowest call: ~200 ms.

```java
CompletableFuture<Credit> credit(Person p) {
  return getAssetsAsync(p)                                    // call 1 starts
      .thenCombine(getLiabilitiesAsync(p), this::calculate); // call 2 starts too; both run at once
}
```

The tools: `CompletableFuture.thenCombine()` for async code, or `StructuredTaskScope` on virtual threads for blocking
code. Calls that depend on each other still add up.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
public CompletableFuture<Credit> credit(Person p) {
  return getAssetsAsync(p)
      .thenCompose(assets -> getLiabilitiesAsync(p)
          .thenApply(liabilities -> calculate(assets, liabilities)));
}
```

</details>

<details><summary>Show answer</summary>

**Defect:** `getLiabilitiesAsync(p)` does not use `assets`, but it starts only after the assets reply arrives. The two
calls run one after another: 400 ms instead of 200 ms. No thread is wasted and the result is correct; the request is
just twice as slow as it needs to be.

**Fix:** start both calls at once and join the results.

```java
return getAssetsAsync(p)
    .thenCombine(getLiabilitiesAsync(p), this::calculate);  // both calls start now
```

**Where it matters:** only for calls that do not need each other's result. When the second call needs the first
result, `thenCompose` is the right tool. The full gain also assumes the downstream can take both calls at once (e.g., a
free DB connection for each).

Async is not concurrent: `thenCompose` waits for one result before it starts the next call.

</details>
