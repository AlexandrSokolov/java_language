## How the OS waits on I/O

### Non-blocking request — what happens at each level?
<details><summary>Show answer</summary>

Assumes an event-loop server and non-blocking drivers with pooled connections. Two sockets to follow: `FD-100`
(client ↔ server) and `FD-200` (server ↔ DB).

**Phase 1: connect and read**
- The kernel does the TCP handshake and creates `FD-100` ([file descriptor](todo)). The server's accept loop registers
  it with [epoll](todo) on one event loop, which owns it for its whole life.
- The request bytes land in `FD-100`'s receive buffer. The event loop wakes from `epoll_wait`, reads the request, and
  a server thread runs your handler ([servlet containers](#servlet-container--who-runs-each-step),
  [Netty](#netty-based-server--who-runs-each-step)).

**Phase 2: send the DB call**
- The handler borrows `FD-200` from the pool (no new socket) and writes the SQL. The write only copies bytes into the
  kernel's send buffer, so it returns at once.
- The handler returns the future; the framework attaches "write the response when done". The thread goes back to the
  server.

**Phase 3: the wait (no thread involved)**
- The kernel holds `FD-100` and `FD-200`: state plus buffers. The heap holds the future chain, with a reference to
  `FD-100`.
- `FD-100` ends only if someone closes it or a [timeout](todo) fires.

**Phase 4: reply and next step**
- The DB reply reaches `FD-200`. The driver's event loop wakes, decodes the rows, and completes the future. The next
  stage runs right there, on that thread: it sends the next call and returns. `FD-200` goes back to the pool.
- After the last reply, the CPU step moves to a CPU pool only because you ask for it: `thenApplyAsync(..., cpuPool)`.
  A plain `thenApply` would run it on the driver's event loop and
  [stall every connection on that loop](6.3_Non-Blocking_Clients.md#one-blocking-call-inside-a-non-blocking-chain--effect).

**Phase 5: respond**
- The finished future hands the response back to the server thread that owns `FD-100` (in Netty: a task in that
  event loop's queue). It copies the JSON into the kernel send buffer, and the kernel sends it.
- `FD-100` stays open ([keep-alive](todo)) for the client's next request, until the client closes it or an idle
  timeout does.

The kernel holds the sockets, the heap holds the plan, and threads only run the short steps between replies.

</details>

### What is a file descriptor?
<details><summary>Show answer</summary>

A small number the kernel gives a process to name one open resource: a file, a pipe, or a socket. When the server
accepts a connection, the kernel creates the socket and hands back a number, say `100`. From then on the process calls
`read(100)`, `write(100)`, `close(100)`, and the kernel looks up the real socket behind the number.

- **Per process:** each process has its own table of numbers. `0`, `1`, and `2` are standard input, output, and error.
- **One per connection:** every client connection and every pooled DB or HTTP connection is one descriptor. A server
  holding 10,000 open connections holds 10,000 descriptors.
- **Limited:** the OS caps descriptors per process (`ulimit -n`). At the cap, `accept` fails with "Too many open
  files", and new connections fail even though CPU and memory are fine.
- **In Java:** a `Socket` or `SocketChannel` wraps one descriptor, and
  [epoll](#how-does-one-thread-watch-many-sockets) watches descriptors, not Java objects.

A file descriptor is the process's number for one open socket or file; every open connection costs one, and they are
capped per process.

</details>

### What does the kernel keep for a socket?
<details><summary>Show answer</summary>

For each connection, e.g. `FD-100` between client `10.0.0.7:51514` and server `10.0.0.2:8080`:

- **Connection state:** the two addresses and ports, the TCP state (`ESTABLISHED`, `CLOSE_WAIT`, `TIME_WAIT`…),
  sequence numbers, and timers for resends and keep-alive probes.
- **Receive buffer:** bytes that have arrived but that the application has not read yet.
- **Send buffer:** bytes the application has written that are not yet sent, or not yet confirmed by the other side.
  They are kept for a resend until confirmed.
- **Who is waiting:** threads blocked in a read on this socket, or the epoll sets watching it.

The kernel runs TCP for the socket on its own: it confirms incoming data, resends lost data, and fills the receive
buffer, with no application thread involved. An idle connection costs a few kilobytes of kernel memory, against about
1 MB of reserved stack for a thread. That's why an open connection with no thread waiting on it is cheap.

A socket is kernel state plus two buffers; the kernel runs TCP for it on its own, so an open connection needs no
thread.

</details>

### Does a socket write wait for the network?
<details><summary>Show answer</summary>

Usually no. `write` copies the bytes into the kernel's send buffer and returns at once; the kernel sends them later,
and keeps them until the other side confirms them. A 2 KB response is "written" in microseconds.

It waits only when the send buffer is full, because the other side reads slowly or the network is slow. Think of a
50 MB download to a slow mobile client:

- **Blocking socket** (`OutputStream.write`): the thread waits until there is room in the buffer.
- **Non-blocking socket** (`SocketChannel.write` in non-blocking mode): it copies what fits, returns how many bytes that
  was (possibly 0), and the application writes the rest when the socket becomes writable again. Netty keeps such a
  write queue for you.

A returned `write` means the kernel accepted the bytes, not that the other side received them. If the connection drops
later, the application isn't told which bytes arrived; confirming delivery is the protocol's job, e.g. an HTTP
response.

A write only hands bytes to the kernel; it waits only when the send buffer is full, and "returned" never means
"delivered".

</details>

### What happens to a thread blocked on a read?
<details><summary>Show answer</summary>

It goes to sleep inside the kernel until data arrives:

1. The thread calls `read` on a socket whose receive buffer is empty.
2. The kernel puts the thread on that socket's wait list and marks it as not runnable. The scheduler runs other
   threads; this one uses no CPU.
3. Data arrives: the network card signals the kernel, TCP puts the bytes into the receive buffer, and the kernel wakes
   the threads waiting on that socket.
4. The thread becomes runnable, waits for a CPU, is switched back in, copies the bytes into its own buffer, and returns.

The cost is not CPU. It's the thread itself, which stays reserved for this one socket the whole time, plus a
[context switch](#what-does-a-context-switch-cost) to wake it.

**In a Java thread dump,** such a thread shows as `RUNNABLE`, not `WAITING`, because it is inside native code. A pool
full of `RUNNABLE` threads sitting in socket reads is a pool of waiting threads.

A [virtual thread](todo) blocked on a read is handled differently: the JDK takes it off its OS thread and watches the
socket with a poller instead.

A blocked read puts the thread to sleep on the socket's wait list; it costs no CPU, but it keeps the thread, and waking
it costs a context switch.

</details>

### What does a context switch cost?
<details><summary>Show answer</summary>

A context switch is the CPU stopping one thread and starting another. The kernel saves the old thread's registers,
picks the next thread, and loads its registers; switching between processes also swaps the memory mappings.

- **Direct cost:** a few microseconds per switch.
- **Hidden cost, often larger:** the CPU caches are full of the old thread's data. The new thread starts with cold
  caches and runs slower until they refill.

It adds up with many threads doing small pieces of work. 1,000 threads, each woken 100 times a second, make 100,000
switches a second. At ~3 µs each that's 0.3 s of CPU every second spent only on switching, before the cache effects.

That's one reason event loops scale: one thread serves many sockets and moves from one to the next without a switch.
[Virtual threads](todo) switch in the JVM instead of the kernel, which costs less than an OS switch.

A context switch costs microseconds directly and more through cold caches; thousands of threads that wake for small
pieces of work pay it all the time.

</details>

### How does one thread watch many sockets?
<details><summary>Show answer</summary>

It asks the kernel to watch them, then waits once for all of them:

1. **Register:** each socket is set to non-blocking mode and added to the kernel's watch list (epoll on Linux, kqueue
   on macOS).
2. **Wait for any:** the thread makes one call that sleeps until at least one socket is ready: data to read, room to
   write, or a new connection.
3. **Handle the ready ones:** the kernel returns only the ready sockets. The thread reads or writes each of them
   without waiting, since the data is already there, then goes back to step 2.

```java
Selector selector = Selector.open();                  // epoll underneath, on Linux
channel.configureBlocking(false);
channel.register(selector, SelectionKey.OP_READ);     // "tell me when this socket has data"

while (true) {
  selector.select();                                  // sleeps until at least one socket is ready
  for (SelectionKey key : selector.selectedKeys()) {
    handle(key);                                      // reads what has arrived; never waits
  }
  selector.selectedKeys().clear();
}
```

So the waiting doesn't disappear; it is shared. Instead of one thread waiting on each socket, the kernel watches all of
them, and one thread waits for whichever is ready first. A Netty event loop is this loop, plus a task queue.

One thread watches many sockets by asking the kernel which ones are ready: it waits once for all of them, and never on
any single one.

</details>

### Why does epoll scale better than select?
<details><summary>Show answer</summary>

Say a server watches 10,000 open connections, and 5 of them have data:

- **`select` / `poll`:** every call hands the kernel the full list of 10,000 sockets. The kernel checks every one, and
  on return the application scans all 10,000 again to find the 5 that are ready. The cost follows the number of
  sockets watched. `select` also has a hard limit of 1,024 sockets.
- **epoll:** the watch list lives in the kernel and is registered once. When data arrives on a socket, the kernel puts
  it on a ready list right away. A wait call returns only the 5 ready sockets. The cost follows the number of ready
  sockets, not the number watched.

That's why a server with many idle connections (keep-alive, long polling) stays cheap with epoll. Java's `Selector`
uses epoll on Linux, and kqueue, the same idea, on macOS.

`select` checks every watched socket on every call; epoll keeps the list in the kernel and returns only the ready ones,
so the cost follows activity, not the number of connections.

</details>

### Servlet container — who runs each step?
<details><summary>Show answer</summary>

Tomcat, Jetty, and Undertow (WildFly) split the work: a few threads watch sockets, and a worker pool runs your code.

1. **Connect and read:** a watcher thread sees data on `FD-100` and passes the request to a worker, which runs your
   handler. The servers differ only in this step:
    - **Tomcat:** the poller hands the socket to a worker; the worker parses the HTTP.
    - **Undertow:** the I/O thread parses the HTTP first, then hands the request to a worker.
    - **Jetty:** the thread that saw the data often runs the handler itself, while a spare thread takes over the
      watching. This keeps the CPU cache hot.
2. **Handler returns a future:** the framework calls `request.startAsync()`. The worker goes back to the pool, and the
   request stays open.
3. **Wait and reply:** no worker is involved. The watcher thread keeps an eye on `FD-100`, and the DB driver's event
   loop handles `FD-200`.
4. **Respond:** when the future completes, a worker thread writes the response.
5. **After:** the idle keep-alive connection goes back to the watcher, and no worker is held.

A watcher finds the data; a worker runs your code.

</details>

### Netty-based server — who runs each step?
<details><summary>Show answer</summary>

Spring WebFlux, Quarkus (Vert.x), and Micronaut run on Netty: a few event loops, about one per core.

1. **Connect and read:** the event loop that owns `FD-100` reads and parses the request and runs your handler itself.
2. **Handler returns a future:** the event loop goes straight back to `epoll_wait`.
3. **Wait and reply:** no thread is involved. The event loop watches `FD-100`, and the DB driver's event loop handles
   `FD-200`.
4. **Respond:** only `FD-100`'s own event loop may write to it. If the result comes from another thread, the write goes
   into that loop's task queue.
5. **After:** the idle keep-alive connection stays on its event loop.

Because your code runs on the event loop, blocking in it stalls every connection on that loop. Some frameworks move
blocking code away: Quarkus runs plain `T` methods on a worker thread and `Uni` / `CompletionStage` methods on the
event loop.

The loop that finds the data runs your code.

</details>

### What happens before the server sees a connection?
<details><summary>Show answer</summary>

The kernel does the whole TCP handshake on its own:

1. **SYN:** the client asks to connect. The server's kernel notes the half-open connection and answers (SYN-ACK).
2. **ACK:** the client confirms. The connection is now established in the kernel and waits in the listening socket's
   accept queue (the backlog).
3. **`accept`:** the server application takes it from the queue and gets a [file descriptor](#what-is-a-file-descriptor).
   This is the first moment the application knows about it.
4. **For HTTPS:** a TLS handshake follows, a few more round trips, before the first request byte.

If the application accepts too slowly, the accept queue fills. The kernel then drops new handshakes (the default on
Linux), and the client retries. The client may already think it's connected, so its request just waits, then times
out. In Tomcat this queue is [`acceptCount`](6.1_Blocking_vs_Non-Blocking_IO.md#all-pool-threads-busy--what-happens).

The kernel finishes the handshake and queues the connection before the server sees it; if the server accepts too
slowly, the queue fills and new connections stall.

</details>

### Why is opening a connection expensive?
<details><summary>Show answer</summary>

Because it costs round trips and CPU before any real work. Take a DB 2 ms away over the network:

- **TCP handshake:** 1 round trip, 2 ms.
- **TLS handshake:** 1 more round trip with TLS 1.3 (2 with TLS 1.2), plus key exchange and certificate checks, which
  cost CPU on both sides.
- **Login and setup:** the DB checks the password (often several round trips) and sets up the session. PostgreSQL even
  starts a new server process for each connection.
- **Slow start:** a new TCP connection starts with a small send window, so its first large transfers are slower.

That's easily 10 ms or more before a 1 ms query runs. Closing costs too: the side that closes first keeps the
connection in `TIME_WAIT` for about a minute on Linux, holding a local port. Many short connections can therefore run
out of ports.

Pools (JDBC, R2DBC, HTTP clients) and HTTP [keep-alive](#what-does-keep-alive-change) exist for this reason: they open
a connection once and reuse it for thousands of calls.

A new connection pays round trips, crypto, and login before any real work, and leaves `TIME_WAIT` behind; pools and
keep-alive pay that once and reuse the connection.

</details>

### What does keep-alive change?
<details><summary>Show answer</summary>

After a response, the HTTP connection stays open for the next request instead of closing. That's the default in
HTTP/1.1.

- **For the client:** the next request skips the TCP and TLS handshakes, saving round trips and CPU
  ([why they cost](#why-is-opening-a-connection-expensive)).
- **For the server:** an idle connection stays open between requests. It costs a descriptor and a few KB of kernel
  memory; on today's servers, no thread, since the poller or event loop watches it. An idle timeout on the server
  closes it eventually.
- **HTTP/1.1 vs HTTP/2:** HTTP/1.1 sends one request at a time per connection, so clients keep several connections
  open. HTTP/2 carries many requests at once on one connection.

**The classic failure:** the server or a load balancer closes an idle connection, while the client's pool still thinks
it's open. The client's next request on it fails with a connection reset. The rule: the client pool's idle timeout
must be shorter than the server's.

Keep-alive also makes connections stick to one backend, so after scaling out, the new instances get traffic only as
old connections close.

Don't confuse it with **TCP keepalive**: that's the kernel sending probes on an idle connection to find dead peers,
after two hours by default on Linux.

Keep-alive trades a few idle open connections for skipped handshakes; keep the client's idle timeout shorter than the
server's.

</details>

### Where does a paused request live?
<details><summary>Show answer</summary>

While a non-blocking request waits for a reply, no thread holds it. It lives in two places:

- **In the kernel:** the client's socket (`FD-100`) and the downstream socket (`FD-200`), each with its state and
  buffers ([what the kernel keeps](#what-does-the-kernel-keep-for-a-socket)).
- **On the heap:** the future chain. That's the steps still to run, with the values their lambdas captured, and the
  framework's callback that will write the response, which holds a reference to the client connection.

What keeps the chain from being garbage-collected: the DB driver or HTTP client keeps the pending call's future until
the reply comes. That future holds the next steps, and the last step holds the connection to the client.

It costs a few KB of heap and kernel buffers per paused request, against a thread with about 1 MB of reserved stack.
At a hundred thousand paused requests, though, that heap [adds up too](6.1_Blocking_vs_Non-Blocking_IO.md#what-caps-a-non-blocking-servers-load).
If nothing ever completes the future, the chain stays until
[a timeout ends it](6.2_Freeing_the_Request_Thread.md#what-if-a-future-never-completes).

A paused request is kernel sockets plus a chain of objects on the heap, kept alive by the client that owes it a reply;
no thread holds it.

</details>

### What ends a long-waiting HTTP call?
<details><summary>Show answer</summary>

Not silence. TCP keeps an idle connection open indefinitely, so a call waiting for a slow response ends only when
someone closes the connection or a timeout fires. Along the path:

- **The client:** its read (response) timeout, e.g. 30 s.
- **Proxies and load balancers in between:** their idle timeouts, often 60 s by default (nginx, AWS load balancers).
  These are often the shortest on the path, and invisible to both ends: the client gets a `504` from the proxy while
  the server keeps working.
- **The server:** for async requests, the framework's async timeout (Spring MVC on Tomcat: 30 s by default).
- **The kernel:** only when the other side is dead or unreachable, through resend timeouts or TCP keepalive probes.
  Never for a response that is merely slow.

The shortest timeout on the path decides. If the work regularly takes longer than that, the fix is not longer timeouts
but an [async API](6.1_Blocking_vs_Non-Blocking_IO.md#async-api-vs-non-blocking-server).

A call waiting in silence is ended by the shortest timeout on its path, often a proxy's; TCP itself never ends it.

</details>

### Why keep slow work off the event loop?
<details><summary>Show answer</summary>

Because the loop handles its sockets one after another. In [the select loop](#how-does-one-thread-watch-many-sockets),
each ready socket is handled in turn, and while one step is slow, the loop doesn't get back to waiting for the others:

- replies that already arrived for other connections sit in their receive buffers;
- responses waiting to be written on this loop wait;
- new requests on its connections are not read.

A loop often serves thousands of connections, so one 200 ms step, blocking I/O or CPU alike, delays all of them by
200 ms. Nothing fails; latency just rises for requests that have nothing to do with the slow one.

So the loop gets only short, non-blocking steps: parsing, routing, handing off. Anything slow moves off it on purpose:

- CPU work → a CPU pool;
- blocking I/O that can't be replaced → a bounded blocking pool
  ([the chain view](6.3_Non-Blocking_Clients.md#one-blocking-call-inside-a-non-blocking-chain--effect)).

Frameworks can catch slow steps for you ([how](6.3_Non-Blocking_Clients.md#how-do-you-find-hidden-blocking-calls)).

An event loop is one thread taking turns among thousands of connections; any slow turn delays all of them.

</details>
