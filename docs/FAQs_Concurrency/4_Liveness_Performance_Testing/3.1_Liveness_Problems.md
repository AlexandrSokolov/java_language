### Synchronized block — how to avoid liveness problems?
<details><summary>Show answer</summary>

Never call code you don't control from inside the block — only code you control. A method you hand off to — an
overridable method, a listener, a function passed in — is **alien**: you don't know what it does while you hold
the lock, and [it can deadlock or re-enter and see half-updated state](#what-can-go-wrong-calling-an-alien-method-from-a-synchronized-block).

</details>

### Which methods count as alien?
<details><summary>Show answer</summary>

Any method you don't control — you can't see what it does while you hold the lock:

- an overridable method (a subclass decides the body),
- a listener or callback you were handed,
- a function passed in as an argument.

The common thread: the code was supplied from outside, so its behavior isn't yours to know.

</details>

### What can go wrong calling an alien method from a synchronized block?
<details><summary>Show answer</summary>

Three ways, all bad:

- **Deadlock.** The alien method tries to take a lock you already hold, or takes a second lock in the opposite
  order another thread uses — both sides wait forever.
- **Reentered state.** The alien method calls back into your object and sees it mid-update — a half-changed state
  you assumed no one could observe while locked.
- **Nondeterministic failure.** Whether it breaks depends on what the caller's code happens to do, so it passes
  in tests and fails in production.

</details>

### How do you call an alien method safely when a lock is needed?
<details><summary>Show answer</summary>

Don't call it inside the lock — call it outside. 
- Do the locked work first, then 
- release the lock, then 
- make the call. 

An alien call made with no lock held is an **open call**.

When the alien call needs data that the locked part produced (like a list you must iterate), 
copy that data under the lock — a **snapshot** — release the lock, then call the alien method using the copy. 
The lock protects the read; the copy lets the call run free of the lock.

So: 
- **open call** is the principle (alien method runs with no lock held), 
- **snapshot** is the mechanism (carry the data out so the open call has what it needs).

</details>

### What does an open call give you?
<details><summary>Show answer</summary>

Two gains:

- **Safety** — the alien method runs with no lock held, so it can't deadlock against your lock or re-enter and
  see half-updated state. This is the reason you do it.
- **Concurrency** — an alien method may run a long time. Inside the lock, every other thread wanting that lock
  waits the whole time, for code that doesn't even need the lock. Outside, they don't wait — so the lock is held
  briefly and more threads get through.

</details>

### When does a reentrant lock fail to protect state?
<details><summary>Show answer</summary>

When you call an [alien method](#which-methods-count-as-alien) from inside the lock *while your state is half-updated*, 
and that method calls back into your object.

Normally the lock keeps others out while you break and restore an invariant. 
But a [reentrant lock](../1_Fundamentals/01_The_Java_Memory_Model.md#what-happens-when-a-thread-re-takes-its-own-lock)
doesn't stop the *same* thread from re-entering — so the alien callback walks straight back in and sees the
half-updated state the lock was supposed to hide.

```java
synchronized void add(E e) {
  data.add(e);              // invariant temporarily broken here
  notify(e);                // alien call, still under the lock
  rebuild();                // would restore the invariant — too late
}
```

If `notify`'s callback re-enters and reads `data`, it sees the broken middle. Without reentrancy that re-entry
would deadlock — a liveness failure, loud and safe. Reentrancy lets it through instead, so you get corrupted
state — a **safety failure**, silent and worse. The same feature that stops self-deadlock removes the wall that
would have caught this.

</details>

### Liveness failure vs safety failure?
<details><summary>Show answer</summary>

Two different kinds of concurrency failure:

- **Liveness failure** — the program stops making progress. Nothing wrong happens; nothing happens at all.
  Deadlock is the classic case — threads wait on each other forever.
- **Safety failure** — the program makes progress, but does the wrong thing. State gets corrupted; a reader
  sees data it should never have seen.

The trade you never want: 
- a liveness failure is loud and safe — it hangs, you notice, the bad state never escapes. 
- A safety failure is silent and worse — it keeps running on corrupted data. 
  [A reentrant lock can turn the first into the second](#when-does-a-reentrant-lock-fail-to-protect-state).

</details>

### Why can a thread pool hang with work left to do?
<details><summary>Show answer</summary>

Thread starvation deadlock: tasks in a bounded pool wait for other tasks that the same pool has no free thread to
run. Every thread is occupied by a task that's blocked waiting for a task still sitting in the queue — so nothing
finishes and nothing starts.

Example: a pool of 3 threads. You submit 3 tasks, each of which blocks until a 4th submitted task completes. All 3
threads are parked waiting; the 4th task never gets a thread to run on; the pool hangs forever. The concurrent
timing framework hits this if the executor can't run all `concurrency` workers at once — the workers that did
start block on the start latch, the ones that didn't never count down the ready latch, and the timer waits
forever.

Avoid it:

- Don't have pool tasks block waiting on other tasks submitted to the same pool.
- Size the pool for the peak number of tasks that can be blocked at the same time.
- Or use a pool that can grow threads on demand rather than a fixed one.

The trap is that nothing throws — no exception, no crash. The pool simply stops making progress (a liveness
failure, not an error).

</details>

### What is a deadlock?
<details><summary>Show answer</summary>

Two or more threads each holding a lock the other needs, each waiting for the other to release — 
so none of them ever moves again. The program does not crash; the threads just stop, permanently.

Spine: a deadlock needs a **cycle** — thread A holds x and wants y, thread B holds y and wants x. 
Everything about deadlocks comes from that cycle: 
the four conditions describe when it can form, and every fix breaks one link of it.

</details>

### Deadlocked vs blocked thread?
<details><summary>Show answer</summary>

Both sit still, waiting on something. The difference is whether the wait can ever end.

- **Blocked** — waiting for something that *will* arrive: a lock another thread holds and will release, I/O that
  will complete. Progress resumes on its own.
- **Deadlocked** — waiting for something that never can, because the thread that would release it is itself
  waiting on you. No outside event ends it.

Handle: a blocked thread is stuck for now; a deadlocked thread is stuck forever — the cycle means nothing will
ever free it.

</details>

### Give an example of a deadlock?
<details><summary>Show answer</summary>

Two accounts, two threads transferring in opposite directions. `transferTo` is synchronized, so it holds the
*source* account's lock, then calls `deposit` on the *target*, which needs the target's lock too:

```java
public synchronized boolean transferTo(FSOAccount other, int amount) {
  // holds THIS account's lock (method is synchronized)
  if (balance >= amount) {
    balance -= amount;
    other.deposit(amount);   // needs OTHER account's lock too — second lock, while holding the first
    return true;
  }
  return false;
}

// Thread A: a.transferTo(b, 1)  -> holds a, wants b
// Thread B: b.transferTo(a, 1)  -> holds b, wants a
```

Thread A holds a's lock and waits for b's. Thread B holds b's lock and waits for a's. Each needs what the other
holds; neither releases. The cycle is closed — both stop forever.

The root move is acquiring a **second lock while holding the first**, in **opposite order** in the two threads.
Remove either — one lock, or same order everywhere — and the cycle cannot form.

</details>

### The four conditions for a deadlock?
<details><summary>Show answer</summary>

A deadlock is possible only when **all four are true at the same time**. 
To prevent it you don't avoid all four — you make just **one** of them impossible. 
Three of them are normal for locks anyway; 
the fix usually targets whichever one is easiest to remove (often circular wait).

- **Mutual exclusion** — a lock is held by one thread at a time; others must wait. (If the resource could be
  shared, no one would wait.)
- **Hold and wait** — a thread holds one lock while asking for another, instead of releasing first.
- **No preemption** — a lock cannot be taken away; only its holder releases it.
- **Circular wait** — a cycle of threads, each waiting for the lock the next one holds.

All four are present in `transferTo` — which is why it deadlocks:

```java
// Thread A: a.transferTo(b)   holds a, wants b
// Thread B: b.transferTo(a)   holds b, wants a
public synchronized boolean transferTo(FSOAccount other, int amount) {
  // mutual exclusion : the method is synchronized — one thread holds THIS lock
  ...
  other.deposit(amount);  // hold and wait : still holding THIS, now asking for OTHER
}                         // no preemption : neither thread's lock can be pulled away
                          // circular wait : A holds a wants b, B holds b wants a — closed loop
```

Handle: all four on here = deadlock. Each fix flips exactly one off — that alone makes the deadlock impossible.

</details>

### How to prevent a deadlock?
<details><summary>Show answer</summary>

A deadlock needs all four conditions at once, so every fix kills one of them. Three ways to attack it:

- **Stop the cycle forming** — acquire every lock in the same global order everywhere, so no cycle can form;
  breaks *circular wait*, via [lock ordering](#fix-lock-ordering).
- **Stop waiting forever** — don't block holding a lock; [time out, release, and retry](#fix-trylock-with-timeout)
  breaks *hold-and-wait / no preemption*.
- **Never hold two locks at once** — remove the nested-lock situation entirely to break *hold-and-wait*, whether by 
  - [releasing before you call out](#fix-open-calls), 
  - guarding everything with [one coarse lock](#fix-one-coarse-lock), or 
  - dropping locks for [atomic updates](#fix-lock-free-with-atomics).

Trigger: a deadlock is a cycle of threads each holding one lock and wanting another — so break it three ways:
order the locks, time out the wait, or never hold two at once.

</details>

### Fix: lock ordering?
<details><summary>Show answer</summary>

Every thread acquires locks in the same global order. If both threads always take a's lock before b's, the cycle
cannot form — the second thread is simply blocked at the *first* lock until the first thread finishes.

```java
// pick a fixed order by some stable key (e.g. account id)
FSOAccount first  = a.id() < b.id() ? a : b;
FSOAccount second = a.id() < b.id() ? b : a;
synchronized (first) {
  synchronized (second) {
    // transfer
  }
}
```

Breaks **circular wait**: with one global order there is no A-holds-a-wants-b vs B-holds-b-wants-a — both want a
first.

Handle: same lock order everywhere = no cycle. The primary, most-asked fix.

</details>

### Fix: tryLock with timeout?
<details><summary>Show answer</summary>

Use `ReentrantLock.tryLock` instead of blocking forever. If the second lock doesn't come within a timeout,
release the first and retry — so no thread sits holding one lock waiting endlessly for another.

```java
if (fromLock.tryLock(1, SECONDS)) {
  try {
    if (toLock.tryLock(1, SECONDS)) {
      try { /* transfer */ }
      finally { toLock.unlock(); }
    } else { /* back off: release from, retry later */ }
  } finally { fromLock.unlock(); }
}
```

Breaks **hold-and-wait / no preemption**: the waiting thread gives up and releases what it holds instead of
waiting forever, so the cycle dissolves.

Handle: can't get the second lock in time → let go of the first and retry. Use when a global order isn't
practical.

</details>

### Fix: open calls?
<details><summary>Show answer</summary>

Don't call another object's method while holding your lock. Do the locked work, release, *then* make the outward
call. With no lock held during the call, no second lock is ever requested while holding the first.

```java
public boolean transferTo(FSOAccount other, int amount) {
  synchronized (this) {
    if (balance < amount) return false;
    balance -= amount;
  }                          // lock released here
  other.deposit(amount);     // open call: no lock held while calling out
  return true;
}
```

Breaks **hold-and-wait**: the second lock (`other`'s) is taken only after the first is released, so two locks are
never held at once. (Note: the money briefly leaves one account before landing — fine here, but the window must
be acceptable for your invariant.)

Handle: never call out while holding a lock — release first, then call. The cleanest structural fix.

</details>

### Fix: one coarse lock?
<details><summary>Show answer</summary>

Guard both accounts (or the whole subsystem) with a single shared lock. With only one lock, a thread can never
hold one while waiting for another — there is no second lock to wait for.

```java
private static final Object BANK = new Object();
public boolean transferTo(FSOAccount other, int amount) {
  synchronized (BANK) {      // one lock for all transfers
    // transfer
  }
}
```

Breaks **hold-and-wait**: only one lock exists, so hold-and-wait is impossible.

Handle: one lock = no deadlock, but everything serializes through it. Simplest fix, real concurrency cost.

</details>

### Fix: lock-free with atomics?
<details><summary>Show answer</summary>

Drop locks entirely for the shared field. An atomic type updates in one hardware step with `compareAndSet`, so
no lock is held across anything and there is nothing to deadlock on.

```java
private final AtomicLong balance;   // minor units, not double
// withdraw: loop compareAndSet(old, old - amount) until it succeeds or funds run out
```

Breaks **mutual exclusion**: the update needs no held lock at all, so none of the deadlock conditions can arise.

Handle: no lock held → no deadlock possible. Works for single-field updates; a two-account transfer needs more
(a lock-free transfer is hard — this is the limit of the technique).

</details>

### How does a deadlock break the fully synchronized object rules?
<details><summary>Show answer</summary>

It violates the **bounded-time** rule — every method must finish in a bounded time. 
A transfer calls `deposit` on the other account while holding its own lock, 
and that call can block forever waiting for the other account's lock. 
Once a method can block indefinitely, it has no bounded running time, and the "safe and live" guarantee is gone.


Handle: a deadlock is the bounded-time rule broken — a method that holds a lock and makes a call that may never return.

</details>
