### What is happens-before?
<details><summary>Show answer</summary>

A guarantee about **order and visibility**, not clock time. If action A happens-before action B, then A is fully
finished *and* everything A did — every write — is visible to B when B runs.

It is the real rule under everything called "visibility" or "flush": those are informal names for "there is a
happens-before edge here." Where no happens-before edge connects two actions, the JVM may run them in either
order and B may not see A's writes at all.

```java
// A happens-before B  =>  B sees everything A wrote, and A is done first
```

Handle: happens-before means A is complete and A's writes are visible to B — an ordering-and-visibility promise,
not "A ran earlier in time."

</details>

### Synchronizes-with vs happens-before?
<details><summary>Show answer</summary>

They work together but are not the same thing.

- **Synchronizes-with** — the specific cross-thread *pairing points* that connect two threads: an unlock pairs
  with a later lock of the same monitor; a volatile write pairs with a later read of the same field. It is the
  bridge between threads.
- **Happens-before** — the resulting *guarantee* (A done and visible to B). You get a cross-thread happens-before
  edge *because* a synchronizes-with pairing created it — and you get a within-thread one from program order.

So synchronizes-with is *how* an edge forms between threads; happens-before is *what that edge promises*. Rule: if
A synchronizes-with B, then A happens-before B.

Handle: synchronizes-with is the pairing that builds the bridge between threads; happens-before is the
visibility promise you get across it.

</details>

### Which pairings create a cross-thread edge?
<details><summary>Show answer</summary>

Two, and one phrase covers both: **releases happen-before acquires.**

- **Unlock → lock** — releasing a monitor synchronizes-with a later acquire of the *same* monitor.
- **Volatile write → read** — writing a volatile field synchronizes-with a later read of the *same* field.

In both, a "release" (unlock, volatile write) publishes everything the thread did up to that point, and the
matching "acquire" (lock, volatile read) picks it up. So a thread that reads a volatile value written by another
is guaranteed to see that value — and every write that came before it.

```java
// Thread A
synchronized (m) { data = 42; }   // release: publishes data
// Thread B
synchronized (m) { read(data); }  // acquire (same m): sees 42
```

Handle: releases happen-before acquires — unlock→lock and volatile-write→read are the two pairings that carry one
thread's writes to another, and only across the *same* monitor or field.

</details>

### How do happens-before edges chain?
<details><summary>Show answer</summary>

Two sources of edges combine by transitivity to reach across threads.

- **Program order** — within one thread, if A is written before B, then A happens-before B.
- **Synchronizes-with** — a pairing (unlock→lock, volatile write→read) gives a happens-before edge between
  threads.
- **Transitivity** — if X happens-before Y and Y happens-before Z, then X happens-before Z.

Chaining them is what lets a write reach a thread it never directly synchronized with:

```java
// Thread A: x = 1;  then  flagA (volatile) = true;      // program order: x hb flagA-write
// Thread B: reads flagA;  then  flagB (volatile) = true; // flagA-write hb flagA-read (pairing); read hb flagB-write
// Thread C: reads flagB;  then  reads x;                 // flagB-write hb flagB-read; read hb read-x
// transitivity: A's x = 1  happens-before  C's read of x  ->  C sees 1
```

This is the formal reason one volatile flag publishes every plain write before it: program order links the plain
write to the volatile write, the pairing carries it across, transitivity stretches it to the far reader.

Handle: program order chains within a thread, a pairing crosses between threads, transitivity links the chain —
so a write can reach a thread it never directly synchronized with.

</details>

### Which edges do start() and join() give?
<details><summary>Show answer</summary>

Two cross-thread edges people forget exist — they publish state without any explicit lock or volatile.

- **`start()`** — everything the starting thread did *before* calling `t.start()` happens-before the new thread's
  first action. So the new thread sees all the setup that preceded its start.
- **`join()`** — every action of a thread happens-before `t.join()` returns in the joining thread. So after
  `join()`, the joiner sees everything the finished thread did.

```java
config = load();        // main thread
t.start();              // new thread sees config, fully built
// ...
t.join();               // main thread now sees everything t wrote
result = t.output;      // safe — published by the join edge
```

Handle: `start()` publishes the starter's prior writes to the new thread; `join()` publishes the finished
thread's writes back to the joiner — both are happens-before edges, no lock needed.

</details>

### Does working code mean no memory bug?
<details><summary>Show answer</summary>

No. The JMM rules are the **minimum** guarantees. A real JVM often behaves *better* than the spec requires — it
may publish writes you never synchronized, on your machine, today.

That is the trap: code with a missing happens-before edge can run correctly for years on one JVM, then read stale
or reorder on a different JVM, a different CPU, or the same one under heavier load. The passing test is a quirk of
one implementation, not a guarantee.

So correctness is judged against the *rules*, not against observed behavior. If there is no happens-before edge
making a write visible, the code is broken even if it currently works.

Handle: the JMM gives minimums, not what your JVM happens to do — code to the happens-before rules, because
working-in-testing can be a quirk hiding a real bug.

</details>
