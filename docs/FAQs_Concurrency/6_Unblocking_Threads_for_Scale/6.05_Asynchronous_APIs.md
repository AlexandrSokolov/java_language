## Asynchronous APIs

### What is an async API?
<details><summary>Show answer</summary>

An API where the client does not get the result in the same call:

```
POST /reports       → 202 Accepted, Location: /reports/42
GET  /reports/42    → 200 {"status": "RUNNING"}
GET  /reports/42    → 200 {"status": "DONE", "file": "/reports/42/file"}
```

- The server stores the job and answers at once; a worker does the work later.
- The client gets the result by polling, by push (webhook, WebSocket, email), or not at all (fire-and-forget).

What it fixes: work that lasts longer than the timeouts on its path, or that the client doesn't need right away. The
price is a changed contract: clients must be written for it.

An async API ends the call before the work is done; the result comes by polling, by push, or not at all.

</details>

### Async API vs async call?
<details><summary>Show answer</summary>

They change different boundaries:

- **Async call** (the server's threads): a method returns a future, so the thread doesn't wait for the DB or API. The
  client still waits on the open connection for `200 OK`.
- **Async API** (the client-server contract): the server answers `202 Accepted` with a job ID, and the call ends. The
  client gets the result later, by polling or push; inside, workers may still block.

An async call frees a thread; an async API frees the client.

</details>

### Async API vs non-blocking server?
<details><summary>Show answer</summary>

They solve different problems: one changes the HTTP contract, the other changes the server's thread model.

- **Async API (the HTTP contract):** the client sends a request and does not wait for the result. The server
  immediately returns `HTTP 202 Accepted` with a job ID, and the call is over. The client polls later or receives a
  webhook.
  Use case: long-running business tasks (e.g., generating a PDF report, processing video).
- **Non-blocking server (the internal architecture):** the client does wait on an open HTTP connection for the final
  `HTTP 200 OK`. Under the hood, the server frees its OS thread to the pool while waiting for the DB or downstream
  services.
  Use case: highly concurrent, standard CRUD or microservice calls.

An async API breaks the HTTP wait. A non-blocking server breaks the thread wait.

</details>
