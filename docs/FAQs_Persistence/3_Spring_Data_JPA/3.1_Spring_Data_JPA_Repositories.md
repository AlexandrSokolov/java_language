# Spring Data JPA Repositories

- Why the repository abstraction exists and how it runs.
- Repository interfaces and basic methods — `save()`, `findById` / `getReferenceById`, deletes, custom fragments.

## Why the abstraction exists

### What did a data-access class look like before Spring Data, and what was the same in every one of them?
<details><summary>Show answer</summary>

Every entity had its own hand-written DAO class, and most of its code was the same for every entity: find by ID, find
all, save, delete, plus a few queries. Only the entity type changed.

```java
public class CustomerDao {
  @PersistenceContext
  private EntityManager em;

  public Customer findById(Long id) {
    return em.find(Customer.class, id);
  }

  public List<Customer> findAll() {
    return em.createQuery("select c from Customer c", Customer.class).getResultList();
  }

  public Customer save(Customer c) {
    if (c.getId() == null) {
      em.persist(c);
      return c;
    }
    return em.merge(c);
  }

  public List<Customer> findByEmail(String email) {
    return em.createQuery("select c from Customer c where c.email = :email", Customer.class)
             .setParameter("email", email)
             .getResultList();
  }
}
```

With Spring Data you declare an interface. The CRUD methods come from one shared generic implementation, and simple
queries come from the method name:

```java
public interface CustomerRepository extends JpaRepository<Customer, Long> {
  List<Customer> findByEmail(String email);
}
```

**Handle:** Spring Data removes the repeated DAO code, not JPA — the same `EntityManager` calls still run underneath.

</details>

### How can a repository work when you only declare an interface?
<details><summary>Show answer</summary>

At startup Spring creates the implementation for you: a proxy object for each repository interface. Every call on the
proxy is routed by method:

- methods inherited from `CrudRepository` / `JpaRepository` → `SimpleJpaRepository`, one generic class that holds the
  `EntityManager` code;
- query methods you declared → a query object built at startup from the method name or from `@Query`;
- methods of a [custom fragment](#how-do-you-add-a-hand-written-method-to-a-generated-repository) → your own class.

Spring Boot turns this on automatically (`@EnableJpaRepositories` without Boot). A repository factory
(`JpaRepositoryFactory`) builds the proxies.

**Handle:** the interface is only a contract; the proxy picks the implementation for each method.

</details>

### Where does the repository abstraction stop helping?
<details><summary>Show answer</summary>

It stops helping when a query or an operation does not fit a method name, an annotation, or a generic CRUD call:

- queries with many optional filters → Specifications or Querydsl;
- work that needs the `EntityManager` or Hibernate `Session` directly (batch processing with `flush()` / `clear()`,
  `StatelessSession`) → a [custom fragment](#how-do-you-add-a-hand-written-method-to-a-generated-repository);
- heavy reporting SQL → a native query, or a reporting tool outside the application.

It also does not hide JPA behaviour. `save()` is still persist or merge, loaded entities are still managed and
dirty-checked, and lazy loading still needs an open session.

**Handle:** the abstraction removes code, not the need to understand the persistence context.

</details>

## Repository interfaces and basic methods

### `CrudRepository` vs `ListCrudRepository` vs `JpaRepository`: what does each level add?
<details><summary>Show answer</summary>

- `Repository<T, ID>` — a marker with no methods. You declare only the methods you want.
- `CrudRepository` — `save`, `saveAll`, `findById`, `existsById`, `findAll`, `findAllById`, `count`, `delete…`;
  collections come back as `Iterable`.
- `ListCrudRepository` (Spring Data 3.0+) — the same methods, returning `List`.
- `PagingAndSortingRepository` — `findAll(Sort)`, `findAll(Pageable)`. Since 3.0 it no longer extends
  `CrudRepository`, so you combine the two.
- `JpaRepository` — everything above plus JPA-specific methods: `flush`, `saveAndFlush`, `saveAllAndFlush`,
  `deleteAllInBatch`, `getReferenceById`.

**Trap:** extending `JpaRepository` gives every caller `deleteAll()` and `deleteAllInBatch()`. For a read-only
repository, extend `Repository` and declare only the read methods; Spring Data still implements them through
`SimpleJpaRepository` when the signatures match.

**Handle:** pick the smallest interface that matches what callers are allowed to do.

</details>

### What does `save()` do for a new entity and for an existing one, and why must you use its return value?
<details><summary>Show answer</summary>

**Persist vs merge:** `save()` first checks whether the entity is new.

- New → `em.persist(entity)`. The same instance becomes managed and is returned.
- Not new → `em.merge(entity)`. JPA copies the state onto a managed instance and returns that one. The instance you
  passed stays detached.

```java
// inside one @Transactional method, customer is detached (e.g. built from a request)
Customer saved = repository.save(customer); // merge: saved is managed, customer is not
saved.setEmail("a@example.com");            // tracked, written at commit
customer.setEmail("b@example.com");         // lost: customer is detached
```

How "new" is decided by default: if the entity has a `@Version` field with a wrapper type (`Long`, `Integer`), a `null`
version means new; otherwise a `null` ID (`0` for primitive IDs) means new. An entity implementing `Persistable`
decides itself through `isNew()`.

**Handle:** always continue with the object `save()` returns.

</details>

### With an ID you assign yourself, why does `save()` run an extra `SELECT` before the `INSERT`, and how do you avoid it?
<details><summary>Show answer</summary>

Because the ID is already set, `save()` decides the entity is not new and calls `merge()`. `merge()` must know whether
the row exists, so Hibernate loads it by ID first: one `SELECT`, nothing found, then the `INSERT`. Every insert costs two
statements. This is typical for UUIDs generated in Java, natural keys (ISBN, country code), or IDs taken from another
system.

Fix 1: implement `Persistable<ID>` and tell Spring Data yourself whether the entity is new:

```java
@Entity
public class Book implements Persistable<String> {
  @Id
  private String isbn;

  @Transient
  private boolean isNew = true;

  @Override
  public String getId() {
    return isbn;
  }

  @Override
  public boolean isNew() {
    return isNew;
  }

  @PostLoad
  @PostPersist
  void markNotNew() {
    isNew = false;
  }
}
```

Fix 2: add a `@Version` field with a wrapper type (`private Long version;`). A `null` version means new, whatever the
ID is.

**Handle:** an assigned ID makes every entity look "existing" — tell Spring Data the truth through `isNew()` or a
version field.

</details>

### `findById` vs `getReferenceById`: when is each one right, and when does the second one fail?
<details><summary>Show answer</summary>

`findById` loads the entity now (a `SELECT`, unless it is already in the persistence context) and returns an
`Optional`, empty when there is no such row. Use it when you need the data or must check that the row exists.

`getReferenceById` returns a lazy proxy with only the ID set and runs no query (`em.getReference`). Use it to link an
association without loading the other entity:

```java
Order order = new Order();
order.setCustomer(customerRepository.getReferenceById(customerId)); // no SELECT for the customer
orderRepository.save(order);
```

**Trap:** the proxy is not checked when it is created. If the row does not exist, you find out later: an
`EntityNotFoundException` on the first access to a non-ID field, or a foreign-key violation at flush. Touching the
proxy after the transaction has ended throws `LazyInitializationException`.

`getReferenceById` replaces the deprecated `getOne()` and `getById()`.

**Handle:** `findById` when you need the data, `getReferenceById` when you only need the foreign key.

</details>

### `deleteAll()` vs `deleteAllInBatch()`: what is the difference in SQL and in lifecycle callbacks?
<details><summary>Show answer</summary>

`deleteAll()` loads all entities and removes them one by one: one `SELECT` plus one `DELETE` per entity. Lifecycle
callbacks (`@PreRemove`), cascades (`CascadeType.REMOVE`) and orphan removal run, and the persistence context stays
correct.

`deleteAllInBatch()` sends one statement: `delete from Customer`. Nothing is loaded and no callbacks or cascades run.
Child rows are not removed, so the database rejects the delete when foreign keys point to the rows (unless the schema
has `ON DELETE CASCADE`). Entities already loaded stay in the persistence context although their rows are gone.

The same split exists for `deleteAll(Iterable)` vs `deleteAllInBatch(Iterable)` and `deleteAllByIdInBatch`.

**Handle:** a per-entity delete keeps JPA's rules and is slow; a batch delete is fast and skips them.

</details>

### How do you add a hand-written method to a generated repository?
<details><summary>Show answer</summary>

Write a separate fragment interface with the method, implement it in a class named after that interface plus `Impl`,
and let the repository extend the fragment. Spring finds the class by its name and routes those calls to it.

```java
public interface CustomerRepositoryCustom {
  List<Customer> search(CustomerFilter filter);
}

class CustomerRepositoryCustomImpl implements CustomerRepositoryCustom {
  @PersistenceContext
  private EntityManager em;

  @Override
  public List<Customer> search(CustomerFilter filter) {
    // Criteria API, flush/clear batching, Hibernate Session, ...
  }
}

public interface CustomerRepository extends JpaRepository<Customer, Long>, CustomerRepositoryCustom {
}
```

The `Impl` class is a normal Spring bean, so other beans can be injected into it. A fragment method takes precedence
over a generated method with the same signature, so a fragment can also replace a CRUD method.

**Handle:** fragment interface + `Impl` class = your own code inside the same repository proxy.

</details>
