# Spring Data Results and Execution

- Projections — interface vs DTO.
- Paging and sorting — `Page` vs `Slice`, offset vs keyset.
- Transactions in repositories — `@Transactional` itself is covered in the Spring decks.

## Projections

### Interface projection vs DTO projection: what does each one select and return, and how do you map a query result straight into a record?
<details><summary>Show answer</summary>

Both select only the listed columns and return objects that are not entities: they are not in the persistence context,
so there is no dirty checking and no lazy loading.

Interface projection: declare getters named after entity properties. Spring Data selects those properties and returns
a proxy that implements the interface.

```java
interface CustomerSummary {
  String getName();
  String getEmail();
}

List<CustomerSummary> findByStatus(Status status);
```

DTO projection (a class or a record): in a derived query, Spring Data selects the properties that match the constructor
parameter names. In `@Query` JPQL, write a constructor expression with the fully qualified class name:

```java
public record CustomerDto(Long id, String name) {}

@Query("select new com.example.customer.CustomerDto(c.id, c.name) from Customer c where c.status = :status")
List<CustomerDto> findDtosByStatus(@Param("status") Status status);
```

The difference: an interface needs less code but gives proxy objects; a DTO is a plain object you can pass on,
serialize and test easily.

**Handle:** both read only what you list; interface = proxy, DTO = plain object.

</details>

### An interface projection with a computed getter: why can it select every column of the entity?
<details><summary>Show answer</summary>

**Open projection:** a getter with `@Value` and a SpEL expression can read any property of the target entity, so
Spring Data cannot tell which columns are needed. It loads the whole entity and evaluates the expression on it.

```java
interface CustomerView {
  @Value("#{target.firstName + ' ' + target.lastName}")
  String getFullName(); // open projection: the whole entity is loaded
}
```

A closed projection has only getters that match entity properties, so Spring Data can select exactly those columns. To
keep it closed and still compute a value, use a default method:

```java
interface CustomerView {
  String getFirstName();
  String getLastName();

  default String getFullName() {
    return getFirstName() + " " + getLastName();
  }
}
```

**Handle:** SpEL in a projection means the whole entity is loaded; a default method keeps it narrow.

</details>

### How can one repository method return different projection types?
<details><summary>Show answer</summary>

Add a `Class<T>` parameter, and let the caller say which type it wants:

```java
<T> List<T> findByStatus(Status status, Class<T> type);

List<CustomerSummary> summaries = repository.findByStatus(Status.ACTIVE, CustomerSummary.class);
List<Customer> entities = repository.findByStatus(Status.ACTIVE, Customer.class);
```

Spring Data builds the matching select for the requested type at call time, so one method replaces a method per view.

**Handle:** a `Class<T>` parameter turns the projection into a choice of the caller.

</details>

### A projection that includes an associated entity: does it still select only the needed columns?
<details><summary>Show answer</summary>

Only partly. Take a nested interface projection: `OrderView` has `getCustomer()`, which returns `CustomerView`. Spring
Data narrows the select for the root entity, but the associated entity is loaded with all its columns *(unverified —
the exact behaviour depends on the Spring Data JPA version)*. For a to-many association, the nested values can also
cause extra queries per row (N+1) *(unverified)*.

To select exactly what you need, flatten the result: use a DTO with a JPQL constructor expression and a join.

```java
@Query("select new com.example.order.OrderRow(o.number, c.name) from Order o join o.customer c")
List<OrderRow> findOrderRows();
```

**Handle:** a nested projection can bring the whole associated entity back; a flat DTO with a join cannot.

</details>

## Paging and sorting

### `Page` vs `Slice` vs `List` with a `Pageable`: what does each one cost?
<details><summary>Show answer</summary>

- `Page` — the rows plus the total count, so two queries per request: the data query and a count query. On big tables
  the count is often the expensive part.
- `Slice` — fetches page size + 1 rows; the extra row only shows whether a next page exists. No count query.
- `List` with a `Pageable` — only the rows, with `LIMIT` / `OFFSET` applied, and no extra information.

Use `Page` when the UI shows the total ("page 3 of 250"), `Slice` for "load more" or infinite scroll, and `List` when the
caller only needs the chunk.

**Handle:** a total count is a second query — pay for it only when someone shows it.

</details>

### Paging over a query with a fetch join on a collection: why can it load the whole table?
<details><summary>Show answer</summary>

**In-memory pagination:** a fetch join on a to-many association returns one SQL row per child, so an SQL `LIMIT` would
cut an entity's children apart. Hibernate therefore leaves `LIMIT` / `OFFSET` out of the SQL, loads all matching rows,
and pages in memory. It only logs warning `HHH90003004` ("firstResult/maxResults specified with collection fetch;
applying in memory"). On a large table this is slow and can run out of memory.

Fixes:

- two queries: page over the IDs first, then fetch join only for those IDs;
- drop the fetch join and load the collection with batch fetching (`@BatchSize` or
  `hibernate.default_batch_fetch_size`).

Setting `hibernate.query.fail_on_pagination_over_collection_fetch=true` turns the warning into an error, so the problem
cannot slip into production.

**Handle:** never page over a collection fetch join — page over IDs, then fetch.

</details>

### Why do deep pages get slow with offset paging, and what does Spring Data offer instead?
<details><summary>Show answer</summary>

`OFFSET 100000` makes the database read and throw away 100,000 rows before it returns the page, so every page further
in is slower. Rows inserted or deleted between requests also shift the pages, so items get skipped or repeated.

Keyset paging remembers the sort values of the last row and asks for the rows after it:
`where id > :lastId order by id limit 20`. With an index, every page costs the same.

Spring Data 3.1+ supports this as scrolling *(unverified — check the method names against your version)*:

```java
Window<Order> findFirst20ByOrderByIdAsc(ScrollPosition position);

Window<Order> first = repository.findFirst20ByOrderByIdAsc(ScrollPosition.keyset());
Window<Order> next = repository.findFirst20ByOrderByIdAsc(first.positionAt(first.size() - 1));
```

The cost: you cannot jump to page N, and the sort must be unique and stable (add the ID as the last sort key).

**Handle:** offset counts rows to skip; keyset remembers where it stopped.

</details>

### Sorting by a field name the client sends: what can go wrong?
<details><summary>Show answer</summary>

Spring Data resolves each `Sort` property against the entity. A name that is not an entity property path fails with
`PropertyReferenceException`, which usually reaches the client as a 500 instead of a 400. A typical case: the client
sorts by DTO field names (`userName`) while the entity path is `user.name`.

The fix: whitelist the sort keys the client may send and map each one to an entity path before you build the `Sort`.

Native queries: Spring Data cannot translate properties to columns, so a `Sort` must use column names or aliases. How
well `Sort` works with native queries has varied between versions *(unverified)*. `JpaSort.unsafe(…)` passes a raw
expression into `ORDER BY`; never build it from client input, because that is SQL injection.

**Handle:** a client's sort key is input — validate and map it, never pass it through.

</details>

## Transactions in repositories

### What transaction does a repository method run in when the caller has none?
<details><summary>Show answer</summary>

The CRUD methods from `SimpleJpaRepository` bring their own. The class is annotated
`@Transactional(readOnly = true)`, and the write methods (`save`, `delete…`) override that with `@Transactional`. Each
call starts a transaction and commits it when the method returns. If the caller already has a transaction, the
repository method joins it.

`readOnly = true` makes Spring switch Hibernate's flush mode to manual, so nothing is dirty-checked and flushed at
commit. It also marks the JDBC connection as read-only, which a routing `DataSource` can use to send the query to a
replica.

Query methods you declare yourself get no transaction by default *(unverified for your version)*. Add
`@Transactional(readOnly = true)` on the repository interface, or rely on the caller's transaction. Derived deletes and
[`@Modifying` queries](3.2_Spring_Data_Queries.md#why-does-an-update-or-delete-in-query-need-modifying) fail without one.

**Handle:** each repository call outside a service transaction is a transaction of its own.

</details>

### A service calls two repository methods with no `@Transactional` around them: what can go wrong?
<details><summary>Show answer</summary>

Each call runs in its own transaction, so the two calls are not one unit of work:

- no atomicity: the first `save()` commits, and if the second call fails, the first change stays — a half-done update;
- no consistent reads: another transaction can change the data between the two calls;
- detached results: entities returned by the first call are detached when its transaction ends, so touching a lazy
  association later throws `LazyInitializationException`.

**Trap:** in a Spring Boot web application, Open Session in View (`spring.jpa.open-in-view`, on by default) keeps the
session open for the whole request. The `LazyInitializationException` then does not appear, but atomicity is still
missing, and lazy loads run outside any transaction.

The fix: put `@Transactional` on the service method.

**Handle:** a business operation that calls several repositories needs one transaction around all of them.

</details>

### A repository method returns `Stream<T>`: what does it require from the caller?
<details><summary>Show answer</summary>

An open transaction for the whole time the stream is consumed, and closing the stream. The stream reads rows lazily
from an open database cursor, which needs a live connection. Without a surrounding transaction, Spring Data throws
`InvalidDataAccessApiUsageException`. If the stream is not closed, the cursor stays open until the transaction ends.

```java
@Transactional(readOnly = true)
public void exportAll(Writer out) {
  try (Stream<Customer> customers = repository.streamAllBy()) {
    customers.forEach(c -> write(out, c));
  }
}
```

Every entity read this way also stays in the persistence context. For big exports, detach each entity after use
(`em.detach`) or clear the context from time to time; otherwise memory grows just as with `findAll()`.

**Handle:** a repository stream is an open cursor — transaction around it, try-with-resources on it.

</details>
