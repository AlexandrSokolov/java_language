# Spring Data Queries

- Derived queries — queries built from method names.
- `@Query` — JPQL vs native SQL; `@Modifying`.

## Derived queries

### How does Spring turn a method name into a query, and when do you find out the name is wrong?
<details><summary>Show answer</summary>

Spring Data parses the name at startup into two parts:

- the subject — `find…By`, `read…By`, `get…By`, `query…By`, `stream…By`, `count…By`, `exists…By`, `delete…By`, with
  optional `Distinct`, `First`, `Top10`;
- the predicate after `By` — entity property names joined by keywords: `And`, `Or`, `Between`, `LessThan`, `Like`,
  `In`, `IsNull`, `OrderBy`, …

```java
List<Customer> findTop10ByStatusAndCreatedAtAfterOrderByCreatedAtDesc(Status status, Instant since);
// select c from Customer c where c.status = ?1 and c.createdAt > ?2 order by c.createdAt desc, limited to 10 rows
```

Each property is checked against the entity when the repository is created. A typo like `findByEmial` stops the
application from starting with `PropertyReferenceException`; it does not wait until the call. JPQL in `@Query` is also
checked at startup, because Hibernate parses it then. Native SQL is not checked.

**Handle:** a derived query is a query written in the method name and validated at startup.

</details>

### When does a derived query stop being a good idea?
<details><summary>Show answer</summary>

When the name no longer reads like a short sentence, or the query needs something method names cannot express:

- `OR` groups that need parentheses — `And` binds tighter than `Or`, and a name has no way to group conditions;
- joins with conditions, subqueries, aggregates, `GROUP BY`;
- exact control over the generated SQL.

Then move to `@Query`, or to Specifications when the conditions are optional filters. There is no fixed limit on the
number of conditions; readability and what the query must express decide.

**Handle:** when the name gets hard to read, the query belongs in `@Query`.

</details>

### A derived `deleteBy…` method: how many statements does it run, and why?
<details><summary>Show answer</summary>

**Load-then-delete:** one `SELECT` loads all matching entities, then one `DELETE` runs per entity through
`em.remove()`. For 10,000 matching rows that is 10,001 statements.

Why: Spring Data keeps JPA's rules. Each entity goes through `em.remove()`, so `@PreRemove` callbacks, cascades and
orphan removal run, and the persistence context stays correct.

It also needs an active transaction. Without one the call fails, because `remove()` cannot run outside a transaction.

For a bulk delete that skips those rules, write the statement yourself:

```java
@Modifying
@Query("delete from Order o where o.status = :status")
int purgeByStatus(@Param("status") Status status);
```

**Handle:** a derived delete is a loop of `em.remove()`; one bulk statement needs `@Modifying @Query`.

</details>

### To check whether a matching row exists, which does the least work: `existsBy…`, `countBy…`, or `findBy…`?
<details><summary>Show answer</summary>

`existsBy…`. Spring Data limits the query to one result, so the database can stop at the first matching row, and the
method returns a `boolean`.

- `countBy…` counts every matching row, so the database must find all of them.
- `findBy…` loads full entities into memory and into the persistence context, only to call `isEmpty()` on the result.

`existsById` from `CrudRepository` does the same for an ID.

**Handle:** to ask "is there one?", use `exists`.

</details>

### What happens when you pass `null` to a derived query parameter?
<details><summary>Show answer</summary>

For a simple equality condition, Spring Data JPA turns `null` into `IS NULL`. `findByEmail(null)` returns the customers
that have no email — not all customers, and not "no filter". So passing `null` does not make a condition optional.

In a hand-written `@Query`, `c.email = :email` with `null` compares with `NULL` and matches no rows at all.

If the package declares Spring's null-safety annotations (`@NonNullApi`), passing `null` to a non-nullable parameter
throws `IllegalArgumentException` instead.

Optional filters need Specifications, Querydsl, or Query by Example.

**Handle:** `null` in a derived query means `IS NULL`, never "skip this condition".

</details>

### A method that returns a single `T` or `Optional<T>`: what happens when the query finds several rows?
<details><summary>Show answer</summary>

It throws `IncorrectResultSizeDataAccessException`, Spring's wrapper around JPA's `NonUniqueResultException`. A return
type of `T` or `Optional<T>` means "zero or one row"; `Optional` only covers the zero case.

Fixes:

- if several rows are possible, return `List<T>`;
- if any one of them will do, use `findFirstBy…OrderBy…`. Always give an order; without one, "first" is whatever the
  database returns first.

**Handle:** `Optional` handles "none", not "many".

</details>

### How does Spring decide where a nested property ends in a method name, and how do you remove the ambiguity?
<details><summary>Show answer</summary>

For `findByAddressZipCode`, Spring first looks for a property `addressZipCode` on the entity. If there is none, it
splits the name at the camel-case humps, starting from the right: `addressZip` + `code`, then `address` + `zipCode`. It
takes the first split that matches a property path. If the entity also has a field `addressZip`, it can pick the wrong
path.

An underscore sets the split explicitly: `findByAddress_ZipCode` means `address.zipCode`.

So avoid underscores in Java field names; Spring Data uses them for this.

**Handle:** `_` in a method name marks the step into a nested property.

</details>

## `@Query` and `@Modifying`

### JPQL vs native SQL in `@Query`: what do you gain and lose with native, and when are you forced to use it?
<details><summary>Show answer</summary>

JPQL works on entities and their fields. Native SQL works on tables and columns and goes to the database unchanged.

What native SQL gives: any SQL the database has — window functions, CTEs, JSON and array operators, upserts
(`ON CONFLICT`, `MERGE`), database-specific hints.

What native SQL costs:

- no startup check, so a typo fails at call time;
- no portability between databases;
- results map to entities only when all columns are selected; otherwise you need a projection;
- [sorting](3.3_Spring_Data_Results_and_Execution.md#sorting-by-a-field-name-the-client-sends-what-can-go-wrong) is limited, and the
  [count query for paging](#why-does-a-paged-query-sometimes-need-an-explicit-countquery) usually has to be written by
  hand.

You are forced to use native SQL only when JPQL cannot express the query. Hibernate 6 HQL supports more than classic
JPQL, including some window functions and CTEs *(unverified per feature — check your Hibernate version)*, so try HQL
first.

**Handle:** JPQL by default; native SQL when the database feature is the point.

</details>

### Why does an `UPDATE` or `DELETE` in `@Query` need `@Modifying`?
<details><summary>Show answer</summary>

Without it, Spring Data runs every `@Query` as a select and tries to read a result list. An `UPDATE` or `DELETE` must
go through `executeUpdate()`, which returns the number of changed rows. `@Modifying` tells Spring Data to call
`executeUpdate()`. Without it, the call fails at run time.

```java
@Modifying
@Query("update Customer c set c.status = :status where c.lastLogin < :before")
int deactivateInactive(@Param("status") Status status, @Param("before") Instant before);
```

The statement also needs an active transaction; without one it fails with `TransactionRequiredException`. Put
`@Transactional` on the calling service method or on the repository method.

**Handle:** `@Modifying` switches a query from "read rows" to "change rows".

</details>

### After a bulk update through `@Query`, why do entities already loaded in the same transaction show old values?
<details><summary>Show answer</summary>

**Stale persistence context:** the bulk statement goes straight to the database and skips the persistence context.
Entities loaded earlier keep their old field values, and a later `findById` for one of them returns the cached object,
not the updated row.

It can get worse. If such an entity was also changed in Java, its flush at commit writes all its columns back, by
default including the ones the bulk update changed. The bulk change is overwritten with old values.

Two attributes fix it:

- `flushAutomatically = true` — flush pending changes before the bulk statement, so they reach the database first;
- `clearAutomatically = true` — clear the persistence context after it, so the next read loads fresh rows.

```java
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("update Customer c set c.status = :status where c.lastLogin < :before")
int deactivateInactive(@Param("status") Status status, @Param("before") Instant before);
```

**Trap:** `clearAutomatically` alone detaches everything, so changes not yet flushed are lost and the entities you still
hold become detached. Use both attributes together.

**Handle:** a bulk statement bypasses the persistence context — flush before it, clear after it.

</details>

### Why does a paged `@Query` sometimes need an explicit `countQuery`?
<details><summary>Show answer</summary>

To return a `Page`, Spring Data needs the total number of rows, so it builds a count query from your query by rewriting
its select part into `count(…)`. That works for simple queries. With fetch joins, `GROUP BY`, `DISTINCT` over joins, or
native SQL, the generated count can be wrong or fail. Then you write it yourself:

```java
@Query(value = "select o from Order o join fetch o.customer where o.status = :status",
       countQuery = "select count(o) from Order o where o.status = :status")
Page<Order> findByStatusWithCustomer(@Param("status") Status status, Pageable pageable);
```

The count query also leaves out the fetch join, because counting does not need the associated data.

**Handle:** when the query is not simple, write the count query yourself.

</details>
