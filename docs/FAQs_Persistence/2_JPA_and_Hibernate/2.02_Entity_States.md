# Entity States

The entity lifecycle: the states an entity can be in, and the calls that move it from one state to another.
Covers what each call does in each state, including the calls that fail.

### What states can an entity be in?
<details><summary>Show answer</summary>

Two questions decide the state — is a context tracking the object, and does a row back it:

- **New** (Hibernate: transient) — no context, no row: `new User()`.
- **Managed** (Hibernate: persistent) — in a context; Hibernate tracks it and writes its changes. It has a row, or its
  `INSERT` is pending.
- **Detached** — has a row, but no context tracks it: the context closed or let it go.
- **Removed** — still in a context, but its `DELETE` is queued for the next flush.

Only a managed entity has its changes written to the database.

</details>

### What moves an entity between states?
<details><summary>Show answer</summary>

- New → managed: `persist()` (or `merge()`, which manages a copy instead).
- Database → managed: `find()`, `getReference()`, a query.
- Managed → detached: `detach()`, `clear()`, `close()`, the end of a transaction-scoped context (commit or
  rollback), serialization.
- Detached → managed: `merge()` — it returns a
  [managed copy](2.05_Persist_vs_Merge.md#what-does-merge-return--and-why-care); the object you pass stays detached.
- Managed → removed: `remove()`.
- Removed → managed: [`persist()`](#persist-on-a-removed-entity) again, before the flush.

Ways in are persist, a load, or merge; every way out is the context letting go.

</details>

### Which calls do nothing on a managed entity?
<details><summary>Show answer</summary>

- `persist()` — ignored, but the cascade still runs (relations marked `PERSIST` or `ALL`).
- `merge()` — returns the same instance; the cascade still runs (relations marked `MERGE` or `ALL`).

The context already holds the entity, so there is nothing to add. Only the cascade does work.

</details>

### Which calls fail on a detached entity?
<details><summary>Show answer</summary>

- [`persist()`](#persist-on-a-detached-entity)
- [`remove()`](#remove-on-a-detached-entity)

`persist()` expects a new object, `remove()` expects a managed one. A detached object is neither.

</details>

### New or detached — how does Hibernate decide?
<details><summary>Show answer</summary>

Neither carries a flag — both are plain objects outside any context. Hibernate looks at their fields:

- Non-primitive `@Version` — decides on its own: `null` → new, set → detached. Works even with an assigned ID.
- No version, or a primitive one (never `null`) — the ID decides:
  - generated ID: `null` → new, set → detached;
  - assigned ID (no generator): always set, so the fields can't tell — Hibernate runs a `SELECT` to find out.

This decides how [`merge()`](2.05_Persist_vs_Merge.md#why-does-merge-run-a-select-first) and Spring Data's
[`save()`](2.05_Persist_vs_Merge.md#how-does-spring-datas-save-choose-persist-or-merge) behave.

No flag — the version decides if it can; otherwise the ID, and with an assigned ID Hibernate has to ask the database.

</details>

### What makes an entity detached?
<details><summary>Show answer</summary>

- Its context closes: `close()`, or a transaction-scoped context ends at commit or rollback.
- Its context lets it go: `clear()` (all entities) or `detach()` (one entity).
- It is serialized: the copy that comes back is never managed — e.g. an entity stored in an HTTP session or sent to
  another service.

Detached means the context that knew it is gone or let it go.

</details>

### Entity returned from a `@Transactional` method — are later changes saved?
<details><summary>Show answer</summary>

- Without [Open Session in View](2.01_Persistence_Context.md#what-does-open-session-in-view-change): no. The
  transaction commits, the context closes, the entity is detached. A setter changes only the Java object — no context
  compares it, no SQL runs.
- With Open Session in View: the entity stays managed until the request ends.
  - The setter alone writes nothing — there is no transaction, so nothing flushes.
  - A later `@Transactional` call in the same request runs on the same `EntityManager`. Its commit flushes the whole
    context, so the controller's change is written by an unrelated method. 

A change is written only while a context tracks the object and a transaction is there to flush it.

</details>

### What happens to entities after a rollback?
<details><summary>Show answer</summary>

- They become detached: a transaction-scoped context closes on rollback too.
- Their fields are not undone: each object still holds the changes the database threw away.
- IDs and versions set during the transaction stay in the objects, though the database never kept them. A new entity
  now has an ID and looks detached, so passing it to `persist()` or `merge()` again can fail — the JPA spec warns
  these objects may not be reusable.

A rollback undoes the database, never the objects.

</details>

### Is a removed entity deleted at once?
<details><summary>Show answer</summary>

No. `remove()` only marks the entity and queues a `DELETE`. The SQL runs at the
[next flush](2.04_Flush.md#when-does-hibernate-flush-on-its-own),
[after all inserts and updates](2.04_Flush.md#in-what-order-does-flush-send-sql). Until then the row is still in the
database, and an error such as a foreign key from another table shows up only at flush.

`remove()` schedules; flush deletes.

</details>

### `persist()` on a removed entity?
<details><summary>Show answer</summary>

It becomes managed again and the queued `DELETE` is cancelled — the row stays. 
This works only before the flush sends the `DELETE`.

Until flush, a `remove()` can be taken back.

</details>

### `remove()` on a detached entity?
<details><summary>Show answer</summary>

`IllegalArgumentException` — `remove()` accepts only managed entities, so nothing is deleted.

```java
User u = userService.load(1L);   // its transaction is over: u is detached
em.remove(u);                    // IllegalArgumentException
```

`remove()` only takes what the context already tracks.

</details>

### How do you delete a detached entity?
<details><summary>Show answer</summary>

Get a managed instance first, then remove that:

- `em.remove(em.find(User.class, u.getId()))` — one `SELECT`; cascades and `@PreRemove` callbacks run, and the
  version is checked against the loaded row.
- `em.remove(em.merge(u))` — also a `SELECT`, plus copying `u`'s fields onto the loaded object first; the version
  check uses `u`'s version, so a stale `u` fails with `OptimisticLockException`. Spring Data's `delete(entity)` does
  this load-and-merge step for you.
- A bulk `delete from User u where u.id = :id` — one statement, no `SELECT`, but no cascades, no callbacks, no
  version check, and copies already in the context
  [go stale](2.01_Persistence_Context.md#why-do-bulk-updates-leave-stale-entities).

`remove()` needs a managed instance — load one, or skip the context with a bulk `DELETE`.

</details>

### `persist()` on a detached entity?
<details><summary>Show answer</summary>

**"detached entity passed to persist"** — `persist()` means "new object, `INSERT` it", but this object has an ID, so
Hibernate sees an existing row and refuses.

- Common cause: setting the ID by hand on a new object whose ID is generated (`user.setId(5L)`).
- Also: passing an object loaded in an earlier transaction.
- With an assigned ID (no generator) the ID is expected; `persist()` fails only when that ID is already in the
  context (at once) or already in the database (at flush, as a constraint error).

`persist()` means `INSERT` — an object that looks like an existing row is refused.

</details>

### A managed entity points to a new, unsaved one — what happens at flush?
<details><summary>Show answer</summary>

**"object references an unsaved transient instance"** — the flush fails.

```java
Order order = em.find(Order.class, 1L);
order.setCustomer(new Customer("Ann"));   // never persisted; no cascade on this field
// flush: TransientPropertyValueException
```

To write the order's foreign key, Hibernate needs the customer's ID — and the customer has no row yet.

A foreign key needs the other row to exist first.

</details>

### What does `getReference()` return — and when does it fail?
<details><summary>Show answer</summary>

- It returns a proxy with only the ID filled in; no `SELECT` runs. If the entity is already in the context, you get
  that object instead.
- The `SELECT` runs on first access to any field other than the ID.
- If the row does not exist, that first access throws `EntityNotFoundException` — far from the `getReference()` line.
  If the context is closed by then, you get `LazyInitializationException` instead.
- Main use: set a foreign key without loading the row — `order.setCustomer(em.getReference(Customer.class, 7L))`.

`getReference()` promises the row exists; the promise is checked only when you touch it.

</details>

### Write calls with no transaction?
<details><summary>Show answer</summary>

- On a Spring-injected (transaction-scoped) `EntityManager`, `persist()`, `merge()`, `remove()` and `flush()` throw
  `TransactionRequiredException` at the call: "No EntityManager with actual transaction available".
- An application-managed (extended) `EntityManager` accepts `persist()` outside a transaction and queues it; nothing
  is written until a transaction commits. `flush()` still needs a transaction.
- Spring Data repository methods are `@Transactional` themselves, so `repository.save()` works without one — each
  call commits on its own.

No transaction, no writes — Spring's `EntityManager` refuses at the call.

</details>

### Lifecycle callbacks — when does each fire?
<details><summary>Show answer</summary>

- `@PrePersist` — inside the `persist()` call (for `merge()` of a new object, on the copy). A generated ID may not be
  set yet.
- `@PostPersist` — after the `INSERT` runs: at flush, or inside `persist()` for `IDENTITY`.
- `@PreUpdate` — at flush, and only if dirty checking found a change; not when the setter is called.
- `@PostUpdate` — after the `UPDATE`.
- `@PreRemove` — inside the `remove()` call; `@PostRemove` — after the `DELETE`.
- `@PostLoad` — after the entity is loaded into the context, and after `refresh()`.
- None of them fire for bulk JPQL or native statements.

"Pre" fires on the call for persist and remove, but at flush for update; "Post" fires after the SQL.

</details>
