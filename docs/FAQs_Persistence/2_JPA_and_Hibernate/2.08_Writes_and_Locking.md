### What does batching fix — and not fix?
<details><summary>Show answer</summary>

Without batching, Hibernate sends each `INSERT` / `UPDATE` on its own and waits for the database to answer: one
network round trip per row. With batching, one round trip carries many statements. 10,000 rows at 1 ms per trip is
10 s of waiting alone; with a batch size of 50 it is 200 trips, about 0.2 s.

What it does not fix:

- **Commit** — all batches run in one transaction. One bad row fails its batch (`BatchUpdateException`), and the
  whole transaction rolls back, earlier batches included. To keep the good rows,
  [commit in chunks](#how-do-you-keep-good-rows-when-some-fail).
- **Memory** — the context still holds every entity, and each flush still dirty-checks all of them. Only
  [`clear()`](#does-flush-empty-the-context) frees them.
- **Work in the database** — each row still goes through constraints, indexes and triggers, and the one long
  transaction holds its locks until the end.

Batching cuts round trips — nothing else.

</details>

### How do you keep good rows when some fail?
<details><summary>Show answer</summary>

Commit in chunks. Each chunk of rows gets its own transaction, so a bad row costs only its chunk. When a chunk fails,
retry its rows one per transaction: the good ones commit, the bad ones get recorded.

```java
public void importAll(List<Row> rows) {        // no @Transactional: each write() commits on its own
  for (List<Row> chunk : partition(rows, 500)) {
    try {
      writer.write(chunk);                     // one transaction: 500 rows commit, or none
    } catch (RuntimeException e) {             // chunk rolled back
      for (Row row : chunk) {
        try {
          writer.write(List.of(row));          // one row per transaction finds the bad ones
        } catch (RuntimeException rowError) {
          failures.record(row, rowError);      // own transaction; the rest of the chunk is kept
        }
      }
    }
  }
}
```

- A chunk is not a JDBC batch. The batch is one round trip; the chunk is one transaction. A chunk of 500 with batch
  size 50 sends 10 batches, then commits.
- `write()` takes input rows and builds the entities inside. Objects from a rolled-back transaction keep the IDs they
  got, so `persist()` treats them as detached and throws.
- The import is no longer all-or-nothing. If the job dies halfway, earlier chunks stay committed, so a rerun must
  know where to restart or skip rows already in (e.g. by a unique business key).
- Spring Batch does the same in a chunk step with skip: commit per chunk, then item by item after a failed write.

One transaction per chunk — a bad row costs its chunk, not the whole run.

</details>
