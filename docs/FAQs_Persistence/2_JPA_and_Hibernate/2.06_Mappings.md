## Relationships

### One-to-many — what can go wrong?
<details><summary>Show answer</summary>

```java
@Entity
class Post {
  @Id Long id;
  String title;
  @OneToMany(cascade = CascadeType.ALL)
  List<Comment> comments = new ArrayList<>();   // the only link between the two
}

@Entity
class Comment {
  @Id Long id;
  String text;                                  // no field pointing back to Post
}
```

A **unidirectional `@OneToMany`** (the parent has the list, but the child has no field pointing back) forces
Hibernate to do extra work to manage the foreign key:

- **The Default Penalty (Extra Table & Inserts):** If you use only `@OneToMany`, Hibernate uses an extra link table
  (e.g., `post_comments` between `post` and `comment`). Every time you add a child, you get one INSERT for the child,
  plus an extra INSERT into the link table.
- **The `@JoinColumn` Penalty (Extra Updates):** If you add `@JoinColumn(name = "post_id")`, the link table
  disappears, but you get a new problem: extra UPDATEs. Because the child entity doesn't know about its parent,
  Hibernate by default inserts the child with a NULL foreign key, then issues a separate update:
  ```sql
  insert into post (id, title) values (1, 'JPA');
  insert into comment (id, text) values (10, 'a');          -- Inserts with NULL post_id
  update comment set post_id = 1 where id = 10;             -- Extra UPDATE to fix it
  ```

**The Root Cause:** The `post_id` foreign key lives in the `comment` table, but `Comment` has no field for it. 
Only `Post` holds the link, so Hibernate has to write it in separate statements after the child is already inserted.

</details>

### One-to-many — how to map it right?
<details><summary>Show answer</summary>

```java
@Entity
class Comment {
  @Id Long id;
  String text;
  @ManyToOne(fetch = FetchType.LAZY)            // not the EAGER default
  @JoinColumn(name = "post_id")
  Post post;                                    // the child holds the link: it writes post_id
}

@Entity
class Post {
  @Id Long id;
  String title;
  @OneToMany(mappedBy = "post", cascade = CascadeType.ALL)
  List<Comment> comments = new ArrayList<>();   // only shows what Comment.post says; never written from

  void addComment(Comment c) {                  // sets both sides
    comments.add(c);
    c.post = this;
  }
  // removeComment(...) mirrors it
}
```

The `post_id` column is in the `comment` table, so `Comment` owns the link with `@ManyToOne`.
The list on `Post` says `mappedBy = "post"`: it only shows what `Comment.post` says,
and Hibernate ignores it when writing. Each comment is inserted with `post_id` already set —
no link table, no extra UPDATE, unlike
[mapping it from the parent only](#one-to-many-mapped-from-the-parent-only--what-goes-wrong):

```sql
insert into post (id, title) values (1, 'JPA');
insert into comment (id, text, post_id) values (10, 'a', 1);
insert into comment (id, text, post_id) values (11, 'b', 1);
```

Hibernate writes only from `Comment.post`, so adding to the list alone leaves `post_id` empty.
`addComment` sets both sides, so the objects in memory and the database agree.

Don't need `post.getComments()`? Keep only the `@ManyToOne`, and query comments by post when needed.

The foreign key's table decides the owner: the child holds `@ManyToOne`, the parent's list is `mappedBy`.

</details>

### Many-to-many if the join table has extra columns — how?
<details><summary>Show answer</summary>

**The Problem:**
A standard `@ManyToMany` hides the join table from your Java code. 
If that table has extra columns (like `enrolled_on` or `grade`), there is nowhere to map them.

**The Solution:** Promote the join table to an entity.
Drop `@ManyToMany`, create a new `@Entity`, `Enrollment`, for the join table itself, and put the extra columns on it.
One many-to-many becomes two one-to-many links: `Student` → `Enrollment` ← `Course`. Each link has two ends:

- `@ManyToOne` on `Enrollment` — one to `Student`, one to `Course`. 
   Required: this end owns the link and writes `student_id` and `course_id`.
- `@OneToMany(mappedBy = ...)` on `Student` and on `Course` — the same link seen from the other end, as a list.
  Optional: add it only if you need `student.getEnrollments()`.

```java
@Entity
class Enrollment {                            // the join table, now an entity
  @Id @GeneratedValue
  private Long id;

  @ManyToOne(fetch = FetchType.LAZY)          // owns the link: writes student_id
  private Student student;

  @ManyToOne(fetch = FetchType.LAZY)          // owns the link: writes course_id
  private Course course;

  private LocalDate enrolledOn;               // the extra column
}

@Entity
class Student {
  @Id @GeneratedValue
  private Long id;

  @OneToMany(mappedBy = "student")            // the same link, seen from Student
  private Set<Enrollment> enrollments = new HashSet<>();
}
// Course has the same: @OneToMany(mappedBy = "course")
```

A join row that carries data is an entity — map it as one.

</details>

### Removing one link from a many-to-many `List` — what SQL runs?
<details><summary>Show answer</summary>

```java
@Entity
class Post {
  @Id Long id;
  @ManyToMany
  List<Tag> tags = new ArrayList<>();        // a List with no order column
}

post.tags.remove(tag5);                      // remove 1 of 10 tags
```

Hibernate deletes every link row for that post, then re-inserts the ones that should stay. If a post has 10 tags and
you remove 1, Hibernate runs 1 DELETE and 9 INSERTs:

```sql
delete from post_tag where post_id = 1;
insert into post_tag (post_id, tag_id) values (1, 2);
insert into post_tag (post_id, tag_id) values (1, 3);
-- ...one INSERT per remaining tag
```

**The Root Cause (The "Bag" Problem):**
A Java `List` allows duplicates. In Hibernate, a `List` with no order column is called a **bag**. Because a bag could
hold the same `(post_id, tag_id)` pair twice, that pair doesn't point to one row, and the join table has no other key.

Since Hibernate can't target one of two identical rows with SQL, it deletes the whole collection in the database and
rebuilds it from the current Java `List`.

**The Fix:**
Use a `Set` instead of a `List` for `@ManyToMany`. A `Set` can't hold duplicates, so the pair points to exactly one row,
and Hibernate runs a single DELETE:

```sql
delete from post_tag where post_id = 1 and tag_id = 5;
```

</details>

## Owning side and `mappedBy`

### Which side of a relationship writes the foreign key?
<details><summary>Show answer</summary>

The **owning side** — the side whose mapping holds the foreign key column. Hibernate reads only that side when it
decides what to write. The other side carries `mappedBy`: it mirrors the owning field, and Hibernate ignores it on save.

A post has many comments; `post_id` is a column of the `comment` table, so `Comment.post` owns the link:

```java
@Entity
class Comment {
  @ManyToOne
  @JoinColumn(name = "post_id")
  private Post post;                          // owning side: writes post_id
}

@Entity
class Post {
  @OneToMany(mappedBy = "post")               // mirror of Comment.post
  private List<Comment> comments = new ArrayList<>();
}
```

`comment.setPost(post)` writes `post_id`. `post.getComments().add(comment)` alone writes nothing for it.

By relationship type:
- One-to-many / many-to-one: the many side always owns — JPA does not allow `mappedBy` on `@ManyToOne`.
- One-to-one: the side whose table has the foreign key column owns.
- Many-to-many: you choose; the side without `mappedBy` owns the link table.

The foreign key's table decides the owner; `mappedBy` marks the mirror, and a change made only on the mirror is not
saved.

</details>

### How do you keep both sides in sync?
<details><summary>Show answer</summary>

Give the parent add and remove methods that set both ends, and change the relationship only through them.

Each end fails on its own. Set only `comment.setPost(post)`: the database is right after flush, but in the same session
`post.getComments()` still lacks the comment — Hibernate hands back the same `Post` object and doesn't reload its list.
Add only to `post.getComments()`: `post_id` is never written, because that list is the
[mirror side](#which-side-of-a-relationship-writes-the-foreign-key).

```java
@Entity
class Post {
  @OneToMany(mappedBy = "post")
  private List<Comment> comments = new ArrayList<>();

  public void addComment(Comment comment) {
    comments.add(comment);      // keeps this object's list right
    comment.setPost(this);      // owning side: this is what gets saved
  }

  public void removeComment(Comment comment) {
    comments.remove(comment);
    comment.setPost(null);
  }
}
```

The database follows the owning side; your objects follow whatever you set — so one method sets both.

</details>

## Cascade and `orphanRemoval`

### Cascade remove vs orphan removal — difference?
<details><summary>Show answer</summary>

Both delete the children when the parent is deleted; only orphan removal also deletes a child that is taken out of the
parent's collection. A child taken out of its parent's collection is an **orphan**.

With `cascade = CascadeType.REMOVE`, `em.remove(post)` deletes the post's comments too, but
[`post.removeComment(c)`](#how-do-you-keep-both-sides-in-sync) deletes nothing: the comment row stays, with `post_id`
set to null.

With `orphanRemoval = true`, `em.remove(post)` deletes the comments as well, and `post.removeComment(c)` deletes that
comment's row on flush.

Cascade remove follows the parent's delete; orphan removal also follows the link — break the link, lose the child.

</details>

### When does cascading a delete go wrong?
<details><summary>Show answer</summary>

When the child doesn't belong to that one parent alone — something else still points at it, or it should live on after
the parent is gone. Three common places:
- On `@ManyToOne`: `Comment.post` with `cascade = REMOVE` (or `ALL`) — deleting one comment tries to delete its post,
  which the other comments still point to.
- On `@ManyToMany`: `Post.tags` with `REMOVE` — deleting a post tries to delete the tag `java`, which other posts still
  use.
- `CascadeType.ALL` on children that outlive the parent: `ALL` includes `REMOVE`, so `Department.employees` with `ALL`
  deletes the employees when a department is closed, instead of leaving them to move to another one.

A cascaded delete is safe only for a child the parent owns alone, for the child's whole life.

</details>

### Replacing a child collection with a new one — what breaks?
<details><summary>Show answer</summary>

On a loaded entity with `orphanRemoval = true`, Hibernate throws at flush instead of saving:

```java
@OneToMany(mappedBy = "post", orphanRemoval = true)
private List<Comment> comments = new ArrayList<>();

post.setComments(new ArrayList<>(newComments));   // post was loaded in this session
// flush → HibernateException: A collection with cascade="all-delete-orphan"
//         was no longer referenced by the owning entity instance: com.example.Post.comments
```

When Hibernate loads `Post`, it puts its own collection class into the field — `PersistentBag` for a `List`,
`PersistentSet` for a `Set`. That object records which children were taken out, which is how Hibernate knows which rows
are orphans. A new `ArrayList` throws that record away: Hibernate can no longer tell which old children to delete, so
it refuses.

This applies only to a managed entity (loaded or saved in this session); a new list on a new entity before `persist()`
is fine.

With orphan removal, Hibernate's own collection object is the only record of which children to delete — lose the
object, lose the record.

</details>

## `equals` and `hashCode` on entities

### Entity `equals`/`hashCode` — what can go wrong?
<details><summary>Show answer</summary>

The two usual versions both break: the default from `Object` fails across sessions, and one built on the generated ID
fails before the entity is saved.

Default from `Object` (equal only when it is the same object): inside one session Hibernate gives one object per row,
so it works there. Load the same row in two sessions and you get two objects that are not equal — a `Set` holding the
old copy and the new one has two entries for one row.

Built on the ID: a new entity has `id == null`. Save it while it sits in a `HashSet`, and the new ID changes its hash,
so the set looks in the wrong bucket:

```java
Set<Post> posts = new HashSet<>();
Post post = new Post();     // id == null
posts.add(post);            // stored under the hash of null
em.persist(post);           // id set → hashCode changes
posts.contains(post);       // false, though the post is still inside
```

Two unsaved posts also both have `id == null`, so `Objects.equals(id, other.id)` calls them equal and a set keeps only
one of them.

An entity's identity must hold in every state — new, loaded, detached — and neither the object itself nor the generated
ID does.

</details>

### Entity `equals`/`hashCode` — which designs work?
<details><summary>Show answer</summary>

Three designs work: the ID with a null check and a fixed hash, a business key, or a UUID set when the object is
created. Which one fits depends on whether the entity has a value that exists from creation and never changes.

**Draft answer — `equals` and `hashCode` on the ID, as the IDE generates them; not yet right.**

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (o == null || getClass() != o.getClass()) return false;
  return Objects.equals(id, ((Post) o).id);
}

@Override
public int hashCode() {
  return Objects.hash(id);
}
```

**Why this draft is not the final design:**
- [Both ID failures](#entity-equalshashcode--what-can-go-wrong): the hash changes on save, and two unsaved posts count
  as equal.
- `getClass()` and the direct read of `.id` fail when `o` is a
  [lazy-loaded proxy](#lazy-loaded-entity-in-equals--what-breaks).

**Correct design (ID-based):**

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Post other)) return false;    // a proxy is a subclass: passes
  return id != null && id.equals(other.getId());   // getter reaches a proxy's data; unsaved posts never equal
}

@Override
public int hashCode() {
  return Post.class.hashCode();                    // fixed: the same before and after save, and for a proxy
}
```

The fixed hash puts every `Post` in one bucket, so a large `HashSet<Post>` searches item by item. Fine for the small
collections an entity holds; bad for a set of thousands.

**Alternative design (business key):** `equals` and `hashCode` on a unique value the entity has from creation and that
never changes — an ISBN, a product code.
- **Buys:** works in every state, spreads well across buckets, and means something to a reader.
- **Costs:** needs a value that is unique, set at creation, and never changes — many entities have none (an email can
  change).

**Alternative design (UUID set at creation):** a value made in Java the moment the object exists, stored in its own
column, and used in `equals` and `hashCode`.

```java
@Column(unique = true, updatable = false)
private UUID uuid = UUID.randomUUID();
```

- **Buys:** stable from the first moment, spreads well across buckets, no database call.
- **Costs:** one more column and index on every table that uses it.

Does the entity have a value that exists from creation and never changes? Yes → build on it. No → add a UUID, or use
the ID with a null check and a fixed hash.

</details>

### Lazy-loaded entity in `equals` — what breaks?
<details><summary>Show answer</summary>

A typical generated `equals` says a real `Post` and the lazy-loaded object for the same row are not equal. That lazy
object is a **Hibernate proxy**: a generated subclass of `Post` that loads the real data on the first method call.

It breaks in two places:
- `getClass() != o.getClass()` — the proxy's class is a generated subclass (`Post$HibernateProxy$...`), not `Post`, so
  the check fails for the same row.
- `other.id` — a direct field read on a proxy reads the proxy's own field, which stays null; the loaded data sits in a
  separate object behind it. Only method calls such as `other.getId()` reach that data.

The two meet when a real `Post` and a proxy for the same row end up side by side — for example a `Post` loaded in an
earlier session and `comment.getPost()` from a later one. Inside one session Hibernate hands out one object per row, so
there they never meet.

A lazy reference is a subclass whose own fields stay empty — a class check and a direct field read both see the wrong
thing.

</details>

### Lombok `@Data` on an entity — what breaks?
<details><summary>Show answer</summary>

`@Data` generates `equals`, `hashCode` and `toString` from every field, relationships included. On an entity that
breaks three ways:
- Loops: `Post.toString()` prints `comments`, each `Comment.toString()` prints `post`, which prints `comments` again —
  `StackOverflowError`. `hashCode()` can loop the same way on a two-way link.
- Hidden loading: `toString()` on a lazy `comments` field loads the collection — an extra query just to write a log
  line — or throws `LazyInitializationException` once the session is closed.
- A hash that changes: the hash covers every field, the ID included, so saving or editing an entity that sits in a
  `HashSet` loses it — the [same failure as hashing on the ID](#entity-equalshashcode--what-can-go-wrong).

Generated methods use every field, and on an entity that means links that loop or load, and values that change.

</details>

## ID generation

### `IDENTITY` vs `SEQUENCE` — which to pick, and why?
<details><summary>Show answer</summary>

Pick `SEQUENCE` when the database has sequences; use `IDENTITY` only when it has none, as on MySQL. The difference is
when the ID appears: out of the INSERT, or before it.

With `IDENTITY` the database sets the ID while it runs the INSERT (an auto-increment column). Hibernate keeps every
saved entity in the persistence context under its ID, so at `persist()` it must run the INSERT at once to get that ID.
It can't hold the INSERTs until flush, so it can't [send them as one batch](2.4_Writes_and_Locking.md).

With `SEQUENCE` Hibernate asks the sequence for the next value before the INSERT, so `persist()` gives the entity its
ID without touching the table. The INSERTs can wait until flush and go out as a batch. Taking a
[block of IDs per sequence call](#what-does-allocationsize-control) keeps the extra calls rare.

`IDENTITY`: the ID comes out of the INSERT, so the INSERT can't wait. `SEQUENCE`: the ID comes first, so the INSERTs
can wait and batch.

</details>

### What does `allocationSize` control?
<details><summary>Show answer</summary>

How many IDs Hibernate takes from one sequence call. With the default of 50, Hibernate calls the sequence once, hands
out the next 50 IDs from memory, and calls again only when they run out.

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "post_seq")
@SequenceGenerator(name = "post_seq", sequenceName = "post_seq", allocationSize = 50)
private Long id;
```

```sql
create sequence post_seq start with 1 increment by 50;   -- step matches allocationSize
```

The sequence's own step must equal `allocationSize`. Hibernate reads each value as the top of a block of 50, so a
sequence that steps by 1 returns values inside blocks already handed out — the same ID twice, a duplicate key error.

`allocationSize` is how many IDs one sequence call buys — and the sequence's own step must buy the same number.

</details>

### `AUTO` ID strategy — why avoid it?
<details><summary>Show answer</summary>

Because the provider picks the strategy, not you, and its pick depends on the database and the Hibernate version.

`@GeneratedValue` with no strategy means `AUTO`. For a numeric ID, Hibernate 5 and later pick a sequence — fine on
PostgreSQL. MySQL has no sequences, so Hibernate fakes one with a one-row table: each new block of IDs costs a SELECT
and an UPDATE on that row in a separate transaction, and every insert that needs a new block waits on that row's lock.

The pick also changes when you switch databases or upgrade Hibernate, so the same code can silently start using a
different ID scheme.

`AUTO` hands the choice to the provider, and the choice moves with the database and the version.

</details>
