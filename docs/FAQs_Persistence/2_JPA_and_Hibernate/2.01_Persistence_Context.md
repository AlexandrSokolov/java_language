# Persistence Context

The place where Hibernate keeps the entities it currently manages, one instance per row. Covers what it holds,
how long it lives, and what goes wrong when it grows too large or stops matching the database.

### What does the persistence context hold?
<details><summary>Show answer</summary>

With plain JDBC a loaded row is just an object: load it twice and you get two copies, change it and nothing happens
until you write the `UPDATE` yourself. Hibernate keeps a memory per `EntityManager` (per `Session`) instead — the
**persistence context**:

- Each loaded or saved entity, in a map keyed by entity type + ID — one Java object per row. Entities in this map are
  [managed](2.02_Entity_States.md#what-states-can-an-entity-be-in).
- A copy of the values each entity had when it was loaded (the snapshot), used to
  [find changes](2.03_Dirty_Checking.md#how-does-hibernate-know-to-run-an-update).

Next to it, the session keeps the queue of SQL waiting for the
[next flush](2.04_Flush.md#when-does-hibernate-flush-on-its-own).

One object per row, plus what it looked like at load — so Hibernate knows what to write.

</details>

### `EntityManager`, context, transaction — how are they related?
<details><summary>Show answer</summary>

- One `EntityManager` (Hibernate: `Session`) owns exactly one persistence context.
- The context is not the transaction. With an [extended context](#how-long-does-a-persistence-context-live), one
  context lives across several transactions.
- In Spring, the injected `EntityManager` is a proxy. Each call goes to the real `EntityManager` bound to the current
  transaction — so each transaction, and each thread, gets its own context.

The `EntityManager` is the handle, the context is the memory behind it, and in Spring the transaction picks which
memory you get.

</details>

### How long does a persistence context live?
<details><summary>Show answer</summary>

- **Transaction-scoped** (the default in Spring and Jakarta EE): created on first use inside a transaction, closed at
  commit or rollback. Every entity in it becomes [detached](2.02_Entity_States.md#what-makes-an-entity-detached).
- **Extended**: lives across many transactions until the `EntityManager` is closed — an application-managed
  `EntityManager`, or `@PersistenceContext(type = PersistenceContextType.EXTENDED)`.
- **Per web request**: with [Open Session in View](#what-does-open-session-in-view-change), on by default in Spring
  Boot, one context spans the whole HTTP request and every transaction in it. *(unverified for Spring Boot 4)*

Its life is tied to the transaction, the `EntityManager`, or the request — and that decides when entities go
detached.

</details>

### Same ID loaded twice — same object?
<details><summary>Show answer</summary>

**Identity map:** yes, inside one context.

```java
User a = em.find(User.class, 1L);
User b = em.find(User.class, 1L);   // no SQL: found in the context
assert a == b;
```

- A query that returns row 1 also returns that same object.
- Two different contexts (two transactions) give two different objects for the same row.

One context, one object per row.

</details>

### Does `find()` always hit the database?
<details><summary>Show answer</summary>

No. `find()` looks in three places, in order:

- the persistence context — if the entity is there, no SQL;
- the second-level cache, if it is turned on for that entity;
- the database — a `SELECT` by ID.

`find()` checks memory before it asks the database.

</details>

### Does a query refresh an already loaded entity?
<details><summary>Show answer</summary>

No.

- You load `User` 1 with name `Ann`. Another transaction changes it to `Bob` and commits.
- You run `select u from User u`. The SQL reads `Bob`, but Hibernate sees ID 1 is already in the context and returns
  the existing object — still `Ann`. The new values in the row are ignored.
- This protects your own unflushed changes: if queries overwrote loaded objects, edits made in memory would be lost.
- A scalar or DTO query (`select u.name from User u`) does not go through the context, so it returns `Bob`.

So the context gives repeatable reads for entity objects only — it is not the database's `REPEATABLE READ`
isolation.

A loaded entity keeps its values until you refresh it; queries don't touch it.

</details>

### Inner `REQUIRES_NEW` transaction — same context?
<details><summary>Show answer</summary>

No. Spring suspends the outer transaction and opens a new `EntityManager` — a new, empty context — for the inner one.

- The outer method loads `Account` 1. The inner method loads `Account` 1 again: a second `SELECT`, a second object.
- The inner method changes the balance and commits.
- The outer object still holds the old balance. If the outer method then changes any field, its `UPDATE` writes all
  columns by default — the old balance included — and the inner change is lost (**lost update**), unless the entity
  has a `@Version`.

New transaction, new context: the same row lives twice in memory.

</details>

### What does Open Session in View change?
<details><summary>Show answer</summary>

Spring opens the `EntityManager` when the web request starts and closes it when the response is written — not when
the `@Transactional` method returns. In Spring Boot it is on by default (`spring.jpa.open-in-view`).
*(unverified for Spring Boot 4)*

- Entities stay managed after the service returns, so lazy fields load in the controller or view without
  `LazyInitializationException`.
- Those lazy loads run outside any transaction: each one is its own `SELECT` in auto-commit mode, and a loop in the
  view easily turns into N+1 queries.

It hides the lazy-loading error by moving the queries out of the transaction and into the view.

</details>

### Why does a big import job run out of memory?
<details><summary>Show answer</summary>

Every entity the job persists or loads stays in the context until the transaction ends — the object plus its snapshot
copy. Nothing is removed on its own: 100,000 rows means 100,000 objects and 100,000 snapshots that the garbage
collector cannot free, because the context still points to them.

The context never forgets on its own — it grows until it is cleared or closed.

</details>

### `clear()` vs `detach()` vs `close()`?
<details><summary>Show answer</summary>

- `detach(entity)` — one entity leaves the context (plus associations marked `CascadeType.DETACH`). Hibernate's
  `evict()` does the same.
- `clear()` — every entity leaves; the context is empty, the `EntityManager` stays usable.
- `close()` — every entity leaves and the `EntityManager` can't be used again.

One entity, all entities, or the whole `EntityManager`.

</details>

### What happens to unflushed changes on `clear()`?
<details><summary>Show answer</summary>

They are dropped, with no warning.

```java
user.setName("Bob");
em.clear();          // the pending UPDATE is thrown away
// commit: no UPDATE for user
```

- Pending inserts are dropped too: an entity persisted with a sequence ID has its ID set, but its row never appears.
- With an `IDENTITY` ID the row stays: its `INSERT` already ran
  [inside `persist()`](2.04_Flush.md#why-does-persist-sometimes-insert-at-once).

`clear()` throws away whatever flush has not sent yet.

</details>

### Why do bulk UPDATEs leave stale entities?
<details><summary>Show answer</summary>

A bulk statement — JPQL `executeUpdate()` or native SQL — goes straight to the database. Hibernate does not touch the
objects already in the context.

```java
Account a = em.find(Account.class, 1L);   // status = ACTIVE
em.createQuery("update Account a set a.status = :s").setParameter("s", CLOSED).executeUpdate();
a.getStatus();                            // still ACTIVE in memory
```

If you then change another field of `a`, the flush
[writes every column](2.03_Dirty_Checking.md#why-does-the-update-list-every-column) and puts `ACTIVE` back — the
bulk change is lost.

A bulk statement changes rows, not the objects you already hold.

</details>

### What does `refresh()` do to unsaved changes?
<details><summary>Show answer</summary>

It overwrites them. `refresh()` runs a `SELECT` and copies the database values into the managed object and its
snapshot, so changes not yet flushed are lost.

Changes already flushed in the same transaction survive: the `SELECT` runs inside your transaction and sees them.

`refresh()` trusts the database over memory.

</details>

### Can threads share one `EntityManager`?
<details><summary>Show answer</summary>

- No. An `EntityManager` and its context are not thread-safe: two threads using one at the same time can corrupt its
  internal maps and its queue of pending SQL.
- In Spring, the injected `@PersistenceContext EntityManager` is a shared proxy. It is safe to share because each call
  goes to the real `EntityManager` bound to the calling thread's transaction.
- The `EntityManagerFactory` is thread-safe and meant to be shared.

One `EntityManager` per thread; the factory is the shared part.

</details>

### Can you keep using the context after an exception?
<details><summary>Show answer</summary>

No. Roll back and throw the context away.

- A failed flush can leave objects holding IDs, versions or values that never reached the database, so the context
  no longer matches the rows. Hibernate treats every exception from the session as one you can't recover from.
- JPA marks the transaction for rollback on almost every `PersistenceException` (except `NoResultException`,
  `NonUniqueResultException`, `LockTimeoutException`, `QueryTimeoutException`). In Spring, catching the exception and
  carrying on ends with `UnexpectedRollbackException` at commit.

After an exception the context is broken — start a new one.

</details>

### First-level vs second-level cache?
<details><summary>Show answer</summary>

- **First-level** — the persistence context itself: one per `EntityManager`, always on, holds the managed objects,
  gone when the context closes.
- **Second-level** — one per `EntityManagerFactory`, shared by all sessions and threads, off until you configure a
  cache provider and mark entities cacheable. It stores field values, not objects; each context builds its own
  object from them.

First-level is private and always on; second-level is shared and opt-in.

</details>
