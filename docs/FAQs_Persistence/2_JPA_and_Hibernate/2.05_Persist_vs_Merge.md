# `persist` vs `merge`

The two ways to hand an entity to Hibernate: `persist` makes the object you pass managed, `merge` copies its state
onto a managed instance. Covers when to use each and how Spring Data's `save()` picks between them.

### What does `persist()` do with your object?
<details><summary>Show answer</summary>

- Makes that exact object managed — no copy, and it returns `void`.
- Sets a generated ID on it (`SEQUENCE`, `IDENTITY`) and queues the `INSERT`; for `IDENTITY` the `INSERT` runs right
  away.
- Cascades to associations marked `CascadeType.PERSIST`.
- Accepts only new objects — a [detached one is refused](2.02_Entity_States.md#persist-on-a-detached-entity).

`persist()` adopts the object you pass.

</details>

### What does `merge()` return — and why care?
<details><summary>Show answer</summary>

`merge()` copies the state of the object you pass onto a managed object and returns that managed object. The one you
passed stays new or detached.

```java
User u = new User(1L, "Alice");   // row 1 already exists
User managed = em.merge(u);
u.setName("Bob");                 // lost: u is not managed
managed.setName("Bob");           // written at flush
```

- `em.contains(u)` is `false`; `em.contains(managed)` is `true`.
- For a new object, the generated ID is set on the returned copy, not on `u`.

`merge()` hands back a different object — keep working with what it returns.

</details>

### Why does `merge()` run a SELECT first?
<details><summary>Show answer</summary>

It needs a managed object to copy onto. If no object with that ID is in the context, Hibernate loads the row by ID —
a `SELECT`, plus more for associations marked `CascadeType.MERGE`. The loaded row also tells it whether the object is
new or existing. Then the fields are copied, and dirty checking decides the `UPDATE` at flush.

No `SELECT` happens if the entity is already in the context.

`merge()` needs a managed copy to write into, and getting one usually means a `SELECT`.

</details>

### `merge()` with a null ID, called twice?
<details><summary>Show answer</summary>

Two rows.

```java
User u = new User("Ann");   // id == null
em.merge(u);                // new → managed copy #1, INSERT queued
em.merge(u);                // u.id is still null → managed copy #2, second INSERT
```

`merge()` sets the ID on the copy it returns, never on `u`, so `u` still looks new on the second call.

`merge()` never changes its argument, so a new object stays new.

</details>

### `merge()` when the row was deleted meanwhile?
<details><summary>Show answer</summary>

The detached object has an ID, but the `SELECT` finds no row.

- Older Hibernate treated the object as new and inserted it — with a generated ID, under a new ID. Deleted data came
  back without any error. *(unverified)*
- Since Hibernate 6.6, it throws `OptimisticLockException` when it can tell the object is detached: the entity has a
  generated ID or a non-primitive `@Version`. *(unverified)*

A missing row means a conflict, not a new row.

</details>

### Merging a half-filled object?
<details><summary>Show answer</summary>

Every missing field is written as `null`.

```java
User u = new User();
u.setId(7L);
u.setName("Ann");   // from a PUT request that sent only id and name
em.merge(u);        // email, phone, ... of user 7 become null at flush
```

`merge()` copies all fields onto the managed `User` 7 — it can't tell "not sent" from "set to null".

`merge()` copies the whole object, so a missing field is a `null` field.

</details>

### `merge()` vs Hibernate's `update()`?
<details><summary>Show answer</summary>

- `merge(u)` copies `u`'s state onto a managed object (with a `SELECT` if needed) and returns it; `u` stays detached.
- Hibernate's [deprecated](#status-of-save--update--saveorupdate) `Session.update(u)` makes `u` itself managed again,
  with no `SELECT`. With no snapshot to compare against, it always queues an `UPDATE`.
- If the context already holds another object with the same ID, `update()` throws `NonUniqueObjectException`;
  `merge()` just copies onto that object.

`update()` brings back the same object; `merge()` brings back a copy.

</details>

### Status of `save` / `update` / `saveOrUpdate`?
<details><summary>Show answer</summary>

- Hibernate 6.0 deprecated `Session.save()`, `update()`, `saveOrUpdate()` and `delete()` in favor of the JPA
  methods; Hibernate 7.0 removed them. *(unverified)*
- Replacements: `save()` → `persist()` (but `save()` returned the ID, `persist()` returns `void`); `update()` and
  `saveOrUpdate()` → `merge()`; `delete()` → `remove()`.

Hibernate's own write methods are gone — the JPA ones are the API.

</details>

### How does Spring Data's `save()` choose persist or merge?
<details><summary>Show answer</summary>

`save()` calls `persist()` if the entity is new, otherwise `merge()`. "New" is decided in this order:

- the entity implements `Persistable` → its own `isNew()`;
- it has a non-primitive `@Version` field → new if the version is `null`;
- otherwise → new if the ID is `null` (or `0` for a primitive ID).

Consequences:

- Assigned IDs (a UUID set in the constructor, a natural key) are never `null`, so every `save()` of a new entity goes
  to `merge()` — a [`SELECT`](#why-does-merge-run-a-select-first) before each `INSERT`.
- Since `save()` may merge, use the object it [returns](#what-does-merge-return--and-why-care), not the one you
  passed.

`save()` guesses new-or-not from the ID and the version; a wrong guess costs a `SELECT`.

</details>
