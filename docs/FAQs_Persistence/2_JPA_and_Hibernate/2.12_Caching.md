# Caching

- First-level cache — the persistence context.
- Second-level cache — shared across sessions; when to use it.
- Query cache.

## First-level cache

### Loading the same row twice in one session — what happens?
<details><summary>Show answer</summary>

One SELECT, and the second load returns the same object. The session keeps every entity it loaded in a map by type and
ID — the **first-level cache**, which is the persistence context itself — and `find()` looks there before it goes to the
database. It is always on; there is no setting to turn it off.

```java
Post a = em.find(Post.class, 1L);   // SELECT from post
Post b = em.find(Post.class, 1L);   // no SELECT: taken from the session
a == b;                             // true: one object per row in a session
```

A session holds one object per row and hands it back instead of asking the database again.

</details>

### How long does the first-level cache live?
<details><summary>Show answer</summary>

As long as its session. In Spring that is one transaction by default — or the whole web request with
[Open Session in View](2.07_Fetching.md#what-does-open-session-in-view-do) — and it belongs to one thread; no other
session or request sees it.

```java
@Transactional
public void first() {
  em.find(Post.class, 1L);   // SELECT; cached until this transaction ends
}

@Transactional
public void second() {
  em.find(Post.class, 1L);   // new transaction, new session: SELECT again
}
```

The first-level cache lives and dies with its session — it never spans two transactions or two threads.

</details>

**Later:**

### Row changed by someone else after loading — what does the session see?
<details><summary>Show answer</summary>

The old values. Once a row is loaded, the session keeps its object, and neither `find()` nor a query replaces its
values.
- `find()` returns the object from the session, so it never sees the change.
- A JPQL query does go to the database and gets the new row, but for an ID the session already holds, Hibernate
  returns the existing object and throws the new values away. It can't overwrite the object: it may hold changes not
  flushed yet.

```java
Post post = em.find(Post.class, 1L);                  // title = "Old"
// another app updates the row: title = "New"
em.find(Post.class, 1L).getTitle();                   // "Old": no SELECT
em.createQuery("select p from Post p where p.id = 1", Post.class)
  .getSingleResult()
  .getTitle();                                        // "Old": SELECT ran, new values dropped
```

Inside a session, the first load of a row wins.

</details>

### Loading 100,000 entities in one session — what goes wrong?
<details><summary>Show answer</summary>

Memory fills up and every flush gets slower: the session keeps every entity it loaded or saved until it ends, plus a
copy of each one's loaded values for dirty checking.

For each managed entity Hibernate holds the object and a snapshot of its state as loaded. At flush it compares every
object with its snapshot to find changes — 100,000 comparisons, even when nothing changed. Nothing is let go before the
session ends, so a long batch job in one transaction ends in `OutOfMemoryError`.

```java
@Transactional
public void importAll(List<Row> rows) {   // 100,000 rows
  for (Row row : rows) {
    em.persist(toEntity(row));            // each one stays in the session until the end
  }
}
```

The session forgets nothing until it ends, so its size and its flush cost grow with every entity it touches.

</details>

### Emptying the session before flush — what is lost?
<details><summary>Show answer</summary>

Every change not written yet: `clear()` detaches all entities and drops their pending inserts and updates, with no
error.

```java
for (int i = 0; i < rows.size(); i++) {
  em.persist(toEntity(rows.get(i)));
  if (i % 50 == 0) {
    em.clear();   // inserts queued since the last flush are dropped
  }
}
```

The detached objects still hold their changes in Java, but nothing tracks them any more, so they never reach the
database.

`clear()` throws away the session's to-do list together with its objects.

</details>

## Second-level cache

### What does the second-level cache add over the first?
<details><summary>Show answer</summary>

A cache shared by all sessions in one app instance, which lives as long as the application, not one transaction. A row
loaded in one transaction can be served to the next one without a SELECT.

```java
// transaction 1
em.find(Post.class, 1L);   // SELECT; values put in the second-level cache
// transaction 2, new session
em.find(Post.class, 1L);   // no SELECT: built from the second-level cache
```

Lookups by ID — `find()`, lazy loads — check the first-level cache, then the second-level cache, then the database.
JPQL queries still go to the database; only the [query cache](#what-does-the-query-cache-store) changes that. It is
off by default: it needs a cache provider and an opt-in per entity.

First-level: one session. Second-level: the whole app instance, across sessions — for lookups by ID.

</details>

### Second-level cache — how does it serve old data?
<details><summary>Show answer</summary>

When the row changes somewhere the cache doesn't hear about. Two common ways:
- Several app instances: each has its own local cache. Instance A updates the post and updates its own entry; instance
  B keeps its old entry and serves it until it expires.
- Writes that skip Hibernate: another application, plain JDBC, a database script. The cache never learns about them.

The cache stays right only for changes made through Hibernate in the same instance; every other write leaves it behind.

</details>

### Which entities fit the second-level cache?
<details><summary>Show answer</summary>

Entities read often and changed rarely, where a slightly old copy does no harm: countries, currencies, categories,
configuration.

Poor fits:
- Entities written often — each write updates or locks the cache entry, so the cache costs more than it saves.
- Entities where an old copy does real damage, like a stock count or an account balance, because the cache
  [can serve old data](#second-level-cache--how-does-it-serve-old-data).
- Big tables where each row is read only now and then — the cache fills with rows nobody asks for again.

Cache what is read many times per change, and only where a stale copy is harmless.

</details>

**Later:**

### What does the second-level cache keep for an entity?
<details><summary>Show answer</summary>

Its field values, not the object. Hibernate stores each entity as an array of plain values — the columns, plus the ID
of each to-one link — and builds a new object from them for every session that asks.

So two sessions reading the same cached row get two different objects, and a change made to one session's object can't
leak into another before commit. Collections are not part of the entry — they need
[their own cache](#caching-an-entity--are-its-collections-cached-too).

The second-level cache keeps data, not objects; each session still gets its own object.

</details>

### How do you turn on the second-level cache?
<details><summary>Show answer</summary>

Three steps: put a cache provider on the classpath, tell Hibernate to use it, and mark each entity to cache.

```properties
# hibernate-jcache plus a JCache provider (Ehcache 3, Caffeine) on the classpath
spring.jpa.properties.hibernate.cache.region.factory_class=jcache
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
```

```java
@Entity
@Cacheable                                            // JPA: this entity may be cached
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)   // Hibernate: how writes keep the cache right
class Country {
  @Id
  private String code;
}
```

Hibernate caches only the entities you mark; the `usage` value is one of the
[strategies](#second-level-cache-strategies--how-do-they-differ).

Provider, setting, then an opt-in per entity — nothing is cached until all three are in place.

</details>

### Second-level cache strategies — how do they differ?
<details><summary>Show answer</summary>

They differ in how a write keeps the cache from serving old data — from "no writes allowed" to joining the transaction:
- `READ_ONLY`: the entity never changes; an update fails. The cheapest, with no locking at all.
- `NONSTRICT_READ_WRITE`: removes the entry when the row changes, without a lock, so for a short moment another session
  can still read the old entry.
- `READ_WRITE`: locks the entry while the row changes; other sessions skip the cache and read the database until the
  commit puts the new values in.
- `TRANSACTIONAL`: the cache takes part in the database transaction itself; needs JTA and a cache that supports it.

The stronger the strategy, the more it locks: read-only locks nothing, transactional joins the transaction.

</details>

### Caching an entity — are its collections cached too?
<details><summary>Show answer</summary>

No. A collection has its own cache, turned on with `@Cache` on the collection field, and that cache keeps only the IDs
of the children.

```java
@Entity
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
class Post {
  @OneToMany(mappedBy = "post")
  @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)   // caches the list of comment IDs
  private List<Comment> comments = new ArrayList<>();
}
```

With the IDs in hand, Hibernate loads each child by ID — from the second-level cache if `Comment` is cached, otherwise
with one SELECT per comment.

A cached collection is a list of IDs; the children it points to need their own cache.

</details>

### Lookup by a unique business key — how do you cache it?
<details><summary>Show answer</summary>

Mark the key `@NaturalId` and the entity `@NaturalIdCache`: Hibernate then keeps a separate cache from that key to the
primary key, and loads the entity by ID from the second-level cache.

```java
@Entity
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
@NaturalIdCache
class Book {
  @Id
  private Long id;

  @NaturalId
  private String isbn;
}

Book book = em.unwrap(Session.class)
              .bySimpleNaturalId(Book.class)
              .load("978-0134685991");   // ISBN → ID from the cache, then the entity by ID
```

Without it, a lookup by key is a query, and queries
[skip the second-level cache](#what-does-the-second-level-cache-add-over-the-first). A JPQL query
`where b.isbn = :isbn` doesn't use the natural-ID cache either; only Hibernate's natural-ID lookup does.

Lookups by ID hit the cache, lookups by key don't — a natural-ID cache turns the key into an ID first.

</details>

### Bulk update or native SQL — what happens to the caches?
<details><summary>Show answer</summary>

The first-level cache keeps the old values, and Hibernate clears whole parts of the second-level and query caches,
because it can't tell which rows changed.
- First-level: the statement runs straight in the database. Entities already in the session keep their old values.
- Bulk JPQL (`update Post p set ...`): Hibernate knows the entity type, so it drops every cached `Post` and every
  cached query on the `post` table.
- Native SQL update: Hibernate doesn't know which tables the statement touches, so it clears the whole second-level
  cache and query cache — unless the query declares its tables.

```java
em.createQuery("update Post p set p.status = :s where p.createdAt < :d")
  .setParameter("s", Status.ARCHIVED)
  .setParameter("d", cutoff)
  .executeUpdate();   // every cached Post and every cached query on post is dropped
```

A statement that skips the entities can't update caches row by row — the session's copies stay old, and the shared
caches are cleared in whole parts.

</details>

### Database changed outside the app — how do you drop stale entries?
<details><summary>Show answer</summary>

Evict them through JPA's `Cache` API, which you get from the `EntityManagerFactory`:

```java
Cache cache = emf.getCache();
cache.evict(Post.class, 1L);   // one entity
cache.evict(Post.class);       // every cached Post
cache.evictAll();              // the whole second-level cache
```

The app still has to learn about the change — from a message, an event, or a call from the system that changed the
data.

Hibernate can't see outside writes; whoever knows about them has to evict by hand.

</details>

### Is the second-level cache helping — how do you check?
<details><summary>Show answer</summary>

Turn on Hibernate statistics and compare hits with misses. Hibernate then counts how often an entity was found in the
cache (hit), not found (miss), and put in (put).

```properties
spring.jpa.properties.hibernate.generate_statistics=true
```

Read the counts in the logs, or through `SessionFactory.getStatistics()`, which Micrometer can export. Many misses and
puts with few hits mean the cache does extra work for nothing — the entity doesn't
[fit](#which-entities-fit-the-second-level-cache).

A cache is helping only when hits clearly outnumber misses — count them before trusting it.

</details>

### Spring's `@Cacheable` vs JPA's `@Cacheable` — difference?
<details><summary>Show answer</summary>

Same name, different layers. Spring's caches what a method returns, by its arguments. JPA's marks an entity for
Hibernate's second-level cache.

```java
@org.springframework.cache.annotation.Cacheable("posts")   // Spring: caches this method's result by id
public PostDto find(Long id) {
  return toDto(postRepository.findById(id).orElseThrow());
}

@jakarta.persistence.Cacheable                            // JPA: Post may go into the second-level cache
@Entity
class Post { /* ... */ }
```

Spring's works for any object — DTOs, lists, API responses — and knows nothing about entities or transactions. JPA's
works only for entities and only for Hibernate's lookups by ID.

Spring's `@Cacheable` caches method results; JPA's caches entity rows.

</details>

## Query cache

### What does the query cache store?
<details><summary>Show answer</summary>

For a query text and its parameter values, the list of IDs the query returned — not the entities. The entities are
then loaded by ID, from the second-level cache if they are there.

```java
List<Post> posts = em.createQuery("select p from Post p where p.status = :s", Post.class)
                     .setParameter("s", Status.PUBLISHED)
                     .setHint("org.hibernate.cacheable", true)   // this query may use the query cache
                     .getResultList();
// cached: (query text, PUBLISHED) → [1, 5, 9, ...]
```

It is off by default: it needs `hibernate.cache.use_query_cache=true` and the hint on each query.

The query cache remembers which IDs a query returned; the rows themselves come from the entity cache.

</details>

**Later:**

### Query cache with entities not in the second-level cache — what goes wrong?
<details><summary>Show answer</summary>

Each cache hit turns into one SELECT per result: the query cache returns only IDs, and with no entity cache Hibernate
loads each ID from the database. 100 results → 100 SELECTs instead of one query.

A query cache without an entity cache trades one query for N.

</details>

### Query cache on a table that changes often — what happens?
<details><summary>Show answer</summary>

Every write to the table throws away every cached query that reads it, so the cache keeps emptying and its bookkeeping
is wasted work.

Hibernate records, per table, the time of the last insert, update or delete. A cached result older than that time is
ignored — not only results that include the changed row, but every cached query on that table.

One write to a table makes all its cached queries old, so a busy table leaves the query cache nothing to serve.

</details>
