## Lazy vs eager

### Which relationships load right away by default?
<details><summary>Show answer</summary>

- The to-one links load right away: `@ManyToOne` and `@OneToOne` are eager by default. 
- The collections wait: `@OneToMany` and `@ManyToMany` are lazy by default.

```java
@ManyToOne                         // eager by default
private Post post;

@OneToMany(mappedBy = "post")      // lazy by default
private List<Comment> comments;
```

One row loads now, a list waits — the default follows how much data the link can bring.

</details>

### How does a lazy link load later?
<details><summary>Show answer</summary>

Hibernate puts a placeholder in the field and runs the SELECT the first time your code uses it. 
- For a to-one link the placeholder is a **proxy** — a generated subclass of the entity class that holds only the ID. 
- For a collection it is Hibernate's own collection class (`PersistentBag`, `PersistentSet`), 
  which loads its rows on the first read.

```java
Comment comment = em.find(Comment.class, 10L);   // SELECT from comment only (post mapped with fetch = LAZY)
Post post = comment.getPost();                   // a proxy: no SELECT yet
post.getTitle();                                 // first method call → SELECT from post
```

Both run their SELECT through the persistence context that loaded the parent, so the parent must
[still be managed by it](#reading-a-lazy-link-after-the-transaction-ends--what-happens) — 
not closed, cleared, or detached.

A lazy link is a placeholder that runs its SELECT on first use, through the session that created it.

</details>

### Default eager loading — what does it cost?
<details><summary>Show answer</summary>

An eager link is loaded on every load of the entity, whether the caller reads it or not.

```java
class Comment { @ManyToOne Post post; }       // to-one default: fetch = EAGER
class Post    { @ManyToOne Author author; }
class Author  { @ManyToOne Company company; }
```

**Load by ID (`em.find`, Spring Data `findById`) — one query that joins the whole eager chain.** Hibernate writes
this SQL itself:

```java
Comment comment = em.find(Comment.class, 10L);
```

```sql
select c.*, p.*, a.*, co.*
from comment c
left join post p     on p.id  = c.post_id
left join author a   on a.id  = p.author_id
left join company co on co.id = a.company_id
where c.id = ?
```

You asked for one comment and got its post, author and company too, every time.

**Any query — your own JPQL or a Spring Data method — no joins, then one SELECT per post.** Hibernate turns the query
into SQL as written; the mapping's EAGER adds no join to it:

```java
List<Comment> comments = em.createQuery("select c from Comment c", Comment.class)
                           .getResultList();
```

```sql
select c.id, c.text, c.post_id from comment c       -- 1 query: comments only
select ... from post p where p.id = ?               -- then 1 per different post_id
select ... from post p where p.id = ?
-- ...
```

The rows bring back only `post_id`. Eager forbids a placeholder, so Hibernate loads each post right away, by ID, one at
a time: an [N+1](#listing-posts-then-each-posts-comments--what-goes-wrong) the query text doesn't show. Each of those
post loads brings the rest of its eager chain, so a deeper chain means more hidden work.

This is not only hand-written JPQL. Spring Data runs almost every repository method as a query: `findAll()`, derived
methods like `findByAuthorId(...)`, `@Query`. Only `findById` goes through `em.find`. So in a Spring Data project the
N+1 path is the usual one, not the rare one.

[Eager is fixed on the mapping](#eager-or-lazy--which-to-pick) and paid on every load: `find` pays in joins, queries
pay in hidden SELECTs.

</details>

### Eager or lazy — which to pick?
<details><summary>Show answer</summary>

For each use case we want two things from loading:

- **No extra queries** — the data comes in as few SELECTs as possible; no N+1.
- **No extra data** — only the links the use case reads are loaded.

**Eager on the mapping fails both, on every load.** Queries (your JPQL, Spring Data methods) load each linked entity
by ID afterwards, a [hidden N+1](#default-eager-loading--what-does-it-cost); `find` joins the whole eager chain even
when nothing reads it. It is fixed on the entity, so no query can turn it off.

**Lazy alone meets "no extra data".** The query loads the entity; its links stay as
[placeholders](#how-does-a-lazy-link-load-later). The risk is conditional: if the code then reads the link for each
row, that is one SELECT per row (N+1), or an error if the
[entity is no longer managed](#reading-a-lazy-link-after-the-transaction-ends--what-happens).

**Lazy plus loading the link in the query meets both.** A use case that reads the link
[asks for it in its own query](#how-to-load-a-lazy-link-with-its-parent) and gets it in the same SELECT. A use case
that doesn't read it pays nothing.

- **Buys:** the loading choice sits in the query, next to the code that reads the data.
- **Costs:** every use case must ask for what it reads. Nothing forces it; a forgotten link is a silent N+1.

So: map every link lazy (write it explicitly on to-one, whose default is EAGER) and decide loading per query.

Eager decides once on the entity for every query; lazy lets each query load exactly what it reads.

</details>

### How to load a lazy link with its parent?
<details><summary>Show answer</summary>

The link stays lazy on the mapping; the query asks for it, so the parent and the link come back in one SELECT. The
tool depends on whether you write the query text yourself.

**Your own JPQL — `join fetch`.**

```java
em.createQuery("select c from Comment c left join fetch c.post", Comment.class)
  .getResultList();
```

```sql
select c.*, p.* from comment c left join post p on p.id = c.post_id
```

- `join fetch` is an inner join: comments with no post drop out of the result. Use `left join fetch` when the link
  can be empty.
- A plain `join` without `fetch` only filters rows; the field still holds a placeholder.

**Spring Data method, no query text — entity graph.**

```java
@EntityGraph(attributePaths = "post")    // load post together with each comment
List<Comment> findByAuthorId(Long authorId);
```

Spring Data adds the join to the query it builds for this method only. Other methods on the same repository keep
`post` lazy.

The mapping says lazy; the query that reads the link loads it: `join fetch` in your JPQL, an entity graph on a Spring
Data method.

</details>

### `join` vs `join fetch` — what changes?
<details><summary>Show answer</summary>

Both put a join into the SQL. The difference is what Hibernate does with the joined columns.

```java
// join: post is used only to pick rows
em.createQuery("select c from Comment c join c.post p where p.title like :t", Comment.class)
```

```sql
select c.id, c.text, c.post_id                 -- no post columns
from comment c join post p on p.id = c.post_id
where p.title like ?
```

`comment.getPost()` is still a placeholder; reading it fires one more SELECT per post.

```java
// join fetch: post is also loaded into the field
em.createQuery("select c from Comment c join fetch c.post p where p.title like :t", Comment.class)
```

```sql
select c.id, c.text, c.post_id, p.id, p.title  -- post columns added
from comment c join post p on p.id = c.post_id
where p.title like ?
```

Hibernate builds each `Post` from those columns and puts it into `comment.post`. No extra SELECT later.

`join` uses the link to filter rows; `join fetch` also fills the field with it.

</details>

### `@EntityGraph` — what changes in the SQL?
<details><summary>Show answer</summary>

Same Spring Data method, `post` mapped lazy; the only difference is the annotation.

```java
List<Comment> findByAuthorId(Long authorId);   // no entity graph
```

```sql
select c.id, c.text, c.post_id, c.author_id    -- comment columns only
from comment c
where c.author_id = ?
```

`comment.getPost()` is a placeholder; reading it fires one more SELECT per post.

```java
@EntityGraph(attributePaths = "post")
List<Comment> findByAuthorId(Long authorId);
```

```sql
select c.id, c.text, c.post_id, c.author_id,
       p.id, p.title                           -- post columns added
from comment c
left join post p on p.id = c.post_id           -- join added
where c.author_id = ?
```

Hibernate builds each `Post` from those columns and puts it into `comment.post`, the same result as `left join fetch`.
Left join, so comments without a post stay in the result.

`@EntityGraph` adds the join and the linked entity's columns to the method's query, and fills the field from them.

</details>

### Reading a lazy link's ID — does it load the row?
<details><summary>Show answer</summary>

No — in current Hibernate the proxy already holds the ID it was created from, so `getId()` returns it without a SELECT.
Any other method call loads the row.

```java
Comment comment = em.find(Comment.class, 10L);    // post mapped with fetch = LAZY
Long postId = comment.getPost().getId();          // no SELECT: the proxy knows its ID
String title = comment.getPost().getTitle();      // SELECT from post
```

The ID is the one thing a proxy knows without asking the database.

</details>

### One-to-one — why is LAZY ignored on one side?
<details><summary>Show answer</summary>

To leave a placeholder in a field, Hibernate needs the linked row's ID, or must know the field is `null`.

```java
@Entity
class User {
  @OneToOne(mappedBy = "user", fetch = FetchType.LAZY)   // LAZY is ignored here
  private Profile profile;
}

@Entity
class Profile {
  @OneToOne(fetch = FetchType.LAZY)
  @JoinColumn(name = "user_id")                          // the foreign key is here
  private User user;
}
```

- **Loading a `Profile`:** `user_id` is in the `profile` row, so Hibernate has the ID for free. It leaves a
  placeholder and runs no query.
- **Loading a `User`:** the `user` row has nothing about the profile. Hibernate can't tell "profile 7" from "no
  profile" without reading the `profile` table, and once it reads that table, the row is right there, so it loads
  the whole profile.

So on the side without the foreign key, LAZY acts like [eager](#default-eager-loading--what-does-it-cost): `find`
joins `profile`; a query that loads many users sends one extra SELECT per user, an N+1. This is the default without
bytecode enhancement.

A placeholder needs an ID; the side without the foreign key has none, so Hibernate must read the other table, and
then it loads the row.

</details>

### One-to-one — how to avoid the extra queries?
<details><summary>Show answer</summary>

On the side without the foreign key, [LAZY is ignored](#one-to-one--why-is-lazy-ignored-on-one-side): loading a
`User` always loads its `Profile`. So the choice is: load it in the same query, make the field truly lazy, or don't
put the link on that side.

**Keep `User.profile`:**

- **Load it in the query** — [`left join fetch` or an entity graph](#how-to-load-a-lazy-link-with-its-parent) on each
  query that loads users. 10 users → one SELECT with a join.
  - Buys: no mapping change. Costs: every query that loads users must remember it; the profile is still always loaded.
- **Bytecode enhancement** — Hibernate watches field access instead of using a placeholder, so it doesn't need to know
  "profile or `null`" upfront. The field becomes truly lazy.
  - Buys: real lazy, no query changes. Costs: a build plugin and more Hibernate machinery to understand.

**Change where the link lives:**

- **Move the foreign key** to the `user` table (`profile_id`). `User` becomes the side with the key, and LAZY works
  as usual.
  - Buys: plain lazy on `User`. Costs: a schema change; only fits if the model allows it.
- **Drop `User.profile`** and load the profile only when needed. With a shared primary key the profile's ID is the
  user's ID:

  ```java
  @Entity
  class Profile {
    @Id private Long id;                                 // same value as the user's ID
    @MapsId @OneToOne(fetch = FetchType.LAZY)
    private User user;
  }

  Profile profile = em.find(Profile.class, user.getId()); // load on demand, by the known ID
  ```

  - Buys: no forced load at all; the simplest mapping. Costs: no `user.getProfile()` navigation.

The side without the key always loads the profile: load it in the same query, or move the link off that side.

</details>

### One-to-one — map it on one side only?
<details><summary>Show answer</summary>

Map the link only on the side with the foreign key (`Profile.user`). `User` has no profile field, so loading users
never touches the `profile` table, and the [forced load](#one-to-one--why-is-lazy-ignored-on-one-side) is gone.

```java
@Entity
class User {
  @Id private Long id;                                   // no profile field
}

@Entity
class Profile {
  @Id private Long id;
  @OneToOne(fetch = FetchType.LAZY)
  @JoinColumn(name = "user_id")
  private User user;
}
```

What you give up:

- **No cascade from `User`.** Saving or deleting a user does nothing to its profile; you save and delete the profile
  yourself. Delete the profile first, or the foreign key blocks the user delete (unless the database key has
  `ON DELETE CASCADE`).
- **No `user.getProfile()`.** You load the profile when you need it: by user ID, or from the profile side when you
  need both: `select p from Profile p join fetch p.user where ...`. With a
  [shared primary key](#mapsid--what-does-it-do) this becomes a plain `em.find(Profile.class, userId)`.

The reverse side is worth keeping only if almost every user load reads the profile anyway, and even then each query
needs a fetch to avoid N+1.

Map one-to-one on the key side only: the forced load disappears; you pay with no cascade and no navigation from
`User`.

</details>

### `@MapsId` — what does it do?
<details><summary>Show answer</summary>

It makes the foreign key to the parent also the child's primary key: the profile's ID is the user's ID.

```sql
-- without @MapsId: two columns, two different values
profile(id PK, user_id FK UNIQUE, ...)

-- with @MapsId: one column, both key and link
profile(user_id PK FK, ...)
```

```java
@Entity
class Profile {
  @Id private Long id;                          // no @GeneratedValue: copied from the user on persist
  @MapsId                                       // the link to user is also this entity's primary key
  @OneToOne(fetch = FetchType.LAZY)
  private User user;
}

Profile profile = em.find(Profile.class, userId);   // load by primary key; no lookup by user_id
```

- **Load by ID instead of searching.** Knowing the user's ID means knowing the profile's ID. `em.find` checks the
  persistence context first; a query by `user_id` always goes to the database.
- **One profile per user, enforced by the key.** A primary key can't repeat, so no separate unique constraint on
  `user_id` is needed.

`@MapsId` turns the link to the parent into the child's primary key, so the child's ID is the parent's ID.

</details>

## N+1 queries

### What is the N+1 problem?
<details><summary>Show answer</summary>

One SELECT loads a list (the 1), then one more SELECT runs per element for data the first query didn't bring (the N).
100 posts → 101 queries.

```java
List<Post> posts = em.createQuery("select p from Post p", Post.class)
                     .getResultList();     // 1 query
for (Post post : posts) {
  post.getComments().size();               // 1 query per post: N more
}
```

Each query is fast, so it passes tests on small data; the cost is the round trips, and it grows with the list.

Where it comes from:

- **[Eager link + any query](#default-eager-loading--what-does-it-cost)** — unconditional: the extra SELECTs run right
  after the query, even if nothing reads the link.
- **[Lazy link read without a fetch](#eager-or-lazy--which-to-pick)** — conditional: only when the code reads the link
  for each element, as in the loop above.
- **[One-to-one, side without the foreign key](#one-to-one--why-is-lazy-ignored-on-one-side)** — LAZY is ignored, so
  it behaves like eager.

One query brings the list; each element then pays its own round trip for what the first query didn't bring.

</details>

### Fetching a collection — what changes vs to-one?
<details><summary>Show answer</summary>

A to-one join adds columns: one row per parent. A collection join adds rows: one row per child, so each parent
repeats.

```java
em.createQuery("select p from Post p left join fetch p.comments", Post.class)
```

```sql
-- p.id | p.title | c.id | c.text
--  1   | Java    |  11  | ...
--  1   | Java    |  12  | ...     -- post 1 again
--  1   | Java    |  13  | ...     -- and again
--  2   | SQL     |  14  | ...
```

What follows from the repeated rows:

- **Repeated parents.** The rows hold post 1 three times. Hibernate 6 removes the repeats in the result list itself;
  Hibernate 5 returned post 1 three times unless the query said `select distinct`.
- **Paging breaks.** `setMaxResults(10)` would become `limit 10` on rows, which cuts a post's comments in half. So
  Hibernate loads all rows, builds the posts, and pages in memory, with a warning in the log.
- **Two collections multiply.** `join fetch p.comments join fetch p.tags`: 3 comments × 4 tags = 12 rows per post.
  With two `List` collections (a "bag": a `List` without an order column), Hibernate refuses the query:
  `MultipleBagFetchException`.

A to-one fetch widens each row; a collection fetch multiplies the rows, and every trap comes from that.

</details>

### How do you choose what to load per method, outside the query?
<details><summary>Show answer</summary>

With an **entity graph**: a list of links to load, passed in with the call instead of written into the query text.
Hibernate adds the joins for that call only.

```java
EntityGraph<Post> graph = em.createEntityGraph(Post.class);
graph.addAttributeNodes("comments");

Post post = em.find(Post.class, 1L, Map.of("jakarta.persistence.fetchgraph", graph));   // comments loaded too
```

It works where there is no JPQL to put a fetch join in: `find()`, and Spring Data derived methods, where
`@EntityGraph(attributePaths = "comments")` on the repository method does the same. One query, different load plans
per caller. A graph used in many places can be named once on the entity with `@NamedEntityGraph`.

A fetch join hard-codes what to load in the query text; an entity graph passes it in with the call.

</details>

### Fetch graph vs load graph — difference?
<details><summary>Show answer</summary>

jakarta.persistence.loadgraph — грузит связи из графа плюс то, что и так eager на маппинге.
jakarta.persistence.fetchgraph — по спецификации грузит только связи из графа, остальное считается lazy. 
Насколько последовательно Hibernate это соблюдает для eager-связей, зависит от версии; не проверял.

They differ only for links the graph doesn't name. A **fetch graph** treats every link not in it as lazy, even links
mapped eager. A **load graph** leaves links not in it as they are mapped. Both load what the graph names.

For a `Comment` with `post` (eager by default) and a lazy `author`, a graph naming only `author`:
- as a fetch graph: loads `author`, leaves `post` lazy;
- as a load graph: loads `author`, and `post` too, because it is mapped eager.

Spring Data's `@EntityGraph` uses a fetch graph unless you set `type = EntityGraphType.LOAD`.

Fetch graph: the graph is the whole plan. Load graph: the graph is added on top of the mapping.

</details>

### Fetch-joining a collection — why do parents repeat?
<details><summary>Show answer</summary>

The SQL returns one row per child, and each row maps to the same parent — so a post with three comments appears three
times in the result list.

```java
List<Post> posts = em.createQuery("select p from Post p join fetch p.comments", Post.class)
                     .getResultList();
// Hibernate 5: one list entry per comment; the same Post object repeated once per comment
```

This is Hibernate 5 behavior. Hibernate 6 removes the repeats by itself.

The join makes a row per child; Hibernate 5 turns each row into a list entry, so the parent repeats.

</details>

### Fetch join on a collection plus paging — what goes wrong?
<details><summary>Show answer</summary>

Hibernate can't page in SQL, so it reads every matching row and pages in memory: `setMaxResults(10)` still loads all
posts with all their comments.

SQL `LIMIT` counts rows, and with a fetch join a row is one comment, not one post. `LIMIT 10` could return two posts,
the second with half its comments missing. So Hibernate leaves `LIMIT` out of the SQL, reads everything, and keeps the
first 10 posts in Java, logging a warning that it is paging in memory.

```java
List<Post> page = em.createQuery("select p from Post p left join fetch p.comments", Post.class)
                    .setMaxResults(10)
                    .getResultList();   // SQL has no LIMIT: all rows read, first 10 posts kept in memory
```

Small test data hides it; production data turns it into slow queries and memory pressure.

SQL pages rows, a fetch join makes a row per child — so Hibernate drops the page limit and pages in memory.

</details>

### Fetch-joining two `List` collections — what fails?
<details><summary>Show answer</summary>

Hibernate refuses the query with `MultipleBagFetchException` ("cannot simultaneously fetch multiple bags").

A `List` with no order column is a **bag**: duplicates allowed. Joining two collections in one query returns every
comment paired with every tag — 20 comments × 10 tags = 200 rows for one post. With bags, Hibernate can't tell a real
duplicate from a repeat made by the join, so it can't rebuild the lists, and it stops.

```java
em.createQuery("select p from Post p left join fetch p.comments left join fetch p.tags", Post.class)
  .getResultList();   // MultipleBagFetchException: cannot simultaneously fetch multiple bags
```

Two collections in one join multiply each other's rows; with bags Hibernate can't undo that, so it refuses.

</details>

### Loading children for many parents without a join — how?
<details><summary>Show answer</summary>

Two Hibernate options make the first lazy load also fill the collections of the other loaded parents, in one extra
query instead of one per parent.

**Batch size** — loads the children of up to N loaded parents by a list of their IDs:

```java
@OneToMany(mappedBy = "post")
@BatchSize(size = 25)
private List<Comment> comments;
```

```sql
select * from comment where post_id in (1, 2, 3, ..., 25)
```

100 posts → 1 + 4 queries. `hibernate.default_batch_fetch_size` sets it for every link at once.

**Subselect** — loads the children of every parent the first query returned, by running that query again as a
subquery:

```java
@OneToMany(mappedBy = "post")
@Fetch(FetchMode.SUBSELECT)
private List<Comment> comments;
```

```sql
select * from comment where post_id in (select p.id from post p where p.status = 'PUBLISHED')
```

100 posts → 1 + 1 queries, but the parent query runs twice.

Both keep a separate query for the children but let one query serve many parents: batch size by a list of IDs,
subselect by repeating the parent query.

</details>

### Join fetch vs batch loading — trade-off?
<details><summary>Show answer</summary>

Join fetch makes one round trip but sends the parent's columns again with every child. Batch loading makes a few more
round trips but sends each row once.

With a join fetch, 100 posts with 20 comments each come back as 2,000 rows, each carrying its post's columns again — a
large post (a text body) multiplies with it. It also can't be combined with
[paging on the parents](#fetch-join-on-a-collection-plus-paging--what-goes-wrong), and two collections
[multiply each other](#fetch-joining-two-list-collections--what-fails).

With batch loading, the same data takes 1 + 4 queries at batch size 25, every row arrives once, and paging works,
because the parent query stays a plain query.

Few children per parent and no paging → join fetch. Many children, large parents, paging, or several collections →
batch loading.

</details>

## `LazyInitializationException`

### Reading a lazy link after the transaction ends — what happens?
<details><summary>Show answer</summary>

**`LazyInitializationException`**: the lazy link tries to run its SELECT, but the session that loaded the parent is
closed, so there is nothing to run it through.

```java
@Transactional
public Post findPost(Long id) {
  return em.find(Post.class, id);   // comments not loaded yet
}

// caller, after the transaction and its session ended:
post.getComments().size();          // LazyInitializationException: failed to lazily initialize ... no Session
```

What matters is the closed session, not the missing transaction: with
[Open Session in View](#what-does-open-session-in-view-do) there is no transaction in the controller, but the session
is still open, so the load works.

A lazy link loads through the session that created it; once that session is closed, the load has nowhere to go.

</details>

### `LazyInitializationException` — the right fix?
<details><summary>Show answer</summary>

Load everything the caller needs before the transaction ends, so nothing is left to load lazily afterwards. Per use
case, in the service:
- a [fetch join](#how-do-you-load-parents-and-children-in-one-query) or an
  [entity graph](#how-do-you-choose-what-to-load-per-method-outside-the-query) that loads the links the caller reads;
- a [DTO projection](#read-only-data-for-a-screen--what-do-you-load-instead-of-entities) when the caller only reads;
- `Hibernate.initialize(post.getComments())` inside the transaction — it loads that one link with its own query, so in
  a loop it brings [N+1](#what-is-the-n1-problem) back.

The fix is in the service: decide per use case what to load, and load it inside the transaction.

</details>

### Read-only data for a screen — what do you load instead of entities?
<details><summary>Show answer</summary>

A **DTO projection**: a query that builds plain objects with just the columns the screen needs, instead of managed
entities.

```java
record PostSummary(Long id, String title) {}

List<PostSummary> rows =
    em.createQuery("select new com.example.PostSummary(p.id, p.title) from Post p", PostSummary.class)
      .getResultList();
```

The DTO has no lazy links, so nothing can fail after the transaction. The SELECT reads only the named columns. And
Hibernate doesn't track these objects for changes, so flush has nothing to check.

For reading, load the shape the screen needs, not the entities behind it.

</details>

### `LazyInitializationException` — which fixes only hide it?
<details><summary>Show answer</summary>

Three: making the link eager, keeping the session open for the whole web request, and letting Hibernate open a new
session for each lazy load. Each makes the exception go away and leaves the real gap — no load plan per use case — in
place, now as slow queries.
- Eager: the link loads for every caller, everywhere, and
  [no query can switch it off](#default-eager-loading--what-does-it-cost).
- [Open Session in View](#why-turn-open-session-in-view-off): lazy loads run in the controller and while the response
  is written, outside any transaction.
- `hibernate.enable_lazy_load_no_trans=true`: every lazy load after the session closed opens its own temporary session
  and connection — an N+1 where each query also takes a new connection.

Each of these keeps lazy loading working after the service; the right fix makes it unnecessary.

</details>

## Open Session in View

### What does Open Session in View do?
<details><summary>Show answer</summary>

It opens the session when a web request starts and closes it after the response is written, so lazy links can still
load in the controller and while the response is turned into JSON. Spring Boot turns it on by default for this
reason: lazy loading just works in the web layer, with no `LazyInitializationException`.

Transactions don't change: they still start and end at the `@Transactional` service methods. Only the session
outlives them.

```text
request starts      → session opens
  service call      → transaction starts ... commits
  controller code   → post.getComments() runs a SELECT, outside any transaction
  JSON writing      → more lazy links, more SELECTs
response written    → session closes
```

Spring Boot logs a warning at startup when it is on and `spring.jpa.open-in-view` is not set explicitly.

Open Session in View stretches the session, not the transaction, to the whole request — that is why lazy loads work in
the web layer.

</details>

### Why turn Open Session in View off?
<details><summary>Show answer</summary>

It holds a database connection for the whole request, and it runs queries you don't see, outside any transaction.

Once the service's transaction takes a connection, the open session keeps it until the response is written. A
controller that then calls a slow external API holds that connection idle for the whole call; under load the pool runs
out, and requests wait for connections the database isn't even using.

Lazy loads in the controller and in JSON writing run as separate statements outside the transaction — an N+1 during
serialization that no service code shows.

Open Session in View trades one exception for a held connection and queries nobody sees.

</details>
