# Dirty Checking

How Hibernate finds the changes made to managed entities and writes them without any `save()` call. Covers what this
costs, how to skip it for read-only work, and the cases where it misses a change or sees one that is not there.

### How does Hibernate know to run an `UPDATE`?
<details><summary>Show answer</summary>

Through **dirty checking**, in three steps:

- **Snapshot** — when an entity is loaded, Hibernate keeps a copy of its values in memory.
- **Comparison** — at flush, it goes through every managed entity and compares each field with the snapshot.
- **Update** — a difference makes the entity dirty, and an `UPDATE` is queued. No difference — no SQL.

Hibernate doesn't watch setters; it compares at flush.

</details>

### Why is a change saved without a `save()` call?
<details><summary>Show answer</summary>

```java
@Transactional
void markDraft(long id) {
  Document d = em.find(Document.class, id);
  d.setStatus("DRAFT");
}   // commit → flush → UPDATE document SET status = 'DRAFT' ...
```

`d` is managed. The commit flushes, the flush compares `d` with its snapshot, finds `status` changed, and writes it.
For a managed entity there is no "save" step — a `save()` call
[adds nothing](#save-on-an-already-managed-entity--what-does-it-do).

Managed + flush = written.

</details>

### `save()` on an already managed entity — what does it do?
<details><summary>Show answer</summary>

Spring Data's `save()` sees an entity that is not new and calls `em.merge()`. 
On a managed entity, `merge()` returns the same object and does nothing to it:

- **No SQL of its own** — no `SELECT`, no `UPDATE`.
- **Cascade only** — it walks the associations marked `CascadeType.MERGE` (or `ALL`) and merges them the same way.
- **The write comes later** — the `UPDATE`, if any, still comes from
  [dirty checking](#how-does-hibernate-know-to-run-an-update) at flush.

The call is useless but harmless.

</details>

### What does change detection cost?
<details><summary>Show answer</summary>

- **Memory** — a second copy of every managed entity's values, plus copies of its collections.
- **CPU, per flush** — every flush compares every managed entity with its copy, changed or not. The time grows with
  the number of managed entities, not with the number of changes.
- **CPU, flush count** — flushes are not only at commit. In `AUTO` mode (the default), Hibernate runs this check before
  each query, so the query sees unsaved changes — several times per transaction, even when nothing ends up written.

You pay per managed entity, on every flush, whether it changed or not.

</details>

### Which columns does Hibernate's `UPDATE` set?
<details><summary>Show answer</summary>

By default, every column — even when only one field changed.

- **Default, all columns** — Hibernate builds one fixed SQL string per entity at startup and reuses it for every
  change. Buys statement plan reuse and JDBC batching. Costs more data sent, triggers firing for unchanged columns, and
  overwriting other transactions' changes to other columns (without `@Version`, those changes are lost).
- **`@DynamicUpdate`, changed columns only** — Hibernate builds the SQL at flush with only the modified fields. Buys
  smaller writes and leaves other columns alone. Costs statement reuse and batching: each set of changed columns gives
  a different SQL string.

Fixed SQL buys reuse and batching; `@DynamicUpdate` buys smaller writes.

</details>

### How do you skip change detection for reads?
<details><summary>Show answer</summary>

Change detection needs an entity that is both managed and writable. Take away either one:

- **Skip entities entirely**
  - Return DTOs — `select new com.example.UserDto(u.id, u.name) from User u` returns plain objects; the context stays
    empty.
- **Make the entities read-only**
  - Per query — the `org.hibernate.readOnly` hint loads the results with no snapshot.
  - Per class — `@Immutable` tells Hibernate the entity never changes: no snapshot, no check, changes ignored.
- **Make the session read-only or stateless**
  - Per transaction — Spring's `@Transactional(readOnly = true)` makes the session read-only and sets flush mode
    `MANUAL`, so loaded entities keep no snapshot.
  - No context at all — `StatelessSession` manages nothing; each call goes straight to the database.

No managed, writable entity — nothing to compare.

</details>

### Why is a row updated that nobody changed?
<details><summary>Show answer</summary>

Something changed a field after load, so the comparison sees a difference:

- Property access with a getter that returns something other than what the setter received (trims, turns `null`
  into `""`, wraps the value). Hibernate loads through the setter and compares through the getter.
- Code that writes a field right after load — a `@PostLoad` method, or a getter that fills in a default.
- A mapped collection replaced with a new collection object — Hibernate
  [rewrites it](#how-is-a-collection-change-detected).

Dirty checking compares values, not intentions: any write to a field after load makes an `UPDATE`.

</details>

### Which changes go unnoticed?
<details><summary>Show answer</summary>

To be saved, a change must happen to a mapped, updatable field of a managed, writable entity:

- **The entity is not checked**
  - Not managed — a [new or detached](2.02_Entity_States.md#what-states-can-an-entity-be-in) object is outside the
    context, so there is no snapshot to compare against.
  - Not writable — entities from a read-only query, or marked `@Immutable`, skip the check.
- **The field is not checked**
  - Not mapped — `@Transient` (or Java `transient`) fields are not in the snapshot at all.
  - Not updatable — `@Column(updatable = false)` fields are left out of the `UPDATE`.

Miss any one of the four, and the change is not saved.

</details>

### How is a collection change detected?
<details><summary>Show answer</summary>

**How it works.** At load, Hibernate puts its own collection class into the field (`PersistentBag`, `PersistentSet`,
…). It marks itself changed on `add()`, `remove()` and `clear()`, and keeps a copy of the loaded elements. At flush,
for a collection that owns its rows (join table, `@ElementCollection`), Hibernate writes only the difference from that
copy — except for a `List` without `@OrderColumn` (a bag), where a removal deletes all rows and inserts the rest again.

**The trap: replacing the collection.** `order.setItems(new ArrayList<>(items))` throws the wrapper and its copy away:

- **Full rewrite** — with nothing to compare, Hibernate deletes all rows of a collection that owns them and inserts
  them all again.
- **Crash with `orphanRemoval = true`** — the flush fails because the collection is "no longer referenced by the owning
  entity instance": the wrapper Hibernate used to find removed elements is gone.

Change the collection Hibernate gave you; don't replace it.

</details>

### How does Hibernate find the changed fields?
<details><summary>Show answer</summary>

Two ways — they differ in *when* the work is done:

- **Compare at flush (the default)** — at load, Hibernate keeps a copy of each entity's values. At every flush it
  compares every field of every managed entity with that copy.
- **Record each write (bytecode enhancement, opt-in)** — a Maven/Gradle plugin rewrites the compiled entity classes,
  so every field write also notes the field name inside the entity. At flush Hibernate just asks each entity which
  fields changed.

Compare everything at flush, or note each write as it happens.

</details>

### Snapshot compare vs bytecode tracking — which when?
<details><summary>Show answer</summary>

Both find the [changed fields](#how-does-hibernate-find-the-changed-fields); they trade build setup for flush speed:

- **Snapshot compare (default)**
  - Buys: nothing to set up; the classes that run are the ones you wrote.
  - Costs: each flush checks unchanged entities too, so flush time grows with the size of the context.
- **Bytecode tracking (plugin)**
  - Buys: flush cost follows the number of changes — unchanged entities are skipped at once.
  - Costs: an extra build step; the running classes differ from your source, and a run without the plugin (IDE, some
    tests) silently falls back to comparing.

Compare by default; record writes only when a big context and frequent flushes make flush time show up in profiling.

</details>
