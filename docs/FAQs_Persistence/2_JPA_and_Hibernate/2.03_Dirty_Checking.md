# Dirty Checking

How Hibernate finds the changes made to managed entities and writes them without any `save()` call. Covers what this
costs, how to skip it for read-only work, and the cases where it misses a change or sees one that is not there.

### How does Hibernate know to run an `UPDATE`?
<details><summary>Show answer</summary>

**Dirty checking:** with plain JDBC, changing an object changes nothing until you write the `UPDATE`. Hibernate writes
it for you:

- At load, it keeps a copy of the entity's values — the snapshot.
- At flush, it goes through every managed entity and compares each field with the snapshot.
- A difference makes the entity dirty, and an `UPDATE` is queued. No difference — no SQL.

Hibernate doesn't watch setters; it compares at flush.

</details>

### Why is a change saved without a `save()` call?
<details><summary>Show answer</summary>

```java
@Transactional
void markDraft(long id) {
  Document d = em.find(Document.class, id);
  d.setStatus("DRAFT");
}   // commit → flush → UPDATE document SET status = 'DRAFT' ...
```

`d` is managed. The commit flushes, the flush compares `d` with its snapshot, finds `status` changed, and writes it.
For a managed entity there is no "save" step — a `save()` call
[adds nothing](#save-on-an-already-managed-entity--what-does-it-do).

Managed + flush = written.

</details>

### `save()` on an already managed entity — what does it do?
<details><summary>Show answer</summary>

Spring Data's `save()` sees an entity that is not new and calls `em.merge()`. `merge()` on a managed entity returns
the same object: no `SELECT`, no SQL of its own — only a walk over the associations marked `CascadeType.MERGE`. The
`UPDATE` still comes from dirty checking at flush.

The call is useless but harmless.

</details>

### What does change detection cost?
<details><summary>Show answer</summary>

- Memory: a second copy of every managed entity's values, plus copies of its collections.
- CPU: every flush compares every managed entity, changed or not. The cost grows with the size of the context, not
  with the number of changes — and under `AUTO` a flush check can happen before each query.

You pay per managed entity, on every flush, whether it changed or not.

</details>

### Why does the `UPDATE` list every column?
<details><summary>Show answer</summary>

By default Hibernate builds one `UPDATE` per entity that sets every column, and reuses it for every change.

- Buys: one fixed SQL string — JDBC batching works, and the database reuses the statement plan.
- Costs: more data sent, triggers fire for columns that didn't change, and the full-row write puts old values back in
  columns someone else changed (without `@Version`, that change is lost).
- `@DynamicUpdate` builds the SQL at flush with only the changed columns — smaller writes, no overwrite of other
  columns, but a different SQL string per change pattern, so less reuse and batching.

Fixed SQL buys reuse and batching; `@DynamicUpdate` buys smaller writes.

</details>

### How do you skip change detection for reads?
<details><summary>Show answer</summary>

Make sure there is nothing managed and writable to compare:

- DTO projection — `select new com.example.UserDto(u.id, u.name) from User u` — no entities, nothing in the context.
- Read-only entities — the `org.hibernate.readOnly` query hint, or `session.setDefaultReadOnly(true)`: no snapshot is
  kept and they are never compared.
- Spring `@Transactional(readOnly = true)` — Spring makes the Hibernate session read-only and sets flush mode
  `MANUAL`. *(unverified)*
- `StatelessSession` — no context at all.
- `@Immutable` on the entity — Hibernate never updates it.

No managed, writable entity — nothing to compare.

</details>

### Why is a row updated that nobody changed?
<details><summary>Show answer</summary>

Something changed a field after load, so the comparison sees a difference:

- Property access with a getter that returns something other than what the setter received (trims, turns `null`
  into `""`, wraps the value). Hibernate loads through the setter and compares through the getter.
- Code that writes a field right after load — a `@PostLoad` method, or a getter that fills in a default.
- A mapped collection replaced with a new collection object — Hibernate
  [rewrites it](#how-is-a-collection-change-detected).

Dirty checking compares values, not intentions: any write to a field after load makes an `UPDATE`.

</details>

### Which changes go unnoticed?
<details><summary>Show answer</summary>

- Changes to a [detached or new](2.02_Entity_States.md#what-states-can-an-entity-be-in) object — no context compares
  it.
- `@Transient` fields — not mapped, not in the snapshot.
- Columns mapped with `@Column(updatable = false)` — left out of the `UPDATE`.
- Read-only and `@Immutable` entities — their changes are ignored.

Only mapped, updatable fields of a managed, writable entity are compared.

</details>

### How is a collection change detected?
<details><summary>Show answer</summary>

At load, Hibernate puts its own collection class into the field (`PersistentBag`, `PersistentSet`, ...). It marks
itself changed on `add()` / `remove()` and keeps a copy of the loaded elements, so at flush Hibernate writes only the
difference.

- Replacing the collection (`order.setItems(new ArrayList<>(items))`) throws that away. For a collection that owns its
  rows (join table, `@ElementCollection`), Hibernate deletes all rows and inserts them all again.
- With `orphanRemoval = true`, replacing it fails at flush: **"A collection with cascade="all-delete-orphan" was no
  longer referenced by the owning entity instance"**.

Change the collection Hibernate gave you; don't replace it.

</details>

### Snapshot compare vs bytecode tracking?
<details><summary>Show answer</summary>

- Snapshot compare (default): at flush, every field of every managed entity is compared with its snapshot.
- Bytecode tracking: Hibernate's build plugin rewrites the entity classes so every field write records the field
  name inside the entity. At flush Hibernate just asks each entity which fields changed.
- Buys: flush cost follows the number of changes, not the size of the context.
- Costs: an extra build step, and the classes that run are not the ones in your source — tests run without the
  plugin behave differently.

Compare everything at flush, or record each write as it happens.

</details>
