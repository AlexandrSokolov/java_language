# Flush

When Hibernate sends pending changes to the database as SQL, and in what order. Covers the flush modes and how a
flush differs from a commit.

### Flush vs commit — what's the difference?
<details><summary>Show answer</summary>

Hibernate collects changes in memory and sends them to the database later. Two steps get them there:

- **Flush** — Hibernate sends the pending `INSERT` / `UPDATE` / `DELETE` statements over the open connection. The
  rows change inside your transaction only: other transactions don't see them (at the usual isolation levels), and a
  rollback still undoes them.
- **Commit** — the database makes the transaction's changes permanent and visible to others. Hibernate always
  flushes right before it commits.

Flush moves changes from memory into the transaction; commit moves them from the transaction to everyone.

</details>

### What happens to flushed rows on failure?
<details><summary>Show answer</summary>

A flush sends the SQL, but the rows [stay inside the open transaction](#flush-vs-commit--whats-the-difference).
When a later statement fails, the transaction rolls back and takes every flushed row with it.

```java
em.persist(transfer);                                        // pending INSERT on transfer
em.createQuery("select t from Transfer t").getResultList();  // AUTO flush: INSERT transfer runs now
em.persist(new User("ann@example.com"));                     // email already taken
// commit → flush → INSERT user fails → rollback: the transfer row is gone too
```

Catching the exception does not save the rest. Under JPA, almost every `PersistenceException` marks the transaction
rollback-only, which means it can no longer commit, only roll back.

Flush sends; only commit keeps. 

</details>

### When does Hibernate flush on its own?
<details><summary>Show answer</summary>

Under the default `AUTO` mode:

- before commit;
- before a JPQL / HQL / Criteria query that reads a table with pending changes, so the query sees them
  ([only those tables](#does-a-query-flush-changes-to-an-unrelated-table));
- before a native SQL query — [the rules differ](#does-a-native-query-see-pending-changes).

An explicit `flush()` is not an `AUTO` trigger — it is your call and works in every mode.

Before commit, and before any query that could otherwise read old data.

</details>

### Does a query flush changes to an unrelated table?
<details><summary>Show answer</summary>

No. Under `AUTO`, Hibernate checks which tables the query reads and flushes only if one of them has pending changes.

```java
account.setBalance(newBalance);                              // pending UPDATE on account
em.createQuery("select t from Transfer t").getResultList();  // reads transfer only: no flush
em.createQuery("select a from Account a").getResultList();   // reads account: flush first
```

The `Account` update keeps waiting until commit, or until a query reads `account`.

`AUTO` flushes for the tables a query reads, not for the whole context.

</details>

### Does a native query see pending changes?
<details><summary>Show answer</summary>

It depends on the API, because Hibernate can't read native SQL to find out which tables it uses:

- Through JPA's `em.createNativeQuery(...)`, Hibernate flushes the whole context first. *(unverified)*
- Through Hibernate's own `Session` API, older versions did not flush at all unless you named the tables with
  `addSynchronizedEntityClass(...)` / `addSynchronizedQuerySpace(...)`. *(unverified for Hibernate 6/7)*

Hibernate can't see inside native SQL — it flushes everything, nothing, or the tables you declare.

</details>

### What flush modes exist?
<details><summary>Show answer</summary>

- `AUTO` (JPA, the default) — flush before commit and before queries that may read pending changes.
- `COMMIT` (JPA) — flush only at commit; queries may miss pending changes.
- `MANUAL` (Hibernate) — never on its own, not even at commit; only an explicit `flush()` writes.
- `ALWAYS` (Hibernate) — before every query, even one that reads unrelated tables.

The modes differ in when a query triggers a flush — and `MANUAL` never flushes on its own.

</details>

### When would you choose `COMMIT` mode?
<details><summary>Show answer</summary>

When a transaction runs many queries that never need to see its own pending changes — e.g. a batch job that reads
reference data between writes.

- Buys: under `AUTO`, each query can trigger a dirty check of the whole context and break a batch of writes into
  small pieces; `COMMIT` does one flush at the end.
- Costs: a query that does read changed tables returns the old rows — your own changes are invisible to it.

`COMMIT` trades correct query results inside the transaction for fewer flushes.

</details>

### Why does a constraint error appear at commit?
<details><summary>Show answer</summary>

`persist()` only queues the `INSERT`; the database checks the constraint when the SQL runs at flush.

```java
em.persist(new User("ann@example.com"));   // email is unique and already taken — no error here
// ... more work ...
// commit → flush → INSERT → unique constraint violation
```

The exception comes out of the commit (or out of a later query that triggered a flush), far from the line that
caused it — with Spring, from the proxy that commits after your method body has finished.

An `IDENTITY` ID is the exception: its `INSERT` [runs inside `persist()`](#why-does-persist-sometimes-insert-at-once),
so the error appears there.

The database judges a change only when flush sends it.

</details>

### In what order does flush send SQL?
<details><summary>Show answer</summary>

Not in the order of your calls. Hibernate groups the queued actions by kind:

- orphan removals;
- inserts;
- updates;
- collection changes (removals, updates, re-creations);
- deletes — last.

The order bites when a delete must happen first:

```java
em.remove(oldUser);                        // email ann@example.com
em.persist(new User("ann@example.com"));   // same unique email
// flush: INSERT runs before DELETE → unique constraint violation
```

Flush groups SQL by kind — inserts first, deletes last.

</details>

### Why does `persist()` sometimes INSERT at once?
<details><summary>Show answer</summary>

With `GenerationType.IDENTITY` (an auto-increment column) the database creates the ID only while running the
`INSERT`. A managed entity must have an ID — the context is a map keyed by ID — so Hibernate runs the `INSERT` inside
`persist()` instead of waiting for flush.

- Hibernate can't batch these inserts.
- With `SEQUENCE`, Hibernate gets IDs ahead of time (a block per call, e.g. 50) and keeps the `INSERT` for the flush.

No ID without the `INSERT`, so `IDENTITY` can't wait for flush.

</details>

### How do you batch inserts?
<details><summary>Show answer</summary>

- Set `hibernate.jdbc.batch_size` (e.g. 50) — without it, every statement is sent alone.
- Take IDs from a `SEQUENCE`, not `IDENTITY` — `IDENTITY`
  [turns batching off](#why-does-persist-sometimes-insert-at-once).
- Set `hibernate.order_inserts=true` — groups statements by entity, so parent and child inserts don't keep breaking
  the batch.
- In the loop, call `flush()` and `clear()` every `batch_size` rows — sends full batches and keeps the context small.
- On MySQL, add the driver flag `rewriteBatchedStatements=true`, or the driver still sends the statements one by one.

Batch size on, IDs from a sequence, statements ordered, context flushed and cleared every batch.

</details>

### Does flush empty the context?
<details><summary>Show answer</summary>

No. After a flush every entity stays managed, its snapshot is updated to the values just written, and the queue of
pending SQL is empty. Memory use doesn't drop — only `clear()` frees it.

Flush writes; clear forgets.

</details>
