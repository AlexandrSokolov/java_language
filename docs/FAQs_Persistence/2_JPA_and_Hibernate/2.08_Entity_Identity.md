## `equals` and `hashCode` on entities

### Entity `equals`/`hashCode` — what can go wrong?
<details><summary>Show answer</summary>

An entity's identity must remain stable across all states (new, managed, detached).
The two most common approaches both break this rule:

**Default from `Object` — breaks across sessions.** Inside one session Hibernate gives one object per row, so the
same-object check works. Load the row in two sessions and you get two unequal objects: a `Set` holding both has two
entries for one row.

**Built purely on the generated ID — breaks before save.** A new entity has `id == null`, and saving it changes the hash:
- **Collisions:** Two brand-new entities both have id == null, so equals() thinks they are the exact same object.
  A Set will refuse to add the second one.
- **Lost in the Set:** If you add a new entity (id == null) to a HashSet, then persist() it, the ID gets set.
  The `hashCode` changes while it is inside the `Set`, stranding it in the wrong hash bucket. `set.contains(post)` will
  silently return false.

```java
Set<Post> posts = new HashSet<>();
Post post = new Post();     // id == null
posts.add(post);            // stored under the hash of null
em.persist(post);           // id set → hashCode changes
posts.contains(post);       // false, though the post is still inside
```

And two unsaved posts both have `id == null`, so they count as equal, and a set keeps only one of them.

An entity's identity must hold in every state — new, loaded, detached — and neither the object itself nor the
generated ID does.

</details>

### Entity `equals`/`hashCode` — when to override?
<details><summary>Show answer</summary>

Often you don't need to. Inside one session Hibernate gives exactly one object per row, so the default `equals` from
`Object` already works there. Override only when objects from different sessions meet — that's where
[the default breaks](#entity-equalshashcode--what-can-go-wrong):

- in one `Set` holding copies loaded in different sessions;
- when you compare or reattach detached entities.

No such case → write nothing.

</details>

### Entity `equals`/`hashCode` — which designs work?
<details><summary>Show answer</summary>

**First: do you need it at all?** Often not. Inside one session Hibernate gives exactly one object per row, so the
default `equals` from `Object` already works there. Override only:
- when objects from different sessions meet — in one `Set`, or
    - when you compare or reattach detached entities.

No such case → write nothing.


Two rules hold for every design, because Hibernate may hand you a
[lazy-loaded proxy](#lazy-loaded-entity-in-equals--what-breaks) — a generated subclass whose own fields are empty:

- **`instanceof`, not `getClass()`** — the proxy's class is a subclass of `Post`, so `getClass()` calls a proxy and its
  real entity different.
- **Getters, not fields** —
    - `other.id` on a proxy is `null`;
    - `other.getId()` forces the proxy to initialize and fetch the real ID

Then pick the value to compare. Does the entity have a value that exists from creation and never changes?

- **Yes** → use it: a [business key](#entity-equals-without-the-id--which-value), like an ISBN.
- **No** →
    - add a [UUID set at creation](#entity-equals-without-the-id--which-value), or
    - use the [ID with a null check and a fixed hash](#entity-equals-on-the-id--how-to-do-it-right).

</details>

### Entity `equals` without the ID — which value?
<details><summary>Show answer</summary>

Use a value that exists from the moment the object is created, before any save, and never changes. It works in every
state and spreads well across buckets — no [fixed hash](#entity-equals-on-the-id--how-to-do-it-right) needed. The
code is the same for both kinds:

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Book other)) return false;
  return isbn.equals(other.getIsbn());            // or uuid.equals(other.getUuid())
}

@Override
public int hashCode() {
  return isbn.hashCode();                         // or uuid.hashCode()
}
```

- **Business key (natural ID)** — a unique real-world value the entity already has: an ISBN, a product code. In
  Hibernate: `@NaturalId`.
    - **Buys:** no extra column; it means something to a reader.
    - **Costs:** many entities have none — users, for example, can change their email.
- **UUID made in Java** — generated the moment the object is created, stored in its own unique column:
```java
  @Column(unique = true, updatable = false)
  private UUID uuid = UUID.randomUUID();
```
- **Buys:** any entity can have one; no database call.
- **Costs:** one more column and index on the table.

</details>

### Entity `equals` on the ID — how to do it right?
<details><summary>Show answer</summary>

A generated ID is `null` until the entity is saved. So on top of the
[two rules for every design](#entity-equalshashcode--which-designs-work), the ID needs two more:

- **Unsaved entities are never equal** — if the ID is `null`, `equals` returns `false`. Otherwise two new posts
  [count as one](#entity-equalshashcode--what-can-go-wrong).
- **Fixed `hashCode`** — a hash built on the ID changes on save and
  [loses the object in a `HashSet`](#entity-equalshashcode--what-can-go-wrong). A constant never changes.

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Post other)) return false;   // instanceof: a proxy passes
  return id != null && id.equals(other.getId());  // null check: unsaved never equal; getter: reaches a proxy's ID
}

@Override
public int hashCode() {
  return Post.class.hashCode();                   // fixed: the same before and after save
}
```

**Trade-off:** the fixed hash puts every `Post` in one bucket. Fine for the small collections an entity holds; slow
for a `HashSet` of thousands.

</details>

### Lazy-loaded entity in `equals` — what breaks?
<details><summary>Show answer</summary>

A lazy-loaded reference, like `comment.getPost()`, is a **Hibernate proxy**: a generated subclass of `Post` that loads
the real data when first used. The data then sits in a separate object behind the proxy; the proxy's own fields stay
empty. A typical generated `equals` breaks on it twice:

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (o == null || getClass() != o.getClass()) return false;  // Post vs Post$HibernateProxy$...: never equal
  return Objects.equals(id, ((Post) o).id);                    // the proxy's direct id field: always null
}
```

So a real `Post` and a proxy for the same row compare as different.

They meet only across sessions — for example, a `Post` loaded in an earlier session and `comment.getPost()` from a
later one. Inside one session Hibernate hands out one object per row, so a real `Post` and its proxy never exist side
by side.

Fix: `instanceof` and getters — the [two rules for every design](#entity-equalshashcode--which-designs-work).

A lazy reference is a subclass whose own fields stay empty — a class check and a direct field read both see the wrong
thing.

</details>

### Lombok `@Data` on an entity — what breaks?
<details><summary>Show answer</summary>

`@Data` generates `equals`, `hashCode` and `toString` from every field, relationships included. On an entity that
breaks three ways:
- **The Infinite Loop**: `Post.toString()` prints `comments`, each `Comment.toString()` prints `post`,
  which prints `comments` again — `StackOverflowError`. `hashCode()` can loop the same way on a two-way link.
- **Hidden Lazy Loading**: `toString()` on a lazy `comments` field loads the collection —
  an extra query just to write a log line — or throws `LazyInitializationException` once the session is closed.
- Changing Hash (Lost in the Set): the hash covers every field, the ID included, so saving or editing an entity
  that sits in a `HashSet` loses it — the [same failure as hashing on the ID](#entity-equalshashcode--what-can-go-wrong).

Generated methods use every field, and on an entity that means links that loop or load, and values that change.

</details>
