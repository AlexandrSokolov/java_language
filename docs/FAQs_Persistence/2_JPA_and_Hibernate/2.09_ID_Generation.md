## ID generation

### Entity ID generation — what are the options?
<details><summary>Show answer</summary>

- `AUTO` (default) — Hibernate inspects your configured database dialect and automatically chooses the best
  available strategy.
- `UUID` — the provider generates a random UUID in Java before the database call (JPA 3.1+).
- `IDENTITY` — the database fills an auto-increment column; the ID is known only after the INSERT.
- `SEQUENCE` — the ID comes from a database sequence, fetched before the INSERT; `@SequenceGenerator` with
  `allocationSize` reserves a block of values per call.
- `TABLE` — a separate table holds the next value, imitating a sequence.

**Hibernate adds:**
- `@UuidGenerator` — a UUID in a chosen style: random or time-based.
- A custom generator — your own class, attached with `@IdGeneratorType` (older versions: `@GenericGenerator`).

</details>

### `IDENTITY` vs `SEQUENCE` — which to pick, and why?
<details><summary>Show answer</summary>

Pick `SEQUENCE` when the database has sequences (PostgreSQL, Oracle); use `IDENTITY` only when it has none, as on MySQL.

What `persist()` of two posts sends:

```
IDENTITY:  persist(a) → insert into post ...          -- runs now: the ID comes out of the INSERT
           persist(b) → insert into post ...
           flush      → nothing left to send

SEQUENCE:  persist(a) → select nextval('post_seq')    -- ID first; one call reserves a block
           persist(b) → nothing (next ID from the block)
           flush      → insert a, insert b — one batch
```

Hibernate keeps every saved entity in the persistence context under its ID, so `persist()` must have the ID right away.
- With `IDENTITY`(Disables Batching) the only way to get it is to run the INSERT,
  so INSERTs can't wait until flush and can't [go out as one batch](2.08_Writes_and_Locking.md).
- With `SEQUENCE`(Enables Batching) the ID comes first, Hibernate can safely queue the INSERT statements and
  send them all at once at flush time as a single, highly efficient JDBC batch;
  taking a [block of IDs per sequence call](#what-does-allocationsize-control) keeps the extra calls rare.

`IDENTITY`: the ID comes out of the INSERT, so the INSERT can't wait.
`SEQUENCE`: the ID comes first, so the INSERTs can wait and batch.

</details>

### What does `allocationSize` control?
<details><summary>Show answer</summary>

How many IDs Hibernate takes from one sequence call. With the default of 50,
Hibernate calls the sequence once, hands out the next 50 IDs from memory, and calls again only when they run out.

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "post_seq")
@SequenceGenerator(name = "post_seq", sequenceName = "post_seq", allocationSize = 50)
private Long id;
```

```sql
create sequence post_seq start with 1 increment by 50;   -- step matches allocationSize
```

The sequence's own step must equal `allocationSize`. Hibernate reads each value as the top of a block of 50, so a
sequence that steps by 1 returns values inside blocks already handed out — the same ID twice, a duplicate key error.

`allocationSize` is how many IDs one sequence call buys — and the sequence's own step must buy the same number.

</details>

### `TABLE` ID generation?
<details><summary>Show answer</summary>

A plain table holds the next value and imitates a sequence.

```sql
-- once per block of 50 IDs, in a separate transaction:
select next_val from id_gen where sequence_name = 'post' for update;   -- locks the row
update id_gen set next_val = ? where sequence_name = 'post';
```

**Good:**

- Works on every database — no sequences or auto-increment needed.
  Same schema and mapping everywhere; you don't care which database it runs on.
- The ID comes before the INSERT, so INSERTs can still wait for flush and go out as a batch.

**Bad:**

- Every thread that needs a new block waits on that one locked row.
- The separate transaction needs an extra database connection for each fetch.
- One more table to create and keep.

A bigger `allocationSize` makes the fetches rarer, but each one still locks the row.

The portability is almost never worth the lock contention penalty.
Avoid it unless you are forced to support obscure legacy databases that lack both native sequences and identity columns.

</details>

### `AUTO` ID strategy?
<details><summary>Show answer</summary>

Because the provider picks the strategy, not you, and its pick depends on the database and the Hibernate version.

`@GeneratedValue` with no strategy means `AUTO`. For a numeric ID, Hibernate 5 and later pick a sequence — fine on
PostgreSQL. MySQL has no sequences, so Hibernate fakes one with a one-row table: each new block of IDs costs a SELECT
and an UPDATE on that row in a separate transaction, and every insert that needs a new block waits on that row's lock.

The pick also changes when you switch databases or upgrade Hibernate, so the same code can silently start using a
different ID scheme.

`AUTO` hands the choice to the provider, and the choice moves with the database and the version.

</details>
