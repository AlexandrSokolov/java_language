# Query Plans

Reading what the database actually does with a query. Examples use PostgreSQL; other databases have the same ideas
under different names.

- Why plans exist — what the database decides on its own.
- `EXPLAIN` vs `EXPLAIN ANALYZE` — what a plan shows, how to read it, what it never shows.

## Why query plans exist

### A query is slow, but the SQL looks fine. What does the database decide on its own that the SQL never says?
<details><summary>Show answer</summary>

SQL says *what* rows you want, not *how* to get them. The database decides the "how" itself:

- how to read each table — the whole table, an index, or only an index;
- in which order to join the tables;
- which join method to use for each pair;
- whether to sort, hash or aggregate, and in memory or on disk.

The same correct SQL can run in 5 ms or 5 minutes depending on these choices. The result of the choices is the query
plan, and `EXPLAIN` shows it.

**Handle:** SQL describes the result; the plan is how the database gets it — a slow query is usually a slow plan.

</details>

### Who builds a query plan, and how does it choose between options?
<details><summary>Show answer</summary>

The planner (optimizer) builds it before the query runs. It lists possible plans — access methods for each table, join
orders, join methods — estimates a cost for each one, and picks the cheapest.

The cost is an estimate in made-up units, built from the expected number of rows and the price of each operation: a
sequential page read, a random page read, processing one row. In PostgreSQL these prices are settings
(`seq_page_cost = 1`, `random_page_cost = 4` by default).

With many tables, trying every join order gets too expensive, so the planner limits its search. PostgreSQL switches to
a heuristic (genetic) search above a threshold of tables *(unverified: default threshold 12)*.

**Handle:** the planner picks the plan with the lowest *estimated* cost — it is only as good as its estimates.

</details>

### What does the database know about the data when it chooses a plan?
<details><summary>Show answer</summary>

Only the statistics it collected earlier, not the data itself. In PostgreSQL, `ANALYZE` (also run by autovacuum)
samples each table and stores:

- per table: number of rows and number of pages;
- per column: share of `NULL`s, number of distinct values, the most common values with their frequencies, a histogram
  of the other values, and how well the physical row order matches the column order.

From these the planner estimates how many rows each condition matches. By default it treats columns as independent:
for `city = 'Berlin' AND country = 'DE'` it multiplies the two shares, although the conditions are almost the same.
Extended statistics (`CREATE STATISTICS`) can record such dependencies.

**Handle:** the planner sees a summary of the data from the last `ANALYZE` — when the summary is wrong, the plan is
wrong.

</details>

### The same query is fast in dev and slow in prod. Why can the plan differ?
<details><summary>Show answer</summary>

The plan depends on more than the SQL, and all of these differ between environments:

- data volume — on a small dev table a full scan is cheapest, so dev never shows the index problem;
- data distribution — a value that is rare in dev can match half the rows in prod;
- statistics — prod statistics may be stale after a big load;
- indexes — dev and prod schemas drift apart;
- settings — memory (`work_mem`), cost settings, database version;
- parameter values — prod sends values dev never tests;
- cache state and concurrent load.

So test plans on a copy with prod-like volume and distribution, not on dev data.

**Handle:** a plan is a function of SQL + data + statistics + settings — change any of them and the plan can change.

</details>

## `EXPLAIN` vs `EXPLAIN ANALYZE`

### `EXPLAIN` vs `EXPLAIN ANALYZE`: what does each one show, and which one actually runs the query?
<details><summary>Show answer</summary>

`EXPLAIN` does not run the query. It shows the chosen plan with the planner's *estimates*: cost and expected rows per
step.

`EXPLAIN ANALYZE` runs the query for real and adds what *actually* happened per step: time, actual rows, number of
loops. The result rows are thrown away instead of being sent to the client.

```text
Index Scan using orders_customer_idx on orders  (cost=0.43..8.45 rows=1 width=64) (actual time=0.021..0.023 rows=1 loops=1)
```

Use `EXPLAIN` when running the query is too slow or not safe. Use `EXPLAIN ANALYZE` to see the truth, and to compare
estimates with actual numbers.

**Handle:** `EXPLAIN` shows the plan the planner believes in; `EXPLAIN ANALYZE` shows what it really cost.

</details>

### Why is `EXPLAIN ANALYZE` on an `UPDATE` or `DELETE` dangerous, and how do you run it safely?
<details><summary>Show answer</summary>

Because it really executes the statement: rows are changed or deleted, triggers fire, and with autocommit the change is
committed. Only the output is suppressed, not the effect.

Run it inside a transaction and roll back:

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders WHERE created_at < '2020-01-01';
ROLLBACK;
```

Even then, the statement still does all the work: it takes row locks that block other sessions until the rollback,
writes to the transaction log, and uses sequence values that a rollback does not return. On production, prefer a copy,
or plain `EXPLAIN`.

**Handle:** `ANALYZE` means "really run it" — for writes, always wrap it in `BEGIN` / `ROLLBACK`.

</details>

### How do you read a plan: which node runs first, and what do cost, rows and width mean?
<details><summary>Show answer</summary>

A plan is a tree. Each node gets rows from its children (the indented lines with `->` under it), so the most indented
nodes run first and the top node returns the final result. Read it from the inside out.

```text
Hash Join  (cost=12.50..45.10 rows=120 width=72)
  Hash Cond: (o.customer_id = c.id)
  ->  Seq Scan on orders o  (cost=0.00..28.00 rows=1200 width=40)
  ->  Hash  (cost=10.00..10.00 rows=200 width=32)
        ->  Seq Scan on customers c  (cost=0.00..10.00 rows=200 width=32)
```

On each node:

- `cost=12.50..45.10` — startup cost (before the first row) .. total cost (all rows), in the planner's units, including
  the children;
- `rows` — the estimated number of rows this node returns;
- `width` — the estimated average row size in bytes.

With `ANALYZE`, actual time is in milliseconds and is *per loop*: multiply by `loops` to get the node's real total.

**Handle:** read the tree from the innermost nodes up; every number is per node and includes its children.

</details>

### Can you compare the cost of two different queries to tell which one will run faster?
<details><summary>Show answer</summary>

Not reliably. Cost is the planner's estimate in its own units, not time. It is made to compare alternative plans *for
the same query*, under the same statistics and settings. That is the only comparison the planner itself makes.

Across different queries, cost is at best a rough hint:

- the estimates behind it can be wrong — a plan with a low cost and a bad row estimate can be the slowest;
- it leaves out things such as sending rows to the client, lock waits and cache effects.

To compare queries, compare `EXPLAIN ANALYZE` actual times (and buffers), several runs, with real parameter values.

**Handle:** cost ranks plans for one query; time compares queries.

</details>

### Estimated rows and actual rows differ by a factor of 100. What does that tell you?
<details><summary>Show answer</summary>

The planner's picture of the data is wrong, so its plan was chosen for data that does not exist. A typical result: it
expects 10 rows, picks a nested loop with one index lookup per row, and gets 1,000,000 rows.

Usual causes:

- stale statistics after a large insert, update or delete;
- columns that depend on each other, treated as independent;
- conditions the planner cannot estimate — functions or expressions on columns — so it uses a fixed default guess;
- strongly skewed data that the sample missed.

Find the *lowest* node where estimate and actual first diverge; the nodes above it inherit the error. Fixes: run
`ANALYZE`, raise the column's statistics target (`ALTER TABLE … ALTER COLUMN … SET STATISTICS`), add extended
statistics, or rewrite the condition so it can be estimated.

**Handle:** a big estimate error is the root cause behind most bad plans — fix the estimate before the plan.

</details>

### What does a plain `EXPLAIN ANALYZE` not show about disk and cache reads, and how do you see it?
<details><summary>Show answer</summary>

It shows time, but not *why* a node was slow: how many pages came from memory and how many had to be read. Add the
`BUFFERS` option:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

```text
Buffers: shared hit=1200 read=8500 dirtied=10
```

- `shared hit` — pages found in PostgreSQL's own cache: cheap;
- `read` — pages fetched from outside it: from disk or from the OS cache, and the plan cannot tell which;
- `dirtied` / `written` — pages changed or written out during the query;
- `temp read/written` — temporary files, meaning something did not fit in memory.

This also explains why a second run is faster: the reads became hits. Compare buffers, not only times, when cache state
differs between runs. In recent PostgreSQL versions `BUFFERS` is on by default with `ANALYZE` *(unverified: PostgreSQL
18)*.

**Handle:** time says *that* a node was slow; buffers say whether it was reading from disk.

</details>

### Why is a sort that spills to disk a red flag in a plan, and how is it tied to memory settings?
<details><summary>Show answer</summary>

A sort that fits in memory shows `Sort Method: quicksort  Memory: 25kB`. One that does not shows
`Sort Method: external merge  Disk: 102400kB`: the database wrote the data to temporary files, sorted it in parts and
merged them. That is many times slower than an in-memory sort.

The limit is `work_mem`: the memory *each* sort or hash operation may use before it spills to disk. It applies per
operation and per connection, so one query can use it several times, and many connections multiply it.

Fixes, in this order:

- avoid the sort: an index that already returns rows in the needed order;
- sort less: fewer rows (filter first, `LIMIT`) and fewer or narrower columns;
- give more memory to this query only: `SET LOCAL work_mem = '256MB'` inside its transaction. Raising it globally can
  run the server out of memory under load.

**Handle:** "Disk" in a sort node means the sort did not fit in `work_mem` — remove the sort or shrink it before
adding memory.

</details>

### What does a plan never show, even with `ANALYZE`?
<details><summary>Show answer</summary>

- Sending rows to the client — `ANALYZE` throws the rows away, so network transfer and client-side processing are
  missing.
- Why time was lost waiting — a lock wait is inside the node's time, but the plan does not say it was a lock.
- Other parameter values — the plan is for the values you typed; another value can get a completely different plan.
- Other moments — concurrent load, cache state and data at a different time.
- Repeated calls — one fast query run 10,000 times by an ORM (N+1) looks fine in a single plan.

For those, look at the application side (logs, tracing), the lock views (`pg_locks`, `pg_stat_activity`) and
statement statistics (`pg_stat_statements`).

**Handle:** a plan explains one execution inside the database — not the network, not the waits, not the call count.

</details>

### A query is fast when you run it with `EXPLAIN ANALYZE` in a console, but slow from the application. Why?
<details><summary>Show answer</summary>

Because the application usually does not run the same thing:

- prepared statements: the application sends parameters, the console uses literal values. After several executions
  PostgreSQL may switch to a generic plan that ignores the actual values. That plan can be bad for skewed values
  (`plan_cache_mode` controls this);
- parameter types: the driver may bind a parameter with a different type than the column. The database then converts
  the column, and the index is not used;
- different SQL: the ORM adds joins, selects more columns, or runs many small queries instead of one;
- fetching: the application downloads and maps all rows; the console's `EXPLAIN ANALYZE` does not;
- session settings, connection pool waits, and cache state differ.

To reproduce it, run the exact SQL from the application log with its parameter types. You can force a generic plan with
`PREPARE` / `EXECUTE` or `SET plan_cache_mode = force_generic_plan`.

**Handle:** to explain an application's slow query, reproduce what the application sends, not what you typed.

</details>

### How do you get the plan for the SQL your ORM actually sends?
<details><summary>Show answer</summary>

- Log the SQL with its bound parameters (in Hibernate: the `org.hibernate.SQL` logger plus parameter binding logging),
  then run `EXPLAIN (ANALYZE, BUFFERS)` on it with those values.
- Let the database log plans itself: the `auto_explain` module writes the plan of every statement slower than a
  threshold (`auto_explain.log_min_duration`) to the server log. With `log_analyze` it also records actual numbers. It
  catches the real prepared statement with its real values.
- Find which statements matter: `pg_stat_statements` sums calls and time per normalized statement. A query that is
  fast once but called 50,000 times shows up here and in no single plan.

**Handle:** log what the ORM sends, let `auto_explain` capture slow plans, and use `pg_stat_statements` to choose what
to look at.

</details>
