# Query Tuning

Why the database skips an index, and what to do with what a plan shows. Examples use PostgreSQL.

- Why the database skips an index — functions on the column, leading `%` in `LIKE`, few distinct values, and other
  traps.
- Using the results — fixes, their cost, and how to prove a fix.
- Interview scenarios.

## Why the database skips an index

### A function or expression on an indexed column in `WHERE`: why is the index not used, and what fixes it?
<details><summary>Show answer</summary>

A B-tree index is sorted by the stored column value. `lower(email)` or `created_at::date` is a different value that is
not in the index, so the database cannot search the index for it. It has to compute the expression for every row.

Fixes:

- index the expression itself, and use exactly the same expression in the query:

  ```sql
  CREATE INDEX users_email_lower_idx ON users (lower(email));
  SELECT * FROM users WHERE lower(email) = 'anna@example.com';
  ```

- or rewrite the condition so the column stands alone:

  ```sql
  -- instead of: WHERE created_at::date = '2026-11-14'
  WHERE created_at >= '2026-11-14' AND created_at < '2026-11-15'
  -- instead of: WHERE amount + 1 > 10
  WHERE amount > 9
  ```

**Handle:** keep the indexed column bare in the condition, or index the exact expression you filter on.

</details>

### `LIKE '%abc'` vs `LIKE 'abc%'`: why can only one of them use a normal index, and which kind of index handles substring search?
<details><summary>Show answer</summary>

A B-tree index is sorted, so `LIKE 'abc%'` is a range: all values from `abc` up to just before `abd`. The index jumps
to the start of that range. With a leading `%` there is no starting point: a match can be anywhere in the sorted order,
so the index cannot narrow the search.

**Trap:** in PostgreSQL with a non-`C` collation, a normal B-tree cannot serve even `LIKE 'abc%'`. You need an index
with a pattern operator class:

```sql
CREATE INDEX users_name_pattern_idx ON users (name text_pattern_ops);
```

For substring search (`LIKE '%abc%'`, `ILIKE`) use a trigram index from the `pg_trgm` extension:

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX users_name_trgm_idx ON users USING gin (name gin_trgm_ops);
```

For searching words in text, full-text search (`tsvector` with a GIN index) is the better tool.

**Handle:** a B-tree finds prefixes; substrings need a trigram index.

</details>

### A column with few distinct values: why does the planner ignore its index?
<details><summary>Show answer</summary>

What matters is how many rows a value matches, not the number of distinct values as such. If `status = 'ACTIVE'`
matches 95% of the rows, an index scan would do a random table read for almost every row, and reading the whole table
in order is cheaper ([full scan vs index scan](1.3.2_Scans_and_Joins.md#when-is-a-full-table-scan-faster-than-an-index-scan)).

The planner knows the frequencies from the most-common-values statistics. So the same index is skipped for `'ACTIVE'`
(95%) and used for `'BLOCKED'` (0.1%). For a column where only the rare value is ever searched, a partial index fits
better:

```sql
CREATE INDEX accounts_blocked_idx ON accounts (id) WHERE status = 'BLOCKED';
```

**Handle:** an index pays off for values that match few rows — on a skewed column, only the rare values benefit.

</details>

### Comparing a column with a value of a different type: why does the index stop working?
<details><summary>Show answer</summary>

When the types differ, the database converts one side. If it converts the *column*, every row's value must be
converted before comparing, and the index on the original values is useless. If it converts the *parameter*, the index
still works. Which side gets converted depends on the database's type rules.

Typical cases:

- MySQL: a `VARCHAR` column compared with a number (`WHERE phone = 1234567`) converts every column value to a number;
- PostgreSQL: a `bigint` column compared with a `numeric` value is converted to `numeric`;
- SQL Server with Java: the JDBC driver sends strings as `NVARCHAR` by default, so a `VARCHAR` column gets converted
  (the driver setting `sendStringParametersAsUnicode=false` fixes it).

The fix: send the parameter in the column's exact type — in SQL literals and in the driver or ORM type mapping.

**Handle:** a type mismatch can silently become a function on the column — match the parameter type to the column.

</details>

### An index on `(a, b)` and a query filtering only by `b`: why is the index not used?
<details><summary>Show answer</summary>

A composite B-tree is sorted by `a` first, and by `b` only inside each value of `a`. Matching `b` values are spread over
the whole index, with no single range to jump to. The index can be searched by `a`, or by `a` and `b`, but not by `b`
alone (the leftmost-prefix rule).

Fixes: a separate index on `(b)`, or a different column order if the other queries allow it. A common rule for the
order: columns compared with `=` first, then the column with a range condition.

Some databases can still use `(a, b)` for `b` when `a` has few distinct values, by jumping through each `a` value (skip
scan). Oracle has it; PostgreSQL added it in version 18 *(unverified)*.

**Handle:** a composite index is usable only from its first column onward.

</details>

### `OR` across different columns: why can it turn an indexed query into a full scan?
<details><summary>Show answer</summary>

For `WHERE email = ? OR phone = ?`, an index on `email` cannot find the rows that match only by `phone`, so one index
scan is not enough. If either column has no index, the database must read the whole table to find all matches.

With an index on each column, PostgreSQL can combine them: two bitmap index scans joined with `BitmapOr`
([bitmap scan](1.3.2_Scans_and_Joins.md#where-does-a-bitmap-scan-sit-between-an-index-scan-and-a-full-scan)). Other
databases have similar "index merge" features. If the planner still does not do it, rewrite the query as two indexed
queries:

```sql
SELECT * FROM users WHERE email = :email
UNION
SELECT * FROM users WHERE phone = :phone;
```

`OR` on the *same* column is not a problem: it is the same as `IN (…)`.

**Handle:** `OR` over different columns needs an index on every column involved, or a `UNION`.

</details>

### After a large data load the planner picks a bad plan. What went stale?
<details><summary>Show answer</summary>

The statistics. They describe the table as it was at the last `ANALYZE`. After a bulk insert, a big delete, or filling a
new table in one batch, the planner still believes the old numbers. It may think a table has 0 rows and pick a nested
loop over what is now millions of rows.

Autovacuum runs `ANALYZE` only after enough rows have changed, and with a delay, so a batch job that loads data and
queries it right away is ahead of it. Temporary tables are never analyzed automatically.

The fix: run `ANALYZE <table>` as a step of the load job, right after the load. It shows up in plans as
[estimates far from actual rows](1.3.1_Query_Plans.md#estimated-rows-and-actual-rows-differ-by-a-factor-of-100-what-does-that-tell-you).

**Handle:** after a bulk change, analyze before you query.

</details>

### The index is usable, but the query returns a large share of the table. Why is it skipped?
<details><summary>Show answer</summary>

Because the planner is right: for `WHERE created_at > now() - interval '5 years'` matching 90% of the rows, a full scan
is cheaper than an index scan. Here nothing prevents the index — the database chooses not to use it, and that is not a
bug.

The fix, if the query is too slow, is in the query, not in the index:

- return fewer rows — page, aggregate in the database, or narrow the filter;
- read fewer columns, so that a covering index allows an index-only scan;
- if the query really needs most of the table, make that cheaper: summary tables, a reporting replica.

**Handle:** when a query needs most of the table, no index will save it — change what it asks for.

</details>

### A condition `WHERE column IS NULL`: can it use an index, and how does an index on only part of the table help, for example to find unprocessed queue rows?
<details><summary>Show answer</summary>

In PostgreSQL, yes: a B-tree index stores `NULL`s, so `IS NULL` can use it. This differs by database. In Oracle, for
example, a single-column B-tree does not store rows where the key is `NULL`, so `IS NULL` cannot use it.

A partial index stores only the rows that match its `WHERE`:

```sql
CREATE INDEX jobs_pending_idx ON jobs (created_at) WHERE processed_at IS NULL;

SELECT * FROM jobs
WHERE processed_at IS NULL
ORDER BY created_at
LIMIT 100;
```

For a queue it fits perfectly: millions of processed rows, a few pending ones. The index holds only the pending rows,
so it stays small, fast and cheap to maintain, and rows drop out of it once processed. The query's condition must match
the index condition, or the planner cannot use it. For several workers polling the same queue, add
`FOR UPDATE SKIP LOCKED`.

**Handle:** a partial index indexes only the rows you search for — ideal for "small active part of a big table".

</details>

## Using the results

### After reading a plan, what are the usual fixes, and in what order do you try them?
<details><summary>Show answer</summary>

From the cheapest and safest to the most invasive, checking the plan again after each step:

- correct the estimates — `ANALYZE`, a higher statistics target, extended statistics. A wrong estimate often causes the
  whole bad plan;
- rewrite the query — keep indexed columns bare in conditions, match parameter types, read fewer rows and columns,
  replace `OR` with `UNION`;
- change the indexes — an expression index, a better column order, a covering index, a partial index;
- adjust settings for this query only — for example `work_mem` for a large sort or hash;
- force a plan — only as a last resort.

**Handle:** fix what the planner knows, then what you ask, then the indexes — force plans last.

</details>

### Why is "just add an index" not free?
<details><summary>Show answer</summary>

- Writes get slower: every `INSERT`, `DELETE`, and every `UPDATE` of an indexed column must update each index.
- In PostgreSQL, an index on a column that is updated often prevents the cheaper in-page ("HOT") update, so the table
  and its indexes bloat faster.
- Indexes take disk space and compete for cache memory with the data itself.
- Building one on a large table blocks writes, unless you use `CREATE INDEX CONCURRENTLY`.

So remove indexes nobody uses: `pg_stat_user_indexes` shows `idx_scan = 0` for them. Prefer extending an existing index
(a composite or covering index) over adding a new one.

**Handle:** every index speeds some reads and taxes every write — keep only those that earn their place.

</details>

### Why is forcing a plan (hints, switching off a scan type) a last resort?
<details><summary>Show answer</summary>

A forced plan freezes one decision while the data keeps changing. It is right today and wrong when the table has grown
or the distribution has shifted, and nobody notices because nothing changed in the code. It also hides the real cause —
usually a bad estimate or a bad query — instead of fixing it.

In PostgreSQL there are no hints in the core product (the `pg_hint_plan` extension adds them). The `enable_*` settings
(`SET enable_seqscan = off`) are a diagnostic tool: use them in a session to check whether the other plan really is
faster. If it is, find out why the planner did not pick it.

If you do force a plan, limit it to that one query and document why.

**Handle:** use plan switches to test a theory, not as the fix.

</details>

### How do you prove a fix helped? What do you compare before and after?
<details><summary>Show answer</summary>

- Run `EXPLAIN (ANALYZE, BUFFERS)` before and after, with the same parameter values — several of them, including the
  rare and the very common ones.
- Compare buffers as well as time, because time depends on the cache state. Fewer pages read means the fix works even
  when timings are noisy. Run each version several times.
- Use production-like data volume, or the result means little.
- After deployment, check the real effect in `pg_stat_statements`: mean and total time for that statement.
- If the fix added an index, also check write performance on that table.

**Handle:** prove a fix with the same inputs, buffers as well as time, and production numbers afterwards.

</details>

## Interview scenarios

### A query got slow overnight with no code change. How do you investigate?
<details><summary>Show answer</summary>

No code change means something else changed: data volume or distribution, statistics, the plan, the load, or the
settings.

- Confirm which statement and since when: `pg_stat_statements`, monitoring, slow-query logs.
- Get its current plan with real parameters: `EXPLAIN (ANALYZE, BUFFERS)`, and compare it with an older plan if one was
  logged (`auto_explain`). A changed plan ("plan flip") is the most common cause.
- Compare estimated and actual rows to find where the planner went wrong.
- Check the statistics and vacuum state: `last_analyze`, `last_autovacuum`, dead rows in `pg_stat_user_tables`.
- Check waiting: locks and wait events in `pg_stat_activity` — the plan may be the same, and the query is just waiting.
- Check load and settings: other heavy jobs, a recent configuration or version change.

Then fix the cause, usually `ANALYZE`, an index, or a query rewrite, and verify it with the same plan comparison.

**Handle:** same code, new slowness — find what changed: plan, statistics, data, or waiting.

</details>

### How do you decide whether an index is worth adding?
<details><summary>Show answer</summary>

Weigh what it saves against what it costs:

- the gain: how slow the query is and how often it runs. `pg_stat_statements` total time shows its real weight;
- the selectivity: the index must narrow the condition to few rows, or the planner will not use it;
- the write cost: how write-heavy the table is, and how many indexes it already has;
- the alternatives: can an existing index be extended (an extra column, `INCLUDE`), or can the query be rewritten
  instead?

Then test on production-like data: the plan before and after, buffers, and write timings. After deployment, check that
the index is actually used (`idx_scan`).

**Handle:** an index is worth it when frequent, selective reads gain more than the table's writes lose.

</details>
