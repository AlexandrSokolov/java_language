# Scans and Joins

The operators inside a query plan: how a table is read and how two inputs are joined. Examples use PostgreSQL.

- Full table scan vs index scan vs index-only scan, bitmap scan.
- Nested loop vs hash join vs merge join, and the join order.

## Scan types

### Full table scan vs index scan vs index-only scan: what does each one read?
<details><summary>Show answer</summary>

- Full table scan (`Seq Scan`) reads every page of the table in physical order and checks each row against the
  condition.
- Index scan (`Index Scan`) walks the index to the matching entries, then fetches each matching row from the table by
  its pointer. The index is read in order, but the table pages are random reads.
- Index-only scan (`Index Only Scan`) answers from the index alone and does not touch the table, because every column
  the query needs is in the index.

From the table's point of view: a full scan reads all of it, an index scan reads only the matching rows at random
places, and an index-only scan ideally reads none of it.

**Handle:** full scan = all pages in order; index scan = index + random table reads; index-only = index only.

</details>

### When is a full table scan faster than an index scan?
<details><summary>Show answer</summary>

When the query needs a large share of the table. An index scan pays one random table read per matching row, and a full
scan reads each page once, in order. Sequential reads are much cheaper than random ones, so above some share of rows
the full scan wins. The share depends on row size, caching and how the rows are spread, so there is no fixed
percentage.

Also on small tables: a few pages are read faster in one pass than through an index.

So a `Seq Scan` in a plan is not a bug in itself. It is a problem only when the query returns few rows and the
planner chose it anyway.

**Handle:** an index helps to find *few* rows; for many rows, reading everything in order is cheaper.

</details>

### What makes an index-only scan possible, and why can it still touch the table?
<details><summary>Show answer</summary>

It needs every column the query uses — in `SELECT`, `WHERE`, `ORDER BY` — to be in the index. A covering index adds
extra columns only for this purpose:

```sql
CREATE INDEX orders_customer_idx ON orders (customer_id) INCLUDE (status, total);
```

It can still touch the table because a PostgreSQL index does not know whether a row version is visible to your
transaction; only the table has that information. PostgreSQL keeps a visibility map that marks pages where all rows are
visible to everyone. For pages not marked, the scan must check the table. The plan shows how often:

```text
Index Only Scan using orders_customer_idx on orders  (actual rows=5000 loops=1)
  Heap Fetches: 4800
```

`VACUUM` (usually autovacuum) updates the visibility map. A table that is updated often, with vacuum lagging behind,
has many heap fetches, and the "index-only" scan reads the table anyway.

**Handle:** index-only needs all columns in the index *and* a fresh visibility map — check `Heap Fetches`.

</details>

### Where does a bitmap scan sit between an index scan and a full scan?
<details><summary>Show answer</summary>

It is for the middle case: too many rows for one random read per row, too few for reading the whole table. It works in
two steps:

- `Bitmap Index Scan` reads the index and builds a bitmap of the table pages that contain matches;
- `Bitmap Heap Scan` reads those pages in physical order, each page only once, and rechecks the condition there.

```text
Bitmap Heap Scan on orders  (actual rows=40000 loops=1)
  Recheck Cond: (status = 'NEW')
  ->  Bitmap Index Scan on orders_status_idx  (actual rows=40000 loops=1)
```

Bitmaps from several indexes can also be combined (`BitmapAnd`, `BitmapOr`). That lets PostgreSQL use two separate
indexes for `a = 1 OR b = 2`. When the bitmap does not fit in `work_mem`, it keeps only whole pages, and the recheck
filters more rows.

**Handle:** a bitmap scan turns many random row reads into one ordered pass over the needed pages.

</details>

## Join algorithms

### How does a nested loop join work, and when does the planner choose it?
<details><summary>Show answer</summary>

For each row of the outer input, it looks up the matching rows in the inner input. The work is roughly
"outer rows × cost of one inner lookup".

It is the best choice when the outer input is small and the inner table has an index on the join key: a few rows, each
with one cheap index lookup. That is why it is typical for fetching one order with its lines. It is also the only
method for join conditions that are not equality, such as `a.start < b.time`.

**Trap:** if the planner expects 10 outer rows and gets 1,000,000, the nested loop runs a million index lookups. This is
the classic disaster plan caused by a bad row estimate.

**Handle:** nested loop = a small outer input with an index lookup per row; great for few rows, terrible for many.

</details>

### Why does a hash join need memory, and what happens when the hash table does not fit?
<details><summary>Show answer</summary>

A hash join reads one input (usually the smaller one) and builds a hash table on the join key in memory. Then it reads
the other input row by row and looks each key up in that table. Both inputs are read once, so it suits large inputs
with no useful index. It works only for equality joins.

The hash table must fit into the operation's memory limit (`work_mem`, multiplied by `hash_mem_multiplier` in newer
PostgreSQL *(unverified: default 2.0)*). If it does not fit, the join splits both inputs into batches, writes them to
temporary files, and processes one batch at a time. The plan shows it:

```text
Hash  (actual rows=2000000 loops=1)
  Buckets: 131072  Batches: 16  Memory Usage: 4096kB
```

`Batches` above 1 means extra disk I/O. A bad estimate can also make the planner build the hash on the input that is
actually the larger one.

**Handle:** hash join = build a table from one side, probe with the other; it is fast while the hash table fits in
memory.

</details>

### What must be true of the input before the planner can use a merge join?
<details><summary>Show answer</summary>

Both inputs must be sorted on the join key, and the condition must be an equality. Then the join walks both sorted
inputs in step, like merging two sorted lists, and reads each one once.

The sorted order comes either from an index scan on the join key or from an explicit `Sort` node. Merge join wins when
both inputs are large and already sorted. If they first have to be sorted, the sort cost often makes a hash join
cheaper. It is also a good fit when the query needs the result in that order anyway.

**Handle:** merge join = two sorted inputs zipped together; it is cheap when the order already exists.

</details>

### The query says `A JOIN B JOIN C`. Does the plan join them in that order, and who decides the real order?
<details><summary>Show answer</summary>

Not necessarily. For inner joins, the written order has no meaning for execution. The planner tries different orders
and join methods and picks the cheapest estimated combination. Usually it starts from the input that leaves the fewest
rows after filtering.

Limits:

- outer joins restrict reordering, because moving them would change the result;
- with many tables, the planner stops searching all orders. In PostgreSQL, above `join_collapse_limit` (default 8)
  it keeps the written order for the rest, and above a larger threshold it switches to a heuristic search
  *(unverified: defaults)*.

So for queries joining many tables, the written order can matter again, and bad estimates lead to bad join orders.

**Handle:** you write which tables to join; the planner decides the order — except where outer joins or table count
limit it.

</details>
