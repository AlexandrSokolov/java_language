
### What to keep in mind handling NPE?
<details><summary>Show answer</summary>

The problem is unique to NPE: a well-written exception says what went wrong in its message ("email is required"),
but a null dereference historically said almost nothing. So NPE is the one exception where the message alone rarely
lets you act, and the design has to work harder to make it locatable.

**Before (pre-JDK 15).** A null dereference threw with a **null message** — the code did `throw new
NullPointerException()` implicitly, no string. `toString()` gave you the class name alone: `java.lang.NullPointerException`,
nothing about *what* was null or *where*. In an expression like `a.b.c.d`, you could not tell which link was null
without a debugger or a full stacktrace dump.

**Now, default compile (JDK 15+, no flags).** JEP 358 rewrote the message to name the null reference:
`Cannot invoke "String.getHost()" because "<local2>" is null`. You learn the failed operation and *that* a local was
null — but by a synthetic name (`<local2>`), because the local's real name is not in the class file without debug info.

**With debug info (`javac -g`).** The synthetic name becomes the source name: `... because "config" is null`. Now the
message reads like your code. Still **no line number** — helpful-NPE names the reference, never the line.

**What you extend to get full context.** Two additions, each closing a different gap:

- **Caller context** — the failing spot knows what was null, not *why it was called* (which object, which run). Only
  the caller has that. Pass it in and attach it to the failure: `tenant 9002 nightly run -> ...`.
- **Throw site, not the whole stack** — `error.getStackTrace()[0]` is one `Class.method(File:line)` line: the exact
  spot, no stack dump. For a wrapped chain, walk `getCause()` and take `[0]` of each link — guard the walk with an
  identity check (`IdentityHashMap`), because a self-referential cause loops forever.

Rule of thumb: 
- message names *what* was null (free, JDK 15+), 
- `-g` makes the name real, 
- caller context adds *why*,
- `getStackTrace()[0]` adds *where* — pick the level the reader needs.

</details>

### What to keep in mind enabling debug info for compiler?
<details><summary>Show answer</summary>

Debug info is three tables the compiler writes into the class file: 
- **lines** (`LineNumberTable` — maps bytecode back to source lines, this is what puts `File.java:214` in a stacktrace), 
- **vars** (`LocalVariableTable` — the real names of locals, 
  this is what makes helpful-NPE say `config` instead of `<local2>`),  
- **source** (the source file name).

**Cost side — all small for server code:**
- Bigger class files. The tables add ~10-20% to `.class` size. It's disk and load-time footprint, not runtime speed.
- **No execution cost.** The JIT never reads these tables; bytecode runs identically with or without them. Anyone who
  says `-g` slows a program down is wrong.
- Your own code is a few hundred KB against tens of MB of Spring/Hibernate/Netty you didn't write — the size bump is
  invisible at that ratio.

**The one real trade-off — information disclosure.** `vars` puts your real local names into the shipped bytecode, so a
decompiler produces near-source output. Matters for code you *hand out* (a distributed library/desktop app). Does not
matter for a service on a machine you control — nobody pulls your bytecode off it.

**What the build tools actually do (so you know the default you're overriding):**
- **Gradle** defaults to full `-g` (source + lines + vars) — Spring itself is Gradle-built and *needs* `vars`, its bean
  wiring can read local names.
- **Maven** compiler plugin: `debug` is on by default and with no level set it passes bare `-g`, which is also full.
- Plain `javac` with no flags gives lines + source but **not** vars.

So the libraries you depend on ship with full debug info — not by hand-writing `-g:vars`, but because the build default
is full and nobody strips it.

**Maven — force full debug explicitly** (line numbers + local names):

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <debug>true</debug>
    <debuglevel>lines,vars,source</debuglevel>
  </configuration>
</plugin>
```

Rule of thumb: for a server you control, ship full debug info — the size cost is noise and the disclosure cost doesn't
apply. Strip `vars` only when you hand the bytecode to someone else.

</details>

### Bad argument value — which exception?
<details><summary>Show answer</summary>

`IllegalArgumentException` — the caller passed an argument whose value is inappropriate (e.g. a negative count for a
parameter that means "how many times to repeat").

</details>

### Arg is well-formed but the call can't succeed now?
<details><summary>Show answer</summary>

Local checks answer one question — *is this data well-formed?* (format, required fields, no nulls). 

The state answers a different one — *given this data, is the thing it points at usable right now?* 
A config can be perfectly formatted and still name credentials that don't log in, or a host that's down.


When the failure is that second kind, don't throw an argument exception just because you found the problem by looking at
an argument. The argument did its job — it was well-formed. What failed is the state behind it: the session isn't valid,
the login doesn't work, the resource isn't in a usable condition. Name it as a state problem.


And sometimes you can't even finish the state check — the network drops, the host is unreachable — so you never learn
whether the state is good or bad. That's not an argument problem either: the data was fine, you just couldn't reach the
thing to verify it. That belongs to the outside world failing.


Why lean to state, not argument, when it could formally go either way: state is the more honest description. 
"Bad argument" tells the reader *you passed something wrong* — but they didn't, the input was correct. 
The real story is the world the input describes wasn't ready. 
Naming it a state failure sends whoever reads the log to the session, the connection, 
the remote system — not back to re-check an argument that was never the problem. 
That's what makes it more maintainable: the exception points at the actual cause, not at where you first noticed it.

</details>

### Null passed where null is banned — which exception?

`NullPointerException`, not `IllegalArgumentException` — that's the convention for a prohibited null argument.

### Exception chaining — what to actually consider?
<details><summary>Show answer</summary>

Chaining means: catch the failure, throw your own exception, pass the original in as the *cause*
(`new AppException(msg, cause)`) so `getCause()` and the merged stack trace survive.

**When do I even catch?** With the unchecked convention you already catch checked exceptions at the source and rethrow
unchecked, keeping the cause. So "should I chain" is mostly settled — the open question is *where* you catch, and that's
decided by context, not by layers.

**With context vs without context — the real axis.** Chaining alone keeps the cause but adds nothing. What makes it
worth doing is the *message you add at the catch site* — facts the cause can't carry. Catch at the spot that *holds*
those facts, which is often the caller, not the throw-site. Example: a list's `get(index)` can only add the index. Its
*caller* knows the index **and** the current size — so it can say "index 5 but list held 4", pointing straight at the
real bug (the splitter thought it had 5 items). The throw-site can't say that; it doesn't know the caller's story.
`new AppException(cause)` is useless at 3am; `new AppException("index " + i + " of " + size, cause)` survives the
incident. Same idea as the streams `Result` `source`/`stage`/`describe()` fields — the exception is the transport, the
added context is the value.

**Low-level vs high-level type (mostly for interview).** There's a named principle worth being able to state: a method
shouldn't leak an exception from a lower layer, because it confuses the caller and ties the higher API to
implementation details that break clients when they change — so you translate the type to one that fits the caller's
level (e.g. an iterator's "no such element" → an index-out-of-range). Note this is a separate axis from
checked-vs-unchecked: a type can be unchecked and *still* leak a low-level concept.

</details>

### Catching a low-level exception — how to wrap it right?
<details><summary>Show answer</summary>

A low-level exception names a low-level thing ("no such element", "SQL constraint violated"). Correct there, wrong for
a caller working higher up — it can't act on a concept it doesn't understand, and your API is now tied to that type
(swap the storage, it breaks).

**Wrap by re-expressing the concept in the caller's words, not re-boxing the same one:**
- "no such element" → "index out of range" (caller asked by index)
- "SQL constraint violated" → "user already exists" (caller creating a user)

`catch (SQLException e) { throw new SQLRuntimeException(e); }` — still says "SQL". Leaked. Ask *what does this mean to
the caller?*, not *what threw it here?*

Keep the cause: `new HigherException(msg, cause)` — caller sees a type it understands, debugger keeps the root.

</details>

### Catch-and-log — what goes wrong in practice?
<details><summary>Show answer</summary>

The common advice is to log the failure in the catch block and insulate the caller. We don't take that fully: logging
in every catch that then rethrows produces the same error logged at each layer, each with its own stack trace. The log
fills with duplicates and the two lines you need are buried in two hundred.

Our rule: a catch that *rethrows* doesn't log — it isn't done handling. Only the catch that *stops* the error logs it,
once, with the whole chain: the top handler, or the point where you convert to a result and move on.

</details>

### Avoiding exceptions instead of chaining them?
<details><summary>Show answer</summary>

The best failure is one that never throws. Before reaching for chaining, check the inputs up front and return a result
that carries either the value or the error — so the normal path has no exception to catch at all.

This isn't part of chaining; it's the layer above it. Chaining is what you do *once you've decided a throw is the right
tool*. Prefer validation and a result type first; chain only for the failures you couldn't prevent.

</details>



### Diagnose: `logger.error(exc)`
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
try {
  ...
} catch (SomeException exc) {
  logger.error(exc);
}
```

</details>

<details><summary>Show answer</summary>

Passes the exception where a message string is expected, so only `exc.toString()` is logged — class name plus message,
no stack trace. Often useless: you get "SomeException: failed" with no line, no cause chain, no way to locate it.

Fix — pass it as the *cause*, second arg, with a message:

```java
logger.error("loading config for tenant " + id, exc);
```

Now the full stack trace and cause chain are logged. 
Rule: the throwable goes in the throwable slot, never the message slot.

</details>

### How to document a method's exceptions?
<details><summary>Show answer</summary>

Two segments — document checked and unchecked separately, each with `@throws`:
- **checked** — part of the contract, the caller must handle them.
- **unchecked** — the preconditions; each one tells the caller what not to do.

```java
/**
 * @throws IOException           if the file can't be read
 * @throws IllegalArgumentException if {@code count} is negative
 * @throws NullPointerException  if {@code path} is null
 */
public Data load(Path path, int count) throws IOException { ... }
```

Checked go in the `throws` clause in the method signature too; unchecked only in the doc. 
Documenting the unchecked ones turns them into a stated precondition list.

If the same exception is thrown by many methods for the same reason, document it once on the *class*, not per method —
e.g. "all methods throw `NullPointerException` if any parameter is null."

</details>

### How should an exception's message read?
<details><summary>Show answer</summary>

Two different messages for two different audiences — don't merge them:

- **Detail message** (in the exception, for whoever debugs) — max information, all the values that caused it, not
  localized, readability doesn't matter. `"index 5, size 4, tenant 9002"`.
- **User-level message** (shown to the end user) — readable, no internals, often localized. `"Couldn't load your file."`

Trap: putting a debug-grade string in front of the user, or a polite vague string in the exception. The first leaks
internals; the second throws away everything you'd need at 3am. Keep them separate — the handler maps one to the other.

</details>

### Secrets in an exception message?
<details><summary>Show answer</summary>

Never — no passwords, keys, or tokens in a detail message. Stack traces get pasted into tickets, logs, and chats seen
by many people.

</details>

### Carrying failure details beyond `toString()`?
<details><summary>Show answer</summary>

`toString()` gives one flat string — fine for a log, useless if a caller needs a *value* from the failure. To carry
structured detail:

- **Constructor takes the raw values**, builds the message itself — the thrower can't forget to include them:

```java
public NotEnoughStock(int requested, int available) {
  super("requested " + requested + ", only " + available + " available");
  this.requested = requested;
  this.available = available;
}
```

- **Accessors expose them** (`getRequested()`, `getAvailable()`) so a caller can read the fields, not parse the string.

This is the real reason to write your own exception type: needing these extra fields *is* the justification. If a
standard type carries everything, reuse it; if you need to carry `requested`/`available`, that's your own class.

</details>

### Keeping an object's state clean when a call fails?
<details><summary>Show answer</summary>

Goal: a failed method leaves the object as it was before the call — no half-done mutation.

For a single in-memory object it's usually cheap. Ways to get it, cheapest first:

- **Immutable object** — free; a failure just prevents a new object, never corrupts an existing one.
- **Check inputs first** — validate before mutating, so most throws happen before any change.
- **Order the work** — run the parts that can fail before the parts that mutate.
- **Copy and swap** — do the work on a temporary copy, replace the original only on success.

Doesn't hold under unsynchronized concurrent modification, and don't bother for `Error`/`AssertionError`.

For persisted, multi-system work none of this holds — you can't un-send a remote call or roll back memory. There you
lean on the transaction boundary, idempotent retries, and a workflow state that records how far it got, so a failed
step can be re-driven instead of undone.

</details>

### When is swallowing an exception OK — and how to mark it?
<details><summary>Show answer</summary>

Rarely, but yes: when there's genuinely nothing to recover and no reason to abort — e.g. a failure closing a stream
you've already read, or an optional step that timed out and a default is fine.

Mark it so it doesn't read as a forgotten catch: name the variable `ignored` and add a comment saying *why* it's safe.

```java
try {
  numColors = f.get(1, SECONDS);
} catch (TimeoutException | ExecutionException ignored) {
  // default coloring is fine; the result is an optimization, not required
}
```

An empty, silent catch is indistinguishable from a bug. The name + comment is what makes it a deliberate choice.

</details>
