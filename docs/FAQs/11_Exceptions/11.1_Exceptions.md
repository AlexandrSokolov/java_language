
### What must exceptions never do?
<details><summary>Show answer</summary>

Drive ordinary control flow — normal loops or branches. They're only for exceptional conditions.

</details>

### Method valid only sometimes — what to provide?
<details><summary>Show answer</summary>

A "state-dependent" method — one that can be called only under certain conditions the caller can't predict —
should generally come with a separate "state-testing" method that tells the caller whether calling it is
appropriate right now. This keeps the API from forcing clients to use exceptions for ordinary control flow.

</details>

### State-testing pair — JDK example?
<details><summary>Show answer</summary>

`Iterator`: `next()` is the state-dependent method — legal only when more elements remain, otherwise it throws
`NoSuchElementException`. `hasNext()` is its state-testing pair — returns whether calling `next()` is safe now.

```java
while (it.hasNext())   // state-testing: safe to call next()?
  process(it.next());  // state-dependent: throws if called when empty
```

Without `hasNext()`, the caller would have to call `next()` and catch the exception to detect the end — exactly
the exception-for-control-flow the pair avoids.

</details>

### State-testing — where to put the check?
<details><summary>Show answer</summary>

**1. Separate state-testing method** (e.g. `hasNext` beside `next`) — caller checks first, then calls.
- For: readable call site; caller can test **without** triggering the effect — needed when they want the answer
  but not the action (e.g. run every validation and collect all failures before doing anything).
- Against: two calls where one might do; **races** if the object's state can change between test and call
  (another thread, or the call itself mutates state) — the test's answer is stale by the time you act on it.

**2. Fold the test into the state-dependent method** — no separate method; the call itself reports the state.
- For: one call, no gap for the state to change in — no race.
- Against: the caller can't ask in advance, so they can't check without committing to the call.


Choosing: 
- prefer the separate method when the caller needs the answer without the effect and no concurrency threatens the gap; 
- prefer `Optional`/throw when the object is shared or its state shifts between test and call.

</details>

### State check — what to return?
<details><summary>Show answer</summary>

One axis: **how much the return value carries.** More carried = caller learns more without a second call, at the
cost of a heavier type. Pick the least that answers what the caller must decide.

**boolean — 1 bit: "OK or not."**
- Fits when there's only one way to fail, or the caller doesn't care why (e.g. `hasNext`).
- Breaks down when there are several failure reasons and the caller must tell them apart — a `boolean` forces a
  second call to find out why, or worse, callers guess.

**`Optional<T>` — presence: "here's something, or nothing."** Two ways to use it, opposite meanings:
- **Standard:** present = the value, empty = failure/absence. Folds the check into the return; the signature
  makes "may be empty" impossible to forget.
- **Inverted — `Optional<Error>`:** empty = success (nothing wrong), present = the error. This reads very clean
  for validation: a check returns empty when it passes, or the problem when it fails. Callers drop the empties
  and keep the failures — `filter(Optional::isPresent)` across many checks gathers every error into one report,
  then you decide once whether to proceed. No exceptions, no separate tester.
- Limit of both: `Optional` carries presence only, not a value *and* a reason together. If success must also
  carry a payload, `Optional` runs out of room — move to `Result`.

**`Result` / `Either` — full outcome: "success with a value, or failure with a reason."**
- Fits when failure needs an explanation the caller acts on — validation errors, distinct causes, anything
  where "what went wrong" drives the next step.
- Cost: not built into the JDK (you write or import it), and callers must unwrap it. Worth it exactly when the
  reason is load-bearing.
- This is also what lets you **collect many failures instead of stopping at the first** — run every check, keep
  each non-success, combine into one report. A boolean or exception can't do that; the reason has to be a value
  you can gather.

**Note — throwing** is a fourth channel, but it only works folded into the call, never as a separate testing
method (a tester that throws defeats its own purpose). Use it when failure is truly rare and unrecoverable here;
avoid it for ordinary, expected failure — that's control flow by exception.

Handle: **least that answers the caller's real question** — one bit → boolean; a value-or-nothing → `Optional`; a
reason the caller acts on → `Result`.

</details>

### Collecting all validation errors — ways?
<details><summary>Show answer</summary>

Goal: run every check and report **all** failures at once, not stop at the first. Three ways in Java:

**1. Manual — collect into a list.** Run each check, gather the failures yourself, decide at the end.

```java
List<String> errors = new ArrayList<>();
if (name.isBlank())        errors.add("name is blank");
if (age < 0)               errors.add("age is negative");
if (!email.contains("@"))  errors.add("email is malformed");
if (!errors.isEmpty()) return failure(errors);  // stop before doing the work
```

Or with `Optional<Error>` per check: `Stream.of(check1(), check2(), ...).filter(Optional::isPresent)...`.
No dependency, works everywhere — but you hand-roll the accumulation every time and nothing enforces that a
check's result gets inspected. This is you doing by hand what a library type does for you.

**2. Vavr `Validation`** — a library type built for exactly this. `Valid` holds the success; `Invalid` holds a
`Seq` of errors. Unlike a monad (which stops at the first error), `combine(...).ap(...)` runs every check and
gathers all failures:

```java
Validation<Seq<String>, Person> result =
  Validation.combine(validateName(name), validateAge(age)).ap(Person::new);
// Valid(Person(...))  or  Invalid(Seq("name bad", "age bad"))
```

This is the closest Java gets to the Scala/Cats fail-slow style — a real applicative that accumulates instead
of short-circuiting. Cost: a third-party dependency.

**3. Bean Validation (JSR-380, `@NotNull`/`@Size` + a `Validator`)** — annotation-driven; `validator.validate(obj)`
returns the full `Set<ConstraintViolation>`, all errors at once. Fits when validation is field-level on a bean
(web form, request DTO). Cost: reflection/annotations, less flexible for cross-field or state-of-system checks.

Handle: manual (always available, you accumulate by hand) → Vavr `Validation` (applicative, accumulates for you)
→ Bean Validation (annotations, all violations in one `Set`). Pick by how much machinery the failure justifies.

</details>

### Why does Scala's for-loop stop at first error?
<details><summary>Show answer</summary>

Scala's `for`-comprehension desugars to `flatMap`/`map`. `flatMap` is **sequential** — each step gets the previous
step's unwrapped value, so step 2 can't run until step 1 succeeds. That data dependency is what forces **fail-fast**:
the first error has nowhere to hand its value to, so the chain stops. This isn't `Either` being special — `Either`
short-circuits *because* you thread it through `flatMap`. Any type in a `for`-comprehension fail-fasts.

To accumulate all errors you need the opposite combine: **applicative** (`mapN`, `tupled`), which combines
independent steps in parallel with no step depending on another's result. With no data dependency, there's nothing
forcing a stop at the first failure, so all failures can be gathered.

- **Monad** (`flatMap`, `for`) → sequential → fail-fast. Use when a step depends on an earlier step's value.
- **Applicative** (`mapN`) → independent → accumulate. Use when the checks don't depend on each other — validation.

The dividing line is **independence**: you can only accumulate when the checks don't depend on each other. The
moment step 2 needs step 1's output, fail-fast is forced by the logic, not the type. The Cats library supplies the
accumulating type (`Validated` / `ValidatedNel`) — same shape as `Either` but with an applicative combine that
collects `Invalid` values instead of stopping.

Java has none of this at the language level: no `for`-comprehension, no applicative machinery. You do it by hand
(collect a `List<Error>`) or reach for Vavr's `Validation`, which is the direct analog of Cats' `Validated`.

</details>

### Exception types — language difference?
<details><summary>Show answer</summary>

`Throwable` splits into three:

**`Error`** — thrown by the JVM for serious problems you're not meant to recover from (`OutOfMemoryError`, 
`StackOverflowError`). Unchecked. Don't catch, don't subclass.

**`Exception` minus `RuntimeException` — checked.** The compiler forces the caller to either `catch` it or declare
`throws` in the signature. Won't compile otherwise. (`IOException`, `SQLException`.)

**`RuntimeException` — unchecked.** No compiler obligation — catch it or don't, declare it or don't, it compiles
either way. (`NullPointerException`, `IllegalArgumentException`, `IllegalStateException`.)

The rule is purely a **subtype test**, checked at compile time: 
is the thrown type a subclass of `RuntimeException` or `Error`? → unchecked. 
Otherwise → checked. 
Nothing about the exception's *meaning* enters into it; it's where the class sits in the hierarchy.

Handle: **checked = compiler makes you handle it; unchecked (`RuntimeException` + `Error`) = it doesn't.** 
The line is drawn by the class tree, not by how serious the failure is.

</details>

### Checked exceptions — rules worth questioning?
<details><summary>Show answer</summary>

Bloch's case for checked, each claim met with a question and the proof unchecked does the same. 

**"Checked forces the caller to deal with the problem — better reliability."**
- Ask: does forcing produce *handling*, or just `catch (e) { throw new RuntimeException(e); }` at every layer?
- Proof: the forced action is usually a mechanical rethrow, done worse than choosing one place to handle. It
  also breaks streams and lambdas. Enforcement buys awareness, not reliability.

**"Use checked for recoverable conditions."**
- Ask: is there a recoverable operation that *cannot* be handled with unchecked?
- Proof: none found. Unchecked expresses any recovery — catch it and act. The only thing dropped is the compiler
  mandate. Recoverability and checked-ness are independent axes.

**"Checked exceptions carry methods that help the caller recover."**
- Ask: is that a property of *checked*, or of exceptions being objects?
- Proof: unchecked exceptions carry the same data. `WebApplicationException` (unchecked) holds a full `Response`;
  Spring's unchecked `DataAccessException` carries rich cause info. Recovery data has nothing to do with checked.

**The industry check (the strongest single question):**
- Ask: is there any modern framework that still uses checked exceptions?
- Proof: no major one. Spring (`DataAccessException`), Hibernate (rewrote checked→unchecked, kept subtypes),
  Jakarta REST (`WebApplicationException extends RuntimeException`), Kotlin (dropped checked from the language).
  Every one moved *from* checked *to* unchecked, and kept types. The verdict: API flexibility over enforcement.

Handle: against any pro-checked claim, ask two questions — **"does a live framework use it?"** and **"can unchecked
do the same?"** Both answers push the same way. Enforcement is checked's only real offer, and the industry
declined it.

</details>

### Exception types — how many do you need?
<details><summary>Show answer</summary>

A type exists to let code **branch** on it. If nothing branches, the type selects nothing — it's dead weight.
So the count follows one question: **does a caller take a different code path per cause?**

- **Library / framework — many types.** The caller is a stranger whose code branches on what failed; the type is
  their only machine-readable signal. Give distinct types (`ConstraintViolationException`,
  `OptimisticLockException`). Parsing your message string instead is fragile and non-portable.
- **Application with a uniform handler — one type.** Every failure gets the same reaction (report + park the
  state), so no code branches on the cause. The cause lives in the *message*, not the type. One neutral base type
  (`AppException extends RuntimeException`) is enough — and prefer it over reusing `IllegalStateException`, whose
  JDK meaning ("object in wrong state") lies about an IO or config failure.

Where apps go wrong: building a library-sized hierarchy no code ever branches on. Every unused type is a tax —
each review you stop and adjudicate "does this distinction matter here?" across a hundred cards. Add a type only
when your own code will `catch` it separately.

Handle: **type per branch, not per cause.** Many branchers (a stranger's code) → many types. One uniform handler
(your app) → one type; the cause goes in the message.

</details>

### What should error handling aim for?
<details><summary>Show answer</summary>

The goal is not to record what broke — it's to turn a failure into something the **least-skilled person who
must act** can act on, with no code branch and no developer pulled in. In an app specifically:

- **Feedback is for the user or support, not the developer.** A clear "what went wrong and how to fix it" in the
  place they look — not a stack trace, not a technical cause. The reader should resolve it without reading logs.
- **Minimize developer involvement.** Ideally nobody with deep knowledge is needed to fix it. Pulling in support
  is already costly; pulling in a developer is worse. A good message removes both from the loop.
- **Report vs. retry are different jobs.** Reporting tells a human what to do. Retry is not the human's job and
  not the catch block's — it lives in the state machine: leave the item unadvanced, the next run re-picks it. A
  transient failure clears itself; a permanent one keeps failing and its message escalates.
- **Forgetting to handle must be harmless.** If an unhandled error can corrupt state, the bug is that correctness
  depended on a `catch`. Make the operation atomic — then skipping the handler just reports, it doesn't break
  anything. Consistency lives in the transaction, not the caller's diligence.
- **Library vs. app differ in destination.** A library hands the error *up* to a caller who branches on it. An app
  *resolves* it into human-actionable feedback — the buck stops here, it doesn't propagate to a stranger.

Handle (provisional): the handler turns a failure into a fix the least-skilled reader can apply alone — feedback
not stack trace, retry in the state machine not the catch, correctness in the transaction not the caller.

</details>

### Does checked have one real advantage?
<details><summary>Show answer</summary>

One, and only one: **enforced awareness.** The compiler forces the caller to make a conscious decision at the
call site — a `throws` clause can't be silently ignored, a Javadoc `@throws` line can. Unchecked cannot do this.
Everything else checked offers, unchecked matches; this is the single real difference.

So the honest question isn't "can unchecked do it?" — it's "is the forced awareness worth its cost?" Two reasons
it usually isn't:

- **The forced decision is almost always the wrong one.** What the compiler extracts is `catch (e) { throw
  unchecked(e); }` — awareness on paper, a mechanical rethrow in practice, plus broken streams and lambdas.
- **Correctness shouldn't depend on the caller remembering.** The case for enforced awareness is "if they forget,
  something breaks." But if forgetting can break an invariant, the fix is to make the operation atomic — then
  forgetting is harmless (it just reports). Consistency belongs in the transaction, not the caller's `catch`.
  Once correctness is guaranteed by the operation, enforcement protects nothing.

What survives after both: a caller who must take a **forward action only they can decide**, at that site, where
doing nothing is silently wrong and no atomic boundary covers it. Real in theory — but every concrete instance
probed (payment shortfall, parse-with-fallback, transfer) dissolved into *reporting to a human* or into
*unchecked-with-a-type*. Rare enough to never meet in practice, and still beatable with typed-unchecked plus state.

Handle: checked's only genuine edge is **enforced awareness**. Reject it not because unchecked mimics it — it
can't — but because the forced decision is a rethrow, and real correctness lives in atomic operations and state,
not in the caller remembering to catch.

</details>

### Which throwable types may you define?
<details><summary>Show answer</summary>

Only subclasses of `RuntimeException` (for your unchecked types) or `Exception` (for checked). Two things are
off-limits:

- **Never subclass `Error`, and never throw one** (except `AssertionError`, which the JVM/assert machinery owns).
  By near-universal convention `Error` is reserved for the JVM to signal conditions that make continuing
  impossible — resource limits, invariant failures. Defining your own collides with that meaning.
- **Never define a throwable that's neither `Exception` nor `RuntimeException`.** It's legal — a direct
  `Throwable` subclass behaves as a checked exception — but it has zero benefit over an ordinary checked exception
  and only confuses users. Bloch's word for when to do this: never.

Handle: your throwables subclass `RuntimeException` or `Exception` — nothing else. `Error` belongs to the JVM.

</details>

### Why not read an exception's message text?
<details><summary>Show answer</summary>

To pull extra detail out of a failure, call **accessor methods** on the exception — not parse its string form.
A gift-card charge that fails for insufficient funds should expose the shortfall amount as a method, so the caller
can read it directly.

Why not the string: throwable classes rarely specify their string format, so it differs between implementations
and releases. Code that parses `toString()`/`getMessage()` to extract data is non-portable and breaks on any
change to the message. The string is for humans; methods are for callers.

Handle: put recovery data behind **accessor methods**, because the string representation is unspecified and
fragile — never a data source.

</details>

### How do you eliminate a checked exception?
<details><summary>Show answer</summary>

Two refactorings turn a checked exception into an unchecked API:

- **Return `Optional`.** Instead of throwing on failure, return an empty `Optional`. Cost: it carries no detail
  about *why* it failed — an exception can carry a type and accessor methods, an empty `Optional` can't.
- **Split into a state-testing method + unchecked call.** Replace `throws` with a `boolean` tester the caller
  checks first: `if (obj.actionPermitted(args)) obj.action(args);`. See
  [where to put the check](#state-testing--where-to-put-the-check). Same caveats as any state-testing method: it's
  wrong if another thread (or the call itself) can change the state between the test and the call, and ruled out
  on performance grounds if the test duplicates the action's work.

Handle: drop a checked exception by returning `Optional` (loses the reason) or splitting off a state-testing
method (fails under concurrent state change).

</details>
