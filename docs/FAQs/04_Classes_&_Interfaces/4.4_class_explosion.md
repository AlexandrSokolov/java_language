## Classes and Interfaces - Avoiding Class Explosion

### What causes subclassing to explode?
<details><summary>Show answer</summary>

Putting a **free-combining feature** onto a tree that sorts objects along a **single axis**. 
A hierarchy categorizes by one trait; 
a feature that mixes freely with every branch forces a subclass for every combination, 
so the count **multiplies**, not adds. 
The feature is one of two kinds:

- [→ explosion on varying state](#how-does-subclassing-explode-on-varying-state)
- [→ explosion on varying behavior](#how-does-subclassing-explode-on-varying-behavior)

</details>

### How does subclassing explode on varying state?
<details><summary>Show answer</summary>

The free-combining feature is **state** — a value every type can carry. Modeled as subtypes instead of held on the
type, each new value multiplies the leaves: a class per combination, the product not the sum.

Drinks group by kind: `Espresso`, `Tea`, `HotChocolate`. Add size (small / medium / large) — it applies to every kind:

```java
class SmallEspresso  extends Espresso { }
class MediumEspresso extends Espresso { }
class SmallTea       extends Tea { }
// … kind × size; each new size adds a class to every branch
```

Size has nothing to do with kind, yet subclassing fuses them. Add temperature (hot / iced) and it becomes
kind × size × temp.

</details>

### How do you fix state explosion?
<details><summary>Show answer</summary>

Take the feature off the tree and hold it on the object (composition) — the tree keeps the **one** grouping you
truly subtype on. Which tool depends on what the feature does:

- **Passive data** — stored and read, no behavior (size, a flag) → a
  [plain field](#when-should-a-new-concern-be-modeled-as-a-plain-field).
- **Participates, one choice at a time** — a complete, swappable algorithm for a single job (sync vs queued) → a
  [strategy field](#when-is-strategy-the-right-tool).
- **Participates and stacks** — acts and layers in open combinations (coffee add-ons) → a
  [decorator](#when-is-decorator-the-right-tool).

</details>

### When should a new concern be modeled as a plain field?
<details><summary>Show answer</summary>

When it's **passive data** — a value you store and read, with no behavior. Held on the type as a field, it
[stops the tree exploding](#how-do-you-fix-state-explosion): the value combines freely without a subclass per 
combination. The markers:

- **Data, not behavior** — recording the value is all you need; it doesn't change how methods compute.
- **Combines freely** — every instance can carry it, so it belongs on the type, not a subtree.
- **Doesn't stack** — one value, not a layered pile in arbitrary order.
- **You own the class** — you can add the field where it belongs.

```java
class Coffee {
  Size    size;   // S / M / L — one value, pure data
  boolean decaf;  // a flag, no behavior
}
```

The default — reach for a field first.

</details>

### Why isn't a plain field always enough?
<details><summary>Show answer</summary>

A field can only **record** a value — it can't **act**. It holds while the concern is passive data. 
Once the value starts to *compute*, *swap*, or *stack*, it stops being state and becomes **behavior** — 
and behavior that varies freely is the same multiplication problem, now fixed with objects held as parts, not a field.

So the state question hands off here: passive data was the last true state case; anything past it is
[behavior explosion](#how-does-subclassing-explode-on-varying-behavior).

</details>

### How does subclassing explode on varying behavior?
<details><summary>Show answer</summary>

Same multiplication as state, but the free concern is a **behavior**: when any implementation can pair with any type,
subtyping gives a class per combination — the product. Pull the behavior off the tree and hold it as a part — two shapes:

- **One choice at a time**, swapped per instance → a [strategy](#when-is-strategy-the-right-tool).
- **Many layering** in open combinations → a [decorator](#when-is-decorator-the-right-tool).

</details>

### When is strategy the right tool?
<details><summary>Show answer</summary>

When an object needs **one pluggable behavior** — a single job delegated to a swappable component, not baked into the
class. The markers:

- **One active slot** — holds exactly one implementation at a time ("how it sends", "how it sorts").
- **Chosen at runtime** — assigned at creation or swapped while it lives; a subtype can't.
- **Behavior, not data** — holds the actual algorithm, replacing `if`/`else` flag checks with pure delegation.
- **Independent variation** — mixes freely with any type on the tree without multiplying subclasses (kind × strategy).

```java
interface SendStrategy { void send(Message m); }

class Notification {
  private SendStrategy sender;                    // held as a part
  void setSender(SendStrategy s) { sender = s; }  // swapped at runtime
  void notify(Message m) { sender.send(m); }      // delegate, no branching
}
```

One line: **one job, swappable choices, chosen per instance.** If features instead stack and layer at once, that's a
[decorator](#strategy-or-decorator--which-fits).

</details>

### When is decorator the right tool?
<details><summary>Show answer</summary>

When behavior needs to **act and stack** — layering additions over a base object rather than replacing its core
algorithm. The markers:

- **Same interface** — the wrapper implements the same interface as what it wraps, staying transparent to the client.
- **Delegates and adds** — intercepts the call, applies its own bit, delegates the rest to the inner object.
- **Open-ended stacking** — sharing the interface, wrappers nest indefinitely in any combination.
- **Preserves encapsulation** — depends only on the public contract, sidestepping fragile-base-class issues.

```java
interface Coffee { double cost(); }

abstract class Addon implements Coffee {
  protected final Coffee inner;
  protected Addon(Coffee inner) { this.inner = inner; }
}

class Milk extends Addon {
  Milk(Coffee inner) { super(inner); }
  public double cost() { return inner.cost() + 0.5; }  // adds its bit, delegates the rest
}

Coffee c = new Caramel(new Milk(new Espresso()));  // layered, zero combination classes
```

The shape in brief: wrap a base to stack layered behaviors. If you only need one swappable choice at a time, that's a
[strategy](#strategy-or-decorator--which-fits).

</details>

### What are the downsides of a decorator?
<details><summary>Show answer</summary>

- **Many small wrapper objects** — one per layer.
- **Lost identity** — `==`/`instanceof` see the wrapper, not the core object.
- **Harder debugging** — calls step through delegation layers.
- **Order-sensitive** — wrappers must be applied in the right order.
- **Interface-bound** — no access to inner methods the shared interface doesn't expose.

</details>

### Strategy or decorator — which fits?
<details><summary>Show answer</summary>

Both pull varying behavior off the tree via composition, but solve different problems: **swap one** vs **stack many**.

- **Strategy (swap)** — one active slot for a single job ("how to send"); you pick one implementation at a time and
  replace it wholesale.
- **Decorator (stack)** — open-ended layering; each add-on wraps the base, accumulating features in any order.

The deciding questions:

- **Replace or accumulate?** One alternative from a list → strategy. Combining multiple features → decorator.
- **Does it nest?** Layers share the base interface and wrap each other indefinitely → decorator. Strategies don't
  wrap each other.

```java
notification.setSender(new EmailSender());         // strategy: one choice, swapped wholesale
Coffee c = new Caramel(new Milk(new Espresso()));  // decorator: open-ended layers stacked
```

In short: strategy swaps an algorithm; decorator stacks features.

</details>
