## Classes and Interfaces - Inheritance

### What is inheritance, and what benefits does it provide?
<details><summary>Show answer</summary>

**Inheritance** lets a class (subclass) reuse and extend the behavior of another (superclass).

**Benefits:**

- **Code reuse** — common behavior defined once in the base class, reused by subclasses; 
  less duplication, easier maintenance.
- **Abstraction & hierarchy modeling** — expresses *is-a* relationships; 
  this is about how you **structure** your types.
- **Polymorphism** — follows *from* that hierarchy: it's what you can do **at runtime** because of the
  structure — treating related objects uniformly through a common supertype.

The last two are a pair: hierarchy is the compile-time structure, polymorphism is the runtime payoff it enables.

</details>

### What is polymorphism?
<details><summary>Show answer</summary>

**Polymorphism** ("many forms") — the ability of a language to bind one name to multiple types or behaviors.

It allows:
- a value or variable to have more than one type, and
- an operation to apply to values of more than one type.

Either side can vary:
- the data (one variable, several possible types)
  ```java
  List<String> list = new ArrayList<>(); // declared List, actually an ArrayList
  CharSequence cs = "hello";             // declared CharSequence, actually a String
  ```
- the operation (one operation, many types it accepts)
  ```java
  void print(int i)    { ... }
  void print(String s) { ... } // same name "print", different argument types
  ```

</details>

### What forms of polymorphism exist?
<details><summary>Show answer</summary>

Each takes one name across many types — the difference is whether the **dispatched behavior** is the same for all
or chosen per type:

- **Parametric** — same name, different types, **one shared body** (type not named); generics, `List<T>`; 
  resolved at **compile time**.
- **Subtype (inclusion)** — same name, different subtypes, **dispatch picks each subclass's own body**; 
  caller still treats them uniformly; also known as inheritance; resolved at **runtime**.
- **Ad-hoc overloading** — same name, different parameter types, **a separate body per type**; 
  resolved at **compile time**.

</details>

### How do inheritance and polymorphism relate?
<details><summary>Show answer</summary>

Inheritance provides **subtype polymorphism** specifically — the *runtime* kind. 
A subclass instance can be used wherever its supertype is expected, and a call to an overridden method runs the
**subclass's** implementation, chosen by the object's actual runtime type:

```java
Shape s = new Circle();   // supertype reference, subtype object
s.draw();                 // runs Circle.draw(), not Shape.draw()
```

**Mechanism — dynamic dispatch:** overridable methods live in a per-class virtual table; 
the call is bound at runtime via the object's actual class.

Hierarchy is the *compile-time* structure (is-a); subtype polymorphism is the *runtime* payoff — override plus
dynamic dispatch let you treat related objects uniformly through a common supertype.

</details>

### When should you inherit — and when not?
<details><summary>Show answer</summary>

- [**True is-a relationship**](#how-do-you-know-its-a-real-is-a-relationship) —
  the subtype really *is* a kind of the base, not just shared code.

  *Fails when:* you use `extends` only to reuse code — that's has-a. But a passing test isn't enough on its own:
  [inheritance can still be the wrong call](#why-does-inheritance-fail-even-when-is-a-seems-obvious).

- [**Substitutability (LSP)**](#how-does-a-subtype-violate-substitutability-lsp) — 
  a subclass stands in for the base everywhere.

  *Fails when:* a subclass changes base behavior, or callers must downcast to reach behavior the base doesn't expose.
  **Classic warning sign:** *"this class extends another just to override half of its behavior."*

- **Stability (Designed for Extension)**: the base is designed and documented for extension.

  *Violation:* [fragile base class](#what-are-the-typical-traps-of-incorrectly-choosing-inheritance) — you depend on
  undocumented internals, so a change inside the base breaks you.

- [**Designed polymorphism**](#how-do-inheritance-and-polymorphism-relate) — 
  using subtypes through the supertype is a deliberate goal.

  *Fails when:* you reach for `extends` with no intent to use the objects through the supertype.

</details>

### How do you know it's a real is-a relationship?
<details><summary>Show answer</summary>

Test it by **substitution, not by shared fields**: the subtype is a real is-a only if it can stand in for the parent
*everywhere the parent is used*, through a parent reference, without callers noticing or breaking. If code must know
the concrete subtype to use it correctly, it isn't a true is-a — it's reuse wearing an is-a costume.

</details>

### What are the typical traps of incorrectly choosing inheritance?
<details><summary>Show answer</summary>

The substitution test tells you the type fits — not that inheritance is the right tool. Even when an is-a looks
plausible, it fails in one of three ways:

1. **The "Shared Code" trap (false is-a).** You use inheritance strictly to reuse utility code. Inheriting drags in
   an unwanted public API that breaks your own invariants
   ([`Properties` extending `Hashtable`](#a-jdk-class-where-inheritance-violated-the-subclasss-own-invariants)).
   *Fix:* [composition](#what-class-relationships-replace-implementation-inheritance) (has-a).
2. **Fragile base class trap (true is-a).** The relationship is genuine and substitutable, but the base
   [isn't designed for extension](#when-is-it-safe-to-subclass-a-class-and-when-does-subclassing-introduce-significant-risk):
   it couples you to its [internal self-use](#what-is-the-relationship-between-inheritance-and-encapsulation), so a
   base change breaks you though your code never changed. *Fix:* composition (wrapper) — depend only on the public
   contract, which buys immunity from internal changes.
3. **Class explosion/Free Combination trap (real is-a, wrong tool).** You use the inheritance tree to mix freely 
   varying state or behavior, so every combination needs its own subclass, and the number of classes multiplies into
   [class explosion](4.4_composition.md#what-causes-subclassing-to-explode).
   *Fix:* [decorator](4.4_composition.md#when-is-decorator-the-right-tool) (layering behavior via composition).

Handle: the is-a test is necessary, not sufficient — ask **what you actually wanted**: 
If you just want the code, use composition. If you want to mix features, use composition.
Only use inheritance if you need the polymorphic type and the base class is built to support it.

</details>


### If composition is preferable, why not avoid inheritance entirely?
<details><summary>Show answer</summary>

Because "prefer composition" is a *default*, not an absolute — and inheritance retains genuine
advantages composition can't replicate cleanly. The guidance is narrower than it sounds: it warns
against **implementation inheritance across a boundary you don't control**, not against all inheritance.

Where inheritance is still the right tool:

- **A genuine, stable is-a relationship.** When the subtype truly *is* the supertype and substitutes
  for it everywhere (LSP holds), inheritance models it directly. Forcing composition here adds
  indirection to express a relationship the language already has a keyword for.
- **Polymorphism is the goal.** If the point is to treat many subtypes uniformly through a supertype
  reference, inheritance (or interface implementation) is the mechanism that provides it. Composition
  doesn't give you subtype substitutability.
- **Designed and documented for extension.** When the superclass author has opened the class for it —
  self-use documented, hooks provided — the coupling is part of the contract, so the main objection
  (depending on undocumented internals) goes away.
- **Less boilerplate for true specialization.** Composition requires forwarding every delegated method;
  for a real subtype that extends a stable base, inheritance avoids that forwarding cost.

What composition buys that inheritance can't — and why it's the *default*:

- It avoids the encapsulation-weakening coupling entirely (you depend only on a public contract).
- It composes along **multiple independent axes** without combinatorial class explosion.
- The wrapped object can be swapped or chosen at runtime; an inherited superclass is fixed at
  compile time.

So the rule isn't "never inherit" — it's "**don't reach for inheritance by default for code reuse.**"
Use it when there's a real is-a, substitutability holds, or the class is built for extension; reach for
composition for everything else — which, in practice, is most of the time.

</details>

### How does a subtype violate substitutability (LSP)?
<details><summary>Show answer</summary>

A subtype breaks substitutability when it can't truly stand in for the base everywhere the base is expected. Two forms:

- **Altering base behavior** — the subtype must override, disable, or significantly change what the base does, so code
  written against the base behaves wrongly when handed the subtype. E.g., `Properties` extends `Hashtable`: inheriting
  drags in an unwanted public API (`put(Object, Object)`) that breaks `Properties`' own strings-only invariant.
- **Hidden behavior the base doesn't expose** — callers must downcast to a concrete subtype to reach a method the base
  doesn't declare (`((Dog) animal).bark()` where `bark` is only on `Dog`). The supertype reference can't actually be
  used on its own; callers must know the real type, which defeats the abstraction.

The downcast form usually shows up as an `instanceof` check followed by a cast — the classic sign that the supertype is
the wrong abstraction (incomplete, or chosen only for reuse). You're manually re-dispatching on the concrete type, which
is exactly what polymorphism was meant to remove. The fix is normally to put the behavior on the supertype (so it
dispatches polymorphically) or to admit the subtype isn't really substitutable for that base.

</details>

### When is it safe to subclass a class, and when does subclassing introduce significant risk?
<details><summary>Show answer</summary>

**Safe:**
- **Package-private superclass** — *structurally* safe: 
  it can't be subclassed from outside the package at all (compiler-enforced), so no external subclass can ever exist.
- **Designed for inheritance** — the superclass is explicitly documented and structured to be extended safely 
  (self-use documented, hooks provided).

**Dangerous:**
- **Across package boundaries, on an ordinary concrete class** — such a class was *not* designed for subclassing. 

</details>

### What is the main problem of using inheritance?
<details><summary>Show answer</summary>

Inheritance [**weakens encapsulation**](#what-is-the-relationship-between-inheritance-and-encapsulation). 
A subclass depends on the *implementation details* of its superclass, not just its public contract.

</details>

### What is the relationship between inheritance and encapsulation?
<details><summary>Show answer</summary>

**Inheritance weakens encapsulation.** A subclass depends not just on the base's public contract but on its
*internal implementation* — most often the superclass's **self-use**: which overridable methods the base calls, and when.
That self-use isn't part of the public API, yet a subclass that overrides those methods is silently coupled to it.


The consequence: a change to the superclass's internal implementation can break a subclass **even
though the subclass's code is unchanged and the superclass's public API is unchanged**. The coupling is
strong but *implicit*


So inheritance is safe only when the base is **designed and documented for extension** — self-use spelled out,
overridable methods and their guarantees made part of the contract — and its dependents can absorb its changes.

</details>

### A JDK class where inheritance violated the subclass's own invariants?
<details><summary>Show answer</summary>

`java.util.Properties extends Hashtable` — a classic mistake.

The root error: a `Properties` object isn't a general hashtable, it *has* one — so the is-a was false;
it should have been composition. Because it inherited instead:

- **Leaked, conflicting methods** — inherited `get(key)` behaves differently from `Properties`'
  own `getProperty(key)`, giving two confusingly different access paths.
- **Broken invariants** — `Properties` is meant to hold only string keys and values, but inherited
  `Hashtable` methods (`put(Object, Object)`) let clients insert arbitrary objects, violating that
  guarantee.

And once clients depended on the inherited behavior, the flaw was frozen — unfixable without breaking
backward compatibility. Composition (`Properties` *holds* a map, exposes only string operations) would
have avoided all of it.

</details>

### What class relationships replace implementation inheritance?
<details><summary>Show answer</summary>

Instead of *being* the other class (is-a), your class **has** one and delegates to it.
In practice "composition" often just means has-a — the owned-vs-borrowed line below is frequently ignored.
The two kinds, split by who owns the part's lifecycle:

- [**Composition**](#what-is-composition) (Strict Ownership): The new class creates and entirely manages the lifecycle
  of the reused component. If the container is destroyed, the component is destroyed with it.
- [**Aggregation**](#what-is-aggregation) (Independent Lifecycle): The new class receives an existing instance of the
  component from the outside (e.g., passed through a constructor). The component can outlive the container.

</details>

### What is composition?
<details><summary>Show answer</summary>

Your class **creates** the part itself and owns it — the part exists only inside the whole. Destroy the whole and the
part goes with it.

```java
class Car {
  private final Engine engine = new Engine();  // created inside — owned
}
```

Handle: owned part, shared with no one, dies with the whole.

</details>

### What is aggregation?
<details><summary>Show answer</summary>

Your class **receives** an already-built part from outside, usually a constructor parameter. It uses the part but
doesn't own it — the part can be shared and outlives the whole.

```java
class Playlist {
  private final List<Song> songs;
  Playlist(List<Song> songs) { this.songs = songs; }  // passed in — borrowed, not owned
}
```

Handle: borrowed part, may be shared, outlives the whole.

</details>


### What are the forms of inheritance?
<details><summary>Show answer</summary>

Two kinds:

- **Implementation inheritance** — a class extends another class and inherits its *implementation and
  behavior* (`extends`).
- **Interface inheritance** — a class implements an interface, or an interface extends another;
  *only the method contracts* are inherited, no implementation.

Why the distinction matters: the encapsulation-weakening problem is almost entirely a property of **implementation** 
inheritance — there's an implementation to depend on, so the subclass can couple to internals. 
**Interface** inheritance carries no implementation, so there's nothing internal to couple to — 
which is a large part of why interfaces are the safer extension mechanism.

</details>

### What are the consequences of extending a class by adding new methods while leaving existing methods unchanged?
<details><summary>Show answer</summary>

Even purely *additive* subclassing — only adding new methods, never overriding — is not risk-free. 
The danger comes from a **future change to the superclass** that retroactively collides with your added
method, breaking code that was correct when written:

- **Superclass later adds a method with the same signature but a different return type** — your
  subclass no longer compiles (signature conflict).
- **Superclass later adds a method with the same signature and return type** — your method silently
  *overrides* it, and almost certainly fails to honor the new method's contract — a contract that
  didn't exist when you wrote the method.

The deeper point: you can be broken by a change you didn't make and couldn't have anticipated. 
Adding methods feels safe but still couples you to the superclass's *future* evolution.

</details>

### How do you allow inheritance but keep control?
<details><summary>Show answer</summary>

The default choice is all-or-nothing: `final` blocks every subclass, a plain class allows unlimited unknown ones.
A [sealed class](#what-is-a-sealed-class) is the middle — you name the exact subtypes allowed with `permits`, 
so the supertype stays public but the implementation list is fixed to the ones you chose.

Handle: sealed trades "anyone or no one" for "exactly these."

</details>

### What is a sealed class?
<details><summary>Show answer</summary>

A class or interface that names exactly which types may extend it, using `permits`. Every permitted subtype must
itself say how it continues the hierarchy — `final` (closes it), `sealed` (restricts again), or `non-sealed`
(reopens it).

```java
public sealed interface Result permits Success, Failure {}
public record Success(Object value) implements Result {}
public record Failure(Throwable cause) implements Result {}
```

Handle: `final` forbids all inheritance, a plain class allows unlimited inheritance, `sealed` allows a fixed,
hand-picked set.

</details>

### Why choose sealed over final or open?
<details><summary>Show answer</summary>

Before sealed, controlling a hierarchy was all-or-nothing: leave it open and anyone can extend it (no behavioral
guarantee possible), or mark it `final` and nobody can — killing variants and internal polymorphism. Package-private
constructors were the only middle ground, and they leak across the package.

[Sealed](#what-is-a-sealed-class) is the missing middle: a supertype public to the world, an implementation list
locked to the ones you named. Two payoffs:

- **Closed domain models.** A type with a fixed, known set of variants (`Result` = `Success` | `Failure`). The set
  is part of the contract, not an accident.
- **Contract safety.** No outside code can inject a subtype that breaks your invariants — 
  without forcing you to use `final` or rely on package-private constructors.

Handle: `final` forbids inheritance; standard classes allow infinite inheritance; 
`sealed` allows explicitly curated inheritance.

</details>

### How does a closed type list help the caller?
<details><summary>Show answer</summary>

When a [sealed type](#what-is-a-sealed-class) names all its subtypes, the compiler knows the list is complete. So a
`switch` that handles every one of them is *exhaustive* — you write no `default` branch, because the compiler has
proven no other type can reach it.

```java
sealed interface Result permits Success, Failure {}

String describe(Result r) {
  return switch (r) {
    case Success s -> "ok";
    case Failure f -> "failed";
    // no default — compiler knows these are the only two
  };
}
```

The payoff is at change time: add `Pending` to the `permits` list and every `switch` missing that case fails to
compile. The compiler hands you the list of places to fix instead of letting a wrong `default` swallow the new case
at runtime.

Handle: a closed subtype list turns "did I handle them all?" from a runtime guess into a compile-time guarantee.

</details>
