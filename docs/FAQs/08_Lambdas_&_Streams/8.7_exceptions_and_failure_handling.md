## Lambdas and Streams - Exceptions and Failure Handling

### Lambda throws — what happens?
<details><summary>Show answer</summary>

**Unchecked exception:** it propagates out of the terminal operation and up through your method as normal. The
pipeline stops where it stood; already-produced side effects stay. Nothing special about streams here.

**Checked exception:** it does not compile. `Function`, `Predicate`, `Consumer` and friends declare no `throws`
clause, so a lambda body cannot throw a checked exception at all — even if the enclosing method declares it. The
compiler rejects the lambda, not the pipeline.

The fix is a **wrapper** that adapts a throwing lambda into the normal functional interface — catch inside, rethrow
unchecked:

```java
@FunctionalInterface
interface ThrowingFunction<T, R> { R apply(T t) throws Exception; }

static <T, R> Function<T, R> unchecked(ThrowingFunction<T, R> f) {
  return t -> {
    try { return f.apply(t); }
    catch (Exception e) { throw new RuntimeException(e); }
  };
}

paths.stream()
     .map(unchecked(Files::readString))   // Files::readString throws IOException; now compiles
     .forEach(System.out::println);
```

This drops the checked restriction so streams work — which is the goal, not a compromise. 

The wrapper rethrows, so the pipeline still aborts on the first failure. When you need it to keep going instead, the
failure has to become a value: see [How to make a failure a value?](#how-to-make-a-failure-a-value).

</details>

### How to make a failure a value?
<details><summary>Show answer</summary>

A stream has no error channel. Any exception escaping a lambda aborts the terminal operation, so the failure has to
travel *inside the element* instead of being thrown — a wrapper that holds either the value or the error. The lambda
then never throws, the terminal always completes, and success and failure come out side by side as data.

Once the failure is a value you can count it, report it, retry it, or fail the batch over it — none of which a throw
allows, because a throw ends the run.

The working type, its `map` for chaining steps, and the caller-context design are in
[Result_Error_Collecting.md](Result_Error_Collecting.md) — copy-paste ready.

See [Collecting failures instead of aborting?](#collecting-failures-instead-of-aborting) for the batch-level payoff.

</details>

### Collecting failures instead of aborting?
<details><summary>Show answer</summary>

With the failure carried as a value (not a throw), every element runs to the end regardless of what broke. Partition
the results once — successes on one side, failures on the other — and you have processed everything processable *and*
kept every failure, instead of stopping at whichever element failed first.

The failure value carries the caller's context, so each one names what it was doing, not just which input broke —
turning "an exception somewhere" into a report you can act on.

Rests on the failure-as-value idea: [How to make a failure a value?](#how-to-make-a-failure-a-value). Full working
example — the pipeline, the partition, the failure report — in
[Result_Error_Collecting.md](Result_Error_Collecting.md).

</details>
