## Lambdas and Streams - Side effects

### What is a side effect?
<details><summary>Show answer</summary>

A function has a **side effect** when it changes something outside itself — state that some later caller, or another
thread, could notice. The function does more than return a value; it leaves a mark on the world.

Concrete: writing a field or a `static`, adding to a list someone else holds, mutating an argument, writing a file,
sending to a queue, saving to a DB. After the call, something is different that was not different before.

Not a side effect: reading. `Integer.parseInt(s)` reads its argument and returns. `config.getTimeout()` reads a
field. A read — however far it travels, even to a network — changes nothing, so it is not a side effect.

The test: **after the call, is anything different in the world?** If yes, side effect. If no, none.

</details>

### What does side effect mean and what not?
<details><summary>Show answer</summary>

A pure function has two separate guarantees, and each is broken by a different thing:

- **Same input, same output** — the return value depends only on the arguments. Broken by a **side cause**.
- **No side effect** — it changes nothing outside itself. Broken by a **side effect**.

The two terms name opposite directions:

- **Side cause** — a hidden *input*. The function **reads** outside state it was not given: a DB row, the clock,
  config, a global. The outside world can change between calls, so the same argument can give two answers. This
  breaks the first guarantee, not the second.
- **Side effect** — a hidden *output*. The function **writes** outside state: saves to a DB, updates a global,
  prints. This changes the world. It breaks the second guarantee.

**Reading from an external system that changes the result on top of the input data is NOT a side effect — it is a
side cause.** A side effect is only a write.

Why the confusion exists: the two guarantees must cut on two different axes, or one would be redundant. If reading
counted as a side effect, "no side effect" would already cover "same input, same output," and the first guarantee
would mean nothing. It doesn't — so reads and writes are two different things.

The trap: purely functional languages (Haskell) send both reads and writes through the same `IO` machinery, so
they loosely call **all** outside interaction a "side effect." Some Java book authors copy that loose usage and get
it wrong. In a two-guarantee model, keep them apart: read = side cause, write = side effect.

</details>

### What is a pure function?
<details><summary>Show answer</summary>

A **pure function's** output depends **only on its input**. Same argument, same answer, forever. 
`Integer.parseInt`, `String::trim`, `Math::sqrt`.

Two separate things break purity, and a function can have either alone:

- **It writes state outside itself** — [a side effect](#what-is-a-side-effect). `list::add`.
- **It reads state it was not given** — an external dependency. `userService.findAddress(id)`: the DB row can change
  between calls, so the same `id` can give two answers.

</details>

### Does throwing break purity?
<details><summary>Show answer</summary>

Yes.

- **A throw is not an output.** Pure means the output depends only on the input and is always the same for the
  same input. `parseInt("x")` gives no output; it throws. The caller is forced to catch it, or the first bad input
  stops the whole run.
- **It breaks referential transparency.** A pure call can always be replaced by its result. A throwing call has no
  result to put in its place.

</details>

### What kinds of order are in a stream?
<details><summary>Show answer</summary>

- **Source order** — the order the source produces elements in. Can be encounter (ordered) or unordered.
- **Execution order** — when the `map`/`filter` lambdas fire, on which thread. 
  - For parallel streams always undefined.
  - For sequential streams always matches the source order
- **Result order** — what the terminal op returns. Always matches source order — except `forEach`, which always
  matches execution order.

</details>

### What does a stream guarantee?
<details><summary>Show answer</summary>

Promised:
- each element goes through the stages in the order you wrote them — `map` runs before `filter`, always
- the terminal gives the result back in [source order](#what-kinds-of-order-are-in-a-stream) — sequential or
  parallel — except `forEach`, which gives it back in execution order

Free — not promised:
- [execution order](#what-kinds-of-order-are-in-a-stream) — when each lambda runs, and on which thread
- how many elements the terminal pulls through — `findFirst` or `limit` stop early, so only some elements go through;
  `count()` can pull none, taking the size from the source directly. A skipped element runs no stage at all — 
  the promise that stages run in written order still holds, it just never fires for that element

</details>

### What should a stream stage not do?
<details><summary>Show answer</summary>

A stage's lambda must be **stateless** if you need the same result every run — sequential or parallel. A stateful
lambda — one whose result depends on state that can change during the run — often works on a sequential stream, but
its result depends on order and threads, so it breaks [what the stream promises](#what-does-a-stream-guarantee) the
moment it runs in parallel.

</details>

### What is a stateful lambda?
<details><summary>Show answer</summary>

From the [stream docs](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/stream/package-summary.html#Statelessness):
a stateful lambda is one whose *result depends on any state which might change during the execution of the stream
pipeline*. The key word is *result*: the rule is about what the result depends on, not about what the lambda does.

People usually get this wrong in three places.

**Who changes it does not matter.** The pipeline itself or some other thread: either way the result can differ from
run to run. Limiting the rule to "state the pipeline changes" leaves a hole.
```java
stream.map(w -> idx.getAndIncrement())              // stateful: the pipeline moves idx on every call
stream.filter(w -> w.size() < settings.maxAllowed)  // stateful: another thread may set the field mid-run
```

**The snapshot fix.** It does not matter whether the state actually changes during this run. Only a value that
cannot change is safe. Copy the field into a local primitive before the stream starts, so the lambda depends on
that copy and not on the shared field.
```java
int limit = settings.maxAllowed;                    // copied once; the lambda sees a value that cannot change
stream.filter(w -> w.size() < limit)                // not stateful
```

**A side effect is not statefulness.** Writing is not the test. A lambda can change outside state and still be
stateless, as long as that change does not flow back into its result.
```java
stream.map(w -> { calls.incrementAndGet(); return w.length(); })  // not stateful: bumps a counter, result ignores it
```

</details>

### Side effect vs statefulness?
<details><summary>Show answer</summary>

Both bump a shared counter; only one is stateful:
```java
stream.map(w -> idx.getAndIncrement())                            // stateful: returns the counter
stream.map(w -> { calls.incrementAndGet(); return w.length(); })  // not stateful: result depends only on w
```

Both at once:
```java
stream.map(img -> uploader.send(img))   // side effect: sends the image; stateful: result depends on the network
```

- [side effect](#what-is-a-side-effect) is what the lambda changes; 
- [stateful](#what-is-a-stateful-lambda) is what its result depends on. One does not imply the other.

</details>

### May a stage have a side effect?
<details><summary>Show answer</summary>

Yes, unless it changes the stream's [source](8.9_parallel_streams_2.md#what-happens-if-a-lambda-modifies-the-streams-source), 
though the stream docs discourage it. 
A side effect is [not the same as stateful](#side-effect-vs-statefulness): a stage can change the world while
its result depends only on its input.

```java
users.stream()
     .map(u -> {
       auditLog.record(u);   // side effect: writes outside the stream
       return u.getId();     // not stateful: result depends only on u
     })
     .toList();
```

What you lose:
- **Safe reruns** (any side effect, stream or loop): a pure pipeline can be stopped and run again with nothing broken. 
  Here, a crash halfway and a retry write the first users to the log twice.
- **Control over when and where it runs** (what streams add): the call happens only when a later step asks for the
  element. Add `findFirst()` and it runs for fewer users; `count()` may skip it entirely (Java 9+). In parallel it
  also runs in any order, on any thread, so it must be thread-safe.

Fine when an extra or missing write does not hurt: debug logs, rough metrics. 
When it must happen once per element, move it to the terminal `forEach` or a loop. 
That fixes the second loss, not the first: 
reruns still repeat the write unless the write is safe to repeat (**idempotent**).

</details>

### May a stage call a service?
<details><summary>Show answer</summary>

A read is not a [side effect](#what-is-a-side-effect): the stage asks a question, returns the answer, and
changes nothing. It is a [side cause](#what-does-side-effect-mean-and-what-not).

```java
users.stream()
     .map(userService::findAddress)             // reads the DB
     .map(deliveryService::deliveryCompany)     // reads a REST API
     .filter(deliveryService::isAvailable)
     .toList();
```

**But it makes the lambda [stateful](#what-is-a-stateful-lambda):** the answer comes from data that can change mid-run. 

If per-call answers are fine, leave it. If every element must see the same data, read it once before the stream:

```java
Set<Company> available = deliveryService.availableCompanies();  // one read, before the run
// ...same pipeline, with:
     .filter(available::contains)
```

</details>

### What belongs in forEach?
<details><summary>Show answer</summary>

**Only consuming the final result** (e.g., printing, logging, or sending to an API). Never computation.

If your `forEach` block updates variables or builds a collection, the pipeline is just decoration. 
You are writing a for loop with extra syntax, sacrificing both readability and parallel safety.

</details>
