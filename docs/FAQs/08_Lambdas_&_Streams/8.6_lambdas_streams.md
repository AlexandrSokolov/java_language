## Lambdas and Streams - Parallel Streams

### What governs whether parallel() helps?
<details><summary>Show answer</summary>

Five things must hold, and the sixth decides.

1. [**The source splits cheaply**](#how-does-source-type-affect-parallel-streams) — a chain source cannot be cut, so
   one thread does all the work.
2. [**The lambdas are legal**](#which-lambda-rules-break-under-parallel) — stateful or interfering ones give a wrong
   answer, and sequential runs hide it.
3. [**The terminal op merges cheaply**](#which-terminal-ops-suit-parallelism) — a finish that cannot be split caps
   the whole pipeline.
4. [**Order is not needed**](#does-parallel-preserve-element-order) — asking for encounter order back puts the
   sequence back too.
5. [**The pool is not a problem**](#how-do-parallel-streams-share-threads) — one shared pool for the whole program,
   so blocking work starves everyone else.
6. [**It measures faster**](#parallel--when-do-you-add-it) — the only thing that actually answers the question.

Spine: it has to split, the lambdas have to be legal, the finish has to merge, order has to be affordable, the
threads are shared — and then you measure.

</details>

### How does source type affect parallel streams?
<details><summary>Show answer</summary>

Splitting is cheap when the source has known size and a structure that can be cut without walking it:

- arrays, `ArrayList`, `IntStream.range` — random access by index, so the splitterator hands out index ranges
  instantly.
- `HashMap`, `HashSet` — no index, but the splitterator cuts the internal bucket table into ranges of buckets.

It fails when the source is a **chain** — element N is produced from element N-1, so reaching N means walking 1..N-1.
No cut point exists.

</details>

### Which sources split badly in parallel?
<details><summary>Show answer</summary>

A chain source: element N is produced from element N-1, so reaching N means walking 1..N-1. No cut point exists.

- `Stream.iterate(seed, f)` — each element is `f` applied to the one before, so #500000 can't be produced without
  first producing all 499999 ahead of it.

    ```java
    Stream.iterate(BigInteger.ONE, n -> n.multiply(TWO))  // #3 needs #2, #2 needs #1
          .parallel()                                     // no thread can start at #500000
          .limit(500_000)
          .forEach(System.out::println);                  // one thread does all the producing
    ```
- `BufferedReader.lines()` — reads forward through the file; size is unknown and you can't jump to line N without
  reading every line before it.
- `Iterator`-based streams — the only operation is "give me the next one"; there's no size and no random access to
  hand a chunk to another thread.

    ```java
    Iterable<Order> orders = repository.streamAll();      // Iterator only: hasNext() / next()
    StreamSupport.stream(orders.spliterator(), true)      // true = parallel
                 .forEach(this::handle);                  // spliterator has no size, no index
                                                          // it can only buffer next() results in batches
    ```

- Cursor-paginated APIs — page N's request needs the cursor returned by page N-1, so pages can only be fetched one
  after another.

</details>

### Which random source for parallel streams?
<details><summary>Show answer</summary>

`SplittableRandom` — built for this: it splits into independent generators, one per thread, so the source parallelizes
cleanly and can scale near-linearly.

The other two, worst-last:
- `ThreadLocalRandom` — made for a single thread; used as a parallel source it works but won't match
  `SplittableRandom`.
- `Random` — synchronizes on every call, so all threads contend on one lock and the parallelism collapses. (Fine
  single-threaded; only bad as a parallel source.)

Handle: can the generator be *split* or only *shared*? Splittable → scales. Shared behind a lock → contention.

</details>

### What kinds of order are in a parallel stream?
<details><summary>Show answer</summary>

Different orders live in a parallel stream and they behave differently — telling them apart is the whole point:

- **Source order** — the order the source produces elements in. Can be encounter (ordered) or unordered.
- **Execution order** — when the `map`/`filter` lambdas fire, on which thread. Always undefined.
- **Result order** — what the terminal op returns. Matches source order, except `forEach`, which emits in
  execution order.

Spine trigger:
- an unordered source keeps nothing
- on an ordered source:
    - execution order is still undefined and
    - result order matches the source order — except `forEach`

</details>

### How can a source's order be classified?
<details><summary>Show answer</summary>

Every source produces elements in some order. It can be:

**Ordered (encounter order)** — set by the spliterator's `ORDERED` flag — the source promises an order, 
so order-sensitive ops (`findFirst`, `limit`, `skip`) honor it:
- `List`, arrays, `IntStream.range` — order is the index.
- `LinkedHashSet`, `LinkedHashMap` — order is insertion order.
- `TreeSet`, `TreeMap` — order is the sort order.

**Unordered** — the source makes no promise, so order-sensitive ops have nothing to keep:
- `HashSet`, `HashMap` keys — see [Is a HashSet ordered?](#is-a-hashset-ordered).
- `Collectors.toSet()`, and any stream after `.unordered()`.

</details>

### Is a HashSet ordered?
<details><summary>Show answer</summary>

No. A `HashSet` has an iteration order — some repeatable sequence comes out — but the spliterator does **not** report
`ORDERED`. That sequence is an accident of which bucket each hash landed in, so the stream promises nothing about it
and order-sensitive ops ignore it.

</details>

### What is the execution order under parallel?
<details><summary>Show answer</summary>

Undefined. Which thread runs which element, and when each `map`/`filter` lambda fires, is not fixed — independent of
the source. Run the same pipeline twice and the lambdas may fire in a different order each time.

</details>

### How does result order match the source order?
<details><summary>Show answer</summary>

Splitting builds a **left-to-right tree**: each split cuts the source into `left | right`, where left holds the
earlier part of the source. The leaves compute in parallel, in any time order. The terminal op then combines **back
up the tree**, and for an order-sensitive op each combine prefers the left child. That rebuilds encounter order.

Source `[10,5,6,2,3,7,4,1,9,8]`, heavy `map` + `filter`, match = value in `{2,5,7}`:

```text
                 [10,5,6,2,3,7,4,1,9,8]
                  /                    \
              LEFT                    RIGHT
        [10,5,6,2,3]              [7,4,1,9,8]
         /        \                /        \
     [10,5,6]    [2,3]         [7,4]      [1,9,8]
     match:5     match:2       match:7    none
```

- **Position is not stored on elements.** No element carries an index. "Earlier" means *sits in a left branch* —
  that fact lives in the tree shape, not on the elements.
- **Finish time is ignored.** Leaves may finish `2, 7, 5`; that order is thrown away. Each result slots into its
  fixed place in the tree.
- **`findFirst` = prefer left up the tree.** `combine([10,5,6]=5, [2,3]=2)` → **5**; `combine(LEFT=5, RIGHT=7)` →
  **5**. Result is **5** — earliest in the list (index 1), not `2` (smallest) and not `7` (finished first).
  Deterministic, identical to sequential.
- **The cost is the wait.** `findFirst` can't take the early right-side `7` until the left side finishes proving it
  has no earlier match. It waits for left instead of stopping on the first match found in time.

</details>

### Which terminal ops parallelize well?
<details><summary>Show answer</summary>

The axis: **does the terminal step split into independent chunks and merge cheaply, or does it force a sequence?**
Ops that combine without caring about left-vs-right are safe; ops that must respect left-before-right pay the wait —
see [how result order is rebuilt](#how-is-result-order-rebuilt-under-parallel).

**Safe** — the combine is order-free, so no leaf waits on another
- `reduce`, and the prepackaged `min`, `max`, `count`, `sum` — each thread reduces its chunk to one value, and the
  merge combines a few values in any order.
- `anyMatch`, `allMatch`, `noneMatch` — the first thread to find the answer ends it for all; position doesn't matter.
- `findAny` — any thread's match ends the run for all and cancels the rest. Full short-circuit under parallel.
- `collect` with `toList`, `groupingBy`, `toMap` — each thread builds its own container, and the merge combines a
  few of them. This is the default choice. See [collect into one collection](#parallel-work-merged-into-one-collection).

**Avoid on an [ordered source](#which-sources-have-encounter-order)** — the combine must prefer left, so leaves wait
for earlier positions ([how order is rebuilt](#how-is-result-order-rebuilt-under-parallel))
- `forEachOrdered` — must run the action in encounter order, so a thread holding a later element waits for every
  earlier one. Puts the whole sequence back.
- `findFirst` — must return the leftmost match, so an early right-side match can't end the run until the left side
  proves it has none. It waits instead of short-circuiting.
  On an unordered source there is no leftmost, so `findFirst` turns into `findAny` — same semantics, no wait.

One trigger: an op is safe when a leaf can finish without waiting on another leaf's position. Left-before-right is
what forces the wait.

</details>

### Reduce vs collect — what's the difference?
<details><summary>Show answer</summary>

`reduce` folds elements into a single immutable value by repeatedly applying a combine function — each step takes the
running result and the next element and returns a new value. Nothing is mutated. Fits `sum`, `min`, `max`, `count`.

`collect` accumulates elements into a **mutable container** — each element is added into the same growing structure
(list, map, `StringBuilder`). This is "mutable reduction": the result is a container being filled, not a value being
folded.

Consequence for parallel: `reduce` merges by combining a few final values — cheap. `collect` (non-concurrent
collector) merges by combining whole containers — copying, resizing, rehashing — a cost that scales with the data.

Signatures — (multiple overloads, most general one) —

`reduce`:

```java
<U> U reduce(
        U identity, 
        BiFunction<U, ? super T, U> accumulator,  // result type U differs from element T
        BinaryOperator<U> combiner);              // combiner merges partials under parallel
```

`collect`:

```java
<R>    R collect(
        Supplier<R> supplier,                                    // makes a fresh container
        BiConsumer<R, ? super T> accumulator,                    // writes one element into the container
        BiConsumer<R, R> combiner);                             // merges two containers under parallel
```

The three-arg forms line up, and the differences all fall out of **mutable container vs immutable value**:

- **identity vs supplier.** 
    - `reduce`'s **identity** is a *value* — one seed like `0` or `""`, 
      shared by all threads because no thread ever changes it. 
    - `collect`'s **supplier** is a *factory* — `() -> new ArrayList<>()` — called once per thread so 
      each gets its **own separate container** to mutate without touching another's. 
    Collect needs a factory because it mutates; reduce needs only a shared value because it never mutates. 
- **accumulator.** Same job — fold one element into the running result — done two opposite ways:
    - `collect`: `(container, element) -> void`. Mutates the container in place (`list.add(element)`), returns nothing.
      The container is the same object before and after; it just has one more thing in it.
    - `reduce`: `(partial, element) -> newPartial`. Cannot mutate — the partial is often an immutable value like an
      `Integer` — so it produces a new value (`partial + element`) and returns it; the old partial is discarded.

  The return type is the tell: void = "I changed your container," a value = "I made you a new one."
- **combiner.** Only used under parallel — it merges the partial results the threads produced. `collect` merges two
  containers; `reduce` merges two values.

</details>

### What value is a valid reduce identity?
<details><summary>Show answer</summary>

The identity is the first argument — the value each fold starts from. Three rules govern what it may be:

1. **It must satisfy the identity law** — combining it with any value gives that value back. See
   [what the identity law requires](#what-does-the-reduce-identity-law-require). This is the core rule.
2. **It must not be a mutable object you fill.** The identity is shared across all chunks under parallel, so an
   accumulator that mutates it corrupts the one value every chunk started from. `reduce` folds new values; it never
   writes into the starting one.
3. **An immutable collection does not rescue rule 2.** Passing `List.of()` blocks the mutation, but then nothing can
   be folded in without copying the whole collection each step — O(N²). Immutability removes the crash, not the
   wrong choice: a collection is never a valid `reduce` identity, mutable or not.

One trigger: **a valid identity is an immutable value that changes nothing when combined — never a container.**
The failures of rules 2 and 3 are shown in [common mistakes with reduce's starting value](#common-mistakes-with-reduces-starting-value).

</details>

### What does the reduce identity law require?
<details><summary>Show answer</summary>

The identity must be a value that changes nothing when combined: `combine(identity, x) == x` for every `x`. 
For `+` it is `0`, for `*` it is `1`, for string concat it is `""`. 
It is not "any starting value" — pick the wrong one and the result is wrong.

Why the law is strict under parallel: each chunk starts its fold from the identity, so with N chunks the identity is
folded in **N times** before the chunks merge. Only a true identity survives that — folding in something that changes
nothing, any number of times, is still harmless.

Sum of `[1,2,3,4,5,6]` with identity `100`, three chunks:

```java
// chunk A: 100 + 1 + 2 = 103
// chunk B: 100 + 3 + 4 = 107
// chunk C: 100 + 5 + 6 = 111
// merge:   103 + 107 + 111 = 321   // want 21; the 100 was added three times
```

The bug is also non-deterministic: the identity is added once per chunk, and the chunk count depends on data size and
cores, so a different split gives a different wrong answer. Sequential adds it only once (`121` here), so a bad
identity can look merely "offset" sequentially and then blow up under `parallel()`.

</details>

### Common mistakes with reduce's starting value?
<details><summary>Show answer</summary>

Each one breaks one of the rules from [what makes a valid identity](#what-value-is-a-valid-reduce-identity). 
Two break the identity law, two break the no-mutate rule. Worst-hidden last:

1. [Passing a non-identity value?](#passing-a-non-identity-value) — *(identity law)* `100` where `0` is needed. Each
   chunk folds it in, so parallel adds it once per chunk. Wrong, and non-deterministic.
2. [Reduce into a mutable collection?](#reduce-into-a-mutable-collection) — *(no-mutate)* `new ArrayList<>()` with an
   accumulator that calls `add`. The accumulator writes into its input instead of returning a new value.
3. [Reduce into an immutable collection?](#reduce-into-an-immutable-collection) — *(no-mutate)* `List.of()`, thinking
   immutability is the fix. It blocks the mutation but forces a full copy each step — O(N²) — or throws on `add`.
4. [Reduce with a shared container?](#reduce-with-a-shared-container) — *(identity law)* one container reused as the
   starting value. Every chunk starts from the same object, so the combiner double-counts and the result shifts with
   the split. Sequential prints the right answer; it breaks only once someone adds `parallel()`.

One trigger: **two rules, two mistakes each — a non-identity value or a shared instance breaks the law; a mutable or
immutable collection breaks no-mutate.**

</details>

### Passing a non-identity value?
<details><summary>Show answer</summary>

Passing a starting value that is not a true identity — `100` for a sum where `0` is required. 
It compiles and runs; the number is just wrong.

```java
int sum = Stream.of(1, 2, 3, 4, 5, 6)
                .parallel()
                .reduce(100, Integer::sum);   // want 21
```

Under parallel each chunk starts its fold from `100`, so it is added once per chunk:

```java
// chunk A: 100 + 1 + 2 = 103
// chunk B: 100 + 3 + 4 = 107
// chunk C: 100 + 5 + 6 = 111
// merge:   103 + 107 + 111 = 321
```

Result `321`, not `21` — the `100` was added three times. The count of chunks depends on data size and cores, so a
different split gives a different wrong answer: the bug is non-deterministic. Sequential adds it only once (`121`),
so it can look merely "offset" until `parallel()` blows it up. Breaks the
[identity law](#what-does-the-reduce-identity-law-require): 
only a value that changes nothing survives being folded in N times.

</details>

### Reduce into a mutable collection?
<details><summary>Show answer</summary>

Folding into a collection by mutating it. It compiles — `reduce` takes any function — but the accumulator writes into
its input and returns the same reference, which `reduce` forbids.

```java
List<Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(new ArrayList<>(),                          // starting container
                  (list, n) -> { list.add(n); return list; }, // MUTATES input, returns same reference — the break
                  (a, b) -> { a.addAll(b); return a; });
```

`reduce` takes an identity **value**, not a factory: it evaluates `new ArrayList<>()` **once** and may reuse that one
object as the seed for several chunks — harmless for a real identity like `0`, fatal for a mutable list. On top of
that, every accumulator call returns the same list, so the framework's "separate partials" are one aliased object.
Under parallel the combiner reads a list while an accumulator on another thread is still `add`-ing to it — a data
race on a plain `ArrayList`: lost elements or corruption.

```java
// the framework evaluates `new ArrayList<>()` ONCE and may reuse that one object as the seed for
// several chunks — legal for a real identity, fatal for a mutable one:
// multiple chunks add into the SAME list, and combiner may run a.addAll(b) where a IS b
// result: duplicated or dropped elements, or a concurrent-modification failure — undefined per run
// chunk A: add(1), add(2)      → list = [1, 2]
// chunk B: add(3), add(4)      → list = [1, 2, 3, 4]      // B appends to A's live list
// combiner a.addAll(b): a IS b → [1,2,3,4].addAll(itself) // reads while another thread may still add
// possible run: [1, 2, 3, 4, 1, 2, 3, 4]  // duplicates; another run drops elements or throws — undefined
```

To obey the rule the accumulator would have to copy the container each step — O(N²). That copy is
what `collect(toList())` avoids by giving each thread its own private container. Breaks the
[no-mutate rule](#what-value-is-a-valid-reduce-identity): use `collect`, not `reduce`.

</details>

### Reduce into an immutable collection?
<details><summary>Show answer</summary>

Reaching for `List.of()` after learning mutation is forbidden — treating immutability as the fix. It is not: the
problem was never that the container *could* be mutated, it is that `reduce` must not mutate at all.

```java
List<Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(List.of(),                                  // immutable starting container
                  (list, n) -> {
                    var next = new ArrayList<>(list);         // forced to COPY — cannot add to an immutable list
                    next.add(n);
                    return List.copyOf(next);                 // freeze again — no immutable "add one" exists
                  },
                  (a, b) -> {
                    var m = new ArrayList<>(a); m.addAll(b);  // combiner copies too
                    return List.copyOf(m);
                  });
```

Call `list.add(n)` directly and it throws `UnsupportedOperationException` — an immutable list rejects the write. 
So each accumulator step must copy the whole list, add one, and freeze again. It is safe under parallel — every chunk
returns its own frozen lists, so no chunk can corrupt another's — but each step rebuilds the list from scratch:

```java
// chunk A [1, 2]: starts from List.of()
//   add 1: copy []     + 1 → [1]         (0 copied)
//   add 2: copy [1]    + 2 → [1, 2]      (1 copied)   → chunk A result = [1, 2]
// chunk B [3, 4, 5]: also starts from List.of()
//   add 3: copy []     + 3 → [3]         (0 copied)
//   add 4: copy [3]    + 4 → [3, 4]      (1 copied)
//   add 5: copy [3, 4] + 5 → [3, 4, 5]   (2 copied)   → chunk B result = [3, 4, 5]
// combiner combine(A, B): copy [1,2] + addAll [3,4,5] → [1,2,3,4,5]   // one more full copy
// correct result, but every element was copied many times over — copies grow as O(N²)
```

So immutability removes the race, not the wrong choice: a collection is never a valid starting value, mutable or not.
It just trades the mutable case's data race for a quadratic copy — safe, but pointless work. Same fix —
[`collect(toList())`](#what-value-is-a-valid-reduce-identity), which mutates one private container per thread and
copies nothing.

</details>

### Reduce with a shared container?
<details><summary>Show answer</summary>

Passing one container *instance* as the starting value, reused across every chunk. The worst version, because
sequential prints the right answer and it breaks only under `parallel()`.

```java
Map<Boolean, Integer> shared = new ConcurrentHashMap<>();     // one instance, used as the starting value

Map<Boolean, Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(shared,
                  (acc, n) -> { acc.merge(n % 2 == 0, n, Integer::sum); return acc; },  // odds→false, evens→true
                  (a, b) -> { b.forEach((k, v) -> a.merge(k, v, Integer::sum)); return a; });
```

The container is the best available — concurrent, no lost writes, safe merge — and is **not** the problem. 
The problem is one shared instance as the identity: every chunk starts from `shared`, so they all write into the **same**
map, and in each combiner call `a` and `b` are that same object:

```java
// one `shared` map is every chunk's starting value — all chunks write into it:
// chunk A [1, 2]: shared.merge(false,1), shared.merge(true,2)  → shared = {false:1, true:2}
// chunk B [3, 4]: SAME object → merge(false,3), merge(true,4)  → shared = {false:4, true:6}
// chunk C [5]:    SAME object → merge(false,5)                 → shared = {false:9, true:6}
// combiner combine(shared, shared): a IS b, so it merges the map INTO ITSELF:
//   {false:9, true:6}.merge each entry with itself → {false:18, true:12}
// want {false:9 (1+3+5), true:6 (2+4)}; got everything doubled
```

The combiner double-counts because it folds the shared object into itself, and the number of combiner calls tracks
how the source split — so the totals shift between runs. Sequential makes no combiner call, so it looks correct, and
because `shared` lives outside the pipeline a second run stacks on the first. Breaks the
[identity law](#what-does-the-reduce-identity-law-require): a filled shared container is not an identity, and it is
folded in once per chunk.

</details>

### What lets other functional languages reduce into collections?
<details><summary>Show answer</summary>

Their collections are **persistent**: adding an element returns a new version that shares structure with the old
one instead of copying it. Both versions stay valid, so `reduce`'s no-mutation contract costs almost nothing.

In Scala, for instance:

```scala
val a = List(2, 3)
val b = 1 :: a        // one new cell pointing at a — a is untouched, nothing copied, O(1)

val v = Vector(1, 2, 3)
val w = v :+ 4        // trie with wide nodes — copies one path, shares the rest, O(log N)

(1 to 5).foldLeft(List.empty[Int])((acc, n) => n :: acc)   // each step O(1), total O(N)
```

Clojure, Haskell and F# have the same thing under different names.

The language does not force this; the immutability does. A language where mutation is not the normal tool has to
make immutable collections cheap, or nothing would be usable.

The JDK never made that choice. `List.of` cannot add an element at all, and every `List` copy constructor copies
the whole array, so the same reduction is O(N²). The difference is the collection library, not the operation.

</details>

### Parallel work merged into one collection?
<details><summary>Show answer</summary>

`collect` — mutable reduction. The collector carries three functions plus a set of characteristics:

- **supplier** — makes a fresh container. `reduce` has one identity value instead, and that is the whole difference.
- **accumulator** — writes into that container. Allowed to mutate, because the container belongs to one worker.
- **combiner** — merges two containers the framework knows are separate objects.

Plain `groupingBy` or `partitioningBy` on a parallel stream is correct and is the normal way. The supplier gives
every worker its own map, each worker fills only its own, and the combiner merges those maps pairwise at the end.
No two threads ever touch the same container. `reduce` cannot do this: with one identity value and no supplier,
every worker starts from the same object.

```java
Map<Boolean, Integer> result =
    numbers.parallelStream()
           .collect(Collectors.partitioningBy(n -> n % 2 == 0,
                                              Collectors.summingInt(n -> n)));
```

`groupingByConcurrent` and `toConcurrentMap` declare the `CONCURRENT` characteristic. That is an optimization, not
a safer option: it skips the per-worker maps and lets every worker write into one shared map, so there is no merge
step. It requires a concurrent container, and the collector must also be `UNORDERED` — within a key the elements
land in whatever order the workers wrote them.

```java
ConcurrentMap<Boolean, List<Integer>> byParity =
    numbers.parallelStream()
           .collect(Collectors.groupingByConcurrent(n -> n % 2 == 0));
```

It pays when merging would dominate — many workers and many keys. It does not remove the coordination cost, it
moves it into the shared map, paid on every write. Merge cost scales with the number of keys, not the number of
elements, so a two-bucket result has nothing to merge and plain `groupingBy` wins. Default to the plain collector.

</details>

### Which lambda rules break under parallel?
<details><summary>Show answer</summary>

Safety failures — wrong results, not just slow ones — from lambdas that violate the `Stream` spec. Three requirements
on the function objects (e.g. `reduce`'s accumulator and combiner): **stateless, non-interfering, associative**.

- [**Stateless**](#why-does-a-stateful-lambda-pass-sequential-but-fail-parallel) — the result for an element mustn't
  depend on other elements or on a running count of them.
- [**Non-interfering**](#what-happens-if-a-lambda-modifies-the-streams-source) — doesn't modify the source while the
  stream runs. Broken by `list.stream().peek(x -> list.add(...))`.
- [**Associative**](#when-does-reduce-give-different-results-in-parallel) — regrouping the operands mustn't change the
  result; non-associative ops break. Subtraction: `reduce(0, (a, b) -> a - b)` gives -36 sequential, 0 parallel.

The trap: sequential execution hides **stateless** and **associative** — one thread means no race and no regrouping,
so they run right and nothing flags the bug; parallelize and they fail. (Non-interference throws in both modes, so it
isn't hidden.) Sequential correctness is not evidence the lambdas are legal.

</details>

### Why does a stateful lambda pass sequential but fail parallel?
<details><summary>Show answer</summary>

A stateful lambda carries a value from one element to the next, so an element's result depends on **how many elements
were processed before it**. Sequential runs on one thread in encounter order, so "before" is fixed and the result is
predictable. Parallel splits the elements across threads, so "before" is no longer fixed — the count each element
sees depends on thread timing.

```java
Set<String> names = new TreeSet<>(List.of("Anna", "Ben", "Carl"));   // sorted: Anna, Ben, Carl
AtomicInteger seq = new AtomicInteger();
List<Row> rows = names.parallelStream()
  .map(name -> new Row(seq.getAndIncrement(), name))                 // id = how many ran before this one
  .collect(Collectors.toList());
```

Expected: Anna→0, Ben→1, Carl→2. Actual under parallel: the **list order** is still Anna, Ben, Carl (`collect` keeps
encounter order), but the **ids are scrambled** — e.g. Anna→5, Ben→0, Carl→1 — and can differ from run to run. The
number no longer matches the element it was meant to label. The `AtomicInteger` prevents duplicate ids, not the
mismatch.

Handle: The spec says *stateless* because carried state depends on order, and parallel doesn't promise order.

</details>

### What happens if a lambda modifies the stream's source?
<details><summary>Show answer</summary>

**Non-interference:** no lambda in the pipeline may change the source collection while the stream runs. Unlike the
stateful trap, this one usually fails **loudly and in both modes** — not silently under parallel.

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
list.stream()
  .peek(x -> { if (x == 3) list.add(99); })   // modifies the source mid-stream
  .collect(Collectors.toList());              // throws ConcurrentModificationException
```

Fail-fast sources (`ArrayList`, `HashMap`) detect the structural change and throw `ConcurrentModificationException` —
sequential *and* parallel alike. The stream captures the source's state at the terminal operation; changing it
underneath is the violation.

Caveat: non-fail-fast sources (`CopyOnWriteArrayList`, concurrent collections) don't throw — the change is silently
ignored or seen inconsistently, which is worse. The rule holds regardless: don't write to the source you're reading.

Handle:
- interference breaks the source you're iterating;
- statefulness breaks the result you're building.

</details>

### When does reduce give different results in parallel?
<details><summary>Show answer</summary>

When the combine function is **not associative** — when regrouping the operands changes the result. Sequential folds
strictly left to right, so one grouping is used and the answer is stable. Parallel splits the elements into chunks,
reduces each chunk, then combines the partial results — a *different* grouping. If the operation is sensitive to
grouping, the two paths disagree.

```java
List<Integer> nums = List.of(1, 2, 3, 4, 5, 6, 7, 8);
nums.stream().reduce(0, (a, b) -> a - b);          // sequential:  -36
nums.parallelStream().reduce(0, (a, b) -> a - b);  // parallel:      0
```

Subtraction breaks because `(a - b) - c ≠ a - (b - c)`. Addition, multiplication, `min`, `max`, string concatenation
are associative — grouping doesn't matter, so they give the same answer either way.

Handle: parallel reduces in chunks and combines, so the grouping differs from left-to-right. Only associative
operations survive that regrouping.

</details>

### Does parallel preserve element order?
<details><summary>Show answer</summary>

Not with `forEach` — it makes no encounter-order promise, so a parallel run emits in whatever order threads finish.

`forEachOrdered` restores encounter order — but only at the **emit** step. All elements are still computed fully in
parallel; the stream buffers finished results and hands them to your consumer in order. If a later element finishes
first, its result is held until the earlier ones have been emitted. The heavy work stays parallel; only delivery is
serialized, and that holding-back is the cost.

Separate from safety failures: the pipeline computed correct elements, it just delivered them in an order the
sequential version didn't have.

</details>

### Terminal ops — which thread runs them?
<details><summary>Show answer</summary>

The workers do it. The terminal op is not a separate step where one thread gathers what the others produced — its
per-element work splits across the workers like every other stage, and what is left is a cheap merge of a few
partial results.

- `forEach` — the action runs on the worker holding the element, no merge at all.
- `reduce`, `min`, `max`, `count`, `sum` — each worker folds its chunk, the combiner merges partials.
- `anyMatch`, `allMatch`, `noneMatch` — the predicate runs on the workers, the first answer ends the run.
- `collect` — each worker fills its own container, merged as the split tree unwinds.

`forEachOrdered` is the exception. The action still runs on the workers, but each must wait for the elements before
it, so the pipeline is parallel in name only.

The caller thread blocks until the pipeline finishes; on the common pool it usually takes a share of the work too.

</details>

### How do parallel streams share threads?
<details><summary>Show answer</summary>

Every parallel stream in the whole program runs on **one shared pool** — the common `ForkJoinPool`, sized by default
to the machine's core count minus one. You don't create it or pass it in; `parallelStream()` and `.parallel()` use it
automatically.

Because it's shared program-wide, one heavy or slow pipeline occupies those workers and starves every other parallel
pipeline running at the same time — unrelated code slows down because it's waiting for the same threads.

Consequence: the blast radius is larger than the pipeline you wrote, so it must be measured in a realistic running
system. A benchmark of one pipeline alone never shows the interference, because alone it has the whole pool.

</details>

### How do you keep a parallel stream off the common pool?
<details><summary>Show answer</summary>

Run the stream as a task submitted to your own `ForkJoinPool`. A parallel stream started while executing inside a
`ForkJoinPool` task uses *that* pool's workers instead of the common pool:

```java
ForkJoinPool pool = new ForkJoinPool(4);
try {
  List<Row> rows = pool.submit(() ->
    items.parallelStream().map(this::heavy).collect(Collectors.toList())
  ).get();
} finally {
  pool.shutdown();
}
```

Caveat — this is **undocumented behavior**, not a contract. It works reliably across JDK versions but the spec never
promises it, so a reviewer who knows the internals will flag it. The officially-supported way to control the pool is
not `parallelStream()` at all — use `CompletableFuture` with an explicit `Executor`, or submit your own recursive
task, where the executor is part of the API.

Handle: wrapping in a custom pool isolates the threads but rides on an implementation detail; `CompletableFuture` +
`Executor` is the contract-backed alternative.

</details>

### parallel() — when do you add it?
<details><summary>Show answer</summary>

**Strictly a performance optimization** — so it inherits every rule about optimization: measure before and after in
realistic conditions, and keep it only if the numbers justify it. It is never a default or a style choice.

The order:

1. Have reason to believe correctness survives — legal lambdas, no order dependence.
2. Have reason to believe it gets faster — splittable source, heavy per-element work.
3. Measure in a realistic setting.
4. Only then ship it.

Step 2 is a filter, not an answer. `elements × lines of code ≥ ~100,000` is only the cheap-CPU-work case — it treats
every line as equal cost, so it misses blocking work. A few elements doing seconds of I/O each (file generation,
uploads, network calls) clear the bar that a million trivial elements never would. Heavy per-element work wins even
on a small collection; cheap work loses even on a large one. Count of elements is a poor proxy.

Only step 3 answers whether parallel helps. Skipping to step 4 risks a hang or a wrong answer, both worse than slow.

Skipping to step 4 risks a hang or a wrong answer, both worse than slow. The odds are against you: in large
stream-heavy codebases, the places where parallel actually pays off are rare.

</details>
