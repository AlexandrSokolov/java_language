## Lambdas and Streams - Side effects

### What is a side effect?
<details><summary>Show answer</summary>

A function has a **side effect** when it changes something outside itself — state that some later caller, or another
thread, could notice. The function does more than return a value; it leaves a mark on the world.

Concrete: writing a field or a `static`, adding to a list someone else holds, mutating an argument, writing a file,
sending to a queue, saving to a DB. After the call, something is different that was not different before.

Not a side effect: reading. `Integer.parseInt(s)` reads its argument and returns. `config.getTimeout()` reads a
field. A read — however far it travels, even to a network — changes nothing, so it is not a side effect.

The test: **after the call, is anything different in the world?** If yes, side effect. If no, none.

</details>

### What is a pure function?
<details><summary>Show answer</summary>

A **pure function's** output depends **only on its input**. Same argument, same answer, forever. 
`Integer.parseInt`, `String::trim`, `Math::sqrt`.

Two separate things break purity, and a function can have either alone:

- **It writes state outside itself** — [a side effect](#what-is-a-side-effect). `list::add`.
- **It reads state it was not given** — an external dependency. `userService.findAddress(id)`: the DB row can change
  between calls, so the same `id` can give two answers.

</details>

### Does throwing break purity?
<details><summary>Show answer</summary>

No — not if the exception follows from the input. `parseInt("x")` throws and is still pure. `findAddress` failing
because the network is down is different: the *environment* decided, not the argument. That failure is a symptom of
the read, not a separate defect.

</details>

### What kinds of order are in a stream?
<details><summary>Show answer</summary>

- **Source order** — the order the source produces elements in. Can be encounter (ordered) or unordered.
- **Execution order** — when the `map`/`filter` lambdas fire, on which thread. 
  - For parallel streams always undefined.
  - For sequential streams always matches the source order
- **Result order** — what the terminal op returns. Always matches source order — except `forEach`, which always
  matches execution order.

</details>

### What does a stream guarantee?
<details><summary>Show answer</summary>

Promised:
- each element goes through the stages in the order you wrote them — `map` runs before `filter`, always
- the terminal gives the result back in [source order](#what-kinds-of-order-are-in-a-stream) — sequential or
  parallel — except `forEach`, which gives it back in execution order

Free — not promised:
- [execution order](#what-kinds-of-order-are-in-a-stream) — when each lambda runs, and on which thread
- how many elements the terminal pulls through — `findFirst` or `limit` stop early, so only some elements go through;
  `count()` can pull none, taking the size from the source directly. A skipped element runs no stage at all — 
  the promise that stages run in written order still holds, it just never fires for that element

</details>

### What should a stream stage not do?
<details><summary>Show answer</summary>

A stage's lambda must be **stateless** if you need the same result every run — sequential or parallel. A stateful
lambda — one whose result depends on state that can change during the run — often works on a sequential stream, but
its result depends on order and threads, so it breaks [what the stream promises](#what-does-a-stream-guarantee) the
moment it runs in parallel.

</details>

### What is a stateful lambda?
<details><summary>Show answer</summary>

From the stream docs: a stateful lambda is one whose *result depends on any state which might change during the
execution of the stream pipeline*.

The test is not "does it read outside state" — it is "does that state **change while the stream runs**".

Stateful — result depends on state changing during the run:
```java
AtomicInteger idx = new AtomicInteger();
stream.map(w -> idx.getAndIncrement())   // idx moves on every call — result depends on when this runs
```

Not stateful — reads state that stays put during the run:
```java
int limit = config.getMaxAllowed();      // fixed before the run, never changes during it
stream.filter(w -> w.size() < limit)     // same limit for every element — result does not depend on timing
```

Also not stateful — writes, but the result does not depend on the write:
```java
stream.map(img -> uploader.send(img))    // writes to the network, returns a Result; result depends only on img
```

So a read of fixed state is fine, and a write you do not read back is fine. 
What is stateful is a result that **depends on state the run itself is changing**.

</details>

### When is a side effect in a stage safe?
<details><summary>Show answer</summary>

Two abstract principles decide it. Together they cover every safe case.

**Principle 1 — A stateful lambda is only a problem if its outcome depends on state that the stream run itself is actively changing.**
If the pipeline does not read the changing state back during the execution, the side effect cannot break the stream. 
The final result relies entirely on what each stage *returns*, not what it writes. 
Because the write is never observed by the stream itself, the outcome remains perfectly stable and identical across runs:
```java
.map(uploader::send)   // writes to the network, returns a Result
.toList()              // result = the returned Results; the write itself is invisible to it
```

**Principle 2 — Principle 1 may be broken, as long as you do not care about the order.**
You may actively write and read shared state that the run itself changes — 
which explicitly violates Principle 1 because you are reading changing state — 
but it is safe because you do not require a stable, identical item-to-state pairing across different runs:
```java
AtomicInteger id = new AtomicInteger();
.map(u -> u.withId(id.getAndIncrement()))   // each gets a unique id; who gets which varies run to run — you don't care
```


Separate note — **strictly sequential streams follow no rule at all and still work.**
When execution is tied to a single thread running in deterministic source order, 
you cannot accidentally observe raw timing or concurrency defects.

**Why this is a maintenance trap:**
This code is correct here and now, but strategically wrong to rely on. 
The safety does not live in your logic — it lives entirely in an external execution configuration. 
The moment a developer attempts to optimize performance and switches the source from sequential to parallel, 
the lack of structural rules will instantly destroy the code's correctness. 
Prefer the two principles above, where safety inherently survives that change.

```java
List<String> log = new ArrayList<>();
words.stream().forEach(log::add);   // Safe today, but breaks silently if changed to parallelStream()
```

</details>

### May a stage call a service?
<details><summary>Show answer</summary>

Yes. A read of an external system is not [a side effect](#what-counts-as-a-side-effect) — the stage takes its input,
asks a question, returns an answer, and changes nothing. It is [not a math function](#when-is-a-function-not-a-math-function),
but the pipeline never asked for one.

```java
users.stream()
     .map(userService::findAddress)             // reads the DB — legal
     .map(deliveryService::deliveryCompany)     // reads a REST API — legal
     .filter(deliveryService::isAvailable)
     .toList();                                 // terminal builds the result
```

</details>

### What belongs in forEach?
<details><summary>Show answer</summary>

Only reporting the result — print it, send it, hand it to something else. Never computing it.

`forEach` is the weakest terminal: no order guarantee, and it exists to consume the result, not compute one.
Everything that makes a stream worth using lives in the other terminals. If the work happens inside `forEach`, the pipeline is
decoration — you wrote a loop with more syntax.

```java
// Not streams code — a loop in disguise. All the work is in forEach, mutating a table outside the pipeline.
Map<String, Long> freq = new HashMap<>();
try (Stream<String> words = new Scanner(file).tokens()) {
  words.forEach(word -> freq.merge(word.toLowerCase(), 1L, Long::sum));
}

// The pipeline computes; nothing outside is touched. Shorter, and parallel-safe for free.
Map<String, Long> freq;
try (Stream<String> words = new Scanner(file).tokens()) {
  freq = words.collect(groupingBy(String::toLowerCase, counting()));
}
```

Why people write the first one: `forEach` looks like a for-each loop, so it feels familiar. That familiarity is the
whole reason the anti-pattern exists.

Legal exception: pushing a finished result into a collection that already exists.

</details>
