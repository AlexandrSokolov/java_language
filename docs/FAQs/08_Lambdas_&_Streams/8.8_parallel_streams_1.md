## Lambdas and Streams - Parallel Streams #1

### What governs whether parallel() helps?
<details><summary>Show answer</summary>

Five things must hold, and the sixth decides.

1. [**The source splits cheaply**](#how-does-source-type-affect-parallel-streams) — a chain source cannot be cut, so
   one thread does all the work.
2. [**The lambdas are legal**](#which-lambda-rules-break-under-parallel) — stateful or interfering ones give a wrong
   answer, and sequential runs hide it.
3. [**The terminal op merges cheaply**](#which-terminal-ops-suit-parallelism) — a finish that cannot be split caps
   the whole pipeline.
4. [**Order is not needed**](#does-parallel-preserve-element-order) — asking for encounter order back puts the
   sequence back too.
5. [**The pool is not a problem**](#how-do-parallel-streams-share-threads) — one shared pool for the whole program,
   so blocking work starves everyone else.
6. [**It measures faster**](#parallel--when-do-you-add-it) — the only thing that actually answers the question.

Spine: it has to split, the lambdas have to be legal, the finish has to merge, order has to be affordable, the
threads are shared — and then you measure.

</details>

### How does source type affect parallel streams?
<details><summary>Show answer</summary>

Splitting is cheap when the source has known size and a structure that can be cut without walking it:

- arrays, `ArrayList`, `IntStream.range` — random access by index, so the splitterator hands out index ranges
  instantly.
- `HashMap`, `HashSet` — no index, but the splitterator cuts the internal bucket table into ranges of buckets.

It fails when the source is a **chain** — element N is produced from element N-1, so reaching N means walking 1..N-1.
No cut point exists.

</details>

### Which sources split badly in parallel?
<details><summary>Show answer</summary>

A chain source: element N is produced from element N-1, so reaching N means walking 1..N-1. No cut point exists.

- `Stream.iterate(seed, f)` — each element is `f` applied to the one before, so #500000 can't be produced without
  first producing all 499999 ahead of it.

    ```java
    Stream.iterate(BigInteger.ONE, n -> n.multiply(TWO))  // #3 needs #2, #2 needs #1
          .parallel()                                     // no thread can start at #500000
          .limit(500_000)
          .forEach(System.out::println);                  // one thread does all the producing
    ```
- `BufferedReader.lines()` — reads forward through the file; size is unknown and you can't jump to line N without
  reading every line before it.
- `Iterator`-based streams — the only operation is "give me the next one"; there's no size and no random access to
  hand a chunk to another thread.

    ```java
    Iterable<Order> orders = repository.streamAll();      // Iterator only: hasNext() / next()
    StreamSupport.stream(orders.spliterator(), true)      // true = parallel
                 .forEach(this::handle);                  // spliterator has no size, no index
                                                          // it can only buffer next() results in batches
    ```

- Cursor-paginated APIs — page N's request needs the cursor returned by page N-1, so pages can only be fetched one
  after another.

</details>

### Which random source for parallel streams?
<details><summary>Show answer</summary>

`SplittableRandom` — built for this: it splits into independent generators, one per thread, so the source parallelizes
cleanly and can scale near-linearly.

The other two, worst-last:
- `ThreadLocalRandom` — made for a single thread; used as a parallel source it works but won't match
  `SplittableRandom`.
- `Random` — synchronizes on every call, so all threads contend on one lock and the parallelism collapses. (Fine
  single-threaded; only bad as a parallel source.)

Handle: can the generator be *split* or only *shared*? Splittable → scales. Shared behind a lock → contention.

</details>

### What kinds of order are in a parallel stream?
<details><summary>Show answer</summary>

Different orders live in a parallel stream and they behave differently — telling them apart is the whole point:

- **Source order** — the order the source produces elements in. Can be encounter (ordered) or unordered.
- **Execution order** — when the `map`/`filter` lambdas fire, on which thread. Always undefined.
- **Result order** — what the terminal op returns. Matches source order, except `forEach`, which emits in
  execution order.

Spine trigger:
- an unordered source keeps nothing
- on an ordered source:
    - execution order is still undefined and
    - result order matches the source order — except `forEach`

</details>

### How can a source's order be classified?
<details><summary>Show answer</summary>

Every source produces elements in some order. It can be:

**Ordered (encounter order)** — set by the spliterator's `ORDERED` flag — the source promises an order, 
so order-sensitive ops (`findFirst`, `limit`, `skip`) honor it:
- `List`, arrays, `IntStream.range` — order is the index.
- `LinkedHashSet`, `LinkedHashMap` — order is insertion order.
- `TreeSet`, `TreeMap` — order is the sort order.

**Unordered** — the source makes no promise, so order-sensitive ops have nothing to keep:
- `HashSet`, `HashMap` keys — see [Is a HashSet ordered?](#is-a-hashset-ordered).
- `Collectors.toSet()`, and any stream after `.unordered()`.

</details>

### Is a HashSet ordered?
<details><summary>Show answer</summary>

No. A `HashSet` has an iteration order — some repeatable sequence comes out — but the spliterator does **not** report
`ORDERED`. That sequence is an accident of which bucket each hash landed in, so the stream promises nothing about it
and order-sensitive ops ignore it.

</details>

### What is the execution order under parallel?
<details><summary>Show answer</summary>

Undefined. Which thread runs which element, and when each `map`/`filter` lambda fires, is not fixed — independent of
the source. Run the same pipeline twice and the lambdas may fire in a different order each time.

</details>

### What is the result order under parallel?
<details><summary>Show answer</summary>

The result order match the source order (except `forEach`).

Splitting builds a **left-to-right tree**: each split cuts the source into `left | right`, where left holds the
earlier part of the source. The leaves compute in parallel, in any time order. The terminal op then combines **back
up the tree**, and for an order-sensitive op each combine prefers the left child. That rebuilds encounter order.

Source `[10,5,6,2,3,7,4,1,9,8]`, heavy `map` + `filter`, match = value in `{2,5,7}`:

```text
                 [10,5,6,2,3,7,4,1,9,8]
                  /                    \
              LEFT                    RIGHT
        [10,5,6,2,3]              [7,4,1,9,8]
         /        \                /        \
     [10,5,6]    [2,3]         [7,4]      [1,9,8]
     match:5     match:2       match:7    none
```

- **Position is not stored on elements.** No element carries an index. "Earlier" means *sits in a left branch* —
  that fact lives in the tree shape, not on the elements.
- **Finish time is ignored.** Leaves may finish `2, 7, 5`; that order is thrown away. Each result slots into its
  fixed place in the tree.
- **`findFirst` = prefer left up the tree.** `combine([10,5,6]=5, [2,3]=2)` → **5**; `combine(LEFT=5, RIGHT=7)` →
  **5**. Result is **5** — earliest in the list (index 1), not `2` (smallest) and not `7` (finished first).
  Deterministic, identical to sequential.
- **The cost is the wait.** `findFirst` can't take the early right-side `7` until the left side finishes proving it
  has no earlier match. It waits for left instead of stopping on the first match found in time.

</details>

### Which terminal ops parallelize well?
<details><summary>Show answer</summary>

The axis: **does the terminal step split into independent chunks and merge cheaply, or does it force a sequence?**
Ops that combine without caring about left-vs-right are safe; ops that must respect left-before-right pay the wait —
see [how result order is rebuilt](#how-is-result-order-rebuilt-under-parallel).

**Safe** — the combine is order-free, so no leaf waits on another
- `reduce`, and the prepackaged `min`, `max`, `count`, `sum` — each thread reduces its chunk to one value, and the
  merge combines a few values in any order.
- `anyMatch`, `allMatch`, `noneMatch` — the first thread to find the answer ends it for all; position doesn't matter.
- `findAny` — any thread's match ends the run for all and cancels the rest. Full short-circuit under parallel.
- `collect` with `toList`, `groupingBy`, `toMap` — each thread builds its own container, and the merge combines a
  few of them. This is the default choice. See [collect into one collection](#parallel-work-merged-into-one-collection).

**Avoid on an [ordered source](#which-sources-have-encounter-order)** — the combine must prefer left, so leaves wait
for earlier positions ([how order is rebuilt](#how-is-result-order-rebuilt-under-parallel))
- `forEachOrdered` — must run the action in encounter order, so a thread holding a later element waits for every
  earlier one. Puts the whole sequence back.
- `findFirst` — must return the leftmost match, so an early right-side match can't end the run until the left side
  proves it has none. It waits instead of short-circuiting.
  On an unordered source there is no leftmost, so `findFirst` turns into `findAny` — same semantics, no wait.

One trigger: an op is safe when a leaf can finish without waiting on another leaf's position. Left-before-right is
what forces the wait.

</details>

### Reduce vs collect — what's the difference?
<details><summary>Show answer</summary>

`reduce` folds elements into a single immutable value by repeatedly applying a combine function — each step takes the
running result and the next element and returns a new value. Nothing is mutated. Fits `sum`, `min`, `max`, `count`.

`collect` accumulates elements into a **mutable container** — each element is added into the same growing structure
(list, map, `StringBuilder`). This is "mutable reduction": the result is a container being filled, not a value being
folded.

Consequence for parallel: `reduce` merges by combining a few final values — cheap. `collect` (non-concurrent
collector) merges by combining whole containers — copying, resizing, rehashing — a cost that scales with the data.

</details>

### Reduce vs collect — the signatures?
<details><summary>Show answer</summary>

Signatures — (multiple overloads, most general one) —

`reduce`:

```java
<U> U reduce(
        U identity,                               // same for all threads
        BiFunction<U, ? super T, U> accumulator,  // result type U differs from element T
        BinaryOperator<U> combiner);              // combiner merges partials under parallel
```

`collect`:

```java
<R>    R collect(
        Supplier<R> supplier,                                    // makes a fresh container in each thread
        BiConsumer<R, ? super T> accumulator,                    // writes one element into the container
        BiConsumer<R, R> combiner);                             // merges two containers under parallel
```

The three-arg forms line up, and the differences all fall out of **mutable container vs immutable value**:

- **identity vs supplier.**
    - `reduce`'s **identity** is a *value* — one seed like `0` or `""`,
      shared by all threads because no thread ever changes it.
    - `collect`'s **supplier** is a *factory* — `() -> new ArrayList<>()` — called once per thread so
      each gets its **own separate container** to mutate without touching another's.
      Collect needs a factory because it mutates; reduce needs only a shared value because it never mutates.
- **accumulator.** Same job — fold one element into the running result — done two opposite ways:
    - `collect`: `(container, element) -> void`. Mutates the container in place (`list.add(element)`), returns nothing.
      The container is the same object before and after; it just has one more thing in it.
    - `reduce`: `(partial, element) -> newPartial`. Cannot mutate — the partial is often an immutable value like an
      `Integer` — so it produces a new value (`partial + element`) and returns it; the old partial is discarded.

  The return type is the tell: void = "I changed your container," a value = "I made you a new one."
- **combiner.** Only used under parallel — it merges the partial results the threads produced. `collect` merges two
  containers; `reduce` merges two values.

</details>

### What value is a valid reduce identity?
<details><summary>Show answer</summary>

The identity must satisfy the [identity law](#what-does-the-reduce-identity-law-require) — combining it with any
value gives that value back: `combine(identity, x) == x` for every `x`

</details>

### What does the reduce identity law require?
<details><summary>Show answer</summary>

The identity must be a value that changes nothing when combined: `combine(identity, x) == x` for every `x`.
For `+` it is `0`, for `*` it is `1`, for string concat it is `""`.
It is not "any starting value" — pick the wrong one and the result is wrong.

Why the law is strict under parallel: each chunk starts its fold from the identity, so with N chunks the identity is
folded in **N times** before the chunks merge. Only a true identity survives that — folding in something that changes
nothing, any number of times, is still harmless.

Sum of `[1,2,3,4,5,6]` with identity `100`, three chunks:

```java
// chunk A: 100 + 1 + 2 = 103
// chunk B: 100 + 3 + 4 = 107
// chunk C: 100 + 5 + 6 = 111
// merge:   103 + 107 + 111 = 321   // want 21; the 100 was added three times
```

The bug is also non-deterministic: the identity is added once per chunk, and the chunk count depends on data size and
cores, so a different split gives a different wrong answer. Sequential adds it only once (`121` here), so a bad
identity can look merely "offset" sequentially and then blow up under `parallel()`.

</details>

### Common mistakes with reduce's starting value?
<details><summary>Show answer</summary>

Each uses a collection as the starting value, and each breaks the
[core rule](#what-value-is-a-valid-reduce-identity) — a container is never a valid identity. 

1. [Reduce into a mutable collection?](#reduce-into-a-mutable-collection) — `new ArrayList<>()` with an accumulator
   that calls `add`. It writes into its input instead of returning a new value, and under parallel several chunks
   share the one list — a data race.
2. [Reduce into an immutable collection?](#reduce-into-an-immutable-collection) — `List.of()`, thinking immutability
   is the fix. It blocks the mutation but forces a full copy each step — O(N²) — or throws on `add`.
3. [Reduce with a shared container?](#reduce-with-a-shared-container) — one external list reused as the starting
   value. Every chunk starts from the same object, so the combiner double-counts and the result shifts with the
   split. Sequential prints the right answer; it breaks only once someone adds `parallel()`.

One trigger: **a collection is never a valid identity — mutable races, immutable copies O(N²), shared double-counts.**

</details>

### Reduce into a mutable collection?
<details><summary>Show answer</summary>

Folding into a collection by mutating it. It compiles — `reduce` takes any function — but the accumulator writes into
its input and returns the same reference, which `reduce` forbids.

```java
List<Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(new ArrayList<>(),                          // same object for all threads — evaluated once
                  (list, n) -> { list.add(n); return list; }, // MUTATES input, returns same reference — the break
                  (a, b) -> { a.addAll(b); return a; });
```

`reduce` takes an identity **value**, not a factory: it evaluates `new ArrayList<>()` **once** and may reuse that one
object as the input for every thread. Two failures follow. All threads mutate the same list at once, and mutating a
plain `ArrayList` from many threads is never thread-safe — corrupted data. And every accumulator returns that same
list, so the combiner runs `a.addAll(b)` where `a` and `b` are the one object — a list adding itself, duplicating
elements.

A thread-safe collection (`ConcurrentLinkedQueue`) fixes only the first failure. The second stays: it is one shared
object, so the combiner still merges it with itself and still duplicates. The bug is the shared identity, not the
collection's thread-safety.

```java
// the framework evaluates `new ArrayList<>()` ONCE and may reuse that one object as the seed for
// several chunks — legal for a real identity, fatal for a mutable one:
// multiple chunks add into the SAME list, and combiner may run a.addAll(b) where a IS b
// result: duplicated or dropped elements, or a concurrent-modification failure — undefined per run
// chunk A: add(1), add(2)      → list = [1, 2]
// chunk B: add(3), add(4)      → list = [1, 2, 3, 4]      // B appends to A's live list
// combiner a.addAll(b): a IS b → [1,2,3,4].addAll(itself) // reads while another thread may still add
// possible run: [1, 2, 3, 4, 1, 2, 3, 4]  // duplicates; another run drops elements or throws — undefined
```

</details>

### Reduce into an immutable collection?
<details><summary>Show answer</summary>

Reaching for `List.of()` after learning mutation is forbidden — treating immutability as the fix. It is not: the
problem was never that the container *could* be mutated, it is that `reduce` must not mutate at all.

```java
List<Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(List.of(),                                  // same immutable object for all threads — evaluated once
                  (list, n) -> {
                    var next = new ArrayList<>(list);         // forced to COPY — cannot add to an immutable list
                    next.add(n);
                    return List.copyOf(next);                 // freeze again — no immutable "add one" exists
                  },
                  (a, b) -> {
                    var m = new ArrayList<>(a); m.addAll(b);  // combiner copies too
                    return List.copyOf(m);
                  });
```

Call `list.add(n)` directly and it throws `UnsupportedOperationException` — an immutable list rejects the write. 
So each accumulator step must copy the whole list, add one, and freeze again. It is safe under parallel — every chunk
returns its own frozen lists, so no chunk can corrupt another's — but each step rebuilds the list from scratch:

```java
// chunk A [1, 2]: starts from List.of()
//   add 1: copy []     + 1 → [1]         (0 copied)
//   add 2: copy [1]    + 2 → [1, 2]      (1 copied)   → chunk A result = [1, 2]
// chunk B [3, 4, 5]: also starts from List.of()
//   add 3: copy []     + 3 → [3]         (0 copied)
//   add 4: copy [3]    + 4 → [3, 4]      (1 copied)
//   add 5: copy [3, 4] + 5 → [3, 4, 5]   (2 copied)   → chunk B result = [3, 4, 5]
// combiner combine(A, B): copy [1,2] + addAll [3,4,5] → [1,2,3,4,5]   // one more full copy
// correct result, but every element was copied many times over — copies grow as O(N²)
```

</details>

### Reduce with a shared container?
<details><summary>Show answer</summary>

Passing one container *instance* as the starting value, reused across every chunk. The worst version, because
sequential prints the right answer and it breaks only under `parallel()`.

```java
Map<Boolean, Integer> shared = new ConcurrentHashMap<>();     // one instance, used as the starting value

Map<Boolean, Integer> result =
    Stream.of(1, 2, 3, 4, 5)
          .parallel()
          .reduce(shared,
                  (acc, n) -> { acc.merge(n % 2 == 0, n, Integer::sum); return acc; },  // odds→false, evens→true
                  (a, b) -> { b.forEach((k, v) -> a.merge(k, v, Integer::sum)); return a; });
```

The container is the best available — concurrent, no lost writes, safe merge — and is **not** the problem. 
The problem is one shared instance as the identity: every chunk starts from `shared`, so they all write into the **same**
map, and in each combiner call `a` and `b` are that same object:

```java
// one `shared` map is every chunk's starting value — all chunks merge into it:
// chunk A [1, 2]: merge(false,1)→false:1;  merge(true,2)→true:2                        → shared = {false:1, true:2}
// chunk B [3, 4]: SAME object → merge(false,3)→false:1+3=4;  merge(true,4)→true:2+4=6  → shared = {false:4, true:6}
// chunk C [5]:    SAME object → merge(false,5)→false:4+5=9                             → shared = {false:9, true:6}
// so far correct: false:9 (1+3+5), true:6 (2+4)
// but combiner combine(a, b) runs with a IS b (both are `shared`), folding the map into itself:
//   merge(false, 9)→false:9+9=18;  merge(true, 6)→true:6+6=12          → {false:18, true:12}
// want {false:9, true:6}; got everything doubled by the self-merge
```

The combiner double-counts because it folds the shared object into itself, and the number of combiner calls tracks
how the source split — so the totals shift between runs. Sequential makes no combiner call, so it looks correct, and
because `shared` lives outside the pipeline a second run stacks on the first. 

</details>

### Why can a wrong reduce identity produce the right result?
<details><summary>Show answer</summary>

A sequential stream never calls the combiner. It folds every element through one accumulator chain, start to finish,
so a container used as the starting value — mutable, immutable, or shared — still ends up filled correctly. The
answer looks right, so the code ships.

The combiner runs only under `parallel()`, where the split makes separate partials that must merge. 

So the bug was always there; sequential just never ran the combiner that exposes it. 
It breaks the day someone adds `parallel()`, or the day the data grows enough to split.

</details>

### What lets other functional languages reduce into collections?
<details><summary>Show answer</summary>

Their collections are **persistent**: adding an element returns a new version that shares structure with the old
one instead of copying it. Both versions stay valid, so `reduce`'s no-mutation contract costs almost nothing.

In Scala, for instance:

```scala
val a = List(2, 3)
val b = 1 :: a        // one new cell pointing at a — a is untouched, nothing copied, O(1)

val v = Vector(1, 2, 3)
val w = v :+ 4        // trie with wide nodes — copies one path, shares the rest, O(log N)

(1 to 5).foldLeft(List.empty[Int])((acc, n) => n :: acc)   // each step O(1), total O(N)
```

Clojure, Haskell and F# have the same thing under different names.

The language does not force this; the immutability does. A language where mutation is not the normal tool has to
make immutable collections cheap, or nothing would be usable.

The JDK never made that choice. `List.of` cannot add an element at all, and every `List` copy constructor copies
the whole array, so the same reduction is O(N²). The difference is the collection library, not the operation.

</details>

### Parallel work merged into one collection?
<details><summary>Show answer</summary>

`collect` — mutable reduction. The collector carries three functions:

- **supplier** — makes a fresh container. `reduce` has one identity value instead, and that is the whole difference.
- **accumulator** — writes into that container. Allowed to mutate, because the container belongs to one worker.
- **combiner** — merges two containers the framework knows are separate objects.

The three functions spelled out — each worker gets its own list from the supplier, fills only that list, and the
combiner merges the separate lists at the end:

```java
List<Integer> result =
    numbers.parallelStream()
           .collect(ArrayList::new,       // supplier — a fresh list per worker
                    ArrayList::add,       // accumulator — write into that worker's own list
                    ArrayList::addAll);   // combiner — merge two separate lists
```

The short form — `toList()` packs the same three functions into one collector:

```java
List<Integer> result =
    numbers.parallelStream()
           .collect(Collectors.toList());
```

</details>

### Parallel work merged into one map?
<details><summary>Show answer</summary>

Plain `groupingBy` / `partitioningBy` on a parallel stream is correct and is the default. Each worker gets its own
map, fills only that one, and the combiner merges the separate maps at the end — no two workers touch the same map.

```java
Map<Boolean, List<Integer>> byParity =
    numbers.parallelStream()
           .collect(Collectors.groupingBy(n -> n % 2 == 0));
```

Switching to `groupingByConcurrent` / `toConcurrentMap` (the `CONCURRENT` characteristic) has a get and a lose.

**What you get** — two independent reasons:
1. **No merge step.** Every worker writes into one shared concurrent map, so nothing is merged at the end. Pays off
   when there are many keys; a two-bucket result has nothing to merge and plain wins.
2. **A `ConcurrentHashMap` back.** The returned map is safe to keep using across threads in later parallel work.

**What you lose** — within-group order. Only when the value is a `List<V>` (grouping with no downstream): many
workers write into the same key's list at once, so the list is in write order, not source order. If the value is a
sum, a count, or one mapped value, there is no order to lose and this cost disappears.

```java
ConcurrentMap<Boolean, List<Integer>> byParity =
    numbers.parallelStream()
           .collect(Collectors.groupingByConcurrent(n -> n % 2 == 0));
```

One trigger: **concurrent map = skip the merge and get a shareable map back, at the cost of within-group order — and
only the list-valued form has any order to lose.**

</details>
