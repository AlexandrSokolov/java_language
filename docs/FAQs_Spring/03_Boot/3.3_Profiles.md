# Profiles

Why profiles exist, how a deployment picks its set of them, and how profile files layer over the base config.

### Profiles — what are they for?
<details><summary>Show answer</summary>

A profile switches a feature on or off for a deployment: which beans exist and the settings that go with them — real
Kafka or an in-memory queue, a real mail sender or a fake one.

The common first habit is one profile per environment — `application-dev.yml`, `application-qa.yml`,
`application-prod.yml`, each with its own URLs, passwords and pool sizes. It is not the final design:

- **Secrets in the jar** — every build carries every environment's settings, secrets included;
- **New environment = new build** — its values must be added to the jar first;
- **Profile explosion** — `prod-eu`, `prod-us`, `prod-eu-canary`…, and `@Profile` checks spread through the code.

Values that differ per environment come from outside the jar —
[the environment owns them](3.2_Configuration.md#a-setting--owned-by-the-app-or-by-the-environment).

Does the setting change which code runs? → profile. Only a value? → an outside property.

</details>

### Composing and enabling a set of profiles — options?
<details><summary>Show answer</summary>

Two ways to say which features a deployment runs:

- **A list** — `SPRING_PROFILES_ACTIVE=postgres,kafka,json-logs`; every deployment repeats the full set
  ([activation](#how-do-you-activate-a-profile)).
- **A group** — `spring.profiles.group.prod: [postgres, kafka, json-logs]` in `application.yml`; the deployment sets
  only `prod` ([groups](#what-are-profile-groups-for)).

The set is changed in another place by its own rules:

- a stronger source [replaces the active list whole](#springprofilesactive-set-in-two-sources--result);
- to add without replacing — [`include` and friends](#adding-a-profile-without-replacing-the-active-ones--options);
- a group itself can be [redefined per deployment](#a-profile-group-defined-in-the-jar--how-to-change-it-per-deployment).

The group names the set in the jar; the deployment only picks the name.

</details>

### What does a profile switch on?
<details><summary>Show answer</summary>

```java
@Bean
@Profile("dev")
DataSource devDataSource() { /* in-memory H2 */ }
```

A profile is a name (`dev`, `prod`, `kafka`). When it is active, it switches on two things:

- **beans** marked `@Profile("dev")`;
- **its property file** — `application-dev.yml` loads on top of `application.yml`.

`@Profile` takes expressions: `@Profile("!prod")`, `@Profile("prod & eu")`. With nothing active —
[see here](#no-profile-set--what-is-active).

A profile is a name that switches on its beans and its property file.

</details>

### No profile set — what is active?
<details><summary>Show answer</summary>

The profile `default`. Beans marked `@Profile("default")` and `application-default.yml` apply only then; as soon as
any profile is active, `default` is off.

`spring.profiles.default=local` gives the fallback another name — e.g. a local setup that applies when nobody set
anything.

Beans with no `@Profile` are always on, whatever is active.

Nothing active → `default`; anything active → `default` is off.

</details>

### How do you activate a profile?
<details><summary>Show answer</summary>

Set `spring.profiles.active` from any configuration source:

```
SPRING_PROFILES_ACTIVE=prod          # environment variable — the usual way in containers
-Dspring.profiles.active=prod        # system property
--spring.profiles.active=prod        # command-line argument
```

In tests: `@ActiveProfiles("test")`.

- Several at once: `prod,eu` — on a conflict, the later one wins.
- Setting it in `application.yml` works, but only as a default: any outside source
  [replaces it](#springprofilesactive-set-in-two-sources--result).
- Setting it inside a profile-specific file is an error — a profile can't activate profiles.

`spring.profiles.active`, set from outside the jar — usually an environment variable.

</details>

### `spring.profiles.active` set in two sources — result?
<details><summary>Show answer</summary>

The stronger source's list replaces the weaker one whole; the two are not combined.

```yaml
# application.yml
spring.profiles.active: dev,kafka
```

```
SPRING_PROFILES_ACTIVE=prod
```

→ only `prod` is active; `kafka` is gone. It is the same rule as for
[any list](3.2_Configuration.md#same-key-in-several-sources--what-is-merged-what-is-replaced).

So `active` in `application.yml` is only a local default. A deployment must name every profile it needs — or use
[a group](#what-are-profile-groups-for) or
[`include`](#adding-a-profile-without-replacing-the-active-ones--options).

A stronger `active` replaces the list; it never adds to it.

</details>

### Adding a profile without replacing the active ones — options?
<details><summary>Show answer</summary>

- **`spring.profiles.include`** — profiles added to whatever is active; set in `application.yml`, not in a
  profile-specific file.
- **`SpringApplication.setAdditionalProfiles("metrics")`** — in code, before `run()`.
- **A group** — put the profile into the [group](#what-are-profile-groups-for) the deployment activates.

`include` is itself a list: a stronger source replaces it whole too *(unverified)*.

`active` is replaced; `include` and groups add.

</details>

### What are profile groups for?
<details><summary>Show answer</summary>

```yaml
spring:
  profiles:
    group:
      prod: [postgres, kafka, json-logs]
      dev: [h2, local-queue]
```

Activate `prod` and Boot also activates `postgres`, `kafka` and `json-logs`. Each small profile holds one concern — its
beans and its own `application-postgres.yml` — and the environment profile just picks the set.

Without groups you either repeat `SPRING_PROFILES_ACTIVE=prod,postgres,kafka,json-logs` in every deployment, or copy
the same settings into each environment's file.

One environment name switches on a set of small, single-purpose profiles.

</details>

### A profile group defined in the jar — how to change it per deployment?
<details><summary>Show answer</summary>

A group is an ordinary property, `spring.profiles.group.prod`, holding a list. A stronger source replaces that
group's list whole; the other groups stay:

```
--spring.profiles.group.prod=postgres,json-logs        # kafka is dropped for this run
SPRING_PROFILES_GROUP_PROD=postgres,json-logs          # the same as an environment variable (unverified)
```

If deployments keep needing different sets, the group mixes features that should be chosen separately — activate
them [as a list](#how-do-you-activate-a-profile) instead.

A group is a list property: a stronger source redefines it.

</details>

### Profile file vs base file: which wins?
<details><summary>Show answer</summary>

```yaml
# application.yml
shop.mail.host: localhost

# application-prod.yml
shop.mail.host: smtp.acme.com
```

With `prod` active: `smtp.acme.com`. The profile file loads on top of the base file: keys it sets win, keys it doesn't
set fall through to the base. With several active profiles (`prod,eu`), the one listed last wins.

Location still comes first: a base `application.yml` *outside* the jar beats `application-prod.yml` *inside* it —
[the full order](3.2_Configuration.md#which-source-wins).

Profile file over base file, last profile over earlier ones — within the same location.

</details>

### How do you put several profiles in one file?
<details><summary>Show answer</summary>

```yaml
shop.mail.host: localhost              # always
---
spring.config.activate.on-profile: prod
shop.mail.host: smtp.acme.com          # only with prod
---
spring.config.activate.on-profile: test
shop.mail.host: fake-smtp
```

Each `---` starts a new document in the same file; `spring.config.activate.on-profile` makes a document apply only for
that profile. Later documents override earlier ones. In a `.properties` file the separator is `#---`.

Since Boot 2.4, `spring.config.activate.on-profile` replaces the old `spring.profiles` key inside documents.

`---` splits the file; `on-profile` decides when each part applies.

</details>
