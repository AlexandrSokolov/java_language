# Properties and Profiles

Where Boot's settings come from, how they reach the code, and how profiles switch them per environment.

### What governs Boot configuration?
<details><summary>Show answer</summary>

Settings live outside the code. Boot reads them from many places into one `Environment`, the code binds them into
fields or objects, and profiles switch whole sets of them per environment:

- [Sources](#where-can-configuration-come-from) — files, environment variables, the command line… looked up
  [in order](#how-does-the-environment-look-up-a-property), and [the higher one wins](#which-source-wins).
- [Binding](#configurationproperties-vs-value-which-when) — into `@Value` fields or typed `@ConfigurationProperties`
  objects, with [many accepted spellings of a name](#what-is-relaxed-binding).
- [Profiles](#what-does-a-profile-switch-on) — named sets of beans and properties, switched on per environment.

Trigger: *many sources → one ordered lookup → bound into typed objects → profiles pick the set.*

</details>

## Sources

### Where can configuration come from?
<details><summary>Show answer</summary>

The sources most apps meet:

- `application.properties` / `application.yml` — inside the jar, and next to it (`./` and `./config/`);
- profile files — `application-{profile}.yml`;
- environment variables — `SPRING_DATASOURCE_URL=...`;
- Java system properties — `-Dserver.port=8081`;
- command-line arguments — `--server.port=8081`;
- `SPRING_APPLICATION_JSON` — a whole JSON block in one variable;
- imported files and folders — `spring.config.import`, e.g. a folder of mounted secrets;
- `@PropertySource` on a configuration class, and defaults set in code.

Inside the jar, next to it, in the environment, on the command line — and
[the further outside, the stronger](#which-source-wins).

</details>

### How does the `Environment` look up a property?
<details><summary>Show answer</summary>

```java
String url = env.getProperty("spring.datasource.url");
```

The `Environment` holds an ordered list of `PropertySource`s — one per source: command-line arguments, system
properties, environment variables, each config file… `getProperty()` asks them one by one from the top and returns the
first value it finds.

So "which source wins" just means "which one sits higher in the list". `@Value`, `@ConfigurationProperties` and
`${...}` placeholders all go through this same lookup.

To see the list: `((ConfigurableEnvironment) env).getPropertySources()`, or the actuator endpoint `/actuator/env`,
which shows every source and the value each one holds.

One ordered list of sources; the first one that has the key wins.

</details>

### Which source wins?
<details><summary>Show answer</summary>

Highest first:

- command-line arguments (`--server.port=9000`)
- `SPRING_APPLICATION_JSON`
- Java system properties (`-D`)
- OS environment variables
- config files:
  - `application-{profile}` outside the jar
  - `application` outside the jar
  - `application-{profile}` inside the jar
  - `application` inside the jar
- `@PropertySource` on configuration classes
- defaults set in code

Test settings (`@TestPropertySource`, `@SpringBootTest(properties = ...)`) sit above all of these.

Note the config files: a plain `application.yml` *outside* the jar beats `application-prod.yml` *inside* it. The
classic surprise: a change in `application.yml` has no effect because an environment variable sets the same key.

The further outside the code a value is set, the stronger it is.

</details>

### How do you load config from outside the jar?
<details><summary>Show answer</summary>

- **Next to the jar** — `application.yml` in the working folder or in `./config/` is picked up automatically.
- **Other locations** — `spring.config.location` replaces the default locations; `spring.config.additional-location`
  adds to them. Both must be set from outside the files: command line, environment variable or system property.
- **Imports** — from inside a config file:

```yaml
spring:
  config:
    import:
      - optional:file:/etc/shop/shop.yml     # optional: no error if the file is missing
      - configtree:/run/secrets/             # a folder: each file name is a key, its content the value
```

An import without `optional:` fails startup when the file is missing.

Next to the jar is automatic; `spring.config.import` pulls in more, with `optional:` if it may be missing.

</details>

### How do you add your own property source?
<details><summary>Show answer</summary>

```java
public class VaultPropertiesPostProcessor implements EnvironmentPostProcessor {
  @Override
  public void postProcessEnvironment(ConfigurableEnvironment env, SpringApplication app) {
    Map<String, Object> secrets = loadFromVault();
    env.getPropertySources().addFirst(new MapPropertySource("vault", secrets));   // top of the list
  }
}
```

Register it in `META-INF/spring.factories`:

```properties
org.springframework.boot.env.EnvironmentPostProcessor=com.acme.config.VaultPropertiesPostProcessor
```

It runs before any bean is created, so its values are available everywhere — even to auto-configuration conditions.
Its position in the list decides its rank: `addFirst` beats everything, `addLast` loses to everything.

For a fixed file, `spring.config.import` is enough. `@PropertySource` also works, but it is added late — too late for
auto-configuration conditions and logging settings.

An `EnvironmentPostProcessor` adds a source before the context starts; where you add it decides its rank.

</details>

## Binding

### `@ConfigurationProperties` vs `@Value`: which when?
<details><summary>Show answer</summary>

```java
@Value("${shop.mail.host}") String host;                               // one value

@ConfigurationProperties("shop.mail")
record MailProperties(String host, int port, Duration timeout) { }    // a group of values, typed
```

|                 | `@Value`                                   | `@ConfigurationProperties`                       |
|-----------------|--------------------------------------------|--------------------------------------------------|
| Binds           | one value                                  | a group under a prefix                           |
| Types           | simple conversion                          | nested objects, lists, maps, `Duration`, `DataSize` |
| Validation      | no                                         | `@Validated`                                     |
| Name spellings  | only if you write the lowercase-dash name  | [all of them](#what-is-relaxed-binding)          |
| SpEL (`#{...}`) | yes                                        | no                                               |
| IDE completion  | no                                         | yes, with the metadata processor                 |

Default: `@ConfigurationProperties` for anything your code is configured with; `@Value` for a single one-off value or
when you need an expression.

One value or an expression → `@Value`; a group of settings → `@ConfigurationProperties`.

</details>

### What is relaxed binding?
<details><summary>Show answer</summary>

```java
@ConfigurationProperties("shop.mail")
record MailProperties(String smtpHost) { }
```

All of these set `smtpHost`:

```
shop.mail.smtp-host=...      # the canonical form: lowercase with dashes — use it in files and in code
shop.mail.smtpHost=...
shop.mail.smtp_host=...
SHOP_MAIL_SMTPHOST=...       # environment variable
```

Boot matches keys to fields ignoring case, dashes and underscores. Environment variables follow
[their own rule](#how-do-environment-variables-map-to-properties). The `prefix` itself must be in the canonical form.

One canonical name, many accepted spellings — so files, YAML and environment variables can each use their own style.

</details>

### How do environment variables map to properties?
<details><summary>Show answer</summary>

Environment variable names can't contain dots or dashes, so Boot maps them by rule:

- dots → `_`
- dashes removed
- all uppercase
- list index → `_0_`

```
spring.datasource.url        → SPRING_DATASOURCE_URL
shop.mail.smtp-host          → SHOP_MAIL_SMTPHOST
shop.servers[0].host         → SHOP_SERVERS_0_HOST
```

Trap: `SHOP_MAIL_SMTP_HOST` maps to `shop.mail.smtp.host` — a different key. It does not set `smtp-host`.

Underscore means dot, dashes vanish, everything uppercase.

</details>

### How does `@ConfigurationProperties` bind values?
<details><summary>Show answer</summary>

```java
@ConfigurationProperties("shop.mail")
public record MailProperties(String host, int port, Duration timeout, List<String> admins, Retry retry) {
  public record Retry(int attempts, Duration delay) { }
}
```

```yaml
shop:
  mail:
    host: smtp.acme.com
    port: 587
    timeout: 10s                  # Duration: 10s, 500ms, 2m
    admins: [ops@acme.com, dev@acme.com]
    retry:
      attempts: 3
      delay: 2s
```

Each key under the prefix goes to the field with the matching name; nested keys go to nested objects. The text is
converted to the field's type — numbers, `Duration`, `DataSize` (`10MB`), enums, lists, maps. A key with no field is
ignored; a value that can't be converted fails startup.

The class must be registered: `@ConfigurationPropertiesScan` on the application class, or
`@EnableConfigurationProperties(MailProperties.class)`. Then inject it like any bean.

Prefix plus field names make the keys; Boot converts the text to each field's type.

</details>

### How do you bind properties to a class you don't own?
<details><summary>Show answer</summary>

```java
@Bean
@ConfigurationProperties("shop.pool")
HikariDataSource shopPool() {
  return new HikariDataSource();      // Boot then calls its setters with the shop.pool.* values
}
```

```properties
shop.pool.jdbc-url=jdbc:postgresql://db/shop
shop.pool.maximum-pool-size=20
```

Put `@ConfigurationProperties` on the `@Bean` method. After the method returns the object, Boot binds the properties
to it through its setters. Any class with setters works, and it needs no annotation of its own.

Setters are required: the object is already created, so it can't be bound through its constructor.

Annotate the `@Bean` method — Boot fills the returned object through its setters.

</details>

### How do you make a properties class immutable?
<details><summary>Show answer</summary>

```java
@ConfigurationProperties("shop.mail")
public record MailProperties(String host, @DefaultValue("587") int port) { }
```

With a single constructor — a record, or a class with final fields — Boot binds through the constructor instead of
setters. No setters, so nothing can change the values after startup.

- `@DefaultValue` gives a value when the property is missing; otherwise you get `null`, or `0`/`false` for primitives.
- With several constructors, mark the one to use with `@ConstructorBinding`; with one, no annotation is needed (since
  Boot 3).
- Boot must create the object itself, so register it with `@ConfigurationPropertiesScan` or
  `@EnableConfigurationProperties` — not as a `@Component` or a `@Bean` method.

One constructor → Boot binds through it, and the object can't change after startup.

</details>

### How do you catch bad properties at startup?
<details><summary>Show answer</summary>

```java
@Validated
@ConfigurationProperties("shop.mail")
public record MailProperties(@NotBlank String host, @Min(1) @Max(65535) int port, @Valid Retry retry) { }
```

With `@Validated` and Bean Validation rules on the fields, Boot checks the values when it binds them. A bad or missing
value fails startup with a message naming the property and the rule — instead of failing at the first email, hours
later.

Needs a Bean Validation implementation on the classpath (`spring-boot-starter-validation`). Mark nested objects
`@Valid` so their rules are checked too.

`@Validated` turns a wrong setting into a startup failure instead of a failure hours later.

</details>

### What happens when a property is missing?
<details><summary>Show answer</summary>

- **`@Value("${shop.mail.host}")`** — no value in any source → startup fails because the placeholder can't be resolved.
  Give a default: `${shop.mail.host:localhost}`, or an empty one: `${shop.mail.host:}`.
- **`@ConfigurationProperties`** — the field just stays unset: `null`, `0`, or the default you gave. No error, unless
  you [validate it](#how-do-you-catch-bad-properties-at-startup).
- **`env.getProperty("x")`** — returns `null`; `env.getRequiredProperty("x")` throws.

`@Value` fails loudly at startup; `@ConfigurationProperties` stays silently empty — validate what is required.

</details>

## Profiles

### What does a profile switch on?
<details><summary>Show answer</summary>

```java
@Bean
@Profile("dev")
DataSource devDataSource() { /* in-memory H2 */ }
```

A profile is a name (`dev`, `prod`, `kafka`). When it is active, it switches on two things:

- **beans** marked `@Profile("dev")`;
- **its property file** — `application-dev.yml` loads on top of `application.yml`.

With no profile active, the profile `default` is active. `@Profile` takes expressions: `@Profile("!prod")`,
`@Profile("prod & eu")`.

A profile is a name that switches on its beans and its property file.

</details>

### How do you activate a profile?
<details><summary>Show answer</summary>

Set `spring.profiles.active` from any configuration source:

```
SPRING_PROFILES_ACTIVE=prod          # environment variable — the usual way in containers
-Dspring.profiles.active=prod        # system property
--spring.profiles.active=prod        # command-line argument
```

In tests: `@ActiveProfiles("test")`.

- Several at once: `prod,eu` — on a conflict, the later one wins.
- Setting it in `application.yml` works, but only as a default: any outside source overrides it.
- Setting it inside a profile-specific file is an error — a profile can't activate profiles.

`spring.profiles.active`, set from outside the jar — usually an environment variable.

</details>

### Profile file vs base file: which wins?
<details><summary>Show answer</summary>

```yaml
# application.yml
shop.mail.host: localhost

# application-prod.yml
shop.mail.host: smtp.acme.com
```

With `prod` active: `smtp.acme.com`. The profile file loads on top of the base file: keys it sets win, keys it doesn't
set fall through to the base. With several active profiles (`prod,eu`), the one listed last wins.

Location still comes first: a base `application.yml` *outside* the jar beats `application-prod.yml` *inside* it —
[the full order](#which-source-wins).

Profile file over base file, last profile over earlier ones — within the same location.

</details>

### How do you put several profiles in one file?
<details><summary>Show answer</summary>

```yaml
shop.mail.host: localhost              # always
---
spring.config.activate.on-profile: prod
shop.mail.host: smtp.acme.com          # only with prod
---
spring.config.activate.on-profile: test
shop.mail.host: fake-smtp
```

Each `---` starts a new document in the same file; `spring.config.activate.on-profile` makes a document apply only for
that profile. Later documents override earlier ones. In a `.properties` file the separator is `#---`.

Since Boot 2.4, `spring.config.activate.on-profile` replaces the old `spring.profiles` key inside documents.

`---` splits the file; `on-profile` decides when each part applies.

</details>

### What are profile groups for?
<details><summary>Show answer</summary>

```yaml
spring:
  profiles:
    group:
      prod: [postgres, kafka, json-logs]
      dev: [h2, local-queue]
```

Activate `prod` and Boot also activates `postgres`, `kafka` and `json-logs`. Each small profile holds one concern — its
beans and its own `application-postgres.yml` — and the environment profile just picks the set.

Without groups you either repeat `SPRING_PROFILES_ACTIVE=prod,postgres,kafka,json-logs` in every deployment, or copy
the same settings into each environment's file.

One environment name switches on a set of small, single-purpose profiles.

</details>

### When should you not use a profile?
<details><summary>Show answer</summary>

The common first habit: one profile per environment holding all its values — `application-dev.yml`,
`application-qa.yml`, `application-prod.yml`, each with its own URLs, passwords and pool sizes.

Why that is not the final design:

- the jar carries every environment's settings, secrets included;
- a new environment means a new build;
- profiles multiply (`prod-eu`, `prod-us`, `prod-eu-canary`…), and `@Profile` checks spread through the code.

Better: use profiles for differences in *behaviour* — which beans exist (real or fake mail sender, Kafka or an
in-memory queue). Values that differ per environment — URLs, passwords, sizes — come from outside the jar:
environment variables, mounted config, a config server.

Does the setting change which code runs? → profile. Only a value? → an outside property.

</details>

## Optional

### How do you keep secrets out of config files?
<details><summary>Show answer</summary>

Never commit a secret in `application.yml`. The jar holds only the key; the value arrives from outside at startup:

- **Environment variable** — `SPRING_DATASOURCE_PASSWORD=...`. Simple, but anything that can read the process
  environment can read it.
- **Mounted files** — `spring.config.import=configtree:/run/secrets/`: each file name is a key, its content the value.
  This is how Kubernetes secrets are usually mounted.
- **A secret store** — Vault or a cloud secret manager, through Spring Cloud or an
  [own property source](#how-do-you-add-your-own-property-source).

The actuator endpoints `/actuator/env` and `/actuator/configprops` hide values by default since Boot 3 — keep it
that way.

The jar holds the key names; the environment holds the secrets.

</details>
