# Configuration

Where settings come from, who owns them, which one wins, and how to lay out the config files.

### Configuring an app — which questions come first?
<details><summary>Show answer</summary>

Before picking a file or a key, answer for each setting:

- **Owner** — [the app or the environment](#a-setting--owned-by-the-app-or-by-the-environment)?
- **Change point** — [build, deploy, launch or runtime](#config-sources--options)?
- **Precedence** — [which source wins](#which-source-wins) when the key is set in several places?
- **Override** — how to [change a value baked into the jar](#a-value-baked-into-the-jar-is-wrong-for-one-environment--options)
  without a rebuild?
- **Merge or replace** — [what is combined, what is replaced](#same-key-in-several-sources--what-is-merged-what-is-replaced)?
- **Secrets** — may this value [be in a file at all](#how-do-you-keep-secrets-out-of-config-files)?
- **File layout** — [how to split the files](#organizing-config-files--which-decisions) and
  [which traps to avoid](#config-files--which-traps).

Owner first: it decides where the value lives, and the rest follows.

</details>

## Sources

### A setting — owned by the app or by the environment?
<details><summary>Show answer</summary>

Ask who decides the value.

- **The app** — what the code needs to work the same everywhere: retry rules, serializers, timeouts derived from how
  the code behaves. Lives in `application.yml` inside the jar, versioned and tested with the code.
- **The environment** — what depends on where the app runs: ports, URLs, broker addresses, credentials, topic names,
  number of consumer threads. Decided by whoever runs the system (compose, K8s, IDE); comes from outside — environment
  variables, mounted files — with [no default in the jar](#kafka_bootstrap_serverslocalhost9092--what-can-go-wrong).

Test: would the value differ between two deployments of the same build? Then it is the environment's.

Same in every deployment → the app's, in the jar; differs per deployment → the environment's, from outside.

</details>

### Config sources — options?
<details><summary>Show answer</summary>

Split by when can each change:
- **Build** — baked into the jar; change = rebuild and redeploy:
  - defaults in code — `SpringApplication.setDefaultProperties(...)`, `@Value("${server.port:8080}")`; the last
    fallback, so the app still starts when nobody set the key;
  - `@PropertySource` on a classpath file — pulls in one extra file tied to a config class, e.g. a library's own
    settings;
  - `application.yml` inside the jar — the base values for every environment, versioned and tested with the code.
- **Deploy** — files placed outside the jar; change = edit the file, restart, no rebuild:
  - `application.yml` in `./` or `./config/` next to the jar — per-server values on a plain VM install;
  - `spring.config.import` — extra files or folders, e.g. K8s ConfigMaps and Secrets mounted as files; secrets come
    in from outside and are never baked into the image.
- **Launch** — values passed to the process; change = restart with other values, no file to edit:
  - environment variables — `SPRING_DATASOURCE_URL=...`; the usual way in Docker/K8s, one flat string per key;
  - Java system properties — `-Dserver.port=8081`; set per JVM, often through `JAVA_OPTS` in a start script;
    shows in the process list (`ps`), so no secrets here;
  - `SPRING_APPLICATION_JSON` — a whole JSON block in one variable; for lists and nested values that flat variables
    carry badly;
  - command-line arguments — `--server.port=8081`; a quick override for one run; also shows in `ps`.
- **Running** — plain Boot reads nothing above again; config is loaded once, at start. Changing values in a running
  app needs extra tooling, e.g. Spring Cloud with a config server and `@RefreshScope` beans.

Profile files (`application-{profile}.yml`) are not a separate place: they sit in the jar or next to it and change like
any file there. Which one is used is picked by
[`spring.profiles.active`](3.3_Profiles.md#how-do-you-activate-a-profile), usually set at launch.

Build → deploy → launch: the later a value is set, the [stronger it is](#which-source-wins).

</details>

### Which source wins?
<details><summary>Show answer</summary>

Highest first — [build → deploy → launch](#config-sources--options), reversed, with tests on top:

- **Tests** — `@TestPropertySource` > `@DynamicPropertySource` > `@SpringBootTest(properties = ...)`
- **Launch** — command-line args > `SPRING_APPLICATION_JSON` > `-D` system properties > env variables
- **Deploy** — config files outside the jar
- **Build** — config files inside the jar > `@PropertySource` > defaults in code

Between config files: outside beats inside; at the same place, `application-{profile}` beats `application`. So a plain
`application.yml` outside the jar beats `application-prod.yml` inside it. Imported files have
[their own order](#same-key-in-two-imported-files--which-wins).

The classic surprise: you change `application.yml` and nothing happens, because an env variable sets the same key.
[Check who wins](#how-does-the-environment-look-up-a-property).

The later a value is set, the stronger it is.

</details>

### How does the Environment look up a property?
<details><summary>Show answer</summary>

The `Environment` holds an ordered list of `PropertySource`s — CLI args, env variables, config files… `getProperty()`
asks them top to bottom and returns the first match. The list is [the same order](#which-source-wins), strongest on
top — [read from the other end](#precedence-first-found-vs-last-wins--difference).

**Override:** no need to edit the original — set the same key in a source that sits [higher](#which-source-wins).
E.g. a value baked into `application.yml` in the jar loses to an env variable (`SPRING_DATASOURCE_URL`) or a CLI arg
(`--spring.datasource.url`).

**Change the order?** Boot sets it at startup. Code can reorder it (`MutablePropertySources.addFirst(...)` in an
`EnvironmentPostProcessor`), but you rarely need to — pick a higher source instead.

**Verify:** `/actuator/env/{key}` lists the sources in order and shows which one won. The endpoint must be exposed over
HTTP, and since Boot 3 values are masked (`******`) by default — the source names are enough.

First found wins — so put your value in a source above the one that holds it now.

</details>

### Precedence: first-found vs last-wins — difference?
<details><summary>Show answer</summary>

None in the result — they are the same order, read from opposite ends.

- **Last wins** — how the docs describe loading: sources are read from weakest to strongest, and each later one
  overwrites the keys set before it.
- **First found wins** — how the `Environment` is built: Boot puts each later-loaded source *above* the earlier ones,
  so the list is strongest first, and `getProperty()` stops at the first match.

Use one at a time: to predict which value wins, think last-wins — [build → deploy → launch](#config-sources--options);
to debug, think first-found — `/actuator/env` lists the sources top-down.

Weakest-to-strongest overwriting and strongest-first lookup give the same value.

</details>

### A value baked into the jar is wrong for one environment — options?
<details><summary>Show answer</summary>

Leave the jar as it is and set the same key in a [stronger source](#which-source-wins):

- **Environment variable** — `SHOP_MAIL_HOST=smtp.eu.acme.com`; the usual way in containers.
- **Mounted file** — via `spring.config.import` or `spring.config.additional-location`; for many keys at once, e.g. a
  K8s ConfigMap.
- **`application.yml` next to the jar** — on a plain VM install.
- **Command-line argument** — `--shop.mail.host=...`; for a one-off run.

Only that key changes; the other keys from the jar stay — [Boot merges by key](#same-key-in-several-sources--what-is-merged-what-is-replaced).
Check the result with `/actuator/env/shop.mail.host`.

If the value differs in every environment, it does not belong in the jar —
[the environment owns it](#a-setting--owned-by-the-app-or-by-the-environment).

Same key, stronger source, no rebuild.

</details>

### Same key in several sources — what is merged, what is replaced?
<details><summary>Show answer</summary>

Boot merges by key, not by file: every source is a flat set of keys, and each key is looked up on its own.

```yaml
# application.yml in the jar
shop.mail:
  host: localhost
  port: 587
  admins: [ops@acme.com, dev@acme.com]
  headers: { x-app: shop, x-team: core }
```

```
SHOP_MAIL_HOST=smtp.acme.com
SHOP_MAIL_ADMINS_0=boss@acme.com
SHOP_MAIL_HEADERS_XENV=prod
```

- **Single values** — the strongest source wins for that key; the rest of the tree stays. Result: `host` from env,
  `port` from the jar. A file never replaces another file's tree.
- **Lists** — replaced whole by the strongest source that sets any element. Result: `admins = [boss@acme.com]` —
  `ops@` and `dev@` are gone.
- **Maps** — merged by map key across sources; the same map key → the strongest wins. Result: `headers` has
  `x-app`, `x-team` and `xenv`.

What can be replaced as a whole is the set of places Boot reads files from —
[`spring.config.location`](#springconfiglocation-vs-additional-location-vs-import--differences).

Keys and map entries merge; a list is replaced whole.

</details>

### Removing a property set by a lower source — options?
<details><summary>Show answer</summary>

There is no way to delete a key: a stronger source can only give it another value.

- **Empty value** — `SHOP_MAIL_HOST=` sets an empty string; the code must treat it as "off".
- **`null` in `SPRING_APPLICATION_JSON`** — counts as missing, so the value from the lower source comes through.
- **An explicit switch** — `shop.mail.enabled=false`, read by the code or by `@ConditionalOnProperty`.

The real fix is upstream: don't put a value into a low source if some environment must not have it — let that
environment [provide it](#a-setting--owned-by-the-app-or-by-the-environment).

Overriding replaces a value; nothing removes it.

</details>

### `SPRING_APPLICATION_JSON` — effect on existing config?
<details><summary>Show answer</summary>

It adds one property source with the JSON split into flat keys. It does not replace the config tree.

```
SPRING_APPLICATION_JSON='{"shop":{"mail":{"host":"smtp.eu.acme.com","admins":["ops@acme.com"]}}}'
```

→ `shop.mail.host` and `shop.mail.admins[0]`. `port`, `timeout` and everything else from `application.yml` stay.

- **Per key** — each leaf overrides its own key, like any [stronger source](#which-source-wins);
- **Lists** — [replaced whole](#same-key-in-several-sources--what-is-merged-what-is-replaced), like from any source;
- **`null`** — counts as missing; it [can't remove](#removing-a-property-set-by-a-lower-source--options) a value;
- **Precedence** — above env variables and `-D`, below command-line args.

Also accepted as `-Dspring.application.json=...` or `--spring.application.json=...`.

One JSON block, split into keys, each key overriding on its own.

</details>

### How do you load config from outside the jar?
<details><summary>Show answer</summary>

- **Next to the jar** — `application.yml` in the working folder or in `./config/` is picked up automatically.
- **Other locations** — `spring.config.location` replaces the default locations; `spring.config.additional-location`
  adds to them. Both must be set from outside the files: command line, environment variable or system property.
  [The difference matters](#springconfiglocation-vs-additional-location-vs-import--differences).
- **Imports** — from inside a config file:

```yaml
spring:
  config:
    import:
      - optional:file:/etc/shop/shop.yml     # optional: no error if the file is missing
      - configtree:/run/secrets/             # a folder: each file name is a key, its content the value
```

An import without `optional:` fails startup when the file is missing.

Next to the jar is automatic; `spring.config.import` pulls in more, with `optional:` if it may be missing.

</details>

### `spring.config.location` vs `additional-location` vs `import` — differences?
<details><summary>Show answer</summary>

- **`spring.config.location`** — **replaces** the default locations. `application.yml` inside the jar and next to it
  are no longer read at all — the classic trap.
- **`spring.config.additional-location`** — **adds** locations to the defaults; its files beat the default ones.
- **`spring.config.import`** — written **inside** a config file; pulls extra files into that file; the imported
  values beat the file that imports them.

`location` and `additional-location` are read before any file, so they must come from outside: command line,
environment variable or system property. A folder location ends with `/`.

Missing files: the default locations are optional. Locations you name explicitly — in any of the three — fail startup
when missing, unless prefixed `optional:` (or `spring.config.on-not-found=ignore` for all).

`location` replaces, `additional-location` adds, `import` pulls in from inside a file.

</details>

## Secrets

### How do you keep secrets out of config files?
<details><summary>Show answer</summary>

Never commit a secret in `application.yml`. The jar holds only the key; the value arrives from outside at startup:

- **Environment variable** — `SPRING_DATASOURCE_PASSWORD=...`. Simple, but anything that can read the process
  environment can read it.
- **Mounted files** — `spring.config.import=configtree:/run/secrets/`: each file name is a key, its content the value.
  This is how Kubernetes secrets are usually mounted.
- **A secret store** — Vault or a cloud secret manager, through Spring Cloud.

The actuator endpoints `/actuator/env` and `/actuator/configprops` hide values by default since Boot 3 — keep it
that way.

The jar holds the key names; the environment holds the secrets.

</details>

## Organizing files

### Organizing config files — which decisions?
<details><summary>Show answer</summary>

- **External vs internal** — [one file lists what the environment must provide](#values-the-environment-must-provide--where-do-you-keep-them);
  the rest refers to it.
- **Defaults** — [none for environment values](#kafka_bootstrap_serverslocalhost9092--what-can-go-wrong), so a
  missing one fails startup.
- **Split** — [one file per feature](#one-large-applicationyml--how-to-split-it), each key in exactly one file.
- **The exception** — [values tied by one rule](#timeouts-spread-across-feature-files--problem) live together, even
  across features.
- **Import order** — [which imported file wins](#same-key-in-two-imported-files--which-wins) on a shared key.

Outside separate from inside, one file per feature, one key in one place.

</details>

### Config files — which traps?
<details><summary>Show answer</summary>

- **Shadowed main config** — [a test `application.yaml`](#test-values-in-srctestresourcesapplicationyaml--what-can-go-wrong)
  hides the main one.
- **Duplicate YAML keys** — [a second `spring:` block](#a-second-spring-block-in-the-same-yaml-file--what-happens) in
  one file.
- **No Boot property** — [a setting Boot can't set](#a-setting-with-no-boot-property--where-does-its-value-go) ends up
  hardcoded in Java.
- **Invisible client defaults** — [values you never set](#kafka-client-settings-you-never-set--how-do-you-see-their-values)
  are still in effect.
- **Hardcoded names in tests** — [the test checks a different setup](#topic-name-hardcoded-in-a-test--what-can-go-wrong)
  than the code runs.

Each trap passes review and fails later — in tests, at startup or in production.

</details>

### Values the environment must provide — where do you keep them?
<details><summary>Show answer</summary>

**Environment contract:** one file lists every value the environment must provide, each taken from an environment
variable with no default. The other files refer to these entries, never to environment variables directly.

```yaml
# settings/env.yaml
env:
  server:
    port: ${SERVER_PORT}
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP_SERVERS}
```

```yaml
# settings/kafka.yaml
spring.kafka.bootstrap-servers: ${env.kafka.bootstrap-servers}
```

`env` is just a prefix you choose, not a Boot namespace. What it gives:

- one place to read what a deployment must set;
- internal files hold no environment variable names;
- renaming a variable touches one line.

An entry fails startup only when something reads it *(unverified)* — keep only used entries in the contract.

What comes from outside is listed in one file; everything else points to it.

</details>

### `${KAFKA_BOOTSTRAP_SERVERS:localhost:9092}` — what can go wrong?
<details><summary>Show answer</summary>

**Silent fallback:** the variable is forgotten in production, the app starts anyway and connects to `localhost` — or
to a shared dev broker. The failure shows up late and far from its cause.

Without a default — `${KAFKA_BOOTSTRAP_SERVERS}` — startup fails at once with `Could not resolve placeholder`.

Defaults belong only to values [the app owns](#a-setting--owned-by-the-app-or-by-the-environment). Values for local
runs come from the local setup — an IDE run config, a `.env` file, a compose file — not from a default in the jar.

An environment value without a default fails loudly at startup instead of quietly in production.

</details>

### One large `application.yml` — how to split it?
<details><summary>Show answer</summary>

**Split by concern:** one file per feature, imported from `application.yml`.

```yaml
# application.yml — the service's identity and the list of its files
spring:
  application.name: login-processing-service
  config:
    import:
      - classpath:settings/env.yaml
      - classpath:settings/kafka.yaml
      - classpath:settings/http-client.yaml
      - classpath:settings/oauth2-client.yaml
      - classpath:settings/actuator.yaml
```

A file holds all keys of its feature, whatever the namespace: `kafka.yaml` has both `spring.kafka.*` and
`app.kafka.*`. Each key lives in exactly one file.

What it gives: a feature file moves to another project with the feature and is deleted with it; a change to one
feature touches one file.

One file per feature, holding every key that feature needs.

</details>

### Timeouts spread across feature files — problem?
<details><summary>Show answer</summary>

**Values tied by one rule:** some values only make sense together. The worst case per record must fit
`max.poll.interval.ms`; the listener's shutdown timeout must cover it; Spring's shutdown phase must exceed that; the
container's stop grace period must exceed Spring's. Spread across feature files, the rule is invisible, and one change
breaks it silently.

Put them in one file, `timeouts.yaml`, with the rule on top; feature files point to it:

```text
record   = attempts x (connect + read) + backoff        = 37.25s
poll     = max-poll-records x record < max.poll.interval.ms
shutdown : record < listener timeout < shutdown phase < stop grace period
```

This is the exception to [split by concern](#one-large-applicationyml--how-to-split-it): grouped by the rule, not by
the feature. Each key still lives in one file.

Values bound by one formula live in one file, with the formula on top.

</details>

### Same key in two imported files — which wins?
<details><summary>Show answer</summary>

- An imported file beats the file that imports it.
- In an import list, a later entry beats an earlier one.

So `application.yml` can't override a value its own import sets — that key belongs in the imported file. Files outside
the jar and launch values still beat all of them — [the full order](#which-source-wins).

With each key in exactly one file, the order never matters — that is the point of
[the split](#one-large-applicationyml--how-to-split-it).

Imported beats importer, later beats earlier — or keep each key in one file.

</details>

### Test values in `src/test/resources/application.yaml` — what can go wrong?
<details><summary>Show answer</summary>

**Shadowed main config:** the test file has the same name in the same classpath location as the main one. The
classpath returns the test copy first, so the main `application.yaml` is not read at all — tests run with only the
test keys.

Put it in `src/test/resources/config/application.yaml` instead: `classpath:/config/` is a different location, loaded
on top of the main file, so it holds only the differences.

The other way: `application-test.yaml` and `@ActiveProfiles("test")`.

Same name, same place → replaced; another place → merged on top.

</details>

### A second `spring:` block in the same YAML file — what happens?
<details><summary>Show answer</summary>

**Duplicate keys:** Boot's YAML loader rejects a key that repeats at the same level — startup fails with a
duplicate-key error *(unverified)*. Other YAML tools often keep the last block silently, so the file can look fine in
an editor.

Add new keys inside the existing block. A really separate part goes into its own file or after a `---`.

One key, one block — per level, per file.

</details>

### A setting with no Boot property — where does its value go?
<details><summary>Show answer</summary>

**No Boot property:** keep the value in YAML under your own prefix, next to related values, and apply it in a
customizer bean — not as a constant in Java.

```java
@Bean
ContainerCustomizer<Object, Object, ConcurrentMessageListenerContainer<Object, Object>> shutdownTimeout(
    @Value("${app.kafka.listener-shutdown-timeout}") Duration timeout) {
  return container -> container.getContainerProperties().setShutdownTimeout(timeout.toMillis());
}
```

Boot applies a `ContainerCustomizer` bean to the listener containers it creates *(unverified)*. The value stays
visible in the config files and can be overridden from outside like any other.

No property → own key in YAML, applied by a customizer.

</details>

### Kafka client settings you never set — how do you see their values?
<details><summary>Show answer</summary>

**Invisible client defaults:** a value you don't set comes from defaults inside the `kafka-clients` code — not from
your files or Boot's docs, and `/actuator/env` doesn't show it.

At startup the client logs every value in effect, at INFO: the `ConsumerConfig values:` and `ProducerConfig values:`
blocks. Read them once per setup.

If a calculation depends on a default (e.g. `max.poll.interval.ms`), set it explicitly so the dependency is visible.

The startup log shows what the client really runs with.

</details>

### Topic name hardcoded in a test — what can go wrong?
<details><summary>Show answer</summary>

**Hardcoded names in tests:** the code reads `${app.kafka.topics.customer-login}`, the test sends to
`"customer-login"`. Rename the topic in config and the test still uses the old name: it tests a different setup.

Read the same property in the test:

```java
@Value("${app.kafka.topics.customer-login}")
String customerLoginTopic;
```

Code and tests read names from the same config.

</details>
