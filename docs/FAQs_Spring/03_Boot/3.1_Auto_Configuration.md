# Auto-Configuration

How Spring Boot configures beans on its own.

### What governs auto-configuration?
<details><summary>Show answer</summary>

Boot ships hundreds of ready-made `@Configuration` classes. At startup it lists them, checks each one's conditions
against your classpath, your beans and your properties, and keeps only the ones that match:

- [How they're found](#how-does-boot-find-auto-configurations) — a list file inside each jar, read because
  [`@SpringBootApplication`](#what-does-springbootapplication-switch-on) switches it on.
- [When they run](#when-do-auto-configurations-run) — after your own configuration, so they can see your beans.
- [Whether each one applies](#what-decides-whether-an-auto-configuration-applies) — conditions on classes, beans and
  properties.
- [What brings them in](#what-is-a-starter) — a starter puts libraries on the classpath, and that flips the class
  conditions.
- [What actually happened](#how-do-you-see-what-boot-configured-and-why) — the condition report.
- [Your own](#how-do-you-write-your-own-auto-configuration) — the same mechanism for your own library.

Trigger: *list file → after your config → conditions decide → starters flip them → the report shows the result.*

</details>

## How it's found

### What does `@SpringBootApplication` switch on?
<details><summary>Show answer</summary>

```java
@SpringBootApplication
public class ShopApplication {
  public static void main(String[] args) { SpringApplication.run(ShopApplication.class, args); }
}
```

It is three annotations in one:

- `@SpringBootConfiguration` — this class is a `@Configuration` (and the one `@SpringBootTest` looks for);
- `@ComponentScan` — scan this class's package and everything below it;
- `@EnableAutoConfiguration` — load Boot's auto-configurations.

So the class belongs in the root package: components outside that package tree are not scanned.

Configuration class + scan from here down + auto-configuration.

</details>

### How does Boot find auto-configurations?
<details><summary>Show answer</summary>

Each jar that offers auto-configurations contains this file:

`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`

with one class name per line:

```
com.acme.mail.MailAutoConfiguration
com.acme.mail.MailHealthAutoConfiguration
```

`@EnableAutoConfiguration` reads this file from every jar on the classpath and collects the names.

Before Boot 2.7 the list lived in `META-INF/spring.factories`, a shared file also used for many other kinds of
extensions. Boot 2.7 added the separate file; Boot 3.0 stopped reading auto-configurations from `spring.factories`. A
library that still registers only there is silently ignored on Boot 3.

Being listed only makes a class a candidate — [its conditions](#what-decides-whether-an-auto-configuration-applies)
decide whether it applies.

One list file per jar; listed means candidate, not applied.

</details>

### When do auto-configurations run?
<details><summary>Show answer</summary>

```java
@Configuration
class DbConfig {
  @Bean
  DataSource dataSource() { /* ... */ }               // your bean: registered first
}

// inside Boot's DataSource auto-configuration (simplified):
@Bean
@ConditionalOnMissingBean(DataSource.class)           // sees yours → backs off
DataSource dataSource(DataSourceProperties props) { /* ... */ }
```

Boot processes your configuration first — scanned components, your `@Configuration` classes and `@Bean` methods —
and only then the auto-configurations. So when an auto-configuration asks "is there already a `DataSource` bean?", your
bean is already registered.

This order is what makes [defining your own bean replace Boot's](#how-do-you-replace-a-bean-boot-creates).

Your config first, Boot's after — so Boot can step aside.

</details>

## Conditions

### What decides whether an auto-configuration applies?
<details><summary>Show answer</summary>

```java
@AutoConfiguration
@ConditionalOnClass(DataSource.class)                          // a library is on the classpath
@ConditionalOnProperty(name = "shop.db.enabled", matchIfMissing = true)   // a property allows it
public class ShopDbAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean                                    // you haven't defined one yourself
  ShopDb shopDb(DataSource ds) { return new ShopDb(ds); }
}
```

A condition on the class decides for the whole class; on a `@Bean` method, for that one bean. Three questions:

- **Is the library here?** — `@ConditionalOnClass` / `@ConditionalOnMissingClass`. It
  [doesn't crash on a missing class](#how-does-conditionalonclass-avoid-a-missing-class-crash).
- **Is there already a bean?** — `@ConditionalOnBean` / `@ConditionalOnMissingBean`. This is how you
  [replace a Boot bean](#how-do-you-replace-a-bean-boot-creates), and why these conditions are
  [risky in your own config](#why-are-bean-conditions-risky-in-your-own-config).
- **Does a property allow it?** — `@ConditionalOnProperty`, to
  [switch a feature on or off](#how-do-you-switch-a-feature-on-with-a-property).

More exist (web application, resource present, cloud platform). Class conditions are checked earlier than bean
conditions — [when each is checked](#class-vs-bean-conditions-when-are-they-checked). And you can
[turn one auto-configuration off](#how-do-you-turn-off-one-auto-configuration) entirely.

Classpath, existing beans, properties — every condition must say yes.

</details>

### Class vs bean conditions: when are they checked?
<details><summary>Show answer</summary>

- **Class conditions** (`@ConditionalOnClass`) — checked early, while Spring reads the configuration classes. If one
  fails, the whole class is skipped before any of its methods are looked at. Boot even pre-checks them from a metadata
  file built at compile time, without loading the auto-configuration class. They depend only on the classpath, so the
  answer never changes during startup.
- **Bean conditions** (`@ConditionalOnBean` / `@ConditionalOnMissingBean`) — checked later, while bean definitions
  are being registered. The answer depends on which beans are registered *so far*, so order matters.

That is why auto-configurations put class conditions on the class (cheap, skips everything) and bean conditions on
`@Bean` methods, and why bean conditions are
[risky outside auto-configuration](#why-are-bean-conditions-risky-in-your-own-config).

Class conditions read the classpath — early and fixed; bean conditions read what is registered so far — late and
order-dependent.

</details>

### How does `@ConditionalOnClass` avoid a missing-class crash?
<details><summary>Show answer</summary>

```java
@AutoConfiguration
@ConditionalOnClass(KafkaTemplate.class)      // Kafka not on the classpath → no NoClassDefFoundError
public class ShopKafkaAutoConfiguration { /* ... */ }
```

Normally, code that mentions a missing class fails when its class is loaded. Here Spring reads the annotation from the
class file's bytes (with ASM) instead of loading the class, so `KafkaTemplate.class` is only a name it checks against
the classpath. If the name is missing, the configuration class is skipped and never loaded.

This works for the annotation on a class. On a `@Bean` method it doesn't protect you: the JVM loads the enclosing class
first, and a missing type in the method's signature fails then. Two fixes:

- move such beans into a nested `@Configuration` class with its own `@ConditionalOnClass` — what Boot itself does;
- use the string form, which is safe anywhere:
  `@ConditionalOnClass(name = "org.springframework.kafka.core.KafkaTemplate")`.

On a class, the condition reads the class as a name, without loading it; on a method, put it in a nested class.

</details>

### How do you replace a bean Boot creates?
<details><summary>Show answer</summary>

```java
@Configuration
class DbConfig {
  @Bean
  DataSource dataSource() {                     // Boot's DataSource auto-configuration sees it and backs off
    HikariDataSource ds = new HikariDataSource();
    ds.setJdbcUrl("jdbc:postgresql://db/shop");
    return ds;
  }
}
```

Define your own bean of the same type. Boot's bean is guarded by `@ConditionalOnMissingBean`, and your config is
[processed first](#when-do-auto-configurations-run), so Boot sees yours and doesn't create its own. Everything that
injects `DataSource` now gets yours.

The catch: Boot's bean read the `spring.datasource.*` properties; yours doesn't, unless you
[bind them yourself](3.2_Properties_and_Profiles.md#how-do-you-bind-properties-to-a-class-you-dont-own). When you only
want to change a detail, look for a property or a customizer bean first — replacing loses all of Boot's setup for that
bean.

Your bean of the same type wins, because Boot checks for it after your config is in.

</details>

### Why are bean conditions risky in your own config?
<details><summary>Show answer</summary>

```java
@Configuration
class CacheConfig {
  @Bean
  @ConditionalOnMissingBean(CacheManager.class)   // in YOUR config: the result depends on scan order
  CacheManager fallbackCacheManager() { return new ConcurrentMapCacheManager(); }
}
```

A bean condition sees only the beans registered *so far*. Among your own configuration classes, that order comes from
scanning and imports — nothing you control. If another of your classes registers a `CacheManager` later, this
condition has already answered "missing", and you end up with two.

In auto-configurations it is safe: they run [after all your config](#when-do-auto-configurations-run), and among
themselves their order is [set on purpose](#how-do-you-order-auto-configurations). Hence Boot's own rule: use
`@ConditionalOnBean` and `@ConditionalOnMissingBean` only in auto-configuration classes.

A bean condition answers "so far"; only an auto-configuration knows what "so far" includes.

</details>

### How do you switch a feature on with a property?
<details><summary>Show answer</summary>

```java
@AutoConfiguration
@ConditionalOnProperty(prefix = "shop.audit", name = "enabled", havingValue = "true", matchIfMissing = false)
public class AuditAutoConfiguration { /* ... */ }
```

- `shop.audit.enabled=true` → applies.
- `havingValue` — the value that turns it on. Without it, any value except `false` matches.
- `matchIfMissing` — what happens when the property is not set at all: `true` means on by default; `false` (the
  default) means off until someone sets it.

The property can come from any [configuration source](3.2_Properties_and_Profiles.md#where-can-configuration-come-from)
— a file, the environment variable `SHOP_AUDIT_ENABLED=true`, the command line.

`havingValue` says which value turns it on; `matchIfMissing` says what "not set" means.

</details>

### How do you turn off one auto-configuration?
<details><summary>Show answer</summary>

```java
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
public class ShopApplication { /* ... */ }
```

Or without recompiling, from any configuration source:

```properties
spring.autoconfigure.exclude=<full class name of the auto-configuration>
```

`excludeName` takes the class name as a string, for a class that isn't on your compile classpath.

Excluding removes the whole auto-configuration class and every bean in it — it never runs. Before excluding, check
whether a property switches the feature off, and find the exact class name in the
[condition report](#how-do-you-see-what-boot-configured-and-why).

Exclude names the whole auto-configuration; it never runs.

</details>

## Starters

### What is a starter?
<details><summary>Show answer</summary>

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-jdbc</artifactId>   <!-- HikariCP, Spring JDBC, ... -->
</dependency>
```

A dependency with no code — just a build file that pulls in a set of libraries that work together. Their versions come
from Boot's dependency management, so they fit each other.

The starter itself configures nothing. It puts the libraries on the classpath; the auto-configurations whose
[class conditions](#class-vs-bean-conditions-when-are-they-checked) look for those libraries then switch on.

A starter brings jars; the jars flip class conditions; the auto-configuration does the work.

</details>

## Debugging

### How do you see what Boot configured, and why?
<details><summary>Show answer</summary>

Start with `--debug` (or set `debug=true`). At startup Boot prints the condition evaluation report, roughly:

```
Positive matches:
   DataSourceAutoConfiguration matched:
      - @ConditionalOnClass found required classes ... (OnClassCondition)

Negative matches:
   MongoAutoConfiguration:
      Did not match:
         - @ConditionalOnClass did not find required class 'com.mongodb.client.MongoClient' (OnClassCondition)
```

- **Positive matches** — applied, with the condition that said yes.
- **Negative matches** — skipped, with the reason. A bean you expected is missing → find its auto-configuration here and
  read why.
- **Exclusions** — turned off on purpose.

In a running app, the actuator endpoint `/actuator/conditions` returns the same report as JSON.

The condition report lists every auto-configuration with the reason it ran or didn't.

</details>

## Your own

### How do you write your own auto-configuration?
<details><summary>Show answer</summary>

```java
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
  @Bean
  @ConditionalOnMissingBean
  AuditClient auditClient(AuditProperties props) {
    return new AuditClient(props.url());
  }
}
```

Register it with one line in
`src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`:

```
com.acme.audit.autoconfigure.AuditAutoConfiguration
```

Rules:

- `@AutoConfiguration`, not `@Configuration` — it is a `@Configuration` with
  [`proxyBeanMethods = false`](../01_Core_Container/1.1_DI_and_Configuration.md) plus
  [ordering attributes](#how-do-you-order-auto-configurations);
- every bean `@ConditionalOnMissingBean`, so users can [replace it](#how-do-you-replace-a-bean-boot-creates);
- settings through a `@ConfigurationProperties` class, not `@Value`;
- [never picked up by a component scan](#why-must-an-auto-configuration-stay-out-of-component-scan).

A conditional `@AutoConfiguration` class plus one line in the imports file.

</details>

### Why must an auto-configuration stay out of component scan?
<details><summary>Show answer</summary>

```
com.acme.shop                                  ← the app scans from here
com.acme.shop.audit.AuditAutoConfiguration     ← found by the scan by accident
```

A scanned auto-configuration is loaded as ordinary user configuration:

- its conditions are checked together with your config, before other beans are known — its `@ConditionalOnMissingBean`
  sees an incomplete picture ([bean conditions depend on order](#why-are-bean-conditions-risky-in-your-own-config));
- its `before`/`after` ordering is ignored;
- `exclude` no longer removes it — exclusion works only on the imports list.

`@SpringBootApplication`'s scan skips classes that are listed in an imports file, but a plain `@ComponentScan`, or a
missing imports entry, doesn't.

Fix: put auto-configurations in their own package, outside your users' packages (`com.acme.audit.autoconfigure`), and
register them only in the imports file. Inside one, pull in other classes with `@Import`, never `@ComponentScan`.

An auto-configuration comes in only through the imports file — never through a scan.

</details>

### How do you order auto-configurations?
<details><summary>Show answer</summary>

```java
@AutoConfiguration(after = DataSourceAutoConfiguration.class)
@ConditionalOnBean(DataSource.class)                 // needs Boot's DataSource registered first
public class AuditJdbcAutoConfiguration { /* ... */ }
```

- `after` / `before` on `@AutoConfiguration` (or the older `@AutoConfigureAfter` / `@AutoConfigureBefore`) — run
  after or before named auto-configurations.
- `@AutoConfigureOrder` — a number for a rough position, like `@Order`, without naming others.

Ordering only decides the order in which bean definitions are registered — which is exactly what bean conditions read.
It does not decide the order in which beans are created; their dependencies decide that.

Order an auto-configuration after the one whose beans its conditions check.

</details>

### How do you test an auto-configuration?
<details><summary>Show answer</summary>

```java
class AuditAutoConfigurationTest {
  private final ApplicationContextRunner runner = new ApplicationContextRunner()
      .withConfiguration(AutoConfigurations.of(AuditAutoConfiguration.class));

  @Test
  void createsClient() {
    runner.withPropertyValues("acme.audit.url=http://audit")
        .run(ctx -> assertThat(ctx).hasSingleBean(AuditClient.class));
  }

  @Test
  void backsOffForUserBean() {
    runner.withUserConfiguration(UserClientConfig.class)
        .run(ctx -> assertThat(ctx).getBean(AuditClient.class).isSameAs(UserClientConfig.CLIENT));
  }

  @Test
  void skippedWithoutLibrary() {
    runner.withClassLoader(new FilteredClassLoader(AuditClient.class))   // hides the library
        .run(ctx -> assertThat(ctx).doesNotHaveBean(AuditClient.class));
  }
}
```

`ApplicationContextRunner` starts a tiny context for each case in milliseconds — no full application.
`AutoConfigurations.of(...)` loads the class the way Boot loads auto-configurations, so conditions and ordering behave
as in production; `withUserConfiguration(...)` adds user config, processed first. `FilteredClassLoader` makes a
library look absent.

One tiny context per case: library present, library missing, user bean, property set.

</details>

### How do you name and split your own starter?
<details><summary>Show answer</summary>

Two modules:

- **`acme-audit-spring-boot-autoconfigure`** — the code: `@AutoConfiguration` classes, `@ConfigurationProperties`, the
  imports file. Library dependencies are marked optional, so the class conditions really check whether the user
  brought them.
- **`acme-audit-spring-boot-starter`** — no code. It depends on the autoconfigure module plus the libraries a typical
  user needs.

Naming: `spring-boot-starter-*` is reserved for Boot's own starters; yours puts the project name first. Use your own
property prefix (`acme.audit.*`), never Boot's namespaces such as `spring.*`.

A small library may merge both into one module.

The autoconfigure module holds the logic, the starter holds only dependencies, and your name goes first.

</details>
