# Transaction Settings

What the `@Transactional` settings change: propagation, isolation, `readOnly`, timeout.

### Which `@Transactional` settings matter?
<details><summary>Show answer</summary>

```java
@Transactional(propagation = Propagation.REQUIRED, isolation = Isolation.DEFAULT, readOnly = false, timeout = -1)
```

These are the defaults. Each setting answers one question:

- [Propagation](#what-does-propagation-decide) — a transaction is already open: join it, start a second one, or refuse?
  The setting behind most bugs.
- [Isolation](#what-does-the-isolation-attribute-set) — how much of other transactions' unfinished work this one sees.
- [`readOnly`](#what-does-readonly--true-change) — "no writes coming", so each layer can skip work.
- [Timeout](#what-does-timeout-limit) — how long the transaction may run.

Isolation, `readOnly` and timeout apply only when the method starts the transaction —
[a method that joins one inherits the caller's](#when-is-the-isolation-setting-ignored). Rollback rules are in
[Transactions](2.3_Transactions.md#which-exceptions-roll-back-by-default).

Trigger: *who joins whom → what it sees → what it may skip → how long it may run.*

</details>

## Propagation

### What does propagation decide?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {   // transaction T1 is open
  orders.save(order);
  audit.log(order);                // audit.log() is @Transactional too: join T1, open T2, or refuse?
}
```

Propagation decides what a `@Transactional` method does when it is called while a transaction is already open — and
when none is. The values group by what they do with an open transaction:

- **Join it** — `REQUIRED` (the default), `SUPPORTS`, `MANDATORY`.
- **Put it on hold** — `REQUIRES_NEW` starts a second transaction; `NOT_SUPPORTED` runs without one.
- **Refuse** — `NEVER` throws.
- **Mark a point inside it** — `NESTED` sets a savepoint.

Details: [`REQUIRED` vs `REQUIRES_NEW`](#required-vs-requires_new-difference),
[when to use a second transaction](#when-should-a-call-get-its-own-transaction) and
[what it costs](#what-can-requires_new-cost), [`NESTED`](#nested-vs-requires_new-difference),
[the other values](#what-do-the-other-propagation-values-do), and the classic failure of a shared transaction,
[`UnexpectedRollbackException`](#why-does-the-outer-commit-throw-unexpectedrollbackexception).

Propagation works only when the call goes through the proxy: on an
[internal call](2.1_Proxies.md#why-does-an-internal-call-skip-cacheable), `REQUIRES_NEW` does nothing.

Propagation is what the called method does with the caller's transaction.

</details>

### `REQUIRED` vs `REQUIRES_NEW`: difference?
<details><summary>Show answer</summary>

```java
@Transactional                                           // REQUIRED, the default
public void place(Order order) {
  orders.save(order);
  audit.log(order);                                      // REQUIRES_NEW: committed when log() returns
  throw new IllegalStateException();                     // place() rolls back — the audit row stays
}

@Transactional(propagation = Propagation.REQUIRES_NEW)   // in the audit bean
public void log(Order order) { /* ... */ }
```

- **`REQUIRED`** — joins the open transaction (or starts one if none is open). One connection, one commit at the end;
  if anything fails, everything rolls back together.
- **`REQUIRES_NEW`** — puts the caller's transaction on hold, takes a second connection, runs and commits (or rolls
  back) its own transaction, then hands control back to the caller's. Its outcome is separate: its commit survives the
  caller's rollback. If it throws, the exception still reaches the caller, which rolls back too unless it catches it.

`REQUIRED` shares one fate; `REQUIRES_NEW` has its own fate and its own connection.

</details>

### When should a call get its own transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void process(Long jobId) {
  try {
    work.run(jobId);
  } catch (RuntimeException e) {
    jobs.markFailed(jobId);        // REQUIRES_NEW in the jobs bean — otherwise rolled back with everything else
    throw e;
  }
}
```

When its work must have a different outcome from the caller's:

- a record that must stay even when the main work rolls back — an audit entry, a "failed" status as above;
- work whose failure must not spoil the caller's transaction.

Not "just to be safe": each one holds a second connection and can't see the caller's unsaved rows —
[the costs](#what-can-requires_new-cost).

Does this work need a different outcome from the caller's? Yes → `REQUIRES_NEW`. No → `REQUIRED`.

</details>

### What can `REQUIRES_NEW` cost?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);              // connection 1, held until place() ends
  audit.log(order);                // REQUIRES_NEW: connection 2, while connection 1 waits
}
```

- **Two connections at once** — the caller's connection is on hold, not given back. With a pool of 10 and 10 requests
  in `place()` at the same time, each holds one connection and waits for a second that never comes. Everything hangs
  until the pool's wait times out.
- **Blind to the caller's work** — the new transaction uses another connection, so it doesn't see the order row the
  caller has not committed yet.
- **Waiting on yourself** — if it needs a row the caller has locked, it waits for the caller, and the caller waits for
  it to return. The database can't see that second wait, so it hangs until a lock timeout.

Every `REQUIRES_NEW` holds two connections at once and can't see the caller's unsaved rows.

</details>

### `NESTED` vs `REQUIRES_NEW`: difference?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  try {
    coupons.redeem(order);         // NESTED: on failure, only redeem()'s work is undone
  } catch (CouponException e) {
    // carry on — the order is still there
  }
}
```

- **`NESTED`** — same transaction, same connection. Before the call Spring sets a **savepoint** — a marker inside the
  transaction you can roll back to. Inner failure → roll back to the savepoint, and the caller carries on. Caller
  failure → the inner work is undone too, because it was never committed on its own. The inner call sees the caller's
  rows.
- **`REQUIRES_NEW`** — a second transaction on a second connection. Its commit is final, even if the caller rolls back.

`NESTED` needs JDBC savepoints, so it works with `DataSourceTransactionManager`. With JPA/Hibernate it is not usable in
practice: the savepoint covers the connection, not the entities Hibernate keeps in memory.

`NESTED` undoes part of one transaction; `REQUIRES_NEW` runs a second, independent one.

</details>

### What do the other propagation values do?
<details><summary>Show answer</summary>

| Value           | A transaction is open                    | None is open                             |
|-----------------|------------------------------------------|------------------------------------------|
| `SUPPORTS`      | join it                                  | run without one                          |
| `MANDATORY`     | join it                                  | throw `IllegalTransactionStateException` |
| `NOT_SUPPORTED` | put it on hold, run without one          | run without one                          |
| `NEVER`         | throw `IllegalTransactionStateException` | run without one                          |

Typical uses:

- `MANDATORY` — guard on code that must only run inside a caller's transaction.
- `NEVER` — guard on code that must never run inside one, e.g. a slow remote call.
- `SUPPORTS` — read code that works either way.
- `NOT_SUPPORTED` — work that must not be part of the caller's transaction. The caller's connection stays on hold
  meanwhile.

Two guards (`MANDATORY`, `NEVER`) and two "either way" values (`SUPPORTS` joins, `NOT_SUPPORTED` steps out).

</details>

### Why does the outer commit throw `UnexpectedRollbackException`?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  try {
    coupons.redeem(order);         // @Transactional (REQUIRED), throws CouponException (a RuntimeException)
  } catch (CouponException e) {
    log.warn("no coupon", e);      // "carry on without the coupon"
  }
}                                  // commit → UnexpectedRollbackException, nothing saved
```

`redeem()` joined the same transaction. When the exception left it, its proxy marked the shared transaction
rollback-only. Catching the exception afterwards doesn't remove the mark. At the end of `place()` Spring tries to
commit, finds the mark, rolls back instead, and throws `UnexpectedRollbackException` — so the caller isn't told
"saved" when nothing was.

Fix, depending on what you want:

- the inner failure must not spoil the caller → give `redeem()` a savepoint (`NESTED`) or its own transaction
  (`REQUIRES_NEW`);
- the failure is an expected case → don't throw; return a result instead;
- this exception should not roll back at all → `noRollbackFor = CouponException.class` on `redeem()`.

In a shared transaction, an exception that crosses any proxy decides for everyone — catching it later is too late.

</details>

## Isolation

### What does the `isolation` attribute set?
<details><summary>Show answer</summary>

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Report monthly() { /* two reads that must agree */ }
```

When the transaction starts, Spring sets the level on the connection (`Connection.setTransactionIsolation()`), and puts
the old level back before the connection returns to the pool.

`Isolation.DEFAULT`, the default, keeps the database's own level: `READ COMMITTED` on PostgreSQL, Oracle and SQL
Server; `REPEATABLE READ` on MySQL InnoDB. The other values are `READ_UNCOMMITTED`, `READ_COMMITTED`,
`REPEATABLE_READ`, `SERIALIZABLE` —
[what each one means](../../FAQs_Persistence/1_SQL/1.4_Transactions_and_Isolation.md).

The database may treat a level its own way: PostgreSQL runs `READ_UNCOMMITTED` as `READ COMMITTED`.

Spring only passes the level to the connection; the database decides what it means.

</details>

### When is the isolation setting ignored?
<details><summary>Show answer</summary>

```java
@Transactional                                           // starts the transaction at the default level
public void checkout(Cart cart) {
  pricing.recalc(cart);                                  // isolation = SERIALIZABLE → silently ignored
}
```

Isolation is applied only when a method starts a transaction. A method that joins an open one runs at the caller's
level, with no warning. The same goes for `readOnly` and `timeout`.

To turn the silent case into an error, call `setValidateExistingTransaction(true)` on the transaction manager: a
joining method with a different level then throws `IllegalTransactionStateException`.

Fix: put the setting on the method that starts the transaction, or use `REQUIRES_NEW` if the method really needs its
own level.

Settings belong to whoever starts the transaction; methods that join inherit them silently.

</details>

## `readOnly` and timeout

### What does `readOnly = true` change?
<details><summary>Show answer</summary>

```java
@Transactional(readOnly = true)
public List<Order> recent() { return orders.findTop100ByOrderByCreatedDesc(); }
```

It is a hint passed down to each layer, and each layer uses it to skip work:

- **Hibernate** — no automatic flush, and loaded entities are read-only, so there is no dirty checking at the end and no
  copies kept for it. Big reads use less memory and CPU.
- **JDBC** — the connection is set read-only. Some databases use that to run the transaction more cheaply; PostgreSQL
  and MySQL also reject writes in it.
- **Routing** — a routing `DataSource` can send read-only transactions to a replica.

It applies only when this method starts the transaction — [a method that joins inherits the caller's
setting](#when-is-the-isolation-setting-ignored).

`readOnly` tells every layer that no writes are coming, so each one can skip work.

</details>

### Does `readOnly` stop writes?
<details><summary>Show answer</summary>

```java
@Transactional(readOnly = true)
public void rename(Long id, String name) {
  orders.findById(id).orElseThrow().setName(name);   // no error, and not saved
}
```

Not reliably. What happens depends on the layer:

- **Hibernate** — changed entities are never flushed, so the change is silently lost. No error.
- **Database** — PostgreSQL and MySQL reject a write sent on a read-only connection; some drivers ignore the hint, and
  the write goes through.
- **Joined transaction** — `readOnly` on a method that joins a read-write transaction does nothing.

For real protection, use a database user without write rights, or a read-only replica.

`readOnly` is a hint for speed, not a lock against writes.

</details>

### What does `timeout` limit?
<details><summary>Show answer</summary>

```java
@Transactional(timeout = 5)                  // seconds, counted from the transaction start
public void importBatch(List<Row> rows) {
  rows.forEach(repo::save);
  partner.notify(rows);                      // a slow HTTP call here is NOT stopped
}
```

Spring doesn't stop the thread. It checks the deadline each time a database statement starts:

- it sets the statement's query timeout to the time left, so the driver cancels a slow SQL query;
- if the deadline has already passed, it throws `TransactionTimedOutException` instead of running the statement.

Slow Java code or a remote call between statements runs on; the failure comes only at the next database call — or
never, if there is none. The setting applies only when this method starts the transaction.

`timeout` limits database statements, not the method.

</details>
