## AOP

### What problem does AOP solve?
<details><summary>Show answer</summary>

It separates **cross-cutting concerns** (infrastructure code needed everywhere) from core business logic.

**Before AOP:**

```java
public void place(Order order) {
  log.info("place start");                 // logging
  checkPermission("orders:write");         // security
  tx.begin();                              // transactions
  try {
    repo.save(order);                      // <-- the actual business logic
    tx.commit();
  } catch (RuntimeException e) {
    tx.rollback();
    throw e;
  }
}
```

This manual approach creates two flaws:

- **Code tangling** — one method mixes business logic with infrastructure, hiding what the method actually does.
- **Code scattering** — the same boilerplate is copy-pasted across dozens of classes. Miss one, and you have a bug.

**After AOP:**

AOP extracts this boilerplate into standalone **aspects**. You write the infrastructure code once and attach it by
rules (**pointcuts** — patterns that pick which methods get it) or by annotations.

```java
@Transactional
@PreAuthorize("hasAuthority('orders:write')")
public void place(Order order) {           // logging is applied by a global pointcut
  repo.save(order);
}
```

</details>

### How to refuse a call without permission?
<details><summary>Show answer</summary>

`@PreAuthorize("hasAuthority('orders:write')")` — the rule is checked before the method runs. 
If it fails, the method never runs and the caller gets an `AccessDeniedException`.

</details>

### How to reject bad method arguments?
<details><summary>Show answer</summary>

`@Validated` on the class, plus constraints like `@NotNull` or `@Size` on the parameters. 
Bad input throws `ConstraintViolationException` before the method runs.

</details>

### How to make several writes all-or-nothing?
<details><summary>Show answer</summary>

`@Transactional` — a transaction starts before the method, commits when it returns, and rolls back when it throws an
unchecked exception.

</details>

### How to avoid recomputing the same result?
<details><summary>Show answer</summary>

`@Cacheable("prices")` — the first call runs the method and stores the result, keyed by the arguments. 
Later calls with the same arguments get the stored result, and the method does not run.

</details>

### How to run a method without waiting?
<details><summary>Show answer</summary>

`@Async` — the method runs on another thread, and the caller moves on at once.

</details>

### How to try a failing call again?
<details><summary>Show answer</summary>

`@Retryable` — if the method throws, the call is made again, up to a set number of attempts.

</details>

### Two annotations on one method: which runs first?
<details><summary>Show answer</summary>

**The rule.** Spring puts one proxy in front of the bean, and the proxy calls the wrappers one inside the other, like
Russian dolls. The order of the annotations in the source is ignored. The `order` value decides: lowest value = outer
layer — first on the way in, last on the way out.

**The trap: retry vs. transaction.**

```java
@Retryable
@Transactional
public void reserve(String sku) { /* ... */ }
```

- **Correct (retry outside)** — the retry wrapper gets the call first. Each attempt calls inward and starts a fresh,
  clean transaction.
- **Wrong (transaction outside)** — the transaction starts first, and every attempt runs inside it. A failed attempt
  usually marks the shared transaction **rollback-only** — it can only roll back now, never commit. Later attempts may
  succeed, but the commit fails with `UnexpectedRollbackException`. And the commit runs after retry has finished, so
  any failure found there (an optimistic-lock conflict, say) is never retried.

**Setting the order.**

- Framework wrappers: the `order` attribute on the enabling annotation, e.g. `@EnableTransactionManagement(order = 1)`
  and `@EnableRetry(order = 0)`.
- Your own aspects: `@Order(int)` on the `@Aspect` class.
- Two wrappers with the same order value have no fixed order.

</details>

### AOP terms: how do they fit together?
<details><summary>Show answer</summary>

```java
@Aspect                                                    // ASPECT: the container
@Component
class TimingAspect {
  @Around("@annotation(com.shop.Timed)")                   // POINTCUT: the filter — the string, not @Around
  Object time(ProceedingJoinPoint call) throws Throwable { // ADVICE: the what & when
    long start = System.nanoTime();
    try {
      return call.proceed();                               // JOIN POINT: the actual method execution
    } finally {
      log.info("{} took {} ns", call.getSignature(), System.nanoTime() - start);
    }
  }
}
```

To remember them, think of it as a logical chain:

- **Join point** (the "Where"): a specific moment during program execution where extra code could run. 
  In Spring AOP, this is always a method execution.
- **Pointcut** (the "Filter"): the rule or expression that selects exactly which join points get the extra code.
- **Advice** (the "What & When"): the actual code to run, plus when it runs (before, after, or around).
- **Aspect** (the "Container"): the Java class that groups the pointcuts and advice together.

Note: In Spring code, you will also meet the term **Advisor**. It is a Spring-specific term for exactly one pointcut
paired with one advice. Built-in features like `@Transactional` use advisors under the hood.

</details>

### Spring AOP vs AspectJ: how do they differ?
<details><summary>Show answer</summary>

The core difference is the mechanism: **Spring AOP adds an object in front; AspectJ changes the class itself**.
- **Spring AOP (Proxy-based)** — at runtime, Spring creates a [proxy](2.1_Proxies.md#what-is-a-spring-proxy) in front of the bean.
  Your compiled class stays exactly as written.
- **AspectJ (Bytecode Weaving)** — the extra code is injected into the class's own bytecode. This happens either:
  - at compile-time (using the ajc compiler) or 
  - while the JVM loads the class (using a Java agent).

With AspectJ nothing stands in front of the class, so there is nothing to go around — which is why
[it catches what proxies miss](#what-can-aspectj-catch-that-a-proxy-cant).

</details>

### Does Spring AOP use AspectJ?
<details><summary>Show answer</summary>

**AspectJ syntax, Spring proxies.** It borrows the language but ignores the engine.

**What it borrows (The Syntax):**
- The annotations (`@Aspect`, `@Around`, `@Pointcut`) come directly from `org.aspectj.lang.annotation`.
- The pointcut expressions are parsed by AspectJ's parser.

**What it ignores (The Weaving Engine):**
- Spring AOP does not use AspectJ's compiler (ajc) or JVM agent to alter bytecode.
- Under the hood, the extra code still runs entirely through standard Spring proxies.


Because the execution engine is still purely proxy-based, 
all standard [proxy limits](2.1_Proxies.md#what-does-a-proxy-not-see)
(such as internal method calls silently bypassing the aspect) still apply.

</details>

### What can AspectJ catch that a proxy can't?
<details><summary>Show answer</summary>

Because AspectJ weaves the extra code directly into the bytecode, there is no external wrapper object to bypass.
This allows it to intercept everything a proxy misses:
- Internal & direct calls — calls inside the same class (`this.find()`, the
  [internal call problem](2.1_Proxies.md#why-does-an-internal-call-skip-cacheable)) and objects made with `new`.
- **Methods a proxy can't take over** — `private`, `final` and `static` methods.
- Non-method executions — constructors, class initialization, and direct field reads/writes.

</details>

### When is AspectJ weaving worth it?
<details><summary>Show answer</summary>

**The Default:** Always start with Spring AOP proxies. 
They require no extra build steps or JVM agents, and the code is easier to debug because it is exactly what you wrote.


**When to switch to AspectJ:**
Use it only when you hit a strict proxy limit that you cannot fix by simply refactoring and splitting the class


**The classic use case:**
In a "Rich Domain Model" (Domain-Driven Design), you might want to inject dependencies into objects 
that Spring does not create, such as domain entities instantiated manually with `new` 
(using Spring's **@Configurable** annotation):

```java
@Configurable
public class Order {

  @Autowired
  private transient OrderRepository repository; // Spring will inject this!

  private String status;

  public Order() {
    this.status = "NEW";
  }

  public void complete() {
    this.status = "COMPLETED";
    repository.save(this); // This works! The repository is NOT null.
  }
}

// We bypass Spring entirely and create the object ourselves
Order myOrder = new Order();

// This succeeds because AspectJ secretly wired the repository during 'new'
myOrder.complete();
```

If you do not have this exact problem, stay with standard proxies.

</details>
