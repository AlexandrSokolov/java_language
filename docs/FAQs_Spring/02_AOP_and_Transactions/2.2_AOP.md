# AOP

How Spring adds behaviour around a bean's methods.

### What governs Spring AOP?
<details><summary>Show answer</summary>

AOP lets you write code that runs around many methods without putting it inside them. In Spring that code runs on
[proxies](2.1_Proxies.md#what-is-a-spring-proxy).

- [Why it exists](#what-problem-does-aop-solve) — otherwise the same extra code is copied into every method.
- [Built-in features](#what-can-a-wrapper-do-to-a-call) — `@Transactional`, `@Cacheable`, `@Async`… are ready-made
  wrappers, and [their order matters](#two-annotations-on-one-method-which-runs-first) when several meet on one method.
- [Your own aspect](#aop-terms-how-do-they-fit-together) — the same machinery for your own extra code: a rule that picks
  methods, plus the code to run.
- [AspectJ](#spring-aop-vs-aspectj-how-do-they-differ) — the other way in: it changes the class itself, for when proxy
  limits get in the way.

Trigger: *same code in many methods → write it once → Spring runs it through proxies, built-in or yours → AspectJ
when proxies can't reach.*

</details>

### What problem does AOP solve?
<details><summary>Show answer</summary>

```java
public void place(Order order) {
  log.info("place start");                 // logging
  checkPermission("orders:write");         // security
  tx.begin();                              // transaction
  try {
    repo.save(order);                      // the only line about orders
    tx.commit();
  } catch (RuntimeException e) {
    tx.rollback();
    throw e;
  }
}
```

Every service method needs the same logging, security and transaction code. Copied into each one, it hides the real
work, and changing it means editing every method — miss one and it's a bug.

AOP takes that code out of the methods, writes it once, and attaches it by a rule that says which methods get it. The
method keeps only its own job:

```java
@Transactional
@PreAuthorize("hasAuthority('orders:write')")
public void place(Order order) {           // logging comes from an aspect
  repo.save(order);
}
```

Field term: **cross-cutting concern** — code that many unrelated classes need.

Write the shared code once, attach it by rule, and keep each method about its own job.

</details>

## Built-in features

### What can a wrapper do to a call?
<details><summary>Show answer</summary>

The wrapper gets the call before the method does, so it can:

| What it does to the call             | Feature                                       |
|--------------------------------------|-----------------------------------------------|
| check it first, maybe refuse it      | `@PreAuthorize`, `@Validated`                 |
| run code before and after it         | `@Transactional` — begin; commit or roll back |
| skip it and return a stored result   | `@Cacheable`                                  |
| run it on another thread             | `@Async`                                      |
| run it again when it fails           | `@Retryable`                                  |

Refuse, surround, skip, move or repeat — all possible because the wrapper gets the call first.

</details>

### Two annotations on one method: which runs first?
<details><summary>Show answer</summary>

```java
@Retryable
@Transactional
public void reserve(String sku) { /* ... */ }
```

The wrappers sit one inside the other. Their order comes from their `order` value: the lowest value is the outer layer —
first on the way in, last on the way out. The order of the annotations in the source does not matter.

Here retry must be the outer layer, so each attempt gets a fresh transaction. If retry sits inside, all attempts share
one transaction: the first failure usually marks it for rollback, and a failure at commit comes after retry has already
finished.

Set the order with the `order` attribute on `@EnableTransactionManagement`, `@EnableCaching` or `@EnableAsync`, and
with `@Order` on your own `@Aspect` classes. Two wrappers with the same order run in an undefined order.

Lower order value = outer layer; when it matters, set it — never rely on the default.

</details>

## Your own aspect

### AOP terms: how do they fit together?
<details><summary>Show answer</summary>

```java
@Aspect                                                    // aspect: the class that holds it all
@Component
class TimingAspect {
  @Around("@annotation(com.shop.Timed)")                   // pointcut: which method calls
  Object time(ProceedingJoinPoint call) throws Throwable { // advice: the code, and when it runs (around)
    long start = System.nanoTime();
    try {
      return call.proceed();                               // join point: the matched call, run here
    } finally {
      log.info("{} took {} ns", call.getSignature(), System.nanoTime() - start);
    }
  }
}
```

- **[Join point](#join-point-vs-pointcut-difference)** — a place where extra code can run. In Spring AOP: a call to a
  bean's method.
- **Pointcut** — [the rule that picks](#how-do-you-pick-methods-for-an-aspect) which join points get it;
  [by name or by annotation](#name-pattern-or-annotation-which-pointcut) is the main design choice.
- **[Advice](#advice-vs-aspect-difference)** — the code that runs there, plus when:
  [before, after or around](#which-advice-can-change-the-result).
- **Aspect** — the class that holds pointcuts and advice together. It runs only if
  [it is a bean](#why-does-an-aspect-class-never-run), and `@Around` must
  [pass the result back](#what-if-around-doesnt-return-the-proceed-result).

In Spring code you'll also meet **advisor** — one pointcut plus one advice. Each built-in feature (`@Transactional`,
`@Cacheable`, …) registers one.

The pointcut picks join points, the advice runs at them, the aspect holds both.

</details>

### Join point vs pointcut: difference?
<details><summary>Show answer</summary>

`orderService.place(order)` running right now is a **join point** — one real moment where extra code can be attached.
In Spring AOP a join point is always a call to a bean's method.

`execution(* com.shop.order..*.*(..))` is a **pointcut** — a rule. It matches that call and every other method call in
the `com.shop.order` package and below.

Join points are the candidates; the pointcut is the filter. One pointcut matches many join points.

</details>

### Advice vs aspect: difference?
<details><summary>Show answer</summary>

```java
@Aspect
@Component
class AuditAspect {                                            // aspect: groups everything for auditing
  @Before("@annotation(com.shop.audit.Audited)")
  void logCall(JoinPoint call) { /* ... */ }                   // advice: runs before the call

  @AfterThrowing(pointcut = "@annotation(com.shop.audit.Audited)", throwing = "e")
  void logFailure(JoinPoint call, Exception e) { /* ... */ }   // advice: runs when the call throws
}
```

- **Advice** — one piece of extra code plus *when* it runs: `logCall()` before the call, `logFailure()` when it throws.
- **Aspect** — the class that groups advice, and the pointcuts they use, for one concern: `AuditAspect`.

Advice is one method of extra code; the aspect is the class that holds the advice for one concern.

</details>

### Which advice can change the result?
<details><summary>Show answer</summary>

```java
@Around("@annotation(com.shop.cache.Cached)")
Object cached(ProceedingJoinPoint call) throws Throwable {
  Object hit = cache.get(call.getArgs());
  if (hit != null) {
    return hit;                          // the method never runs
  }
  Object result = call.proceed();        // proceed(newArgs) would change the arguments
  cache.put(call.getArgs(), result);
  return result;                         // the caller gets whatever this returns
}
```

Only `@Around`. It holds the call itself and decides: call `proceed()` or not, with which arguments, what to return,
whether to catch or swap the exception.

The others only watch the call go by:

- `@Before` — runs before; can stop the call only by throwing.
- `@AfterReturning` — sees the result; can't replace it.
- `@AfterThrowing` — sees the exception; can't swallow it, only throw a different one.
- `@After` — runs either way, like `finally`.

Only `@Around` holds the call, so only `@Around` controls it.

</details>

### How do you pick methods for an aspect?
<details><summary>Show answer</summary>

With a pointcut expression. The common ones:

```
execution(* com.shop.order..*.*(..))              // by signature: package, class, method name, arguments
within(com.shop.order..*)                         // every method of the classes in a package
@annotation(com.shop.audit.Audited)               // methods that carry this annotation
@within(org.springframework.stereotype.Service)   // every method of classes that carry this annotation
bean(*Service)                                    // by bean name — Spring AOP only
```

Combine them with `&&`, `||`, `!`, and name one with `@Pointcut` on an empty method to reuse it:

```java
@Pointcut("within(com.shop.order..*)")
void orderLayer() { }

@Before("orderLayer() && @annotation(com.shop.audit.Audited)")
void audit(JoinPoint call) { /* ... */ }
```

Pick by where the code is (`execution`, `within`), by a mark on it (`@annotation`, `@within`), or by bean name (`bean`).

</details>

### Name pattern or annotation: which pointcut?
<details><summary>Show answer</summary>

Two ways to pick the methods for an audit aspect:

```java
@Before("execution(* com.shop..*Service.save*(..))")    // by name pattern
@Before("@annotation(com.shop.audit.Audited)")           // by annotation
```

**Name pattern**

- **Buys:** target code stays untouched; new methods that follow the naming are covered without any change.
- **Costs:** rename a method or move a class and it silently drops out; a new `saveDraft()` silently drops in. Nothing
  at the method shows it is wrapped.

**Annotation**

- **Buys:** the method says it is wrapped; renames and moves change nothing; matching is exact.
- **Costs:** you touch every target method, and forgetting one is also a silent miss.

Decide by asking: does the behaviour belong to a whole layer (all repositories, all controllers) or to chosen methods?
Layer → `within` the package or `@within` the stereotype. Chosen methods → annotation. A name pattern is the weakest
choice: it ties the aspect to naming habits.

</details>

### Why does an `@Aspect` class never run?
<details><summary>Show answer</summary>

```java
@Aspect                                  // no @Component
public class TimingAspect {
  @Around("@annotation(com.shop.Timed)")
  public Object time(ProceedingJoinPoint call) throws Throwable { /* ... */ }
}
```

`@Aspect` only marks the class as an aspect. It doesn't make it a bean, and component scanning doesn't pick up `@Aspect`
on its own. Spring builds proxies only from aspects that are beans, so this one is never seen — no error, no effect.

Fix: add `@Component`, or declare it with `@Bean`.

Same symptom, second cause: aspect support is off — no `@EnableAspectJAutoProxy` in plain Spring, or no `aspectjweaver`
on the classpath in Boot.

An aspect works only if it is a bean and aspect support is on.

</details>

### What if `@Around` doesn't return the `proceed()` result?
<details><summary>Show answer</summary>

```java
@Around("@annotation(com.shop.Timed)")
public void time(ProceedingJoinPoint call) throws Throwable {   // void: the result is thrown away
  long start = System.nanoTime();
  call.proceed();
  log.info("took {} ns", System.nanoTime() - start);
}
```

The method runs, but its return value is dropped. The advice returns nothing, so every caller gets `null`. If the
method returns a primitive (`int`, `boolean`), the call fails with `AopInvocationException` instead, because `null`
can't become an `int`.

Fix: return `Object` and pass the result back:

```java
@Around("@annotation(com.shop.Timed)")
public Object time(ProceedingJoinPoint call) throws Throwable {
  long start = System.nanoTime();
  try {
    return call.proceed();
  } finally {
    log.info("took {} ns", System.nanoTime() - start);
  }
}
```

Forget `proceed()` entirely and the method never runs at all.

`@Around` stands in for the method: it must call `proceed()` and pass back what it returns.

</details>

## Spring AOP vs AspectJ

### Spring AOP vs AspectJ: how do they differ?
<details><summary>Show answer</summary>

- **Spring AOP** — at runtime, Spring creates a [proxy](2.1_Proxies.md#what-is-a-spring-proxy) in front of the bean.
  Your class stays exactly as written.
- **AspectJ** — the extra code is put into the class's own bytecode. This is called **weaving**. It happens at compile
  time (the `ajc` compiler), on already compiled classes, or while the JVM loads the class (a Java agent).

With AspectJ nothing stands in front of the class, so there is nothing to go around — which is why
[it catches what proxies miss](#what-can-aspectj-catch-that-a-proxy-cant).

Spring AOP adds an object in front; AspectJ changes the class itself.

</details>

### Does Spring AOP use AspectJ?
<details><summary>Show answer</summary>

Only its language, not its weaving:

- the annotations — `@Aspect`, `@Around`, `@Pointcut`… — come from AspectJ (`org.aspectj.lang.annotation`);
- the pointcut expressions are parsed by AspectJ's parser, from the `aspectjweaver` jar.

The extra code still runs through Spring's proxies: no `ajc`, no agent, no bytecode change. All the
[proxy limits](2.1_Proxies.md#what-does-a-proxy-not-see) still apply.

AspectJ syntax, Spring proxies.

</details>

### What can AspectJ catch that a proxy can't?
<details><summary>Show answer</summary>

The code is inside the class itself, so no call has to pass through anything:

- **Calls that skip the proxy** — calls inside the same class (`this.find()`, the
  [internal call problem](2.1_Proxies.md#why-does-an-internal-call-skip-cacheable)) and objects made with `new`.
- **Methods a proxy can't take over** — `private`, `final` and `static` methods.
- **Things that aren't method calls** — constructors, and field reads and writes.

No object in front, so nothing to go around.

</details>

### When is AspectJ weaving worth it?
<details><summary>Show answer</summary>

The first instinct — "proxies have limits, so use AspectJ" — is not the default. Most limits stop hurting once classes
are split well.

**Spring AOP proxies (default)**

- **Buys:** no build or JVM changes; the running code is the code you wrote.
- **Costs:** the [proxy limits](2.1_Proxies.md#what-does-a-proxy-not-see); a small cost on each wrapped call.

**AspectJ weaving**

- **Buys:** wraps internal calls, `private` and `final` methods, objects made with `new`, constructors and fields; no
  proxy hop per call. Built-in features can use it too (`@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)`, the
  same for caching and async).
- **Costs:** an extra compiler step in the build, or a JVM agent at startup; the running code is no longer exactly the
  code you wrote, so debugging is harder; the team has to know the tool.

Decide by asking: do you need to wrap something a proxy can't reach, and can you not fix it by splitting the class? A
typical yes is injecting into objects that Spring doesn't create (`@Configurable` domain objects). Otherwise stay with
proxies.

</details>
