# Proxies

How Spring puts an object in front of a bean, and what that object can't see.

### What governs Spring proxies?
<details><summary>Show answer</summary>

A Spring proxy is one object placed in front of a bean. Each part of the chapter follows from that:

- [What it is](#what-is-a-spring-proxy) — an object of the bean's type that runs extra code, then calls the real bean.
- [How it's built](#how-can-spring-build-a-proxy) — from the bean's interfaces, or as a subclass of its class.
- [Which beans get one](#which-beans-get-wrapped) — only beans with a method some feature wants to wrap, and only
  [after the bean is set up](#when-in-the-lifecycle-is-the-proxy-made).
- [What it can't see](#what-does-a-proxy-not-see) — methods it can't take over, and calls that never pass through it.
- [How to work with one](#how-do-you-tell-a-bean-is-a-proxy) — spot it, reach the real object, read annotations right.

Trigger: *one object in front → built from interface or subclass → made after init, only where needed → sees only
outside calls to methods it can take over.*

</details>

### What is a Spring proxy?
<details><summary>Show answer</summary>

A proxy is a wrapper object created by Spring during bean initialization to intercept method calls. 
It sits directly in front of your actual bean, executing extra logic (like opening transactions) 
before and after delegating the call to the real method.

```java
@Service
public class OrderService {
  @Transactional
  public void place(Order order) { /* ... */ }
}
```

A call to `orderService.place(order)` from another bean reaches the proxy first. The proxy starts a transaction, calls
`place()` on the real `OrderService`, then commits or rolls back.

</details>

### What does Spring inject when a bean depends on a proxied bean?
<details><summary>Show answer</summary>

Spring injects the proxy object, not the actual bean instance. 
Whenever the bean is injected (via constructor or @Autowired) or looked up using getBean(), Spring hands out the proxy. 
The proxy then holds the reference to the real object.

```java
@RestController
class OrderController {
  private final OrderService orders;        // OrderService has a @Transactional method → this is the proxy

  OrderController(OrderService orders) {
    this.orders = orders;
    System.out.println(orders.getClass());  // e.g. OrderService$$SpringCGLIB$$0, not OrderService
  }
}
```

</details>

### How can Spring build a proxy?
<details><summary>Show answer</summary>

Two ways: 
- **[JDK dynamic proxy](#how-does-a-jdk-dynamic-proxy-work)** — a class that implements the bean's interfaces.
- **[CGLIB proxy](#how-does-a-cglib-proxy-work)** — a subclass of the bean's class.

</details>

### How does a JDK dynamic proxy work?
<details><summary>Show answer</summary>

A JDK dynamic proxy is a class created at runtime by the JDK that implements one or more interfaces of the target bean. 
It routes all method calls through a single InvocationHandler - `JdkDynamicAopProxy` in Spring. 
The handler executes the cross-cutting logic (like opening a transaction) and then uses reflection 
to invoke the corresponding method on the real target object.
Because it is strictly interface-based, it only knows about the methods defined in those interfaces.

```java
public interface OrderService { void place(Order order); }
public class OrderServiceImpl implements OrderService { /* ... */ }

// JDK proxy:   class $Proxy42 implements OrderService
```

</details>

### How does a CGLIB proxy work?
<details><summary>Show answer</summary>

CGLIB (Code Generation Library) generates a proxy by creating a subclass of the target bean's class at runtime.
It overrides the methods of the parent class that are not `final` or `private`.
Every override does the same thing: it passes the call to one `MethodInterceptor`, with the `Method` that was called and
its arguments. The interceptor runs the extra code and calls the same method on the real target, which is a separate
object.
Because it relies on inheritance, the target class must not be `final` or `private`.

```java
public interface OrderService { void place(Order order); }
public class OrderServiceImpl implements OrderService { /* ... */ }

// CGLIB proxy: class OrderServiceImpl$$SpringCGLIB$$0 extends OrderServiceImpl
```

In Spring, `CglibAopProxy` builds it.

</details>

### JDK proxy vs CGLIB — trade-offs?
<details><summary>Show answer</summary>

JDK proxies require the bean to implement an interface, and the proxy is only that interface. Injecting the bean by its
class type (`OrderServiceImpl` instead of `OrderService`) fails at startup. Casting to it throws `ClassCastException`.

CGLIB subclasses the bean's class, so injection by the class type works. But it cannot proxy `final` classes, and it
cannot intercept `final` methods. A call to a `final` method skips the extra code and runs on the proxy object itself,
whose fields were never set. The result is a `NullPointerException` or wrong data, with no error at startup.

Which one is possible:
- Only an interface, no class behind it → only JDK.
- No interface → only CGLIB.
- A `final` class with an interface → only JDK.
- A normal class with an interface → both. CGLIB avoids the JDK injection trap.

</details>

### How does Spring choose the proxy type?
<details><summary>Show answer</summary>

Spring Framework's rule:
- The bean implements an interface with methods → JDK proxy. Spring callbacks like `InitializingBean` don't count.
- No such interface → CGLIB.
- `proxyTargetClass = true` → CGLIB, even with interfaces.
- The bean type is only an interface, with no class of yours behind it (Spring Data repositories, `@HttpExchange`
  clients) → JDK, always.

Spring Boot sets `spring.aop.proxy-target-class=true` by default, so `@Transactional` beans and aspects get CGLIB.

How to change it:
- Plain Spring: `proxyTargetClass = true` on `@EnableTransactionManagement`, `@EnableAspectJAutoProxy`,
  `@EnableCaching` or `@EnableAsync`.
- Spring Boot: `spring.aop.proxy-target-class=false` brings back the Framework rule.

</details>

### Why does injecting the class behind an interface fail?
<details><summary>Show answer</summary>

```java
public interface OrderService { void place(Order order); }

@Service
public class OrderServiceImpl implements OrderService {
  @Transactional
  public void place(Order order) { /* ... */ }
}

@RestController
class OrderController {
  OrderController(OrderServiceImpl orders) { }   // asks for the class, not the interface
}
```

With JDK proxies (plain Spring, or Boot with `spring.aop.proxy-target-class=false`), the bean in the container is a
`$Proxy` class that implements `OrderService`. It is not an `OrderServiceImpl`, so the container has nothing to inject
and startup fails (`BeanNotOfRequiredTypeException` or `UnsatisfiedDependencyException`, depending on which bean is
created first).

Fix: inject the interface, `OrderService` — that is what it is for. Switching to CGLIB also makes it work, which is why
Boot doesn't show the problem.

A JDK proxy is its interfaces and nothing else.

</details>

### Which beans get wrapped?
<details><summary>Show answer</summary>

```java
@Service
public class PriceService { }                     // nothing to wrap: injected as itself

@Service
public class OrderService {
  @Transactional
  public void place(Order order) { /* ... */ }    // one matching method → the whole bean is wrapped
}
```

After a bean is set up, Spring checks it against every feature that wraps methods — `@Transactional`, `@Async`,
`@Cacheable`, `@PreAuthorize`, `@Validated`, your own `@Aspect` classes. Each brings a rule that picks methods.

- At least one method matches → the bean gets a proxy, and every other bean gets the proxy.
- Nothing matches → the real object is injected. No proxy, no cost.

Methods that match nothing still pass through the proxy, but no extra code runs for them.

One matching method is enough to wrap the bean; no match, no proxy.

</details>

### What does `@Enable…` switch on?
<details><summary>Show answer</summary>

```java
@Service
public class ReportService {
  @Async
  public void build() { /* ... */ }   // without @EnableAsync: runs on the caller's thread, no error
}
```

`@Async` on its own is only a label. Nothing reads it until `@EnableAsync` registers the part that does: a bean
post-processor that wraps beans with `@Async` methods. `@EnableCaching`, `@EnableTransactionManagement` and
`@EnableMethodSecurity` do the same for their annotations.

Forget it and nothing fails: there is no proxy, and the method just runs plain.

Spring Boot switches on transactions, and `@Aspect` support when `aspectjweaver` is on the classpath. You still add
`@EnableAsync`, `@EnableCaching` and `@EnableMethodSecurity` yourself.

The annotation marks the method; `@Enable…` makes Spring act on the mark.

</details>

### When in the lifecycle is the proxy made?
<details><summary>Show answer</summary>

Order for one bean: constructor → dependencies injected → `@PostConstruct` / `afterPropertiesSet()` / init method →
**proxy made** → other beans get the proxy.

The proxy comes from a bean post-processor, in its after-initialization step. So all init code runs on the real object,
before any proxy exists, and can't use its own wrapped features
([`@Async` in `@PostConstruct`](#why-does-async-do-nothing-in-postconstruct) is the classic case).

One exception: a bean in a [circular dependency](../01_Core_Container/1.4_Circular_Dependencies.md) may get its proxy
early, so the other bean can be given the proxy instead of the raw object.

Init first, proxy after — init code always talks to the real object.

</details>

### `@Async` in `@PostConstruct`?
<details><summary>Show answer</summary>

```java
@Service
public class CacheWarmer {
  @PostConstruct
  void init() {
    warmUp();                  // runs on the startup thread and blocks startup
  }

  @Async
  public void warmUp() { /* slow */ }
}
```

Two reasons, and both mean the call never reaches a proxy:

- The proxy doesn't exist yet: it is made [after init](#when-in-the-lifecycle-is-the-proxy-made).
- `warmUp()` is called on `this`, the real object, so even a finished proxy would be skipped — the
  [internal call](#why-does-an-internal-call-skip-cacheable) problem.

Fix: drop `@PostConstruct` and let Spring call the method once the app is up:

```java
@Service
public class CacheWarmer {
  @Async                                      // another thread; needs @EnableAsync
  @EventListener(ApplicationReadyEvent.class) // after startup is done
  public void warmUp() { /* slow */ }
}
```

Spring calls an event listener on the bean it gets from the context, which is the proxy, so `@Async` applies.

Init code talks to the real object, so wrapped features don't apply there.

</details>

### What does a proxy not see?
<details><summary>Show answer</summary>

A proxy adds code to a call only when both of these hold:

- **The method is one it can take over** — it implements it (JDK) or overrides it (CGLIB).
  - [A `final` class](#why-cant-a-final-class-be-proxied) can't be subclassed at all.
  - [Some methods](#which-methods-does-a-proxy-miss) can't be overridden or aren't on the interface.
  - [A `final` method](#what-happens-to-a-final-method-on-a-proxied-bean) is skipped silently, and runs on an empty
    object.
- **The call comes through the proxy** — the caller holds the proxy, not the real object.
  - [A call inside the class](#why-does-an-internal-call-skip-cacheable) goes through `this`;
    [here is how to fix it](#how-do-you-fix-the-internal-call).
  - [Init code](#why-does-async-do-nothing-in-postconstruct) runs before the proxy exists.

The proxy sees a call only if the call comes through it and the method is one it can take over.

</details>

### Why can't a `final` class be proxied?
<details><summary>Show answer</summary>

```java
@Service
public final class PriceService {
  @Cacheable("prices")
  public Price find(String sku) { /* ... */ }
}
```

CGLIB builds the proxy as a subclass, and a `final` class can't have one. With CGLIB — Boot's default — startup fails
with an error saying Spring could not generate the CGLIB subclass.

If the class implements an interface and CGLIB isn't forced, Spring uses a JDK proxy instead and it works: that proxy
implements the interface and never extends the class.

Fix: remove `final`.

No subclass, no CGLIB proxy.

</details>

### Which methods does a proxy miss?
<details><summary>Show answer</summary>

| Proxy | Can take over                      | Misses                                  |
|-------|------------------------------------|-----------------------------------------|
| JDK   | methods declared on the interface  | every other method of the class         |
| CGLIB | methods it can override            | `private`, `final` and `static` methods |

An annotation on a missed method does nothing, with no error at startup.

Whether a feature honours its annotation on a non-`public` method that CGLIB *can* override depends on the feature and
the Spring version.

If the proxy can't implement or override the method, it can't wrap it.

</details>

### What happens to a `final` method on a proxied bean?
<details><summary>Show answer</summary>

```java
@Service
public class OrderService {
  private final OrderRepository repo;

  public OrderService(OrderRepository repo) { this.repo = repo; }

  @Transactional
  public final void place(Order order) {
    repo.save(order);              // NullPointerException: repo is null here
  }
}
```

The CGLIB subclass can't override `place()`, so a call to it runs the method body **on the proxy object itself**, not on
the real bean. Spring normally creates the proxy object without running its constructor, so all its fields are `null`.

Two failures:

- the extra code never runs — no transaction;
- the method reads the proxy's empty fields → `NullPointerException`, or silently wrong values for primitives (`0`,
  `false`).

Fix: remove `final`.

A `final` method on a subclass proxy runs on the empty proxy, not on your bean.

</details>

### Why does an internal call skip `@Cacheable`?
<details><summary>Show answer</summary>

```java
@Service
public class PriceService {
  public Price priceWithTax(String sku) {
    return find(sku).withTax();      // this.find(): the real object → cache never checked
  }

  @Cacheable("prices")
  public Price find(String sku) { /* slow lookup */ }
}
```

Other beans hold the proxy, so `priceService.find(sku)` called from outside checks the cache. But inside
`priceWithTax()`, `find(sku)` means `this.find(sku)`, and `this` is the real object. The call goes straight to the
method and the proxy never sees it.

The same holds for `@Transactional`, `@Async`, `@PreAuthorize` and your own aspects.

Extra code runs only for calls that come through the proxy; `this` goes around it.

</details>

### How do you fix the internal call?
<details><summary>Show answer</summary>

`priceWithTax()` calls `find()` in the same class, so `@Cacheable` on `find()` never runs. Four ways out.

**Move the method to another bean — the default.**

```java
@Service
public class PriceCatalog {
  @Cacheable("prices")
  public Price find(String sku) { /* slow lookup */ }
}

@Service
public class PriceService {
  private final PriceCatalog catalog;      // the proxy

  public PriceService(PriceCatalog catalog) { this.catalog = catalog; }

  public Price priceWithTax(String sku) { return catalog.find(sku).withTax(); }
}
```

- **Buys:** plain code, no Spring tricks; the call goes through a proxy by design.
- **Costs:** one more class.

**Inject the bean into itself.**

```java
@Service
public class PriceService {
  private final ObjectProvider<PriceService> self;   // looked up on use, so no cycle at startup

  public PriceService(ObjectProvider<PriceService> self) { this.self = self; }

  public Price priceWithTax(String sku) {
    return self.getObject().find(sku).withTax();     // through the proxy
  }

  @Cacheable("prices")
  public Price find(String sku) { /* slow lookup */ }
}
```

- **Buys:** no new class.
- **Costs:** a self-reference that looks like a mistake; the next developer calls `find()` directly again.

**Ask Spring for the current proxy.**

```java
((PriceService) AopContext.currentProxy()).find(sku);   // needs @EnableAspectJAutoProxy(exposeProxy = true)
```

- **Buys:** no new field or class.
- **Costs:** Spring API inside business code; fails at runtime if the proxy is not exposed.

**[Weave with AspectJ](2.2_AOP.md#when-is-aspectj-weaving-worth-it).**

- **Buys:** no proxy, so `this.find()` is wrapped too.
- **Costs:** a compiler step or a JVM agent for the whole project.

An internal call to a wrapped method usually means one class does two jobs — split it. Take self-injection only when
the split makes the design worse, and AspectJ only when proxy limits keep hurting across the project.

</details>

## Working with proxies

### How do you tell a bean is a proxy?
<details><summary>Show answer</summary>

```java
AopUtils.isAopProxy(bean);          // any Spring proxy
AopUtils.isCglibProxy(bean);        // subclass proxy
AopUtils.isJdkDynamicProxy(bean);   // interface proxy
```

Without code, read the class name — in `getClass()`, a stack trace or the debugger:

- CGLIB: contains `$$SpringCGLIB$$` (older Spring: `$$EnhancerBySpringCGLIB$$`);
- JDK: a `$Proxy` class, e.g. `jdk.proxy2.$Proxy42`.

Ask `AopUtils`, or look for `$$SpringCGLIB$$` / `$Proxy` in the class name.

</details>

### How do you reach the object behind it?
<details><summary>Show answer</summary>

```java
OrderService real = AopTestUtils.getTargetObject(orders);           // one proxy layer down
OrderService core = AopTestUtils.getUltimateTargetObject(orders);   // through every layer
```

Mostly for tests — to check state or swap a dependency on the real object. A bean can be wrapped more than once, hence
the two methods. In app code `((Advised) bean).getTargetSource().getTarget()` does the same, but needing it there
usually means a design problem.

A call on the real object skips every wrapper: no transaction, no cache, no security check.

Tests may unwrap; app code shouldn't need to.

</details>

### Why does `getClass()` miss method annotations?
<details><summary>Show answer</summary>

```java
Method m = orders.getClass().getMethod("place", Order.class);
m.getAnnotation(Audited.class);          // null: m belongs to the proxy class
```

`orders.getClass()` is the proxy class, not yours:

- **CGLIB** — a subclass that overrides `place()`. The override has no annotations: Java doesn't pass method annotations
  down to overriding methods. Class annotations pass down only if marked `@Inherited`.
- **JDK** — a `$Proxy` class with only the interfaces' methods and none of your class's annotations.

Fix: get the real class first — this works for both proxy types:

```java
Class<?> type = AopUtils.getTargetClass(orders);              // OrderService, not the proxy
Audited a = type.getMethod("place", Order.class).getAnnotation(Audited.class);
```

The proxy class is not your class — reflect on the target class.

</details>
