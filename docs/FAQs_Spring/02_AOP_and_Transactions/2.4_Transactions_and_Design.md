# Transactions and Design

Running a transaction as code you call, and where its boundary belongs.

### What governs transaction design?
<details><summary>Show answer</summary>

[`@Transactional`](2.3_Transactions.md#what-does-transactional-do-around-a-call) makes the whole method one
transaction. Design is about where the boundary should be instead:

- [As a block of code](#how-do-you-run-a-transaction-without-the-annotation) — the same transaction without the
  annotation, for when [the boundary is not the method](#when-is-transactiontemplate-the-better-choice).
- [After the commit](#how-do-you-run-code-only-after-commit) — work that must wait until the data is really saved.
- [Outside the transaction](#why-keep-remote-calls-out-of-a-transaction) — remote calls it can't undo.
- [A separate transaction](#can-you-commit-part-of-a-transaction) — a status that must outlive the work.
- [The right annotation](#which-transactional-should-you-import) — Spring's, not Jakarta's.

Trigger: *a transaction covers only what it can undo — move the rest out of it (remote calls, after-commit work), or
into a transaction of its own (a status that must survive).*

</details>

## Programmatic

### How do you run a transaction without the annotation?
<details><summary>Show answer</summary>

```java
@Service
public class OrderService {
  private final TransactionTemplate tx;

  public OrderService(PlatformTransactionManager manager) {
    this.tx = new TransactionTemplate(manager);
  }

  public Long place(Order order) {
    return tx.execute(status -> {        // begin
      orders.save(order);
      stock.reserve(order);
      return order.getId();              // returns normally → commit; RuntimeException → rollback
    });
  }
}
```

`execute()` runs the block in a transaction and returns its result; `executeWithoutResult()` is the same with no result.
Settings go on the template: `setPropagationBehavior()`, `setIsolationLevel()`, `setReadOnly()`, `setTimeout()`.

The block can't throw checked exceptions — wrap them in a runtime exception, which also rolls back.

No proxy is involved, so it works anywhere the code runs.

Same begin, commit and rollback — written as a block you call instead of an annotation.

</details>

### When is `TransactionTemplate` the better choice?
<details><summary>Show answer</summary>

The annotation makes the whole method one transaction. The template is better when the boundary is not the method:

- **Only part of the method** — a slow HTTP call before or after the database writes
  [stays outside](#why-keep-remote-calls-out-of-a-transaction).
- **One transaction per item** — a bad item undoes only itself:

  ```java
  for (Item item : batch) {
    try {
      tx.executeWithoutResult(status -> importer.save(item));   // own transaction per item
    } catch (RuntimeException e) {
      failed.add(item);                                         // only this item is rolled back
    }
  }
  ```

- **No proxy on the path** — a call inside the same class, a `private` method, an object that is not a bean.
- **Settings known only at runtime** — e.g. a timeout read from config per call.

Cost: Spring API in business code and a few more lines.

Is the transaction exactly the method? Yes → annotation. No → template.

</details>

### How do you run code only after commit?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  events.publishEvent(new OrderPlaced(order.getId()));   // held until the transaction ends
}

@Component
class OrderMailer {
  @TransactionalEventListener                            // default phase: AFTER_COMMIT
  void on(OrderPlaced event) { mail.confirm(event.orderId()); }
}
```

An email sent inside `place()` goes out even if the transaction rolls back a moment later. The listener runs only after
a successful commit, and not at all on rollback. Other phases: `AFTER_ROLLBACK`, `AFTER_COMPLETION`, `BEFORE_COMMIT`.

Two traps:

- Publish with no transaction open and the listener is silently skipped (unless `fallbackExecution = true`).
- The transaction is already finished inside the listener — database writes there need their own transaction
  (`REQUIRES_NEW`).

Put after-commit work in a `@TransactionalEventListener`; it runs only once the data is really saved.

</details>

## Design

### Why keep remote calls out of a transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  payment.charge(order);           // HTTP call, 2 s — the connection and row locks are held all that time
  orders.markPaid(order);
}
```

Two problems:

- **Held resources** — the connection and any row locks stay taken during the call. A slow partner empties the pool,
  and other requests wait or time out.
- **No undo for the remote side** — if the commit fails after the charge went through, the customer is charged and no
  order exists. A rollback can't take back an HTTP call.

Fix: keep the transaction to database work only, and do the call outside it (e.g. with a
[`TransactionTemplate`](#when-is-transactiontemplate-the-better-choice) around just the database parts). Handle the
remote side's failure on its own terms: a status field and a retry, or an outbox table — write "charge this order" in
the same transaction, and let a separate job make the call.

A transaction should cover only what it can roll back.

</details>

### Can you commit part of a transaction?
<details><summary>Show answer</summary>

TODO: moved from [2.04_Flush.md](../../FAQs_Persistence/2_JPA_and_Hibernate/2.04_Flush.md)

No. A commit ends the transaction. A status that must be visible before the work finishes, or must stay `FAILED`
after the work rolls back, needs [its own transaction](2.5_Transaction_Settings.md#when-should-a-call-get-its-own-transaction).

Import with status `RUNNING` → `COMPLETED` / `FAILED`, driven by a method that has no transaction:

```java
public void runImport(long importId) {    // no @Transactional here or in any caller
  status.markRunning(importId, now());    // tx 1: RUNNING + start time, committed at once
  try {
    importer.importRows(importId);        // tx 2: inserts + COMPLETED, commit or roll back together
  } catch (RuntimeException e) {
    status.markFailed(importId, e.getMessage());  // tx 3: runs after tx 2 rolled back
  }
}
```

- `COMPLETED` goes in the same transaction as the rows. Either both commit or neither does, so the rows are never in
  while the status still says `RUNNING`.
- Catch outside `importRows`. The exception can come out of [its commit][commit-error], after the method body has
  finished. Inside the failed transaction, [nothing can commit][failed-rows].

[commit-error]: ../../FAQs_Persistence/2_JPA_and_Hibernate/2.04_Flush.md#why-does-a-constraint-error-appear-at-commit
[failed-rows]: ../../FAQs_Persistence/2_JPA_and_Hibernate/2.04_Flush.md#what-happens-to-flushed-rows-on-failure

A commit ends the transaction, so a status that must outlive the work can't share its transaction.

</details>

### Which `@Transactional` should you import?
<details><summary>Show answer</summary>

```java
import org.springframework.transaction.annotation.Transactional;   // Spring's: all settings
import jakarta.transaction.Transactional;                          // JTA's: fewer settings
```

Spring honours both, and with no settings they behave the same: `REQUIRED`, rollback on unchecked exceptions. The
Jakarta one has no `readOnly`, `isolation`, `timeout` or transaction manager name; propagation goes through `TxType`
(no `NESTED`); rollback rules are `rollbackOn` / `dontRollbackOn`.

The IDE often offers both. In a Spring app use Spring's, everywhere — a mix fails later, when someone adds
`readOnly = true` and it doesn't compile.

Spring's annotation for Spring apps; the Jakarta one only where code must not depend on Spring.

</details>

### Describe a code snippet #NN
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Service
@RequiredArgsConstructor
public class OrderService {

  private final OrderRepository orderRepository;
  private final PaymentRepository paymentRepository;

  public void confirmPayment(Long orderId, Long paymentId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    if (order.getStatus() != OrderStatus.NEW) {
      throw new IllegalStateException("order is not NEW");
    }

    Payment payment = paymentRepository.findById(paymentId).orElseThrow();
    if (!payment.getOrderId().equals(orderId)) {
      throw new IllegalStateException("payment belongs to another order");
    }

    order.setStatus(OrderStatus.PAID);
    payment.setStatus(PaymentStatus.CONFIRMED);
    save(order, payment);
  }

  @Transactional
  public void save(Order order, Payment payment) {
    orderRepository.save(order);
    paymentRepository.save(payment);
  }
}
```

</details>

<details><summary>Show answer</summary>

**What goes wrong:** `save` is meant to write both entities in one transaction, but it is called through `this`. The call
skips the Spring proxy, so `@Transactional` on `save` does nothing. The method runs as **four separate transactions**:
two reads, two writes. If the payment write fails, the order is already committed as `PAID`, so only half the change is
stored.

**How it runs (no Open Session In View):**
- **One transaction per call:** `SimpleJpaRepository` has `@Transactional(readOnly = true)` on the class and
  `@Transactional` on `save`. Each call with no transaction running starts its own, commits on return and closes its
  persistence context.
- **`REQUIRED` does not keep it open:** it joins a transaction only if one is running at the moment of the call. After
  `findById` returns, its transaction is gone, so the next call starts a new one.
- **Detached entities:** `order` and `payment` come back detached. Changes to them are not tracked, which is why the
  code calls `save`.
- **Extra select on save:** `save` on a detached entity with an id calls `merge`. It runs an extra `SELECT` for the
  current row, copies every field from the detached object onto it, then updates.
- **Separate rollbacks:** if `paymentRepository.save` throws, only its own transaction rolls back. There is no outer
  transaction to mark rollback-only.

**Correct fix: one transaction around read, check and write.**

```java
@Transactional
public void confirmPayment(Long orderId, Long paymentId) {
  Order order = orderRepository.findById(orderId).orElseThrow();
  Payment payment = paymentRepository.findById(paymentId).orElseThrow();
  // ...same checks
  order.setStatus(OrderStatus.PAID);
  payment.setStatus(PaymentStatus.CONFIRMED);
} // both updates flushed before commit; a runtime exception rolls back both
```

- **Managed entities, no `save`:** both entities stay managed in one persistence context. Dirty checking writes both
  updates before commit, so either both are stored or neither is. On a managed entity `save` only runs the `isNew`
  check and a `merge` that cascades over the associations and changes nothing, so it is dropped.
- **Proxy rule one level up:** the annotation works only when `confirmPayment` is called from another bean, not from
  another method of `OrderService`.

**Alternative: move `save` into another bean.**
- **Buys:** the two writes become one transaction, so there is no half-written state. When a slow step sits between
  check and write, such as a payment gateway call taking seconds, the write transaction stays short and no DB
  connection is held during the call.
- **Costs:** reads and checks still run in their own, already closed transactions. The status is checked on one state
  and written when it may already be different, so re-check inside the write transaction or use `@Version`.
- Without a slow step, as in this code, keep the correct fix above.

**Still open after the correct fix:** the two entities now change together, but concurrent requests can still cause
[lost update and write skew](#TODO-next-card).

Spring adds a transaction only to calls that come from outside the bean, never through `this`: one such call must cover
read, check and write.

</details>

</details>

### Describe a code snippet #NN
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Service
@RequiredArgsConstructor
public class PaymentService {

  private final PaymentRepository paymentRepository;

  @Transactional
  public void confirmPayment(Long orderId, Long paymentId) {
    if (paymentRepository.existsByOrderIdAndStatus(orderId, PaymentStatus.CONFIRMED)) {
      throw new IllegalStateException("order already paid");
    }
    Payment payment = paymentRepository.findById(paymentId).orElseThrow();
    payment.setStatus(PaymentStatus.CONFIRMED);
  }
}
```

</details>

<details><summary>Show answer</summary>

**What goes wrong:** two requests confirm two different payments, P1 and P2, of the same order at the same time. Both
run the check, both see no confirmed payment, each confirms its own payment, and both commit. The order ends up with two
confirmed payments. This is **write skew**: both transactions decide on the same read, then write different rows.

**Why the transaction does not help:**
- Each transaction writes only its own payment row. No row is written by both, so nothing conflicts at the row level.
- The other transaction's write changes the answer to the check: P2 becoming `CONFIRMED` makes T1's check false, but
  T1 has already passed it.
- `@Version` on `Payment` does not help: each payment row is changed by one transaction only, and nobody writes
  `Order`.
- Run one after another, the same code is correct: the second request sees P1 confirmed and throws. The bug exists only
  when the two run at the same time.

**Solution 1: pessimistic lock on the parent row** (explicit locking, `SELECT ... FOR UPDATE`)

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  Optional<Order> findForUpdateById(Long id);
}

@Transactional
public void confirmPayment(Long orderId, Long paymentId) {
  orderRepository.findForUpdateById(orderId).orElseThrow(); // lock taken here, order is not changed
  if (paymentRepository.existsByOrderIdAndStatus(orderId, PaymentStatus.CONFIRMED)) {
    throw new IllegalStateException("order already paid");
  }
  Payment payment = paymentRepository.findById(paymentId).orElseThrow();
  payment.setStatus(PaymentStatus.CONFIRMED);
}
```

- How: T2 waits on the order row until T1 commits. Its check then runs and sees P1 confirmed.
- Why the parent: the check looks for rows that are not there yet. In PostgreSQL a `FOR UPDATE` with an empty result
  locks nothing, so the lock goes on the parent `Order` row, which always exists. When `Payment` is part of the `Order`
  aggregate, this is called **locking the aggregate root**. If no parent row existed, you would create rows only to
  lock them: **materializing conflicts**.
- Limits: every path that confirms a payment must take this lock first; one path without it brings the bug back. The
  check must run after the lock. At READ COMMITTED each query sees the latest committed data. At REPEATABLE READ the
  check can still read the old snapshot. Requests for other orders do not wait.

**Solution 2: optimistic force increment on the parent** (`OPTIMISTIC_FORCE_INCREMENT`)

```java
@Entity
public class Order {
  @Id private Long id;
  @Version private Long version;
  // ...
}

public interface OrderRepository extends JpaRepository<Order, Long> {
  @Lock(LockModeType.OPTIMISTIC_FORCE_INCREMENT)
  Optional<Order> findWithVersionBumpById(Long id);
}
```

- How: `confirmPayment` calls `findWithVersionBumpById` first, as in solution 1. Hibernate raises the order's version
  before commit even though no field changed: `UPDATE orders SET version = 2 WHERE id = ? AND version = 1`. Both
  transactions now write the same row. The second one updates 0 rows and fails with `OptimisticLockException`. Write
  skew turns into a conflict on one row.
- No waiting. The cost is a failed transaction that must be retried. As in solution 1, every path must take it.

**Solution 3: database constraint** (partial unique index)

```sql
CREATE UNIQUE INDEX one_confirmed_payment_per_order
  ON payment (order_id)
  WHERE status = 'CONFIRMED';
```

- How: the database holds the rule itself. The second transaction's update to `CONFIRMED` breaks the index, and Spring
  throws `DataIntegrityViolationException`. JPA sends the update at flush, so the error comes at commit, not at
  `setStatus`.
- Covers every code path, including writes from outside the application.
- Limits: works only for rules a constraint can express. "At least two doctors on call" cannot be written as a
  constraint. Partial indexes are PostgreSQL syntax; other databases need other ways.

**Solution 4: serializable isolation** (Serializable Snapshot Isolation, SSI, in PostgreSQL)

```java
@Transactional(isolation = Isolation.SERIALIZABLE)
public void confirmPayment(Long orderId, Long paymentId) { /* unchanged */ }
```

- How in PostgreSQL: transactions run in parallel without blocking. The database tracks what each one read and wrote.
  When each transaction's write changes the other's read, it aborts one with a serialization error.
- No code change in the method, but every transaction that touches these rows must run at SERIALIZABLE.
- Cost: tracking overhead, some aborts that were not real conflicts, and retries.
- MySQL InnoDB SERIALIZABLE works differently: plain reads take shared locks, so transactions wait and can deadlock.

**Solution 5: lock outside the rows** (application lock, advisory lock)

- In-JVM lock per order id, for example a `ReentrantLock` from a map keyed by order id. Take it outside the
  transactional call, so it is held until commit. Works only with one application instance.
- Several instances: a lock in the database by key. PostgreSQL **advisory lock** `pg_advisory_xact_lock(orderId)` is
  released automatically at the end of the transaction.
- As in solution 1, every path must take the lock.

**Retry:** solutions 2, 3 and 4 end with a failed transaction. Retry from outside the transactional call; inside it, the
transaction is already marked for rollback. On retry the check sees P1 confirmed and throws, which is the right outcome.

Write skew is fixed by making the two transactions meet on one thing: a locked row, a shared written row, a constraint,
or the database's own tracking.

</details>

</details>
