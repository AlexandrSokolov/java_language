# Transactions

How a transaction works, from the database up to `@Transactional`, and how it ends.

### What governs Spring transactions?
<details><summary>Show answer</summary>

A `@Transactional` method is one database transaction around the whole method. The chapter builds it from the bottom
up; each layer needs the one below:

- [The database and JDBC](#what-is-a-database-transaction) — a transaction is a group of statements; JDBC groups them
  on [one connection with auto-commit off](#how-does-jdbc-group-statements).
- [JPA on its own](#how-does-jpa-start-a-transaction) — the same JDBC transaction, plus changes held
  [in memory](#what-does-the-persistence-context-hold) and [sent at flush](#how-does-flush-differ-from-commit).
- [How Spring runs it](#which-transaction-manager-runs-it) — a transaction manager does the begin and end, and keeps
  the connection [on the thread](#how-does-a-repository-find-the-open-transaction), so
  [other threads are outside it](#why-is-a-new-thread-outside-the-transaction).
- [Spring Data and your method](#why-does-save-work-without-transactional) — each repository call brings its own
  transaction; your `@Transactional` makes them [join one](#what-does-save-do-inside-a-running-transaction):
  [the whole picture](#what-does-transactional-do-around-a-call).
- [Rollback rules](#which-exceptions-roll-back-by-default) — what leaves the method decides commit or rollback.
- [Transactions and Design](2.4_Transactions_and_Design.md#what-governs-transaction-design) — the same transaction as
  code you call, and where its boundary belongs.
- [Settings](2.5_Transaction_Settings.md#which-transactional-settings-matter) — propagation, isolation, `readOnly`,
  timeout.

It runs on a proxy, so [internal calls](2.1_Proxies.md#why-does-an-internal-call-skip-cacheable) and
[`final` or `private` methods](2.1_Proxies.md#what-does-a-proxy-not-see) get no transaction.

Trigger: *statements grouped on one connection → JPA adds memory and flush → Spring keeps the connection on the thread →
repositories join your transaction → what leaves the method decides commit or rollback.*

</details>

## The Database and JDBC

### What is a database transaction?
<details><summary>Show answer</summary>

A transaction is a group of statements that the database:
- makes final together (**commit**) or 
- undoes together (**rollback**).

This all-or-nothing property is called **atomicity**.

</details>

### How does JDBC run statements by default?
<details><summary>Show answer</summary>

A new JDBC connection starts with **auto-commit** on: the driver commits after every statement. So each statement is
its own transaction, and reads and writes both work.

```java
Connection con = dataSource.getConnection();   // auto-commit is on
Statement st = con.createStatement();
st.executeUpdate("INSERT INTO orders ...");    // final right now
st.executeUpdate("INSERT INTO items ...");     // fails → the order row stays
```

There is no "no transaction" mode. A statement you did not group gets a transaction of its own.

</details>

### What breaks under auto-commit?
<details><summary>Show answer</summary>

Under [auto-commit](#how-does-jdbc-run-statements-by-default) every statement is its own transaction and commits when
it ends. Nothing can span two statements:

- **No all-or-nothing (atomicity):** the first INSERT is final before the second runs. If the second fails, the first
  stays, and the change is half done. This breaks even with one user.
- **Read, then write: lost update, write skew.** You read data and write based on what you read.
  Another transaction changes the data in between. 
- **Read, then read: non-repeatable read, read skew.** Another transaction commits between your two SELECTs.
  You lose a consistent view of the data across multiple statements.

Every guarantee a transaction gives, including all-or-nothing and locks, lasts one statement here.

</details>

### How to run a JDBC transaction?
<details><summary>Show answer</summary>

```java
try (Connection con = dataSource.getConnection();
     Statement st = con.createStatement()) {
  con.setAutoCommit(false);                      // begin: Connection has no begin()
  try {
    st.executeUpdate("INSERT INTO orders ...");  // same connection
    st.executeUpdate("INSERT INTO items ...");   // same connection
    con.commit();                                // end: both become final
  } catch (Exception e) {                        // any failure, not only SQLException
    con.rollback();                              // end: both are undone
    throw e;
  } finally {
    con.setAutoCommit(true);                     // the pool hands this connection to the next caller
  }
}
```

- **Begin:** `setAutoCommit(false)`. JDBC has no `begin()` call, so turning auto-commit off is the begin.
- **Same connection:** every statement in the group runs on this one connection. A statement on another connection is
  outside the transaction.
- **End:** `commit()` makes all of them final; `rollback()` undoes all of them.
- **Clean up:** `close()` on a pooled connection does not close it; it goes back to the pool with auto-commit still
  off. HikariCP resets it on return, but JDBC does not require that, so the code turns it back on itself.

Turn auto-commit off to begin, stay on one connection, end with commit or rollback, then turn it back on.

</details>

## JPA on its own

### How does JPA start a transaction?
<details><summary>Show answer</summary>

```java
EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();
try {
  tx.begin();                              // takes a connection, turns auto-commit off
  Order order = em.find(Order.class, id);  // SELECT
  order.setName(name);                     // in memory only, no SQL yet
  tx.commit();                             // sends the UPDATE, then JDBC commit
} catch (RuntimeException e) {
  if (tx.isActive()) tx.rollback();        // commit() may already have ended it
  throw e;
} finally {
  em.close();                              // closes the persistence context
}
```

- **Begin:** `tx.begin()` makes Hibernate take a connection and turn
  [auto-commit off](#how-does-jdbc-group-statements) on it (if it is on). Underneath, the JPA begin is the JDBC begin.
- **Commit:** `tx.commit()` first [sends the changes held in memory](#how-does-flush-differ-from-commit) as SQL, then runs
  the JDBC `commit()`.
- **Rollback:** `tx.rollback()` runs the JDBC `rollback()`.

A JPA transaction is a JDBC transaction underneath, with one extra step before the commit: send the changes held in
memory.

</details>

### How does flush differ from commit?
<details><summary>Show answer</summary>

- **Flush:** Hibernate compares each loaded entity with its copy (field term: **dirty checking**) and sends INSERT,
  UPDATE or DELETE for what changed. The rows change, but only this transaction sees them, and a rollback undoes them.
- **Commit:** makes the flushed changes final and visible to other transactions.

Flush sends the SQL; commit makes it final.

</details>

## How Spring runs it

### Who runs a Spring transaction — which options?
<details><summary>Show answer</summary>

`@Transactional` only marks where a transaction starts and ends. A `PlatformTransactionManager` bean does the
[actual begin, commit and rollback](#how-to-run-a-jdbc-transaction). Which one depends on how you reach the database:

- `DataSourceTransactionManager` / `JdbcTransactionManager` — plain JDBC, `JdbcTemplate`, MyBatis;
- `JpaTransactionManager` — JPA/Hibernate, and JDBC code on the same `DataSource`;
- `JtaTransactionManager` — one transaction across several resources (two databases, a database and a message queue).

Spring Boot picks one from the classpath — with the JPA starter, `JpaTransactionManager`.

</details>

### How does a repository find the open transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);    // finds the connection on the thread
  stock.reserve(order);  // same connection, same transaction
}
```

At begin, the transaction manager binds the transaction's connection to the current thread, in a **ThreadLocal**
(a variable that holds a separate value for each thread). With JPA it binds the `EntityManager`, which holds the
connection.

A repository looks there first:

- found → uses it, so the work joins the transaction;
- not found → takes a fresh connection, outside any transaction.

The transaction lives on the thread. So only code on the same thread joins.

</details>

### Side work must commit separately — which design?
<details><summary>Show answer</summary>

The main transaction saves an order. Side work (an audit row, a notification) must commit on its own, so that its
failure does not roll back the order. One question picks the design: must the side work happen if the order rolls back?

- **Yes, always** → run it in [its own new transaction](#how-to-keep-a-write-after-a-rollback). 
  Example: audit of a failed attempt.
- **Only if the order commits** → run it in an [after-commit listener](#how-to-run-work-only-after-a-commit). 
  Example: a confirmation for a placed order.

Must it survive a rollback? Yes → new transaction. Only on success → after commit.

</details>

### How to keep a write after a rollback?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  audit.logAttempt(order);  // own transaction: committed when this call returns
  orders.save(order);       // fails → place() rolls back, the audit row stays
}

// in AuditService
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logAttempt(Order order) {
  auditRepo.save(new AuditEntry(order.getId()));
}
```

`REQUIRES_NEW` always opens a new transaction, even when one is already open. It commits when `logAttempt()` returns,
so a later rollback of `place()` cannot undo it. With the default `REQUIRED`, `logAttempt()` would join `place()` and
roll back with it.

</details>

### Calling a `REQUIRES_NEW` method — what to watch?
<details><summary>Show answer</summary>

- **The outer transaction waits and keeps its connection.** While the inner one runs, the outer is paused but still
  holds its connection, so each such call needs two connections at once. Under load, every thread can hold one and wait
  for a second; the pool runs out and the threads hang until the pool timeout.
- **An inner failure reaches the outer.** The exception leaves `logAttempt()` and rolls back `place()` too. Catch it if
  the outer must go on. Catching is enough here: because the inner method has its own transaction, the exception rolls
  back and marks only that one. The outer is not marked for rollback and commits normally. (With `REQUIRED` catching is
  not enough: the shared transaction is already marked, and the commit fails.)

```java
try {
  audit.logAttempt(order);      // REQUIRES_NEW: a failure marks only the inner transaction
} catch (RuntimeException e) {
  log.warn("audit failed", e);  // the order goes on and commits
}
```

A separate commit, but the same thread: the outer waits for it, and its error comes back to the outer.

</details>

### How to run work only after a commit?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  events.publishEvent(new OrderPlaced(order.getId()));  // held until place() commits
}

// in a listener bean
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)  // required, see below
public void onPlaced(OrderPlaced event) {
  notifications.save(new Notification(event.orderId()));
}
```

The event waits until `place()` commits. If `place()` rolls back, the listener never runs.

`REQUIRES_NEW` is required. The order of steps is commit → listener → cleanup, so while the listener runs, the old,
already committed transaction is still on the thread. `REQUIRED` joins it, the SQL runs, but no commit follows, and the
write is silently lost.

</details>

### Does after-commit work block the caller?
<details><summary>Show answer</summary>

Yes, by default. The listener runs on the same thread right after the commit, so `place()` returns only when the
listener is done. A slow listener (an email, an HTTP call) slows every order.

Fix: add `@Async` (and `@EnableAsync` on a config class). The listener then runs on another thread, and `place()`
returns at once.

```java
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onPlaced(OrderPlaced event) { ... }
```

</details>

### After-commit work fails — what happens?
<details><summary>Show answer</summary>

The order is already committed, so nothing rolls it back. The side work is lost, and nothing retries it.

- **Same thread (default):** the exception reaches the caller of `place()`, even though the order is saved. The caller
  may treat it as a failed order and retry, which creates a duplicate.
- **With `@Async`:** the exception stays on the other thread and is only logged. The caller never learns of it.

After the commit the order and the side work no longer share a fate: the order stays, the side work can vanish.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  executor.submit(() -> auditRepo.save(new AuditEntry(order.getId())));
}
```

</details>

<details><summary>Show answer</summary>

The task runs on another thread. The transaction's connection is bound to the calling thread, so the task finds nothing
and `auditRepo.save()` runs in its own transaction, outside `place()`:

- `place()` rolls back → the audit row stays;
- the task may run before `place()` commits → it cannot see the new order row yet. This depends on timing, so it fails
  only sometimes.

Fix: first [decide which design you need](#side-work-must-commit-separately--which-design). 
- If the audit must stay even on rollback, use [its own new transaction](#how-to-keep-a-write-after-a-rollback). 
- If it should run only on success, use an [after-commit listener](#how-to-run-work-only-after-a-commit).

A transaction belongs to one thread; work handed to another thread is outside it.

</details>

</details>

### What can JPA do without a transaction?
<details><summary>Show answer</summary>

The method has no `@Transactional`. What works depends on how you reach JPA:

- **`EntityManager` injected by Spring.** Each call opens a persistence context, runs, and closes it right after. Its
  SQL runs in [auto-commit](#how-does-jdbc-run-statements-by-default).
  - **Reads work:** `find()` and queries run. The entity comes back **detached**: nothing tracks it, so changes to it are
    never sent. The exception is open-in-view, which keeps one persistence context open for the whole web request.
  - **Writes fail:** `persist()`, `merge()`, `remove()` and `flush()` throw `TransactionRequiredException`. Changes reach
    the database only at [flush](#how-does-flush-differ-from-commit), and flush needs a transaction.
  ```java
  @PersistenceContext EntityManager em;
  
  public void update(long id) {              // no @Transactional
    Order order = em.find(Order.class, id);  // works: context opens for this call, then closes
    order.setName("x");                      // lost: the entity is detached
    em.persist(new Order());                 // throws TransactionRequiredException
  }
  ```

- **Spring Data repository.** Its methods [bring their own transaction](#why-does-save-work-without-transactional), so
  `save()` works. Each call commits on its own, and the returned entity is detached after the call.


No transaction: `EntityManager` reads one call at a time and cannot write. A repository writes, but each call is its
own transaction.

</details>

## Spring Data and your method

### Why does `save()` work without `@Transactional`?
<details><summary>Show answer</summary>

```java
public void place(Order order) {   // no @Transactional
  em.persist(order);               // throws TransactionRequiredException
  orders.save(order);              // works: the repository starts its own transaction, INSERT, commit
}
```

`orders` is a proxy too. Spring Data's base class `SimpleJpaRepository` carries its own `@Transactional`: read-only
for find methods, normal for `save()` and `delete()`. So each call runs through the same
[proxy and transaction manager](#which-transaction-manager-runs-it) as your own `@Transactional` method: begin, run,
commit, close the persistence context.

An inherited repository method never runs without a transaction: if you did not start one, it starts its own.

</details>

### What breaks when repository calls stand alone?
<details><summary>Show answer</summary>

```java
public void place(Order order) {             // no @Transactional
  orders.save(order);                        // transaction 1: committed here
  stock.reserve(order);                      // throws → the order row stays
}

public int countItems(long id) {             // no @Transactional
  Order order = orders.findById(id).get();   // transaction ends, persistence context closes
  return order.getItems().size();            // lazy list → LazyInitializationException
}
```

Each call commits on its own, so you get the same losses as [under auto-commit](#what-breaks-under-auto-commit), one
level up: no all-or-nothing, and races between read-then-write and read-then-read across calls.

New at this level, **lazy fields**: the persistence context closed when `findById()` returned, so a lazy field has
nothing to load from. Open-in-view (on by default in Spring Boot web apps) keeps one open for the whole request and
hides this.

Each repository call is its own transaction, so you lose everything a transaction spanning the method would give you.

</details>

### What does `save()` do inside a running transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);     // finds the running transaction on the thread → joins it, no commit
  stock.reserve(order);   // joins too
}                         // commit happens here, once
```

The repository's `@Transactional` uses the default setting **REQUIRED**: if a transaction is already on the thread,
join it; if not, start one. Joining means the same connection, the same persistence context, and no commit at the end
of `save()`. Only the method that started the transaction commits.

Field term: [**propagation**](2.5_Transaction_Settings.md#what-does-propagation-decide), meaning what a
`@Transactional` method does when a transaction is already running.

The outermost `@Transactional` starts and commits; every inner one only joins.

</details>

### What does `@Transactional` do around a call?
<details><summary>Show answer</summary>

```java
@Service
public class OrderService {
  @Transactional
  public void place(Order order) {
    orders.save(order);
    stock.reserve(order);   // throws RuntimeException → the saved order is undone too
  }
}
```

A call from another bean goes through the [proxy](2.1_Proxies.md#what-is-a-spring-proxy). When no transaction is
running yet:

- **Begin:** open a persistence context, take a connection and turn auto-commit off, put both on the thread.
- **Run:** `place()` runs; `orders.save()` and `stock.reserve()` [join](#what-does-save-do-inside-a-running-transaction),
  so they use the same connection and the same persistence context.
- **End:** flush, then commit. A `RuntimeException` or `Error` causes a rollback instead;
  [a checked exception still commits](#which-exceptions-roll-back-by-default).
- **Clean up:** undo the begin steps: take both off the thread, close the persistence context, turn auto-commit back
  on, return the connection to the pool.

One connection and one persistence context for the whole method, so all its writes commit or roll back together.
If a transaction is already running, `place()` joins it and does none of these steps.

</details>

## Rollback rules

### Which exceptions roll back by default?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) throws OutOfStockException {
  orders.save(order);
  stock.reserve(order);            // throws checked OutOfStockException → the order row is COMMITTED
}
```

- `RuntimeException` or `Error` leaves the method → rollback.
- A checked exception leaves the method → commit.

The rule comes from EJB: a checked exception was seen as an expected business outcome, not a failure. In practice it
surprises people, as above — the order is saved even though stock failed.

Unchecked rolls back, checked commits — unless you [say otherwise](#how-do-you-roll-back-on-a-checked-exception).

</details>

### How do you roll back on a checked exception?
<details><summary>Show answer</summary>

```java
@Transactional(rollbackFor = OutOfStockException.class)
public void place(Order order) throws OutOfStockException { /* ... */ }
```

`rollbackFor` adds exceptions that roll back; `rollbackFor = Exception.class` covers every checked exception. A rule
also matches subclasses.

The reverse is `noRollbackFor`: a runtime exception listed there commits instead.

```java
@Transactional(noRollbackFor = CouponExpiredException.class)
```

Name the exception in `rollbackFor`; use `noRollbackFor` for the reverse.

</details>

### Catching to avoid rollback — does it work?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  try {
    stock.reserve(order);           // throws an unchecked exception
  } catch (RuntimeException e) {
    log.warn("reserve failed", e);  // intent: keep the order anyway
  }
}
```

The developer catches the exception so that the order is still saved. Whether that works depends on what
`reserve()` is:

- **Plain code** → works. No exception leaves `place()`, so it commits.
- **`@Transactional`, joined this transaction** → does not work. Its proxy marked the shared transaction for rollback
  as the exception left `reserve()`. Catching does not remove the mark, and the commit fails with
  [`UnexpectedRollbackException`](2.5_Transaction_Settings.md#why-does-the-outer-commit-throw-unexpectedrollbackexception).
- **`REQUIRES_NEW`** → works. Only its own transaction is marked, so
  [catching is enough](#calling-a-requires_new-method--what-to-watch).

A catch hides the exception from `place()`'s proxy, but not from a proxy it already passed through.

</details>

### How do you roll back without throwing?
<details><summary>Show answer</summary>

**When you need it:** the method has already written something, then meets an expected outcome (out of stock), and
must report it as a normal return value, not an exception. The writes must be undone, but nothing is thrown, so the
proxy would commit.

First try to avoid it: check before you write (reserve stock, then save the order), or throw and let the caller turn
the exception into a result. Use this only when neither fits. It puts Spring API into business code.

**How:**

```java
@Transactional
public Result place(Order order) {
  orders.save(order);
  if (!stock.tryReserve(order)) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    return Result.OUT_OF_STOCK;     // returns normally, but the proxy rolls back
  }
  return Result.OK;
}
```

`setRollbackOnly()` marks the current transaction. When the method returns, the proxy sees the mark and rolls back
instead of committing. With a `TransactionTemplate`, call `status.setRollbackOnly()` on the status it passes in.

A normal result that must still undo the writes: mark the status rollback-only.

</details>
