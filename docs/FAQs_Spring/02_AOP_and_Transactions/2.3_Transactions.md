# Transactions

How Spring runs a transaction around a method, and how it ends.

### What governs Spring transactions?
<details><summary>Show answer</summary>

A call to a `@Transactional` method goes through a proxy, which opens a transaction, runs the method, and then commits
or rolls back. Each part of the chapter follows from that:

- [What happens around the call](#what-does-transactional-do-around-a-call) — the proxy starts it, a
  [transaction manager](#which-transaction-manager-runs-it) does the work, and the connection
  [rides on the thread](#how-does-a-repository-find-the-open-transaction), so
  [other threads are outside it](#why-is-a-new-thread-outside-the-transaction).
- [How it ends](#which-exceptions-roll-back-by-default) — what leaves the method decides commit or rollback.
- [Without the annotation](#how-do-you-run-a-transaction-without-the-annotation) — the same thing as a block of code
  you call, plus [work that must wait for the commit](#how-do-you-run-code-only-after-commit).
- [Design](#why-keep-remote-calls-out-of-a-transaction) — keep the transaction to what it can undo, and
  [use the right annotation](#which-transactional-should-you-import).
- [Settings](2.4_Transaction_Settings.md#which-transactional-settings-matter) — propagation, isolation, `readOnly`,
  timeout.

It runs on a proxy, so [internal calls](2.1_Proxies.md#why-does-an-internal-call-skip-cacheable) and
[`final` or `private` methods](2.1_Proxies.md#what-does-a-proxy-not-see) get no transaction.

Trigger: *proxy opens it → connection sits on the thread → method runs → what leaves the method decides commit or
rollback.*

</details>

## How it runs

### What does `@Transactional` do around a call?
<details><summary>Show answer</summary>

```java
@Service
public class OrderService {
  @Transactional
  public void place(Order order) {
    orders.save(order);
    stock.reserve(order);          // throws RuntimeException → the saved order is undone too
  }
}
```

A call from another bean goes through the [proxy](2.1_Proxies.md#what-is-a-spring-proxy), in this order:

- take a connection from the pool and turn auto-commit off;
- put the connection on the current thread;
- run `place()` — `orders.save()` and `stock.reserve()` both use that one connection;
- method returns normally → commit; a `RuntimeException` or `Error` leaves it → rollback;
- turn auto-commit back on, take the connection off the thread, give it back to the pool.

One connection for the whole method, opened before it and closed after it — so all its writes commit or roll back
together.

</details>

### How does a repository find the open transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);              // no connection passed in — the repository finds it on the thread
  stock.reserve(order);
}
```

When the transaction starts, the transaction manager stores its connection in a `ThreadLocal` map
(`TransactionSynchronizationManager`), keyed by the `DataSource`. `JdbcTemplate`, the JPA `EntityManager` and Spring
Data repositories look there first:

- found → use that connection, so the work is part of the transaction;
- not found → take a fresh connection, outside any transaction.

So only code on the same thread, using the same `DataSource`, joins. Code that calls `dataSource.getConnection()`
directly skips this lookup and works outside the transaction.

The transaction lives on the thread; anyone who asks on that thread gets the same connection.

</details>

### Why is a new thread outside the transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  executor.submit(() -> audit.save(order));   // another thread: finds no transaction
}
```

The connection is stored on the calling thread. The new thread finds nothing there, so `audit.save()` runs on its own
connection — in its own transaction, or none:

- `place()` rolls back → the audit row stays;
- the task may run before `place()` commits → it can't see the new order row yet.

The same happens with `@Async`, `CompletableFuture`, parallel streams and any executor —
[the transaction does not cross threads][threads].

[threads]: ../../FAQs_Concurrency/7_Architecture_Tradeoffs_and_Pitfalls/7.06_Context_and_Transaction_Boundaries.md

Fix: start the background work [after the commit](#how-do-you-run-code-only-after-commit), or give the other thread its
own transaction on purpose.

A transaction belongs to one thread; work handed to another thread is outside it.

</details>

### Which transaction manager runs it?
<details><summary>Show answer</summary>

`@Transactional` only marks the boundary. The work is done by a `PlatformTransactionManager` bean:

- `DataSourceTransactionManager` / `JdbcTransactionManager` — plain JDBC, `JdbcTemplate`, MyBatis;
- `JpaTransactionManager` — JPA/Hibernate, and JDBC code on the same `DataSource`;
- `JtaTransactionManager` — one transaction across several resources (two databases, a database and a message queue).

Spring Boot picks one from the classpath — with the JPA starter, `JpaTransactionManager`.

With two databases there are two managers, and you must name the one you want:

```java
@Transactional("billingTransactionManager")
public void charge(Invoice invoice) { /* ... */ }
```

Without a name and without `@Primary`, Spring can't pick and the call fails. And a transaction from one manager covers
only its own database: writes to the other one are not rolled back with it.

The annotation marks where; the manager does the work — for its own resource only.

</details>

## Rollback rules

### Which exceptions roll back by default?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) throws OutOfStockException {
  orders.save(order);
  stock.reserve(order);            // throws checked OutOfStockException → the order row is COMMITTED
}
```

- `RuntimeException` or `Error` leaves the method → rollback.
- A checked exception leaves the method → commit.

The rule comes from EJB: a checked exception was seen as an expected business outcome, not a failure. In practice it
surprises people, as above — the order is saved even though stock failed.

Unchecked rolls back, checked commits — unless you [say otherwise](#how-do-you-roll-back-on-a-checked-exception).

</details>

### How do you roll back on a checked exception?
<details><summary>Show answer</summary>

```java
@Transactional(rollbackFor = OutOfStockException.class)
public void place(Order order) throws OutOfStockException { /* ... */ }
```

`rollbackFor` adds exceptions that roll back; `rollbackFor = Exception.class` covers every checked exception. A rule
also matches subclasses.

The reverse is `noRollbackFor`: a runtime exception listed there commits instead.

```java
@Transactional(noRollbackFor = CouponExpiredException.class)
```

Name the exception in `rollbackFor`; use `noRollbackFor` for the reverse.

</details>

### Why does a caught exception not roll back?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  try {
    stock.reserve(order);          // throws RuntimeException
  } catch (RuntimeException e) {
    log.warn("reserve failed", e); // swallowed → method returns normally → commit
  }
}
```

The proxy decides at the end: did an exception come out of the method? Here none does, so it commits — the order is
saved without stock.

Fix: rethrow, or [mark the transaction for rollback](#how-do-you-roll-back-without-throwing).

One twist: if `stock.reserve()` is itself a `@Transactional` method that joined this transaction, its own proxy already
marked the transaction for rollback when the exception passed through it. Catching it later doesn't undo that mark,
and the commit at the end fails with `UnexpectedRollbackException` —
[why](2.4_Transaction_Settings.md#why-does-the-outer-commit-throw-unexpectedrollbackexception).

Only an exception that leaves the method causes a rollback; catch it and you have chosen to commit.

</details>

### How do you roll back without throwing?
<details><summary>Show answer</summary>

```java
@Transactional
public Result place(Order order) {
  orders.save(order);
  if (!stock.tryReserve(order)) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    return Result.OUT_OF_STOCK;    // returns normally, but the proxy rolls back
  }
  return Result.OK;
}
```

`setRollbackOnly()` marks the current transaction. When the method returns, the proxy sees the mark and rolls back
instead of committing. With a `TransactionTemplate`, call `status.setRollbackOnly()` on the status it passes in.

Cost: Spring API inside business code. Throwing an exception is usually cleaner; use this when the method must return
a normal result.

Mark the status rollback-only; the proxy rolls back even though the method returned.

</details>

## Programmatic

### How do you run a transaction without the annotation?
<details><summary>Show answer</summary>

```java
@Service
public class OrderService {
  private final TransactionTemplate tx;

  public OrderService(PlatformTransactionManager manager) {
    this.tx = new TransactionTemplate(manager);
  }

  public Long place(Order order) {
    return tx.execute(status -> {        // begin
      orders.save(order);
      stock.reserve(order);
      return order.getId();              // returns normally → commit; RuntimeException → rollback
    });
  }
}
```

`execute()` runs the block in a transaction and returns its result; `executeWithoutResult()` is the same with no result.
Settings go on the template: `setPropagationBehavior()`, `setIsolationLevel()`, `setReadOnly()`, `setTimeout()`.

The block can't throw checked exceptions — wrap them in a runtime exception, which also rolls back.

No proxy is involved, so it works anywhere the code runs.

Same begin, commit and rollback — written as a block you call instead of an annotation.

</details>

### When is `TransactionTemplate` the better choice?
<details><summary>Show answer</summary>

The annotation makes the whole method one transaction. The template is better when the boundary is not the method:

- **Only part of the method** — a slow HTTP call before or after the database writes
  [stays outside](#why-keep-remote-calls-out-of-a-transaction).
- **One transaction per item** — a bad item undoes only itself:

  ```java
  for (Item item : batch) {
    try {
      tx.executeWithoutResult(status -> importer.save(item));   // own transaction per item
    } catch (RuntimeException e) {
      failed.add(item);                                         // only this item is rolled back
    }
  }
  ```

- **No proxy on the path** — a call inside the same class, a `private` method, an object that is not a bean.
- **Settings known only at runtime** — e.g. a timeout read from config per call.

Cost: Spring API in business code and a few more lines.

Is the transaction exactly the method? Yes → annotation. No → template.

</details>

### How do you run code only after commit?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  events.publishEvent(new OrderPlaced(order.getId()));   // held until the transaction ends
}

@Component
class OrderMailer {
  @TransactionalEventListener                            // default phase: AFTER_COMMIT
  void on(OrderPlaced event) { mail.confirm(event.orderId()); }
}
```

An email sent inside `place()` goes out even if the transaction rolls back a moment later. The listener runs only after
a successful commit, and not at all on rollback. Other phases: `AFTER_ROLLBACK`, `AFTER_COMPLETION`, `BEFORE_COMMIT`.

Two traps:

- Publish with no transaction open and the listener is silently skipped (unless `fallbackExecution = true`).
- The transaction is already finished inside the listener — database writes there need their own transaction
  (`REQUIRES_NEW`).

Put after-commit work in a `@TransactionalEventListener`; it runs only once the data is really saved.

</details>

## Design

### Why keep remote calls out of a transaction?
<details><summary>Show answer</summary>

```java
@Transactional
public void place(Order order) {
  orders.save(order);
  payment.charge(order);           // HTTP call, 2 s — the connection and row locks are held all that time
  orders.markPaid(order);
}
```

Two problems:

- **Held resources** — the connection and any row locks stay taken during the call. A slow partner empties the pool,
  and other requests wait or time out.
- **No undo for the remote side** — if the commit fails after the charge went through, the customer is charged and no
  order exists. A rollback can't take back an HTTP call.

Fix: keep the transaction to database work only, and do the call outside it (e.g. with a
[`TransactionTemplate`](#when-is-transactiontemplate-the-better-choice) around just the database parts). Handle the
remote side's failure on its own terms: a status field and a retry, or an outbox table — write "charge this order" in
the same transaction, and let a separate job make the call.

A transaction should cover only what it can roll back.

</details>

### Which `@Transactional` should you import?
<details><summary>Show answer</summary>

```java
import org.springframework.transaction.annotation.Transactional;   // Spring's: all settings
import jakarta.transaction.Transactional;                          // JTA's: fewer settings
```

Spring honours both, and with no settings they behave the same: `REQUIRED`, rollback on unchecked exceptions. The
Jakarta one has no `readOnly`, `isolation`, `timeout` or transaction manager name; propagation goes through `TxType`
(no `NESTED`); rollback rules are `rollbackOn` / `dontRollbackOn`.

The IDE often offers both. In a Spring app use Spring's, everywhere — a mix fails later, when someone adds
`readOnly = true` and it doesn't compile.

Spring's annotation for Spring apps; the Jakarta one only where code must not depend on Spring.

</details>

### Can you commit part of a transaction?
<details><summary>Show answer</summary>

No. A commit ends the transaction. A status that must be visible before the work finishes, or must stay `FAILED`
after the work rolls back, needs its own transaction.

Import with status `RUNNING` → `COMPLETED` / `FAILED`, driven by a method that has no transaction:

```java
public void runImport(long importId) {    // no @Transactional here or in any caller
  status.markRunning(importId, now());    // tx 1: RUNNING + start time, committed at once
  try {
    importer.importRows(importId);        // tx 2: inserts + COMPLETED, commit or roll back together
  } catch (RuntimeException e) {
    status.markFailed(importId, e.getMessage());  // tx 3: runs after tx 2 rolled back
  }
}
```

- `COMPLETED` goes in the same transaction as the rows. Either both commit or neither does, so the rows are never in
  while the status still says `RUNNING`.
- Catch outside `importRows`. The exception can come out of [its commit](#why-does-a-constraint-error-appear-at-commit),
  after the method body has finished. Inside the failed transaction, [nothing can commit](#what-happens-to-flushed-rows-on-failure).

A commit ends the transaction, so a status that must outlive the work can't share its transaction.

</details>
