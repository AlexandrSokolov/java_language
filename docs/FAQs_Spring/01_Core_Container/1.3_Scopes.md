# Bean Scopes

- Singleton, prototype, request, session.

- Singleton beans and shared state across threads.

### How many instances of a bean exist?
<details><summary>Show answer</summary>

A bean's **scope** decides how many instances exist and how long each one lives. 
You pick one of the [available scopes](#what-scopes-exist) with `@Scope`, on the class or on the `@Bean` method.

</details>

### What bean scopes exist?
<details><summary>Show answer</summary>

- **Core, in every container**
  - `singleton` (the default) — one per bean definition in the container, not one per class
  - `prototype` — a new one each time the bean is requested (each injection, each `getBean()` call)
- **Web, only in a web application**
  - `request` — one per HTTP request
  - `session` — one per HTTP session
  - `application` — one per `ServletContext`
  - `websocket` — one per WebSocket session
- **Added by other Spring projects, or by you**
  - Spring Batch: `step` and `job` — one per step run, one per job run
  - Spring Cloud: `refresh` — one until the configuration refreshes, then a new one
  - `thread` (`SimpleThreadScope`) — one per thread, but not registered by default
  - your own — register a custom `Scope` implementation under a name you choose

Every scope answers one question: one instance per what? 
Per definition, per call, per web lifetime, or per lifetime you add.

</details>

### Spring singleton vs GoF singleton?
<details><summary>Show answer</summary>

- Classic (GoF) singleton: the class enforces it (private constructor, static field), so one instance per class.
- Spring singleton: the container enforces it, one instance per [bean definition](#what-bean-scopes-exist). 
  Two definitions of the same class give two instances, and `new` on the class still works.

Spring's singleton is a promise of the container, not a property of the class.

</details>

### `application` scope vs singleton?
<details><summary>Show answer</summary>

- Singleton: one per `ApplicationContext`.
- `application`: one per `ServletContext` — shared by every Spring context in the same web app (e.g. the root context
  and a `DispatcherServlet` context), and stored as a `ServletContext` attribute.

`application` scope is per web app; singleton is per Spring context.

</details>

### What happens to a prototype bean after injection?
<details><summary>Show answer</summary>

Spring creates a [prototype](#what-bean-scopes-exist), injects it and runs its init callbacks, then lets go: 
the container keeps no reference to it. So destroy callbacks (`@PreDestroy`) never run, not even when the context closes.
A prototype that opens a file or a connection in its init method and closes it in `@PreDestroy` leaks it, unless the
caller closes it by hand.

Spring builds a prototype and walks away.

</details>

### Which beans can be injected into which?
<details><summary>Show answer</summary>

A bean gets its dependencies once, when Spring creates it, and keeps them for its whole life.
So it can safely hold a bean that lives at least as long as it does, and not one that lives shorter.

- Safe: a request or session bean holding a singleton, or a singleton holding a singleton. The held bean already
  exists and outlives the holder.
- Breaks silently: a singleton holding a [prototype](#why-does-a-prototype-in-a-singleton-stay-one-instance)
  keeps the one instance it got at startup: no error, but a new one is never made. Fix: inject an
  [`ObjectProvider`](#how-do-you-get-a-fresh-instance-on-each-use) and ask on each use.
- Breaks at startup: a singleton holding a [request bean](#what-happens-when-a-singleton-needs-a-request-bean)
  with no proxy has no request to get: singletons are built at startup, before any request exists. Fix: inject a
  [scoped proxy](#how-does-a-scoped-proxy-work), which looks up the real bean on each call.

A bean must not outlive what it holds: with a prototype the bug is silent, with a request bean startup fails.

</details>

### Why does a prototype in a singleton stay one instance?
<details><summary>Show answer</summary>

```java
@Component
@Scope("prototype")
class ReportData { }

@Service
class ReportGenerator {
  private final ReportData data;

  ReportGenerator(ReportData data) { this.data = data; }   // injected once

  void generate() { /* always the same ReportData */ }
}
```

The singleton is created once, so its dependencies are injected once. The prototype is created for that one injection,
and every later call to `generate()` uses the same object.

A prototype is new per request to the container — and the singleton asked only once.

</details>

### How do you get a fresh instance on each use?
<details><summary>Show answer</summary>

```java
@Component
@Scope("prototype")
class ReportData { }

@Service
class ReportGenerator {
  private final ObjectProvider<ReportData> data;

  ReportGenerator(ObjectProvider<ReportData> data) { this.data = data; }   // injected once

  void generate() {
    ReportData d = data.getObject();   // a new ReportData on each call
  }
}
```

- `ObjectProvider<ReportData>` — call `getObject()` each time you need a new one.
- `@Lookup` method — a method Spring overrides to return a new bean on each call.
- `jakarta.inject.Provider<ReportData>` — the standard version of `ObjectProvider`.
- A [scoped proxy](#how-does-a-scoped-proxy-work) — injected once, looks up the target on every call.
- `ApplicationContext.getBean()` — works, but hides the dependency.

Inject a way to ask for the object, not the object itself.

</details>

### How do you use `@Lookup`?
<details><summary>Show answer</summary>

TODO:

it is the older way (from the XML days, “lookup method injection”) for a singleton to get a new prototype on each call. 
ObjectProvider, added in Spring 4.3 as far as I remember, does the same job with less magic.

```java
@Component
class ReportGenerator {            // Spring creates it from the class
  @Lookup
  ReportData newData() {           // Spring overrides this method
    return null;                   // placeholder, never runs
  }

  void generate() {
    newData().add("row");          // a new ReportData on each call
  }
}
```

Spring creates a generated subclass (CGLIB) of `ReportGenerator` and overrides `newData()`. The override asks the
container for the bean of the return type on every call. If `ReportData` is a prototype, each call gives a new one, so
a singleton `ReportGenerator` is no longer stuck with one instance.

The method must be one Spring can override: not `private`, `final` or `static`, and the class not `final`.

Spring writes the method body; you write only the signature.

</details>

### `@Lookup` on a bean from a `@Bean` method?
<details><summary>Show answer</summary>

It doesn't work. `@Lookup` relies on Spring making a generated subclass (CGLIB) that overrides the method, and that
happens only when Spring creates the object from the class itself (for example a scanned `@Component`). A `@Bean`
method creates the object with `new`, so the method is never overridden.

```java
@Configuration
class AppConfig {
  @Bean
  ReportGenerator reportGenerator() {
    return new ReportGenerator();   // we create it, not Spring: no subclass
  }
}

class ReportGenerator {
  @Lookup
  ReportData newData() {
    return null;                    // stub body: runs as written, never replaced
  }

  void generate() {
    newData().add("row");           // NullPointerException
  }
}
```

The annotation is ignored. Nothing fails at startup, and the stub body runs, so `generate()` fails later with a
`NullPointerException`.

Fix:
- Let Spring create the class: put `@Component` on `ReportGenerator` and delete the `@Bean` method.
- Or keep the `@Bean` method and pass an [`ObjectProvider<ReportData>`](#how-do-you-get-a-fresh-instance-on-each-use)
  into the constructor.

`@Lookup` needs Spring to create the class — a `@Bean` method creates it for you.

</details>

### What happens when a singleton needs a request bean?
<details><summary>Show answer</summary>

```java
@Component
@Scope("request")                  // no proxyMode
class CurrentUser { }

@Service
class ReportService {              // singleton, built at startup
  ReportService(CurrentUser currentUser) { }
}
```

Spring builds singletons at startup, and no HTTP request exists then, so there is no `CurrentUser` to inject. 
Startup fails with "Scope 'request' is not active for the current thread", and the message advises a scoped proxy.

Fix: let the singleton hold a [scoped proxy](#how-does-a-scoped-proxy-work) — use `@RequestScope`, or set `proxyMode`
on `@Scope`. The proxy is injected at startup and looks up the real bean when a method is called.

Not guaranteed: a lazy singleton that is first built inside a request gets that request's bean with no error, and keeps
it for every later request.

A singleton is built once, with no request — it can hold a stand-in for a request bean, never the bean.

</details>

### How does a scoped proxy work?
<details><summary>Show answer</summary>

```java
@Component
@Scope(value = WebApplicationContext.SCOPE_REQUEST, proxyMode = ScopedProxyMode.TARGET_CLASS)
class CurrentUser { }
```

- The singleton gets a proxy, injected once at startup.
- On every method call, the proxy finds the real object for the current scope — this request's `CurrentUser` — and
  passes the call on.
- `@RequestScope` and `@SessionScope` turn the proxy on by default.

The proxy stays; the object behind it changes per call.

</details>

### Scoped proxy on a prototype — what surprises?
<details><summary>Show answer</summary>

```java
@Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
class Counter {
  int n;
  void inc() { n++; }
  int get() { return n; }
}

counter.inc();
counter.get();   // 0 — each call reached a new Counter
```

Every method call goes through the proxy, and every lookup in prototype scope creates a new object — so two calls
never reach the same instance.

Proxy plus prototype gives a new object per method call.

</details>

### `ObjectProvider` vs scoped proxy — which when?
<details><summary>Show answer</summary>

- `ObjectProvider`: the caller decides when to get a new instance and can keep it for several calls. The lookup is
  visible in the code.
- Scoped proxy: looks like a normal dependency; the lookup is hidden and runs on every call. The right fit for request
  and session scope, where "the current one" is what you want.
- For prototypes, prefer `ObjectProvider` — a proxy gives a
  [new object per call](#scoped-proxy-on-a-prototype--what-surprises).

A provider when you choose the moment; a proxy when the scope chooses it.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Component
@RequestScope
public class CurrentUser {
  private String name;   // set per HTTP request
  // getter, setter ...
}

@Service
public class AuditService {
  private final String owner;

  public AuditService(CurrentUser currentUser) {
    this.owner = currentUser.getName();
  }
  // methods that use owner ...
}
```

</details>

<details><summary>Show answer</summary>

`CurrentUser` is request-scoped, so the constructor gets a [proxy](#how-does-a-scoped-proxy-work) and the injection
works. The call `getName()` in the constructor is the problem: it runs while Spring builds the singleton at startup,
no request exists, the proxy has no real bean to ask, and startup fails with "Scope 'request' is not active for the
current thread".

A second defect sits behind the first: if the call did succeed, `owner` would hold one user's name, and every later
request would see it. A field in a singleton is shared by all requests.

Not guaranteed: it fails at startup only for an eager singleton (the default). A lazy singleton first built inside a
request succeeds, and then it quietly serves the first user's name to everyone.

Fix: do not copy request data into a field. Keep the proxy and read it at call time, on the request thread:

```java
public void audit() {
  String owner = currentUser.getName();   // looked up now, for this request
  // ...
}
```

Read request data at call time, never while the singleton is built.

</details>

</details>

### Describe a code snippet #2
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Component
@RequestScope
public class CurrentUser {
  private String name;   // set per HTTP request

  public final String getName() {
    return name;
  }
  // setter ...
}

@Service
public class GreetingService {
  private final CurrentUser currentUser;
  // constructor ...

  public String greet() {
    return "Hello " + currentUser.getName();
  }
}
```

</details>

<details><summary>Show answer</summary>

`@RequestScope` injects a class-based [proxy](#how-does-a-scoped-proxy-work): a subclass of `CurrentUser` that passes
each call on to the real bean of the current request. A `final` method cannot be overridden in a subclass, so the call
is never passed on. `getName()` runs on the proxy object itself, where `name` was never set, and returns `null`. Every
user sees "Hello null": no exception, wrong data. (A `final` class is different: the proxy cannot be built, and startup
fails.)

Not guaranteed: what comes back depends on how the proxy object was built. Normally its fields are empty, so `null`
here, but never the real value. Spring logs a message about the `final` method when it builds the proxy, easy to miss.

Fix: remove `final` from the method. That is easy to undo by accident (an IDE hint, a language where classes are final
by default). The safer design is an interface-based proxy: `proxyMode = ScopedProxyMode.INTERFACES`, and inject the
interface. Then `final` in the class cannot break it.

The proxy is a subclass — whatever is `final` cannot be proxied.

</details>

</details>

### Describe a code snippet #3
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Component
@RequestScope
public class CurrentUser {
  private String name;   // set per HTTP request
  // getter, setter ...
}

@RestController
public class ReportController {
  private final ReportService reportService;
  // constructor ...

  @PostMapping("/reports")
  public void create() {
    reportService.sendReport();
  }
}

@Service
public class ReportService {
  private final CurrentUser currentUser;
  private final Mailer mailer;
  // constructor ...

  @Async
  public void sendReport() {
    mailer.send(currentUser.getName());
  }
}
```

</details>

<details><summary>Show answer</summary>

`@Async` runs `sendReport()` on a pool thread, and that thread has no HTTP request. `currentUser` is
[request-scoped](#what-bean-scopes-exist), so `getName()` fails with "Scope 'request' is not active for the current
thread". The app still starts fine: `@RequestScope` injects a proxy, and the real bean is looked up only when a method
is called.

The method is `void`, so the exception never reaches the controller. The HTTP call returns normally, no report goes
out, and by default the only trace is a log line.

Not guaranteed: it fails only on a thread with no request. If the call runs on the request thread (no `@EnableAsync`,
or a pool set to run extra tasks on the calling thread), it works. So it can pass in tests and fail in production.

Fix: read the value on the request thread and pass it in as plain data. `CurrentUser` moves to the controller.

```java
// ReportController, runs on the request thread
reportService.sendReport(currentUser.getName());

// ReportService
@Async
public void sendReport(String userName) {
  mailer.send(userName);
}
```

Not the fix to keep: copying the request context to the pool threads removes the error, but the request can be
finished when the task reads it, so it breaks at random.

Request scope lives on the request thread — read it there, pass plain values to other threads.

</details>

</details>

### Are singleton beans thread-safe?
<details><summary>Show answer</summary>

No — Spring adds no locking. One singleton serves every request thread at the same time. It is safe only if it holds
no changing state: dependencies set once in the constructor, and no mutable fields (or only fields that are
thread-safe themselves).

Spring shares the singleton; keeping it safe is your job.

</details>

### Mutable field in a singleton service — what breaks?
<details><summary>Show answer</summary>

```java
@RestController
class OrderController {
  private int requestCount;   // shared by every request thread

  @GetMapping("/orders")
  List<Order> list() {
    requestCount++;           // read, add, write: not atomic
    return orders.findAll();
  }
}
```

- `requestCount++` is three steps; two threads can read the same value, and one increment is lost (**lost update**).
- Worse with per-user data in a field (e.g. `currentUser`): one request reads another user's value.

A field in a singleton is shared by every request at once.

</details>

### How do you keep per-request state in a singleton?
<details><summary>Show answer</summary>

- Pass it as method parameters or keep it in local variables — nothing is shared.
- Use a request-scoped bean behind a [scoped proxy](#how-does-a-scoped-proxy-work).
- Use a `ThreadLocal`, cleared in a `finally` block — server threads are reused, so a value left behind leaks into the
  next request.
- For shared counters: `AtomicInteger` / `LongAdder`, or a metrics library.

Keep per-request data out of fields.

</details>

### Does prototype scope fix a stateful service?
<details><summary>Show answer</summary>

Not when the prototype is injected into a singleton: it is
[created once](#why-does-a-prototype-in-a-singleton-stay-one-instance) and shared by every thread, just like the
singleton. It helps only when each use gets its own instance (e.g. `ObjectProvider.getObject()` per request) — and
then you pay for the object creation and lose the destroy callbacks.

Prototype changes how many copies exist, not who shares them.

</details>

### Request-scoped bean used outside a request?
<details><summary>Show answer</summary>

```java
@Async
public void sendReport() {
  currentUser.getName();   // request-scoped bean, called on another thread
}
```

It fails: "Scope 'request' is not active for the current thread". Request scope is bound to the thread that handles
the HTTP request; `@Async` methods, scheduled jobs and startup code run on threads with no request.

Request scope lives on the request thread; other threads have no request.

</details>
