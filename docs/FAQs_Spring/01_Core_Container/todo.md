Тут смешаны два разных случая, и решения у них разные.

**Случай 1: одинаковое имя класса, но разные классы** (`com.lib.Mapper` и `com.my.Mapper`).
- При injection по типу проблемы нет: типы разные, Spring не путает.
- Проблема в **имени бина**: у обоих default-имя `mapper`. Spring Boot падает при старте с конфликтом имён (overriding по умолчанию запрещён).
- Решение: дать своему бину явное имя, `@Service("myMapper")`. Если оба из библиотек — исключить один из component scan (`excludeFilters`) или зарегистрировать его через свой `@Bean` с другим именем.

**Случай 2: два бина одного типа** (оба реализуют один интерфейс), injection неоднозначен.
Здесь важный момент: **`@Qualifier` не нужно вешать на сам бин**. В точке injection `@Qualifier("beanName")` выбирает бин **по имени**, а имя есть у любого бина, в том числе библиотечного:
```java
public MyService(@Qualifier("libraryClientA") Client client)
```
Так что даже два чужих бина без аннотаций выбираются без проблем. Другие варианты: свой `@Bean @Primary`, который возвращает нужный из двух; или `List<Client>` / `ObjectProvider<Client>`, если нужны оба.

**Аннотация, противоположная `@Primary`, — это `@Fallback`** (Spring Framework 6.2). Да, ты понял правильно: бин с `@Fallback` используется, только если других кандидатов нет. Появился другой бин того же типа — выбирается он.

У библиотек для этого чаще используется похожий, но более сильный механизм Spring Boot — **`@ConditionalOnMissingBean`**:
- `@Fallback`: бин **создаётся**, но проигрывает при выборе;
- `@ConditionalOnMissingBean`: бин **вообще не создаётся**, если ты объявил свой бин этого типа.

Так работает почти вся auto-configuration: объявил свой `RestClient.Builder` или `ObjectMapper`, и Boot свой не создаёт. Поэтому хорошо написанная библиотека сама уступает твоему бину, и ничего вешать не нужно. Это та же ловушка, что пункт 6.18 в pitfalls: второй `KafkaTemplate` убирает Boot-овский.


Разберём твой сценарий целиком:
- интерфейс `Client`;
- твой класс `com.my.DefaultClient implements Client`;
- библиотечный `com.lib.DefaultClient implements Client`;
- оба помечены `@Component`, у обоих одинаковое простое имя класса.

**Шаг 1. До injection дело не дойдёт.** У обоих бинов default-имя `defaultClient` (имя класса с маленькой буквы), и Spring упадёт **при старте** с конфликтом имён. Сначала нужно решить именно это: дать своему бину другое имя. Свой класс ты менять можешь:
```java
@Component("myClient")
public class DefaultClient implements Client { ... }
```

**Шаг 2. Теперь бинов два с разными именами:** `myClient` (твой) и `defaultClient` (библиотечный). В точке injection выбираешь нужный по имени, на сами классы `@Qualifier` вешать не нужно:
```java
public MyService(@Qualifier("myClient") Client client)          // твой
public OtherService(@Qualifier("defaultClient") Client client)  // библиотечный
```
`@Qualifier("…")` с именем бина работает для любого бина, потому что имя есть у каждого, даже если в классе нет ни одной аннотации.

**Если оба класса из библиотек** и поменять ни один нельзя, шаг 1 решается так: один из них исключаешь из component scan (`excludeFilters`) и, если он нужен, регистрируешь сам через `@Bean` с другим именем:
```java
@Bean
Client libraryAClient() {      // имя бина = имя метода
  return new com.liba.DefaultClient();
}
```

На практике конфликт имён с библиотекой бывает редко: библиотеки обычно регистрируют бины через auto-configuration (`@Bean`-методы, имя = имя метода), а не через component scan по своим классам.
