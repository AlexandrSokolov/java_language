# DI and Configuration

How Spring creates objects and wires them together.

- IoC vs DI.
- Constructor vs setter vs field injection.
- Component scanning vs `@Configuration` with `@Bean`.
- `@Configuration` full vs lite mode (`proxyBeanMethods`).
- Choosing between beans of one type — `@Primary`, `@Qualifier`.

### Why not call new for dependencies in a Spring container?
<details><summary>Show answer</summary>

```java
@Service
class OrderService {
  // typed to the interface, but `new` still fixes StripeClient, and Spring never sees this object
  private final PaymentClient client = new StripeClient(System.getenv("STRIPE_KEY"));
}
```

- **The choice is fixed at design time.** `new` names one exact class, so `OrderService` depends on that choice.
  The two classes are tightly coupled. As a result:
  - A test has no clean way to put in a fake, so the unit test calls the real Stripe.
  - Switching to another implementation means editing every class that calls `new StripeClient(...)`.
  - If the constructor takes arguments, `OrderService` must also know how to build the client.
- **The container never sees the object.** It is a plain instance, not a Spring bean, so it misses what the
  container adds:
  - No proxy: transactions, security checks, caching and async calls are gone. Under Spring's default proxy mode,
    `@Transactional` and similar annotations on its methods are silently ignored.
  - No lifecycle: no `@PreDestroy` runs, so nothing closes the client's connections on shutdown.

`new` fixes the class at design time and keeps the container out.

</details>

### Instead of `new`, what options exist, and what does each fix?
<details><summary>Show answer</summary>

- **Static factory:** one class owns the `new` call.

  ```java
    final class PaymentClients {
      static PaymentClient create() {
        return new StripeClient(System.getenv("STRIPE_KEY"));   // the one place to switch, build details here
      }
    }
  
    @Service
    class OrderService {
      private final PaymentClient client = PaymentClients.create();
    }
  ```

  - **Fixes:**
    - Switching the implementation is one edit, in the factory.
    - If `create()` takes no arguments, the build details live there too, and callers stop needing them.
  - **Stays wrong:**
    - **The dependency still points at the vendor:** `OrderService → PaymentClients → StripeClient`. Every caller
      gets the same class, and a test can't put in a fake without changing the factory or mocking the static call.
    - **Your code still creates the object:** the container never sees it. There is no proxy, so no `@Transactional`,
      security or caching, and no lifecycle callbacks.
- **Dependency injection:** the class only declares the dependency (constructor, setter or field), and Spring picks,
  builds and hands in the bean. In Spring, this one mechanism gives both missing inversions:
  - **[Dependency inversion:](#what-is-dependency-inversion)** only the wiring names `StripeClient`; 
    business code depends only on its own interface.
  - **[Inversion of control:](#what-is-inversion-of-control)** the container creates the object, 
    so it can proxy it and run its lifecycle.

A static factory puts `new` in one place; DI inverts both the dependency and the creation.

</details>

### What is dependency inversion?
<details><summary>Show answer</summary>

The Dependency Inversion Principle (DIP), the “D” in SOLID.

```java
// Before
package shop.order;
import shop.stripe.StripeClient;                                 // business code imports the vendor

// After: shop/order/PaymentClient.java
package shop.order;
public interface PaymentClient { void charge(Order order); }     // the business side owns the interface
class OrderService { private PaymentClient client; }             // nothing imported from shop.stripe

// After: shop/stripe/StripeClient.java
package shop.stripe;
import shop.order.PaymentClient;                                 // the vendor imports business code
class StripeClient implements PaymentClient { /* ... */ }
```

Source-code dependencies flip: `OrderService → StripeClient` becomes `OrderService → PaymentClient ← StripeClient`.
Calls still go from business code to Stripe, but the dependency now points the other way: low-level code (vendors,
database) depends on the business side's interface. That flip is the **dependency inversion**.

The principle: high-level code (business logic) must not depend on low-level code; both depend on an interface.

- **Ownership decides it:** the interface must live on the business side. Put it in `shop.stripe` and business code
  still imports the vendor.
- **What it gives:** business code compiles and is tested without the vendor, and a vendor change stays in
  `shop.stripe`.

Dependencies point toward the business logic, not away from it.

</details>

### What is inversion of control?
<details><summary>Show answer</summary>

```java
@Service                                                  // Spring creates this object; you never call new
class OrderService {
  @EventListener
  void onOrderPlaced(OrderPlaced event) { /* ... */ }     // Spring calls this when the event is published

  @Scheduled(fixedRate = 60_000)
  void retryFailedPayments() { /* ... */ }                // Spring calls this every minute
}
```

Normally your code is in charge: it creates its objects and calls methods when it wants. With inversion of control
(**IoC**), a framework is in charge: it creates your objects and calls your code. You call a library; a framework
calls you. Dependency injection (DI) is IoC applied to a bean's dependencies: Spring creates them and hands them in.

**What it gives:** the framework owns the part that is the same everywhere: object creation, lifecycle, event
delivery, scheduling, transactions. You write only the part that differs. The cost is that you don't see who calls
you, so the flow is harder to follow.

</details>

### How do dependency inversion, inversion of control and injection relate?
<details><summary>Show answer</summary>

```java
// package shop.order
public interface PaymentClient { void charge(Order order); }     // DIP: the business side owns the interface

@Service                                                          // IoC: Spring creates OrderService
class OrderService {
  private final PaymentClient client;

  OrderService(PaymentClient client) { this.client = client; }    // DI: Spring hands in the dependency
}
```

- **Dependency inversion (DIP)**, a principle: which way source-code dependencies point. Infrastructure depends on
  interfaces the business side owns.
- **Inversion of control (IoC)**, a principle: who is in charge. The framework creates your objects and calls your code.
- **Dependency injection (DI)**, a technique: how a bean gets its dependencies. The container hands them in.

How they connect:

- DI is one kind of IoC. IoC is wider: lifecycle calls, events and scheduling.
- DIP is a separate axis. DI is the usual way to reach it in Spring, because only the wiring names the concrete
  class. That works only when the injected type is an interface the business side owns;
  [injecting a concrete class inverts nothing](#can-you-inject-without-inverting-dependencies).

DIP is the goal, DI is the tool that delivers it in Spring, and IoC is the family DI belongs to.

</details>

### Can you inject without inverting dependencies?
<details><summary>Show answer</summary>

```java
package shop.order;
import shop.stripe.StripeClient;                // business code still imports the vendor

@Service
class OrderService {
  private StripeClient client;                  // injected (constructor, setter or field), but a concrete vendor class
}
```

The dependency still points `OrderService → StripeClient`. Spring creates the client and hands it in (DI), but
nothing is inverted.

- **Keeps:** Spring creates it in one place, proxies it and runs its lifecycle.
- **Loses:** business code compiles against Stripe, so a vendor change or switch means editing business code.
- **Same with a vendor-owned interface:** if the injected interface lives in `shop.stripe`, business code still
  imports the vendor.

Injection decides who creates the object; only an interface the business side owns inverts the dependency.

</details>

### `getBean()` inside a bean — what's wrong?
<details><summary>Show answer</summary>

```java
@Service
class ReportService {
  @Autowired ApplicationContext ctx;

  void run() {
    ctx.getBean(Exporter.class).export();   // the real dependency, buried in a method
  }
}
```

This is a **service locator**: the class asks the container for what it needs instead of being given it.

- **Hidden dependency:** the fields show only `ApplicationContext`, which can hand out anything. The real need,
  `Exporter`, appears only inside `run()`, so nobody sees it without reading every method.
- **Harder test:** with injection, the test passes in a fake `Exporter`. Here it must first fake `ApplicationContext`
  and stub `getBean(Exporter.class)` to return the fake.
- **Error moves to runtime:** with injection, a missing `Exporter` stops the app at startup. Here the app starts
  fine and fails only when `run()` is first called, maybe days later in production.
- **Tied to the framework:** business code imports Spring's `ApplicationContext`.

Asking the container hides the dependency and moves the error to runtime.

</details>

### How does code ask for a bean explicitly?
<details><summary>Show answer</summary>

Inject the container itself and call `getBean()`:

```java
@Service
class ReportService {
  private final BeanFactory beans;                     // or ApplicationContext: same container underneath

  ReportService(BeanFactory beans) { this.beans = beans; }

  void run() {
    beans.getBean(Exporter.class).export();
  }
}
```

- **`BeanFactory`:** bean access only: `getBean()`, `containsBean()`, `getBeanProvider()`.
- **`ApplicationContext`:** extends `BeanFactory` and adds events, i18n messages, resources and the `Environment`.
- **Same beans either way:** both point at the same running container. Inject `BeanFactory` when you only need
  beans, because it asks for less.
- **Same costs either way:** asking for beans in code is a [service locator](#getbean-inside-a-bean--whats-wrong).

`BeanFactory` is the narrow door to the container, `ApplicationContext` the wide one.

</details>

### How can Spring inject a dependency — trade-offs?
<details><summary>Show answer</summary>

```java
@Service
class OrderService {
  private final PaymentClient client;                  // constructor
  private EmailClient email;                           // setter
  @Autowired private AuditLog audit;                   // field

  OrderService(PaymentClient client) { this.client = client; }

  @Autowired
  void setEmail(EmailClient email) { this.email = email; }
}
```

- **Constructor:**
  - Benefits: plain Java can build the object, so tests that call `new` are checked by the compiler. Fields can be
    `final`, and dependencies are usable inside the constructor.
  - Costs: the most code, a constructor plus one assignment per field. It
    [can get long](#constructor-injection-is-too-long--what-helps).
- **Setter:**
  - Benefits: fits optional dependencies with a default, and third-party classes built with setters.
  - Costs: a public method lets anyone swap the dependency at runtime, and the field can't be `final`.
- **Field:**
  - Benefits: the shortest code. Unit tests can still fill the fields through package-private access or
    `@InjectMocks`, with no container.
  - Costs: only Spring, Mockito or same-package code can fill the fields, so a forgotten dependency is `null` at
    runtime instead of a compile error. Fields are `null` inside the constructor and can't be `final`.

Constructor for what is required, setter for what is optional; field trades compiler checks for less code.

</details>

### Constructor injection is too long — what helps?
<details><summary>Show answer</summary>

```java
@Service
@RequiredArgsConstructor                               // Lombok writes a constructor for all final fields
class OrderService {
  private final PaymentClient client;
  private final EmailClient email;
}
```

- Lombok generates the constructor at compile time. Spring sees one normal constructor and injects through it,
  with no `@Autowired` needed for a single constructor.
- It keeps everything constructor injection gives: `final` fields, plain `new` in tests, and compiler checks.
- Costs: an extra library and annotation processor in the build, and the constructor isn't in the source you read.
  Some teams don't allow Lombok.
- Without Lombok, the IDE can generate the constructor. The lines stay, but you don't type them.

Lombok hides the constructor's lines, not its benefits.

</details>

### One constructor — is `@Autowired` needed?
<details><summary>Show answer</summary>

No. Since Spring 4.3, when a class has only one constructor, Spring uses it for injection without the annotation.

One constructor: Spring uses it without being told.

</details>

### Several constructors — which one does Spring use?
<details><summary>Show answer</summary>

- The one marked `@Autowired`.
- Otherwise the no-argument constructor.
- Otherwise startup fails: Spring can't choose between the others.

Mark the one you mean; Spring won't guess between several.

</details>

### Injecting an optional dependency?
<details><summary>Show answer</summary>

- `Optional<Cache> cache` — empty when no such bean exists.
- `ObjectProvider<Cache> cache` — `getIfAvailable()` returns `null` when there is none, or a default with
  `getIfAvailable(() -> new NoCache())`; the lookup also happens only when you call it.
- `@Autowired(required = false)` on a field or setter — left unset when there is none.

Say in the type that the bean may be missing.

</details>

### Injecting every bean of one type?
<details><summary>Show answer</summary>

```java
OrderService(List<PaymentClient> clients)          // every bean of the type
OrderService(Map<String, PaymentClient> clients)   // key = bean name
```

- The list follows `@Order` / `Ordered`; without them, the order in which the beans were registered.
- Typical use: a registry of strategies — pick one by key at runtime instead of an `if` / `switch` over types.

Ask for a `List` or `Map`, and Spring hands you every implementation.

</details>

### Component scanning vs `@Bean` — when each?
<details><summary>Show answer</summary>

- Scanning (`@Component` on the class): your own classes — Spring finds them in the scanned packages.
- A `@Bean` method in a `@Configuration` class: classes you can't annotate (third-party), creation that needs logic or
  conditions, or several beans of one class with different settings.
- Both produce the same kind of bean; mixing them is normal.

Annotate what you own; write a `@Bean` method for what you don't.

</details>

### `@Component` vs `@Service` / `@Repository`?
<details><summary>Show answer</summary>

- All of them are `@Component` under another name — scanning finds each one the same way.
- `@Repository` adds behavior: a post-processor translates database exceptions into Spring's `DataAccessException`
  types.
- `@Controller` marks a class whose methods handle web requests.
- `@Service` adds nothing — it only says what the class is.

Same bean, different label — only `@Repository` and `@Controller` change behavior.

</details>

### Why isn't my bean found?
<details><summary>Show answer</summary>

- The class sits outside the scanned packages. Spring Boot scans the package of the `@SpringBootApplication` class
  and everything below it; a class in `com.acme.shared`, next to `com.acme.app`, is never seen.
- The class has no `@Component` (or `@Service`, ...) annotation.
- A condition on it didn't match — see [auto-configuration](../03_Boot/3.1_Auto_Configuration.md).

Scanning only looks below its base package.

</details>

### How do you make Spring see beans outside the root package?
<details><summary>Show answer</summary>

```java
@SpringBootApplication(scanBasePackages = {"com.acme.app", "com.acme.shared"})
class App { }
```

- **List the packages:** `scanBasePackages`, as above. Setting it replaces the default, so list the app's own
  package too. `scanBasePackageClasses = {App.class, SharedMarker.class}` does the same with classes and survives
  package renames.
- **Move the main class up** to the common parent (`com.acme`). Simple, but it scans everything below, maybe more
  than you want.
- **Import single classes:** `@Import(SharedConfig.class)` registers a class without scanning. This fits a few
  classes, or a config class that defines them.
- **Let the shared library register itself:** it lists its own config in
  `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, so the app needs no package
  names at all.

Name the packages, import the classes, or let the library register itself.

</details>

### Component scan scope — how wide?
<details><summary>Show answer</summary>

```text
scan scope: com.acme.orders and below
com.acme.orders.service.OrderService   // @Service: registered
com.acme.orders.api.OrderDto           // no annotation: read, skipped
com.acme.audit.AuditLog                // another team's jar: outside the scope
```

The scope is a set of base packages: by default the main class's package and below,
[changed by listing packages](#how-do-you-make-spring-see-beans-outside-the-root-package).

- **Too narrow:** beans outside the scope are [never found](#why-isnt-my-bean-found).
- **Too wide:**
  - **Hurts when it reaches foreign packages:** a base package at a shared prefix like `com.acme` pulls in every jar
    under it, which brings other teams' `@Component` classes, duplicate beans, and beans you never asked for.
  - **Harmless when it only covers your own non-beans:** scanning reads each class file to look for `@Component`,
    without loading the class, so data classes are just skipped. Spring Boot recommends putting the main class in
    your app's root package and scanning everything below, so there's no need to move data classes out.

Scope the scan to your app's own packages; non-beans inside are harmless, foreign packages inside are the risk.

</details>

### How does Spring name a bean?
<details><summary>Show answer</summary>

```java
@Service
class OrderService { }                                  // "orderService"

@Service("billing")
class BillingService { }                                // "billing"

@Configuration
class PaymentConfig {
  @Bean
  PaymentClient stripe() { return new StripeClient(); } // "stripe", not "paymentClient"

  @Bean("paypalClient")
  PaymentClient paypal() { return new PaypalClient(); } // "paypalClient"
}
```

- **Scanned class:** its simple class name with the first letter lowercased. The package is not part of it, so
  `com.a.OrderService` and `com.b.OrderService` get the same name. If the first two letters are both uppercase, the
  name stays as is: `URLParser` → `URLParser`.
- **`@Bean` method:** the method name. The return type plays no part, so two methods returning `PaymentClient` give
  two different names.
- **Explicit name:** `@Service("...")` or `@Bean("...")` replaces the default in both cases.

Class → its simple name, lowercased; method → its own name; an explicit name beats both.

</details>

### What causes two beans with the same name?
<details><summary>Show answer</summary>

A clash happens when two definitions end up with the same [name](#how-does-spring-name-a-bean):

```java
// 1. Two scanned classes with the same simple name
package com.acme.orders;   @Service class PaymentService { }    // "paymentService"
package com.acme.billing;  @Service class PaymentService { }    // "paymentService"

// 2. The same @Bean method name in two config classes
@Configuration class StripeConfig { @Bean PaymentClient paymentClient() { return new StripeClient(); } }
@Configuration class PaypalConfig { @Bean PaymentClient paymentClient() { return new PaypalClient(); } }

// 3. A @Bean named like a scanned class
@Service class AuditLog { }                                                       // "auditLog"
@Configuration class AuditConfig { @Bean AuditLog auditLog() { return new AuditLog(); } }
```

</details>

### What happens when two beans share a name?
<details><summary>Show answer</summary>

The [three causes](#what-causes-two-beans-with-the-same-name) end differently:

- **Spring Boot:** startup fails by default, in every case.
  - Two scanned classes: `ConflictingBeanDefinitionException`.
  - Two config classes, or a `@Bean` vs. a scanned class: `BeanDefinitionOverrideException`. Overriding is off by
    default since Boot 2.1; `spring.main.allow-bean-definition-overriding=true` turns it on.
- **Plain Spring, or Boot with overriding on:**
  - **Fails:** two scanned classes, with `ConflictingBeanDefinitionException`.
  - **Replaces silently:**
    - Two config classes: the one registered last wins, so the result depends on processing order.
    - A `@Bean` vs. a scanned class: the `@Bean` wins.

Boot fails on every shared name; with overriding on, only two scanned classes fail and the rest is replaced silently.

</details>

### One `@Bean` method calls another — how?
<details><summary>Show answer</summary>

- **Full mode:** `@Configuration`, the default.

```java
  @Configuration
  class AppConfig {
    @Bean Repo repo() { return new Repo(); }
    @Bean ServiceA a() { return new ServiceA(repo()); }   // goes through the proxy: the container's Repo
    @Bean ServiceB b() { return new ServiceB(repo()); }   // the same Repo as A
  }
```

Spring runs a CGLIB subclass of `AppConfig`. The call `repo()` goes through it and returns the container's one `Repo`, 
so A and B share it.

- **Lite mode:** `@Bean` methods in a `@Component` class, or `@Configuration(proxyBeanMethods = false)`.

```java
  @Component
  class AppConfig {
    @Bean Repo repo() { return new Repo(); }
    @Bean ServiceA a() { return new ServiceA(repo()); }   // plain Java call: a new Repo
    @Bean ServiceB b() { return new ServiceB(repo()); }   // another new Repo
  }
```

`repo()` is a plain Java call. A and B each get a new `Repo` that is not a bean: no post-processors, no proxies,
no lifecycle callbacks. The container still has its own `Repo` bean, so there are three instances in total.

- **Fix in lite mode:** take the dependency as a parameter.

```java
  @Configuration(proxyBeanMethods = false)
  class AppConfig {
    @Bean Repo repo() { return new Repo(); }
    @Bean ServiceA a(Repo repo) { return new ServiceA(repo); }   // Spring passes in the container's Repo
    @Bean ServiceB b(Repo repo) { return new ServiceB(repo); }   // the same Repo
  }
```

Spring fills each parameter from the container, so A and B share the bean with no CGLIB subclass. It works in
full mode too, and it's how Boot's own auto-configurations are written.

In full mode a `@Bean` call goes to the container; in lite mode it's a method call, so take beans as parameters.

</details>

### Why set `proxyBeanMethods = false`?
<details><summary>Show answer</summary>

- No CGLIB subclass to generate: faster startup, less memory, and simpler for GraalVM native images.
- Spring Boot's own [auto-configuration](../03_Boot/3.1_Auto_Configuration.md) classes use it.
- Cost: calling one `@Bean` method from another now creates a new object. Take the dependency as a method parameter
  instead: `@Bean ServiceA a(Repo repo)`.

Turn off the subclass, then pass beans as parameters instead of calling methods.

</details>

### Why can't a `@Configuration` class be `final`?
<details><summary>Show answer</summary>

In full mode Spring makes a CGLIB subclass of the class at runtime to catch calls to `@Bean` methods. A `final` class
can't be subclassed, so startup fails. For the same reason `@Bean` methods can't be `private` or `final`.

With `proxyBeanMethods = false` there is no subclass, and both limits go away.

Full mode subclasses your config class, so nothing in it may block overriding.

</details>

### Two beans fit one injection point — what happens?
<details><summary>Show answer</summary>

```java
@Component class StripeProcessor implements PaymentProcessor { }
@Component class PayPalProcessor implements PaymentProcessor { }

@Service
class Checkout {
  Checkout(PaymentProcessor processor) { }   // which one?
}
```

Startup fails with `NoUniqueBeanDefinitionException`: "expected single matching bean but found 2:
stripeProcessor,payPalProcessor".

More than one candidate and no rule to choose — Spring refuses to guess.

</details>

### `@Primary` vs `@Qualifier` — which wins?
<details><summary>Show answer</summary>

- `@Primary` on a bean: the default when several fit and the injection point says nothing more.
- `@Qualifier("payPalProcessor")` on the injection point: names the bean it wants.
- When both apply, the qualifier wins: it filters the candidates first, and `@Primary` only chooses among what is left.

Full order: qualifier → `@Primary` → `@Priority` →
[parameter or field name](#matching-by-parameter-name--when-does-it-stop-working).

`@Primary` is the bean's default claim; `@Qualifier` is the caller's explicit choice.

</details>

### Matching by parameter name — when does it stop working?
<details><summary>Show answer</summary>

```java
@Bean PaymentProcessor payPalProcessor() { return new PayPalProcessor(); }
@Bean PaymentProcessor stripeProcessor() { return new StripeProcessor(); }

Checkout(PaymentProcessor payPalProcessor) { /* ... */ }   // two beans fit: which one?
```

When `@Qualifier`, `@Primary` and `@Priority` don't decide, Spring falls back to the name. A bean called
`payPalProcessor` exists, so it takes that one.

- **Fields vs. parameters:** to match, Spring needs the name at runtime, from the `.class` file.
  - Field names are always stored, so field matching always works.
  - Parameter names are stored only with the `-parameters` compiler flag. Without it the constructor is effectively
    `Checkout(PaymentProcessor arg0)`.
- **What changed:** older Spring also read parameter names from debug info (`-g`, on by default). Spring 6.1
  dropped that. Without `-parameters` Spring now sees `arg0`, the fallback fails, and startup ends with
  `NoUniqueBeanDefinitionException`. *(unverified)*
- **Where it bites:** Boot's parent POM and Gradle plugin turn `-parameters` on. A company parent POM that imports
  only Boot's dependency list (the BOM) doesn't, so the upgrade to Boot 3.2 (Spring 6.1) breaks injection that
  worked for years. Unnamed `@RequestParam` / `@PathVariable` and `#param` in `@Cacheable` keys break the same way.
- **How to stay safe:** keep `-parameters` on in every build, or name the bean with `@Qualifier("payPalProcessor")`.

Naming the parameter after the bean works — until the compiler drops the name.

</details>

### Generic type as a qualifier?
<details><summary>Show answer</summary>

```java
@Component class UserRepo implements Repo<User> { }
@Component class OrderRepo implements Repo<Order> { }

@Service
class UserService {
  UserService(Repo<User> repo) { }   // gets UserRepo: the type argument decides
}
```

Since Spring 4.0, the type arguments narrow the candidates like a qualifier. A raw `Repo` or `Repo<?>` still matches
both and fails.

The type argument counts as part of the type Spring matches.

</details>

### What does `@Fallback` do?
<details><summary>Show answer</summary>

- It marks a bean to be used only when no other candidate fits — the opposite of `@Primary`. Added in Spring 6.2.
  *(unverified)*
- Typical use: a default implementation that steps aside as soon as someone defines their own.

`@Primary` says "pick me"; `@Fallback` says "pick me only if no one else fits".

</details>
