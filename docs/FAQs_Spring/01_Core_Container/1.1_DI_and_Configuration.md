# DI and Configuration

How Spring creates objects and wires them together.

- IoC vs DI.
- Constructor vs setter vs field injection.
- Component scanning vs `@Configuration` with `@Bean`.
- `@Configuration` full vs lite mode (`proxyBeanMethods`).
- Choosing between beans of one type — `@Primary`, `@Qualifier`.

### Why not just call `new` for dependencies?
<details><summary>Show answer</summary>

```java
class OrderService {
  private final PaymentClient client = new StripeClient();   // the class picks its own collaborator
}
```

- A test can't swap `StripeClient` for a fake without changing `OrderService`.
- Every `OrderService` builds its own client; nothing can share one instance or its settings.
- Changing the implementation means editing every class that calls `new StripeClient()`.

Handing the collaborator in from outside — usually through the constructor — is **dependency injection**. Spring's
container does the handing in.

A class that creates its collaborators is welded to them.

</details>

### IoC vs DI — what's the difference?
<details><summary>Show answer</summary>

- **Inversion of control (IoC)** — the framework, not your code, runs the flow: it creates the objects and calls your
  code when needed.
- **Dependency injection (DI)** — one form of IoC: an object gets its collaborators from outside instead of creating
  or looking them up.
- Other forms of IoC: callbacks and template methods (`JdbcTemplate` calls your `RowMapper`), event listeners. A
  service locator also takes creation away from the class, but the class still asks for what it needs.

Spring's container is called the IoC container; DI is how it wires beans together.

IoC is the principle; DI is the way Spring applies it to wiring objects.

</details>

### `getBean()` inside a bean — what's wrong?
<details><summary>Show answer</summary>

```java
@Service
class ReportService {
  @Autowired ApplicationContext ctx;

  void run() {
    ctx.getBean(Exporter.class).export();   // hidden dependency
  }
}
```

**Service locator:**

- The dependency on `Exporter` is not visible in the constructor or fields — you find it only by reading the method.
- A unit test needs a real or mocked `ApplicationContext`.
- A missing `Exporter` fails at the call, at runtime, not at startup.

Asking the container hides the dependency and moves the error to runtime.

</details>

### `BeanFactory` vs `ApplicationContext`?
<details><summary>Show answer</summary>

- `BeanFactory` — the basic container: creates and wires beans, and creates a singleton only when it is first asked
  for.
- `ApplicationContext` — extends it: creates all non-lazy singletons at startup (so wiring errors fail early),
  registers post-processors on its own, publishes events, resolves messages for i18n, and loads resources.
- In practice you always use an `ApplicationContext`; the `BeanFactory` is the core inside it.

`BeanFactory` makes beans on request; `ApplicationContext` makes them at startup and adds the services around them.

</details>

### Why is constructor injection the default choice?
<details><summary>Show answer</summary>

- Fields can be `final`: the object is complete after construction and never changes its dependencies.
- Required dependencies are explicit: the object can't be created without them — also in a unit test with `new`, no
  Spring needed.
- A constructor with many parameters shows that the class does too much.
- A dependency cycle [fails at startup](1.4_Circular_Dependencies.md#why-cant-a-constructor-cycle-be-resolved)
  instead of being patched with half-built objects.

The constructor states what the class needs, and the object can't exist without it.

</details>

### What's wrong with field injection?
<details><summary>Show answer</summary>

```java
@Service
class OrderService {
  @Autowired private PaymentClient client;   // set by reflection after the constructor
}
```

- The field can't be `final`.
- A unit test with `new OrderService()` gets `client == null`; setting it needs reflection or a Spring test context.
- Dependencies are hidden: fields can pile up without anything looking wrong.
- The object exists half-built between the constructor and the injection.

Field injection works only inside Spring and hides what the class needs.

</details>

### When does setter injection fit?
<details><summary>Show answer</summary>

- Optional dependencies with a sensible default — the object works without them.
- Dependencies that may be replaced after creation (rare).
- Third-party classes built as JavaBeans, with setters and no suitable constructor.

Cost: the object can be used before a setter runs, and the field can't be `final`.

Setters for what is optional; the constructor for what is required.

</details>

### One constructor — is `@Autowired` needed?
<details><summary>Show answer</summary>

No. Since Spring 4.3, when a class has only one constructor, Spring uses it for injection without the annotation.

One constructor: Spring uses it without being told.

</details>

### Several constructors — which one does Spring use?
<details><summary>Show answer</summary>

- The one marked `@Autowired`.
- Otherwise the no-argument constructor.
- Otherwise startup fails: Spring can't choose between the others.

Mark the one you mean; Spring won't guess between several.

</details>

### Injecting an optional dependency?
<details><summary>Show answer</summary>

- `Optional<Cache> cache` — empty when no such bean exists.
- `ObjectProvider<Cache> cache` — `getIfAvailable()` returns `null` when there is none, or a default with
  `getIfAvailable(() -> new NoCache())`; the lookup also happens only when you call it.
- `@Autowired(required = false)` on a field or setter — left unset when there is none.

Say in the type that the bean may be missing.

</details>

### Injecting every bean of one type?
<details><summary>Show answer</summary>

```java
OrderService(List<PaymentClient> clients)          // every bean of the type
OrderService(Map<String, PaymentClient> clients)   // key = bean name
```

- The list follows `@Order` / `Ordered`; without them, the order in which the beans were registered.
- Typical use: a registry of strategies — pick one by key at runtime instead of an `if` / `switch` over types.

Ask for a `List` or `Map`, and Spring hands you every implementation.

</details>

### Component scanning vs `@Bean` — when each?
<details><summary>Show answer</summary>

- Scanning (`@Component` on the class): your own classes — Spring finds them in the scanned packages.
- A `@Bean` method in a `@Configuration` class: classes you can't annotate (third-party), creation that needs logic or
  conditions, or several beans of one class with different settings.
- Both produce the same kind of bean; mixing them is normal.

Annotate what you own; write a `@Bean` method for what you don't.

</details>

### `@Component` vs `@Service` / `@Repository`?
<details><summary>Show answer</summary>

- All of them are `@Component` under another name — scanning finds each one the same way.
- `@Repository` adds behavior: a post-processor translates database exceptions into Spring's `DataAccessException`
  types.
- `@Controller` marks a class whose methods handle web requests.
- `@Service` adds nothing — it only says what the class is.

Same bean, different label — only `@Repository` and `@Controller` change behavior.

</details>

### Why isn't my bean found?
<details><summary>Show answer</summary>

- The class sits outside the scanned packages. Spring Boot scans the package of the `@SpringBootApplication` class
  and everything below it; a class in `com.acme.shared`, next to `com.acme.app`, is never seen.
- The class has no `@Component` (or `@Service`, ...) annotation.
- A condition on it didn't match — see [auto-configuration](../03_Boot/3.1_Auto_Configuration.md).

Scanning only looks below its base package.

</details>

### Two beans with the same name?
<details><summary>Show answer</summary>

A scanned class is named after its simple class name with a lowercase first letter (`orderService`); a `@Bean` after
its method name.

- Two scanned classes with the same simple name in different packages: startup fails with
  `ConflictingBeanDefinitionException`.
- A `@Bean` or explicit definition that reuses an existing name: plain Spring replaces the first one, with only a log
  line.
- Spring Boot refuses that replacement by default (since 2.1) and fails with `BeanDefinitionOverrideException`.
  *(unverified)*

Names must be unique; plain Spring may replace one silently, Boot refuses.

</details>

### One `@Bean` method calls another — same instance?
<details><summary>Show answer</summary>

```java
@Configuration
class AppConfig {
  @Bean Repo repo() { return new Repo(); }
  @Bean ServiceA a() { return new ServiceA(repo()); }
  @Bean ServiceB b() { return new ServiceB(repo()); }
}
```

- **Full mode** (`@Configuration`, the default): Spring runs a CGLIB subclass of `AppConfig`. The call `repo()` goes
  through it and returns the container's one `Repo`, so A and B share it.
- **Lite mode** (`@Bean` methods in a `@Component` class, or `@Configuration(proxyBeanMethods = false)`): `repo()` is a
  plain Java call. A and B each get a new `Repo` that is not a bean — no post-processors, no proxies, no lifecycle
  callbacks.

In full mode a `@Bean` call goes to the container; in lite mode it's just a method call.

</details>

### Why set `proxyBeanMethods = false`?
<details><summary>Show answer</summary>

- No CGLIB subclass to generate: faster startup, less memory, and simpler for GraalVM native images.
- Spring Boot's own [auto-configuration](../03_Boot/3.1_Auto_Configuration.md) classes use it.
- Cost: calling one `@Bean` method from another now creates a new object. Take the dependency as a method parameter
  instead: `@Bean ServiceA a(Repo repo)`.

Turn off the subclass, then pass beans as parameters instead of calling methods.

</details>

### Why can't a `@Configuration` class be `final`?
<details><summary>Show answer</summary>

In full mode Spring makes a CGLIB subclass of the class at runtime to catch calls to `@Bean` methods. A `final` class
can't be subclassed, so startup fails. For the same reason `@Bean` methods can't be `private` or `final`.

With `proxyBeanMethods = false` there is no subclass, and both limits go away.

Full mode subclasses your config class, so nothing in it may block overriding.

</details>

### Two beans fit one injection point — what happens?
<details><summary>Show answer</summary>

```java
@Component class StripeProcessor implements PaymentProcessor { }
@Component class PayPalProcessor implements PaymentProcessor { }

@Service
class Checkout {
  Checkout(PaymentProcessor processor) { }   // which one?
}
```

Startup fails with `NoUniqueBeanDefinitionException`: "expected single matching bean but found 2:
stripeProcessor,payPalProcessor".

More than one candidate and no rule to choose — Spring refuses to guess.

</details>

### `@Primary` vs `@Qualifier` — which wins?
<details><summary>Show answer</summary>

- `@Primary` on a bean: the default when several fit and the injection point says nothing more.
- `@Qualifier("payPalProcessor")` on the injection point: names the bean it wants.
- When both apply, the qualifier wins: it filters the candidates first, and `@Primary` only chooses among what is left.

Full order: qualifier → `@Primary` → `@Priority` →
[parameter or field name](#matching-by-parameter-name--when-does-it-stop-working).

`@Primary` is the bean's default claim; `@Qualifier` is the caller's explicit choice.

</details>

### Matching by parameter name — when does it stop working?
<details><summary>Show answer</summary>

When several beans fit and nothing else decides, Spring picks the bean whose name equals the parameter or field name:
`Checkout(PaymentProcessor payPalProcessor)`.

- Field names are always in the compiled class. Constructor and method parameter names are there only with the
  `-parameters` compiler flag.
- Since Spring 6.1, Spring no longer reads parameter names from debug info, so without the flag the match silently
  stops and startup fails with `NoUniqueBeanDefinitionException`. *(unverified)*
- Spring Boot's Maven and Gradle plugins turn `-parameters` on; a plain build may not.

Naming the parameter after the bean works — until the compiler drops the name.

</details>

### Generic type as a qualifier?
<details><summary>Show answer</summary>

```java
@Component class UserRepo implements Repo<User> { }
@Component class OrderRepo implements Repo<Order> { }

@Service
class UserService {
  UserService(Repo<User> repo) { }   // gets UserRepo: the type argument decides
}
```

Since Spring 4.0, the type arguments narrow the candidates like a qualifier. A raw `Repo` or `Repo<?>` still matches
both and fails.

The type argument counts as part of the type Spring matches.

</details>

### What does `@Fallback` do?
<details><summary>Show answer</summary>

- It marks a bean to be used only when no other candidate fits — the opposite of `@Primary`. Added in Spring 6.2.
  *(unverified)*
- Typical use: a default implementation that steps aside as soon as someone defines their own.

`@Primary` says "pick me"; `@Fallback` says "pick me only if no one else fits".

</details>
