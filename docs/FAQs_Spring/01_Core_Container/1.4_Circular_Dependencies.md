# Circular Dependencies

- How Spring resolves field and setter cycles — three caches, early references to half-built beans.
- Since Spring Boot 2.6, cycles are refused by default (`spring.main.allow-circular-references`).
- Constructor injection — a cycle fails at startup instead of being patched quietly.
- Breaking a cycle — redesign, `@Lazy`.

### A needs B, B needs A — what happens?
<details><summary>Show answer</summary>

```java
@Service class A { @Autowired B b; }
@Service class B { @Autowired A a; }
```

- With field or setter injection, Spring Framework resolves this **circular dependency** by handing B a half-built A
  ([how](#how-does-spring-resolve-a-field-or-setter-cycle)).
- With constructor injection on both sides it can't — startup fails.
- Spring Boot 2.6+ refuses both kinds by default: startup fails with "The dependencies of some of the beans in the
  application context form a cycle".

Whether a cycle starts depends on the injection type and on Boot's setting.

</details>

### How does Spring resolve a field or setter cycle?
<details><summary>Show answer</summary>

- Spring starts A: it calls A's constructor — A now exists, its fields are still empty.
- It registers an early reference to A (a factory in the third cache).
- It fills A's fields, needs B, and starts B.
- B needs A: Spring finds A's early reference and gives B the half-built A.
- B completes; A gets B and completes.

The three caches:

- `singletonObjects` — finished beans.
- `earlySingletonObjects` — early references already handed out.
- `singletonFactories` — factories that can produce an early reference.

A must exist before anyone can point to it, so its constructor runs first and the object is shared before it is
finished.

</details>

### Why three caches, not two?
<details><summary>Show answer</summary>

- If A will be proxied (e.g. `@Transactional`), B must get the proxy, not the raw A. But the proxy is normally made at
  the end of A's lifecycle.
- The third cache holds a factory instead of the object. Only if someone asks for A early does Spring call it — and
  the factory asks the auto-proxy creator for an early proxy (`getEarlyBeanReference`). The result moves to the second
  cache, so every later request gets the same object.
- With no cycle, the factory is never called, and the proxy is made at the usual time.

The factory makes the early proxy only when a cycle actually needs it.

</details>

### What does B see when it gets A early?
<details><summary>Show answer</summary>

A half-built A: its constructor has run, but some of its fields may still be `null`, and its `@PostConstruct` has not
run.

```java
@Service
class B {
  @Autowired A a;

  @PostConstruct
  void init() {
    a.load();   // A's fields are not all injected yet → NullPointerException inside load()
  }
}
```

An early reference is a bean that exists, not a bean that is finished.

</details>

### Cycle plus `@Async` — why does startup fail?
<details><summary>Show answer</summary>

The message: "Bean with name 'a' has been injected into other beans [b] in its raw version as part of a circular
reference, but has eventually been wrapped".

- B got the early, raw A — no proxy.
- `@Async` proxies are made by `AsyncAnnotationBeanPostProcessor`, which doesn't make early proxies: it wraps A only at
  the end of A's lifecycle.
- Now the container holds the proxy, but B holds the raw object. Spring detects the mismatch and fails with
  `BeanCurrentlyInCreationException`.
- `@Transactional` doesn't hit this: its auto-proxy creator does make early proxies.

Early references work only with proxies that can be made early.

</details>

### Prototype cycle?
<details><summary>Show answer</summary>

Never resolved. Prototypes are not cached, so there is no early reference to hand out: A needs a new B, which needs a
new A, and so on. Spring detects it and fails with `BeanCurrentlyInCreationException`.

No cache, no early reference — a prototype cycle can't close.

</details>

### What changed in Spring Boot 2.6?
<details><summary>Show answer</summary>

- Boot turns circular references off in the bean factory by default: any cycle fails at startup, and Boot prints the
  cycle.
- `spring.main.allow-circular-references=true` brings back the old behavior.
- Spring Framework itself still allows field and setter cycles by default — the refusal comes from Boot. The three
  caches are still there.

Boot turned a quiet patch into a startup error.

</details>

### Allowing cycles again — what does it hide?
<details><summary>Show answer</summary>

- A design problem: two classes that each need the other are usually one job split badly, or a missing third class.
- The runtime risks of early references: [half-built beans](#what-does-b-see-when-it-gets-a-early) and the
  [proxy mismatch](#cycle-plus-async--why-does-startup-fail).

The property removes the error, not the cycle.

</details>

### Why can't a constructor cycle be resolved?
<details><summary>Show answer</summary>

An early reference needs an object, and an object exists only after its constructor returns. A's constructor needs B,
B's constructor needs A — neither constructor can finish, so there is nothing to hand out. Startup fails with
`BeanCurrentlyInCreationException` ("Is there an unresolvable circular reference?").

That is what makes constructor injection useful here: the cycle shows up at once instead of being patched.

No finished constructor, no object — nothing to share early.

</details>

### How do you break a cycle by redesign?
<details><summary>Show answer</summary>

- Extract the part both need into a third bean; A and B depend on it, not on each other.
- Move the method to the side that owns the data, so only one direction is left.
- Turn one direction into an event: B publishes, A listens — B no longer needs A.
- If the two can't work apart, they may be one class.

Find the shared part and give it its own home.

</details>

### How does `@Lazy` break a cycle — and what does it cost?
<details><summary>Show answer</summary>

```java
@Service
class A {
  private final B b;

  A(@Lazy B b) { this.b = b; }   // b is a proxy; the real B is looked up on first call
}
```

- Spring injects a proxy instead of B, so A's constructor can finish and the cycle closes — this works for constructor
  cycles too.
- Costs: the cycle is hidden, not removed; if B can't be created, the error shows on the first call, not at startup;
  every call goes through a proxy.

`@Lazy` hands over a placeholder now and the real bean later.

</details>

### `@Lazy` on the class vs on the injection point?
<details><summary>Show answer</summary>

- On the injection point (field or parameter): Spring injects a proxy — this is what breaks a cycle.
- On the class: the bean is only created later. When another bean needs it, it is created then — through the same
  cycle. It doesn't break the cycle.

`@Lazy` on the class delays the bean; `@Lazy` on the injection point delays the lookup.

</details>

### Other tricks — `ObjectProvider`, setter on one side?
<details><summary>Show answer</summary>

- `ObjectProvider<B>` in A: A asks for B when it needs it, after startup — no cycle at creation time.
- Setter or field injection on one side, constructor on the other: the old early-reference trick — refused under
  Boot 2.6+ defaults.
- Same cost as `@Lazy`: the cycle is still there, only hidden.

Every injection trick moves the cycle; only a redesign removes it.

</details>

### Self-injection under Boot 2.6+?
<details><summary>Show answer</summary>

- Self-injection: a bean injects itself so that calls to its own `@Transactional` methods go through the proxy — a
  [call on `this`](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md) skips it.
- Under Boot 2.6+ defaults it counts as a cycle and startup fails; it works again with `@Lazy` on the self-injected
  field. *(unverified)*

A bean that needs itself is a cycle of one.

</details>
