# Circular Dependencies

### A needs B, B needs A — what happens?
<details><summary>Show answer</summary>

```java
@Service class A { @Autowired B b; }
@Service class B { @Autowired A a; }
```

By default this is not possible: Spring Boot 2.6+ refuses this **circular dependency**, and startup fails with "The
dependencies of some of the beans in the application context form a cycle".

Cycles are allowed in plain Spring Framework by default (for example, a library), or in Boot when you switch the
check off. The Boot switch is a stopgap, for example during a migration: it hides the cycle instead of fixing it.
When cycles are allowed, the result depends on the injection type:

- Field or setter: Spring resolves the cycle by handing B a half-built A
  ([how](#how-does-spring-resolve-a-field-or-setter-cycle)).
- Constructor on both sides: Spring can't resolve it, so startup fails.

</details>

### How does Spring resolve an allowed circular dependency?
<details><summary>Show answer</summary>

- Spring calls A's constructor. A now exists; its fields are still empty.
- It puts a factory into `singletonFactories` that returns an early reference to A (A before it is finished).
- It fills A's fields, needs B, and starts B.
- B needs A. Spring checks the three caches in order:
  - `singletonObjects` (finished beans): not there.
  - `earlySingletonObjects` (early references already handed out): not there.
  - `singletonFactories`: finds A's factory, runs it, moves the result to `earlySingletonObjects`, removes the factory.
- B gets the half-built A, completes, and goes into `singletonObjects`.
- A gets B, completes, and moves to `singletonObjects`.

The third cache holds a factory, not A itself, because of AOP: if A gets a proxy, B must receive the proxy, not the
raw A. The factory builds the proxy early, and only when a cycle actually asks for A.

A must exist before anyone can point to it, so its constructor runs first and the object is shared before it is
finished.

</details>

### How does Spring create a normal proxy without a circular dependency?
<details><summary>Show answer</summary>

Spring keeps singleton instances in three maps:

- `singletonObjects` (L1) — finished beans. This is what callers get.
The next 2 caches used only to resolve [cycles](#how-does-spring-resolve-an-allowed-circular-dependency):
- `earlySingletonObjects` (L2) — half-built beans 
- `singletonFactories` (L3) — factories that can hand out a half-built bean if someone asks for it early.

How a normal proxy (e.g., `@Transactional`) is created and stored (No Cycles):

- Spring calls A's constructor. The raw A exists; its fields are still empty.
- Spring puts a factory into `singletonFactories` (L3) just in case a cycle happens, but it remains unused.
  (Spring Boot 2.6+ forbids cycles by default; there this step is skipped.)
- It fills A's fields and runs A's init methods (`@PostConstruct` and similar).
- **Proxy Generation**: A `BeanPostProcessor` intercepts the fully initialized raw bean, detects the annotation, 
  and builds the proxy object.
- Spring puts the proxy into `singletonObjects` (L1) and removes the unused factory from L3.

Because there was no cycle, the factory in L3 was never called. `earlySingletonObjects` is never used. 
The proxy is generated at the very end of the lifecycle, 
and any other bean requesting this singleton receives the proxy directly from the L1 cache.

</details>

### What does B see when it gets A early?
<details><summary>Show answer</summary>

```java
@Service
class A {
  @Autowired B b;
}

@Service
class B {
  @Autowired A a;

  @PostConstruct
  void init() {
    a.load();   // A's fields are not all injected yet → NullPointerException inside load()
  }
}
```

With a cyclic dependency B sees a half-built A: A's constructor has run,
but some of its fields may still be `null`, and its `@PostConstruct` has not run.

An early reference is a bean that exists, not a bean that is finished.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Configuration @EnableAsync
class AsyncConfig {}

@Service
class A {
  @Autowired B b;

  @Async
  public void sendReport() { /* ... */ }
}

@Service
class B {
  @Autowired A a;
}
```

</details>

<details><summary>Show answer</summary>

With cycles allowed, startup fails with `BeanCurrentlyInCreationException`: A "has been injected into other beans
[b] in its raw version ... but has eventually been wrapped".

- B gets A's early reference: the raw A.
- `AsyncAnnotationBeanPostProcessor` can't make early proxies. It wraps A only at the end of A's lifecycle.
- The container holds the proxy, B holds the raw A. Spring detects the mismatch and fails.

Not guaranteed: it fails only if A is created first. If B goes first, B gets the finished proxy.

Minimal fix: `@Lazy` on B's field, so B looks up the real A on first call, not at startup.

```java
@Autowired @Lazy A a;
```

Better: remove the cycle by moving what B needs out of A.

Early references work only with proxies that can be made early.

</details>

</details>

### Prototype cycle?
<details><summary>Show answer</summary>

Never resolved. Prototypes are not cached, so there is no early reference to hand out: 
A needs a new B, which needs a new A, and so on. Spring detects it and fails with `BeanCurrentlyInCreationException`.

No cache, no early reference — a prototype cycle can't close.

</details>

### What changed in Boot's dependency resolution?
<details><summary>Show answer</summary>

Since Spring Boot 2.6, any bean cycle fails at startup by default, and Boot prints the cycle. Before, Boot let field
and setter cycles through without a word.

Boot did this by switching off circular references in the bean factory. Spring Framework itself didn't change:
without Boot, field and setter cycles still work. `spring.main.allow-circular-references=true` turns them back on in
Boot.

Boot turned a quiet patch into a startup error.

</details>

### Allowing cycles again — what does it hide?
<details><summary>Show answer</summary>

- A design problem: two classes that each need the other are usually one job split badly, or a missing third class.
- The runtime risks of early references: 
  - [half-built beans](#what-does-b-see-when-it-gets-a-early) and 
  - the [proxy mismatch](#describe-a-code-snippet-1).

The property removes the error, not the cycle.

</details>

### Why can't a constructor cycle be resolved?
<details><summary>Show answer</summary>

An early reference needs an object, and an object exists only after its constructor returns. A's constructor needs B,
B's constructor needs A — neither constructor can finish, so there is nothing to hand out. Startup fails with
`BeanCurrentlyInCreationException` ("Is there an unresolvable circular reference?").

That is what makes constructor injection useful here: the cycle shows up at once instead of being patched.

No finished constructor, no object — nothing to share early.

</details>

### How do you handle circular dependencies?
<details><summary>Show answer</summary>

On a design level, a circular dependency usually indicates an architectural flaw. It means classes are tightly coupled,
often violating the Single Responsibility Principle, and forming a tangled graph instead of a clean, testable hierarchy.
They act as one unit split over two classes, which usually means a responsibility sits on the wrong side.

- **Avoid it entirely** This is the only correct long-term strategy. 
  - Spring Boot forbids cycles by default since 2.6 (plain Spring allows them).
  - If you enforce constructor injection, cycles become physically impossible to instantiate, 
    forcing you to fix the architecture immediately.
- **Redesign your own code:** [break the cycle by redesign](#how-do-you-break-a-cycle-by-redesign).
- **Defer injection (when you don't own the code):** [change only the injection side](#how-do-you-handle-a-cycle-you-cant-change).

</details>

### How do you break a cycle by redesign?
<details><summary>Show answer</summary>

Ask why A and B need each other; the reason picks the fix.
- **[They share a part:](#how-do-you-fix-a-shared-part-cycle)** extract it into a third bean. A and B depend on it,
  not on each other.
- **[A method sits on the wrong side:](#what-is-feature-envy)** move it to the side that owns the data, so only one
  direction is left.
- **[B only tells A that something happened:](#how-do-you-fix-a-callback-cycle)** make it an event. 
  B publishes, A listens, and B no longer needs A.
- **They can't work apart:** they may be one class.

</details>

### How do you fix a shared-part cycle?
<details><summary>Show answer</summary>

A and B call each other only to reach the same piece of logic (here, pricing). Move that piece into its own bean;
A and B both inject it instead of each other.

```java
@Service
class Pricing {                  // the part both A and B needed
  BigDecimal priceOf(Item item) { /* ... */ }
}

@Service
class A {
  @Autowired Pricing pricing;    // was: @Autowired B b;
}

@Service
class B {
  @Autowired Pricing pricing;    // was: @Autowired A a;
}
```

</details>

### What is Feature Envy?
<details><summary>Show answer</summary>

**Feature Envy** — a method that uses another class's data more than its own. It sits in the wrong class.

```java
@Service
class OrderService {
  @Autowired CustomerService customers;   // real need: placing an order checks the customer
  List<Order> findByCustomer(long customerId) { /* ... */ }
}

@Service
class CustomerService {
  @Autowired OrderService orders;         // exists only for lastOrderDate()

  LocalDate lastOrderDate(long customerId) {   // reads only orders: wrong side
    return orders.findByCustomer(customerId).stream().map(Order::date).max(Comparator.naturalOrder()).orElse(null);
  }
}
```

`lastOrderDate()` touches no customer data; it only reads orders. Because it lives in `CustomerService`, that class
depends on `OrderService` just to reach the data, and since `OrderService` already depends on `CustomerService`, that
closes a cycle.

The fix is **Move Method**: move it to `OrderService`, the class that owns the data. `CustomerService` no longer needs
`OrderService`, and only one direction is left. This works only if `CustomerService` just passed the call through.
If its own code still needs the date, it still has to inject `OrderService` to call the moved method, and the cycle
stays.

Put the method next to the data it reads, and the dependency goes with it.

</details>

### How do you fix a callback cycle?
<details><summary>Show answer</summary>

A calls B, and B calls A back only to say the work is done. That call back is the whole cycle.

```java
@Service
class A {
  @Autowired B b;

  public void startProcess() { b.doWork(); }
  public void onWorkDone() { /* react to completion */ }
}

@Service
class B {
  @Autowired A a;

  public void doWork() {
    // ... execute logic ...
    a.onWorkDone();   // B only injects A to notify it
  }
}
```

Fix: B publishes an event instead of calling A, and A listens for it. B no longer injects A.

```java
record WorkDoneEvent(String message) {}

@Service
class A {
  @Autowired B b;

  public void startProcess() { b.doWork(); }

  @EventListener
  public void onWorkDone(WorkDoneEvent event) { /* react to completion */ }
}

@Service
class B {
  @Autowired ApplicationEventPublisher publisher;   // was: @Autowired A a;

  public void doWork() {
    // ... execute logic ...
    publisher.publishEvent(new WorkDoneEvent("success"));
  }
}
```

By default the listener runs right away, in the same thread, before `publishEvent` returns. 
That is the same order as the old direct call.

B says what happened; it no longer needs to know who cares.

</details>

### How do you handle a cycle you can't change?
<details><summary>Show answer</summary>

Every injection trick moves the cycle; only a redesign removes it.
A cycle is a sign that a responsibility sits on the wrong side, so the real fix is a
[redesign](#how-do-you-break-a-cycle-by-redesign).

**Only when the cycle runs through code you can't change** (a library, another team's module), change your own side —
how your bean gets the other one:

- [`@Lazy`](#how-does-lazy-break-a-cycle--and-what-does-it-cost) — Spring injects a proxy now and finds the real bean
  on the first call.
- [`ObjectProvider`](#how-does-objectprovider-break-a-cycle) — your bean asks for the other one when it needs it.

**Strict Requirement:**
This only works if the deferred bean is not accessed during the initialization phase. 
You cannot invoke methods on the `@Lazy` proxy or call `.getObject()` inside the constructor or an `@PostConstruct` method. 
The actual usage must be deferred until normal runtime execution.

What both cost:

- The cycle is still there, and it now passes Spring Boot's cycle check, so nothing points at it.
- Delayed failures: If the target bean fails to initialize, the application crashes later at runtime 
  (upon first use) instead of safely failing fast during startup.
- **Overhead**: `@Lazy` adds proxying overhead, and `ObjectProvider` adds boilerplate directly into business logic.

</details>

### How does `@Lazy` break a cycle — and what does it cost?
<details><summary>Show answer</summary>

```java
@Service
class A {
  private final B b;

  A(@Lazy B b) { this.b = b; }   // b is a proxy; the real B is looked up on first call
}
```

- Spring injects a proxy instead of B, so A's constructor can finish and the cycle closes — this works for constructor
  cycles too.
- Costs: the cycle is hidden, not removed; if B can't be created, the error shows on the first call, not at startup;
  every call goes through a proxy.

`@Lazy` hands over a placeholder now and the real bean later.

</details>

### `@Lazy` on the class vs on the injection point?
<details><summary>Show answer</summary>

- On the injection point (field or parameter): Spring injects a proxy — this is what breaks a cycle.
- On the class: the bean is only created later. When another bean needs it, it is created then — through the same
  cycle. It doesn't break the cycle.

`@Lazy` on the class delays the bean; `@Lazy` on the injection point delays the lookup.

</details>

### How does ObjectProvider break a cycle?
<details><summary>Show answer</summary>

**`ObjectProvider<B>` in A:** A doesn't take B at startup; it asks for B when it needs it. 
Spring can finish A without B, so creation has no cycle. 
This works for constructor cycles too, and under Boot 2.6+ defaults.

```java
@Service
class A {
  private final ObjectProvider<B> b;   // was: private final B b;

  A(ObjectProvider<B> b) { this.b = b; }

  void run() {
    b.getObject().doWork();             // B is looked up here, not in the constructor
  }
}

@Service
class B {
  private final A a;                    // B still takes A directly

  B(A a) { this.a = a; }

  void doWork() { /* ... */ }
}
```

Its own cost, on top of the [shared ones](#how-do-you-handle-a-cycle-you-cant-change): a Spring type inside A, and
`getObject()` at every use.

**Setter or field on one side, constructor on the other:** the old early-reference trick. 
It works only if Spring creates the setter-side bean first, and Boot 2.6+ refuses it by default.

</details>

### How does self-injection work in Spring?
<details><summary>Show answer</summary>

A [call on `this`](../02_AOP_and_Transactions/2.1_Proxies.md) skips the proxy, so `@Transactional` on the
called method does nothing. The bean injects itself and calls through `self`, which is the proxy.

```java
@Service
class OrderService {
  @Autowired OrderService self;   // the proxy, not this

  public void placeAll(List<Order> orders) {
    orders.forEach(self::place);  // through the proxy → each place() gets a transaction
  }

  @Transactional
  public void place(Order order) { /* ... */ }
}
```

A bean that needs itself is a cycle of one: `self` gets the early reference, which is already the proxy.

</details>

### How does self-injection work under Boot 2.6+?
<details><summary>Show answer</summary>

Boot turns cycles off by default, so plain self-injection fails at startup. Look the bean up after it is finished
instead; that also gives the final proxy:

```java
@Autowired @Lazy OrderService self;             // a proxy now, the real bean on the first call
@Autowired ObjectProvider<OrderService> self;   // self.getObject().place(order)
```

</details>
