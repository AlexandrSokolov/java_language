# Circular Dependencies

### A needs B, B needs A — what happens?
<details><summary>Show answer</summary>

```java
@Service class A { @Autowired B b; }
@Service class B { @Autowired A a; }
```

By default this is not possible: Spring Boot 2.6+ refuses this **circular dependency**, and startup fails with "The
dependencies of some of the beans in the application context form a cycle".

Cycles are allowed in plain Spring Framework by default (for example, a library), or in Boot when you switch the
check off. The Boot switch is a stopgap, for example during a migration: it hides the cycle instead of fixing it.
When cycles are allowed, the result depends on the injection type:

- Field or setter: Spring resolves the cycle by handing B a half-built A
  ([how](#how-does-spring-resolve-a-field-or-setter-cycle)).
- Constructor on both sides: Spring can't resolve it, so startup fails.

</details>

### Where does Spring keep singleton instances?
<details><summary>Show answer</summary>

In three maps, checked in this order:

- `singletonObjects` (L1) — finished beans.
- `earlySingletonObjects` (L2) — half-built beans already handed out during a cycle.
- `singletonFactories` (L3) — factories that can hand out a half-built bean on request.

Why a factory, not the bean itself:

- If A will be proxied (e.g. `@Transactional`), B must get the proxy, not the raw A. But the proxy is normally made
  at the end of A's lifecycle.
- Spring calls the factory only if someone asks for A before A is finished. The factory asks the auto-proxy creator
  for an early proxy (`getEarlyBeanReference`).
- The result moves to `earlySingletonObjects` and the factory is removed, so the factory runs once and every later
  request gets the same object.
- With no cycle, the factory is never called, and the proxy is made at the usual time.

The factory makes the early proxy only when a cycle actually needs it.

</details>

### How does Spring resolve a field or setter cycle?
<details><summary>Show answer</summary>

- Spring calls A's constructor. A now exists; its fields are still empty.
- It puts a factory into `singletonFactories` that returns an early reference to A (A before it is finished).
- It fills A's fields, needs B, and starts B.
- B needs A. Spring checks the three caches in order:
  - `singletonObjects` (finished beans): not there.
  - `earlySingletonObjects` (early references already handed out): not there.
  - `singletonFactories`: finds A's factory, runs it, moves the result to `earlySingletonObjects`, removes the factory.
- B gets the half-built A, completes, and goes into `singletonObjects`.
- A gets B, completes, and moves to `singletonObjects`.

The third cache holds a factory, not A itself, because of AOP: if A gets a proxy, B must receive the proxy, not the
raw A. The factory builds the proxy early, and only when a cycle actually asks for A.

A must exist before anyone can point to it, so its constructor runs first and the object is shared before it is 
finished.

</details>

### What does B see when it gets A early?
<details><summary>Show answer</summary>

A half-built A: its constructor has run, but some of its fields may still be `null`, and its `@PostConstruct` has not
run.

```java
@Service
class B {
  @Autowired A a;

  @PostConstruct
  void init() {
    a.load();   // A's fields are not all injected yet → NullPointerException inside load()
  }
}
```

An early reference is a bean that exists, not a bean that is finished.

</details>

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Configuration @EnableAsync
class AsyncConfig {}

@Service
class A {
  @Autowired B b;

  @Async
  public void sendReport() { /* ... */ }
}

@Service
class B {
  @Autowired A a;
}
```

</details>

<details><summary>Show answer</summary>

With cycles allowed, startup fails with `BeanCurrentlyInCreationException`: A "has been injected into other beans
[b] in its raw version ... but has eventually been wrapped".

- B gets A's early reference: the raw A.
- `AsyncAnnotationBeanPostProcessor` can't make early proxies. It wraps A only at the end of A's lifecycle.
- The container holds the proxy, B holds the raw A. Spring detects the mismatch and fails.

Not guaranteed: it fails only if A is created first. If B goes first, B gets the finished proxy.

Minimal fix: `@Lazy` on B's field, so B looks up the real A on first call, not at startup.

```java
@Autowired @Lazy A a;
```

Better: remove the cycle by moving what B needs out of A.

Early references work only with proxies that can be made early.

</details>

</details>

### Prototype cycle?
<details><summary>Show answer</summary>

Never resolved. Prototypes are not cached, so there is no early reference to hand out: A needs a new B, which needs a
new A, and so on. Spring detects it and fails with `BeanCurrentlyInCreationException`.

No cache, no early reference — a prototype cycle can't close.

</details>

### What changed in Boot's dependency resolution?
<details><summary>Show answer</summary>

Since Spring Boot 2.6, any bean cycle fails at startup by default, and Boot prints the cycle. Before, Boot let field
and setter cycles through without a word.

Boot did this by switching off circular references in the bean factory. Spring Framework itself didn't change:
without Boot, field and setter cycles still work. `spring.main.allow-circular-references=true` turns them back on in
Boot.

Boot turned a quiet patch into a startup error.

</details>

### Allowing cycles again — what does it hide?
<details><summary>Show answer</summary>

- A design problem: two classes that each need the other are usually one job split badly, or a missing third class.
- The runtime risks of early references: [half-built beans](#what-does-b-see-when-it-gets-a-early) and the
  [proxy mismatch](#describe-a-code-snippet-1).

The property removes the error, not the cycle.

</details>

### Why can't a constructor cycle be resolved?
<details><summary>Show answer</summary>

An early reference needs an object, and an object exists only after its constructor returns. A's constructor needs B,
B's constructor needs A — neither constructor can finish, so there is nothing to hand out. Startup fails with
`BeanCurrentlyInCreationException` ("Is there an unresolvable circular reference?").

That is what makes constructor injection useful here: the cycle shows up at once instead of being patched.

No finished constructor, no object — nothing to share early.

</details>

### How do you break a cycle by redesign?
<details><summary>Show answer</summary>

- **They share a part:** extract it into a third bean. A and B depend on it, not on each other.
- **[A method sits on the wrong side:](#what-is-feature-envy)** move it to the side that owns the data, so only one direction is left.
- **B only tells A that something happened:** make it an event. B publishes, A listens, and B no longer needs A.
- **They can't work apart:** they may be one class.

Extracting a third bean:

```java
@Service
class Pricing {                  // the part both A and B needed
  BigDecimal priceOf(Item item) { /* ... */ }
}

@Service
class A {
  @Autowired Pricing pricing;    // was: @Autowired B b;
}

@Service
class B {
  @Autowired Pricing pricing;    // was: @Autowired A a;
}
```

Ask why A and B need each other; the reason picks the fix.

</details>

### What is Feature Envy?
<details><summary>Show answer</summary>

**Feature Envy** — a method that uses another class's data more than its own. It sits in the wrong class.

```java
@Service
class OrderService {
  @Autowired CustomerService customers;   // real need: placing an order checks the customer
  List<Order> findByCustomer(long customerId) { /* ... */ }
}

@Service
class CustomerService {
  @Autowired OrderService orders;         // exists only for lastOrderDate()

  LocalDate lastOrderDate(long customerId) {   // reads only orders: wrong side
    return orders.findByCustomer(customerId).stream().map(Order::date).max(Comparator.naturalOrder()).orElse(null);
  }
}
```

`lastOrderDate()` touches no customer data; it only reads orders. Because it lives in `CustomerService`, that class
depends on `OrderService` just to reach the data, and since `OrderService` already depends on `CustomerService`, that
closes a cycle.

The fix is **Move Method**: move it to `OrderService`, the class that owns the data. `CustomerService` no longer needs
`OrderService`, and only one direction is left. This works only if `CustomerService` just passed the call through.
If its own code still needs the date, it still has to inject `OrderService` to call the moved method, and the cycle
stays.

Put the method next to the data it reads, and the dependency goes with it.

</details>

### How does `@Lazy` break a cycle — and what does it cost?
<details><summary>Show answer</summary>

```java
@Service
class A {
  private final B b;

  A(@Lazy B b) { this.b = b; }   // b is a proxy; the real B is looked up on first call
}
```

- Spring injects a proxy instead of B, so A's constructor can finish and the cycle closes — this works for constructor
  cycles too.
- Costs: the cycle is hidden, not removed; if B can't be created, the error shows on the first call, not at startup;
  every call goes through a proxy.

`@Lazy` hands over a placeholder now and the real bean later.

</details>

### `@Lazy` on the class vs on the injection point?
<details><summary>Show answer</summary>

- On the injection point (field or parameter): Spring injects a proxy — this is what breaks a cycle.
- On the class: the bean is only created later. When another bean needs it, it is created then — through the same
  cycle. It doesn't break the cycle.

`@Lazy` on the class delays the bean; `@Lazy` on the injection point delays the lookup.

</details>

### Other tricks — `ObjectProvider`, setter on one side?
<details><summary>Show answer</summary>

- `ObjectProvider<B>` in A: A asks for B when it needs it, after startup — no cycle at creation time.
- Setter or field injection on one side, constructor on the other: the old early-reference trick — refused under
  Boot 2.6+ defaults.
- Same cost as `@Lazy`: the cycle is still there, only hidden.

Every injection trick moves the cycle; only a redesign removes it.

</details>

### Self-injection under Boot 2.6+?
<details><summary>Show answer</summary>

- Self-injection: a bean injects itself so that calls to its own `@Transactional` methods go through the proxy — a
  [call on `this`](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md) skips it.
- Under Boot 2.6+ defaults it counts as a cycle and startup fails; it works again with `@Lazy` on the self-injected
  field. *(unverified)*

A bean that needs itself is a cycle of one.

</details>
