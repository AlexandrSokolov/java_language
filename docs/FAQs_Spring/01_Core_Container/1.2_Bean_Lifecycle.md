# Bean Lifecycle

- Steps — instantiation, dependency injection, initialization, use, destruction.
- `BeanPostProcessor` — runs around initialization; where proxies are created.
- `BeanFactoryPostProcessor` vs `BeanPostProcessor`.
- Init callbacks — `@PostConstruct`, `InitializingBean`, `initMethod`.
- Destroy callbacks — `@PreDestroy`, `DisposableBean`, `destroyMethod`.

### Where does setup code that needs dependencies go?
<details><summary>Show answer</summary>

```java
@Service
class PriceCache {
  @Autowired private PriceClient client;

  PriceCache() {
    client.loadAll();   // NullPointerException: client is not set yet
  }
}
```

- Spring calls the constructor first, and fills fields and setters after it — code in the constructor runs before
  `client` is set.
- The container offers a step after injection, an **init callback** such as `@PostConstruct`, where every dependency
  is in place. Init callbacks are one step of the **bean lifecycle**.

The constructor builds the object; the init callback runs once it's wired.

</details>

### What steps does a bean go through?
<details><summary>Show answer</summary>

- Create — the constructor runs (constructor injection happens here).
- Inject — fields and setters are filled.
- `Aware` callbacks — e.g. `setBeanName()`, `setApplicationContext()`.
- `BeanPostProcessor` before-init.
- Init callbacks — `@PostConstruct`, `afterPropertiesSet()`, `initMethod`.
- `BeanPostProcessor` after-init — may replace the bean with a proxy.
- In use.
- Destroy — when the context closes: `@PreDestroy`, `destroy()`, `destroyMethod`.

Each step needs the one before: you can't inject into an object that doesn't exist, init a bean that isn't wired, or
wrap one that isn't ready.

</details>

### What are the `Aware` interfaces for?
<details><summary>Show answer</summary>

- They hand a bean a piece of the container through a callback: `BeanNameAware` (its own name), `BeanFactoryAware`,
  `ApplicationContextAware`, `EnvironmentAware`, ...
- Spring calls them after injection, before the init callbacks.
- Today you mostly inject these instead — `ApplicationContext` and `Environment` can be injected like any bean; the
  interfaces tie the class to Spring.

`Aware` means "give me a piece of the container"; injection does the same with less coupling.

</details>

### When are singletons created?
<details><summary>Show answer</summary>

- At startup: the `ApplicationContext` creates every non-lazy singleton while it starts. A missing dependency or a
  failing constructor stops startup — the error shows early, not at the first request.
- `@Lazy` on the bean delays creation to the first time it is needed — and the error with it. Spring Boot can make all
  beans lazy with `spring.main.lazy-initialization=true`.
- Prototypes are created each time they are requested, never at startup.

Singletons are built at startup so wiring errors fail fast; `@Lazy` trades that for a faster start.

</details>

### How do you run code once all beans are ready?
<details><summary>Show answer</summary>

`@PostConstruct` runs when one bean is ready, not the whole application. For the later moments:

- `SmartInitializingSingleton.afterSingletonsInstantiated()` — after all singletons are created.
- `@EventListener(ContextRefreshedEvent.class)` — after the context has fully started.
- Spring Boot: `ApplicationRunner` / `CommandLineRunner`, or `@EventListener(ApplicationReadyEvent.class)` — after the
  application has started.

Bean setup goes in `@PostConstruct`; application startup work waits for a later callback.

</details>

### What does a `BeanPostProcessor` do?
<details><summary>Show answer</summary>

```java
public interface BeanPostProcessor {
  default Object postProcessBeforeInitialization(Object bean, String name) { return bean; }
  default Object postProcessAfterInitialization(Object bean, String name) { return bean; }
}
```

- Spring calls both methods for every bean in the context, around its init callbacks.
- The return value replaces the bean: return a wrapper, and every other bean gets the wrapper.
- `BeanPostProcessor`s are beans too, created before the ordinary beans.

A `BeanPostProcessor` sees every bean once, and may hand back a different object.

</details>

### Where do `@Transactional` proxies come from?
<details><summary>Show answer</summary>

- A `BeanPostProcessor` (usually the auto-proxy creator) checks each bean in `postProcessAfterInitialization`. If any
  method needs extra behavior — `@Transactional`, `@Async`, `@Cacheable`, an aspect — it returns a
  [proxy](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md) that wraps the bean.
- The proxy replaces the bean in the container, so other beans are injected with the proxy, never the raw object.
- This happens after the init callbacks: inside `@PostConstruct`, `this` is still the raw bean.

Proxies are added by a post-processor after init, and replace the bean everywhere.

</details>

### Who processes `@Autowired` and `@PostConstruct`?
<details><summary>Show answer</summary>

- `@Autowired`, `@Value`, `@Inject` — `AutowiredAnnotationBeanPostProcessor`, during the inject step.
- `@PostConstruct`, `@PreDestroy`, `@Resource` — `CommonAnnotationBeanPostProcessor`.
- They are post-processors like any other; the annotations do nothing on their own.

Annotations are only markers; post-processors give them meaning.

</details>

### `@Autowired` in an object made with `new`?
<details><summary>Show answer</summary>

Nothing happens: the field stays `null`. Only objects the container creates pass through its post-processors.

```java
OrderService s = new OrderService();   // not a bean
s.place(order);                        // client is null → NullPointerException
```

Spring only touches objects it creates.

</details>

### "Not eligible for getting processed by all BeanPostProcessors" — meaning?
<details><summary>Show answer</summary>

The full log line: "Bean 'x' of type [...] is not eligible for getting processed by all BeanPostProcessors (for
example: not eligible for auto-proxying)".

- `BeanPostProcessor`s are created before ordinary beans. If one of them (or the config class that defines it) needs
  bean `x`, Spring must create `x` early — before every post-processor is registered.
- `x` then misses the post-processors created after it: often it gets no proxy, so its `@Transactional`, `@Async` or
  `@Cacheable` silently does nothing.

Beans pulled in by post-processors are built too early to be post-processed themselves.

</details>

### `@Transactional` method called from `@PostConstruct` — transaction?
<details><summary>Show answer</summary>

```java
@Service
class Warmup {
  @PostConstruct
  void init() {
    load();                 // no transaction
  }

  @Transactional
  public void load() { /* queries */ }
}
```

- No. `@PostConstruct` runs before the after-init step that creates the proxy, and `load()` is called on `this` — the
  raw object.
- Even after startup, a call from inside the bean [skips the proxy](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md).

`@PostConstruct` runs on the raw object, before any proxy exists.

</details>

### `@PostConstruct` throws — what happens to startup?
<details><summary>Show answer</summary>

Example: `@PostConstruct` loads data from a database that is down.

- The exception becomes a `BeanCreationException`. For a singleton created at startup, the whole context fails to
  start; Spring destroys the beans it had already created, and the application exits.
- A `@Lazy` bean fails later, on first use, instead.
- Slow work in `@PostConstruct` also slows startup: it runs on the startup thread, one bean after another.

A failing init callback stops the whole context, not just the bean.

</details>

### `BeanFactoryPostProcessor` vs `BeanPostProcessor`?
<details><summary>Show answer</summary>

- **`BeanFactoryPostProcessor`** — runs once, after bean definitions are loaded and before any ordinary bean is
  created. It changes the definitions: class, scope, property values. Example: `PropertySourcesPlaceholderConfigurer`
  resolves `${...}` placeholders.
- **`BeanPostProcessor`** — runs for every bean object, around its init. It changes or wraps the objects.

A `BeanFactoryPostProcessor` changes bean definitions before any bean exists; a `BeanPostProcessor` changes each bean
after it is made.

</details>

### Why must a `BeanFactoryPostProcessor` `@Bean` method be `static`?
<details><summary>Show answer</summary>

```java
@Configuration
class AppConfig {
  @Value("${app.name}") String name;   // stays null

  @Bean   // not static: AppConfig must be created before any BeanPostProcessor exists
  PropertySourcesPlaceholderConfigurer placeholders() {
    return new PropertySourcesPlaceholderConfigurer();
  }
}
```

- `BeanFactoryPostProcessor`s run before ordinary beans. A non-static `@Bean` method needs an `AppConfig` object, so
  Spring creates `AppConfig` that early — before the post-processors that handle `@Autowired` and `@Value` exist.
- `AppConfig` is left with its `@Autowired` and `@Value` fields unset; Spring logs a warning about it.
- A `static` method can be called without creating `AppConfig` at all.

A `static` method lets the post-processor exist before its config class does.

</details>

### Who reads `@Configuration` classes?
<details><summary>Show answer</summary>

- `ConfigurationClassPostProcessor` — a `BeanDefinitionRegistryPostProcessor` (a `BeanFactoryPostProcessor` that may
  also add definitions). It runs first, reads `@Configuration`, `@ComponentScan`, `@Import` and `@Bean`, and registers
  a bean definition for each bean it finds.
- It also sets up the CGLIB subclass for
  [full-mode](1.1_DI_and_Configuration.md#one-bean-method-calls-another--same-instance) `@Configuration` classes.

Java config is itself handled by a post-processor that turns annotations into bean definitions.

</details>

### Three init callbacks — in what order?
<details><summary>Show answer</summary>

- `@PostConstruct` → `InitializingBean.afterPropertiesSet()` → `initMethod` (`@Bean(initMethod = "...")`).
- `@PostConstruct` comes first because a post-processor (`CommonAnnotationBeanPostProcessor`) calls it in the
  before-init step; the other two are the init step itself.
- If two of them name the same method, it runs once.

Annotation, then interface, then config.

</details>

### Which init callback should you use?
<details><summary>Show answer</summary>

- `@PostConstruct` — a standard Jakarta annotation, no Spring interface in your class. The default.
- `initMethod` — for classes you can't change (third-party).
- `InitializingBean` — ties the class to Spring; mostly used inside Spring itself.

Annotate your own classes; configure the init method for others'.

</details>

### `@PostConstruct` silently ignored — why?
<details><summary>Show answer</summary>

- The annotation comes from the wrong package. Spring 6 and Boot 3 look for `jakarta.annotation.PostConstruct`; code
  that still imports `javax.annotation.PostConstruct` (with the old jar on the classpath) compiles, but the method may
  never be called. *(unverified)*
- The object is not a bean — it was [made with `new`](#autowired-in-an-object-made-with-new).

The annotation must be the one Spring looks for, on an object Spring made.

</details>

### Three destroy callbacks — in what order?
<details><summary>Show answer</summary>

- `@PreDestroy` → `DisposableBean.destroy()` → `destroyMethod`.
- They run when the context closes, for singletons —
  [prototypes get none](1.3_Scopes.md#what-happens-to-a-prototype-after-spring-hands-it-out).

Same order as init: annotation, interface, config.

</details>

### When do destroy callbacks not run?
<details><summary>Show answer</summary>

- The process is killed hard — `kill -9`, a crash, power loss — so no Java code runs.
- Plain Spring with no `context.close()` and no shutdown hook — the JVM exits without closing the context. Spring Boot
  registers the shutdown hook for you.
- Prototype beans — Spring doesn't keep track of them.

Destroy callbacks need an orderly close of the context.

</details>

### Why was `close()` called on a bean you never set up for it?
<details><summary>Show answer</summary>

- For a `@Bean` method, `destroyMethod` defaults to "inferred": Spring calls a public no-argument `close()` or
  `shutdown()` method if the class has one.
- So a pool or client returned from a `@Bean` is closed at shutdown — usually wanted, but wrong for an object someone
  else owns, such as one looked up from JNDI or shared with another context.

`@Bean` guesses the destroy method — and closes what it finds.

</details>

### In what order are beans destroyed?
<details><summary>Show answer</summary>

- A bean is destroyed before the beans it depends on, so during its `@PreDestroy` its dependencies still work.
- `@DependsOn("x")` adds an order Spring can't see from injection: the bean is created after `x` and destroyed before
  it.

Dependents go first, so nothing loses a dependency while it is still running.

</details>
