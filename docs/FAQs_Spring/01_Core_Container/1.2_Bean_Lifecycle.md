# Bean Lifecycle

### Describe a code snippet #1
<details><summary><strong>Show details</strong></summary>

<details><summary>Show code</summary>

```java
@Service
class PriceCache {
  @Autowired private PriceClient client;

  PriceCache() {
    client.loadAll();
  }
}
```

</details>

<details><summary>Show answer</summary>

`client.loadAll()` throws `NullPointerException`. Spring calls the constructor first and sets `@Autowired` fields
only after it returns, because a field can only be set on an object that already exists. Inside the constructor
`client` is still `null`.

- The order is fixed, so this fails every time, not by chance. Bean creation fails (the NPE comes wrapped in a
  `BeanCreationException`) and the application does not start.
- Even with `client` set, the call does not belong in a constructor. Loading from another system is slow and can
  throw. In a constructor it runs on every `new PriceCache(...)`, including in a unit test, so the object cannot be
  created without doing the load. The constructor only assigns fields.

The load goes in an **init callback**: a method the container calls once, after all injection. 
The order constructor → fields and setters → init callbacks is the start of the **bean lifecycle**.

```java
@Service
class PriceCache {
  private final PriceClient client;

  PriceCache(PriceClient client) {   // only assigns
    this.client = client;
  }

  @PostConstruct                     // runs once client is set
  void load() {
    client.loadAll();
  }
}
```

- Minimal fix: keep the `@Autowired` field and move the call into a `@PostConstruct` method. It works, but field
  injection stays: `new PriceCache()` in a unit test leaves `client` `null`.
- The rewrite uses constructor injection: `client` is `final` and required, and a test must pass it in.

The constructor only builds and assigns. Work that uses dependencies goes in the init callback.

</details>

</details>

### What steps does a bean go through?
<details><summary>Show answer</summary>

- Create — the constructor runs (constructor injection happens here).
- Inject — fields and setters are filled.
- `Aware` callbacks — e.g. `setBeanName()`, `setApplicationContext()`.
- `BeanPostProcessor` before-init.
- Init callbacks — `@PostConstruct`, `afterPropertiesSet()`, `initMethod`.
- `BeanPostProcessor` after-init — may replace the bean with a proxy.
- In use.
- Destroy — when the context closes: `@PreDestroy`, `destroy()`, `destroyMethod`.

Note: simplified. Some `Aware` callbacks and `@PostConstruct` run inside `BeanPostProcessor` before-init. 
Prototypes are not destroyed.

</details>

### What are the `Aware` interfaces for?
<details><summary>Show answer</summary>

An `Aware` interface is the old way for a bean to get a piece of the container: its own name (`BeanNameAware`), the
`BeanFactory`, the `ApplicationContext`, the `Environment`. It comes from early Spring, when the container itself
could not be injected. The class implements the interface, which has one setter. You write the setter and store the
value in a field yourself. Spring sees the interface and calls the setter after injection, before the init callbacks.

```java
@Component
class ReportJob implements EnvironmentAware {
  private Environment env;                               // not final, null until Spring calls the setter

  @Override
  public void setEnvironment(Environment environment) {  // you write it, Spring calls it
    this.env = environment;
  }

  String reportDir() {
    return env.getProperty("report.dir");
  }
}
```

The cost: 
- the class implements a Spring interface only to receive one object. 
- The field cannot be `final`, `env` is still `null` inside the constructor, and a test must remember to call the setter.


Today `Environment` and `ApplicationContext` are injected like any other bean:

```java
@Component
class ReportJob {
  private final Environment env;

  ReportJob(Environment env) {   // Spring passes it in
    this.env = env;
  }

  String reportDir() {
    return env.getProperty("report.dir");
  }
}
```

There is no extra interface or setter. `env` is `final` and set before any method runs. 
The constructor shows what the class needs, so a test just passes a `MockEnvironment`. 
The one piece that cannot be injected is the bean's own name, so `BeanNameAware` stays.

Old way: implement a setter, and Spring calls it with a piece of the container. Today: inject that piece.

</details>

### When are singletons created?
<details><summary>Show answer</summary>

At startup: the `ApplicationContext` creates every non-lazy singleton while it starts. 
A missing dependency or a failing constructor stops startup, so the error shows early, not at the first request.

`@Lazy` on the bean delays creation to the first time it is needed, and the error moves with it. Spring Boot can make
all beans lazy with `spring.main.lazy-initialization=true`.

Singletons are built at startup so wiring errors fail fast; `@Lazy` trades that for a faster start.

</details>

### How do you run code once a bean is ready?
<details><summary>Show answer</summary>

Spring calls an **init callback** after the bean is created and its dependencies are set:

- `@PostConstruct` on a method — the usual way.
- `InitializingBean.afterPropertiesSet()` — the class implements a Spring interface.
- `@Bean(initMethod = "init")` — for a class you cannot change, such as one from a library.

</details>

### How do you run code once all beans are ready?
<details><summary>Show answer</summary>

`@PostConstruct` only means [*this* bean is ready](#how-do-you-run-code-once-a-bean-is-ready). 
To wait for the whole system, pick the callback by its primary purpose:

- **Cross-bean checks:** `SmartInitializingSingleton.afterSingletonsInstantiated()` — all singletons exist, but the
  context hasn't "started" yet.
- **Warm caches / start schedulers:** `@EventListener(ContextRefreshedEvent.class)` — the core Spring context is fully
  wired and active.
- **Process CLI arguments:** `ApplicationRunner` / `CommandLineRunner` (Spring Boot) — made to read startup `args`.
- **Work that must run last:** `@EventListener(ApplicationReadyEvent.class)` (Spring Boot) — after the runners; the
  app is fully up. Good for starting to read from a queue.

</details>

### What is the primary purpose of a `BeanPostProcessor`?
<details><summary>Show answer</summary>

It is Spring's hook to inspect, change, or completely replace a bean before the application can use it. 
This is how `@Transactional` and `@Async` work: 
a `BeanPostProcessor` sees the annotation and swaps your bean for a proxy that opens and commits the transaction, 
or runs the call on another thread.

```java
public interface BeanPostProcessor {
  default Object postProcessBeforeInitialization(Object bean, String name) { return bean; }
  default Object postProcessAfterInitialization(Object bean, String name) { return bean; }  // proxies are made here
}
```

Spring calls both methods for every bean in the context, around its init callbacks. 
The return value replaces the bean: return a proxy, 
and the rest of the application gets the proxy instead of the original.

</details>

### Where do `@Transactional` proxies come from?
<details><summary>Show answer</summary>

From a `BeanPostProcessor`, usually the auto-proxy creator, in `postProcessAfterInitialization`. It checks each bean,
and if any method needs extra behavior (`@Transactional`, `@Async`, `@Cacheable`, an aspect), it returns a
[proxy](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md) that wraps the bean. That proxy
[replaces the bean](#what-is-the-primary-purpose-of-a-beanpostprocessor) for every bean that injects it.

Proxies come from a post-processor, after init.

</details>

### Who processes `@Autowired` and `@PostConstruct`?
<details><summary>Show answer</summary>

- `@Autowired`, `@Value`, `@Inject` — `AutowiredAnnotationBeanPostProcessor`.
- `@PostConstruct`, `@PreDestroy`, `@Resource` — `CommonAnnotationBeanPostProcessor`.


Annotations do nothing by themselves; a `BeanPostProcessor` finds them by reflection and acts. 
If one has no effect, its processor is not registered, or Spring did not create the object (new).

</details>

### `@Autowired` in an object made with `new`?
<details><summary>Show answer</summary>

Nothing happens: the field stays `null`. Only objects the container creates pass through its post-processors.

</details>

### "Not eligible for getting processed by all BeanPostProcessors" — meaning?
<details><summary>Show answer</summary>

The full log line: "Bean 'x' of type [...] is not eligible for getting processed by all BeanPostProcessors (for
example: not eligible for auto-proxying)".

Spring creates all `BeanPostProcessor`s before ordinary beans. 
A bean that a post-processor needs is created early and misses the post-processors that are not ready yet.

```java
@Component
class AuditTagger implements BeanPostProcessor {
  private final AuditService audit;

  AuditTagger(AuditService audit) {   // a post-processor needs AuditService, so AuditService is created early
    this.audit = audit;
  }
  // ...
}

@Service
class AuditService {
  @Transactional                      // no effect if AuditService missed the proxy step
  public void record(String event) {
    // ...
  }
}
```

If it misses the proxy step, `@Transactional` silently does nothing, everywhere: this early bean is the one the
container keeps.

Fix: inject it with `@Lazy`, so the real bean is created on first use, after all post-processors are ready.

```java
  AuditTagger(@Lazy AuditService audit) {   // a proxy now; the real AuditService is created on first use
    this.audit = audit;
  }
```

For a `@Bean` post-processor in a configuration class, make the method `static`, so the class is not created early.

</details>

### `@Transactional` method called from `@PostConstruct` — how?
<details><summary>Show answer</summary>

```java
@Service
class Warmup {
  @PostConstruct
  void init() {
    load();                 // no transaction
  }

  @Transactional
  public void load() { /* queries */ }
}
```

- No. `@PostConstruct` runs before the after-init step that creates the proxy, and `load()` is called on `this` — the
  raw object.
- Even after startup, a call from inside the bean [skips the proxy](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md).

`@PostConstruct` runs on the raw object, before any proxy exists.

</details>

### `@PostConstruct` throws — what happens to startup?
<details><summary>Show answer</summary>

Example: `@PostConstruct` loads data from a database that is down.

- **Standard Singletons (Eager):** The exception is wrapped in a `BeanCreationException`. 
  The whole Spring context fails to start.
- **`@Lazy` Bean:** fails the first time it is needed instead. It fails the specific request, but the container stays alive.

A failing init callback stops the whole context, not just the bean.

</details>

### What belongs in `@PostConstruct`?
<details><summary>Show answer</summary>

Quick setup of this one bean: check a required property, or build a small lookup map from config.

Slow work, such as a big database load or a call to another service, does not belong there. It delays startup, and
if that system is down, the application does not start. Run it after startup, on another thread:

```java
@Service
class PriceCache {
  private final PriceClient client;
  private volatile Map<String, BigDecimal> prices = Map.of();   // read by request threads, written by the loader

  PriceCache(PriceClient client) {
    this.client = client;
  }

  @Async                                          // another thread; needs @EnableAsync
  @EventListener(ApplicationReadyEvent.class)     // after startup is done
  public void load() {
    prices = client.loadAll();
  }
}
```

Requests that arrive before the load finishes see the empty map, so the code must handle "not loaded yet".

</details>

### `BeanFactoryPostProcessor` vs `BeanPostProcessor`?
<details><summary>Show answer</summary>

They differ in when they run and what they change: blueprints vs. finished objects.

A `BeanFactoryPostProcessor` runs once, before any ordinary bean is created, and changes the `BeanDefinition`, the
blueprint of a bean (class, scope, property values). It is the hook for changing the application's configuration in
code before Spring builds anything: change scopes, change property values, or add new beans (through its
sub-interface `BeanDefinitionRegistryPostProcessor`). Spring's own config is built on it:
`ConfigurationClassPostProcessor` turns `@Configuration`, `@ComponentScan` and `@Bean` into blueprints, and
`PropertySourcesPlaceholderConfigurer` fills in `${...}` placeholders.

```java
@Component
class LazyReportBeans implements BeanFactoryPostProcessor {
  @Override
  public void postProcessBeanFactory(ConfigurableListableBeanFactory factory) {
    for (String name : factory.getBeanDefinitionNames()) {
      if (name.startsWith("report")) {
        factory.getBeanDefinition(name).setLazyInit(true);   // changes the blueprint; the bean does not exist yet
      }
    }
  }
}
```

If you write one, declare its `@Bean` method `static`, and do not pull other beans into it. Anything it pulls in is
created before any `BeanPostProcessor` exists, so it gets no proxies and no `@Autowired` processing.

A [`BeanPostProcessor`](#what-is-the-primary-purpose-of-a-beanpostprocessor) runs for every bean after it is created
and changes or wraps the object, for example by returning a proxy.

</details>

### Why must a `BeanFactoryPostProcessor` `@Bean` method be `static`?
<details><summary>Show answer</summary>

```java
@Configuration
class AppConfig {
  @Value("${app.name}") String name;   // stays null

  @Bean   // not static: AppConfig must be created before any BeanPostProcessor exists
  PropertySourcesPlaceholderConfigurer placeholders() {
    return new PropertySourcesPlaceholderConfigurer();
  }
}
```

- `BeanFactoryPostProcessor`s run before ordinary beans. A non-static `@Bean` method needs an `AppConfig` object, so
  Spring creates `AppConfig` that early — before the post-processors that handle `@Autowired` and `@Value` exist.
- `AppConfig` is left with its `@Autowired` and `@Value` fields unset; Spring logs a warning about it.
- A `static` method can be called without creating `AppConfig` at all.

A `static` method lets the post-processor exist before its config class does.

</details>

### Who reads `@Configuration` classes?
<details><summary>Show answer</summary>

- `ConfigurationClassPostProcessor` — a `BeanDefinitionRegistryPostProcessor` (a `BeanFactoryPostProcessor` that may
  also add definitions). It runs first, reads `@Configuration`, `@ComponentScan`, `@Import` and `@Bean`, and registers
  a bean definition for each bean it finds.
- It also sets up the CGLIB subclass for
  [full-mode](1.1_DI_and_Configuration.md#one-bean-method-calls-another--same-instance) `@Configuration` classes.

Java config is itself handled by a post-processor that turns annotations into bean definitions.

</details>

### Init callbacks — in what order?
<details><summary>Show answer</summary>

- `@PostConstruct` → `InitializingBean.afterPropertiesSet()` → `initMethod` (`@Bean(initMethod = "...")`).
- `@PostConstruct` comes first because a post-processor (`CommonAnnotationBeanPostProcessor`) calls it in the
  before-init step; the other two are the init step itself.
- If two of them name the same method, it runs once.

Annotation, then interface, then config.

</details>

### Which init callback should you use?
<details><summary>Show answer</summary>

- `@PostConstruct` — a standard Jakarta annotation, no Spring interface in your class. The default.
- `initMethod` — for classes you can't change (third-party).
- `InitializingBean` — ties the class to Spring; mostly used inside Spring itself.

Annotate your own classes; configure the init method for others'.

</details>

### `@PostConstruct` silently ignored — why?
<details><summary>Show answer</summary>

- The annotation comes from the wrong package. Spring 6 and Boot 3 look for `jakarta.annotation.PostConstruct`; 
  code that still imports `javax.annotation.PostConstruct` (with the old jar on the classpath) compiles, 
  but the method may never be called. 
- The object is not a bean — it was [made with `new`](#autowired-in-an-object-made-with-new).

The annotation must be the one Spring looks for, on an object Spring made.

</details>

### Destroy callbacks — in what order?
<details><summary>Show answer</summary>

- `@PreDestroy` → `DisposableBean.destroy()` → `destroyMethod`.
- They run when the context closes, for singletons —
  [prototypes get none](1.3_Scopes.md#what-happens-to-a-prototype-after-spring-hands-it-out).

Same order as init: annotation, interface, config.

</details>

### When do destroy callbacks not run?
<details><summary>Show answer</summary>

- The process is killed hard — `kill -9`, a crash, power loss — so no Java code runs.
- Plain Spring with no `context.close()` and no shutdown hook — the JVM exits without closing the context. 
  Spring Boot registers the shutdown hook for you.
- Prototype beans — Spring doesn't keep track of them.

Destroy callbacks need an orderly close of the context.

</details>

### Why was `close()` called on a bean you never set up for it?
<details><summary>Show answer</summary>

- For a `@Bean` method, `destroyMethod` defaults to "inferred": Spring calls a public no-argument `close()` or
  `shutdown()` method if the class has one.
- So a pool or client returned from a `@Bean` is closed at shutdown — usually wanted, but wrong for an object someone
  else owns, such as one looked up from JNDI or shared with another context.

`@Bean` guesses the destroy method — and closes what it finds.

</details>

### In what order are beans destroyed?
<details><summary>Show answer</summary>

- A bean is destroyed before the beans it depends on, so during its `@PreDestroy` its dependencies still work.
- `@DependsOn("x")` adds an order Spring can't see from injection: the bean is created after `x` and destroyed before it.

Dependents go first, so nothing loses a dependency while it is still running.

</details>
