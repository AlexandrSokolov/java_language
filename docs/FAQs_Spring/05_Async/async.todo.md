Короткий ответ: знания Java Concurrency нужны полностью. Spring не заменяет JDK-экзекьюторы, он их оборачивает. Всё поведение под нагрузкой остаётся JDK-шным, Spring добавляет только управление.

**Что внутри.** `ThreadPoolTaskExecutor` — это обёртка над обычным `ThreadPoolExecutor`, и через `getThreadPoolExecutor()` можно достать его в чистом виде. Порядок core → очередь → max → reject — это логика `ThreadPoolExecutor`, Spring её не трогает. Политики отказа те же JDK-шные классы. `waitForTasksToCompleteOnShutdown` — это просто выбор между `shutdown()` и `shutdownNow()`. `Future`, который ты получаешь, — обычный JDK-шный `Future` со всей семантикой `cancel` и `get`. Так же устроен `ThreadPoolTaskScheduler`: внутри обычный `ScheduledThreadPoolExecutor`. Так что сайзинг, очереди, отказы, семантика остановки, прерывания — всё это знание из JCiP, и в Spring оно работает один в один.

**Зачем тогда свой интерфейс.** Причина в основном историческая. `TaskExecutor` появился, когда Spring ещё поддерживал Java 1.4, где не было `java.util.concurrent`. Он прятал разные реализации за одним методом: backport-библиотеку, простые потоки, `WorkManager` в WebSphere и WebLogic, где самому создавать потоки было запрещено. Когда Java 5 стала минимумом, `TaskExecutor` просто начал расширять `Executor`. Сегодня это скорее маркер «экзекьютор, которым управляет Spring», чем отдельная абстракция.

**Почему интерфейс такой узкий.** Это сознательно, а не потеря. Отличие от `ExecutorService` в том, что из интерфейса убрано управление жизненным циклом: `shutdown`, `awaitTermination`, `isShutdown`. В Spring экзекьютор — общий бин, и его останавливает контейнер при закрытии контекста. Если бизнес-код, которому заинжектили общий пул, вызовет `shutdown()`, он убьёт пул для всех остальных. Поэтому коду, который только отправляет задачи, даётся только «отправить». Так же нет `invokeAll` и `invokeAny`. Их место занял `CompletableFuture`: `allOf`, `anyOf`, композиция. Аналога `ExecutorCompletionService` в Spring нет. Если он нужен, берёшь JDK-шный и кладёшь поверх `getThreadPoolExecutor()`: ничего не потеряно, просто не продублировано.

**Что Spring добавляет:**
- Жизненный цикл бина: пул создаётся при старте контекста и останавливается при его закрытии, с ожиданием задач. В чистом JDK про `shutdown` легко забыть, и приложение не завершится.
- Настройку через сеттеры и properties вместо конструктора на семь аргументов.
- `TaskDecorator` — обёртку задачи в момент отправки, на потоке вызывающего. В JDK есть `beforeExecute` и `afterExecute`, но они работают уже на потоке пула и не видят контекст вызывающего, а значит не могут перенести MDC или security context.
- Перевод `RejectedExecutionException` в `TaskRejectedException`.
- Имена потоков через префикс.
- Метрики через Boot.
- В `SimpleAsyncTaskExecutor` — лимит одновременных задач и переключатель на виртуальные потоки.
- `TaskScheduler` поверх scheduled-экзекьютора с cron-выражениями и `Trigger`. В JDK есть только fixed rate и fixed delay.

**Переходы между мирами.** Можно положить в контекст обычный JDK `ExecutorService` как бин, и `@Async` с ним заработает: Spring сам обернёт его адаптером (`TaskExecutorAdapter`, `ConcurrentTaskExecutor`). Есть и обратный адаптер, `ExecutorServiceAdapter`. Но с JDK-пулом теряется автоматическая аккуратная остановка, если не настроить её самому.

**Итоговая модель:** JDK — это двигатель, Spring — крепление двигателя в машине. Как пул ведёт себя под нагрузкой, решает JDK. Кто его создаёт, настраивает, останавливает и какой контекст переносится в задачу, решает Spring.

**По карточкам.** Здесь видно минимум две оси, и в одну карточку их лучше не сливать:
- «Что Spring убирает из `ExecutorService` и почему» — жизненный цикл уходит контейнеру, `invokeAll` уходит в `CompletableFuture`.
- «Что Spring добавляет поверх JDK-пула» — lifecycle, decorator, scheduler с cron, адаптеры.

Можно добавить третью, короткую: «Что остаётся чисто JDK» — сайзинг, очередь, отказы, семантика остановки. Она как раз отвечает на твой страх, что знания не нужны. Нынешнюю карточку про иерархию интерфейсов я бы тогда сделал роутером на эти две-три.
