## Which executor

### Which executor runs `@Async` without Boot?
<details><summary>Show answer</summary>

Lookup when `@Async` names no executor:

- `AsyncConfigurer.getAsyncExecutor()`, if you implement it — wins over everything below;
- else the only bean of type `TaskExecutor`;
- else, with several, the bean named `taskExecutor`;
- else a new `SimpleAsyncTaskExecutor`.

Handle: your configurer, else the one `TaskExecutor`, else the name `taskExecutor`, else a thread per call.

</details>

### Why is the plain Spring default risky?
<details><summary>Show answer</summary>

- `SimpleAsyncTaskExecutor` is not a pool: a new thread per task, and the thread dies after. No limit by default.
- A spike of 10,000 calls → 10,000 platform threads, each with its own stack →
  `OutOfMemoryError: unable to create native thread`, or the machine slows to a crawl.
- Also: no queue, no thread reuse, no metrics.
- Fix: define a `ThreadPoolTaskExecutor`, or at least set `setConcurrencyLimit(n)`.

Handle: no pool means no limit — and the limit is what keeps you alive in a spike.

</details>

### Which executor does Spring Boot give you?
<details><summary>Show answer</summary>

- A `ThreadPoolTaskExecutor` bean named `applicationTaskExecutor` (alias `taskExecutor`); `@Async` picks it.
- Defaults: core 8, queue unbounded, max unbounded (never reached), keep-alive 60 s, thread prefix `task-`.
- Tune with `spring.task.execution.pool.*` (`core-size`, `max-size`, `queue-capacity`, `keep-alive`) and
  `spring.task.execution.thread-name-prefix`.

Handle: Boot gives a real pool, but with an unbounded queue it is 8 fixed threads with an endless backlog.

</details>

### When does Boot's executor back off?
<details><summary>Show answer</summary>

- The auto-configured executor is created only if you have no `Executor` bean. Define any `Executor` bean — even for
  some other job — and `applicationTaskExecutor` is gone.
- `@Async` then uses the plain Spring lookup. If your bean is not a `TaskExecutor`, or there are several and none is
  named `taskExecutor`, you are back on `SimpleAsyncTaskExecutor`.
- An `AsyncConfigurer` with `getAsyncExecutor()` sets the `@Async` executor directly, whatever beans exist.
- Newer Boot versions changed this rule (property `spring.task.execution.mode`).
  <!-- UNVERIFIED: exact back-off rule and the Boot version (3.4/3.5?) where it changed -->

Handle: add one `Executor` bean and Boot's pool may vanish without a word — check which one `@Async` really uses.

</details>

### `TaskExecutor` vs `Executor` vs `AsyncTaskExecutor`?
<details><summary>Show answer</summary>

- `Executor` (JDK) — `execute(Runnable)`.
- `TaskExecutor` (Spring) — extends `Executor`, same method. Marks executors Spring should look for.
- `AsyncTaskExecutor` — adds `submit(...)` returning a `Future`, and `submitCompletable(...)`. Needed for `@Async`
  methods that return a future.
- `ThreadPoolTaskExecutor` — Spring bean around the JDK `ThreadPoolExecutor`; adds bean lifecycle (start, shutdown),
  `TaskDecorator`, settings as properties.

Handle: each level adds one thing — run it → Spring manages it → it gives back a result.

</details>

## Pool under load

### In what order does a pool grow?
<details><summary>Show answer</summary>

A new task arrives:

- fewer than core threads → start a new thread, even if others are idle;
- else → put the task in the queue;
- queue full → start an extra thread, up to max;
- at max with a full queue → reject.

```java
ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
ex.setCorePoolSize(4);
ex.setQueueCapacity(100); // filled before any thread above core starts
ex.setMaxPoolSize(10);
ex.setThreadNamePrefix("report-");
ex.initialize();
```

- The surprise: when the 4 core threads are busy, new tasks wait in the queue. Extra threads start only after 100 tasks
  are waiting.

Handle: queue first, extra threads last — the pool grows only when the queue is full.

vs. [Request pool is full — what happens?](../../FAQs_Concurrency/6_Unblocking_Threads_for_Scale/6.01_Blocking_vs_Non-Blocking_IO.md#request-pool-is-full--what-happens)

Пул @Async (ThreadPoolTaskExecutor). Внутри обычный JDK-шный ThreadPoolExecutor, и порядок у него JDK-шный: core → очередь → max → reject. Твоё замечание про очередь справедливо: в Boot очередь по умолчанию неограниченная, поэтому она никогда не заполнится, и до max дело не дойдёт. Об этом следующая карточка, «Why does max size often do nothing?». Карточка про рост описывает общее правило, а дефолт Boot — это частный случай, при котором шаги 3 и 4 никогда не наступают.

Пул Tomcat. Это не JDK-шный пул и не fixed thread pool. У Tomcat свой класс org.apache.tomcat.util.threads.ThreadPoolExecutor и своя очередь TaskQueue, которая переворачивает порядок. Пока потоков меньше maxThreads (200), очередь отказывается брать задачу, и пул создаёт новый поток. В очередь задачи идут, только когда заняты все 200 потоков. То есть порядок такой: сначала потоки (от minSpareThreads = 10 до 200), потом очередь. Лишние потоки умирают после простоя. Это ближе к cached pool, только с потолком 200 и очередью после него.

Почему Tomcat так сделал: для веб-сервера ждать в очереди при свободной ёмкости плохо, поэтому сначала расти, потом ждать. Для фоновых задач JDK выбирает обратное: копить в очереди и экономить потоки.

Чего не хватает в карточке Tomcat. Шага «до 200 потоков пул растёт, и только потом идёт в очередь». Она начинается с момента, когда пул уже полон, и из-за этого похоже, что пул фиксированный. Отсюда и твоя модель «fixed thread pool».


1. Пул Spring @Async (Карточка 1: ThreadPoolTaskExecutor)
   Цель: Фоновые задачи, шедулеры, асинхронные методы внутри твоего кода.Чей это код: Чистый Spring, обертка над стандартным JDK java.util.concurrent.ThreadPoolExecutor.

Здесь работает классическая, базовая логика Java (JDK):

Заполняем Core потоки.

Когда Core заняты, складываем задачи в Очередь (Queue).

Очередь должна заполниться ЦЕЛИКОМ, и только тогда пул начинает создавать Дополнительные потоки (до Max).

Если Max достигнут и очередь полна — отказ (Reject).

Смысл такого дизайна: Экономия ресурсов процессора. JDK старается до последнего не создавать новые потоки, заставляя задачи ждать в очереди.

2. Пул веб-сервера Tomcat (Карточка 2: Request pool)
   Цель: Обработка входящих HTTP/REST запросов.Чей это код: Внутренности Apache Tomcat (org.apache.tomcat.util.threads.ThreadPoolExecutor).

Tomcat не использует стандартную логику JDK, потому что для веб-запросов ждать в очереди, пока сервер жадничает и не создает потоки — это смерть для Latency (времени ответа). Tomcat намеренно "хакает" стандартное поведение Java пула.

Логика Tomcat:

Заполняем Core потоки (по умолчанию 10).

Создаем Дополнительные потоки (сразу до Max, по умолчанию 200).

Только когда заняты все 200 потоков, новые запросы начинают копиться в Очереди JVM (Worker Queue).

Когда Worker Queue упирается в лимит открытых соединений maxConnections (по умолчанию 8192) — Tomcat перестает принимать TCP-соединения.

Начинает заполняться очередь на уровне операционной системы acceptCount (по умолчанию 100).

Когда заполнена очередь ОС — Connection Refused.

Как Tomcat обманывает JDK:
Tomcat использует собственную реализацию очереди — TaskQueue (наследуется от LinkedBlockingQueue). Когда стандартный JDK-пул пытается положить HTTP-запрос в очередь (метод offer()), TaskQueue смотрит: "Ага, потоков сейчас меньше, чем Max (200)?". Если меньше, она возвращает false (притворяется, что очередь полна!). JDK-пул видит, что очередь "полна", и по своим же правилам вынужден немедленно создать новый поток.

Почему тебе казалось, что там Fixed Thread Pool
Для Tomcat дефолтные настройки (Max 200) в связке с его "хаком" очереди приводят к тому, что под нагрузкой он моментально раздувается до 200 потоков и держит их. Снаружи это действительно выглядит так, как будто это просто огромный FixedThreadPool на 200 потоков, перед которым стоит безлимитная очередь (ограниченная только сетевыми лимитами maxConnections).

Итог:

Карточка 1 (Spring @Async): Поведение — Core -> Queue -> Max. Очередь имеет жесткий размер (настраивается).

Карточка 2 (Tomcat HTTP): Поведение — Core -> Max -> Queue -> OS Queue. Очередь фактически безлимитна на уровне JVM, но ограничена сетевыми лимитами (8192 соединения).

</details>

### Why does max size often do nothing?
<details><summary>Show answer</summary>

- Default queue capacity is `Integer.MAX_VALUE` — in plain `ThreadPoolTaskExecutor` and in Boot. The queue never
  fills, so extra threads never start; the pool stays at core.
- Under load: tasks wait longer and longer, queued tasks hold their arguments in memory → in the end
  `OutOfMemoryError`, with no rejection to warn you.
- Fix: a bounded queue, sized from how long a task may wait; or core = max with a bounded queue.

Handle: unbounded queue = max size is dead, and overload shows up as memory, not as errors.

</details>

### What happens when the pool is full?
<details><summary>Show answer</summary>

- Default `AbortPolicy`: `ThreadPoolTaskExecutor` throws `TaskRejectedException` (wraps `RejectedExecutionException`).
- It is thrown in the caller, at the call to the `@Async` method — even for `void`. It never reaches
  [the async error handler](5.1_Async_Methods.md#where-does-a-void-methods-exception-go).
- Other policies:
  - `CallerRunsPolicy` — the caller runs the task itself;
  - `DiscardPolicy` — drop the new task, silently;
  - `DiscardOldestPolicy` — drop the oldest queued task, silently.
- Set with `ex.setRejectedExecutionHandler(...)`.

Handle: reject loudly, unless losing the task is truly fine.

</details>

### How does `CallerRunsPolicy` slow producers down?
<details><summary>Show answer</summary>

- A rejected task runs on the thread that submitted it — e.g. the Tomcat request thread.
- That thread is now busy, so it can't take or submit more work. Producers slow down to the speed of the pool —
  backpressure without dropping tasks.
- Costs:
  - the call becomes synchronous — the HTTP request waits as long as the task takes;
  - the task runs with the caller's ThreadLocals (transaction, security) — different behavior from the pool path;
  - after the executor is shut down, the task is dropped silently.

Handle: the producer pays for overload with its own time.

</details>

### What do keep-alive and core timeout control?
<details><summary>Show answer</summary>

- Threads above core die after being idle for keep-alive (default 60 s) → the pool shrinks back to core.
- `setAllowCoreThreadTimeOut(true)` → core threads die too → the pool can drop to zero; the next task pays for starting
  a thread. Good for pools used rarely.

Handle: keep-alive decides how fast a pool gives threads back.

</details>

### How big should an `@Async` pool be?
<details><summary>Show answer</summary>

- CPU work: about the number of cores; more threads only add switching.
- Blocking IO: more threads — roughly cores × (1 + wait time / compute time).
- Cap it by what sits behind it: 50 threads on a DB pool of 10 connections → 40 threads wait for a connection.
- Formulas and measuring: [sizing a pool](../../FAQs_Concurrency/4_Structuring_Concurrent_Tasks/4.5_Applying_Thread_Pools.md).

Handle: size by what the task waits for, and by the smallest resource behind it.

</details>

## Separate executors

### Why one executor per kind of task?
<details><summary>Show answer</summary>

- One shared pool: slow report tasks (minutes) take every thread; email tasks (milliseconds) wait in the queue behind
  them → emails late, timeouts.
- Separate pools (**bulkhead** — walls between compartments): slow work can fill only its own pool; a problem stays
  inside it.
- Also buys: sizing per kind (IO vs CPU), metrics per pool, rejection policy per pool.
- Costs: more threads in total, idle capacity in each pool, more config. Don't split without a real difference in
  speed or importance.

Handle: tasks that differ in speed or importance get their own pool.

</details>

### How does a method pick its executor?
<details><summary>Show answer</summary>

```java
@Bean
ThreadPoolTaskExecutor reportExecutor() { ... }

@Bean
ThreadPoolTaskExecutor mailExecutor() { ... }

@Async("reportExecutor") // bean name or @Qualifier value
public CompletableFuture<Report> build(long id) { ... }
```

- `@Async("...")` on a class applies to all its methods.
- `@Async` with no name uses the default. With several `TaskExecutor` beans and none named `taskExecutor`, the default
  is `SimpleAsyncTaskExecutor` — so name one `taskExecutor` or set it in `AsyncConfigurer`.
- In Boot, defining these beans also removes `applicationTaskExecutor`.
- A wrong name fails at the first call, not at startup.
  <!-- UNVERIFIED: executor qualifier is resolved lazily on first invocation -->

Handle: name the pool on the method, and check the unnamed default is still the one you think.

</details>

### How do you watch a pool's health?
<details><summary>Show answer</summary>

- `ThreadPoolTaskExecutor`: `getActiveCount()`, `getPoolSize()`, `getQueueSize()`; completed tasks via
  `getThreadPoolExecutor().getCompletedTaskCount()`.
- Boot with Actuator publishes executor metrics (`executor.active`, `executor.queued`, `executor.pool.size`, ...).
  <!-- UNVERIFIED: exact metric names and which executor beans Boot binds -->
- Alert on: queue size growing, active = max for a long time, rejections.
- Set a thread name prefix per pool — thread dumps and logs then show which pool a thread belongs to.

Handle: queue length is the first sign of overload.

</details>

## Virtual threads

### How do you turn on virtual threads for `@Async`?
<details><summary>Show answer</summary>

- Boot 3.2+ on Java 21+: `spring.threads.virtual.enabled=true` → the auto-configured executor becomes a
  `SimpleAsyncTaskExecutor` on virtual threads; pool properties are ignored.
- Plain Spring 6.1+: `SimpleAsyncTaskExecutor` with `setVirtualThreads(true)`, or `VirtualThreadTaskExecutor`.
- Your own `ThreadPoolTaskExecutor` beans are not changed by the property.

Handle: one property switches Boot's executor; your own pools stay as they are.

</details>

### Why not pool virtual threads?
<details><summary>Show answer</summary>

- Pools exist because platform threads are costly to create and hold a lot of memory. Virtual threads are cheap (a few
  KB, fast to create) → one per task, thrown away after.
- A pool of them gives nothing and brings back old limits: a fixed size caps how many run at once, and a reused thread
  keeps ThreadLocals from the previous task.

Handle: pool the costly resource, not the cheap thread.

</details>

### How do you limit load on a downstream system?
<details><summary>Show answer</summary>

- With a pool, its size was also a hidden limit on DB or API calls. With a thread per task, 10,000 tasks =
  10,000 calls at once.
- Put the limit on the resource directly:
  - `SimpleAsyncTaskExecutor.setConcurrencyLimit(n)` (Boot: `spring.task.execution.simple.concurrency-limit`) — submit
    blocks while n tasks run;
  - a `Semaphore` around the call;
  - the DB connection pool, which caps DB calls anyway.
- Separate executors still make sense — one limit per downstream system. The bulkhead stays; it is now a limit, not a
  pool size.

Handle: virtual threads remove the thread limit, so you add the resource limit back yourself.

</details>

### When do virtual threads not help?
<details><summary>Show answer</summary>

- CPU work: still limited by the number of cores; more threads give nothing.
- Pinning: a virtual thread that blocks inside `synchronized` holds its carrier (platform) thread — fixed in JDK 24
  (JEP 491); native calls still pin. With few carriers, everything stalls.
- ThreadLocal caches (buffers, formatters): no thread reuse → created per task; with many threads, memory grows.

Handle: virtual threads help only when tasks mostly wait.

</details>

## Shutdown

### What happens to running tasks on SIGTERM?
<details><summary>Show answer</summary>

- Kubernetes sends SIGTERM → JVM shutdown hook → Spring closes the context → `ThreadPoolTaskExecutor` is destroyed.
- Default `waitForTasksToCompleteOnShutdown = false` → `shutdownNow()`: running tasks are interrupted, queued tasks are
  dropped — they never run, and nothing reports it.
- A task that ignores the interrupt keeps running until the JVM exits, or until Kubernetes sends SIGKILL after the
  grace period (default 30 s).

Handle: by default shutdown drops the queue and interrupts the rest.

</details>

### How do you let tasks finish on shutdown?
<details><summary>Show answer</summary>

```java
ex.setWaitForTasksToCompleteOnShutdown(true); // shutdown(): no new tasks, finish queued and running
ex.setAwaitTerminationSeconds(20);            // context close waits up to 20 s
```

- The wait flag alone does not block context close — the JVM may still exit while tasks run. You need both.
- Keep the wait shorter than Kubernetes `terminationGracePeriodSeconds` minus other shutdown steps, or SIGKILL comes
  anyway.
- Boot: `spring.task.execution.shutdown.await-termination=true`,
  `spring.task.execution.shutdown.await-termination-period=20s`.
- Tasks that must never be lost don't belong only in memory — use a durable queue or an outbox table.

Handle: wait, but with a limit shorter than the platform's kill timer.

</details>

### How does shutdown fit the context lifecycle?
<details><summary>Show answer</summary>

- Problem: beans are destroyed in dependency order. A task still running may need a `DataSource` or client that is
  already closed → it fails during shutdown.
- Spring 6.1: `ThreadPoolTaskExecutor` takes part in the context lifecycle. On close it stops taking tasks and waits
  early, in its lifecycle phase, before other beans are destroyed. Settings: `setAcceptTasksAfterContextClose`,
  `setStrictEarlyShutdown`, `setPhase`.
  <!-- UNVERIFIED: exact 6.1 lifecycle behavior and setting names -->
- `server.shutdown=graceful` stops new HTTP requests first → fewer new tasks arrive.

Handle: stop taking tasks, let them drain, then destroy what they use.

</details>
