# Async Methods

- `@EnableAsync` and `@Async` — run through a [proxy](../02_AOP_and_Transactions/2.1_Proxies_and_AOP.md);
  self-invocation runs the method in the same thread.
- Return types — `void`, `CompletableFuture`.
- Lost exceptions from `void` methods — `AsyncUncaughtExceptionHandler`.
- What doesn't follow to the new thread — transaction, security context;
  [context propagation](../../FAQs_Concurrency/3_JDK_Concurrency_Libraries/3.7_Context_Propagation.md).

### What governs `@Async` methods?
<details><summary>Show answer</summary>

Trigger: **the call returns at once and the work runs on another thread — so the result, the error and the thread's
context each need their own way back.**

- [Return types](#which-return-types-does-async-allow) — how the caller gets the result.
- [Errors](#where-does-a-void-methods-exception-go) — where an exception ends up.
- [Thread context](#why-doesnt-the-callers-transaction-follow) — what stays behind on the caller's thread.
- [Tests](#how-do-you-test-an-async-method) — how a test waits for the work.

Which threads run the work: [task executors](5.2_Task_Executors.md).

</details>

## Return types

### Which return types does `@Async` allow?
<details><summary>Show answer</summary>

- `void` — fire and forget. The caller gets nothing back, not even errors.
- `CompletableFuture<T>` — the default choice. The caller can wait, chain the next step, or react to failure.
- `Future<T>` — still works, but only a blocking `get()`; no chaining.
- `ListenableFuture<T>` — deprecated since Spring 6.0; use `CompletableFuture`.

Handle: the caller gets back only what fits in a future — or nothing.

</details>

### What if the return type is not allowed?
<details><summary>Show answer</summary>

```java
@Async
public Report build(long id) { ... } // the proxy has no Report to give back yet
```

- Spring 5.x: the task is still submitted, the caller gets `null`. Silent bug — the `NullPointerException` shows up
  later, far from the cause.
- Newer versions may reject the type with `IllegalArgumentException` at call time.
  <!-- UNVERIFIED: exact Spring version where the non-Future return type started to throw -->

Handle: a plain value can't be async — the caller would need it before it exists.

</details>

### How does the method hand back a value?
<details><summary>Show answer</summary>

```java
@Async
public CompletableFuture<Report> build(long id) {
  Report r = heavyWork(id);                // plain blocking code, on the pool thread
  return CompletableFuture.completedFuture(r); // wrap the value at the end
}
```

- For a failure: just throw, or return `CompletableFuture.failedFuture(ex)`.
- The caller gets a different future — Spring's own. It completes when the method's future completes.
- Spring reads your future with `get()` on the pool thread. If you return a future that is not done yet (e.g. from a
  non-blocking HTTP client), the pool thread blocks until it is. Don't put `@Async` on code that is already async.
- `AsyncResult` — deprecated in Spring 6; use `completedFuture`.

Handle: inside the method write normal blocking code and wrap the value at the end.

</details>

### When is `void` the wrong choice?
<details><summary>Show answer</summary>

- With `void` the caller can't know: done? failed? how long did it take? Errors go to a global handler, not to the code
  that started the task.
- Fine for real fire-and-forget: nobody acts on the outcome (send a metric, warm a cache), and a log line on failure is
  enough.
- Wrong when the caller must react: retry, report status, wait for several tasks, put the result into a response — or
  when a test must wait for the work.
- `CompletableFuture<Void>` costs nothing and keeps all these options open.

Handle: if anyone cares about the outcome, return a future.

</details>

### `@Async` vs `supplyAsync`?
<details><summary>Show answer</summary>

Both run code on another thread. The difference is who decides that it runs async.

- `@Async` — set on the method.
  - **Buys:** executor picked by config or by name; call sites stay plain.
  - **Costs:** works only through the Spring proxy (no same-class calls, no private methods); the call site doesn't
    show that the work is async.
- `CompletableFuture.supplyAsync(task, executor)` — set at the call site.
  - **Buys:** visible where it happens; works anywhere, also inside one class; easy to fan out several tasks and join.
  - **Costs:** you must pass the executor. Without it the task runs on `ForkJoinPool.commonPool()` — shared, small
    (cores − 1), bad for blocking IO.

Discriminator: is "runs in the background" a property of the method (→ `@Async`) or a choice of one caller
(→ `supplyAsync`)?

</details>

## Errors

### Where does a `void` method's exception go?
<details><summary>Show answer</summary>

- The interceptor catches it on the pool thread and passes it to `AsyncUncaughtExceptionHandler`.
- The default, `SimpleAsyncUncaughtExceptionHandler`, logs it at ERROR level and drops it.
- The pool thread does not die. The caller has already returned and never learns about the error. No retry, no alert —
  unless someone watches the logs.

Handle: in a `void` async method an error ends as a log line unless you install a handler.

</details>

### How do you plug in your own handler?
<details><summary>Show answer</summary>

```java
@Configuration
@EnableAsync
class AsyncConfig implements AsyncConfigurer {

  @Override
  public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
    return (ex, method, params) -> {
      log.error("Async call failed: {}", method.getName(), ex);
      alerts.notify(method, ex); // metric, alert, dead-letter store
    };
  }
}
```

- One handler for all `void` async methods. It gets the exception, the method and the arguments.
- Methods that return a future never reach it.
- It is global. For per-method handling, catch inside the method.

Handle: one global hook, for `void` methods only.

</details>

### Where does a future method's exception go?
<details><summary>Show answer</summary>

- The interceptor sees a future return type and completes Spring's future with the exception. The global handler is
  not called — the error already has an owner: the caller.
- If nobody reads the future, the error is lost without a trace — not even a log line. Worse than `void`.

Handle: with a future, the error lives inside the future — someone must read it.

</details>

### How does the caller handle a failed future?
<details><summary>Show answer</summary>

- Blocking: `join()` throws `CompletionException`, `get()` throws `ExecutionException`. The real exception is
  `getCause()`.
- Non-blocking:
  - `exceptionally(ex -> fallback)` — replace the failure with a value;
  - `handle((value, ex) -> ...)` — one function for both paths;
  - `whenComplete(...)` — side effect only (log), the failure passes on.
- Inside callbacks `ex` may be a `CompletionException` — unwrap it before checking the type.

```java
service.build(id)
    .orTimeout(5, TimeUnit.SECONDS)
    .exceptionally(ex -> Report.empty()); // ex may be wrapped
```

Handle: when you wait, unwrap the cause; when you chain, handle it in the next step.

</details>

## Thread context

### Why doesn't the caller's transaction follow?
<details><summary>Show answer</summary>

- Spring keeps the transaction (and its DB connection) in a ThreadLocal of the caller's thread. The pool thread has its
  own, empty one.
- So the async code is not in the caller's transaction: its own connection, no common rollback.
- Common bug: the caller saves an entity, calls the async method, then commits. The async thread queries before the
  commit and finds nothing (or old data).
- Fixes:
  - start the async work after commit — `@TransactionalEventListener(phase = AFTER_COMMIT)` plus `@Async`;
  - pass IDs, not managed entities — lazy loading fails, the session belongs to the caller.

Handle: transaction = ThreadLocal; new thread = no transaction, and the caller's data may not be committed yet.

</details>

### `@Async` plus `@Transactional` — what happens?
<details><summary>Show answer</summary>

- Both on one method: Spring puts the async step before the other proxy steps. The call first moves to the pool
  thread, then the transaction starts there.
- Result: a new transaction per call, on the pool thread, committed when the method ends. This works.
- It never joins the caller's transaction — `REQUIRED` finds none on the new thread.
  <!-- UNVERIFIED: order comes from AsyncAnnotationBeanPostProcessor setting beforeExistingAdvisors = true -->

Handle: async first, transaction second — each call gets its own transaction.

</details>

### Why is the security context empty?
<details><summary>Show answer</summary>

- `SecurityContextHolder` keeps the `Authentication` in a ThreadLocal by default. The pool thread has none:
  `@PreAuthorize` on inner calls fails, audit fields show no user.
- Fix: wrap the executor — it copies the context at submit time and clears it after the task.

```java
@Override
public Executor getAsyncExecutor() {
  return new DelegatingSecurityContextAsyncTaskExecutor(pool); // copy per task
}
```

- Don't use `MODE_INHERITABLETHREADLOCAL`. It copies the context only when a thread is created. Pool threads are
  reused, so a task sees the user of whoever caused that thread to be created. A security bug.

Handle: copy per task at submit time, never per thread at creation.

</details>

### How do you carry MDC into the task?
<details><summary>Show answer</summary>

- MDC is a ThreadLocal, so log lines from the task lose the trace ID.
- A `TaskDecorator` wraps each task at submit time, still on the caller's thread:

```java
class MdcTaskDecorator implements TaskDecorator {

  @Override
  public Runnable decorate(Runnable task) {
    Map<String, String> ctx = MDC.getCopyOfContextMap(); // caller thread
    return () -> {
      if (ctx != null) MDC.setContextMap(ctx);           // pool thread
      try {
        task.run();
      } finally {
        MDC.clear(); // else it leaks into the next task on this thread
      }
    };
  }
}
```

- Install: `executor.setTaskDecorator(...)`. Spring Boot applies a `TaskDecorator` bean to its own executor.
- One decorator per executor — combine MDC, security, etc. in one, or use Spring 6.1's
  `ContextPropagatingTaskDecorator`, which copies every registered ThreadLocal through
  [Micrometer context propagation](../../FAQs_Concurrency/3_JDK_Concurrency_Libraries/3.7_Context_Propagation.md).

Handle: capture on submit, restore on run, clear after.

</details>

### Why does a request-scoped bean fail?
<details><summary>Show answer</summary>

- Request-scoped beans and `RequestContextHolder` are bound to the request thread. On the pool thread you get
  `IllegalStateException: No thread-bound request found`.
- Even if you copy them over, the request may be finished and its objects reused by Tomcat when the task runs.
- Fix: read what you need (user ID, a header) in the caller and pass it as method arguments.

Handle: the request ends, the task keeps running — pass values, not the request.

</details>

## Tests

### How do you test an `@Async` method?
<details><summary>Show answer</summary>

- Call it through the Spring bean. A direct call runs synchronously and the test proves nothing about async behavior.
- Future return type: `get(5, SECONDS)` or `orTimeout(...).join()`, then assert. Always with a time limit.
- `void`: wait for the side effect with Awaitility — `await().atMost(5, SECONDS).untilAsserted(...)`. Never
  `Thread.sleep`.
- A `SyncTaskExecutor` in test config runs the task on the test thread — simple, but it hides context loss and races.
  Use it for logic tests; keep at least one test on a real pool.

Handle: wait with a limit, never sleep, and know what a sync executor hides.

</details>
